族谱与选型

⬅ 前置依赖模块 1：对象在堆、数组是对象；模块 2：数组定长 vs 集合动态；模块 3：equals/hashCode 分桶原理（本模块直接应用）。

1.1 两大族谱高频★★★

Collection 与 Map 是两棵独立的树结构
Collection（单值，继承 Iterable → 可 foreach）          Map（键值对，【不继承 Collection】）
├─ List（有序、可重复、有下标）                       ├─ HashMap     无序  ★面试核心
│   ├─ ArrayList   数组，随机访问快                   ├─ LinkedHashMap  HashMap + 双向链表（有序）
│   ├─ LinkedList  双向链表（也实现 Deque）           ├─ TreeMap     按 key 排序（红黑树）
│   └─ Vector      老古董，方法全 synchronized        └─ ConcurrentHashMap 线程安全 ★
├─ Set（不重复）
│   ├─ HashSet     底层就是 HashMap（值当 key）      队列族（Collection 分支）
│   ├─ LinkedHashSet                                  ├─ Queue      FIFO 队列
│   └─ TreeSet     底层 TreeMap                       ├─ Deque      双端队列（ArrayDeque/LinkedList）
└─ Queue/Deque                                         └─ PriorityQueue 堆（小顶堆）

⚠ 高频陷阱：Map 不是 Collection 的子接口！它是平级的另一棵树
⚠ 集合只能存引用类型 —— List<int> 编译错误，List<Integer> 装箱（模块 1 讲过为什么）

1.2 选型速查表★★

List 三兄弟与 ArrayList 扩容

2.1 ArrayList vs LinkedList vs Vector高频★★★

ArrayListLinkedListVector
底层Object[]（连续内存）双向链表（非连续）Object[]

2.2 ArrayList 扩容机制高频★★★

懒加载 + 1.5 倍扩容（源码要点）Java
// JDK 8 ArrayList 关键字段
private static final int DEFAULT_CAPACITY = 10;   // 默认容量 10
transient Object[] elementData;                   // 真正存元素的数组
private int size;                                 // 逻辑大小（≠ 数组长度！）

// ① 懒加载：new ArrayList<>() 时 elementData = 空数组（{}，不占 10 个位置）
//    第一次 add 才真正分配长度 10 的数组 —— 避免大量空 list 浪费内存

// ② add 时容量不够 → 扩容
public boolean add(E e) {
    ensureCapacityInternal(size + 1);             // 检查容量
    elementData[size++] = e;                      // 放元素，size+1
    return true;
}
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // ★ 新容量 = 旧容量 * 1.5
    if (newCapacity < minCapacity) newCapacity = minCapacity;
    // 超过 MAX_ARRAY_SIZE 则 OOM 或请求 Integer.MAX_VALUE
    elementData = Arrays.copyOf(elementData, newCapacity);  // ★ 全量拷贝到新数组
}
// 扩容成本：O(n)（System.arraycopy 全量复制）→ 攒 add 的高频写法：
List<Integer> list = new ArrayList<>(1000_000);   // 预估容量，一次到位，避免反复扩容拷贝
追问：size 和 elementData.length 的区别？为什么 ArrayList 序列化要重写？

size 是元素个数（逻辑大小），length 是数组物理长度（含预留空位）。序列化时若直接序列化 elementData，会把预留的 null 空位也写出去浪费空间——所以 ArrayList 实现 writeObject 只写 size 个真实元素；这也是 elementData 标 transient 的原因（配合自定义序列化，而非跳过）。

HashMap put 全流程

4.1 流程图（面试口述版）超高频★★★

put(key, value) 的八步流程
put(key, value)
 │
 ① table 为空（懒加载）→ 先扩容 resize() 初始化容量 16
 │
 ② 计算 i = (n-1) & hash(key)  ← 注意：扰动后的 hash & (长度-1)，不是取模！
 │
 ③ table[i] 为空 → 直接 new Node 放进去，跳到 ⑦
 │
 ④ table[i] 非空（哈希冲突），逐个比较：
 │   ├─ key 相同（hash 相等 且 (== 或 equals)）→ 覆盖 value，返回旧值，结束
 │   ├─ 节点是 TreeNode → 走红黑树插入
 │   └─ 链表遍历到尾都没找到 → 尾插新节点
 │        └─ 插入后链长 ≥ 8？
 │             ├─ table 长度 < 64 → 先 resize()（小容量时扩容比树化划算）
 │             └─ ≥ 64 → treeifyBin() 链表转红黑树
 │
 ⑤ （结构被修改）modCount++   ← fail-fast 的依据（模块 2 讲过）
 │
 ⑥ ++size > threshold（容量×0.75）→ resize() 扩容为 2 倍
 │
 ⑦ 插入后回调 afterNodeInsertion（LinkedHashMap 钩子，LRU 用的就是它）
 │
 返回 null（新插入）或 旧 value（覆盖）

⚠ 两个细节高频被抠：
  · key 判定"相同"的标准：hash 相等 && (k1==k2 || k1.equals(k2))
    —— 正是模块 3"分桶 + 桶内 equals"两步的落地
  · null key 固定放 0 号桶（hash(null)=0），HashMap 允许一个 null key
一句话回答

put：算 hash 定桶 → 空桶直接放；冲突则桶内按"hash+equals"找 key，找到覆盖、找不到尾插；链长 8 且容量 64 才树化；size 超过 容量×0.75 就扩容翻倍。

05

扰动函数与"2 的幂"

5.1 hash 扰动函数：为什么异或 16 位超高频难点★★★

JDK 8 hash() 源码Java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    //                                            ↑ 高 16 位 异或 到 低 16 位
}

// 为什么需要扰动？—— 定位桶只用 hash 的低位：
//   index = hash & (n - 1)     // n=16 时只用最后 4 个 bit！
//
// 若不扰动：hashCode 高位差异大、低位相同（很常见）的两个对象：
//   0x87654321 → & 0xF → 0101 → 5 号桶
//   0x12344321 → & 0xF → 0101 → 5 号桶   ← 全挤一个桶！高位信息完全浪费
//
// 扰动后：把高 16 位掺进低 16 位 → 低位也携带了高位的信息 → 分布更均匀 → 冲突更少
// 为什么用 ^ 不用 | 或 &：& 偏向 0、| 偏向 1（都会损失随机性），^ 保持 0/1 均衡
// 为什么是 16：int 32 位，对半异或一次，性能与效果的平衡（再扰动收益递减）

5.2 容量为什么必须是 2 的幂超高频难点★★★

& 与 % 的等价性Java
// 定位桶的两种数学等价写法（仅当 n 是 2 的幂）：
hash % n  ==  hash & (n - 1)

// n = 16（二进制 10000）时 n-1 = 15（01111）：
//   hash & 15 = 只保留 hash 的低 4 位 = hash 对 16 取模 ✓
//   （二进制低位天然是"余数"—— 2 的幂的模运算特例）

// 为什么用 & 不用 %：
//   & 是一条位运算指令（1 纳秒级）；% 是除法指令（慢 20+ 倍）
//   put/get 是超高频操作，这里省一点，全局收益巨大

// 代价与保障：这个等价性【要求 n 是 2 的幂】→
//   · 构造传 7 → tableOfFor 找 ≥7 的最小 2 的幂 = 8
//   · 扩容永远 ×2 → 永远保持 2 的幂（16→32→64...）
//   · 这就是"默认 16、扩容 2 倍"设计的底层逻辑！
💡 三个数字一句话串起来

16（默认容量）→ 0.75（负载因子）→ 12（16×0.75=阈值，超过即扩容到 32）。0.75 是时空折中：太大则冲突多（查找慢），太小则扩容频繁（浪费内存）——0.75 是经验最优。追问"为什么是 0.75"答"泊松分布下桶内链长达到 8 的概率约千万分之六，0.75 让冲突和空间浪费达到平衡"即可。

树化与退化

6.1 阈值规则高频★★★

事件阈值说明
链表 → 红黑树链长 ≥ 8 且 table 长度 ≥ 64容量不足 64 时优先扩容（扩容能拆散冲突），不着急树化
resize 时树 → 链表拆分后节点数 ≤ 6退化阈值 6 而非 8：留缓冲带，避免在 7/8 之间来回横跳（链↔树转换都有成本）
remove 时树 → 链表根为空或节点很少时同样保守退化
追问：为什么树化阈值恰好是 8？

源码注释给了答案：理想 hash 下桶内节点数服从泊松分布，参数 0.5 时链长达到 8 的概率约 0.00000006（亿分之六）——正常情况根本到不了 8；一旦到 8，说明 hash 质量差或遭受 hash 攻击（恶意构造同桶 key），此时转红黑树把最坏 O(n) 降到 O(log n) 是防御性设计。而红黑树节点（TreeNode）内存是链表节点的 2 倍，所以阈值不能设低，8 = "几乎只有异常才触发"的平衡点。

07

扩容 rehash 的高低位优化

7.1 JDK 8 扩容：不用重算 hash高频难点★★★

高低位拆链（面试加分项）结构
扩容：n=16 → 32。旧桶 i 的元素去哪？

旧容量 16 时：index = hash & 0b1111      （低 4 位）
新容量 32 时：index = hash & 0b11111     （低 5 位）

→ 新旧 index 的差异，【只取决于 hash 的第 5 位（新增的那一位）】：

   hash 第 5 位 = 0 → 新 index = 旧 index          （原地不动）
   hash 第 5 位 = 1 → 新 index = 旧 index + 16      （旧 index + oldCap）

JDK 8 的做法（resize 内）：
  对每个旧桶的链表，一次遍历按 (e.hash & oldCap) == 0 拆成两条：
   · lo 链（低位）→ 新 table[i]      ← 不动
   · hi 链（高位）→ 新 table[i+16]   ← 整体平移
  相对顺序保持不变（尾插），无需重新计算每个元素的 index！

对比 JDK 7：每个元素都重算 index & (n-1) 且头插（并发成环的根源，见下章）
💡 面试口述模板

"扩容翻倍后，元素新位置只由 hash 在新增那一位的 0/1 决定：要么留在原下标，要么平移旧容量大小。JDK 8 据此把每条链按高低位一分为二，各挂到新数组的两个位置，避免逐个重算 hash，同时保持链表原有顺序。"

08

JDK 7 头插死循环问题

8.1 事故原理高频难点★★★

头插 + 并发扩容 = 成环结构
背景：JDK 7 transfer() 扩容时用【头插法】把旧桶元素搬到新桶
     （头插的原因：认为新插入的数据更"热"，放链头更快被访问）

线程 A、线程 B 同时触发扩容，都在旧 table 基础上搬运：

时刻1  线程A 执行到 e=节点1, next=节点2 后被挂起（e、next 已记在它的栈里）
时刻2  线程B 完整扩容，头插把链表搬成了 2→1（顺序反转！）
时刻3  线程A 恢复，拿着过期的 e=1、next=2 继续头插搬运：
        ① 搬 1：新桶 = 1→null
        ② 搬 2：新桶 = 2→1  （此时 2.next=1，1.next 还指着 2！）
                    ↓
        1.next = 2（旧引用没清）＋ 2.next = 1  →  环形链表！

后果：之后任何 get 落到这个桶 → while 遍历死循环 → CPU 100%

JDK 8 的修复：改尾插（保持原顺序，不反转引用）
⚠ 但 HashMap 依然不是线程安全的！
  修复的只是"成环死循环"，并发 put 仍会丢数据、size 不准
  → 并发场景必须用 ConcurrentHashMap（下一章）
一句话回答

JDK 7 扩容头插会反转链表，两个线程并发扩容时一个线程拿到反转前的旧引用继续头插，形成环形链表，get 时死循环。JDK 8 改尾插修复了成环，但 HashMap 本身依旧线程不安全，并发要用 ConcurrentHashMap。

09

ConcurrentHashMap

9.1 JDK 7 分段锁 → JDK 8 CAS + synchronized超高频★★★

两代设计对比结构
JDK 7：Segment 分段锁
  ConcurrentHashMap
   ├─ Segment[16]（每段是个小 HashMap，继承 ReentrantLock）
   │    └─ table[] 链表
  · 锁粒度 = 段（16 段 → 理论并发度 16）
  · 定位：hash 两次（先定段，再定桶）

JDK 8：Node 数组 + 锁单个桶头节点
  ConcurrentHashMap
   └─ Node[] table（和 HashMap 同构，也是 链表+红黑树）
  · put 流程：
      ① 桶为空 → 【CAS】无锁插入（失败自旋重试）
      ② 桶非空 → synchronized(头节点) 只锁这一个桶 ← 锁粒度=桶！
  · size 统计：baseCount + CounterCell[] 分散计数（借鉴 LongAdder）
  · 扩容：多线程协助扩容（helpTransfer，各认领一段桶区间搬迁）

JDK 8 为什么敢用 synchronized（而不是全用 CAS/ReentrantLock）？
  · 锁的粒度细到单个桶头节点，冲突概率极低
  · JDK 6 后 synchronized 有锁升级优化（偏向→轻量→重量，模块 6 详讲），
    无竞争时性能与 CAS 相当
  · 代码简单、内存省（ReentrantLock 每个桶都要一个对象）
追问：为什么 key/value 都不允许 null？

并发场景下 get(key) 返回 null 存在二义性：无法区分"key 不存在"还是"key 存在但值是 null"。HashMap 单线程可以用 containsKey 二次确认（两次调用之间不会有别人改），ConcurrentHashMap 里 containsKey 后 get 之间可能被其他线程改动，检查了也白检查——所以从设计上直接禁止 null，消除歧义。

Set 家族与 LRU

10.1 HashSet = 换了壳的 HashMap★★

底层实现Java
// HashSet 源码核心：
private transient HashMap<E, Object> map;      // 真身
private static final Object PRESENT = new Object();  // 共享的占位 value

public boolean add(E e) { return map.put(e, PRESENT) == null; }
// add = 往 map put 一个 key，value 全用同一个占位对象
// contains(e) = map.containsKey(e)
// —— 所以 HashSet 的判重完全依赖 key 的 hashCode + equals（模块 3 的直接应用）
// LinkedHashSet / TreeSet 同理套壳 LinkedHashMap / TreeMap

10.2 LinkedHashMap 与 LRU 缓存高频★★★

十分钟手写 LRU（面试真题）Java
// LinkedHashMap = HashMap + 一条贯穿所有节点的双向链表（维护顺序）
new LinkedHashMap<K,V>(16, 0.75f, true);
//                                 ↑ accessOrder=true：按【访问顺序】排列
//                                 false（默认）：按插入顺序

// LRU（最近最少使用）淘汰缓存 —— 继承 LinkedHashMap 三行搞定：
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(16, 0.75f, true);          // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;        // true = 自动删掉"最久未访问"的头部
    }
}
// 原理：每次 get/put 把节点摘下来挂到链表尾部（最新），
//       链表头 = 最久没用的 → 超容量删头即可
// 手写版（不用 LinkedHashMap）：HashMap + 手工双向链表，get/put 后把节点移到尾部
// —— Redis 的 key 淘汰策略、MyBatis/Guava Cache 的 LRU 都是这个思路

fail-fast vs fail-safe

📌 衔接模块 2

模块 2 的"foreach 里 remove 抛 ConcurrentModificationException"在这里给出完整机制和全部正确姿势。

11.1 fail-fast：modCount 机制高频★★★

实现原理 + 正确删除姿势Java
// 机制：AbstractList 维护 modCount（结构修改次数：add/remove/clear 都会 +1）
// 迭代器创建时记下快照 expectedModCount = modCount
// 每次 next()/remove() 检查：modCount != expectedModCount → 立刻抛 CME

// 姿势 ①：迭代器自己的 remove（会同步 expectedModCount）
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove();   // ✅ 安全
}

// 姿势 ②：removeIf（JDK 8，内部就是姿势①）
list.removeIf("b"::equals);                   // ✅ 推荐，一行

// 姿势 ③：倒序 for（只删一个时可用；正序删会跳元素 + 越界）
for (int i = list.size() - 1; i >= 0; i--) {
    if (list.get(i).equals("b")) list.remove(i);   // ✅ 倒序安全
}

// ❌ 反面教材：foreach（增强 for）里 list.remove —— 必炸 CME
// ❌ 正序 for 删除相邻元素会漏删（删完 i++ 跳过了后移过来的元素）

11.2 fail-safe：并发容器★★

fail-fastfail-safe
代表ArrayList / HashMap / HashSetCopyOnWriteArrayList / ConcurrentHashMap
遍历时修改抛 ConcurrentModificationException不抛异常
原理modCount 校验，发现被改就"快速失败"暴露 bug遍历的是快照/弱一致性视图，与真身解耦
代价—CopyOnWrite 写要复制整个数组（读多写少专用）；弱一致读到的可能是旧数据
🐍 Python 对比

Python 的 RuntimeError: dictionary changed size during iteration / list 遍历删除的坑完全同构，正确姿势也是"遍历副本再删"（[x for x in l if keep(x)] ≈ removeIf）或倒序删。两边对照记忆。

Comparable / Comparator

12.1 两种比较方式★★

自然排序 vs 定制排序Java
// Comparable（自然排序）：类自身实现，"我天生知道怎么和自己比"
class User implements Comparable<User> {
    int age;
    public int compareTo(User o) { return Integer.compare(this.age, o.age); }
    // 返回负数=我在前，0=相等，正数=我在后
}
Collections.sort(users);           // 用 compareTo

// Comparator（定制排序）：外部比较器，"临时换个角度排"——不侵入原类
users.sort(Comparator.comparingInt(User::getAge)          // 按年龄升序
                    .thenComparing(User::getName)         // 年龄相同按名字
                    .reversed());                          // 整体倒序

// 工程选择：默认排序且稳定唯一 → Comparable；
//           多维度/临时/无法修改类源码 → Comparator（JDK8 函数式写法）
// TreeMap/TreeSet 两者皆可传入（构造器给 Comparator 优先）

高频面试题速查（自测清单）

1. ArrayList 和 LinkedList 区别？实际怎么选？

数组 vs 双向链表：随机访问 O(1) vs O(n)；头插 O(n) vs O(1)；扩容 1.5 倍 vs 无需。但 LinkedList 定位本身是 O(n) 且节点内存开销大、缓存不友好——实践中默认 ArrayList，栈/队列用 ArrayDeque，LinkedList 基本不用。

2. ArrayList 扩容机制？默认容量？

懒加载：new 时是空数组，首次 add 才分配 10。不够用时 newCapacity = oldCap + (oldCap>>1) 即 1.5 倍，Arrays.copyOf 全量拷贝。预知数据量就 new ArrayList<>(n) 一次到位。

3. HashMap 的 put 流程？

懒加载初始化 16 → hash 扰动 & (n-1) 定桶 → 空桶直接放 → 冲突则按 hash+equals 桶内找，找到覆盖，否则尾插 → 链长 ≥8 且容量 ≥64 树化（容量不足先扩容）→ ++size 超过容量×0.75 扩容翻倍。

4. HashMap 为什么容量是 2 的幂？扰动函数干嘛的？

2 的幂使 hash & (n-1) 等价于 hash % n 但快 20 倍（位运算 vs 除法）；构造器会把你传的容量修正为 ≥ 它的最小 2 的幂，扩容永远 ×2 维持此性质。扰动 (h ^ (h>>>16)) 把高 16 位掺入低 16 位，因为定桶只用低位，不扰动会让高位差异被浪费、冲突集中。

5. 为什么树化阈值 8、退化阈值 6？

泊松分布下链长到 8 的概率约亿分之六，正常到不了 8，到 8 说明 hash 异常或攻击，转红黑树把 O(n) 降到 O(log n)。退化用 6 留 2 的缓冲带，避免 7/8 临界点来回转换（互转都有成本）。TreeNode 内存是链表节点 2 倍，故阈值不能低。

6. JDK 8 扩容怎么优化 rehash？

容量翻倍只新增 1 个有效位，新下标只由该位 0/1 决定：要么原下标，要么原下标+oldCap。遍历每条链按 (e.hash & oldCap)==0 拆成高低两条，分别挂到新数组两个桶，不重算每个元素的 hash，且尾插保持顺序。

7. JDK 7 HashMap 并发死循环是怎么回事？JDK 8 修复了吗？

JDK 7 扩容头插法反转链表，线程 A 记录的旧 e/next 引用在 B 完成搬迁恢复后继续头插，1↔2 互指成环，后续 get 该桶死循环 CPU 100%。JDK 8 改尾插保持顺序，成环修复；但并发 put 仍会丢数据——HashMap 依旧线程不安全，并发必须 ConcurrentHashMap。

8. ConcurrentHashMap JDK 7 和 JDK 8 的实现区别？

JDK 7：Segment[16] 分段锁（每段 ReentrantLock），并发度 16，hash 两次定位。JDK 8：抛弃分段，Node 数组同构 HashMap，空桶 CAS 无锁插入，非空 synchronized 锁桶头节点（粒度更细），size 用 baseCount+CounterCell 分散计数，支持多线程协助扩容。敢用 synchronized 是因为粒度极细 + JVM 锁升级优化。

9. ConcurrentHashMap 的 key/value 为什么不能是 null？

get 返回 null 无法区分"key 不存在"还是"值就是 null"（二义性）。单线程可 containsKey 二次确认，但并发下确认与 get 之间可能被其他线程改掉，确认无意义——设计上直接禁止。

10. 遍历时删除元素有哪些正确姿势？

① iterator.remove()（同步 expectedModCount）；② removeIf（内部即①）；③ 倒序 for 删除。foreach 中调集合 remove 必抛 CME（fail-fast：modCount 与迭代器快照不一致）；正序 for 会漏删相邻元素。并发场景用 CopyOnWriteArrayList（fail-safe，读旧快照）。

11. HashSet 底层？怎么保证不重复？

套壳 HashMap，元素作 key，value 用共享的 PRESENT 占位对象。判重 = hash 定桶 + equals 桶内比对（模块 3），所以存进 HashSet 的类必须正确重写 hashCode+equals。

12. 怎么实现一个 LRU 缓存？

继承 LinkedHashMap(16, 0.75f, true)（accessOrder=true，每次访问把节点移到链尾），重写 removeEldestEntry 在 size>capacity 时返回 true 自动淘汰链头（最久未访问）。手写版：HashMap + 双向链表，get/put 后移节点到尾，超容删头。
