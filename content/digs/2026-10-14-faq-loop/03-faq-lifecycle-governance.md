## A 组：FAQ 手动治理

### ① 可不可以随时卸载/修改？热度模型就是干这个的吧？

**先纠正一半：热度模型不卸载任何东西，它只是记分员。** 卸载（delete）是 FAQ 管理页的手动操作，现在就有。你说的“热度模型去卸载”混淆了“手动清理（已有）”和“自动淘汰（未实现，heat_score 是为它预留的判据）”。

实际能力清单（前端按钮实锤，`frontend/js/pages/faq.js:23-25`）：

| 操作 | 状态 | 说明 |
|---|---|---|
| 卸载（delete） | ✅ 已有 | 库主权限，PG DELETE + Milvus 向量删除 + audit + bump 缓存 |
| 降级（demote） | ✅ 已有 | active→candidate，收回直返资格 |
| 提前升格（promote） | ✅ 已有 | 显式触发路径（“记住这个”），无需等热度 |
| **编辑 question/answer** | ❌ **没有** | 前端只有上面三个按钮，后端也没有 PUT 接口 |

**编辑是真实的功能空白**——改一条 FAQ 的唯一办法是删掉重新补全（热度清零重攒）。这是个很好的“如果继续迭代你会做什么”储备答案：加一个 `PUT /api/faq/{id}`，库主权限，改 answer 时可选重跑蒸馏，audit 记 before/after——和 promote 的审计格式对齐。你说“做增强（faq 管理）对吧”——对，而且一半已经做了，缺的正是编辑。

### ⑤ reject_pr 之后也不计算热度了吗？

**“同构”指的是代码结构同构（权限三重校验 + 状态机迁移 + 审计留痕三件套长得一样），不是热度语义。** 更准确的认知是：**PR 里的东西从头到尾就没进入过 FAQ 世界**——

```
PR 路径：补全 → faq_pr 表一行（question/answer 只是排队副本）→ merge? 
                                                ├─ 是 → 此刻才第一次 add_faq（直接 active）+ 写向量
                                                └─ 否（reject）→ faq_pr.status='rejected，仅留审计
```

被 reject 的 PR：没有 faq 行、没有 Milvus 向量、**从未参与过热度累计**——不是“不再算了”，是“从来没算过”。`faq_pr` 是隔离的候选队列，库主不点头，内容永远碰不到 FAQ 库。rejected 记录保留是为了审计追溯（谁提过什么、什么时候被拒、拒绝理由 `review_note`）。想再贡献：改内容重新提 PR，或者在自己的克隆版里种 candidate 攒热度自用。

### ⑩ 口语 → 结构化：示例

示意重构（按蒸馏 prompt 的行为规则还原，非项目原句）：

```
用户补全原文（candidate.answer）：
  "这个啊 你得去设置里面把那个 enable 就是检索增强那个开关打开，
   然后记得重启一下服务，我上次就是没重启搞了半天"

蒸馏后（active.answer，LLM 改写）：
  "启用检索增强功能的步骤：
   1. 进入系统设置页；
   2. 开启「检索增强」（Enable RAG）开关；
   3. 重启后端服务使配置生效。
   注意：修改配置后必须重启服务，否则不生效。"
```

蒸馏 prompt 要求的四件事，对着看：**去口语**（“这个啊/就是/呃”没了）、**去个人叙事**（“我上次搞了半天”→提炼成通用“注意”提示）、**结构化**（步骤列表）、**保关键事实**（开关名、重启要求一个不丢）。audit 的 `faq.promote` 事件里存了 `before[:300] / after[:300]` 全文对照（`faq_service.py:319-323`）——**蒸馏质量的人工审计入口就是这里**，库主在审计中心能逐条对比改写前后。

## B 组：机制细节

### ③ 惰性更新会拉长链路吗？

**不但不拉长，反而合并了查询。** 看 `increment_faq_hit` 的 SQL（`database.py:508-517`）：`UPDATE ... RETURNING hit_count, heat_score, status, distill_threshold`——一次主键单行 UPDATE，**顺便把 `try_faq_hit` 本来就要查的状态字段带回来了**。对比无热度版本：命中 → `get_faq` 查一次状态 → 再决定直返。现在：命中 → UPDATE RETURNING 一次往返拿全所有字段。PG 单行主键更新是亚毫秒级操作，而这条链路真正的大头是前面的 `aembed_query`（远程 embedding HTTP，几百毫秒）——DB 这次更新在延迟账单上**排不进前五**。

至于“如果不惰性、用后台 Cron 会怎样”：全表扫描 × 每天数次 × 大部分行根本没人命中（白算）——那才是真正持续的额外负载。惰性的本质是**只为真实发生的事件付费**。

### ④ 库内没有相关 chunk 时，蒸馏怎么走？

方向对，但不是“先处理一遍再 distill”两步，是**一步降级**。代码路径（`faq_service.py:289-314`）：

```
取上下文（try/except 包着）：
  ├─ 库内有相关 chunk → context = top-3 拼接 → prompt 带"相关知识库上下文"段 → 对照改写
  ├─ 库内无相关 chunk / 检索失败 → context = "" → prompt 少一段 → 纯原文结构化改写
  └─ （警告日志，不致命，继续蒸馏）

LLM 调用：
  ├─ 正常返回 → distilled = 返回文本.strip()
  ├─ 返回空字符串 → 回退用原文升格（distilled or faq["answer"]）
  └─ 调用抛异常 → 整体 except → return False → 升格失败，保持 candidate，
     下次命中再试（热度已达标这个事实还在，阈值判断会再次触发）
```

三个分支对应三种哲学：**上下文缺失降级不阻塞**（增强路径永不挡主流程）、**空返回用原文**（宁可存原文也不让升格卡死）、**异常回滚升格**（写库类操作失败要显式失败，下次重试，而不是带着不确定性升格）。

## 收个尾：这轮新增的记忆锚

1. **“热度是记分员，不是清洁工”**——卸载靠手动 delete（已有），自动淘汰才用 heat_score（未实现）；编辑功能是真空白。
2. **“PR 队列是隔离舱”**——reject 的东西从未进过 FAQ 世界，不是“停止计热”，是“从未计热”。
3. **“增量 bulk_index 而非全量 reload”**——只搬新 KB 的份，重启还有 load 兜底，双保险。
4. **“版本进 key，不是读后比对”**——key 变了自然 miss，旧缓存等 TTL 腐烂，粗粒度换正确性。
5. **“缓存会冻结自进化”**——两条各自正确的线，交叉点出妖；bump 是契约不是耦合。
6. **“cron 产生事件，SSE 投递事件，落库保证不丢”**——超期检测必须定时器，推送只是加速。
