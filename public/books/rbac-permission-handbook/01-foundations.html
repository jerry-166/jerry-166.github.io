01

面试原题复盘：卡在哪里 ★★★★★

1.1 原题（素材平台 · 页面级 RBAC）

项目背景是一个面向多角色的素材平台，数据库用的是 MongoDB（写多读少场景）。面试中的原始问答与追问如下：

环节内容评价
页面级 RBAC实现了用户、角色两部分；没有建权限表，权限以"页面 / 模块的权限字典"形式存在；用户登录后按权限决定页面显示与操作能力。功能权限基本成立，权限点字典化是常见简化
为什么用 MongoDB该场景写多读少，MongoDB 有优势。选型理由可接受（注：口语常误读为 Mongos）
追问：用户能分组吗平台面向素材需求提供者、创作者、投放者、管理员、普通用户，不同人页面权限不同——答出了"按角色分组"。角色与用户组概念开始混淆
追问：行级数据权限"能打开页面，但只能看到自己投放的素材"——提出"中间表 + 给游戏/素材写入 user id"。卡壳 只有思路，没有表结构
追问：写了 user_id 又分组，group_id 怎么办两个组都对同一游戏有权限时如何处理。未答出 多对多归属
追问：多对多怎么用表维护—未答出
追问：了解 Casbin / OPA 吗没有了解过。开源方案盲区

1.2 标准答案（面试官视角）

页面级 RBAC（功能权限）

用户 → 角色 → 权限（页面 / 模块粒度），MongoDB 写多读少场景可用文档存储；权限码用 模块:页面:操作 命名。

数据权限（Data-level Permission，行级）

核心是 用户 / 角色与数据实体之间是多对多关系，需要 资源归属表 + 权限关联表（如 resource_owner(resource_id, owner_type, owner_id)），支持「本人 / 所在组 / 游戏级 / 游戏类别级」多层范围。

开源方案

Casbin：经典 RBAC/ABAC 权限库，支持策略模型；OPA（Open Policy Agent）：统一策略引擎，Rego 语言。

一句话点题

这道题的真正考点是：你能不能把"权限"从"能不能打开页面"细化到"能看到哪些数据行、哪些字段"，并且设计出多对多的存储模型。

02

三层权限坐标系 全书核心

所有权限系统——无论自研、Casbin 还是 OPA——解决的都是下面这三个正交（互不重叠）的问题。先把这张图刻进脑子，后面的所有内容都是这三层的不同实现。

① 功能权限（Functional Permission）· RBAC 的主战场
控制 能不能看到页面 / 按钮 / 能不能调接口。例：投放者能看到"素材投放"菜单、能点"新增素材"按钮、能调 material:add 接口。
粒度：页面级、模块级、按钮级、接口级。本质：路由/动作的开关，与具体数据无关。
② 数据权限（Data Permission · 行级 / Row-level）· 最难的一层
功能权限放你进了"素材列表"页面，这一层决定列表里能列出哪些行。例：只能看到自己投放的素材；主管能看到本部门所有人的素材；管理员能看全部。
粒度：数据库的行。本质：查询范围（WHERE 条件 / 归属关系）。
③ 字段级权限（Field-level · 列级 / Column-level）· 最细粒度
同一行数据，不同人能看到的列不同。例：普通员工看不到手机号、成本价列，高管 / 财务能看。
粒度：数据库的列。本质：序列化输出时裁字段。

最常见的认知误区（也是面试卡壳点）

把"我能看到这个页面"等同于"我能看到页面里的所有数据"。页面级 RBAC 只管第 1 关；"只能看到自己投放的素材"是第 2 关（行级），它不在 RBAC 的经典职责里，需要额外的数据归属模型，这正是本题被追问到答不出的地方。

功能权限和行级权限为什么不能合成一张表？

功能权限是 角色 ↔ 动作 的关系（哪个角色能调哪个接口），数量有限、变化慢、对所有人生效规则相同；行级权限是 主体 ↔ 具体数据实例 的关系（u101 对 M100 这一条素材有权限），随业务数据爆发增长（每新建一条素材可能产生一条归属）。二者数据量、变化频率、查询方式完全不同，强行合一就是 Casbin EAV 表要面对的"策略膨胀"问题（第三册讲）。

03

权限模型发展史：每一步都在解决上一代的痛

权限模型不是凭空设计的，而是沿着"用户多了怎么办、组织复杂了怎么办、数据海量了怎么办"一步步演进。

ACL · 访问控制列表（Access Control List）
做法：每个资源直接挂一串"谁能干什么"：文件 → {u101:rw, u102:r}。最直观，文件系统至今在用。
痛点：用户一多，授权要逐人逐资源配，无法批量管理。100 个员工换岗位，要改 100 个地方。
RBAC0 · 基础模型（NIST 标准）—— 用户 → 角色 → 权限
核心抽象：在用户和权限之间加一层角色。用户绑定角色，角色绑定权限，给人授角色就是授一批权限。
价值：新人入职给个"投放者"角色即可；权限只在角色上配一次。这是 90% 后台系统的地基。
RBAC1 · 角色继承（Role Hierarchy）
角色可以继承："高级投放者"继承"投放者"的全部权限，再加几个。子角色自动拥有父角色权限，避免重复配置。Casbin 用 RoleManager 内存图实现，若依角色是扁平的、没有继承。
RBAC2 · 约束（Constraints）
给角色加规则：互斥角色（出纳和会计不能同一人）、角色人数上限、角色激活前置条件等。面向职责分离的合规场景。
RBAC3 · 合体（RBAC0 + 1 + 2）
基础 + 继承 + 约束的完整模型。
ABAC · 基于属性的访问控制（Attribute-Based）
不再只看"你是谁"，而是看一组属性：谁（user 部门/级别）、什么资源（resource 的 owner/分类）、什么动作（action）、什么环境（time/IP）。
规则形如 resource.owner_id == user.id OR resource.group_id IN user.groups。行级权限的天然工具，规则型数据权限（如若依 data_scope）就是 ABAC 的简化实践。
PBAC · 策略即代码（Policy-Based）—— OPA 为代表
把授权规则写成可版本化、可评审、可测试的策略代码（Rego），由独立引擎统一决策。规则不再散落在业务代码里。
ReBAC · 基于关系的访问控制（Relationship-Based）—— Google Zanzibar / OpenFGA
把"人 ↔ 资源"的关系本身存成一张关系图（文档-编辑者-用户、文件夹-包含-文档、群组-成员-用户），沿关系链求可达性。Google Docs 里"文档共享给某群，群成员可看"就是它。resource_owner 是 ReBAC 的朴素雏形。
图 1-3　权限模型演进时间线（ACL 直挂 → RBAC 角色 → ABAC 属性 → PBAC 策略 → ReBAC 关系）

3.1 横向对比

模型判断依据擅长短板
ACL资源上的名单少量资源、精细到人海量用户无法批量

记忆要点

不是新模型取代旧模型，而是各管一层：生产系统几乎都是 RBAC 管功能权限 + ABAC/ReBAC 管数据权限。若依、Casbin、OPA 三套方案都能组合，只是实现位置不同。

04

易混概念：role / group / dept 与权限码

面试中"用户可以分组吗"一追问就乱，根因是把三个都叫"组"的东西混为一谈。

角色 role（功能维度）
作用：功能权限的分组容器，挂权限。
例：投放者、创作者、管理员。
一人可多角色；岗位变了角色变。
回答："这个菜单/按钮你能不能用"。
用户组 group（数据归属维度）
作用：横向的数据归属，建议不挂功能权限。
扁平结构，一人可属多个组（如同时在 A、B 项目组）。
回答："这条数据分享给哪个组"。
部门 dept（组织维度）
作用：树形组织架构，parent_id 自关联。
一人通常只属一个部门；主管可看本部门及下属部门数据。
回答："你属于哪个组织、归谁管"。
图 1-4　role 挂权限、group 归数据、dept 表组织——三者正交，不要混用
为什么 group 不建议挂功能权限？

功能权限按岗位（role）走，数据归属按协作关系（group）走。若把功能权限也挂到 group，"A 项目组临时加一个人"就会把这个人不该有的菜单权限也带进来，两个维度耦合后无法独立调整。职责分离是权限模型可维护性的关键。

4.1 权限码（权限标识）的三级命名

功能权限最终落成一个字符串 权限码，业界通用三段式：模块:页面:操作。

权限码命名示例
material:list:query     // 素材模块 · 列表页 · 查询（查看素材列表）
material:list:add       // 素材模块 · 列表页 · 新增
material:list:export    // 素材模块 · 列表页 · 导出按钮
material:detail:edit    // 素材模块 · 详情页 · 编辑
system:user:remove      // 系统模块 · 用户页 · 删除
*:*:*                   // 超级管理员通配（若依约定）

权限码是代码与数据库之间的约定字符串：代码注解里写一份，菜单表 perms 字段存一份，靠字符串完全相等来匹配。这套约定的具体落地在第二册（若依）讲。

05

数据权限（行级）的两条路线 本题核心

这是面试卡壳的地方。"只能看到自己投放的素材"本质是行级过滤，业界有两条互补的实现路线，生产中常常混用。

路线 A · 规则型（data_scope / ABAC 简化）
不存逐条关系，只配规则："本部门可见""仅本人可见"。
查询时把规则翻译成 WHERE 条件拼进 SQL。
适合：海量、规整、按组织归属的数据（订单、部门数据）。
代表：若依 @DataScope 五档。
路线 B · 关系型（资源归属表 / ACL 实例表）
存一条条"谁对哪条资源有什么权限"的关系。
查可见资源 = 查归属表中属于我的关系。
适合：不规则、动态的分享 / 转派 / 协作（文档共享、素材分享给某组）。
代表：resource_owner、Google Docs、Zanzibar。
图 1-5　规则型"按规则现算"，关系型"按关系查表"；不是二选一，生产常 OR 合并
维度路线 A · 规则型路线 B · 关系型
存什么角色上的数据范围配置（如 data_scope=本部门）主体 ↔ 资源实例的逐条关系（resource_owner）
判断方式查询时拼 WHERE：dept_id IN (本部门)JOIN/子查询归属表：resource_id IN (我有归属的)
新增数据零成本，新行天然带 dept_id/create_by 即满足规则要同步写入一条归属关系（分享即写）
数据量规则数固定，不随业务增长随业务数据线性增长，可能百万级
灵活度只能表达预设的几种范围任意人/组/资源的任意组合，最灵活
典型场景员工看本部门订单；主管看下属数据把素材 M100 分享给 G5 组；把文档转派给某人
本题素材平台怎么选

"只能看自己投放的素材" → 规则型即可（owner_id = 当前用户）；"素材分享给某几个组 / 某个游戏多个组都有权限" → 必须上关系型 resource_owner。两者混用：可见范围 = 规则条件 OR 归属表关系。

06

resource_owner 资源归属表设计（多对多的标准答案）

6.1 先理解：为什么是"多对多"

面试追问的两个问题，本质都是多对多：

  • 一个用户 / 组 → 能访问多条素材；
  • 一条素材 → 能被多个用户 / 组访问（"两个组都对同一游戏有权限"）。

关系型数据库用中间表表达多对多；MongoDB 也可以用一个归属集合。这张表不关心业务字段，只记录"哪个主体对哪条资源拥有什么权限"。

6.2 表结构（通用设计，多资源类型共用一张表）

resource_owner（资源归属 / ACL 实例表）
CREATE TABLE resource_owner (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  resource_type VARCHAR(32)  NOT NULL,  -- 资源类型：material / game / category
  resource_id   VARCHAR(64)  NOT NULL,  -- 资源 ID（素材 M100 / 游戏 G1）
  owner_type    VARCHAR(16)  NOT NULL,  -- 归属主体类型：user / group / dept
  owner_id      VARCHAR(64)  NOT NULL,  -- 主体 ID：u101 / g5 / dept8
  perm          VARCHAR(16)  NOT NULL DEFAULT 'view', -- view / edit / manage
  UNIQUE KEY uk_rel (resource_type, resource_id, owner_type, owner_id),
  KEY idx_owner (owner_type, owner_id),
  KEY idx_res (resource_type, resource_id)
);
回答追问"多个不同字段管理权限，是否都放同一张表？"

是的。用 resource_type 区分素材、游戏、类别，不同资源类型共用这一张归属表；用 owner_type 区分归属到个人 / 组 / 部门。这就是"通用 ACL 表"的写法，避免每加一种资源就新建一张表。

6.4 游戏级继承：素材挂在游戏下，权限向下继承

业务素材表冗余一个 game_id。当组对游戏有权限时，该组能看到该游戏下所有素材——这是一层"资源层级继承"，不需要给每个素材复制归属。

6.5 查询：当前用户能看到哪些素材（完整 SQL）

可见素材 = 本人/本组的素材 OR 本人/本组有权限的游戏下的素材
SELECT DISTINCT m.*
FROM material m
WHERE
  -- ① 素材直接归属：本人 或 我所在的组
  EXISTS (
    SELECT 1 FROM resource_owner ro
    WHERE ro.resource_type='material' AND ro.resource_id=m.id
      AND (
        (ro.owner_type='user'  AND ro.owner_id= :userId)
        OR
        (ro.owner_type='group' AND ro.owner_id IN (:myGroupIds))
      )
  )
  OR
  -- ② 游戏级继承：素材所属游戏被分享给本人/本组
  EXISTS (
    SELECT 1 FROM resource_owner ro
    WHERE ro.resource_type='game' AND ro.resource_id=m.game_id
      AND (
        (ro.owner_type='user'  AND ro.owner_id= :userId)
        OR
        (ro.owner_type='group' AND ro.owner_id IN (:myGroupIds))
      )
  );
关键细节
  • 多组并集：一个人在多个组，用 IN (:myGroupIds) 一次覆盖；多个组对同一游戏有权限就是多条 owner 记录，查询天然命中——多对多问题就此解决，不需要在素材上写 group_id。
  • 去重：本人 + 多个组可能同时命中，用 DISTINCT（或 EXISTS 天然不重复）。
  • :myGroupIds 来自"用户-组"中间表，登录时查出（可缓存，见第 7 章）。

字段级权限（手机号列）也走 resource_owner 吗？

不走。resource_owner 解决的是"哪些行"，字段是列，列对所有行规则一致，属于功能权限范畴的扩展——用"字段权限码"（如 field:user:phone）挂角色，序列化时按权限码裁列即可，不需要为每一行存字段关系。具体在第二册（若依）和第三册（Casbin 字段级）展开。

07

性能：Redis 缓存登录权限与权限 Set

功能权限的特点是每个请求都要校验、但变化很少。如果每次请求都查库 JOIN 一遍用户-角色-权限，纯属浪费。标准做法是登录时聚合一次、缓存起来。

7.1 登录时聚合：把"我是谁、我能干什么"算成集合

登录后写入 Redis（Key 设计）
# 权限码集合（功能权限）—— 天然就是 Set
SET  perm:user:{userId}     material:list:query  material:list:add  material:list:export
# 角色集合
SET  role:user:{userId}     publisher  creator
# 用户组 ID 集合（数据权限用）
SET  group:user:{userId}    g5  g7
# 数据范围（规则型，行级）
STRING scope:user:{userId}  data_scope=4   deptIds=[8,12]
# 统一用一个 Hash 也常见（登录态对象）
HSET login:{userId}  perms {...}  roles {...}  groups {...}
呼应你想到的"Redis Set"——完全正确

一个人在多个组、多个角色，权限来自多个角色、多个组，天然是多集合求并集：Redis Set 的 SUNION / 应用层 Set.addAll 正好；校验单个权限码用 SISMEMBER（Redis）或 HashSet.contains（内存），O(1)。

缓存内容说明失效时机
权限码 / 角色 / 组集合小、变化少，命中率极高授权变更时主动删 key（pull 失效）
数据范围配置（data_scope）几条规则配置角色配置变更时删
具体数据行（素材列表）一般不缓存：数据量大、实时性要求高、每个用户结果不同—（交给数据库 + 行级 WHERE）
缓存一致性（多实例）

授权变更后各实例缓存要失效：① 后台改完删除 Redis 中该用户的权限 key（下次请求重新聚合，pull 式）；② 多实例若用本地缓存，可借 Redis 发布订阅通知（这就是 Casbin Watcher 的同款思路，第三册讲）。

本册小结与自测

8.1 必须带走的 6 句话

  1. 权限分三层，正交：功能权限（页面/按钮/接口）、行级（哪些行）、字段级（哪些列）。
  2. RBAC 用"角色"解决批量授权；模型演进 ACL→RBAC0-3→ABAC→PBAC→ReBAC，各管一层，不互斥。
  3. role 挂功能权限、group 表数据归属、dept 表组织树，不要混用。
  4. 行级权限两条路线：规则型（data_scope 拼 SQL）+ 关系型（resource_owner 查表），生产 OR 合并。
  5. 多对多用 resource_owner(resource_type, resource_id, owner_type, owner_id, perm)，多组授权靠多条记录 + IN，权限随游戏层级继承。
  6. 功能权限集合缓存到 Redis，校验是 O(1) 的 Set.contains；数据行不缓存，交给数据库 WHERE。
