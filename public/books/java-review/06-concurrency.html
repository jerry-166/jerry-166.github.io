为什么推荐 Runnable 而不是继承 Thread？—— 任务与执行解耦（任务可复用、可提交线程池），不占用宝贵的单继承名额；Thread 本质是"执行器"，Runnable 才是"任务"。

start() vs run()：本质区别 高频★★★

调用 run() 只是在当前线程里执行一个普通方法——没有新线程，串行执行；调用 start() 才是请求 JVM 创建新线程，由新线程去执行 run()。且 start() 只能调用一次，第二次抛 IllegalThreadStateException（线程状态不可逆回 NEW）。这是个看似简单但常年出现在笔试的送分/送命题。

join() 的底层实现是什么？高频

join() 本质是在当前线程上对目标线程对象 wait()——源码就是 while (isAlive()) wait(0);。目标线程 run() 结束时，JVM 会调用它的 notifyAll() 唤醒所有等待者。所以 join 必须持锁的问题不存在（wait on 对象本身的 monitor 由 JVM 保证）。这也解释了为什么 join 期间可被中断。

yield() 有什么用？和 sleep(0) 一样吗？

yield() 只是"建议"调度器让出当前时间片，从 running 回到 ready——但调度器可以无视，下一拍还是选中它。它不释放锁、不进入等待态（状态仍是 RUNNABLE）。和 sleep(0) 行为接近，但 yield 是纯提示、无跨平台保证，实践中几乎只用于测试并发问题时的"搅局"。

并发三性问题 高频★★★★

一切并发工具都在解决三个问题。先把三个问题各自的"惨案现场"看清楚，后面的工具才有意义。

原子性：i++ 惨案

AtomicityFail.javai++ 不是原子操作
public class AtomicityFail {
    static int count = 0;
    public static void main(String[] args) throws Exception {
        Runnable inc = () -> { for (int i = 0; i < 100000; i++) count++; };
        Thread t1 = new Thread(inc), t2 = new Thread(inc);
        t1.start(); t2.start(); t1.join(); t2.join();
        System.out.println(count); // 期望 200000，实际大概率 < 200000
    }
}
// i++ 字节码三步（复习模块 1 的栈帧操作数栈）：
//   17: getstatic  count   —— 读：把静态变量 count 压栈（比如读到 5）
//   20: iconst_1 / iadd    —— 加：栈顶 5+1=6
//   21: putstatic  count   —— 写：把 6 写回静态变量
// 两个线程交错执行：都读到 5、都算出 6、都写回 6 —— 两次自增丢了一次

原子性定义：一个操作要么不执行，要么全执行完、中间不可被其他线程观察到/打断。i++ 是"读-改-写"三步复合操作，不原子。解法：synchronized / Lock（互斥，一次只许一个线程进入）、CAS（硬件级原子比较交换）、或 JDK 封装好的原子类。

可见性：改了看不见

VisibilityFail.java可能永远不结束的死循环
public class VisibilityFail {
    static boolean flag = true; // 没有 volatile
    public static void main(String[] args) throws Exception {
        new Thread(() -> {
            while (flag) { /* 空转 */ }   // JIT 发现循环体不修改 flag，
        }).start();                       // 优化成 if(flag) while(true) —— 永远出不来
        Thread.sleep(1000);
        flag = false;                     // 主线程改了，工作线程可能永远看不到
    }
}
// 根因：JMM 允许每个线程把共享变量缓存在【工作内存】（CPU 缓存的抽象），
// 不强制立即同步回主内存 —— 读线程读的是自己缓存里的旧值

解法：volatile（写立即刷回主存 + 令其他核的缓存行失效）、synchronized（解锁前把工作内存刷回主存）、final（初始化安全发布）。注意这个例子在解释型执行（解释器逐条读内存）时可能"碰巧"能停下来，加了 JIT 后就是真死循环——所以"我本地测不出问题"不能证明线程安全。

有序性：指令重排

编译器、JIT、CPU 都会为了性能重排指令（不改变单线程语义的前提下）。单线程有 as-if-serial 保护看不出问题，多线程就会暴露：

OrderingFail.java经典双重检查式暴露
// 线程 A 执行                      // 线程 B 同时执行
a = 1;          // 写 a              r1 = b;   // 读 b —— 可能读到 1！
b = 2;          // 写 b              r2 = a;   // 读 a —— 但 a 可能还是 0！
// 若 A 侧发生重排（先写 b 再写 a），B 观察到 b=2 而 a=0
// 推理"b=2 ⇒ a 必然=1"在多线程下不成立 —— 这就是有序性被破坏

解法：volatile 的内存屏障禁止重排、synchronized 的互斥（同一时刻只有一个线程在临界区内，等价于单线程视角）。

哪些操作本身是原子的，不需要加锁？易错

JMM 保证：①基本类型（除 long/double 外）的简单读写是原子的（32 位以内一条指令）；②所有引用类型的赋值是原子的；③volatile 变量（含 long/double）的读写是原子的。注意：long/double 的普通读写因为 JVM 规范允许 64 位拆成两次 32 位操作（实践中 64 位 JVM 基本不拆，但规范不保证），所以多线程共享普通 long 建议加 volatile 或原子类。而 i++、i += 1、check-then-act（if 后 set）都是复合操作，一律不原子。

Python 里有这三性问题吗？Python 对比

三性都被 GIL 大幅简化但没消灭：原子性——GIL 保证单条字节码不交错，CPython 里 dict[k]=v、list.append 事实原子，但 x += 1 编译成 LOAD/INPLACE/STORE 三条字节码，切换点在字节码之间，照样丢更新（和 Java i++ 惨案同构）；可见性——GIL 顺便保证了（全局锁=全局同步点）；有序性——单线程执行字节码天然有序。所以 Python 开发者对三性几乎没有肌肉记忆，这是转 Java 最大的认知债——Java 把 GIL 挡掉的问题全部暴露给你，必须逐个手动处理。

JMM 与 happens-before 难点★★★★

主内存与工作内存

JMM（Java Memory Model）不描述物理内存，它是一套抽象规范：所有共享变量存在主内存；每个线程有自己的工作内存（栈+CPU 缓存的抽象），线程对变量的操作必须在工作内存进行——先从主内存拷贝，改完何时刷回主内存规范不做保证。三性问题正是从这个"允许缓存、允许延迟同步"的模型里长出来的。

happens-before：判断可见性的唯一标尺 高频

JMM 不说"操作 X 一定在 Y 之前执行"，而是说：如果 A happens-before B，那么 A 的结果对 B 可见，且 A 排在 B 前面（逻辑顺序）。这是给程序员的契约，不是给编译器的执行命令——编译器可以任意优化，只要不破坏已声明的 hb 关系。核心规则八条：

#规则含义（前者的结果对后者可见）
1程序顺序规则单线程内按代码顺序，前面的操作 hb 后面的（as-if-serial：结果上像顺序执行）
2监视器锁规则对同一锁的解锁 hb 后续对它的加锁（这就是锁保证可见性的法源）
3volatile 规则对 volatile 的写 hb 后续对它的读（volatile 的法源）
4传递性A hb B 且 B hb C ⇒ A hb C（组合出跨变量可见性）
5start 规则线程 A 执行 threadB.start() 前的所有写，对 B 内部可见
6join 规则线程 B 的所有写，对 join() 返回后的 A 可见
7线程中断规则interrupt() 的调用 hb 被中断线程检测到中断
8对象终结规则构造函数执行完 hb finalize() 的执行

面试答题模板："我不背执行顺序，我用 happens-before 推导可见性"。比如经典题"线程 A 在锁内改了 x，线程 B 拿同一把锁后读 x，能读到吗？"——解锁 hb 加锁（规则2）+ 写 x hb 解锁（规则1）+ 加锁 hb 读 x（规则1），传递性串联：写 x hb 读 x，✅ 能读到。

as-if-serial 和 happens-before 是什么关系？难点

as-if-serial 是单线程契约：无论怎么重排，单线程执行结果不能变（给编译器优化的自由边界）；happens-before 是多线程契约：程序员与编译器之间关于可见性的约定。两者配合构成 JMM 的核心：happens-before 之外的区域（无同步、无 volatile 的共享访问），JMM 不做任何保证——"data race"（数据竞争）区域，行为未定义。JMM 的设计目标就是在"程序员好懂"和"编译器好优化"之间平衡：同步开销集中的地方给强保证（hb），其他地方给自由。

final 字段为什么能保证可见性？

JMM 对 final 有特殊条款：只要对象正确构造（没有 this 逃逸），final 字段在构造函数里写入的值，对所有其他线程可见且看到的是构造后的完整值——哪怕对象引用通过数据竞争发布（比如非 volatile 的静态字段传递）。实现上，构造函数结束前对 final 的写会被插入 StoreStore 屏障，防止与"发布引用"重排。这也是"不可变对象天然线程安全"的法源：String、不可变集合（List.of）不需要任何同步就能自由共享。但注意：对象里如果还有可变字段，只有 final 那些受保护。

volatile 与单例 高频★★★★★

volatile 的两层语义

  • 可见性：写 volatile 变量时，JMM 强制把工作内存的值刷回主存，并使其他 CPU 核上该变量的缓存行失效（底层是 MESI 缓存一致性协议）；读 volatile 变量时强制从主存重新 load。一句话：写立即对所有人可见，读永远读最新值。
  • 有序性：编译器在 volatile 读写前后插入内存屏障，禁止特定方向的指令重排——写前 StoreStore（前面的普通写不能重到后面）、写后 StoreLoad（最全能最贵的屏障）；读后 LoadLoad + LoadStore。
  • 不保证原子性：volatile 的单个读/写是原子的，但 i++ 这种复合操作依然会丢——§3 的三步字节码一步没少，volatile 只是保证每步读到的都是最新值，两个线程仍可能同时读到 5。
一句话回答

volatile 能替代锁吗？——不能。它只管"可见 + 有序"，不管"互斥"；适用场景是"一个线程写、多个线程读"的开关/状态位，凡是涉及读-改-写都必须上锁或用原子类。

DCL 双重检查锁单例：volatile 的最佳实战 高频

public class Singleton {
    // ★ 为什么必须 volatile？看下面"半成品对象"时序图
    private static volatile Singleton instance;

    private Singleton() { /* 防反射破坏：已在创建则抛异常 */ }

    public static Singleton getInstance() {
        if (instance == null) {                    // ① 第一次检查（无锁快路径）
            synchronized (Singleton.class) {       // ② 只在首次创建时才竞争锁
                if (instance == null) {            // ③ 第二次检查（持锁后再验一次）
                    instance = new Singleton();    // ④ 问题就在这一行
                }
            }
        }
        return instance;
    }
}
instance = new Singleton() 实际是三步：
   a. 分配内存（堆）
   b. 调用构造函数初始化对象
   c. 把内存地址赋给 instance 引用

线程 A（持锁）                线程 B（第一次检查处）
a. 分配内存
c. instance = 地址   ──────────► ① instance != null → 跳过 synchronized！
   （对象还没初始化）              返回 instance ──► B 拿到【半成品】
b. 初始化对象字段                   （字段是零值/null，用它就 NPE）

volatile 的写屏障：c 之前的 b 不允许重排到 c 之后 —— B 要么看到 null，要么看到完整对象

CAS 与原子类 高频★★★★

CAS：硬件级乐观并发

CAS（Compare And Swap）："我认为内存位置 V 的值应该是 A，如果是，就把它换成 B；如果不是（说明有人先改了），就失败，我重试"。它是一条 CPU 指令（x86 的 lock cmpxchg），不是 Java 代码，天然原子。

AtomicInteger.java（JDK 源码脉络）i++ 的无锁实现
public class AtomicInteger {
    private volatile int value;   // volatile 保证可见 —— CAS 的前提是读到的旧值是最新的

    public final int getAndIncrement() {
        // Unsafe：JDK 内部直接操作内存的工具类（模块 9 反射也提它）
        return unsafe.getAndAddInt(this, VALUE_OFFSET, 1);
        // 循环体（自旋）：
        //   int old = getIntVolatile(obj, offset);   // 读当前值 old
        //   int next = old + 1;                       // 算新值
        //   if (compareAndSwapInt(obj, offset, old, next)) // CAS：没人动过才写入
        //       return old;                           // 成功退出
        //   // 失败（有人先改了）→ 不睡觉不阻塞，立刻重读重试 —— 这就是【自旋】
    }
}

这套"读旧值→改→CAS 失败重试"的循环就是乐观锁思想。你在批注系统里已经写过一遍它的应用层版本：POST 带 baseUpdatedAt，409 冲突就"拉最新→合并→重推一次"——同一个思想的两个实现层级（应用层用时间戳比较，硬件层用旧值比较）。

        thread1 ─┐

        thread3 ─┘      热点

LongAdder（JDK8，分段削热点）:

        thread2 ──► CAS [ Cell[0] ]  ┐
        thread3 ──► CAS [ Cell[2] ]  ├─── 竞争激烈时按线程哈希分散到不同 Cell
        thread4 ──► CAS [ Cell[5] ]  ┘    每格独立 CAS，热点被摊薄

乐观锁 vs 悲观锁，怎么选？高频

本质是冲突频率假设不同：悲观锁假设冲突频繁（先加锁再操作，别人排队等），乐观锁假设冲突稀少（先操作，提交时验证，失败重试）。读多写少/冲突低→乐观（CAS、数据库 version 字段、批注系统的 baseUpdatedAt）；写多/竞争激烈→悲观（synchronized、select for update），因为乐观锁重试的成本会超过直接阻塞。临界区很大时也选悲观——乐观锁只适合小而快的操作（重试整个大事务代价高）。

为什么 AtomicInteger 内部要 volatile？CAS 不是已经保证了吗？易错

CAS 指令保证的是"比较+交换"这一下的原子与可见，但 CAS 前面还有一步读取旧值（getIntVolatile）。这一步必须读到最新值——否则拿着过期旧值去 CAS，永远失败（别人的新值和你的旧值不等，且永远不会相等），陷入无意义自旋。所以 value 必须 volatile：读最新、写立即可见。这也说明"可见性是原子性的前置条件"，两个特性不是并列关系。

JIT 锁优化（回收模块 5 钩子③）

  • 锁消除：逃逸分析（模块 5）判定锁对象不逃出方法/线程，直接删锁。典型：sb.append() 内部有 sync，但局部 StringBuffer sb = new StringBuffer() 从未逃逸 → append 的锁全被消除。这也是"局部 StringBuffer 比 Builder '理论慢'实际不慢"的原因。
  • 锁粗化：循环里反复对同一对象加解锁（for(i..) synchronized(obj){...}）→ JIT 粗化成循环外加一次大锁，摊薄开销。

synchronized 是可重入锁吗？怎么实现的？高频

是。同一线程可以重复获取自己已持有的锁（A 里调 B，两个方法都 sync 同一对象，不死锁）。实现：偏向/轻量级靠"Mark Word 里记录的线程是自己"；重量级靠 ObjectMonitor 的 _recursions 计数器 +1，解锁时 -1，归零才真释放。ReentrantLock 同理（AQS 的 state 从 0 变 2 再变回 0）。可重入是防"自己锁死自己"的刚需，任何生产级锁都必须可重入。

自旋锁好还是挂起（阻塞锁）好？

取决于等待成本 vs 切换成本。线程挂起+唤醒需要用户态/内核态切换（微秒级），如果临界区只有几十纳秒，"原地自旋等一下"远比"睡一觉再被叫醒"便宜——自旋赢。但临界区长或竞争线程多时，自旋 = 白白烧 CPU，不如挂起让出核——阻塞赢。JVM 的方案是两者混合：轻量级先自适应自旋，转不动了才膨胀挂起。面试可延伸：synchronized 的这个策略本质上就是"先乐观（自旋=CAS重试）后悲观（挂起排队）"。

AQS：一个框架统治半个并发包 难点

AbstractQueuedSynchronizer 是并发包的基座——ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 全是它的子类（模板方法模式：子类只重写"怎么算 state"，排队/阻塞/唤醒全由父类管）。三个核心部件：

① state（volatile int）—— 同步状态的语义由子类定义：
   ReentrantLock: 重入次数（0=无人持有）
   Semaphore:     剩余许可数
   CountDownLatch: 剩多少个计数
   读写锁:        高 16 位=读次数 | 低 16 位=写重入数（一个 int 拆两半用）

② CLH 变体双向队列 —— 抢不到锁的线程包装成 Node 排队：
   head ──► [Node A] ◄──► [Node B] ◄──► [Node C] ◄── tail
     │                          │
   虚拟头节点               每个节点内 thread 字段 + waitStatus
   （哨兵，方便唤醒后继）   抢锁失败的线程在这里 park 挂起

③ 独占 / 共享两种模式 ——
   独占（exclusive）：同一时刻一个线程持锁   → ReentrantLock
   共享（shared）：  多线程可同时通过       → Semaphore / CountDownLatch / 读锁

加锁主流程（非公平 ReentrantLock.lock()）：
   CAS(state: 0→1) 成功 → 拿锁走人
   失败 → addWaiter 入队尾 → 自旋看前驱是不是 head → 是则再 CAS 试一次
        → 还失败 → park 自己（LockSupport.park，线程进 WAITING 态）
   解锁：state 减到 0 → unpark 后继节点（它醒来继续自旋 CAS）

private final ReentrantLock lock = new ReentrantLock(false); // true=公平锁
private final Condition notFull  = lock.newCondition();  // 条件1：队列不满
private final Condition notEmpty = lock.newCondition();  // 条件2：队列不空

public void produce() throws InterruptedException {
    lock.lock();                       // 注意：lock() 在 try 【外】
    try {                              // 防止 lock 本身抛异常时 unlock 一个未持的锁
        while (queue.size() == CAP) notFull.await();   // 条件不满足则让出锁并等待
        queue.offer(item);
        notEmpty.signalAll();          // 唤醒等"不空"这个条件的消费者
    } finally {
        lock.unlock();                 // ★ 必须放 finally，否则异常时锁永久泄漏
    }
}

追问：公平锁和非公平锁的实现差异就一行？

追问：Condition 和 wait/notify 的区别？
①一个锁多个条件队列（生产/消费者各等各的，notify 能精确叫醒同类），synchronized 全体挤一个 WaitSet，notify 随机叫醒可能叫错人（消费者叫醒消费者）只能用 notifyAll 兜底、惊群；②await 可中断、可限时。语义上 await/signal 与 wait/notify 一一对应，且同样必须持锁调用。

线程间通信

wait/notify 为什么必须在 synchronized 内？高频★★★

不是语法洁癖，是防丢失唤醒的硬需求：

没有锁保护的竞态窗口：
线程 A（消费者）                     线程 B（生产者）
1. if (queue.isEmpty())     ── 检查：空 ✓（决定要等）
                                2. queue.add(item)     ── 放入数据
                                3. notify()             ── 叫人（此刻还没人在等！通知蒸发）
4. wait()                   ── 进入等待 ──► 永远没人再 notify ──► 死等

有锁保护时：A 持锁做 1-4 期间，B 的 2-3 必须等锁 —— 检查和入睡是原子的，
通知不可能落在"已检查但还没睡下"的窗口里。这就是 IllegalMonitorStateException
的设计动机：不持锁就让你 wait，等于给你留丢唤醒的坑

配套的两个纪律：① 检查条件必须用 while 不用 if（被唤醒后条件可能又被别人破坏了，必须复查）；② 优先 notifyAll（notify 随机叫一个，可能叫错类别的线程，导致最终无人能推进——"丢失唤醒"的变体）。

park/unpark：顺序无关的精确唤醒

维度wait / notifypark / unpark
前提必须持 monitor 锁无锁要求（AQS 框架内部协调好锁）
顺序notify 先到 = 通知丢失（没人等，白叫）unpark 先到 = 许可证存着，park 时直接通过
精度随机唤醒一个/全部精确到线程（unpark(thread)）
底层ObjectMonitor 的 WaitSet每线程一个 permit（0/1 二元信号量）

permit 不会累积（unpark 两次再 park 两次，第二次 park 还是会睡）——这个细节偶尔出现在追问里。

生产者-消费者：两种实现对照

ProducerConsumer.javawait/notifyAll 版 vs Condition 版
// 版本一：synchronized + wait/notifyAll（教学经典版）
class Buffer1 {
    private final Queue<Integer> q = new LinkedList<>();
    private final int cap = 10;
    public synchronized void put(int v) throws InterruptedException {
        while (q.size() == cap) wait();      // while 复查条件（防虚假唤醒/被插队）
        q.offer(v);
        notifyAll();                          // 只能叫醒所有人，惊群
    }
    public synchronized int take() throws InterruptedException {
        while (q.isEmpty()) wait();
        int v = q.poll();
        notifyAll();
        return v;
    }
}

// 版本二：ReentrantLock + 两个 Condition（生产版，队列分流、精确唤醒）
class Buffer2 {
    private final Queue<Integer> q = new LinkedList<>();
    private final int cap = 10;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    public void put(int v) throws InterruptedException {
        lock.lock();
        try {
            while (q.size() == cap) notFull.await();
            q.offer(v);
            notEmpty.signalAll();             // 只叫等"非空"的消费者，不惊动同行
        } finally { lock.unlock(); }
    }
    // take() 对称：notEmpty.await() / notFull.signalAll()
}

什么是虚假唤醒（spurious wakeup）？为什么 wait 必须放 while 里？易错

两个来源：①OS 底层（pthread）允许在无 notify 时唤醒线程（性能优化允许实现这么干）；②被唤醒后、拿到锁前，条件可能已被其他先醒的线程消费掉（比如唯一的数据被先醒的消费者取走了）。所以醒来后必须重查条件，不成立接着睡——这就是 if 改 while 的全部理由。Javadoc 原话就是 "should always be used in a loop"。

ThreadLocal 完整篇 高频★★★★

思想：不共享才是最彻底的线程安全

解决数据竞争有两条路：抢（锁/CAS）或分（每线程一份副本，各玩各的）。ThreadLocal 走第二条——synchronized 是"时间换空间"（串行访问共享），ThreadLocal 是"空间换时间"（每人一份，零竞争）。典型用途：用户上下文透传（Web 请求的登录信息一路带下去）、SimpleDateFormat 隔离（它非线程安全）、数据库连接绑定。

结构：Thread 持有 Map，key 是 ThreadLocal 难点

            Thread 对象（每线程一份，引用在 Thread 上，不在 ThreadLocal 上！）
            ┌─────────────────────────────────┐
            │  threadLocals: ThreadLocalMap   │
            │   ┌──────┬──────┬──────┐        │
            │   │Entry │Entry │ ...  │        │   Entry extends WeakReference<ThreadLocal>
            │   │ key: ─┼─► (弱引用 ThreadLocal 对象)
            │   │ val: 用户数据                   key 弱引用 = 钩子①：模块 5 四种引用
            │   └──────┴──────┴──────┘        │
            └─────────────────────────────────┘
                          ▲
   ThreadLocal<T> tl = new ThreadLocal<>()  —— tl.set(v) 时：
   当前线程.getThreadLocalMap().set(tl, v)
   所以"同一个 ThreadLocal 实例"在每个线程的 Map 里各有一个 Entry —— 天然隔离

两个反直觉的点：① Map 在 Thread 身上，不在 ThreadLocal 上（这样多线程访问的是各自的 Map，Map 本身无竞争）；② Map 的 key 是弱引用（回收模块 5 钩子①的用武之地）。哈希冲突用开放寻址（线性探测）而不是链表——和 HashMap 的拉链法形成对照。

内存泄漏完整链路（面试拉分题）难点★★★★

泄漏链条（4 步）：
① 强引用断开：ThreadLocal 对象在外部没了引用（比如方法局部变量出栈 / 静态字段置 null）
② GC 回收 ThreadLocal：Entry 的 key 是【弱引用】，拦不住 GC —— key 变成 null
③ 但 value 还活着：Entry → value 是【强引用】，Entry 被 Thread.threadLocals 持有
④ 线程不死，value 永不可达地活着：
   普通线程：run() 结束 → Thread 死 → Map 整个回收 —— 无泄漏（短暂延迟而已）
   ★线程池线程：核心线程【永不退出】→ threadLocals 跟着永生
     → value 既无法访问（key=null 找不到）也永远不回收 = 内存泄漏

弱引用为什么不是"设计缺陷"而是"止损"：
   若 key 用强引用：外部断了引用 ThreadLocal 也回收不了（Map 还攥着）
   —— ThreadLocal 本体 + 它的 Class + 关联类加载器全部泄漏（更惨）
   弱引用至少保证 ThreadLocal 本体能被回收，只剩 value 这一段尾巴

JDK 的自救 + 它为什么不够：
   set/get 时探测到 key=null 的 Entry（stale entry）会顺手清掉它的 value
   （expungeStaleEntry 线性清扫）—— 但这只在【你再调用这个 map】时触发，
   用完就不碰的 Entry 永远等不到清理

标准答案：try { tl.set(user); ...业务... } finally { tl.remove(); }
   —— 防泄漏 + 防线程池"下一个任务读到上一个任务的脏数据"（数据串号，比泄漏更危险）
ThreadLocal 的 key 用弱引用是不是为了解决内存泄漏？易错

常见误区。弱引用不能解决泄漏，只是把泄漏范围从"整个 ThreadLocal 对象"缩小到"单个 value"（见上图对比）。真正的解法永远是显式 remove()。这道题的回答姿势：先纠正"弱引用解决泄漏"，再讲"弱引用是止损不是解药"，最后落到 finally remove——三个层次全答对才算过关。

父子线程怎么传递 ThreadLocal？线程池为什么会失效？

InheritableThreadLocal：子线程创建时把父线程的表拷贝过来——但"创建时"三个字就是它在线程池的死穴：池线程只创建一次、反复复用，第一次任务后再 set 的值，后续任务根本拿不到（拷贝发生在你控制不了的时机）。解法：阿里 TransmittableThreadLocal（TTL，装饰 Runnable 在任务提交时快照、执行时回放）或显式传参/消息体携带上下文。这题是"你真用过吗"的试金石。

Python 的 threading.local 和这个一样吗？Python 对比

思想完全相同（每线程一份字典，属性访问自动路由到当前线程的副本），实现差异：Python 版是动态属性字典（local.x = 1 随便挂属性），Java 版是强类型容器（一个 ThreadLocal 实例对应一个槽，类型固定）。Python 没有"弱引用 key"的泄漏戏码——它的 local 对象被 GC 时会触发 cleanup；Java 的复杂度来自"Map 放在 Thread 上 + 线程池复用线程"这两个工程现实。

线程池 高频★★★★★

为什么需要线程池

线程是昂贵资源：创建销毁有开销（用户态栈内存约 1MB + 内核调度对象）、无上限创建会拖垮系统（线程过多 → 上下文切换风暴 → OOM）。池化的三个收益：复用（摊薄创建成本）、限流（并发度受控）、管理（统一命名、监控、优雅关闭）。

先入队。队列排满才考虑扩到 maximumPoolSize。这和直觉相反（"人手不够应该先加人"），设计意图是扩线程是最后手段——线程是昂贵资源，队列（内存）便宜得多。推论：用无界队列（如默认 LinkedBlockingQueue 无参构造）时，队列永远不满 → maximumPoolSize 形同虚设，临时线程永远不建 → 削峰全靠队列堆积 → 任务无限堆积直到 OOM。这就是阿里规约禁用 Executors.newFixedThreadPool 的根源（它就是无界队列）。

策略行为适用
AbortPolicy（默认）抛 RejectedExecutionException，调用方感知失败能自行降级/重试的调用方（fail-fast）

ConcurrentHashMap：模块 4 伏笔的完整回收

模块 4 讲过 HashMap 并发 put 会成环死循环（JDK7 头插）或丢数据，结论是"并发场景换 ConcurrentHashMap"。现在补齐它自己怎么做到安全：

维度JDK 7（分段锁）JDK 8（CAS + 桶头锁）
结构Segment 数组，每段一个小 HashMapNode 数组 + 链表/红黑树（结构同 HashMap）
锁粒度段级（默认 16 段，最多 16 线程并发写）桶级（锁单个桶头节点）+ 空桶 CAS 无锁插入
getvolatile 读，无锁volatile（Node.val/next），无锁
put锁 Segment（继承 ReentrantLock）空桶 CAS 插入；非空桶 synchronized(头节点)
size各段 count 相加baseCount + CounterCell[] 分段计数（LongAdder 思想）

ChmTrap.java线程安全容器 ≠ 用它写什么都安全
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// ❌ 陷阱：check-then-act 两步，中间可被别的线程插队
if (!map.containsKey(k)) {        // 检查
    map.put(k, computeHeavy());   // 动作 —— 两个线程可能都通过了检查，跑两次 compute
}

// ✅ 正解：用容器提供的原子复合方法（内部一次锁内完成检查+动作）
map.putIfAbsent(k, computeHeavy());          // 存在则不覆盖
map.computeIfAbsent(k, key -> computeHeavy()); // 存在则返回现值，absent 才计算（推荐，惰性）
map.merge(k, 1, Integer::sum);                // 计数器经典写法：v 新增 1，旧值+1

// 大坑提示：computeIfAbsent 的 mapping function 里【不能再操作同一个 map】——
// JDK9+ 会抛 IllegalStateException（递归更新死锁风险，JDK8 会死循环/挂起）

CopyOnWriteArrayList：读多写少的极简方案

写：拿锁 → 复制整个数组 → 在副本上改 → 把引用指向新数组（volatile array）
读：不加锁，读当前引用的数组快照 —— 永远读到"某一时刻的完整版本"

效果：读写不互斥（读的是旧快照也无所谓，反正不可变）、无 ConcurrentModificationException
代价：①写 O(n) 复制（大数组高频写 = 性能灾难）
      ②弱一致：读到的可能不是最新（迭代器是创建时的快照）
适用：白名单/黑名单/配置项/监听器列表 —— 读极多、写极少、量不大

锁工具与死锁排查

读写锁：读多写少的精细化互斥

ReentrantReadWriteLock 规则：读-读共存，读-写互斥，写-写互斥。实现就是 AQS 的 state 拆两半：高 16 位读计数、低 16 位写重入数（§8 埋的点）。两个方向的不对称是高频追问：

  • 锁降级（写→读）允许：写锁内先拿读锁再放写锁——用于"改完后还要基于新值读"且不想让别人插进来改的场景（例：缓存刷新后立刻读返回）
  • 锁升级（读→写）不允许：两个读线程同时想升级，各自等对方放读锁——死锁，所以 API 直接不支持（同一线程拿写锁前必须完全释放读锁）

死锁：四条件与排查

死锁四必要条件（缺一不可）：
① 互斥：资源一次只能一人用（锁的本性）
② 持有并等待：攥着自己的资源，还要别人的
③ 不可剥夺：不能强行抢走别人手里的锁
④ 循环等待：A 等 B 持有的，B 等 A 持有的 —— 成环

    线程1: lock(A) ──lock(B)──►  等待线程2 放 B
    线程2: lock(B) ──lock(A)──►  等待线程1 放 A     ◄── 死环，永远互等

破坏策略（①是锁的本身不能破，攻②③④）：
② 一次性申请所有资源（拿不到就都不拿）
③ tryLock 带超时：拿不到就放掉已持有的，退避重试
④ 【按固定顺序加锁】—— 最常用、成本最低：所有线程都先锁 A 再锁 B，环就成不了

排查：jstack <pid> 日志末尾直接打印
  "Found one Java-level deadlock:"  +  两个线程各自等哪个锁、持哪个锁、卡在哪行
  （这就是为什么 ThreadFactory 必须给线程命名 —— 日志里 thread-1/thread-2 等于白排查）

CountDownLatch 和 CyclicBarrier 本质区别是什么？高频

视角不同：CountDownLatch 是"等事件"——一个/多个线程等 N 件事发生（countDown 的是"完成方"，await 的是"等待方"，两拨人角色固定）；CyclicBarrier 是"等彼此"——N 个线程互相等齐了一起走（参与等待的和被等的是同一拨人）。所以前者不可复用（计数归零即作废）而后者可循环（一轮结束自动重置）。一句话记忆：Latch 等"别人干完活"，Barrier 等"队友到齐"。

Semaphore 能代替线程池做限流吗？

不能，但常配合。线程池限的是"同时执行的线程数"（执行侧资源），Semaphore 限的是"同时进入临界区的并发数"（可以是任意代码段、任意线程来源，比如 50 个池线程里只放 10 个并发去调下游）。你的项目里"第三方 API 有 QPS/并发数限制"的标准解法：线程池管吞吐 + Semaphore（或 Guava RateLimiter 管速率）管并发——两者维度不同。Python 里这个组合你写过：asyncio.Semaphore + 事件循环。
