第 1 章 · MRO：类找方法的路线图P0 高频考点

1.1 为什么出现：多继承的歧义问题

普通函数调用没有歧义：方法名写在哪，就去哪找。但多继承一出现，麻烦就来了——一个方法同时出现在多个父类里，到底先去哪个找？

MRO（Method Resolution Order，方法解析顺序）就是答案：它是一个元组，把从当前类到 object 的所有祖先类按线性顺序排好。运行时查找方法，就是沿这条队伍从头到尾问一遍，谁先应答用谁的。

🏠 比喻：族谱排队

把一个类的所有祖先想象成一支排好队的家族队伍：自己站第一排，爸爸们按声明顺序站第二排，爷爷们往后排，object 永远垫底。找方法就是从队头往队尾挨个问「你有 who 吗？」，第一个说「有」的就成交，后面的不再打扰。

1.2 C3 线性化：三条规则

CPython 用 C3 线性化算法计算这个顺序，规则就三条：

  1. 子类永远排在父类前面（不然爸爸会抢儿子的方法）；
  2. 多个父类按声明顺序排（class D(B, C) 里 B 先于 C）；
  3. 同一个类只出现一次（菱形继承的共同祖先去重）。
class A:
    def who(self): print("A")

class B(A):
    def who(self): print("B")

class C(A):
    def who(self): print("C")

class D(B, C):      # 菱形继承：D → B、C → A
    pass

D().who()           # 输出 B —— 沿 MRO 先找到 B 的，C 根本没被查
D.__mro__           # (D, B, C, A, object) —— 这条队伍就是 MRO
# 队伍怎么来的：
#   规则1：D 排最前（子类在前）
#   规则2：B 在 C 前（class D(B, C) 的声明顺序）
#   规则3：A 只出现一次（B、C 共同的祖先去重，排在他们之后）

如果继承图无法线性化（比如两个类互相要求对方在前），Python 会直接报 TypeError: Cannot create a consistent method resolution——不给运行时埋雷。

展开：菱形继承的查找路径图
MRO：菱形继承的查找路径
D 继承 B 和 C，B、C 都继承 A；C3 线性化为 D → B → C → A → object

1.3 super() 走序列，不走继承图

最容易考的一问：super() 到底跳到哪？直觉答案是「父类」，这是错的。正确答案是：跳到 MRO 的下一个类。

⚙️ 机制：super() 等价于 super(B, self)

super() 的落点不是编译期定的，是运行时按两步算出来的：拿 type(self).__mro__ → 在这条队伍里找到当前类（比如 B）→ 从下一位开始找。B 的下一位是谁？由实例的类的 MRO 说了算，跟「B 的父类是谁」无关。

class A:
    def who(self): print("A")
class B(A):
    def who(self):
        print("B")
        super().who()      # 落点运行时才知道 —— 关键就在这行
class C(A):
    def who(self):
        print("C")
        super().who()
class D(B, C): pass

B().who()   # 输出 B A  ← B 实例：MRO=(B, A, object)，super 跳到 A
D().who()   # 输出 B C A ← D 实例：MRO=(D, B, C, A, object)，B 里的 super 跳到 C！
🧑‍🎓 追问（原话）

「第一个问题是 D 走到 B，我可以理解 D 应该也走到了 C，而不是说 B 里面的 super who 走到了 C。B 和 C 没有关系啊？」

这个追问质量很高，答案分两层：

机制谁发起走法
属性查找 d.who()解释器沿 MRO 找到第一个命中就停：D → B，结束。C 从头到尾没被查过
super() 链你写的代码沿同一条 MRO 显式往下续：B → C → A

所以「走到 C」的不是查找，是 B 方法体里那句 super().who()。B 和 C 之间确实没有继承关系——但它们是 D 的线性化序列里的邻居；super 走序列，不走继承图。这就是为什么 mixin 模式能工作：mixin 不需要认识谁，只要它在最终类的 MRO 里排对位置就行。

🎭 面试作答：MRO 与 super()

30 秒版：MRO 是类查找方法的线性顺序，CPython 用 C3 线性化计算：子类在前、父类按声明顺序、去重。super() 不是跳到父类，是跳到「实例类的 MRO 里当前类的下一位」——落点由实例决定，不由代码位置决定。

2 分钟版：先讲问题来源：多继承时方法可能出现在多个父类，需要一条无歧义的查找顺序。再讲三条规则和菱形继承例子（D→B→C→A→object）。然后甩出关键区分：属性查找找到第一个命中就停；super() 链是显式沿同一条 MRO 往下续。举例：同一份 B.who() 代码，B 实例上 super 跳到 A，D 实例上跳到 C——因为 super() 等价于 super(B, self)，运行时取 type(self).__mro__ 找下一位。最后补一句：MRO 无法线性化时直接 TypeError，错误在类定义期就暴露。

第 2 章 · ob_type 与 __dict__：对象的内部世界P1 高频考点

2.1 类型对象就是类：三个容易混的概念

讨论对象模型之前，先把三个词拆干净：

概念是什么一句话
ob_type字段名每个对象头部那个类型指针，指向「它的类型」
类型对象就是类type(42) 是 int、type(d) 是 D——你自己写的类同样是类型对象；类自己也是对象，type(D) 是 type
object根类所有类隐式继承它，每条 MRO 的最后一站，兜底提供 __init__、__repr__
🧑‍🎓 追问（原话）

「object type 不是 int、string 那些吗？难道 object type 可以是类？一个对象去找方法的时候，会走到 object type 这个类，这个类又有它的一个 MRO，进行了 C3 线性化，然后去里面一个一个去找方法？」

这段复述只改一个词就全对：对象找方法时走到的是它自己的类（D），不是「object type 这个类」。链路是：d --ob_type--> D --__mro__--> 逐类翻 __dict__。int、str 是类，你自己写的 D 也是类——类型对象不神秘，它就是类。

2.2 __dict__：对象的「属性仓库」

每个对象身上（几乎）都有一个 __dict__，就是个字典，存这个对象自己的属性。分两种：

class Point:
    color = "red"                  # 类属性 → 存进「类的 __dict__」

    def __init__(self, x, y):
        self.x = x                 # 实例属性 → 存进「实例的 __dict__」
        self.y = y

    def show(self):                # 方法 → 也存进「类的 __dict__」
        return f"({self.x}, {self.y})"

p = Point(1, 2)

p.__dict__        # {'x': 1, 'y': 2}  ← 实例仓库：只有数据，没有方法
Point.__dict__    # mappingproxy({'color': 'red', '__init__': ..., 'show': ...})

四条要点：

  • 方法不住在实例身上，住在类的 __dict__ 里。第 1 章说「沿 MRO 逐类查 __dict__」，查的就是这排仓库——哪个仓库先命中用哪个；
  • 取属性的完整路径：p.x 先翻 p.__dict__（命中返回）；p.color 实例仓库没有 → 沿类的 MRO 翻类仓库；全没有才 AttributeError；
  • 赋值只写实例仓库：p.color = "blue" 往 p.__dict__ 加了一条，把类里的 "red" 遮住（shadow），类的 __dict__ 纹丝不动——这就是为什么改一个实例不影响别的实例；
  • 两个花边：类的 __dict__ 是 mappingproxy（只读视图，防止绕过语法直接塞东西进类）；定义了 __slots__ 的类没有 __dict__，属性存在固定槽位——「__slots__ 省内存」的原理就在这。
🏠 比喻：两层仓库

实例仓库是你随身的口袋，类仓库是全村共用的祠堂。找东西先掏口袋，口袋没有再去祠堂（按 MRO 的顺序挨家祠堂问）；往口袋里放新东西不会动祠堂，所以你改自己的不影响别人。

2.3 ob_type 的用处：它是「行为说明书」

🧑‍🎓 追问（原话）

「这个 object type 有什么用？是用于 type 包裹的时候去判断它的类型吗？」

type() 判断只是它最不重要的一个用途。ob_type 真正的身价是：Python 一切动态行为都靠它决定「这个对象该怎么表现」。

用途例子说明
类型判断type(x) is int、isinstance(x, T)type() 只是读出 ob_type 指向谁
方法派发d.show()沿 ob_type 指向的类的 MRO 找 show——第 1 章的链路
运算符行为1 + 2、"a" + "b"执行引擎查 type(左值) 的 __add__，同一运算符不同类型不同结果
迭代/长度for x in obj、len(obj)查它的类有没有 __iter__、__len__
造类本身type("D", (B, C), {...})type 是「类的类」（元类），类都是它造出来的

一句话：ob_type 指向的类型对象是所有行为的说明书。判断类型只是翻开说明书看封面，方法派发和运算符分派才是每行代码都在用的功能。

2.4 属性查找的完整链路（把两章拼起来）

d = D()
d.__dict__          # {} —— 实例身上没有 who
'who' in D.__dict__ # False
'who' in B.__dict__ # True ← 方法住在 B 的 __dict__ 里
type(d).__mro__     # (D, B, C, A, object) ← 查找沿这条走
# 完整链路：d --ob_type--> D --__mro__--> 逐类翻 __dict__，B 命中
🎭 面试作答：__dict__ 与属性查找

30 秒版：每个对象有 __dict__ 属性仓库：实例仓库存实例属性，类仓库存类属性和方法。取属性先翻实例 __dict__，没有再沿 type(X) 的 MRO 逐类翻类 __dict__，全没有才 AttributeError；赋值只写实例仓库，遮住类属性但不修改它。

2 分钟版：展开三条：一是方法住在类 __dict__ 而非实例身上，这解释了为什么一千个实例共享一份方法、内存不爆炸；二是 shadow 机制：p.color = "blue" 只是实例口袋里加了一条，类仓库不动，其他实例不受影响；三是 __slots__：定义后实例没有 __dict__，属性存固定槽位，省掉每个实例一个字典的开销——大规模对象（比如百万级数据类）的常规优化。最后点题：这套「口袋+祠堂」的两层结构，配合 MRO，就是 Python 属性系统的全部。

第 3 章 · 魔术方法 vs 魔术属性P1 概念辨析

3.1 一个 callable 判别法

🧑‍🎓 追问（原话）

「我之前应该让你给我展示过它的一个魔术方法，但是你好像并没有给我展示这个 dict 属性。我就奇怪，这个 dict 是魔术方法吗？如果是的话，它还有别的魔术方法，你没有给我说明吗？」

答案：__dict__ 不是魔术方法，是「魔术属性」。双下划线家族其实分两支，判别标准一句话：魔术方法是「函数」，被你写的语法隐式调用；魔术属性是「数据」，挂在你身上等你主动去读。

callable(d.__dict__)     # False —— 是个字典，不是函数 → 魔术属性
callable(Demo.__init__)  # True  —— 魔术方法，可调用
callable(d.__call__)     # True  —— 魔术方法，可调用
🏠 比喻：钩子 vs 数据兄弟

魔术方法是钩子：你写 d + other、len(d)、with d:，Python 替你悄悄调用对应的 __add__、__len__、__enter__——你不喊它，它只在语法触发时出现。魔术属性是数据兄弟：__dict__、__mro__、__closure__ 只是安静挂在身上的仓库和账本，你不主动读它就永远不工作。

3.2 魔术方法全景表

类别代表方法被什么触发

字符串表示__repr__、__str__、__format__print(x)、f-string

值得盯住的细节：一个「全副武装」的演示类里，整个脚本没有一处显式调用 .__add__()、.__len__()——全是 d + Demo(1)、len(d) 这种普通语法，钩子被隐式触发。还有一个彩蛋：list(d) 会多触发一次 __len__——因为 list() 构造时会先问对象「你大概多长」来预分配空间，协议之间也会互相调用。

3.3 魔术属性的来源：三线供应

🧑‍🎓 追问（原话）

「我知道 __init__、__call__ 这几个魔术方法是由元类提供的；而关于迭代、调用、运算符比较以及上下文等一些魔术方法，是由 object 类提供的。那我想知道，魔术属性应该也是由 object 类提供的吧？」

两个前提都要修，先看事实：

  • 「__init__、__call__ 由元类提供」——半对。 Demo(3) 这整个动作确实走元类：type.__call__ 在 type 身上，它内部再去调 __new__ 和 __init__。但 __init__/__new__ 本身是 object 提供的（证据：Demo.__init__ is object.__init__ → True，你没写 init 时直接用 object 的）；而 d()（实例被调用）查的是 Demo 的 __call__，object 不提供，得自己写；
  • 「迭代、运算符、上下文由 object 提供」——不对。 object 只提供一小撮默认：__init__、__new__、__repr__、__eq__、__hash__。__iter__、__len__、__add__、__enter__ 没有任何默认实现，你不写就是 TypeError: object is not iterable。这正是鸭子类型的立足点：协议靠你实现，不靠从 object 白拿。

魔术属性的完整答案是分三线供应，规则统一：

谁的魔术属性描述符挂在哪例子
实例的object 身上 + 造类时注入每个类的命名空间__dict__（getset_descriptor）、__class__
类的type 身上__mro__（member_descriptor）、__name__、__bases__
函数的FunctionType 身上__code__、__closure__、__defaults__

统一规则：查 X 的魔术属性和查普通属性走同一条路——沿 type(X) 的 MRO 找。实例沿 (Demo, object)，类沿 (type, object)，函数沿 (FunctionType, …)。魔术属性不是特殊通道，找到的只是一个 C 级描述符。两个收尾认识：描述符和数据是分离的——描述符只定义「怎么读写」，数据存在每个对象自己的 C 结构里，所以 d.__dict__ 是 {'x': 1} 而 d2.__dict__ 是 {}；例外是 __wrapped__——object 和 type 身上都没有它，它是 functools.wraps 手动塞的普通属性。

🎭 面试作答：魔术方法 vs 魔术属性

30 秒版：双下划线家族分两支：魔术方法是函数钩子，被语法隐式触发（len() 触发 __len__、+ 触发 __add__）；魔术属性是数据（__dict__、__mro__、__closure__），要主动去读。判别法一条：callable() 测试。来源上，魔术属性沿 type(X) 的 MRO 查，描述符分别在 object、type、FunctionType 身上。

2 分钟版：先给判别法，再给全景表里的三四个高频族（容器协议、比较哈希、上下文管理、异步协议）。然后讲两个容易答错的细节：一，object 只提供 __init__/__new__/__repr__/__eq__/__hash__ 等一小撮默认，__iter__/__len__/__add__ 没有默认实现——鸭子类型的协议是「你不写就没有」；二，「类() 被调用」这个动作本身走 type.__call__（元类），但 __init__ 的默认版本来自 object。最后点题：这套机制统一在「沿 type(X) 的 MRO 找属性」一条路上——Python 的对象模型没有第二套查找逻辑。

第 4 章 · 生成器协程：yield from 与 send()P0 高频考点

为什么叫「协程」？普通函数是调用-返回一次就结束；生成器是暂停-恢复多次产出值；加了 send() 之后还能接收外部传进来的值——函数和调用方能双向通信，这就有了协程的雏形。

4.1 send()：不只是取值，还能塞值进去

普通 yield 生成器是单向的（只产出）：

def gen():
    yield 1
    yield 2
    yield 3

g = gen()
next(g)    # 1  ← 取值
next(g)    # 2

给 yield 加接收能力——x = yield value：yield value 把 value 抛出去、暂停；下次 g.send(数据) 把数据塞回 yield 表达式，赋值给 x，函数继续跑：

def accumulator():
    total = 0
    while True:
        x = yield total      # 抛出 total，暂停；send(n) 时 x = n
        total += x           # 接收到外部传来的 x，累加

acc = accumulator()
next(acc)          # 0  ← 第一次必须 next「启动」，跑到第一个 yield，返回 total=0
acc.send(10)       # 10 ← 把 10 塞给 x，total=0+10=10，抛出
acc.send(20)       # 30 ← 把 20 塞给 x，total=10+20=30，抛出
acc.send(5)        # 35

send() 的两条规则：第一次必须用 next() 启动（首个 yield 前没有接收点，send 无处可塞，会报错）；send(v) 和 next() 一样返回下一个 yield 抛出的值——区别只是 next() 塞的是 None，send(v) 塞的是你指定的值。

展开：send() 双向通信时序图
send()：调用方与生成器双向通信
yield 既是出口（抛出值）也是入口（接收 send 的值）

4.2 yield from：委托子生成器

yield from 让一个生成器把产出职责委托给另一个生成器：

# 不用 yield from：手动逐个转发
def chain(a, b):
    for x in a:
        yield x      # 从 a 取一个，抛给调用方
    for x in b:
        yield x

# 用 yield from：直接委托整个子生成器
def chain(a, b):
    yield from a     # 把 a 的产出全部转发，a 结束才继续
    yield from b

list(chain([1, 2], [3, 4]))   # [1, 2, 3, 4]

它等价于把子生成器的每个值透传出去，但还做了三件手动 for 做不到的事：

yield from 自动做的事说明
1 值透传子生成器的产出直接给调用方
2 send 透传调用方的 send 塞回子生成器
3 return 透传子生成器的 return 值成为表达式结果：result = yield from sub

手动 for+yield 只能做第 1 件，后两件做不到。验证「return 透传」：

def sub():
    yield 1
    yield 2
    return "done"          # 子生成器的返回值

def outer():
    result = yield from sub()   # 透传 1、2；sub 结束后 result = "done"
    print(f"sub 返回: {result}")
    yield 3                    # sub 结束后 outer 继续

g = outer()
next(g)   # 1       ← sub 产出，透传给调用方
next(g)   # 2       ← sub 产出，透传
next(g)   # 打印 "sub 返回: done"，然后产出 3

yield from 的价值：把多层生成器串起来时，send 和 return 能穿透中间层直达底层。这是异步编程的基石——await 本质上是增强版的 yield from。

4.3 三件套与准协程

g = accumulator()
next(g)              # 启动

g.send(10)           # 塞值进去（数据通道）
g.throw(ValueError)  # 在 yield 处抛异常，生成器内可 try/except 捕获
g.close()            # 在 yield 处抛 GeneratorExit，生成器收尾退出

throw 让调用方能往生成器注入异常，close 通知生成器终止。三个方法让生成器从「被动产出器」变成「能接收值、能被注入异常、能被通知终止的受控执行体」——这就是协程的雏形。

把 send + yield from 拼起来，一个能接收数据、能委托的「准协程」：

def sub_accumulator():
    """子生成器：累加，send 进来的数加到 total"""
    total = 0
    while True:
        x = yield total      # 抛出 total，暂停等 send
        if x is None:        # None 表示结束信号
            return total     # 返回累加结果
        total += x

def main():
    result = yield from sub_accumulator()   # 委托，sub 的 return 值传给 result
    print(f"最终: {result}")

g = main()
next(g)         # 启动，sub 跑到 yield，返回 total=0
g.send(10)      # 10  ← sub 收到 10，total=10
g.send(20)      # 30
g.send(None)    # 打印 "最终: 30"，sub return 30 传给 result

整个链条：调用方 send → 外层 yield from 透传 → 子生成器收到并处理 → 子 return → 外层 result 接住。外层只做「接线」，真正干活的是子生成器。

🎭 面试作答：生成器怎么变协程

30 秒版：生成器本来只产出；PEP 342 加了 send/throw/close——send 把值塞回 yield 表达式，实现双向通信；PEP 380 加了 yield from——委托子生成器并透传产出、send、return。三者合起来，生成器成了能暂停恢复、能双向通信、能受控终止的执行体，就是协程雏形；async/await 底层就是这套协议。

2 分钟版：按演化讲：先讲 yield 单向产出（暂停-恢复），再讲 x = yield value 双向版（send 塞值、首次必须 next 启动、next 就是 send(None)），再讲 yield from 三件透传（值、send、return）——手动 for 只能做第一件。举例 accumulator：send(10) → total=10 → yield 10。最后收在 send/throw/close 三件套：这是「受控执行体」的完整协议，原生协程对象至今沿用同一套 send/throw/close，只是挂起点从 yield 换成了 await。

第 5 章 · async/await：从生成器协程到原生协程P0 高频考点

5.1 三个常见误解修正

学习者的类比（async=子生成器用 yield 收参数，await=外部调用 send 传参数）骨架对，三处要修——这三处正是面试的区分点：

误解修正
「async 用 yield 接收参数干活」这条通道 asyncio 压根不用：send 的永远是 None，只是「继续跑」的信号；原生协程里写 yield 会变成异步生成器（另一个东西）
「await 时传入参数」方向反了：await 是等结果。值走 yield from 的 return 透传通道（见下方 Future.__await__）
「我的代码驱动协程」驱动者是事件循环：唤醒、传值、抛异常全是循环和 Task 干的，你的代码只负责写 await
# Future.__await__ 的真身（简化）——值走 return 通道的铁证
def __await__(self):
    if not self.done():
        yield self           # 把 Future 抛给 Task：我还没好，先挂起
    return self.result()    # 值从这里 return，沿 await 链一路上传

5.2 状态总账房：Future / Task / 事件循环

🏠 比喻：取餐叫号屏、一桌的总账、总调度台

Future 是一次性的取餐叫号屏：PENDING → FINISHED（记 result 或 exception）/ CANCELLED，一个屏管一件事。Task 是一整桌的总账本：包住一条协程负责驱动，协程抛的异常记在 Task 身上，没人取才在 GC 时打警告。事件循环是总调度台：管三本账——就绪队列（谁该跑了）、定时器堆（何时该跑）、selector（I/O 好了没）。

5.3 跟一个 await 走完一圈（六步）

  1. Task.__step 调 coro.send(None)，协程跑到 await fut；
  2. fut 未完成：Task 把自己挂到 fut 的完成回调上，控制权还给循环；
  3. 循环去跑别的就绪任务，或用 selector.select(timeout) 等 I/O——单线程的「同时」就发生在这里；
  4. I/O 就绪：回调调 fut.set_result(数据)，顺手把 Task.__step 重新排进就绪队列；
  5. 轮到它：coro.send(None) 恢复，Future.__await__ 里 return self.result()，值沿 await 链上传；
  6. 协程继续跑到下一个 await，或结束（StopIteration.value 成为 Task 的结果）。

「谁成功谁失败」的用户出口：

results = await asyncio.gather(fetch_a(), fetch_b())   # 全成功给结果列表；一个失败立刻抛

async with asyncio.TaskGroup() as tg:                   # 3.11+：一个失败 → 取消其余 → 抛 ExceptionGroup
    tg.create_task(fetch_a())
    tg.create_task(fetch_b())

真正实现并发的杠杆是 create_task：await job() 是顺序（当场跑完才继续），create_task(job()) 才是把协程注册给循环、让它和别的任务交错跑。单线程并发 = 在 await 点之间来回切换，把 I/O 等待时间让给别人——I/O 密集赚翻，CPU 密集不加速（GIL 还在）。

🎭 面试作答：async/await 与生成器的关系

30 秒版：async/await 是生成器协程的语法分家：机制同源（协程对象一样有 send/throw/close，一样靠挂起帧暂停恢复，await ≈ yield from），但 asyncio 里 send 永远传 None（只是唤醒信号），数据走 Future.__await__ 的 return 通道上传；驱动者是事件循环，不是用户代码。

2 分钟版：先讲同源：PEP 342/380 让生成器有了双向通信和委托透传，3.4 时代用 @coroutine + yield from 写异步；3.5 分家出 async/await，原因是 yield 一身二职容易写错、且错误只在运行时暴露，原生协程把挂起点收窄为 await、定义期就检查 awaitable。再讲三条通道：唤醒通道 send(None)；数据通道 Future.result() 沿 await 链 return 上传；异常通道 task.cancel() → coro.throw(CancelledError)。最后讲杠杆：await 本身不产生并发，create_task 把协程注册给循环才产生交错——单线程并发发生在 select 等待的那一觉里。

第 6 章 · 事件循环与 selector：摸到内核门口P0 高频考点

6.1 协程是惰性的：没有循环它根本不跑

🧑‍🎓 追问（原话）

「原来 await 是顺序的，只有加入了事件循环，它才是一个并发的。没有事件循环它也还是阻塞呗。」

比阻塞更彻底：协程对象是惰性的，根本不会跑。async def 函数被调用只产出协程对象，一行代码都不执行，直到被 send() 驱动；asyncio.run() 的第一件事就是建循环。所以并发公式是：多任务 + 一个调度器，async/await 只贡献「挂起点」这个原材料，本身不给并发。

6.2 迷你事件循环：三个部件

手写一个 60 行的循环（不用 asyncio），核心就三个部件，对照 asyncio 内部：

迷你循环asyncio 里对应作用
ready 双端队列loop._ready就绪队列：下一个该跑的协程在这排队
timers 定时器堆loop._scheduled闹钟堆：(唤醒时刻, 协程)
coro.send(value)Task 里的 coro.send(None)驱动协程跑到下一个挂起点
StopIteration.valueTask 的结果协程 return 的值从这里捞出来
yield ("sleep", t)await asyncio.sleep(t)挂起时向循环递交「我要睡多久」
（没实现）selector（epoll）真实循环多这一样：I/O 就绪时叫醒任务
while ready or timers:                  # 还有活干就转
    if not ready:                       # 没人可跑 → 睡到最近的闹钟响
        wake_at, _, coro = heapq.heappop(timers)
        time.sleep(max(0, wake_at - time.monotonic()))
        ready.append((coro, None))
        continue

    coro, value = ready.popleft()
    try:
        request = coro.send(value)      # 驱动协程，直到下一个挂起点
    except StopIteration as e:          # 跑完了
        results[coro] = e.value         # return 值捞出来
        continue

    if request[0] == "sleep":           # 协程请求睡觉 → 上闹钟
        heapq.heappush(timers, (time.monotonic() + request[1], next(tick), coro))

当时对真实 asyncio 流程的复述被打分 90 分，被修正的三处细节（也是面试易错点）：

易错说法修正
「小顶堆，先执行时间短的任务」堆确实是小顶堆，但按到期时刻排，不是任务时长——弹出的永远是「下一个该响的闹钟」
「循环最后一步把 socket 交给 selector」注册发生在协程请求等待的那一刻（request 分支里）；select() 调用发生在没人可跑时——两件事时机不同
「操作系统和程序实时通信」OS 不推送，是程序主动问：select/epoll_wait 阻塞等待，OS 只在被问时回答「哪些 fd 就绪了」

「没有任务了就等着呗」——对，但分三种情况：ready 空但 timers/I/O 有货 → 阻塞在唯一的等待点等最近的事件（真实 asyncio 里 select(timeout=距最近闹钟)，I/O 和定时器共用这一个等待点）；全空 → while 条件不成立，循环退出收尾；有人不挂起（纯 CPU 循环）→ 单线程被独占，别人全卡住——协作式调度的代价。

6.3 selector：外包给操作系统的监控台

🏠 比喻：外包监控台

selector 是「外包给操作系统的监控台」——你把一堆 socket 登记给它，然后在一个地方睡觉，OS 谁就绪了就叫醒你并告诉你「是哪几个」。没有它，单线程想同时等 3 个连接，只能挨个 recv 试试（忙轮询烧 CPU）或者一个连接开一个线程（1000 连接就是 1000 线程）。它就是「一个线程 + 一次等待 + N 个连接」的那个开关。

三个动作对到代码就是三行：

  • 请求分支里 sel.register(target, EVENT_READ, data=coro)——登记，顺手把协程当包裹存进 data 字段；
  • 等待区 sel.select(timeout)——全脚本唯一一次真正的睡觉；
  • 醒来后 sel.unregister + key.data 取回协程塞回 ready。

关键道具是 data 字段：登记时把协程存在登记簿上，fd 就绪时从登记簿上把协程领回来——这就是 asyncio 里「Future.set_result 的完成回调把任务排回就绪队列」的迷你版。

任务 A 的完整闭环（六步对应六行代码）：

  1. coro.send(None) 跑到 yield from wait_read(r_A)，把 ("read", r_A) 抛给循环——协程挂起，它自己不碰 selector，只递申请单；
  2. 循环在 request 分支里 sel.register(r_A, EVENT_READ, data=coro_A)——fd 进登记簿，协程存进 data；
  3. ready 空了，循环算出 timeout = 0.30 - now = 0.15（距最近闹钟），调 sel.select(0.15)——线程在这里睡着，这一觉同时等两件事：3 个 fd 谁可读、闹钟响；
  4. t=0.20 后台线程 sendall，内核把 r_A 标记可读，select 立刻醒来返回 [(key_A, ...)]——是 OS 叫醒的，不是我们轮询发现的；
  5. sel.unregister(r_A)（一次性，用完即注销），key_A.data 领回 coro_A，塞进 ready；
  6. 下一轮 coro_A.send(None)，从 yield 处恢复，recv(1024) 拿到数据（fd 已被担保可读，绝不阻塞），函数 return，StopIteration.value 进 results。
方案等待方式代价
阻塞式 + 每连接一线程每个线程各自阻塞在 recv1000 连接 = 1000 线程，切换和内存开销爆炸
非阻塞式 + 轮询挨个 recv 试，设非阻塞CPU 空转，大部分试读是白试
selector（多路复用）登记后睡一觉，OS 叫醒1 线程 1 等待点，N 连接随便挂

6.4 fd：内核发的取件号；epoll 比 select 强在哪

🏠 比喻：取件号

fd（file descriptor）= 内核发给每个 I/O 资源的取件号，一个小整数：socket 是 3 号、文件是 5 号，管道、终端都有号——Unix「一切皆文件」的落地。Python 的 socket 对象只是包装纸，sel.register 真正登记进内核的是 fileno() 那个数字。

顺带三个高频小问题：

  • recv(1024) 是什么、为什么 1024？recv 就是「取件」：把内核替你存在接收缓冲区里的字节搬进 Python 内存；1024 是这一次最多取多少字节的缓冲区大小，纯属习惯值。recv 返回「现在有的」，可能少于 1024——发了 7 字节就还你 7 字节；10MB 大文件得循环拼到够数为止。它平时是阻塞调用，但醒来时内核已担保可读，所以必不阻塞——「先确认就绪、再动手」。
  • OS 不知道协程的存在：ready 队列和 timers 堆是循环自己的账本；selector 登记簿是「循环写入、内核盯梢」；OS 只认 fd，叫醒到 fd 就收工。「fd → 协程」的换算是循环用 key.data 自己做的。
  • 模拟实验里的角色分配：socketpair() 造一对互通的真 socket——写端 w 给后台线程（扮演「0.2 秒后才回包的假服务器」），读端 r 给事件循环登记进 selector；中间隔的是真内核：sendall 的字节由内核搬进 r 的接收缓冲区并标记可读、叫醒 select。内核侧机制和真实网络通信一字不差。

epoll 强在哪：老 select 每次调用都要把全部 fd 拷进内核再挨个扫一遍；epoll 在内核里常驻一份就绪清单，返回的直接就是就绪的那几个——fd 一多差距就爆炸。DefaultSelector 自动挑当前系统最强的实现：Linux 是 epoll，macOS 是 kqueue，兜底才是老家伙 select。

6.5 「不还是 for 循环去问吗？」——select 睡等 vs 轮询

🧑‍🎓 追问（原话）

「while ready or timers or sel.get_map(): … for key, _ in sel.select(timeout): … 可是这里不还是 for 循环去问吗？」

不是。这个 for 不问任何东西——等待发生在 sel.select(timeout) 这一次调用的内部，for 只是在拆它醒来后交回来的返回值列表。实测数据说话：同样等 0.5 秒，select 只花了 0.146 毫秒 CPU（线程真在睡），轮询烧掉 0.5 秒 CPU、空转了 567,650 次。

片段发生什么问 OS 几次
sel.select(timeout)一次系统调用：问一遍「谁就绪了？」然后线程挂起，数据到达或闹钟到点才返回问 1 次，睡到底
返回值 [(key_A, ...)]一个普通 Python 列表，通常 0~2 项0 次
for key, _ in ...遍历上面这个列表，逐项拆包0 次，纯内存操作

两个循环也别混：外层 while 是调度循环，一圈代表「处理一批就绪事件 + 跑一轮协程」，节奏是「问一次 → 睡 → 醒 → 干活」慢慢转；「每秒问一百万次」的那种 while True 才叫轮询。睡觉发生在括号里，for 发生在睡醒后。

🎭 面试作答：事件循环的工作原理

30 秒版：事件循环是个 while 调度循环，管三个结构：就绪队列（待驱动的协程）、定时器堆（按到期时刻排的小顶堆）、selector 登记簿（fd → 协程）。协程在挂起点递交申请（睡多久/等哪个 fd），循环驱动其他任务；没人可跑时阻塞在唯一等待点 select(timeout)，被 OS 或闹钟叫醒后把就绪协程塞回队列。单线程并发就发生在这场重叠的等待里。

2 分钟版：先纠正两个常见误区：协程是惰性的，async def 调用只产出对象、不执行代码，必须被循环 send(None) 驱动——所以「多任务 + 调度器」才等于并发；等待不是轮询，select 是一次系统调用内部挂起，被 OS 主动叫醒，for 只是拆返回值。再讲数据流六步：协程 yield 申请单 → 循环 register(fd, data=coro) → 循环睡在 select(timeout) → OS 标记可读并叫醒 → key.data 换回协程塞回 ready → send(None) 恢复、recv 取件、StopIteration 收结果。最后补协作式调度的代价：谁不挂起谁独占线程，CPU 密集任务会把别人全卡住——所以 asyncio 只适合 I/O 密集。

第 7 章 · Python 是编译型还是解释型？P0 经典问题

经典疑问：「教程说 Python 是解释型语言，Java 是编译为字节码然后由虚拟机运行——到底哪个对？」

结论：两种说法各对一半。机制上 Python 和 Java 是同一种东西：源码 → 编译成字节码 → 虚拟机执行。教程没讲错运行机制，错在分类标签——「解释型」是历史遗留的简化叫法。真正的区别不在「有没有编译」，而在编译发生在什么时候、编译产物给谁看。

7.1 三个可以亲手跑的铁证

# 证据一：编译阶段真实存在，且在执行前完成
# compile() 一行代码都没执行，但看常量表：
import dis
code = compile("y = 1 + 2 * 3", "", "exec")
print(code.co_consts)   # (7,)  ← 1 + 2*3 这道算术在「编译期」就算完了（常量折叠）！
dis.dis(code)           # 只有 LOAD_CONST 7 / STORE_NAME y —— 运行时直接取结果

code2 = compile("z = a + 1", "", "exec")
print(code2.co_consts)  # (1,)  ← a 是变量，没法折叠，保留 BINARY_ADD 指令等运行时再算
# 同一门语言里，有的计算编译期完成、有的留到运行时——「存在编译阶段」的铁证
# 证据二：虚拟机吃的是字节码，不是源码
# 用 py_compile 生成 .pyc 后删掉 victim.py，直接跑 .pyc 照样出结果
# —— 和「删掉 .java 只留 .class，java 命令照样能跑」是一模一样的事

# 证据三：编译时机是「加载时」，且只缓存被导入的模块
# cached_mod.py 当主脚本跑，不生成 __pycache__；
# 被 import 后立刻生成 .pyc —— 主脚本每次在内存里现编译，导入的模块才落盘复用

7.2 CPython 和 JVM 到底差在哪

维度CPythonJava (JVM)
源码→字节码加载时隐式编译，用户无感运行前显式 javac，独立步骤
产物内存里的 code object；仅导入模块落盘 .pyc.class 文件，正经构建产物
分发形态分发源码 .py分发字节码 .class/.jar
编译期检查几乎没有：名字、类型都留到运行时才发现强类型检查，大量错误编译期拦截
VM 执行策略逐条解释字节码（3.13 起有实验性 JIT，默认不开）HotSpot：解释器起步 + 分层 JIT，热点编译成机器码
字节码形态栈式虚拟机栈式虚拟机（这点两家一样）

一句话概括：Java 把编译做成看得见的工序，Python 把编译藏进加载的瞬间。用户感知差异太大，于是各自得了不同的标签。而「.pyc 是编译的证据」这个常见说法也不准确——.pyc 只是缓存，真正的编译每次都在，只是主脚本的那份不落盘。

为什么教程还叫 Python「解释型」？四个原因叠出来的印象：有 REPL（敲一行跑一行，体验上纯解释）；没有可见的编译命令（对比 javac）；生态分发的是源码不是字节码；谱系上被归进「脚本语言」家族。这些感知都对，但都推不出「没有编译阶段」——常量折叠就推翻了它。

编译成本地机器码C / Rust / Go源码 → 机器码 → CPU 直接执行
字节码 + JITJava / C#源码 → 字节码 → VM 解释 + 热点编译
字节码 + 纯解释CPython源码 → 字节码 → VM 逐条执行

🎭 面试作答：Python 是编译型还是解释型？

30 秒版：准确说是「编译为字节码、由虚拟机解释执行」——和 Java 同构，只是把编译藏进了加载瞬间。证据：compile() 不执行代码但常量表里已有常量折叠的结果（1+2*3 变成 7）；删掉 .py 直接跑 .pyc 照样工作；主脚本不生成 .pyc、被 import 的模块才落盘缓存。

2 分钟版：先给结论再上三个证据：一、常量折叠——纯常量算术在编译期完成，变量运算保留 BINARY_ADD 到运行时，说明存在真实的编译阶段；二、.pyc 可独立执行，说明 VM 吃的是字节码不是源码；三、编译时机是加载时、隐式、只缓存导入模块——.pyc 是缓存不是「编译的证据」。然后对比 JVM：javac 显式独立、强类型编译期检查、HotSpot 有分层 JIT；CPython 隐式无感、几乎无编译期检查、逐条解释（3.13 才有实验性 JIT）。最后一句定位：它不是「没有编译的解释型」，是「藏起编译的字节码+纯解释」。

考题速答（30 秒版）
Q1 MRO 是什么？super() 跳到哪？MRO 是 C3 线性化的方法查找顺序（子类在前/声明顺序/去重）；super() 跳到实例类 MRO 的下一位，不是「父类」——落点由实例决定
Q2 __dict__ 是什么？和类属性什么关系？对象的属性仓库。实例库存实例属性，类库存类属性和方法；赋值只写实例库（shadow 机制），__slots__ 的类没有 __dict__
Q3 魔术方法和魔术属性的区别？callable() 判别：方法是语法触发的函数钩子（__add__/__len__）；属性是挂在身上的数据（__dict__/__mro__/__closure__）；后者沿 type(X) 的 MRO 查，描述符在 object/type/FunctionType 三线供应
Q4 生成器怎么变协程？send 塞值（双向通信，首启必须 next）+ yield from 三透传（值/send/return）+ throw/close 三件套 = 受控执行体；async/await 底层就是这套协议
Q5 await 和 yield from 什么关系？同源但收紧：await ≈ yield from，但 asyncio 里 send 永远传 None（唤醒信号），数据走 Future.__await__ 的 return 通道，驱动者是事件循环
Q6 事件循环怎么工作？三结构（ready 队列/定时器堆/selector 登记簿）+ 唯一等待点 select(timeout)；协程惰性必须被驱动；OS 只认 fd 不认协程，key.data 换回协程
Q7 select 是轮询吗？不是。等待发生在一次系统调用内部（线程挂起被 OS 叫醒）；for 只是拆返回值列表。实测：等 0.5s，select 花 0.146ms CPU，轮询烧 0.5s CPU 空转 56 万次
Q8 Python 编译型还是解释型？编译为字节码+VM 纯解释，和 Java 同构但编译藏进加载时；证据：常量折叠、.pyc 独立可执行、只有导入模块落盘缓存；区别于 JVM：无显式 javac、无编译期类型检查、无分层 JIT（3.13 才有实验性 JIT）
Q9 asyncio 适合什么场景？I/O 密集（等待重叠就是并发）；CPU 密集不加速——协作式调度里谁不挂起谁独占线程，GIL 也还在
Q10 await 不 create_task 会怎样？纯顺序执行，没有并发。await 只是挂起等待；create_task 才把协程注册给循环参与轮转——「多任务+调度器」才等于并发
