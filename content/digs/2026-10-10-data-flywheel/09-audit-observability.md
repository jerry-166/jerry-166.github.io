## A1 · 第2轮

### Q8 观测成本预算详细说

**问题的账**：最初设计想每次 cache get/set 打审计事件（`cache.hit`/`cache.miss`）。成本推演：每次检索产生 2 个事件（查+写结果）→ 事件量 = O(请求数)×2；stage-4 一轮压测几千请求 = 上万事件 → ① PG 写放大（每条一行 INSERT，批量也扛不住高频）② `audit_log` 表体积暴涨（年百万级的估算直接翻倍以上）③ 审计页面查询变慢 ④ **最有价值的信号（配置变更/权限事件）被海量 hit/miss 噪声淹没**——这第④条最致命。

**解法的账**：计数器 + 周期快照——

```
每次 get/set：内存 dict 计数器 +1（纳秒级，零 IO）
每 60s：后台 task 把各层 hit/miss/evict 计数打包成 1 条 cache.stats 事件入审计
```

事件量从 **O(请求数)** 降到 **O(时间/60s)**，信息保留为窗口聚合值。前端缓存中心页的 24h 命中率曲线，数据源就是这些快照（复用审计管道，不用另建存储）。

**通用原则**（面试点题）：**高频指标用聚合（metrics），低频事实用事件（events）**。这跟 OTel 的设计完全同构——OTel metrics 是累积计数器+周期导出，OTel logs 才逐条记录；指标基数失控（high cardinality）是可观测性领域经典坑，我们压测阶段就预判到了。

## 模块七：审计与测试

### Q21 降级文件 audit_fallback.log 的内容会处理吗

**实测现状**（`audit.py:175-194`）：JSON Lines 追加写，**没有自动回灌机制**——文件写完静静躺着，不会有后台任务把它读回 PG。

**但它不是废数据**：格式就是审计事件的原样序列化（occurred_at/user_id/action/detail 全字段），**随时可人工/脚本回灌**——十几行 Python 读文件 → `db.insert_audit_batch()` 即可。运维 SOP：发现 fallback.log 有内容 → 查 PG 为什么挂 → 恢复后跑回灌脚本。

**为什么不自动回灌**（工程论证）：① 触发条件罕见（队列满 10000 或 DB 挂，都是异常态）；② 回灌有坑——服务起来时文件可能还在被写（并发读写）、重复回灌要去重（audit_log 无唯一键约束）、要处理部分恢复——做对需要文件锁/去重状态机，**为一个罕见路径上这套复杂度，YAGNI**；③ 金融级要求才值得（那种场景的正解是本地消息表 + 重试队列 + 死信）。

诚实声明口径：审计的完整性保证是“**尽力而为 + 文件证据保全**”——进程崩溃丢 ≤500ms 队列残留（兜底中间件粗记录补偿），DB 挂期间靠文件保住。业界同构：Fluentd 的 file buffer、OTel Collector 的 queued_retry 导出器（那个就是自动重试版的降级文件）。

### Q22 pytest 和 verify 脚本不都一样吗

**你的质疑基本对**：verify_task5/6 本质就是断言脚本——pytest 能做的断言，脚本都能做。**差别不在“能不能”，在工程化外壳**：

| 能力 | verify 脚本 | pytest |
|---|---|---|
| 断言 | 手写 if + print PASS/FAIL | assert 失败自动打印变量现场 |
| 运行 | 记住 N 个脚本手动跑 | 一条命令全跑，自动发现 |
| 环境隔离 | 自己管前置/清理 | fixture setup/teardown |
| 分组 | 无 | 标记 unit/integration/slow，CI 分层 |
| 失败定位 | 自己拼错误信息 | 开箱即用 |
| CI 集成 | 要自己解析输出 | 退出码/报告（allure/pytest-html）原生 |

**为什么当时用脚本**：stage-cache 是**验收驱动**——每 Phase 完成要向你汇报“含数据的证据”，verify 脚本就是验收演示的产物；且它们要连真实 PG/Redis/Milvus（集成测试性质），pytest 的核心价值（mock、单元隔离）在纯断言层面用不上。

**差距真正在哪**（面试诚实讲法）：不是断言能力，是**回归防线缺失**——脚本没有“改代码后自动跑”的环节，pytest+CI 有。迁移成本其实很低（每个 assert 包成 `test_` 函数）。一句话：“验证方式是验收脚本而非单测框架，断言强度等价，缺的是自动化回归的外壳；知道怎么补、补的成本低”。

## 8. pytest + CI 流程确认

基本正确，一处措辞精确化：**拦的不是“提交”，是“合并进主干”**。

```
git commit（本地）──拦不住（git 是分布式的，本地想提交就提交）
   ↓ push / PR
GitHub Actions 触发 workflow → 跑 pytest（+ lint / type check）
   ↓ 失败
Branch Protection 规则：required status check 不绿 → 禁止 merge 进主干
   ↓ 通过
merge → 后续部署流程
```

完整的反馈链是三级（越左越快）：**pre-commit 本地钩子**（秒级，格式问题当场报）→ **PR CI 门禁**（分钟级，跑测试）→ **merge 后部署**。“防止它进行提交”在面试里要说成“**防止未通过验证的代码进入主干**”——这是 branch protection 的标准表述。
