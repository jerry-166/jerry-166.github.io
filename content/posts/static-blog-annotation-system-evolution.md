# 纯静态博客的划线批注系统：从 localStorage 到云端同步再到 CI 自动注入

> 博客托管在 Vercel 纯静态部署，没有后端、没有数据库。这套批注系统从"只动前端能不能做"出发，一路演进到云端多设备同步、多书自动适配、CI 自动接入。本文复盘整个演进过程——**每一步的方案都是被当时的约束逼出来的**，这是我觉得比功能本身更值得记录的东西。

[在线体验](/books/java-review/index.html)：打开任一教程页，选中文字即可划线写批注（支持 Markdown），换设备批注自动回来。

## 一、背景与约束

我的博客有一批"教程书"：静态 HTML 页面组成的系列手册（Java 复习、FastAPI 面试笔记、MySQL 架构……），部署在 `public/books/` 下。复习时想要纸质书的两个基本能力：**划线**和**写批注**。

约束很硬：

| 约束 | 含义 |
|---|---|
| 纯静态托管 | 没有后端服务，无法写传统接口 |
| 无数据库 | 批注数据没有落点 |
| 公开仓库 | 源码可见，任何口令不能硬编码 |
| 多设备使用 | 手机、电脑、平板来回切换 |

有意思的是，这四条约束依次被后面的版本逐个拆掉——静态托管逼出了前端方案，无数据库逼出了云 KV 选型，多设备逼出了同步协议，公开仓库逼出了环境变量 + 写口令的双层设计。

## 二、v1：纯前端批注——"只动前端可以做到吗"

**结论先行：完全可以，而且 90% 的需求在这一步就解决了。**

纯前端方案的三块基石：

1. **渲染**：选中文字 → `Range` API 拆文本节点 → `<span class="anno-hl">` 包裹上色；
2. **定位**：批注要能跨刷新还原。用 XPath 记录起止节点 + 偏移量（`sx/so/ex/eo`），同时冗余存一份选中文本；
3. **持久化**：`localStorage`，键 = 页面文件名。

这里有个容易被低估的设计：**XPath 定位 + 文本匹配双保险**。页面内容更新后（教程书会改稿），XPath 可能失效，此时按文本重新查找——文本也找不到就标记"位置失效"但保留批注数据，而不是静默丢弃。数据资产和渲染状态分离，是整个系统后面敢做各种重渲染的前提。

v1 的局限也很快暴露：换浏览器/清缓存批注全没。这是 localStorage 的本质决定的——**它只是缓存，不是存储**。

## 三、v2：交互重构——用户反馈驱动

第一版的交互是划线后弹小窗写批注，实测体验差：文本框太小、写 Markdown 没法预览、批注列表没有汇总入口。重构为：

- **右侧长条边栏**：汇总本页全部批注，逐条展开/收起、跳转定位、编辑、删除；
- **Markdown 渲染**：批注内容支持加粗、列表、代码块、引用；
- **三种语义颜色**：重点（黄）/已掌握（绿）/疑问（红）。

这一版没什么架构可讲，但它确立了一个原则：**批注边栏和管理面板是运行时动态注入的 DOM，不入侵页面原有结构**——整个系统对宿主页面保持"寄生"姿态，这为后面接入任意教程书埋下伏笔。

## 四、v3：云端持久化——乐观锁、离线补推与降级

多设备需求出现后，方案变成 **localStorage（缓存层）+ 云端 KV（权威源）** 的双层结构。

### 4.1 选型：Upstash Redis

无后端约束下，两条路：BaaS（Supabase/Firebase）或 Serverless KV + 一个 API 路由。选了后者：

- Vercel 部署的 Next.js 可以加 `app/api/annotations/route.ts`——**静态托管的项目其实有"半个后端"**（Serverless Functions），这是很多人不知道的；
- Upstash Redis 有免费档（256MB 存储、月 50 万命令），批注场景用量不到 2%；
- 顺带一提：Vercel KV 这个产品 2024 年已下线，底层本来就是 Upstash，现在直接用 `@upstash/redis` SDK + Upstash 集成，环境变量名从 `KV_REST_API_*` 换成 `UPSTASH_REDIS_REST_*`，踩过这个坑的搜不到文档多半是这个原因。

### 4.2 接口设计：读开放，写有口令

```
GET  /api/annotations?page=xxx          → 公开（批注本来就不敏感）
POST /api/annotations                   → body 携带 ANNO_WRITE_TOKEN 校验
```

为什么需要自己的写口令而不用 KV 的 token？因为 KV token 是服务器和数据库之间的凭证，**绝不能下发到浏览器**。写口令是应用层自己发明的一层薄鉴权：首次保存时提示输入一次，存本机，之后无感。最坏后果只是批注被人乱写，风险可接受。

### 4.3 乐观锁：多设备并发写

场景：A、B 两台设备都基于云端版本 T0 拉过数据，A 先推（云端变 T1），B 后推。协议：

```
B 推送时携带 baseUpdatedAt=T0
  → 服务端发现云端版本 T1 > T0 → 返回 409，拒绝
  → B 客户端：拉云端最新 → 按 id 合并（同 id 本地覆盖 + 补本地独有）→ 重推一次
```

合并策略是**本地优先**——发起合并的一定是刚改完批注的那台设备，它对自己刚写的内容有最新认知。只重试一次，防 409 死循环。

这里的洞察：**乐观锁不是数据库的专利，任何"读-改-写"场景都能用版本号自造**。面试聊 CAS、聊 `@Version`，这就是一个自己实现的案例。

### 4.4 离线补推：两本时间戳账

一个容易想当然的问题：断网时写的批注，什么时候推上去？**答案不是页面关闭时，而是下次打开时**——浏览器不会在页面销毁后替你干活。

`localStorage` 里记两笔账：

```
MTIME  = 本地最后一次修改时间
PUSHED = 最后一次成功推送云端时间
MTIME > PUSHED  →  有欠账
```

下次打开页面时：有欠账 → 先推再拉；无欠账 → 直接拉。配合推送请求的 `keepalive: true`（页面销毁后浏览器仍会完成已发出的请求，body ≤ 64KB），"划完线立刻关页"也基本不丢。

### 4.5 降级设计

Redis 客户端**懒初始化**，环境变量缺失或网络不可达时接口返回 503，前端收到后自动降级为"仅本机"模式——批注功能完整可用，只是不同步。状态标签（☁已同步/✎仅本机）让用户始终知道自己处于哪种模式。

**缓存层永远可以独立工作，权威层挂了不带走缓存**——这个原则让系统在云端未部署的页面（比如本地 file:// 打开）也完全可用。

## 五、打磨期：一个事件时序 bug 与多书接入的设计取舍

### 5.1 多书接入：为什么不是装饰器

批注系统要接入十几本结构各异的教程书。直觉方案是"每本书写一个适配器类"，或者"用装饰器模式层层包装"。分析后都否了：

- **装饰器的本质是行为叠加**（Java IO 的 `BufferedInputStream(FileInputStream(...))`），而各书的差异是**参数级**的：正文容器选择器、存储键、API 地址——三个槽位，不是洋葱层；
- 硬套装饰器 = 过度设计。

实际落地是三个思想的组合：

```
window.ANNO_CONFIG = { page, api, root }   ← 配置对象：差异收敛于此（开闭原则）
        ↓ 缺省时
rootOf() 三级探测                            ← 适配器：归一化各种页面结构
  ① 显式配置 root      → 一行直达
  ② 约定链             → main → article → [role=main] → .content…
                        （命中条件：容器内正文 >200 字，防误配评论区）
  ③ 启发式兜底         → body 下文本量最大的子元素（>500 字才算数）
```

配套原则是**约定优于配置**：90% 的书正文都在 `<main>` 里，零配置接入；偏离约定的才加一行配置。`rootOf()` 内部那三级是策略模式的"可替换算法族"+ 短路责任链，但它们是**框架内部的实现细节**，不是暴露给使用者的扩展点。

还有一条工程约束决定了形态：anno.js 是单文件零依赖脚本，靠 `<script src>` 直连静态页，没有构建流程。**模式服从部署约束**——教科书里的 class 继承体系在这里反而是负担。

### 5.2 一个值得记录的 bug：isConnected

加"点击页面空白处收起边栏"功能后，编辑模式炸了：点"编辑"按钮，编辑框弹一下就消失。

根因是教科书级的**事件时序问题**：

```
点"✎ 编辑" → 按钮处理器重渲染边栏 → 按钮被移出 DOM 树
→ 但 click 事件还在冒泡途中 → 冒泡到 document 级监听器
→ closest('.anno-drawer') 沿【实时 DOM】向上找祖先 → 按钮已无父节点 → 找不到
→ 被误判为"点击了页面外部" → 收起刚打开的编辑框
```

修复只有一行：`e.target.isConnected === false` 的事件目标必然是被脚本重渲染移除的节点，**不可能来自用户对页面的正常点击**，直接放行。

这个 bug 的教学价值在于：**事件对象里的 target 是"快照引用"，而 closest() 查询的是"实时 DOM"**——冒泡过程中 DOM 结构变了，两者就会给出矛盾的答案。

## 六、CI 自动注入：从"每页手写"到"push 即接入"

多书接入的最后一公里：14 个页面还是得每页手写一行 `<script src="anno.js">`。能不能不写？

先想清楚一件事：**无论哪种方案，script 标签最终都要出现在 HTML 里**，区别只是"谁、在什么时机"放进去：

| 时机 | 方案 | 现实对应 |
|---|---|---|
| 编写时 | 每页手写一行 | v3.2 现状 |
| 构建时 | 脚本批量注入 | **本次落地** |
| 服务时 | 中间层改写响应 | nginx sub_filter、统计脚本注入 |
| 浏览时 | 浏览器扩展 | Hypothes.is 等网页批注产品 |

静态托管下构建时注入是最优解：零运行时成本。落地为 GitHub Actions：

```
push main（paths: public/books/** 或注入脚本变化）
  → 检出代码 → node scripts/inject-anno.mjs
  → 有变更则 bot 追加一个提交（含 [skip ci]）→ 自动部署
```

注入器（~100 行零依赖 Node 脚本）做三件事：以 `public/books/anno.js` 为权威源同步副本到各书目录、`</body>` 前插标签（已注入跳过）、检测同名 HTML 自动注入存储键命名空间防串数据。

### 这条流水线教我的三件事

**① 新增 workflow 的首次 push 不触发它自己。** GitHub 在 push 落地前判定触发条件，彼时分支上还没有这个文件。解法：`workflow_dispatch`（手动触发按钮）+ 把 workflow 文件纳入自己的 paths 过滤器。

**② 防自触发循环要双保险。** bot 提交用 `GITHUB_TOKEN` 推送——GitHub 内建规则：这种推送不再触发任何工作流；提交信息里的 `[skip ci]` 是显式第二重保险。没有这两层，工作流自己触发自己，无限循环。

**③ 幂等是 CI 脚本的命门。** CI 会反复跑同样任务，注入脚本必须做到：已注入的文件跳过、无变更不产生空提交、保留原文件换行风格（避免整文件 diff）、畸形文件（无 `</body>`）警告跳过而不炸 CI。

另一个容易被忽略的点：**CI 改的不是你上传的内容，而是追加一个新提交**。你的原始 commit 永远原封不动，`git log` 里你的提交和 bot 的提交泾渭分明——可审计性是 CI 的核心价值，不是副作用。

代价也要说：本地工作流得改。push 后 bot 可能追加提交，下次开写前必须 `git pull`，否则必然冲突。

## 七、复盘

### 成本账

| 项 | 数值 |
|---|---|
| 书/页面 | 9 本 / 14 页，全部自动接入 |
| 数据量 | 单页约 45KB，KV 上限 256MB（0.3%）|
| 命令配额 | 月用量约 1.5%（保存一次 = 2 条：乐观锁 GET + SET）|

存一次为什么是 2 条而不是 1 条？想把"读旧版本+比较+写入"塞进一个 Lua `EVAL` 技术上可行，但配额富余 98.5%，为省一半配额引入脚本字符串的维护成本——**典型的过早优化，知道不做和知道怎么做一样重要**。

### 知识地图

这套"小玩具"意外地串起了不少知识点的**一手实现**：

- 设计模式：适配器（容器归一）、策略（探测链）、配置对象（开闭原则）、约定优于配置——以及一次"为什么不用装饰器"的取舍论证；
- 并发控制：乐观锁（版本号 + 409 + 合并重试）、缓存与权威源分层、离线补推的记账设计；
- 前端底层：事件冒泡与实时 DOM 的时序差（isConnected bug）、Range/XPath/selection API、localStorage 语义；
- CI/CD：幂等、防循环、首次触发规则、bot 提交的审计边界。

面试被问"项目难点"时，比起背概念，讲一段"我加了个功能结果把编辑模式搞炸了，根因是事件冒泡时 DOM 已经变了"——有细节、有决策、有取舍，这比任何八股都有说服力。

### 如果重来一次

两个会调整的地方：一是 v1 阶段就该把"存储键 = 文件名"的设计换成显式命名空间，后面多书接入时就不会有同名撞键的隐患（虽然注入器兜住了）；二是 API 的乐观锁直接用 Lua 脚本实现 CAS 语义会更干净——不是为了省配额，是让"检查+写入"原子化，现在的 GET+SET 之间理论上存在竞态窗口（低频写场景可忽略，但这属于"知道欠账在哪"的技术债）。
