## Q1 · 第4轮 · 初始

匹配社区(聚类摘要) → 取社区报告文本，lightrag还会生成社区报告吗？他会聚类吗？他的离线入库模式是什么样的？我知道微软的 GraphRAG，它会去抽取实体关系，聚合生成社区报告，同时还有一份顶层的摘要报告。
在匹配时，它的流程是：
1. 先匹配摘要报告；
2. 再匹配社区报告；
3. 去对应的社区中查找实体和关系；
4. 最后拿到值，进行生成。

## A1 · 第4轮

## Q2 · LightRAG 的离线入库：会聚类、会生成社区报告——这正是"lite"的分界线

你的方向对：**LightRAG 离线入库确实做社区检测 + 社区报告**（基于论文与开源实现，标注：论文级知识，本项目未对它插桩）。完整入库流程：

```
chunk 切块(token-based)
 → 每 chunk 一次 LLM 抽取实体+关系        ← 与我们 EntityEnhancer 同构,我们也有
 → 同名实体合并 / 关系去重累加 weight
 → NetworkX 建图
 → ★ Leiden 社区检测,得到层级社区          ← 我们没有
 → ★ 每个社区一次 LLM 生成社区报告          ← 我们没有(索引成本的差异来源)
 → PGVector 存四类 embedding:
   chunk / 实体 / 关系 / 社区报告
```

查询时它的 global 模式就是**拿 high-level keywords 的 embedding 去匹配社区报告**——社区报告是它 global 检索的弹药库。我们没有社区报告，所以没有也不需要 global 模式，这就是 GraphRAG-**lite** 的具体含义。

### 但你对微软 GraphRAG 匹配流程的复述要修正

你说的“①先匹配顶层摘要报告 → ②再匹配社区报告 → ③进社区找实体关系 → ④生成”是**层级导航瀑布**——实际不是这样。微软 GraphRAG 是**两条正交查询通道**，各自独立：

```
Global 通道(答"整个数据集讲了什么"类全局问题):
  query → 社区报告分批喂 LLM 打分出部分答案(map)
        → 汇总合成最终答案(reduce)
  ※ map-reduce 遍历社区报告,不"进社区找实体"——报告本身就是素材

Local 通道(答具体实体问题):
  query → 识别种子实体 → 邻居实体/关系/原文单元 + 所在社区报告
        → 全部拼 context → 一次生成
  ※ 这里才涉及实体关系
```

顶层摘要报告不是“第一道闸门”，它只是社区层级树（Leiden 产出层级）的根节点报告，参与 global 的 map-reduce 候选池。**面试别说成瀑布式导航**，说成“global 和 local 两条通道，global 走社区报告 map-reduce，local 走实体种子扩展”——这是准确版本。

### 三方对照表（可直接背，回答“你和 LightRAG/GraphRAG 差在哪”）

| 维度 | 我们 GraphRAG-lite | LightRAG | 微软 GraphRAG |
|------|-------------------|----------|---------------|
| 实体关系抽取 | ✅ 每 chunk 1 次 LLM | ✅ 同左 | ✅ 同左（+gleaning 多轮重抽，更贵） |
| 社区检测 | ❌ | ✅ Leiden | ✅ Leiden 层级 |
| 社区报告 | ❌ | ✅ 每社区 1 次 LLM | ✅ 每层 map-reduce 摘要（**成本大头，官方大语料 $20-500+**） |
| 查询期 LLM 调用 | **2 次**（锚点+重排） | 2 次（keyword+生成） | global 多次（map-reduce）/ local 1-2 次 |
| 擅长 | 精准多跳关联问答 | 平衡型 | 全局 summarization（“这个库整体讲什么”） |
| 我们的场景为何不选后两者 | — | 查询耦合生成 | 企业 KB 要的是精准问答不是语料级摘要，且索引成本不可控 |

## A2 · 第5轮

## GraphRAG vs LightRAG 离线管线：并排总览

```
微软 GraphRAG(全量重管线)                     LightRAG(为增量而瘦身)
══════════════════════════                   ══════════════════════════
切块                                           切块
  ↓                                              ↓
① LLM 要素抽取                                 ① LLM 实体关系抽取
   实体/关系/claim                             (单轮,prompt 借鉴 GraphRAG)
   + gleaning 多轮追问 ★                      (不做 gleaning ★)
     ("还有吗?"×N 轮,成本倍增)
  ↓                                              ↓
② 实体解析(LLM 判断相似实体合并) ★             ② 同名/相似名合并 ★
                                              (profile 字典 key 对齐,便宜)
  ↓                                              ↓
③ NetworkX 建图                                ③ NetworkX 建图
  ↓                                              ↓
④ Leiden 层级社区检测                           ④ Leiden 社区检测(flat 一层)
  ↓                                              ↓
⑤ 社区报告:层级 map-reduce ★                  ⑤ 社区报告:一层,可后置/
   叶社区逐层向上聚合到根                       手动 rebuild ★
   (每层每社区 1 次 LLM)                       (增量插入默认不重算)
  ↓                                              ↓
存储:原文+实体+关系+社区+各级报告              存储:原文+实体+关系+一层社区报告
                                              ★ 增量插入:只跑①②③局部合并,
                                                不动全图 ★
```

## 五个优化点逐一展开（LightRAG 相对 GraphRAG）

### ① 增量更新 vs 全量重跑 —— 最大架构差异

GraphRAG 的社区报告是**全局耦合结构**：叶社区报告聚合成上层报告、一直到根层全局摘要——任何新文档进图，社区划分变了，整条层级链的 LLM 摘要理论上都要重算，实践中等于全量重建索引。

LightRAG 的取舍：增量插入只做“新 chunk 抽取 → 实体/关系合并进已有图”（纯局部操作，无全图重算）；社区报告弱化成 flat 一层且**可后置 rebuild**——代价是增量期间社区报告有时效滞后（不 rebuild 就旧）。这是典型的“用结构换弹性”。

### ② 抽取成本：单轮 vs gleaning

GraphRAG 的 gleaning：抽完一轮后追问 LLM“还有遗漏的实体吗”再抽（默认 1 轮，可调 N 轮）——抽取召回率换 LLM 成本倍增。LightRAG 直接砍掉，单轮抽取。我们项目的 `ENTITY_TEMPLATE` 也是单轮——在这点上我们和 LightRAG 同款。

### ③ 实体合并：轻量 vs 重量

GraphRAG 有显式的 entity resolution 阶段（LLM 判断“AI”和“人工智能”是否同一实体再合并）。LightRAG 用 profile 字典按名字对齐合并（同名/相似名），便宜得多——代价是同义不同名的实体可能分裂成两个节点。**我们的 `upsert_entity` 是同一哲学**：`UNIQUE(kb_id, name)` + 同名合并 source_chunk_ids，description 留长版——零 LLM 成本的合并。

### ④ 社区报告：一层按需 vs 层级全量

GraphRAG：每层每社区一次 LLM，成本随社区数 × 层数放大，这是它索引贵的主因（官方大语料实测从几百到几千美元量级；我们简历引用 $20-500+ 是保守口径）。LightRAG：一层社区报告，查询期直接用 embedding 匹配 top-N 报告——**离线的简化直接决定了在线检索的简化**（见下）。

### ⑤ 查询期成本差异是离线差异的下游（“检索成本降低 99%”的出处）

GraphRAG global search 拿社区报告做 **map-reduce**：分批喂 LLM 打分（map）再汇总（reduce）——LLM 调用次数 = 社区报告数/批大小，语料越大越多。LightRAG global 是**向量匹配社区报告**（毫秒）+ 一次生成。港大宣传的“检索成本降低 99%”就是指这个：把 GraphRAG 查询期的 LLM 遍历换成离线预计算的 embedding 匹配。**这是“离线决定在线”的教科书案例**——GraphRAG 把成本花在索引期的层级摘要（查询期还得再花 LLM 遍历它们），LightRAG 把社区报告变成可向量检索的静态资产。

## 关联到我们：lite 在这个光谱上的位置 + 一个被忽略的红利

我们的 GraphRAG-lite 连社区层都没有，在“离线成本光谱”上比 LightRAG 更左：

```
离线成本/全局能力光谱:
  我们 lite ──────── LightRAG ──────── GraphRAG
  抽取:1次/chunk      +社区报告(1层)     +gleaning+层级报告+实体解析
  无社区              增量便宜但社区滞后   全量重跑
  全局问题:答不了     社区级             语料级最佳
```

**被忽略的红利：我们的架构增量是“免费”的**。因为没有社区这种全局耦合结构，新文档入库只做局部操作——`upsert_entity` 同名合并（`database.py:851-887`）、`add_entity_relation` 三元组去重（`database.py:889-909`）、Milvus 实体向量先删后插（`milvus_client.py:633-651`）——没有任何全图重算。KB65 在 C 轮 2 前补 700 篇 non-rel 文档、46 个 timeout 后用 sync 脚本补向量，全程没碰已有数据，就是这个性质的实证。

**面试金句（把三个系统一句话串起来）**：

> “增量友好度是全局耦合度的反面。GraphRAG 的社区层级是全局耦合结构，增量等于重建；LightRAG 把社区弱化成一层可后置的静态资产，换来便宜增量但牺牲报告时效；我们干脆不做社区——没有全局结构，增量天然免费，代价是回答不了‘整个库讲了什么’类全局问题，而企业 KB 的需求是精准问答，这个取舍我认为是对的。”

**能力边界的诚实声明**（如果被问“那你的全局问题怎么办”）：如实答“当前架构不覆盖，这是 lite 的明确取舍；如果业务出现全局摘要需求，演进路径是给 LightRAG 式的一层社区报告作为可选增强层，导入侧增量可控”——展示你知道怎么补，而不是没想过。
