## A1 · 第3轮

## D 组：存储与索引工程

### ⑥ BM25 克隆后 corpus 是空的吗？应该重新 load 吧？

**你的直觉（会空）和方案（要重新加载）都对——而且代码已经做了**，只是实现方式比你设想的“重新 load”更精确。上轮贴过 `faq_service.py:400-412`，现在把三种方案摆开看为什么选它：

| 方案 | 做法 | 问题 |
|---|---|---|
| a. 什么都不做 | PG 有数据，内存索引不更新 | 克隆库关键词检索**静默返回空**（你担心的场景，对） |
| b. 重新 `load_from_database`（你建议的） | 全量从 PG 加载**所有 KB** 的 chunk 进索引 | 语义错：只想让 1 个新 KB 生效，却重建全世界——慢、且启动期之外的调用语义混乱 |
| c. **增量 `bulk_index_chunks`（实际实现）** | 只取**新 KB 的 chunk** 精确写入内存索引 | 快（只搬增量）、不影响其他 KB 已建好的索引、语义正好匹配“新增了一个 KB”这个事件 |

还有一层**双保险**：就算增量索引这步失败（warning，不阻塞），下次服务重启时 `load_from_database` 全量加载会从 PG 自然带出克隆库的 chunk——**PG 是持久真相，内存索引是可再生的派生物，丢了随时能重建**（这和 ⑰ Milvus 是同一条原则）。

### ⑦ cache invalidation / index rebuild（业界全景）

这个问题的本质一句话：**持久化真相源（DB）和派生加速结构（缓存/内存索引/搜索索引）生命周期不同步——真相变了，派生物不会自动变。** Phil Karlton 那句名言：“计算机科学只有两个真正的难题：缓存失效和命名。”

业界方案族谱（从粗到细）：

```
TTL 过期          → 懒，最简单，容忍旧数据一个窗口（Redis 默认打法）
事件驱动失效       → 写路径显式通知，"写时失效"（我们的 bump_kb_cache 在这档）
版本号/世代号      → 不删旧缓存，换钥匙——版本变=key 变，旧条目等 TTL 自然死（我们的实现细分）
写穿透 write-thru → 写库同时写缓存，永不错——代价是写路径变重
CDC 订阅          → 订阅 binlog（Debezium/Canal），彻底解耦写路径——重基建，大厂玩法
重建 reindex      → ES reindex：mapping/分词器不能原地改 → 建新索引 → reindex API 搬数据 → alias 原子切换（零停机重建的标准姿势）
预热 warm-up      → 新实例（新从库/新节点）缓存是冷的，直接放流量会打穿到磁盘 → 先喂影子流量/预热脚本再接流量（MySQL buffer pool、OS page cache 同理）
```

我们项目在这个谱系上的位置（可以当一个小地图背）：
- **启动期**：BM25 `load_from_database` = 启动预热（对应“读库扩容索引预热”）
- **运行期**：克隆 `bulk_index_chunks` = 运行时增量预热
- **缓存失效**：`bump_kb_cache` = 版本号 + TTL 双保险（下面 F 组展开）
- **Milvus**：PG 权威 + 向量可再生 = "派生物可重建"原则

## ③ 上线后不能频繁重启，运行时刷新怎么解决？

先纠正一个前提：**这个项目的“运行时增量更新”其实已经解决了一半**——`clone_kb` 里的 `bulk_index_chunks` 就是不重启把新 KB 数据进内存索引的路径。重启时的 `load_from_database` 是**兜底**（增量这步失败了，重启自然修复），不是唯一手段。所以并不存在“为单个用户刷新关键词要重启”的依赖。

通用的解法谱系（按一致性从强到弱）：

```
1. 写路径同步维护（write-through）     ← 项目现状：clone 时同步 bulk_index
   数据变更的同一流程里顺手更新索引。强一致；代价是写路径变重 + 失败要兜底
2. 事件驱动异步更新                    ← 大厂标准：写库 → 发事件（PG NOTIFY / Kafka / CDC-Debezium）
   → 索引服务订阅、增量消费。解耦、最终一致；代价是要事件基建
3. 增量轮询                           → 定时扫 updated_at > 上次水位 的行
   简单、有延迟；适合变更低频场景
4. cache-aside 回源                   → 查询时发现索引没有 → 回 PG 查 → 顺手填进索引
   按需加载；适合读时才需要的冷数据
```

另外，“上线后不能重启”在现代部署里也要修正——**不能的是“停机重启”，不是“重启”**：滚动重启（k8s rolling update，实例一个一个换，LB 先摘流量）+ 启动预热（load_from_database 就是）+ 就绪探针（**索引加载完才允许接流量**）——重启期间服务不间断。所以完整答案是三层：**能增量就不重启（1/2/3/4），必须重启就滚动重启，重启期间用就绪门挡住流量**。项目里 Stage 1 的启动优化（lifespan 异步化 + readiness gate）就是这套思想的启动期版本——两条简历线在这里又咬合了一次。
