开场：Java 8 为什么是分水岭

Java 8 之前的 Java 是一门纯命令式、纯面向对象的语言——一切行为都必须包在类和方法里，连"传一个行为"都要先造个对象。Java 8 一次性带来了四样改变语言性格的东西：

新特性一句话概括解决什么痛点
Lambda 表达式把"行为"当值传递匿名内部类的臃肿噪音
Stream API声明式数据处理流水线命令式循环的样板代码
接口默认方法接口可以带实现已发布接口无法演化（加了方法全炸）
Optional / java.time空值与时间的现代化NPE 满天飞 / Date 又臭又不可靠

这四样不是孤立的——Lambda 是地基，Stream 是 Lambda 最大的消费者，默认方法是 Stream 能进 Collection 接口的前提，Optional 和 java.time 是同一波"现代化"思潮的产物。整条链是这样咬合的：

痛点：给集合排序，要传"比较规则"（一个行为）
   └─► Lambda：让行为成为一等公民，可以像值一样传来传去
         └─► Stream：既然行为能传，集合的"过滤/映射/汇总"就能声明式拼接
               └─► 接口默认方法：stream() 要加进 Collection 接口，
                     但接口加抽象方法会让所有实现类编译报错
                     → 带着实现加进去（default）
   （Optional 和 java.time 是并行的两条现代化支线）

Lambda：从臃肿到极致 高频

2.1 痛点：匿名内部类的噪音

Java 一切皆对象——那么"给排序器传一个比较规则"这种事，就必须把规则包进一个对象。Java 8 之前的写法：

Before.java五行情报，一句有效
list.sort(new Comparator<User>() {          // 为了传"比较规则"
    @Override                                 // 造一个类
    public int compare(User a, User b) {      // 签名是上下文早就知道的
        return a.getAge() - b.getAge();       // ★ 唯一有意义的一行
    }
});
// 5 行代码里，4 行是"仪式"，1 行是"意图"。
// 更糟的是：编译期就生成一个 Outer$1.class 文件（后面细说）

观察这 5 行：类名、方法名、参数类型、@Override——全是上下文"本来就知道"的信息。真正想表达的只有"a 的年龄减 b 的年龄"。Lambda 的思路：把已知信息全部省掉，只写意图：

After.java三连瘦身
list.sort((a, b) -> a.getAge() - b.getAge());        // Lambda：参数和意图
list.sort(Comparator.comparingInt(User::getAge));   // 方法引用：连"减"都不用写了
users.sort(comparing(User::getAge));                 // 静态导入后的极简形态

2.2 语法速览

(参数列表) -> { 方法体 }

各种形态：
  () -> 42                        // 零参数，表达式体（自动 return）
  x -> x * x                      // 单参数可省括号
  (a, b) -> a + b                  // 多参数
  (String s) -> s.length()        // 显式类型（基本不用，编译器会推断）
  (a, b) -> {                      // 多语句块体：花括号 + 显式 return
      int t = doSomething(a);
      return t + b;
  }

2.3 前提：函数式接口（Lambda 的"类型"）

关键问题：(a, b) -> a - b 这个东西，到底是什么类型？答案是——它自己没有类型，它的类型由上下文决定。Lambda 只能出现在一个地方：函数式接口（Functional Interface）的赋值目标上。函数式接口的定义：

FunctionalInterface.java有且仅有一个抽象方法
@FunctionalInterface                     // 编译器检查：不是单抽象方法就报错
interface Comparator<T> {
    int compare(T o1, T o2);              // ★ 唯一的抽象方法（SAM）
    // equals/hashCode 这种从 Object 继承的不算数；
    // Java 8 后的 default / static 方法也不算数
}

// Lambda 的类型 = 目标位置的函数式接口：
Comparator<User> c1 = (a, b) -> a.getAge() - b.getAge();   // 这里它是 Comparator
ToIntFunction<User> f1 = u -> u.getAge();                 // 同样的写法，这里它又是另一个类型
理解 Lambda 的心智模型：

  Lambda 本体      =  一段"无主"的行为（参数 → 结果）
  函数式接口       =  给这段行为起的名字（契约：参数什么类型、返回什么类型）
  目标类型推断     =  编译器看左边/上下文，把行为"装进"对应契约的盒子

  (a, b) -> a - b   本身没有类型；
  放在 Comparator 位置 → 它就是 Comparator；
  放在别的 SAM 位置   → 它就是那个接口。
  —— 这就是"目标类型决定一切"，也是后面方法引用能简写的基础。

2.4 变量捕获：为什么必须 effectively final

Lambda 可以用外部局部变量，但有个著名限制：被捕获的局部变量必须是 effectively final（事实上的 final——只赋值一次）。为什么？

模块 1 的钩子：方法局部变量在栈上，方法返回栈帧就没了。
而 Lambda 的生命周期可能超出方法（被传走、被线程异步执行）。

编译器的做法：把捕获的变量【值拷贝】进 Lambda 实例（同步进堆里）。
  基本类型 → 拷贝值本身
  引用类型 → 拷贝"引用"（指向的对象还是共享的）

如果允许在 Lambda 外/内修改这个变量：
  外面改了 → Lambda 里是旧拷贝，两边看到的值不一致；
  里面改了 → 改的是堆里的拷贝，外面的栈变量纹丝不动。
两边都会撒谎 —— 语义直接崩坏。

所以 Java 的选择：禁修改。要么不许动（值恒定，拷贝永远可信），
要么你自己包成数组/AtomicInteger/对象字段（改的是"引用指向的内容"，
引用本身没变 —— 回收模块 1 的"引用的拷贝 vs 对象的共享"）。
Capture.java经典坑：循环变量
for (int i = 0; i < 3; i++) {
    new Thread(() -> System.out.println(i)).start();   // ✗ 编译错误：i 在变
}

// 解法一（Java 8 时代）：拷进一个事实 final 的变量
for (int i = 0; i < 3; i++) {
    int fi = i;                                        // 每轮新变量，只赋值一次
    new Thread(() -> System.out.println(fi)).start();  // ✓
}
// 解法二：用 IntStream.range(0, 3).forEach(i -> ...)，i 是流的参数不是外部变量
一句话回答

Lambda 是什么？——一段"无主行为"（参数→结果），自身无类型，必须装进"恰好一个抽象方法的接口"（函数式接口）里使用；类型由上下文推断。捕获的局部变量必须 effectively final，因为实际捕获的是值的拷贝。

Python 的 lambda 和 Java 的比，差在哪？Python 对比

Python 的 lambda 只能写单个表达式（lambda x: x*2，想写两行都不行）；Java 的 lambda 可以写多语句块（{ ... }），能力对齐匿名函数。变量捕获上 Python 反而更宽松（闭包捕获的是 cell，可读可写，还支持 nonlocal）——Java 用"只读捕获"换掉了闭包变量共享的所有并发坑。面试被问"两种语言的闭包差异"，答"Python 闭包可变、Java 捕获只读且是拷贝"就够专业。

实例字段能被 Lambda 修改吗？也算"变量捕获"吗？

能，且不受 effectively final 限制——因为字段不捕获，捕获的是 this。lambda 里写 this.count++，实际是"我持有的 this 引用不变，改的是它指向对象的字段"——和 2.4 里"改引用指向的内容"是同一个原理。这也是 lambda 和匿名内部类在 this 语义上的关键差异点，下一节展开。

03

Lambda 底层：不是语法糖 原理高频

面试官的经典开局："Lambda 是匿名内部类的语法糖吗？"标准答案是：不是。两者编译产物、运行机制、this 语义全都不一样。这一节把原理讲透，答出层次感。

3.1 先看证据：编译产物完全不同

写一个类，里面各来一个匿名内部类和一个 Lambda，javac 编译后：

  class Outer {
      Runnable a = new Runnable() { public void run() {...} };   // 匿名内部类
      Runnable b = () -> {...};                                   // Lambda
  }

编译产物对比：
  匿名内部类：  编译期就生成 Outer$1.class  ← 真实存在的类文件，类加载器要加载它
  Lambda：      没有任何额外 class 文件！    ← 编译期只在字节码里留了一条
                                              invokedynamic 指令 + 一个私有静态方法

验证：javap -p Outer 看不到 Lambda 对应的类，只能看到
      private static void lambda$new$0()   ← 你的 lambda 体被挪进了这个方法

也就是说：匿名内部类是编译期就定型的类；Lambda 是运行时才生成的实现——生成机制由 JVM 的 invokedynamic 指令驱动。

3.2 原理：invokedynamic + LambdaMetafactory

invokedynamic（简称 indy）是 JDK 7 引入的字节码指令，设计初衷是给动态语言跑在 JVM 上用的（Groovy、JRuby），特点是：调用点第一次执行时，才决定"真正调用哪个方法"，之后把决定缓存下来。Java 8 借它来实现 Lambda：

Runnable r = () -> doWork();   的执行时序：

  编译期（javac）：
    lambda 体          → 挪进私有方法 lambda$new$0()
    赋值语句           → 编译成一条 invokedynamic 指令（指向 bootstrap 方法）

  运行期（第一次执行到这行）：
    invokedynamic 触发 bootstrap：调用 LambdaMetafactory.metafactory()
      输入：函数式接口的 SAM 描述（方法签名） + 你的 lambda$new$0 的引用
      动作：【现场生成一个实现类】（JDK 8 用内部 ASM 生成字节码，
            JDK 15+ 换成隐藏类 HiddenClass），实现 SAM 方法，
            方法体就是"转发调用 lambda$new$0"
      产物：一个 CallSite，绑定了刚生成的实现类的构造器
    用 CallSite 里的构造器 new 一个实例 → 装进 r

  运行期（第二次及以后执行到这行）：
    直接走缓存的 CallSite，不再走 bootstrap —— 路径已经焊死

★ 无状态 Lambda 的彩蛋：不捕获任何变量的 lambda，
  生成的实例是【单例缓存】的 —— 写 1 万个 () -> 42，
  运行时只会有一个对象在反复被复用（饿汉式复用，不是每次 new）。
  捕获了变量的 lambda 才会每次 new（因为要装捕获的值）。
🔍 为什么绕这么大一圈，不直接像匿名内部类那样编译期生成？

三个理由：① 启动性能——匿名内部类在编译期生成一堆小类，应用启动就要全部加载验证（想想一个大项目里成千上万个 lambda）；indy 让类推迟到真正执行时才生成，还允许 JIT 对无捕获 lambda 做单例缓存。② 解耦——生成策略（用 ASM 还是 HiddenClass、要不要脱糖成私有方法）是 JDK 内部实现，未来可以换，字节码不用重编；匿名内部类的类文件一旦生成就焊死了。③ 语言中立——indy 本来就是给动态语言设计的通用机制，lambda 只是它的第一个"官方 Java 应用"。

3.3 this 语义：最容易被问懵的差异

ThisDiff.java同一个位置打印 this
public class Outer {
    void demo() {
        Runnable anon = new Runnable() {
            public void run() {
                System.out.println(this);      // 打出 Outer$1@xxxx —— 匿名类自己！
                System.out.println(Outer.this);// 要拿到外围得这么写
            }
        };
        Runnable lamb = () -> System.out.println(this);  // 打出 Outer@xxxx —— 外围实例！
    }
}

原理一句话：匿名内部类是真的独立类，有独立的 this；Lambda 不是类，它只是外围类里的一个方法（lambda$new$0），里面的 this 自然指向外围实例——术语叫词法 this（lexical this）：this 由"代码写在哪"决定，不由"运行时包在哪个对象里"决定。这也解释了 2.4 的遗留问题：lambda 里改 this.count 合法，因为它就是外围类的字段。

一句话回答

Lambda 是匿名内部类的语法糖吗？——不是。匿名内部类编译期生成独立 class 文件、this 指向自身；Lambda 编译成 invokedynamic 指令，运行期由 LambdaMetafactory 动态生成实现（无捕获 lambda 单例复用），this 是词法的、指向外围类。且 Lambda 只能实现函数式接口。

1
追问：那 Lambda 性能比匿名内部类好吗？
首次调用有 bootstrap 开销（生成类，微秒~毫秒级）；热路径执行时性能持平甚至更好（无捕获单例复用 + JIT 可内联转发链）。冷启动敏感的场景（低延迟交易、CLI 工具）首次调用开销才需要在意，日常业务无感。
2
追问：怎么亲眼看到 lambda 没生成类？
javac 编译后 ls *.class：只有 Outer.class 没有 Outer$1（匿名内部类的对照组会有）；javap -p Outer 能看到 lambda$xxx$0 私有方法；javap -v 里能看到 invokedynamic 指令和 BootstrapMethods 表。面试说出"我会用 javap 验证"，原理可信度直接拉满。
3
追问：方法引用和 lambda 在字节码层面一样吗？
一样，都是 invokedynamic。区别只在 bootstrap 的参数：lambda 传"编译器生成的私有方法"，方法引用传"已有方法的句柄"（MethodHandle）。所以方法引用不是又一层魔法，只是"省得编译器再抄一遍"的写法。
04

方法引用与函数式接口家族

4.1 方法引用：lambda 的极致简写

当 lambda 体只有一句、且这句恰好是在调用一个现成方法时，可以进一步省略——连参数都不用写，直接点名那个方法：

MethodRef.java四种形态
// ① 类名::静态方法
Function<String, Integer> f = Integer::parseInt;          // 等价 s -> Integer.parseInt(s)

// ② 对象::实例方法
String prefix = "user-";
Predicate<String> p = prefix::startsWith;               // 等价 s -> prefix.startsWith(s)

// ③ 类名::实例方法（★最特殊，4.2 专讲）
BiPredicate<String, String> bp = String::startsWith;    // 等价 (s, arg) -> s.startsWith(arg)

// ④ 类名::new（构造器引用）
Supplier<ArrayList<String>> sup = ArrayList::new;        // 等价 () -> new ArrayList<>()

4.2 类名::实例方法 为什么不别扭了

③ 是最容易看懵的：startsWith 明明是实例方法，凭什么可以用"类名"去引用？规则是——函数式接口的第一个参数，成为方法的调用者（接收者），剩下的参数依次传入：

BiPredicate<String, String> bp = String::startsWith;

调用 bp.test("user:admin", ":admin")
   等价于执行："user:admin".startsWith(":admin")
                    ↑              ↑
        第一个参数变成接收者    第二个参数是方法实参

为什么这样设计？—— 让"对象的方法"也能当"函数"传：
  Stream<String> 里每个元素都是接收者：
  list.stream().map(String::toUpperCase)
       每个流元素 s → s.toUpperCase()     —— 参数 s 自己当了主语
没有这个规则，凡是涉及实例方法都得写回 lambda，方法引用的适用面砍一半。

4.3 四大内置函数式接口（必背）

JDK 在 java.util.function 包里预定义了几十个函数式接口，但万变不离四大金刚——记住四个抽象方法，全家都认识：

接口抽象方法语义（记忆口诀）典型场景
Function<T,R>R apply(T t)有进有出：进去 T 出来 R（加工厂）map：元素怎么变形
Consumer<T>void accept(T t)只进不出：消费 T，无返回（无底洞）forEach：拿到元素干点啥
Supplier<T>T get()不进就出：无中生有给一个 T（发电机）惰性求值、工厂、orElseGet
Predicate<T>boolean test(T t)进 T 出 boolean（裁判：行不行你说了算）filter：留还是丢
家族扩展规则（认识即可，不用背全）：
  Bi 前缀     = 参数变两个：BiFunction<T,U,R>、BiConsumer、BiPredicate
  XxxFunction = 类型特化（避开自动装箱）：ToIntFunction<T>、IntToLongFunction...
  UnaryOperator<T> = Function 的"进同出"特例：T -> T（如 String::trim）
  BinaryOperator<T> = BiFunction 的"进同出"特例：(T,T) -> T（reduce 的合并器！）

为什么大量类型特化？—— 回收模块 4 的教训：泛型只能装引用类型，
int 要 Integer（装箱），Stream 大数据量下装箱开销会被放大，
所以库作者提供了 IntStream / ToIntFunction 这条"原生类型旁路"。
📌 面试问"你常用哪些函数式接口"

不要背全家桶。答法："四大核心是 Function/Consumer/Supplier/Predicate，对应 Stream 里 map/forEach/惰性供给/filter 的参数类型；实际开发里 Function 最常见——比如 HashMap.computeIfAbsent(key, k -> new ArrayList<>()) 的第二个参数（回收模块 4：一行实现"键不存在则放入"的多值分组）。"

一句话回答

方法引用是什么？——lambda 体只有一句且恰好是调用现成方法时的简写：类::静态方法、对象::实例方法、类::实例方法（首参数当接收者）、类::new 四种形态；字节码层面和 lambda 相同（都是 invokedynamic，只是 bootstrap 参数从"编译器生成的私有方法"换成"已有方法的 MethodHandle"）。

@FunctionalInterface 注解不加行不行？加了有什么用？

行——注解只是编译期检查，不加也能当函数式接口用（Runnable 从 Java 1.0 就没这注解照样接 lambda）。加上后编译器会替你把关：不小心加了第二个抽象方法、或父接口带来了冲突的抽象方法时直接编译报错，而不是等到 lambda 写不出来才发现。规范建议：给"设计出来就是要接 lambda"的接口都加上，属于把契约写成文档。

Python 里的对应物？Python 对比

方法引用 = Python 的绑定方法：str.upper、"x".startswith、len 都是"函数当值传"的日常——sorted(users, key=operator.attrgetter('age')) 或 key=lambda u: u.age 就是 comparing(User::getAge) 的镜像。区别：Python 一切皆对象函数从来都是一等公民，Java 8 的这整套"函数式接口 + lambda"本质上是在不破坏类型系统的前提下，把函数抬成一等公民的补丁——这也是面试聊设计时能说出高度的一句。

Stream：声明式数据流水线 高频

5.1 痛点：命令式循环的样板噪音

"找出年龄大于 18 的用户，按名字排序，取出名字列表"——命令式写法：

Imperative.java意图被淹没在流程里
List<String> result = new ArrayList<>();          // ① 先准备容器
for (User u : users) {                            // ② 手动遍历
    if (u.getAge() > 18) {                        // ③ 过滤（if 套层皮）
        result.add(u.getName());                  // ④ 变形（add 里面做映射）
    }
}
result.sort(String::compareTo);                   // ⑤ 排序（另一轮操作）
// 5 个步骤讲的是"怎么做"（怎么遍历、怎么放、怎么排），
// 而"要什么"（大于18、按名排序、只要名字）被拆散埋在流程里
Declarative.java只说要什么
List<String> result = users.stream()
        .filter(u -> u.getAge() > 18)            // 要什么：大于 18
        .sorted(Comparator.comparing(User::getName))  // 按名字排
        .map(User::getName)                        // 只要名字
        .collect(Collectors.toList());             // 装成列表

这就是命令式 vs 声明式的差别：命令式写"机器怎么一步步做"，声明式写"我要什么样的结果"。Stream 把"遍历、暂存、排序"这些流程控制全部收编进库，你的代码只剩业务谓词。

5.2 心智模型：三段式流水线

一条完整的 Stream 流水线 = 三段：

  【数据源】──►【中间操作 × N（惰性，只搭管道）】──►【终端操作（1 个，触发执行）】

  users.stream()          .filter(...)  .map(...)  .sorted(...)     .collect(...)
  └─ 数据源               └──────── 中间操作（返回新 Stream）        └─ 终端操作
    集合/数组/            无状态：filter map flatMap peek           触发整条流水线
    生成器/I/O channel    有状态：sorted distinct limit skip        汇聚成结果

铁律一：中间操作不干活，只是把"工序"登记进管道 —— 没有终端操作，
       这条流水线一行代码都不会执行（5.1 的代码去掉 collect 就什么都不发生）
铁律二：终端操作只能有一个，触发后流就被"消费"了 —— 同一个 Stream
       不能再 collect 一次（IllegalStateException，见 5.6）

5.3 常用 API 速查

中间操作（返回 Stream，惰性）
filter(Predicate)过滤：留下 test 为 true 的
map(Function)一对一变形：T → R
flatMap(Function)一对多变形并摊平：T → Stream<R> → 拍扁（5.4 专讲）
distinct()去重（按 equals，有状态）
sorted() / sorted(cmp)排序（有状态：需要全量数据，见第 6 节）
limit(n) / skip(n)截取前 n 个 / 跳过前 n 个（短路能力）

终端操作（触发执行，出结果）

reduce(BinaryOperator)折叠：把流合并成一个值（求和/求积/拼接）
count / min / max计数 / 最值（min/max 返回 Optional）

5.4 flatMap：一对多再摊平

map 是一对一：一个元素进来一个元素出去。但如果一个元素要变出一组元素（比如每个订单取它的全部商品），map 会得到"流的流"（Stream<Stream<Item>>）——flatMap 在 map 之后把所有内层流摊平成一条流：

FlatMap.java所有订单的全部商品
List<List<Item>> orders = ...;

// map 版：一对一，得到 Stream<List<Item>>，还得再剥一层
orders.stream().map(Order::getItems);           // Stream<List<Item>>

// flatMap 版：一对多 + 摊平
orders.stream()
      .flatMap(o -> o.getItems().stream())      // 每个订单 → 一条商品流
      .collect(toList());                       // 所有商品合成一条流再收集

// 拆字符串的经典应用：
List<String> words = Arrays.asList("hello world", "java stream").stream()
        .flatMap(s -> Arrays.stream(s.split(" ")))   // 每句 → 多个单词
        .collect(toList());                          // [hello, world, java, stream]
🐍 Python 对比

flatMap = 列表推导的双 for：[w for s in texts for w in s.split()]；map = [f(x) for x in xs]；filter = [x for x in xs if p(x)]。区别在你写 Python 时"惰性/及早"由选 [] 还是 () 决定，Java 里由"有没有终端操作"决定——见下一节。

5.5 collect 与 Collectors：汇聚的艺术

Collectors.java日常高频六件套
// ① 基础汇聚
List<String> names = users.stream().map(User::getName).collect(toList());
Set<String>  uniq  = users.stream().map(User::getName).collect(toSet());

// ② toMap：key 冲突会直接炸（IllegalStateException: Duplicate key）
//    必须给第三个参数：冲突时怎么合并 —— 高频坑！
Map<Long, User> byId = users.stream().collect(
        toMap(User::getId, u -> u, (a, b) -> a));        // 重复 id：留先出现的

// ③ groupingBy：分组（等价 SQL 的 GROUP BY，替代 Map<K, List<V>> 手写循环）
Map<String, List<User>> byCity = users.stream().collect(groupingBy(User::getCity));

// ④ groupingBy + 下游收集器（多级聚合的精髓）
Map<String, Long> countByCity = users.stream().collect(
        groupingBy(User::getCity, counting()));            // 每组人数
Map<String, Double> avgAge = users.stream().collect(
        groupingBy(User::getCity, averagingInt(User::getAge)));

// ⑤ partitioningBy：按谓词一分为二（key 就是 boolean）
Map<Boolean, List<User>> adults = users.stream()
        .collect(partitioningBy(u -> u.getAge() >= 18));

// ⑥ joining：字符串拼接（比手写 StringBuilder 干净）
String s = names.stream().collect(joining(", ", "[", "]"));

5.6 两个高频陷阱

⚠ 陷阱一：流只能消费一次

Stream 不是集合，更像一个只能读一次的迭代器（很多源如生成器、IO 通道根本无法"倒带"）。对同一个流调两次终端操作 → 第二次抛 IllegalStateException: stream has already been operated upon or closed。要多次用就再 list.stream() 拿一条新的——流是"管道图纸"，集合才是"库存"。

⚠ 陷阱二：peek 不是终端操作

调试时写了 stream.peek(System.out::println) 却什么都没打印？因为 peek 是中间操作，没有终端操作整条流水线都不执行（惰性求值，下一节原理）。它必须搭配终端操作才能"流起来"——顺便，peek 里做业务逻辑是反模式，它的设计意图就是调试观察。

一句话回答

Stream 是什么？——声明式的数据流水线：数据源 → 中间操作（惰性、返回新 Stream）→ 终端操作（唯一、触发执行）。中间操作不碰数据、只登记工序；终端操作一发令，数据一次性流过全管道。流只能消费一次。

Stream 和集合到底什么区别？什么时候不该用 Stream？

集合是装数据的容器（在内存里、可反复遍历）；Stream 是对数据的计算描述（不存数据、一次性、可来自无限生成器）。不该用的场景：① 需要过程中随时访问/修改中间状态（Stream 管道里拿不到"当前下标"）；② 循环体里有复杂分支跳转（break/continue 多层嵌套）；③ 数据量极小且 lambda 捕获大量外部变量——普通 for 更直白。判断标准：流水线是"纯数据变换"就用 Stream，一旦掺杂流程控制就该回 for。

reduce 怎么用？和 collect 什么区别？

reduce 是"把 N 个变 1 个"的折叠：nums.stream().reduce(0, Integer::sum)（初始值 + 合并函数）。区别在于可变归约 vs 不可变归约：reduce 每次都产生新值（String 拼接会复制 N 次，O(n²)）；collect 是可变归约——往同一个 StringBuilder 里 append，O(n)。所以规约成 List/Map/String 永远用 collect，规约成 数值/Optional 用 reduce。这个区分在并行流里还有正确性含义（不可变归约天然并行安全）。

06

Stream 原理：惰性求值与并行 原理高频

6.1 惰性求值：不推不动，一推全通

LazyDemo.java亲眼验证惰性
Stream<Integer> s = Stream.of(1, 2, 3, 4, 5)
        .filter(x -> { System.out.println("filter " + x); return x % 2 == 0; })
        .map(x ->     { System.out.println("map " + x);    return x * 10; });

System.out.println("—— 到这里为止，一行 filter/map 都没打印过 ——");

s.forEach(x -> System.out.println("输出 " + x));   // 终端操作：此刻才开始动

为什么这么设计？三个理由：① 合并遍历——所有操作在一次遍历里流水完成，不用为每步生成中间集合（对比命令式的 for+if+newList）；② 短路成为可能——见 6.3；③ 描述与执行分离——同一份"图纸"可以被串行执行、也可以被并行执行（6.4），集合框架的遍历做不到这一点。

6.2 实现机制：Sink 回调链

"一次遍历跑完所有操作"在源码层面是怎么实现的？答案：把流水线反向串成回调链（Sink 链）：

.filter(even).map(x*10).forEach(print) 的执行结构：

终端操作 forEach 触发时，JDK 从尾到头把每道工序包成 Sink（带回调的"水槽"）：

  Spliterator（源迭代器，模块化数据源）
        │ tryAdvance(e) —— 每推一个元素进来：
        ▼
   ┌─ Sink①（filter）──accept(e)：不满足条件就【丢弃】（链到此断掉）
   │                        满足 → 往下传
   ▼
   └─ Sink②（map）────accept(e)：算 x*10 → 往下传
        ▼
   └─ Sink③（forEach）─accept(e)：打印

关键点：
  ① 每个元素是【纵向】流过全部工序 —— 1 号元素从头走到尾，才轮到 2 号
     （对比命令式：所有元素先过完 filter 存入中间 list，再全部过 map……横向分批）
  ② 不满足 filter 的元素在 Sink① 就被丢弃，根本流不到后面的 map
  ③ 没有中间集合 —— 元素一直"在传送带上"，不落地

这个"元素纵向流过全管道"就是 Stream 高效的本质：命令式的多步操作 = 多趟遍历 + N 个中间集合；Stream = 一趟遍历 + 零中间集合（sorted 这类有状态操作除外，它必须落地缓冲）。

6.3 短路操作：流水线的刹车

// 无限流 + 短路：不可能"先处理完全部数据"
Stream.iterate(1, i -> i + 1)          // 1, 2, 3, ... 无限流
      .filter(i -> i % 3 == 0)         // 3 的倍数
      .limit(5)                        // ★ 短路刹车：拿够 5 个立刻停
      .forEach(System.out::println);   // 打印 3,6,9,12,15 后终止

短路家族：limit / takeWhile（J9）
         findFirst / findAny
         anyMatch / allMatch / noneMatch

原理：短路 Sink 在条件满足时通知上游"不用再推了"
（cancellationRequested），Spliterator 停止 tryAdvance —— 整条
流水线提前熄火。这也解释了为什么中间操作要区分【无状态】和【有状态】：
  无状态（filter/map）：来一个处理一个，可流式、可短路；
  有状态（sorted/distinct）：必须【攒齐全量】才能出结果
    —— sorted 不看到最后一个元素，怎么知道谁排第一？
    —— 有状态操作是流水线上的"蓄水池"，切断了短路传播、
       也伤害并行度（第 6.4 节）。

6.4 并行流：一行 .parallel() 背后

ParallelDemo.java同一份图纸，并行执行
long total = users.parallelStream()                 // 或 stream().parallel()
        .filter(u -> u.getAge() > 18)
        .mapToLong(User::getScore)
        .sum();                                     // 描述与执行分离的红利

原理三件套（对应模块 6/6B 的知识）：

  1. 任务切分：数据源包装成 Spliterator（splitable-iterator），trySplit() 把数据对半切、递归分治，直到块足够小；
  2. 执行池：切出的任务丢进 ForkJoinPool.commonPool()——JVM 全局共享的 Fork/Join 线程池（回收模块 6：线程数默认 CPU 核数 - 1）；
  3. 结果合并：每块独立跑完流水线，reduce/collect 把各块结果两两合并（combiner）。
⚠ 并行流四大陷阱（面试重灾区）

① 共享可变状态：forEach(list::add) 在并行下 ArrayList 直接坏——要汇聚结果必须用 collect/reduce（无锁合并），而不是 forEach+共享容器；② IO 操作吃光公共池：并行流里查数据库/调接口，阻塞的 worker 占满 commonPool，全 JVM 所有并行流一起饿死（IO 请回模块 6 的自定义线程池 + CompletableFuture）；③ 有状态操作拖后腿：sorted 需要全量聚合，并行优势归零；④ 小数据量负优化：切分与合并的协调开销 > 并行收益（经验值：元素数万级、单元素计算微秒级以上才值得）。

一句话回答

并行流原理？——Spliterator.trySplit 把数据递归对半切成分治任务，提交到全局共享的 ForkJoinPool.commonPool 并行执行，各块结果用 combiner 合并。适合"纯 CPU 计算 + 大数据量 + 无共享可变状态"；有 IO、有状态操作、小数据量都不适合。

1
追问：parallelStream 线程数能配吗？
commonPool 的默认并行度 = CPU 核数 - 1，可用系统属性 java.util.concurrent.ForkJoinPool.common.parallelism 调整（全局生效，改的是所有用户的池）。想给某个流水线专用线程池，得绕过 parallel() 手动提交到自己的 ForkJoinPool 里执行（customPool.submit(() -> stream...)）——能说出"commonPool 是共享的、会被别人影响"就是加分回答。
2
追问：为什么 forEach + 共享 list 会坏，collect 就没事？
forEach 的 Consumer 被多线程同时调，ArrayList 非线程安全（模块 4/6：并发写丢更新）；collect 是"可变归约"，JDK 的收集器为并行设计了 per-thread 累积容器（如 toList 每个线程攒自己的 List），最后 combiner 一次性合并——把"并发写"变成"各自写+串行合并"，无锁且正确。

6.5 CompletableFuture：把编排带进异步 高频

模块 6 埋过钩子说"CompletableFuture 是模块 7 的内容"——因为它是 Java 8 函数式（lambda）和 Java 7 并发（Future）的合体：用回调式的链式 API 解决老 Future 的两大残废：

老 Future（模块 6 见过）的两个致命伤：
  ① get() 是【阻塞】的 —— 想拿结果就得原地等，异步了个寂寞
  ② 任务之间【无法编排】 —— "A 完成后用 A 的结果跑 B，B 完成后合并 C/D"
     用老 Future 只能层层 get() 嵌套（阻塞套阻塞）

CompletableFuture 的答案：把"下一步干什么"【提前登记成回调】——
  f.thenApply(x -> ...)      结果到了自动加工（map 语义）
  f.thenCompose(x -> f2)     结果到了自动启动下一个异步（flatMap 语义）
  f.thenCombine(g, merger)   两路异步都到了自动合并
  CompletableFuture.allOf(f1, f2, f3)   等全完成（CountDownLatch 的异步版）
全程【零阻塞】：你登记的是"流程图"，执行是事件驱动的。
AsyncPipeline.java典型异步编排
// 查用户 + 查订单 并行，合并成详情 —— 谁也不阻塞谁
CompletableFuture<User> userF =
        CompletableFuture.supplyAsync(() -> queryUser(id));          // 异步任务
CompletableFuture<List<Order>> orderF =
        CompletableFuture.supplyAsync(() -> queryOrders(id));

CompletableFuture<Detail> detailF =
        userF.thenCombine(orderF, (user, orders) ->                 // 两路合并
                new Detail(user, orders));

detailF.thenAccept(d -> render(d))                                  // 结果到了自动消费
       .exceptionally(ex -> { log.error("失败", ex); return null; }); // 异常兜底

// ★ 最重要的工程细节（回收模块 6 的坑）：
// supplyAsync 不传线程池 → 默认 ForkJoinPool.commonPool()（CPU 核数-1）
// 里面跑的是【查库/调接口这种 IO 阻塞活】→ 吃光公共池 → 全 JVM 的并行流陪葬！
// IO 任务必须显式给线程池：
CompletableFuture.supplyAsync(() -> queryUser(id), ioExecutor);     // 自定义线程池

// thenApply vs thenCompose（面试爱问，纯 Optional/Stream 的既视感）：
f.thenApply(x -> transform(x))        // 同步加工：T → R           （map）
f.thenCompose(x -> asyncStep(x))      // 异步串联：T → CF<R> 摊平   （flatMap）
一句话回答

CompletableFuture 是什么？——回调式的异步编排工具：把"A 完成后干什么"登记成 thenApply/thenCompose/thenCombine 的链条，事件驱动、零 get() 阻塞。默认线程池是 ForkJoinPool.commonPool（IO 任务必须换自定义池），thenApply 是 map、thenCompose 是 flatMap、allOf 是异步版 CountDownLatch。

并行流和 CompletableFuture 都用 commonPool，什么时候用谁？Python 对比

并行流 = 数据并行（一大坨数据切成块同时算，分治模型）；CompletableFuture = 任务并行（几个不同任务各自跑、之间有依赖编排，DAG 模型）。一堆元素统一变换 → parallelStream；查三个接口再汇总 → CompletableFuture.allOf。Python 对应物：前者像 multiprocessing.Pool 的 map，后者就是你熟的 asyncio.gather / loop.run_in_executor——连"IO 别占 CPU 池"的告诫（别在 event loop 里跑阻塞调用）都一一对得上。

Optional：把 NPE 提前到编译期 高频

7.1 痛点：null 是十亿美元的错误

发明引用类型的计算机科学家 Tony Hoare（快速排序之父）晚年公开道歉："1965 年我发明了 null 引用……这是我犯的十亿美元级的错误。"null 的问题不在"空"本身，而在类型系统对它视而不见：

String findUser(Long id) { ... }   // 返回 String —— 但可能返回 null

调用方拿到返回值，类型是 String，编译器担保"这是个字符串"，
结果一调 .length() —— 运行时 NPE 爆炸。

"可能没有"这个信息【存在于程序员的脑子里】，不存在于类型里：
  编译器不知道 → 不能帮你检查
  后来维护的同事不知道 → 忘判 null
  你自己三天后也不知道 → NPE 在深夜生产环境等着

Optional<String> 的本质：把"可能没有"从【脑子】搬进【类型系统】——
返回类型写 Optional<String>，调用方【必须】打开盒子才能用值，
打开的动作天然逼你面对"两种情况"。

7.2 正确用法：返回值类型专用

OptionalFlow.java链式取值 vs if-null 地狱
// 老写法：嵌套 if-null 地狱（每一层都可能炸）
if (user != null) {
    Address addr = user.getAddress();
    if (addr != null) {
        String city = addr.getCity();
        if (city != null) { ... }
    }
}

// Optional 链：和 Stream.map 同源的管道思维
String city = findUser(id)                              // Optional<User>
        .map(User::getAddress)                          // Optional<Address>：空则跳过
        .map(Address::getCity)                          // Optional<String>
        .orElse("未知城市");                             // 兜底：全链任一环节为空都用它

// of / ofNullable / empty 的区别（创建端）
Optional<User> a = Optional.of(user);                  // user 为 null 直接 NPE（明确"不该为空"时用）
Optional<User> b = Optional.ofNullable(user);         // 允许为 null → 装成空盒子
Optional<User> c = Optional.empty();                   // 显式的空盒子

map 里的逻辑：盒子有值 → 对值变形、装回新盒子；盒子是空 → 什么都不做，返回空盒子——空值像管道里的"幽灵"直接穿过全链，最后在 orElse 处被兜住。嵌套的 Optional 展平用 flatMap（和 Stream 同款语义）。

7.3 高频陷阱：orElse vs orElseGet 必考

OrElseTrap.java一个参数求值时机问题
String result = optionalUser
        .map(User::getName)
        .orElse(queryDefaultFromDb());    // ✗ orElse 的参数是【值】—— 立刻求值！

// 无论盒子有没有值，queryDefaultFromDb() 都会执行：
//   盒子有值 → 查了白查，数据库白白挨一刀（性能事故）
//   盒子为空 → 查询结果被用上（碰巧正确）

// 正解：orElseGet —— 参数是 Supplier（回 4.3 的"发电机"），【惰性求值】
String result = optionalUser
        .map(User::getName)
        .orElseGet(() -> queryDefaultFromDb());   // 只有盒子为空才执行查询
记忆锚点（回收 4.3 四大金刚）：
  orElse(T other)         参数是【值】     —— 方法调用的参数永远先求值（模块 2 的坑）
  orElseGet(Supplier<T>)  参数是【发电机】 —— 值需要时才现场发电

什么时候 orElse 也行？—— 兜底值是字面量/常量：
  .orElse("默认值")        // 求值零成本，两者等价
只要兜底值【有计算成本】（查库、new 大对象、读文件），必须 orElseGet。

7.4 反模式清单（说得出这些 = 真用过）

反模式为什么错正确做法
isPresent() + get()等价于 != null + 直接用，只是换了个更啰嗦的 null 检查，没吃到类型收益map/filter/orElse 链式表达
拿 Optional 做字段字段可空 = 类没序列化好；Optional 不可序列化，JPA/JSON 全出问题字段该空就空，getter 返回时再包 Optional
拿 Optional 做方法参数三个参数三个 Optional，调用方痛苦且编译器不强制（还能传 null）用重载/默认参数语义，或 @Nullable 注解
Optional<List<T>> 当返回值两种"空"语义重叠（空盒子 vs 空列表）返回空集合 Collections.emptyList()——空列表是明确的"没有"

一句话回答

Optional 是什么？——把"可能没有"编码进返回类型，逼调用方在编译期面对空值分支的包装类；专用领域是返回值，用 map/flatMap/orElse 链式消费，不碰 isPresent+get、不当字段不当参数。orElse 参数立即求值、orElseGet 惰性求值——有成本的兜底必须用后者。

Optional 能彻底消灭 NPE 吗？

不能，它只是把"可能没有"显式化，消灭的是"忘了判空"这一类。Optional 本身也可能是 null（Optional<String> o = null 完全合法），所以工厂方法要规范地用 ofNullable；第三方库/老代码返回的也可能随时是 null。工程上的完整答案是：Optional 管自己 API 的出参入参契约 + Objects.requireNonNull 管不变量 + @Nullable/@NonNull 注解管边界 + IDE 静态分析兜底——分层防御。

Python 里你怎么处理这个问题的？Python 对比

三条对应物：① Optional[str] 类型注解——但纯注解不强制，要 mypy/pyright 检查才等价于 Java 编译器；② 兜底惯用 user.city if user else default 或 getattr(x, "city", default)，惰性语义天然安全（这题在 Python 里反而不容易踩坑）；③ Kotlin/Swift 的 ? 和 ?: 才是 Optional 语义的语言级完全体。面试可以补一句："Java 用库的方式做了别的语言做进语法的事"——显示你对语言设计的理解。

接口的默认方法与冲突裁决 原理高频

8.1 痛点：已发布的接口没法演化

Java 7 时代的世界：
  interface Collection<E> 已发布十年，全宇宙无数实现类

  Java 8 想加 stream() —— 问题来了：
  ├─ 加抽象方法？所有实现类（你项目里的、老开源库里的）全部编译报错
  │  —— 接口是【契约】，契约加条款，所有签了字的类都得补实现
  └─ 不加？Stream 无处安放，函数式革命死在第一步

解法：default 方法 —— 带着实现体进接口：
  interface Collection<E> {
      default Stream<E> stream() {
          return StreamSupport.stream(spliterator(), false);
      }   // 实现类不写也有默认行为；想优化的自己覆盖（ArrayList 覆盖了）
  }

代价：接口从【纯契约】变成【契约 + 部分实现】
—— 菱形继承问题（多继承冲突）随之而来，需要裁决规则（8.3）

顺带的配套：Java 8 还允许接口带 static 方法（工具方法直接挂接口上，如 Comparator.comparing）；Java 9 进一步允许 private 方法（给多个 default 方法复用私有逻辑）。

8.2 菱形问题：两份默认实现，听谁的？

DiamondConflict.java三条裁决规则
interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }

// 冲突：C 同时继承 A、B，两个同名 default
class C implements A, B {
    // ✗ 不写 hello() 直接编译错误：
    //   "class C inherits unrelated defaults for hello() from types A and B"

    // 规则三：冲突必须由你显式裁决——要么覆盖，要么点名委托
    public String hello() {
        return B.super.hello() + " wins";      // ★ X.super.m() 语法：点名用哪个爹的版本
    }
}

// 规则一（类优先）：父类的具体方法 > 接口的默认方法
class Base { public String hello() { return "Base"; } }
class D extends Base implements A {}            // hello() = "Base"，不冲突，编译通过

// 规则二（更具体的接口优先）：子接口的 default 胜过父接口
interface SubA extends A { default String hello() { return "SubA"; } }
class E implements SubA, A {}                   // hello() = "SubA"（编译器选更具体的）
裁决优先级（从高到低）：
  ① 你自己覆盖的                          （最高，一锤定音）
  ② 父类（class）的具体方法                （类优先：类层次永远压接口一头）
  ③ 更具体的子接口的 default              （SubA extends A → SubA 赢）
  ④ 平级冲突（A vs B，谁也不具体）         编译报错，逼你显式选边：X.super.m()

为什么"类优先"？—— 兼容性铁律：Java 8 发布前，已有的类都继承自各种父类；
如果接口 default 能压过父类方法，升级 JDK 8 就可能【悄悄改变线上类的行为】。
规则一保证了：加 default 方法，永不改变既有类的行为 —— 演化安全。

8.3 抽象类 vs 接口：Java 8 之后怎么选

能力抽象类接口
实例字段（状态）✓✗（只有 static final 常量）
构造器✓✗
具体方法✓✓ default/static/private（Java 8/9）
多继承✗ 单继承✓ 实现多个（类型的可组合性）
访问控制成员可 protected方法只 public

选型一句话（回收模块 3）：接口定义"能做什么"（能力契约，可组合多个：Comparable + Serializable + Runnable）；抽象类共享"是什么"（骨架 + 状态 + protected 复用，如 AbstractList 之于 ArrayList）。Java 8 让接口能带实现，模糊了界限，但状态和构造器永远属于类——模板方法需要中间状态时（AQS 的 owner 字段！回收模块 6B 第五幕），仍然只能用抽象类。

一句话回答

默认方法是什么？——接口里带 default 的有实现方法，为的是"已发布接口可以安全演化"（stream() 进 Collection 而不炸全世界的实现类）。冲突裁决三规则：类优先 → 子接口优先 → 平级冲突编译报错、必须覆盖或 X.super.m() 显式点名。

抽象类也能有默认实现，为什么不干脆都用抽象类？

两个硬约束：① 单继承瓶颈——一个类只能 extends 一个抽象类，但能 implements 无限个接口；给 Collection 全家加 stream() 如果用抽象类，已经继承了别的抽象类的集合类就无路可走；② 演化扩散——抽象类位于继承链中间，加方法影响所有子类布局；接口 default 只在"没人实现这个方法时"兜底，已实现的类纹丝不动。一句话：default 方法本质是面向"接口演化"的设计，不是"给接口加工具"的语法福利——后者的正统写法是 static 方法。

default 方法能重写 Object 的方法吗（比如 toString）？

不能。编译器明文禁止接口给 toString/equals/hashCode 提供 default——因为每个类都从 Object 继承了这些方法，按"类优先"规则，Object 的版本永远赢，接口里的 default 永远是死代码，禁掉是为了避免错觉（看起来写了实际永远不生效）。这也是一条很好的"面试聊细节"素材。

罪状表现呼应模块

9.2 家族地图

java.time 包按"你关心什么"分家：

【人类时间：挂历/手表视角】（无时区语义，就是你看到的数字）
  LocalDate     2026-09-23        （日期：生日、纪念日 —— 不关心几点）
  LocalTime     19:30:05          （时间：每天打卡 —— 不关心哪天）
  LocalDateTime 2026-09-23 19:30  （日期+时间：日常 90% 场景）
  ZonedDateTime LocalDateTime+时区 （"东京 2026-09-23 20:00"：跨时区会议）

【机器时间：时间线视角】（一个绝对刻度，无日历含义）
  Instant       1770000000.123 秒（从 1970-01-01T00:00:00Z 起的纳秒数 —— Unix 时间戳）
  Duration      PT1H30M           （两时刻之间隔多久：时分秒粒度）
  Period        P1Y2M3D           （两日期之间隔多久：年月日粒度）

【工具】
  DateTimeFormatter   格式化/解析（不可变 → 线程安全，static final 随便共享）
  TemporalAdjusters   "下个周五""当月最后一天"这种日历运算

速判：存库/分布式传时间 → Instant（UTC 时间线，无歧义）；
     展示给用户 → 转成用户时区的 LocalDateTime/ZonedDateTime。

9.3 不可变设计：所有操作返回新对象

NewTime.java对比老 API 的"原地改"
// 老 API：原地修改（共享即灾难的根源）

// 新 API：返回新对象，原对象永不变化

LocalDateTime firstOfMonth = t.withDayOfMonth(1); // with = 调整某个字段，也是新对象
// t 始终是 2026-09-23 19:30 —— 像 String 一样安全（回收模块 1 的 String 不可变）

// 格式化：不可变 → 线程安全 → 可以 static final 全局共享
private static final DateTimeFormatter FMT =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
// 直接并发使用，没有 SimpleDateFormat 的任何坑（模块 6 的惨案在这里终结）

// 互操作：老代码的 Date 桥接
Instant i = oldDate.toInstant();

// 计算

一句话回答

java.time 的核心是什么？——全部不可变（每个操作返回新对象），从根上治好 Date/SimpleDateFormat 的线程安全问题；按语义分家：LocalDateTime 管"挂历"（人类时间）、Instant 管"时间线"（机器时间，UTC 存储首选）、DateTimeFormatter 不可变可全局共享。

为什么说 Instant 和 LocalDateTime 是"机器时间 vs 人类时间"？

Instant 是时间线上的一个绝对刻度（Epoch 纳秒），全球同一刻只有一个值，没有"几点"的含义——直到你选定一个时区，它才能翻译成"北京时间 19:30 / 伦敦 12:30"。LocalDateTime 是挂历读数：只有"2026-09-23 19:30"这组数字，不知道在哪个时区，就不锚定时间线上任何一点（北京时间 19:30 和伦敦 19:30 是两个不同的 Instant）。所以分布式系统存 Instant/UTC 时间戳（无歧义），展示层才按用户时区转 LocalDateTime——把这句话讲清楚，比背 API 高一个段位。

Python 的时间处理和这个像吗？Python 对比

设计哲学完全同款：你天天用的 datetime 里 naive datetime（无时区）≈ LocalDateTime，aware datetime ≈ ZonedDateTime，datetime.utcnow()/timestamp() ≈ Instant；timedelta ≈ Duration。而且 Python 的 datetime 也是不可变风格（返回新对象）、strptime/strftime 也是无状态可共享的。区别：Java 把"日期/时间/日期时间/时刻"拆成了四个独立类型，Python 全挤在一个 datetime 类里靠"填不填字段"区分——你可以反过来吐槽 Python 的设计让 datetime.time() 和 datetime.time 撞名，这种对比在面试里很出彩。

10.4 record：一行解决模块 3 的手撕题 渐热

RecordDemo.java纯数据载体的声明式写法
// 模块 3 手撕过的四件套：构造器 + getter + equals + hashCode（+ toString）
// record 一行全包：
public record Point(int x, int y) {}

// 编译器自动生成：
//   全参构造器 Point(int x, int y)
//   访问器 x() / y()              ← 注意：不叫 getX()！
//   equals / hashCode             ← 基于全部字段（和 Arrays.equals/mix 语义）
//   toString                      ← "Point[x=1, y=2]"

// 紧凑构造器：参数校验/规范化的钩子（没有参数列表，直接在构造器体写逻辑）
public record Range(int lo, int hi) {
    public Range {                              // 紧凑形式
        if (lo > hi) throw new IllegalArgumentException("lo > hi");
        // 结束时自动 this.lo = lo; this.hi = hi;
    }
}

// record 的三条铁律（都是"不可变"推出来的）：
//   ① 字段隐式 final —— 没有 setter，改值 = new 一个新的
//   ② 不能继承类（隐式 extends Record）也不能被继承（隐式 final）
//   ③ 仍可实现接口 —— 想加行为就写默认方法或静态工厂
Point p = new Point(1, 2);
Point q = new Point(1, 2);
p.equals(q);        // true —— 结构相等，模块 3 的语义比较，白送

什么时候用：DTO、值对象、Map 的复合 key（equals/hashCode 白送——回收模块 3 分桶图）、Stream 的中间结果载体。和 Lombok 的分工：record 是语言级、不可变、全字段参与 equals；@Data 是可变 JavaBean 补全（getter/setter/toString），面向 MyBatis 这类需要 setter 的旧框架生态——新项目新代码，纯数据优先 record。

🐍 Python 对比

record ≈ dataclass(frozen=True)：一行声明、自动 repr/eq、不可变；紧凑构造器 ≈ __post_init__ 校验。区别是 record 的生成物在字节码里真实存在（反编译能看到 equals/hashCode 方法体），dataclass 是运行时动态往类上挂方法——这个对比能自然引出"Java 的编译期 vs Python 的运行时"元话题。

10.5 sealed：把"多态的可能性"关进笼子

SealedDemo.java继承者白名单
// 模块 3 的老问题：switch 一个接口的子类，永远不敢删 default ——
// 明天谁又 new 了一个实现类呢？编译器不知道"全部可能性"。

// sealed：把可能性关进笼子（permits 白名单）
public sealed interface Shape permits Circle, Square, Triangle {}
//              ↑ 密封                ↑ 只准这三个实现/继承
record Circle(double r) implements Shape {}
record Square(double w) implements Shape {}
record Triangle(double b, double h) implements Shape {}
// 白名单外的类 implements Shape → 直接编译错误

// 配合 switch 模式匹配（Java 21）：穷尽检查，不用 default
double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.r() * c.r();
        case Square sq   -> sq.w() * sq.w();
        case Triangle t  -> 0.5 * t.b() * t.h();
    };  // ★ 漏一个分支编译报错！编译器知道 Shape 的全部可能性了
        //   未来新增 permits 成员，所有旧 switch 会【编译期集体报警】
}

和三件套的对照（回收模块 3 的继承语义）：final = 谁都不许继承；sealed = 白名单里的人许；普通类/接口 = 谁都许。sealed 的本质是把"开放扩展"从全开放变成可声明的有限集合——代数数据类型（ADT）思想进入 Java，函数式语言玩了几十年的东西。Python 对比：没有直接对应物，最接近的是 Literal["a", "b"] + match-case 的组合，或 Enum 限定成员——所以这个概念对你是新的，但接口很小：sealed + permits + 穷尽 switch，一屏讲完。

10.6 全模块速查

Lambda / 方法引用
  • Lambda = 装进函数式接口的无主行为；类型由上下文推断
  • 不是语法糖：invokedynamic + LambdaMetafactory 运行时生成；无捕获单例复用；this 是词法的
  • 捕获变量必须 effectively final（捕获的是值拷贝）
  • 方法引用四形态：类::静态 / 对象::实例 / 类::实例（首参当接收者）/ 类::new
四大函数式接口
  • Function<T,R> apply：有进有出（map）
  • Consumer accept：只进不出（forEach）
  • Supplier get：无中生有（惰性/orElseGet）
  • Predicate test：进 T 出 boolean（filter）
  • Bi 前缀两参 / XxxFunction 避装箱 / xxOperator 进同出
Stream
  • 三段式：源 → 中间（惰性）→ 终端（触发）
  • Sink 链：元素纵向流过全管道，一趟遍历零中间集合
  • 短路：limit/findFirst/anyMatch；有状态操作（sorted）切断短路
  • 流只能消费一次；peek 必须配终端操作
  • toMap 冲突炸、必须给 merge 函数
并行流
  • Spliterator.trySplit 分治 → ForkJoinPool.commonPool
  • 适合：纯 CPU + 大数据 + 无共享可变状态
  • 四陷阱：共享容器 / IO 阻塞 commonPool / 有状态 / 小数据量
  • 汇聚结果用 collect（per-thread 容器 + combiner），不用 forEach+共享 list
Optional
  • 定位：返回值类型专用，把"可能没有"编码进类型
  • 链式：map/flatMap/filter/orElse
  • ★orElse 参数立即求值，orElseGet(Supplier) 惰性
  • 反模式：isPresent+get、字段、参数、Optional<List>
默认方法
  • 动机：已发布接口安全演化（stream() 进 Collection）
  • 裁决：类优先 → 子接口优先 → 平级冲突必须 X.super.m()
  • 禁 default Object 方法（类优先下永远死代码）
  • 接口 vs 抽象类：状态和构造器永远属于类
java.time
  • 全不可变 → 线程安全，formatter 可 static final 共享
  • LocalDateTime=挂历；Instant=时间线（UTC 存储）；Duration/Period
  • 操作返回新对象：plus/with；老 Date 用 toInstant 桥接
Java 9~21
  • var：编译期推断、仅局部变量、不是动态类型（字节码无痕）
  • switch 表达式：箭头无穿透 + yield；文本块三引号
  • record：纯数据载体，四件套白送，不可变；紧凑构造器做校验
  • sealed + permits：继承白名单 + 穷尽 switch（无 default）
  • 虚拟线程（21）→ 原理回模块 6
