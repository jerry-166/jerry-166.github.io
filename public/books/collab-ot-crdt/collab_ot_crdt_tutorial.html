第 0 幕 · 锁为什么答非所问 悲观锁 / 乐观锁 / LWW

协作编辑的本质是多副本持续合并，而锁解决的是互斥访问——两者根本不在一个岗位上。但要讲清"哪里不像"，得先把四个容易混淆的东西放到一张表里。

岗位冲突时干什么输家的下场适合
悲观锁门卫（管准入）不让你进根本改不了短临界区、强一致事务
乐观锁门卫（管准入）提交时查版本号，拒绝重试，全部重来业务事务（转账/下单），修改不能丢
OT合并员（管内容）挪位置，你的字我的字都保留没有输家文本/结构化文档协同
LWW合并员（管内容）时间戳新的覆盖旧的无声丢尸——改动直接蒸发"输家无所谓"的字段：头像、在线状态、属性色
🔧 机制要点：乐观锁和 LWW 长得像，收场完全相反

相似点：都"不提前拦人，事后处理"。但乐观锁发现撞车后输家必须重做（业务修改绝不能丢）；LWW 发现撞车后直接扔掉输家。而 OT 和 LWW 是"合并哲学"的两个极端：OT 是"人人有座位"（意图保持），LWW 是"赢家通吃"（整字段覆盖）。实验台实验 1 的三个按钮分别演示了悲观锁断网悬死、乐观锁 409 丢字、LWW 整段蒸发。

🎪 LWW 真正的家：CRDT 工具箱里的一件工具

LWW 不是 OT 的兄弟，它是 CRDT 工具箱里管"不占位置的标量字段"的工具。Wave 的设计里"位置类操作用平移规则、属性类操作用 LWW"；Figma 公开方案是"单元格内容细粒度合并、单元格属性（颜色字体）属性级 LWW"。为什么属性用 LWW 就行？两个人都把背景色改成不同颜色，本来也只能留一个——LWW 是对这种场景的诚实投降。这正是"参数级差异"的架构思路：按数据的性质（占不占位置）配不同的合并策略，而不是一套策略包打天下。

第 1 幕 · OT 诞生与 TP1/TP2 死穴 GROVE 1989 / 变换函数 / 不可满足定理

OT 的原始想法（Ellis & Gibbs 1989，GROVE 系统）：不改别人的编辑，只改"别人编辑落到我这边时的执行方式"。执行修改由变换函数 T(op, concurrentOp)完成——把一个操作翻译成"包含对方效果之后的版本"。TP = Transformation Property（变换性质），是文献对变换函数提出的正确性公理（早期论文称 Condition C1/C2）。

1.1 变换菱形：TP1（两方并发）

设 o1、o2 是两个并发操作（基于同一文档状态 S 生成），TP1 要求：

apply( apply(S, o1), T(o2, o1) )  ==  apply( apply(S, o2), T(o1, o2) )
//   先走 o1 再走"翻译过的 o2"   ==   先走 o2 再走"翻译过的 o1"
//   菱形的两条路必须到达同一个文档（收敛）
TP1 变换菱形（格子图视角）
横轴 = Alice 本地操作数，纵轴 = 已收到的服务器广播数；斜走一格 = 做一次变换 T()；两条路终点必须一致
路径① 先本地后广播路径② 先广播后本地终点一致=菱形闭合

1.2 两个可手工复算的 TP1 反例

反例 A：平局规则不对称（Ellis & Gibbs 原始函数的真实坑）

插入撞插入（同位置）时，原始函数的平局规则是"函数第一个参数排左边"——问题在于 T(y, x) 和 T(x, y) 里"谁是第一个参数"不同，规则就不同了：

手工复算：文档 "ab"，Alice 插 x、Bob 并发插 y，都在位置 1（a|b 之间）
# Alice 端：先应用自己的 x → "axb"
#   收到 y，调用 T(y, x) —— y 是第一个参数 → y 排左 → Ins(1,"y")
#   结果 "ayxb"    ← y 跑到了 x 左边
# Bob 端：先应用自己的 y → "ayb"
#   收到 x，调用 T(x, y) —— x 是第一个参数 → x 排左 → Ins(1,"x")
#   结果 "axyb"    ← x 跑到了 y 左边
# "ayxb" ≠ "axyb"  → TP1 违反，两副本永不收敛

修复：平局规则必须换成"与调用参数顺序无关的全序"，比如 clientID 大者排右——双方在任何一台机器上算出同一结果。实验台实验 2 用的正是 clientID 平局。

反例 B：Ins/Del 边界 off-by-one

删除与插入互穿时，边界条件写错一个等号就是灾难。Imine 等人 2003 年干的事就是把学术界已发表的 10 个变换函数丢进模型检查器自动穷举——大半都能找到这类反例。不是某个函数写得差，而是"手写平局/边界规则"这个做法本身极度脆弱。

手工复算：BUG 版边界（p1 > p2 才后移，正确应为 p1 >= p2）
T_del_vs_ins(Del(p1), Ins(p2)):     # 删除操作要"路过"一个插入
    if p1 >= p2: return Del(p1 + 1)  # 正确边界
    else:      return Del(p1)
# BUG 版写成 p1 > p2，则 p1 == p2 时不后移：

# 文档 "ab"：Alice 插 X 在位置1（a|b 间），Bob 并发 Del(1)（删 b）
# Alice 端：Ins 生效 → "aXb"；收到 Del(1)，BUG 版不后移 → 删位置1 = 刚插的 X！
#   结果 "ab"（X 没了，b 还活着）
# Bob 端：Del 生效 → "ab"；收到 Ins(1,"X") 相对删除的变换 → "aXb"
# "ab" ≠ "aXb"：Bob 想删 b，Alice 端却把刚插的 X 删了 → TP1 违反

1.3 TP2：三方插队与裁决尺子（大白话版）

TP1 只管两方。当三个并发操作 o1、o2、o3 基于同一状态、且没有中央服务器定序时，o3 要"穿过" o1 和 o2 落地，TP2 要求（数学形式）：

T( T(o3, o1), T(o2, o1) )  ==  T( T(o3, o2), T(o1, o2) )
// 先穿 o1 再穿"被 o1 影响过的 o2"  ==  先穿 o2 再穿"被 o2 影响过的 o1"
🎪 大白话：三条队伍同时有人插队，你问路的顺序不能改变你的站位

你、A、B 三人同时拿着同一张旧照片插队。你要确定站哪，得"路过" A 和 B 修正位置。难点不是"要问两个人"，而是 A 和 B 的答复会互相改变——A 的位置因 B 而变，B 的位置也因 A 而变，你问的是"流动的答案"。TP2 的要求：先问 A 后问 B，和先问 B 后问 A，最终站位必须一模一样。

💥 翻车现场：裁决尺子量的东西在两条问法里不一样

队伍 v0 有 7 人。A 插"第 1 人后"、B 插"第 2 人后"、你也插"第 2 人后"（和 B 同点，平局！）：

问法一（先问 A，再问"被 A 修正后的 B"）：
  ① 路过 A：A 在你前面(1<2) → 你变"第 3 后"
  ② B 也被 A 修正：A 插在 B 前面 → B 变"第 3 后"
  ③ 平局裁决发生在"第 3 后 vs 第 3 后"之间  ← 尺子量的是 3 和 3

问法二（先问 B，再问"被 B 修正后的 A"）：
  ① 路过 B：你俩同报"第 2 后" → 平局裁决发生在"2 vs 2"  ← 尺子量的是 2 和 2
  ② 裁决完你变"第 3 后"，再路过 A（A 不受 B 影响）+1 → "第 4 后"

两种问法里裁决发生的时机不同、量到的数字也不同。历史上真实发表的函数里，平局规则有"按位置数字定""按到达先后定"——只要裁决规则跟"量到的数字"沾边，两种问法就可能给出相反裁决：一种里你排 B 前，另一种里你排 B 后。两台服务器各用一种问法 → 同一份操作合并出两个队伍 → 永不收敛。

1.4 不可满足定理与两条出路

📄 文献硬结论（"TP2 是死穴"的准确出处）
  • 纯插入操作集 + 一致全序平局（如 clientID）→ 存在同时满足 TP1+TP2 的函数（可手工推演验证两条路径同结果）。
  • 一旦加入删除：Randolph / Boucheneb / Imine（2013，控制器合成穷举）证明——在 Ins(pos,str)/Del(pos) 经典签名下，不存在同时满足 TP1 和 TP2 的变换函数。要满足 TP2 必须给操作加额外参数（如 adOPTed 的时间戳方案）。
  • 所以"死穴"不是"没人找到"，而是"被证明了不存在"。
出路代表做法
架构绕开（业界全部选它）Jupiter 1995 → Wave → Google Docs中央服务器定序，TP2 场景根本不出现，只需满足 TP1（第 2 幕）
加参数硬解adOPTed、TTF操作带时间戳/全序化信息满足 TP2，但实现复杂、代价高，未成为主流

第 2 幕 · Jupiter：用服务器定序绕开死穴 Xerox PARC 1995

2.1 星型拓扑与影子副本

        Alice ───┐
        Bob ────┼──→ 服务器 S（唯一权威副本 + 全局总序）
        Carol ──┘

关键架构事实：服务器与每个客户端之间跑一条独立的"两方协议"。n 个客户端 = n 条互不知晓的链路，每条链路各维护一个"影子副本"（doppelganger）。服务器存的是（全局操作序列 + 每个客户端的进度指针）。

2.2 二维状态空间格子图

对每条链路定义坐标系：横轴 = 该客户端本地已发生的操作数，纵轴 = 已收到的服务器广播数。每个格子 (i,j) = 一种文档状态；"斜走一格" = 做一次变换。完整格子图见第 1 幕的菱形图——那就是 Jupiter 链路的坐标系。

2.3 三客户端完整推演（可逐行复算）

初始：S、Alice、Bob、Carol 都持有 "Hello"
1. Alice 打 " World" → o_a = Ins(5, " World")
   Alice 本地立即生效 → "Hello World"，同时发给 S

2. Bob 并发打 "!" → o_b = Ins(5, "!")        # Bob 还没收到 o_a 的广播
   Bob 本地 → "Hello!"

3. S 收到 o_a：S 当前是 "Hello"（还没见过 o_b）→ 无需变换直接应用
   → "Hello World"，o_a 进全局序列第 1 位

4. S 收到 o_b：S 当前已含 o_a，而 o_b 基于 "Hello" 生成
   → S 亲自计算 T(o_b, o_a) = Ins(11, "!")    # 位置 5 跳过 " World" 的 6 字符
   → 应用得 "Hello World!"，变换版 o_b 进全局序列第 2 位

5. S 按每条链路定制广播：
   → Alice 收 T(o_b, o_a)=Ins(11,"!")，本地已是 "Hello World"，直接应用 ✓
   → Bob  收 S 替他算好的 T(o_a, o_b)=Ins(11," World")，应用于 "Hello!" ✓
   → Carol 收 [Ins(5," World"), Ins(11,"!")] 依序应用 ✓

四方全部收敛于 "Hello World!"。
服务器对每条链路独立计算"该客户端能听懂的版本"——这就是实验台实验 2 的引擎。

2.4 "绕开 TP2"的准确含义

🔧 不是"满足"，而是"不适用"

TP2 出现的前提是"没有中央定序、三个并发操作被不同副本以不同顺序两两互穿"。Jupiter 星型架构下：① 所有并发操作必经服务器钉进唯一全局序列；② 任何操作相对其他并发操作的"变换路径"被服务器的定序唯一固定——不存在"先穿 o1 还是先穿 o2"的选择；③ 每条链路只剩两方菱形，TP1 就够了。所以 Google Docs、Wave、ShareDB、ot.js 全部采用中央服务器——不是不知道 TP2，而是知道被证明不可满足之后，全部选择绕路。

第 3 幕 · Wave：XML 树、单批在途与联邦 Google 2009-2010 / Apache Wave

3.1 XML item 模型：统一坐标系

Wave 白皮书（wave-protocol 开源仓 whitepapers/operational-transform）的文档模型：每个字符、每个开始标签、每个结束标签都是 item（项），item 之间的间隙是 position：

"Hello <b>W</b>orld" 看成 item 序列：
[ H ][ e ][ l ][ l ][ o ][ <b> ][ W ][ </b> ][ o ][ r ][ l ][ d ]

操作词汇（十来个小操作通吃全部富文本）：
Retain(n) / InsertCharacters(s) / InsertElement(tag) / DeleteItem /
SetAttributes / annotations 更新（给字符区间贴属性：加粗、颜色、链接）
🔧 统一之后不是"解析不同结构写变换函数"，恰恰相反——几乎不用分叉了

所有"占位置的东西"都是 item：插入一个 <b> 和插入一个字符 'x' 对变换函数是同一个操作 Ins(pos, item)，一套位置平移规则通吃。真正分叉的只有操作类型这一维：① 位置类（Ins/Del item）→ 平移规则；② 属性类（setAttributes/annotations 的 map 更新）→ 不占位置，用 LWW 或按 key 合并。两套规则正交、互不干扰。设计精髓：把"无限种内容结构"压平成"一种位置坐标系 + 一种属性 map"，变换函数只需覆盖两个正交的小类型系统。相对纯文本的三大加持：结构化文档（回复树/gadget/图片）、回放（文档=操作历史的折叠，可逐步重演）、机器人以同一操作协议对等参与编辑。

3.2 单批在途：不需要锁的状态机

单批在途（one outstanding request）状态机
客户端同一时刻只有一批未确认操作在路上；后续本地操作在 pending 队列排队（本地视图零延迟）
首批直发后续排队ack 推动下一批
🔧 为什么不需要锁：run-to-completion 语义

判断"是否在途 + 设置标志 + 入队"发生在同一个事件处理步里——单线程事件循环（JS 天然单线程；服务器端 actor 模型串行化）保证这段逻辑中间不会被另一个本地编辑穿插。这就是 TCP 停等协议（stop-and-wait，窗口=1）的思路：靠协议状态机保证"只有一条在途"，而不是靠互斥锁。

两个坑：① 单线程 ≠ 永远安全——事件处理步里若有 await，"检查标志"和"设置标志"之间会让出线程，竞态回来；规则：状态变更必须在不含 await 的同步代码段内完成。② 多线程后端（Java/Go）要么加锁/CAS，要么把所有请求序列化进一个 actor 的 mailbox——后者本质是"用消息队列人造一条逻辑单线程"，与事件循环同源。防竞态的不是"标志"本身，而是"标志的读-改-写不可分割"；单线程事件循环、actor mailbox、锁是达成它的三种手段。

代价：高延迟链路每批一个 RTT，吞吐低 → 实现用批量聚合（一次 ack 确认一整批）摊薄，但"未确认批次 ≤ 1"的协议性质不变。

3.3 联邦 ≠ 多权威

联邦协议：不同管理域的服务器互相连通交换数据的协议（类比 email：Gmail 用户能给 QQ 邮箱发信靠 SMTP 联邦）。Wave 联邦基于 XMPP 扩展（Google Wave Federation Protocol，2010），解决"组织间互通"，不解决正确性问题。

🔧 关键区分：持副本 ≠ 持权威
权威服务器 (authoritative)   ← 只有一台（通常是创建该 wavelet 的域）
  · 持有定序权：所有操作必须路由到这里定序；可写，产出官方操作历史

订阅服务器 (其他联邦域)      ← 可以有很多台
  · 持有副本 = 缓存（本域低延迟访问）+ 只读中继
  · 无定序权 → 不产生"第二种顺序" → TP2 场景不出现

类比 git：一个仓库可以有无数 mirror，但 upstream 只有一个，镜像只拉不改。
"唯一权威"是对每个 wavelet 说的——联邦的价值 = 权威可因文档而异地分布，
但任一时刻任一文档仍只有一个。

权威挂了怎么办？该 wavelet 变只读，直到权威恢复或迁移——没有"接管定序"的降级路径。这就是 OT 死穴之一中心化依赖的现场。

💥 三个概念拆干净（常见混淆）

① 传输乱序= 网络问题，ack/序号/重传去重就能解决（TCP 层面的事），与 TP2 无关；② TP2 = 变换函数的数学性质问题，在"有中央服务器定序"的架构下根本不出现；③ Wave 联邦的正确性 = 每个 wavelet 有唯一权威服务器定序，联邦只是跨域传播操作历史，星型定序架构一点没变——每条链路依旧两方协议，只需 TP1（TP1 可满足）。

📄 "Wave 没有理论问题吧？"——边界要划准
层面状态
理论架构干净：单权威定序 + 链路式两方同步，只需 TP1，TP1 可满足
工程实现加固过：海量随机/模糊测试轰炸变换函数，全开源供检验（wave-protocol 仓库是生产级 OT 最详细的公开参考）
数学兜底没有：模糊测试通过 ≠ 数学证明。对比：CRDT 的收敛性有定理（操作合并满足交换律/结合律/幂等 → 半格收敛）。这正是 2015 后学界全面转向 CRDT 的原因

Wave 产品 2012 年关停（产品失败，与正确性无关）；技术遗产活下来：wave-protocol 开源码 + ShareDB。

🎪 一句话定位

Wave 是一艘沉船，ShareDB 是从船上拆下来的发动机。作者 Joseph Gentle 是前 Wave 团队成员：拿走 Wave 的引擎（OT 服务器 + 客户端订阅协议），扔掉产品包袱（blip/gadget/机器人/联邦），做成通用 Node.js 实时协作后端框架。

第 4 幕 · OT 四死穴与 400 万次变换 平方代价的准确含义

4.1 四死穴总表

死穴表现大白话
① 中心化依赖权威服务器挂了系统只读（第 3 幕）队伍的登记处关门，谁也别想进人
② 实现脆弱10 个已发表变换函数大半被模型检查揪出反例（第 1 幕）手写平局规则=手工雕花，雕花必有毛刺
③ 离线合并平方代价2000×2000 = 400 万次变换调用（本幕）每个人都要挨个问每个人
④ 有状态服务器服务器要维护每客户端进度指针 + 全局序列登记处要记住每个人问到第几条了

4.2 插队比喻：逐格穿越 vs COT vs CRDT

🎪 场景设定

文档 = 队伍，位置 = "前面有几个人"。官方照片 v0（7 人）。Alice 让 2000 个朋友插进自己那条队伍，每个朋友的指示是"从前面数插在第 K 人后面"（数字位置，基于照片 v0）。Bob 的朋友"你"也是这么说的。现在两条队伍要合成一条——Bob 朋友的指示全部失效，"第 5"已经不是原来那个第 5 了。

为什么必须挨个问 2000 人（乘法的来源）

你想一步算完："我前面一共多了 K 个人，5+K 完事" —— 不行！
因为 Alice 的 2000 个朋友插的位置各不相同：
  插在你前面的 → 才影响你（+1）   插在你后面的 → 与你无关（+0）
  （删除则 -1）
"到底几个在前几个在后"没有汇总公式，只能逐个判断
"你在前面吗？→ 影响我；你在后面吗？→ 不影响"

Bob 每个朋友把 Alice 的 2000 人挨个问一遍
→ 2000 个朋友 × 2000 次询问 = 400 万次问答 = O(N×M)

注意：路径是确定的（从队头问到队尾）——不是因为"路径未知"，
而是"判断影不影响我"没有批量公式。传统 OT 的操作只带位置，
不带"出生地"，收到的人只能逐个比对逐个变换。
🎪 传统 OT：挨个问

逐格穿越 → O(N×M)
每个 Bob 朋友逐个问 Alice 的 2000 人"你在前面吗"→ "第 5" 变 "第 7"。谁在前谁在后只能逐人判断——这就是 400 万。

🎪 COT：查对照表

上下文向量 → 一步跳
报名时多带一句"我看的是 v0 照片"（出生地标签）。负责人掏出对照表：v0 第 5 位 ⇄ v3 第 7 位，一步到位。

🎪 CRDT：根本不报数字

锚定 id → 无需换算
"我站王二麻子后面"——队伍怎么变都找得到位置。没有位置可换算，"变换"这个步骤整个消失，合并退化为认人+排序。

三种方案解决同一个问题："基于旧照片说的数字，怎么在当前队伍里兑现"
挨个问（400万次）→ 查表（一步，但表很贵）→ 不用数字（无问可问）。CRDT 赢在换了问题，而不是赢了换算。

4.3 COT 的代价（为什么它停留在学术界）

代价说明
空间 ①每个操作携带 O(客户端数) 的上下文向量，操作包变大
空间 ②服务器要维护"所有中间状态的操作列表"（状态空间格）才能造对照表
复杂度实现/调试上台阶，而 Jupiter 星型已经"够好"

生产系统的实际选择：在线实时 → Jupiter 式单线够用；离线合并 → 与其上 COT，不如直接换 CRDT。CRDT 本质是把 COT 思路推到极限：操作自带全部因果信息（origin id + Lamport），连"变换"都不要了，合并退化为按 ID 排序。另有 COT/LBT 用上下文向量把 O(N×M) 降到近线性（状态空间跳跃），同属"跳步"思路。

第 5 幕 · CRDT：从"发座位号"到"认人" WOOT 2006 → Loro 1.0

5.1 裁判 vs 邮差（"没有中央服务器"的准确含义）

OT 的服务器CRDT 的服务器
角色裁判：定序、裁决平局、亲自做变换邮差：转发、持久化、离线补发
正确性依赖是（没有定序就没有收敛保证）否（任何投递顺序都能收敛）
可替换性不可替换可换任何中继、甚至 P2P

"CRDT 没有中央服务器"的准确含义是没有中央权威，不是没有后端基础设施——生产系统当然有后端，但它只干物流，不参与正确性计算。实验台实验 3 里那个"投递队列洗牌机"就是邮差的全部戏份。

5.2 不变 ID 三件套 + Lamport 时钟

ID 唯一性由本地三件套保证，不需要任何服务器参与：
1. clientID：会话启动时本地随机生成（Yjs 32bit 随机；Automerge 用更大随机空间）
2. seq：本地单调递增计数器（每敲一个字符 +1）
3. (clientID, seq) 全局唯一 —— 每个客户端的每个 seq 只被自己使用
   碰撞概率：32bit≈42.9亿，100 万客户端按生日悖论约 1 次碰撞
   → Yjs 实际带冲突检测（发现重复就重新随机）

辅助结构：
- Lamport 时钟：counter = max(自己的, 见过的所有 counter) + 1
  → 保证因果先于 ⇒ 时钟更小（保因果序），给 RGA 提供"全序比较键"
- 版本向量：每副本记 [从每个 client 见过多少 op]（见 5.3）
🎪 为什么不能"直接按 seq 排序"：bob 的接龙

时间线：alice 打了 10 个字（seq 0..9）→ bob 加入，看见了 alice 的全部字符，接着她的末尾继续打。bob 的字 seq 从 0 重新计数——按 (clientID, seq) 排序，bob 的 (bob,0) 与 alice 的 (alice,0..9) 没有可比性，只能靠 clientID 平局 → bob 明明接在后面，排出来却可能整块跳到前面——因果错乱。

Lamport 时钟修的就是这个：bob 打第一个字前见过 alice counter=9 → bob 的 counter = max(0,9)+1 = 10 → bob 的字必然排在 alice 全部字符后面。✓

一句话：seq 只在一个客户端内部有意义；Lamport counter 把"我见过的全部历史"压缩成一个整数，使跨客户端的"谁更晚"可比较。定理：因果先于 ⇒ 时钟更小（反向不成立——时钟小的两个可能只是真并发，真并发时随便定序+clientID 平局，照样一致）。

注意：CRDT 里删除不参与排序竞争——删除只是给某个 id 打墓碑标记，作用在具体 id 上，不占位置。Lamport 时钟只服务并发插入的排序。CRDT 里根本不存在 OT 那种 IT(Ins,Del) 变换——这正是它砍掉变换函数的原因。

5.3 版本向量：因果的三本账

🎪 Lamport 时钟是"把历史压成一个数"，版本向量是"把历史完整记账"
副本 Alice 的账本：{alice: 12, bob: 8, carol: 5}
意思："我见过 alice 的 12 个操作、bob 的 8 个、carol 的 5 个"

用途① 差距计算（离线重连）：
  对方发来账本 {alice:12, bob:10, carol:5} 一对比
  → "我缺 bob 的 2 个操作" → 精确补发，不用全量对账
用途② 并发判定：
  两个操作互相不在对方账本里 → 真并发（排序/墓碑回收的判据）
用途③ 墓碑回收：
  所有副本的账本都 ≥ 删除操作 D 的账本快照
  → 世上不存在"没见过 D 的副本" → D 删的字符可以物理剪掉（5.8）

5.4 三条主线、七版演化

CRDT 演化全景：不是七个并列方案，是三条路线的接力
位置型谱系引用型谱系存储层革命（Loro 1.0 = Fugue 语义 + Eg-walker 存储）

5.5 WOOT 的"集成算法" / Logoot 膨胀机理

🔧 术语翻译：集成算法 = "收快递上架"的逻辑

集成算法（integration algorithm）＝"一个乱序到达的字符块，如何找到它在本地文档列表中的正确位置"。各版本 CRDT 的差异大半就在这个"上架逻辑"上：

WOOT 的集成：字符 w 随身带"左邻 id + 右邻 id"双锚。
  上架时必须先确认左右邻居都已到货（没到就缓存等待、递归确保），
  然后扫"左邻和右邻之间"找位插入。
  → 递归依赖 + 缓存重试，又慢又难写 —— 这就是"WOOT 集成复杂"的确切含义。
Logoot 的集成：按座位号字典序二分查找，O(log n)，简单。
RGA 的集成：找到锚点 → 向右跳过"所有锚定在同一位置的、ID 比我小的并发兄弟"
  → 插在它们后面（实验台实验 4 的 integrate() 就是它的简化版）。

Logoot 的座位号与膨胀死穴

🔧 [10] < [10,3] < [11] 可以理解成分数 10 < 10.3 < 11（字典序 = 无限精度小数）

常见误解："顺序打字就是 10、11、12 一直往上涨"。不成立——座位号必须无限可分：任意两个座位号之间要永远能再发一个。[10] 和 [11] 之间只有 [10,x]，没有整数可用了。于是顺序打字的死穴真实机理是元组深度增长：

打第1个字 → 座位号 [10]
打第2个（接着打）→ [10] 与 [11] 之间 → 只能发 [10, 5]     ← 元组深度 +1
打第3个 → [10,5] 与 [11] 之间 → 只能发 [10,5,7]          ← 又 +1
顺序打 100 个字 → 最深座位号约 100 层 → 元数据随文本长度线性膨胀
→ 讽刺的是：越普通的场景（顺着打字）越惩罚位置型；
  并发插入反而不膨胀（[10,11) 开区间里 [10,x] 有无穷多个可发）。
LSEQ 的贡献 = 优化发号策略（分层选中点/边界），把深度压到对数级。
Treedoc 同源问题：座位号 = 从根到叶的 0/1 路径，树单边倾斜 → 路径变长。
🎪 位置型的共同宿命

WOOT 发相对坐标、Treedoc 发树路径、Logoot 发分数座位号、LSEQ 优化发号策略——四个都在"发号"这个思路里打转，而发号思路天然被"连续打字"惩罚。引用型干脆换思路：不发号，发关系（锚定前一个字符的 id），词内顺序被链结构物理锁定，交错和膨胀一起消失——这就是 RGA→Yjs→Fugue 赢下主流的原因。

5.6 RGA 保序 vs Logoot 交错（原理图解）

场景：空文档，Alice 与 Bob 并发在同一个锚点，各打一个词：Alice 打 "hello"，Bob 打 "world"。

同一场景两种结局：位置型穿插 vs 引用型整链连续
Logoot：每个字符独立生成座位号 → 两串数字天然穿插 → 字符跟着穿插（交错异常）；RGA：字符手拉手成链 → 链内顺序被结构锁定 → 链间 ID 一次裁决
Alice 的链：每字锚定前一字 idBob 的链：独立成链Yjs 的 origin/originRight 双锚是 RGA 单锚的扩展（锚点被删也不歧义）；Fugue 把"何时需要双锚"缩到最小

5.7 元数据四代瘦身：Yjs → Fugue → Eg-walker

起点：RGA 的账单（为什么要瘦身）

RGA 每个字符一个独立对象：{id, 锚点id, 字符, 墓碑标记, ...}
JavaScript 里一个对象的固定开销约 50~100 字节
→ 存一个 'h'，元数据比正文大几十倍
→ 一本书 100 万字符 = 内存几百 MB（"元数据是文本的 3~16 倍"的来源）

第一、二刀：Yjs —— 把零售改成批发，再把批发打包

🎪 分块（block）+ 列式编码

分块：你连续敲 50 个字不是 50 个独立决定，而是一个连续动作。Yjs 把"同一客户端连续敲的字"合成一个块：原来 50 份 {id,锚点,字符}，现在一个块 {起始id, 锚点id, "整段 50 字"}——50 个字共享 1 份元数据，顺序打字时压缩比极高。列式二进制编码：序列化时把所有块的"ID 列、锚点列、内容列"分开打包，ID 用增量差分 → 传输大小压到文本的 3~5 倍（同数据库列式存储原理：同列数据相似，压缩率高）。生产最广的 CRDT。

第三刀：Fugue —— 平时只绑一根绳

🎪 Yjs 人人左右双保险，Fugue 平时单手抓杆

YATA/Yjs 每块带左右双锚（origin/originRight）——相当于每个人随身绑两根绳到左右邻居，锚点被删光也不歧义，但 99% 的时间右绳白带。Fugue 的洞察：只有"并发抢位置"那一刻才需要第二根绳。平时顺着前一节点继续写 → 只记左锚；检测到并发分叉 → 才补记另一侧。元数据压到理论下限（论文证明），且不产生交错异常。Loro 1.0 用的就是 Fugue 语义。

第四刀：Eg-walker —— 掀桌子，不维护文件夹了

🎪 老方案把剧本排成家谱挂满墙，Eg-walker 把剧本按时间摞成一摞

前面所有版本都在优化"内存里那棵树怎么组织才又对又省"。但无论怎么优化，打开文档都要把整棵树在内存里建出来。Eg-walker 的洞察：你要的从来不是"树"，你要的是"当前的文本"，树只是算出文本的手段。做法：一切还原成按时间堆叠的事件流水账（append-only，列式存储："谁、在哪个位点、插/删了什么"，按 (clientID, seq) 编址），内存里只维护轻量索引（各客户端连续段位置表）。要看文本 → 按索引翻流水账算出来，不建树。

收益：内存低一个数量级（≈文本 1~2 倍）、加载快几个数量级（根本不用"挂墙"）。墓碑顺带受益：流水账里"全体副本确认过的删除段"可整段折叠。代价：渲染文本要付一次带索引的 walk。

🔧 Eg-walker 精确心智模型（给后端的类比）

常见误解修正：不是"把权威数据放库里"（CRDT 没有权威，是每个副本都这样存）；也不是"每步修改都去历史翻"（写和读是两条路）。它就是 Event Sourcing + CQRS：

传统 CRDT ≈ CRUD：内存里维护"当前状态"（那棵树），改状态
Eg-walker  ≈ 事件溯源：不存状态，存事件日志
            写 = append 事件（O(1)，跟写日志一样便宜）
            读 = 需要"当前文本"这个视图时，临时 walk 账本算出来（投影）
            连续段索引 = 物化视图/快照，防止每次全量重放
            版本向量 = 快速判断"见过什么"
真要走长路的只有罕见情况：离线三天的副本回来往文档中间塞远古插入。
日常 99% 的事件落在序列尾部附近，走快路径。

5.8 mark-sweep GC：墓碑什么时候能扫

为什么墓碑必须留：被删的字符可能正是别人插入的锚点。
  你删 'l'，离线副本上有人正基于这个 'l' 插了 "!"——物理删掉 'l'，
  迟到的 "!" 锚点悬空，无法定位。（实验台实验 3 勾"显示墓碑"可见依赖）

回收条件（mark-sweep 式）：
  1. mark  ：每个副本定期广播自己的版本向量
  2. 求交 ：算出"所有副本都已收编的公共因果前缀"（安全下界）
  3. sweep：删除操作若落在安全下界内 → 它删的字符的墓碑可物理剪枝
     理由：世上已不存在"还没见过这条删除"的副本，
           未来的插入必然锚定在活字符上，不会再引用这块墓碑

风险：永久离线的副本会把安全下界卡死，阻塞全体回收
     （需要 epoch/超时机制宣告弃号）。
实现现状：Yjs 基本不自动 GC（内存换简单）；Automerge 有
         版本向量 + bloom filter 的回收；Loro 支持 GC。
视频说的 mark-sweep 是学术方案/部分实现的做法，非所有库默认开。

第 6 幕 · 同步引擎：第三条路线 Figma / 本地优先 / Replicache 家族

OT 和 CRDT 之外还有一条务实路线：不追求文本级"意图保持"，而是用"属性粒度 + 服务器定序 + 简单合并规则"把工程复杂度压到最低——Figma 是代表；再加上 Ink & Switch 提出的"本地优先软件"理想，构成 2020 年代的第三极。

Figma：属性级 LWW + 服务器定序

Figma 公开博客的方案（与 CRDT 划清界限）：对象树 + 属性级 LWW（每个属性一个小格子，谁新听谁的）+ 服务器定序。并发改同一个属性本来就只能留一个 → LWW 是诚实投降；并发改不同属性互不影响 → 天然合并。工程上比文本 CRDT 简单一个量级，代价是放弃了文本级意图保持（Figma 场景里不存在"两人同时改一个文本段落"的高频需求）。

本地优先（Local-first）七条理想

Ink & Switch 宣言：数据在本地、快如本地应用；离线可用；多端同步；协作；长久可用（不随厂商死）；隐私与默认安全；用户拥有最终控制权。技术组合 = 本地 DB + 服务器日志 + 回滚重放：客户端把操作写成日志，服务器只做日志的中继与持久化，冲突由客户端数据模型（CRDT 或简单合并）解决。

第 7 幕 · AI 并发编辑四实践 从 apply patch failed 到流式可打断

痛点一句话：AI 写东西和你改东西同时发生。传统方案让 AI 对着几分钟前的旧快照生成整段补丁，写完回来发现你已经改了那个区域 → apply patch failed。更深一层：即使技术上收敛了，还有"意图漂移"——AI 和你各自对文档的理解漂向不同方向（实验台实验 4 复现了 "The ecat sleeps."）。四个实践是四种解法：

🎪 ① Yjs Agent：给 AI 发工牌

不是让 AI 当"绕过所有人直接改文件的后台进程"，而是给 AI 发一个工牌：文档里的一个虚拟协作者账号，每个字都通过 CRDT 协议正常进文档。你打你的、AI 打 AI 的，天然并发安全——AI 写到一半你在同一屏改字，谁也不覆盖谁。解决"并发安全"；"想法打架"靠下面两个。

🎪 ② 主管 + 写手：包工头分地盘

多个 AI 全文乱写会互相覆盖、风格漂移。解法：一个 AI 当包工头，只干一件事——拆任务分地盘："你写第 1 节，你写第 2 节，谁也别越界。"写手各占地盘 → 空间上根本不并发 → 冲突在分地盘那一刻消失。这不是高深算法，是用工作流设计回避并发问题——与悲观思路同源：与其让十个线程抢一把锁，不如一开始就别让它们碰同一份资源。

🎪 ③ 分块编辑：别憋大招，小批交作业

反面模式：AI 闷头写 3 分钟甩一整篇——方向全错则 3 分钟白等。分块模式：Agent 循环里每写几十/几百字 apply 一次：你看到"打字机效果"；你随时喊停 → 已交作业生效、未写的取消。工程上就是把"末尾一次大 patch"拆成"循环里的连续小 delta"。（与 Wave 单批在途同源：小批化让打断成为可能）

🎪 ④ Zed Delta：带座位号的事件流

传统模式：AI 输出 diff/patch——"把第 10~20 行换成……"是对旧快照说的数字位置，你一改就打不上。Zed 2025 的做法：文档本身是字符级 CRDT，AI 每步编辑直接生成为文档 delta——一串带座位号（锚定 id）的编辑事件流进文档。流式（边生成边应用）、可打断（打断是原生能力：收到信号，后续 delta 不再应用，已应用的自然保留）、不冲突（座位号认人不认数字位置）。DeltaDB＝这些 delta 流的可查询数据库。以前给的是"第 3 排左边全换红砖"的施工图（队伍一动就找不着第 3 排），现在给的是"跟在王二麻子后面盖红砖"的指令条。

3 分钟版（面试官说"展开讲讲"时）

🎤 叙事骨架：问题 → 尝试 → 翻车 → 解法 → 遗留
  1. 锁为什么不够：悲观锁断网悬死、乐观锁 409 让人重做、LWW 输家无声丢尸——它们管的是准入，协作要的是合并。（30 秒）

  3. Jupiter 1995 / Wave：星型服务器定序，把 TP2 的适用场景架构性消除，只需 TP1；代价是中心化依赖 + 有状态服务器 + 离线合并 O(N×M) 平方代价。

追问预判（按被追问概率排序）

追问要点回答
"TP2 为什么不可满足？"三方并发时变换路径无关性要求"裁决平局的尺子在任何问答顺序下稳定"，而尺子量的位置数字本身在问答中被改写；Randolph 等人 2013 用控制器合成穷举证明：insert/delete 签名下不存在这样的尺子（纯插入+全序平局可以，加删除就不行）。
"既然 OT 有死穴为什么 Google Docs 还在用？"死穴是"无中心定序下的理论不可满足"，而星型架构让该场景不出现；生产正确性 = 架构绕开 + 海量模糊测试。代价明确：中心化依赖、权威挂了只读、离线合并平方代价。
"CRDT 没有 ID 服务器怎么保证不重？"本地三件套：随机 clientID + 本地单调 seq + (clientID,seq) 全局唯一；32bit 有生日悖论碰撞概率所以带冲突检测。服务器只当邮差——正确性不依赖它，这是与 OT 的分水岭。
"RGA 为什么不交错而 Logoot 会？"Logoot 每字符独立采样座位号，两串数字天然穿插；RGA 每字符锚定前一字 id 成链，链内顺序被结构锁定，并发链间用 (Lamport, clientID) 一次裁决整链胜负。
"CRDT 内存为什么大、怎么解决？"每字符养对象+墓碑 → 3~16 倍文本。四代瘦身：Yjs 分块+列式编码（3~5 倍）→ Fugue 平时单锚（理论下限）→ Eg-walker 不养树只记事件账本（Event Sourcing，内存低一个数量级、加载快几个数量级）。Loro 1.0 = Fugue 语义 + Eg-walker 存储。
"墓碑什么时候能删？"删除的字符可能是别人插入的锚点，不能立刻物理删；mark-sweep：所有副本的版本向量都确认见过该删除（安全下界）后才剪枝；离线副本会卡住下界，需要 epoch 机制。Yjs 基本不自动 GC，Automerge/Loro 有。
"AI 同时改文档怎么处理？"四实践：AI 当虚拟协作者进 CRDT 文档（Yjs Agent）；多 AI 用包工头分地盘回避并发；分块流式输出支持打断；Zed 把 AI 编辑做成带座位号的 delta 流。核心认识：并发安全解决了"覆盖"，解决不了"意图漂移"——那要靠工作流设计。
"飞书/腾讯文档用什么？"诚实版：飞书未公开表格内核；官方开放平台文档 API 明示 offset 自动修正（OT 家族行为特征），第三方拆解为"每文档串行处理+OT"（二手）。表格类参考架构：单元格内容细粒度合并 + 结构变更服务器定序 + 属性 LWW。展示"从官方 API 行为反推架构"的推理能力，不编造。
"LWW 和乐观锁什么区别？"岗位不同：乐观锁是门卫（管准入，输家重试）；LWW 是合并员（管内容，赢家通吃输家丢尸）。LWW 的家在 CRDT 工具箱——管不占位置的标量字段。
