## Q1 · 第3轮 · 初始

rerank 把部分 relevant doc 挤到 10 名外的指纹，为啥 record 不是更应该把那些相关的排到前面去嘛？怎么反而把相关的排到后面去了。哦，我懂了，这就是 qrel 的构建偏差嘛。
因为我们构建的 ground truth 以及 context，都是根据 native 模式召回生成的，它的位置也是那样的。所以我们用 native 去召回的话，召回率肯定是 100%，因为我们的结果就是从 native 里面拿出来的嘛。
而开启 rerank 之后，我们对 native 召回的信息进行了重排，导致顺序和之前用 native 召回时不一致，从而导致了 NDCG 的降低。

我们的 Graph 采用了一种检索策略。该策略在注册器中进行了注册（即存放在哈希表中），可以随时注册并从中获取对应的实现。这个注册器配合了策略模式，使得策略可以随时切换，通过注册器即可取得对应的检索模式。
具体的流程如下：
1. 提取锚点：首先由大模型提取锚点，构造实体和描述的 Embedding。
2. 向量匹配：使用实体在 PG 中进行精确匹配，并在 Milvus 中进行向量相似性匹配。
3. 多跳查询：匹配后回到 PG 权威源进行多跳查询。多跳查询利用了前后的双索引，响应是毫秒级别的。
4. 信息回约：将对应的信息回约到 Trunk 中。
5. 大模型重排：通过大模型进行一次重排，保留相关信息，去掉不相关信息。
6. 融合：最终通过 RRF 融合以及 BGE Reranker 精排，生成最终答案。
我们的优势主要体现在架构和性能上：
1. 检索与生成分离：
检索可以缓存，并且可以独立扩缩容，还可以装配成 Agent 多平台工具。
2. 性能优势：
(a) 查询响应：PostgreSQL 具有单跳毫秒级别的优势。虽然多跳查询可能略微比图便利慢一些，但整体优势是在的。
(b) 匹配速率：我们使用 Milvus 实体向量匹配大概是毫秒级别，而 LightRAG 使用 PG vector 是秒级别。在这种情况下，我们的速率大概比他们快四五倍。
(c) 对于模型锚点实体抽取以及最终答案生成，都有 token 长度限制

我们选择了中科大的 CRUD 测评集，它是一个 query 对应一个 doc。在测试场景下，我们 graph 的 hit@1 的值大约在 0.88 左右，这正说明了我们 graph 的优势以及它的容错率。

在这个过程中，我们的 graph 要经过三个环节：
第一环：锚点提取的大模型，锚点提取准不准？
第二环：关系匹配真不真？因为大模型抽取的关系本身有噪声。
第三环：重排准吗？因为这也是大模型进行打分，会有判断误差。
这三级误差相乘，最终大概算出来有 12% 的 query 会压错。
同时，在 CRUD 测评集上，我们的 graph 平均只返回一个 chunk。因为一个问题可能只提取出了一个关键词去多跳，查不出相关的 chunk，相当于每次只去抽一个。而 Naive 方法是分散的，它会返回 10 个。就算有 9 个不对，只要压中一个，就可以提高召回率。
所以在这种情况下，我们的召回率能达到 0.88，实际效果是非常不错的。

## ⚠️ 纠偏一（最危险）：“匹配速率比他们快四五倍” —— 这个数字不能说

你的原话：“我们使用 Milvus 实体向量匹配大概是毫秒级别，而 LightRAG 使用 PG vector 是秒级别。在这种情况下，我们的速率大概比他们快四五倍。”

**问题**：我们对 LightRAG **从未做过内部分环节插桩**。43.3s 是端到端 p50，它的内部构成（向量检索占多少、keyword 抽取占多少、生成占多少）只有排除法推断（“生成是大头”），“LightRAG 向量检索是秒级”本身都是推断不是实测。“快四五倍”是**在推断值上又乘出来的数字**——两级虚構。面试官一句“你怎么知道它的 PGVector 是秒级？”就击穿。

**能说的版本**：
- 实测级：“我们的 Milvus 实体向量匹配毫秒级、PG 一跳 SQL 毫秒级——这是我们自己的链路数据”
- 推断级（必须带标注）：“LightRAG 端到端 43s，剔除同模型的生成步后，残余的检索+编排估算在 5-10s 量级 vs 我们 1.8s，残余架构差距约 5-10×——**估算，未插桩**”
- 架构级（最稳）：“向量引擎选型上 Milvus 专用 ANN 引擎 vs PGVector 扩展，在纯检索延迟上业界公认有量级差，但这不是我们 43s vs 1.8s 的主因——主因是 LLM 编排次数和生成步”

**记住排序**：23.5×（实测但口径为检索 vs 端到端）> 5-10×（剔除生成的估算）> “向量匹配快 4-5×”（❌ 不存在，删掉）。

## ⚠️ 纠偏二（机制错位）：“一个问题只提取出一个关键词去多跳，查不出相关 chunk”

这句把因果链的最后一环说错了。正确的因果链：

```
锚点提取(通常1-5个实体,不是1个)
  → 61% 精确匹配率,命中锚点变少        ← 环1
  → 一跳扩展出的关系本来就少:0.6 条/entity ← ★真正的主因(关系密度)
  → LLM 重排过滤后常只剩 1 条关系
  → 1 条关系 = 1 个 source_chunk_id = 1 个 chunk
```

“只提取出一个关键词”不是实测事实（锚点通常提出多个），**avg 1 chunk 的直接原因是关系稀疏**——这正是 0.6 条/entity 这个数字存在于简历上的意义。说错这一环，面试官追问“你锚点平均提几个？”你答不上 1，整条归因链就断了。A/B 三方案证伪（降阈值/二跳/LIKE 全无效、锚点匹配率从 61% 提升后 hit 不动）恰恰证明“不是锚点不够，是关系不够”。

|---------|------|----------|
| qrel 构建偏差的整个推理（native 自证 → rerank 挪位 → nDCG 降） | ✅ 到位 | 补一个细节：native 自测 Recall 是 **0.988 不是 100%**——top_k 截断会切掉部分“自己召回的”标注 doc，循环论证也做不到满分，这个细节反而证明你懂 top_k 截断效应 |
| 策略注册器（哈希表 + 策略模式，随时切换） | ✅ 正确 | `@register_strategy` 装饰器 + `_REGISTRY` 字典，`get_strategy(retrieval_mode, ctx)` 按名取——开闭原则：加策略不改 `milvus_client.query` 一行代码 |
| 锚点→PG 精确匹配 + Milvus 向量匹配 | ✅ 正确 | 路A还有 LIKE fallback（61% 匹配率的应对，保留至今） |
| “多跳查询…双索引毫秒级” | ⚠️ 半对 | **默认一跳**（`GRAPH_HOP=1`，config.py:138）。面试别说“多跳”当默认——A/B 实测二跳在本数据集**负收益**（hit 微升 89% 但噪声多 + 延迟 94s）。正确说法：“默认一跳，跳数配置化；二跳试过、数据证明一跳够用” |
| “信息回约到 Trunk” | ✅ 机制对，术语修 | chunk **回链**：路径 B（relation.source_chunk_id 直查，0.9）为主 + 路径 A（entity.source_chunk_ids，0.75）兜底 |
| 三环误差相乘 → 12% 押错 | ✅ 正确 | 精确表述：12% 是**实测值**（1−0.880），三环是**归因模型**；其中环 1 有独立实测（锚点匹配率 61%，20q 分析） |
| “hit@1 大约 0.88” | ⚠️ 术语 | 口径是 **Recall@10 = 0.880（300 query 全量 BEIR）**。数值上像 hit@1 是因为单 chunk 押注（返回 1 个，命中必在第 1 位）——这本身是指纹分析的一环，但口径名要报对 |
| “0.88 说明优势以及容错率” | ⚠️ 两个词都要修 | ①“优势”：0.88 **低于** native 的 1.0，单说优势会被怼。正确表述：“88% 押中时拿到的是路径 B 高置信证据（关系直查 + LLM 重排双重把关），窄而准；短板是召回，兜底补到 100%”。②“容错”用反了：单 chunk 押注恰恰是**零容错**（押错即零分），native 10 个才是分散容错，**兜底是给 graph 补容错** |
| native “9 个不对只要押中 1 个就提高召回” | ✅ 正确 | 这就是 1-to-1 qrel 下分散押注 vs 单次押注的统计差异 |
| “召回率 0.88 实际效果非常不错” | ⚠️ 补框架 | 必须带前提说：“在关系密度 0.6/entity 的稀疏数据 + 三环级联误差下仍有 88% 命中”——去掉前提的“非常不错”会被追问“native 100% 你 88% 怎么就不错” |
| 检索生成分离三点（缓存/扩缩/agent 工具） | ✅ 正确 | 补第四点：检索独立 → **L2 缓存才可能**（rag_tools.py:239-250，检索结果整体缓存复用） |
| “生成最终答案”在第 6 步 | ⚠️ 半对 | 链路终点是“返回 contexts 给 **agent**”，生成发生在 agent 层——这恰是检索生成分离主张的最后一环，别在自己嘴里把链路闭合回“生成答案” |
| “锚点提取和生成都受 token 限制” | ✅ 正确 | 补数字弹药：锚点 `max_tokens=300`（L381）、重排 `max_tokens=800`（L461）——**两次都是短输出**，这是与 LightRAG 长输出生成拉开延迟差的实质 |
