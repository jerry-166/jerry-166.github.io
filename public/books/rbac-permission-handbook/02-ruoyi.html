01

若依表结构全览 ★★★★★

若依权限体系的第一个关键认知：它没有独立的"权限表"，菜单和权限点是同一张 sys_menu 表。下面是真实表清单（以 RuoYi-Vue 为例）。

主体表（5 张）
sys_user 用户
sys_role 角色
sys_menu 菜单/目录/按钮/权限点（合一）
sys_dept 部门（树形，parent_id 自关联）
sys_post 岗位
中间表（4 张）
sys_user_role 用户-角色
sys_role_menu 角色-菜单/权限点
sys_role_dept 角色-自定义数据范围部门
sys_user_post 用户-岗位
数据权限扩展（若依无原生）
resource_owner（需自建，第一册的通用 ACL 表）
若依原生行级只用 data_scope 规则，不做实例级分享
图 2-1　若依权限相关表：主体 5 + 中间 4；没有独立权限表，权限点寄生在 sys_menu
表类型关键作用
sys_menu主体既存前端导航树（menu_type/path/component/icon），又存后端权限点（perms），是全册最关键的表
sys_role主体含 data_scope 字段（1全部/2自定义/3本部门/4本部门及以下/5仅本人），决定行级范围
sys_dept主体部门树，parent_id 自关联；业务表冗余 dept_id 用于行级过滤
sys_user_role中间用户-角色多对多
sys_role_menu中间角色-权限点多对多（字段权限复用后也走这张表）
sys_role_dept中间仅 data_scope=2（自定义）时用，挂该角色能看的部门
对比你最初的 8~9 张表

若依没有独立的 group（用户组），横向数据归属用"部门 dept"代替；也没有独立 permission 表，权限点并进 sys_menu。表少了，但 sys_menu 一身二任，理解它就理解了若依的功能权限。

02

sys_menu 的双重身份：UI 路由 + 后端鉴权 高频

同一张 sys_menu，两类字段分别服务两个完全不同的消费者：

身份一 · 服务前端 UI（导航/路由）
menu_name 显示名
menu_type 目录/菜单/按钮
path / component / icon / visible
前端用它生成左侧菜单树、路由表、按钮显隐
身份二 · 服务后端鉴权
perms 权限码，如 material:list:add
后端 @PreAuthorize("@ss.hasPermi('...')") 运行时与当前用户权限集合比对
图 2-2　sys_menu 一行记录，前端读它的路由字段、后端读它的 perms 字段，互不相干又共用一表
sys_menu 关键字段（一条"新增素材"按钮记录）
menu_id   = 1102
menu_name = '素材新增'
parent_id = 1100               -- 挂在"素材列表"菜单下
menu_type = 'F'                -- 按钮（Function）
perms     = 'material:list:add'   -- 后端鉴权只认这个
path/component/icon = NULL    -- 按钮没有路由，UI 字段为空
为什么字段权限也能复用这张表？

登录时聚合权限码的 SQL 不按 menu_type 过滤——只要角色勾了这条记录，它的 perms 就进权限集合。所以新增一条 menu_type='I'、perms='field:user:phone' 的记录，既不生成路由（不参与前端导航），又能让后端拿到字段权限码，零新表、零新链路（第 7 章详讲）。

03

菜单类型 M / C / F / I 与"目录"是什么

若依菜单管理里的类型常量，是面试常问的细节：

类型常量/含义是什么在页面上的表现
MTYPE_DIR='M'
Directory 目录		导航分组容器，点击只展开/收起，本身不跳转、没有页面左侧导航里"系统管理""素材中心"这种可展开的分组标题
CTYPE_MENU='C'
Menu 菜单页面		一个真实 Web 页面，有路由 component，点击跳转"素材列表"页面、"用户管理"页面
FTYPE_BUTTON='F'
Function 按钮		挂在页面下的操作点（按钮/链接），无路由，只有 perms页面上的"新增""导出""删除"按钮
I扩展约定：字段（Item/Field）若依原生没有，是为字段级权限扩展的类型：不参与路由，只挂 perms不出现在导航，只产出权限码 field:user:phone
▼ 素材中心 [M 目录，点一下展开，不跳转]
▸ 素材列表 [C 菜单页面，点击进入 /material/list]
· 新增按钮 [F → material:list:add]
· 导出按钮 [F → material:list:export]
· 手机号列 [I 字段 → field:user:phone，不可见]
图 2-3　M 是"抽屉"（无页面），C 是"页面"，F 是页面上的"按钮"，I 是我们扩展的"字段权限点"
回答你的提问"目录是什么 / C 是什么英文"

目录（M）就是左侧导航里的分组文件夹，作用是收纳菜单，本身不对应任何页面；F 官方含义是 Function（功能/按钮）；C 是约定码，可理解为 Content/Menu（菜单页）。

04

权限码与 @PreAuthorize：后端如何校验

4.1 注解写在接口上

MaterialController.java
@RestController
@RequestMapping("/material")
public class MaterialController {

    @PreAuthorize("@ss.hasPermi('material:list:query')")
    @GetMapping("/list")
    public TableDataInfo list(Material m) { ... }

    @PreAuthorize("@ss.hasPermi('material:list:add')")
    @PostMapping
    public AjaxResult add(@RequestBody Material m) { ... }
}
  • @ss 是 Spring 容器里名为 ss 的 PermissionService Bean；
  • @ss.hasPermi("xxx") 在方法执行前调用，本质是从当前登录用户的权限 Set<String> 里做 contains；
  • 超级管理员拥有 *:*:*，匹配时直接放行（通配）。
PermissionService（@ss 的本质，简化版）
public class PermissionService {
    public boolean hasPermi(String permission) {
        LoginUser user = SecurityUtils.getLoginUser();
        if (user.getUser().isAdmin()) return true;   // *:*:* 超管
        return user.getPermissions().contains(permission); // Set.contains，O(1)
    }
    public boolean hasRole(String role) { ... }
}
高频误区：注解会在启动时扫描入库吗？——不会

@PreAuthorize 只是一个运行时校验锚点，若依没有任何机制在启动时扫描它、把权限码写进 sys_menu。注解里的字符串和 sys_menu.perms 字段，靠人工约定保持完全一致。你写了注解但菜单表里没配 perms，这个权限就永远不会被授予任何人（超管除外）。

05

权限码与代码的先后顺序（code-first）+ 代码生成器

5.1 标准流程：先定权限码，再发版配菜单

回答你"先有代码还是先在菜单里选"的问题——权限码是开发先设计好的约定，走 code-first：

① 设计权限码
确定命名 material:list:add
→
② 写代码
接口加 @PreAuthorize，前端按钮加 v-hasPermi
→
③ 菜单 SQL
menu.sql 随版本发版（Flyway 执行），写入 sys_menu
→
④ 角色授权
管理员在后台勾选角色，写 sys_role_menu
→
⑤ 登录生效
用户重新登录聚合到新权限码
图 2-4　code-first：权限码随代码版本发布；"给角色关联"是上线后管理员的人工动作（最小权限）
新增一个接口，能不能自动给相关角色关联权限，不用管理员手动加？

正确的安全默认是"不自动"：新权限默认无人拥有（最小权限原则），必须管理员显式授权。如果"新增接口自动授予所有相关角色"，一旦新接口是高危操作（如批量删除），就会被无意中放开。可接受的自动化仅限：开发环境自动给超管角色；或发布单里附带一条"申请给 XX 角色开通 XX 权限"的审批流。

5.2 若依代码生成器（纠正"建菜单生成代码"的理解）

方向是反的：建表 → 生成代码和菜单，而不是建菜单 → 生成代码

ruoyi-generator 是表驱动：① 先在数据库建好业务表（如 material）；② 在代码生成器里导入这张表、配置字段与生成选项；③ 生成前后端 CRUD 代码 + 一份 menu.sql（含列表页 C、增删改查 F 按钮和对应权限码）；④ 执行 menu.sql、把生成的代码放进工程；⑤ 给角色授权。

所以"创建菜单时自动生成 CRUD、权限也设计好"的准确表述是：以业务表为输入，一次性产出 CRUD 代码和菜单权限 SQL；之后你做的确实是菜单分配（给角色授权）。

5.3 "权限组"概念有意义吗？

页面由多个接口/按钮组成（查询、新增、导出…），这些权限点在若依里天然通过菜单树的父子结构聚合：C 菜单是父节点，F 按钮是子节点，"某页全部权限"就是这棵子树。不需要再单独建一张"权限组"表——角色勾选父菜单时可级联勾选子按钮，这就是权限聚合。

06

行级权限：data_scope 五档 + @DataScope 高频

先纠正一个口误：不存在 "dashscope 表"

DashScope 是阿里大模型平台，与权限无关。若依的行级数据权限由 sys_role 表的 data_scope 字段 + sys_role_dept 表 + sys_dept 部门树 实现，配合业务表的 dept_id / create_by 字段。

6.1 五档数据范围（sys_role.data_scope）

值档位拼出的 WHERE 条件（示意）
1全部数据不加限制（管理员）
2自定义数据dept_id IN (sys_role_dept 里勾选的部门)
3本部门数据dept_id = 当前用户部门
4本部门及以下dept_id IN (本部门 + 子孙部门)，沿 sys_dept 树向下展开
5仅本人数据create_by = 当前用户 ← 这就是"只看自己投放的素材"

6.2 运行机制：@DataScope AOP 拼 WHERE

① Mapper 方法
加 @DataScope(deptAlias="d", userAlias="u")
→
② 切面拦截
DataScopeAspect 读当前用户角色的 data_scope
→
③ 生成 SQL 片段
按五档拼出 WHERE 字符串，塞进 BaseEntity.params.dataScope
→
④ XML 拼接
SQL 末尾 ${params.dataScope}，下推数据库
图 2-5　data_scope 是"规则型"行级权限：不存逐条关系，每次查询把角色档位翻译成 WHERE
切面拼出的 SQL（本部门及以下，第 4 档）
SELECT m.*, d.dept_id, d.ancestors
FROM material m
LEFT JOIN sys_dept d ON m.dept_id = d.dept_id
-- 下面这段由 @DataScope 自动拼接，开发者不用手写：
WHERE (
    d.dept_id = 8                         -- 本部门
    OR d.dept_id IN (SELECT dept_id FROM sys_dept
                           WHERE find_in_set(8, ancestors)) -- 所有子孙部门
);
关键定性

data_scope 是 ABAC 的简化版（规则型），不是 ACL 实例表：它只能表达"本人/本部门/自定义部门"这几种预设范围，无法表达"把素材 M100 单独分享给 G5 组"。后者需要第一册的 resource_owner，两者可 OR 合并。

07

字段级权限：若依原生没有，怎么扩展

先厘清：若依的 @Sensitive 是数据脱敏（手机号固定显示成 138****1234，按角色区分度有限），不是字段级鉴权。字段级"无权限就整个不返回"需要自己扩展。

7.1 权限码存储：两个方案

方案做法评价
方案一（推荐）
复用 sys_menu		新增一条 menu_type='I' 的记录，perms='field:user:phone'，角色勾选后照常走 sys_role_menu零新表、零新链路：登录聚合权限 Set 时自动带上，后端 @ss.hasPermi 直接判
方案二
独立字段表		建 sys_field + sys_role_field 两张表语义清晰但要新增表、CRUD、聚合 SQL，维护成本高
为什么"复用 sys_menu"能成立（你自己想通的那一步）

角色勾选 type=I 记录后，用户登录聚合出的权限 Set 里就有了 field:user:phone；聚合 SQL 不看 menu_type，所以字段权限和按钮权限走完全相同的链路，区别只是它不生成路由、不出现在导航。

7.2 实现：Jackson 序列化时裁字段（注册一次，全局生效）

字段级判断不能在每个字段上手写 enforce，正确做法是注册一个 Jackson 序列化修饰器，在 VO 转 JSON 时统一处理：

① VO 字段上打自定义注解
public class UserVO {
    private Long id;
    private String name;

    @FieldPerm("field:user:phone")   // 无此权限码，该字段不序列化
    private String phone;

    @FieldPerm("field:user:cost")
    private BigDecimal cost;
}
② 全局 BeanSerializerModifier（一次性注册）
public class FieldPermSerializerModifier extends BeanSerializerModifier {
    @Override
    public List<BeanPropertyWriter> changeProperties(
            SerializationConfig config, BeanDescription bd,
            List<BeanPropertyWriter> props) {
        Set<String> perms = SecurityUtils.getPermissions();   // 当前用户权限 Set
        List<BeanPropertyWriter> kept = new ArrayList<>();
        for (BeanPropertyWriter w : props) {
            FieldPerm fp = w.getAnnotation(FieldPerm.class);
            if (fp == null || perms.contains(fp.value())) {
                kept.add(w);                          // 无注解 或 有权限 → 保留
            }                                            // 无权限 → 直接丢弃（不序列化）
        }
        return kept;
    }
}
性能要点（呼应第四册批量决策）

权限 Set 在每个请求开始时取一次，序列化 n 行数据时每行只是对几个字段做 Set.contains（O(1)），不会逐字段查库或调权限引擎。裁列的 O(n·k) 是序列化输出本身的成本，不是权限成本。

08

权限生命周期：落库、新增、删除、应急

8.1 装饰器（注解）拿到权限后，还需不需要落库？

需要。注解是代码里的"校验点"，但授权管理页面需要列出"系统里有哪些权限可分配"，角色-权限关系（sys_role_menu）也必须有外键目标。权限元数据落库（sys_menu）后，管理后台才能勾选、权限才能被授予。注解解决"校验"，库解决"授权"，二者靠权限码字符串约定一致。

8.2 新增权限的完整动作

  1. 开发定权限码、写注解、写 menu.sql（随版本发版，落 sys_menu）；
  2. 上线后新权限默认无人拥有（最小权限）；
  3. 管理员在角色管理里勾选，写 sys_role_menu；
  4. 用户下次登录（或删其权限缓存后）聚合到新权限。

8.3 修改 / 删除权限与级联

推荐顺序（你说的基本正确，补充软删）

正常下线：先下代码（去掉注解/接口）→ 再删关联（sys_role_menu 等中间表，按 menu_id 级联）→ 最后处理菜单记录（推荐 del_flag 软删而非物理删，保留审计）。涉及多表写操作放在一个事务里。

  • 改权限码：等同"删旧 + 增新"，旧角色关联迁移到新码；
  • 级联清理：删 sys_menu 记录时同步删 sys_role_menu 中引用（外键 ON DELETE CASCADE 或显式 delete）；
  • 为什么软删：保留历史授权记录用于审计，且避免误删导致线上用户大面积丢权限。

8.4 应急场景：代码不能改，要立刻关掉某接口

你设想的"逻辑删除权限、防止别人访问"是真实场景（接口出 bug/漏洞，紧急止血）。但要注意两个漏洞：

只删权限码挡不住两类人
  • 超级管理员（*:*:* 通配）不受权限码控制；
  • 已经在白名单 / 内部调用链里的请求。

生产级止血要在权限码体系之外加一道 deny 优先的功能黑名单 / Feature Flag（开关）：网关或 AOP 里维护"已禁用接口清单"，deny 优先于 allow，对超管也生效，配置中心可秒级下发。

09

本册小结与自测

9.1 必须带走的 7 句话

  1. 若依没有独立权限表：菜单与权限点合一为 sys_menu，前端读路由字段、后端读 perms。
  2. 菜单类型 M 目录（无页面）/ C 菜单页面 / F 按钮，扩展 I 字段。
  3. 后端 @PreAuthorize("@ss.hasPermi('x')") 本质是权限 Set 的 O(1) contains，超管 *:*:*。
  4. 注解不会自动扫描入库，code-first：定码→写注解→menu.sql 发版→人工授权。
  5. 代码生成器是表驱动：建表→生成 CRUD+menu.sql，不是建菜单生成代码。
  6. 行级用 data_scope 五档 + @DataScope 拼 WHERE（规则型，非 ACL），不是 dashscope 表。
  7. 字段级复用 sys_menu（type=I）+ Jackson 全局修饰器裁字段；若依原生只有 @Sensitive 脱敏。
