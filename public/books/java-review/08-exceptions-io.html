02

异常体系：一棵继承树 必考

2.1 痛点：错误码时代的三个灾难

先看没有异常机制的 C 时代是怎么处理失败的，才能理解 Java 这棵树为什么长成这样：

// C 风格：错误码 + errno 全局变量
int fd = open("data.txt", O_RDONLY);
if (fd == -1) {                       // 灾难一：调用方【可以不理】返回值
    fprintf(stderr, "open failed: %s", strerror(errno));   // 错误信息贫瘠
    return -1;                        // 灾难二：错误【没有类型】，只有 -1 和全局 errno
}
int n = read(fd, buf, size);
if (n == -1) { ... return -2; }       // 灾难三：错误层层上报 = 层层 if，
//                                   // 五层调用栈 = 五层 if (ret < 0) 的样板
// 而且：错误沿【返回值通道】逆流而上，和正常数据共用一条路，
//       编译器无法区分"这是数据还是错误"

Java 的解法是把"出错"从返回值通道里剥离出来，走一条专属通道：异常沿调用栈向上冒泡（throw → 逐层上抛 → 直到有人 catch），没人接住就崩给 JVM 看栈轨迹。这个"沿调用栈上抛"的机制叫栈展开（stack unwinding）——回收模块 1：每层方法调用对应一个栈帧，异常展开时逐帧弹出，并把"经过哪些帧"记下来，这就是 stack trace 的本质：一张案发路径快照。

★ 两条分界线（面试一句话）：
  第一刀：Error vs Exception —— 问题出在【JVM】还是【程序】
  第二刀：受检 vs 非受检 —— 编译器【强制你处理】还是【随你便】

读这棵树的姿势（回收模块 3 的继承树读法）：每一刀切分都问"按什么维度分"。第一刀按"故障归属"分——Error 是 JVM 自己病入膏肓（内存耗尽、栈溢出、类加载失败），Exception 是程序运行中遇到的问题。第二刀按"编译器态度"分——受检异常编译器逼你处理，非受检异常全凭自觉。两刀切出四个象限，Java 把两个象限合并了（Error 也归非受检）。

2.3 为什么 Exception 要再分一刀：编译器的强制契约

CheckedDemo.java不处理受检异常 = 编译不过
// 受检异常：编译器强制"要么接住，要么声明上抛"——二选一，不许装看不见
public String readConfig(String path) {
    BufferedReader r = new BufferedReader(new FileReader(path));
    // ✗ 编译错误：Unhandled exception: java.io.FileNotFoundException
    //    —— FileReader 的构造器声明了 throws FileNotFoundException，
    //       调用方【必须】表态
}

// 表态方式一：接住处理
try {
    BufferedReader r = new BufferedReader(new FileReader(path));
} catch (FileNotFoundException e) {
    log.error("配置缺失，用默认配置", e);
    return defaultConfig();
}

// 表态方式二：声明上抛（"这事我处理不了，交给调用方"）
public String readConfig(String path) throws IOException { ... }

// 对比：NPE 这种 RuntimeException 不强制
String s = map.get(key).trim();
// 编译通过 —— 挂了运行时才炸。编译器认为：这是【你的 bug】，
// 该修代码（判空），而不是"处理"异常

设计动机一句话：受检异常 = 方法签名的一部分，把"这个操作可能失败"写进契约。像 FileNotFoundException 这种"外界环境导致的、调用方有能力预见的失败"，编译器逼你看一眼，理论上能消灭一类"忘处理的线上事故"。

2.4 受检异常的争议：为什么别的语言都把它扔了

Java 是主流语言里唯一有受检异常的（C++/Python/Kotlin/Scala/Go 全都没有，Go 甚至直接回退到错误码 if err != nil）。面试聊到这就有意思了——受检异常的好意在实际工程里变了味：

争议一【演化灾难】：
  接口方法加一个受检异常 → 所有实现类和调用方全部编译报错。
  和模块 8 接口默认方法要解决的是同一个问题：
  "已发布的契约怎么安全演化"——受检异常让演化变得更脆。

争议二【Lambda 不兼容】（回收模块 7）：
  Stream.map(s -> new FileReader(s))    // ✗ 编译错误
  // Function<T,R> 的 SAM 不声明 throws，
  //    lambda 里抛受检异常就装不进这个函数式接口
  // → 全 JDK 的函数式接口都不带 throws，Lambda 时代受检异常成了累赘

争议三【吞异常泛滥】：
  强制的本意是"逼你处理"，实际催生的是：
  catch (IOException e) { e.printStackTrace(); }   // 假装处理了
  或者方法签名 throws Exception                     // 躺平摆烂
  —— 强制处理 ≠ 正确处理

所以业界的实践共识：新代码少抛受检异常，底层 API 用非受检 +
  文档/异常体系自己设计（Spring 的 DataAccessException 就是全家非受检）。
一句话回答

Java 异常体系？——Throwable 一分为二：Error 是 JVM 级致命伤（OOM/StackOverflow，别 catch）；Exception 再分受检（编译器强制 catch 或 throws，如 IOException）与非检（RuntimeException，程序 bug，修代码而不是接异常）。stack trace 的本质是栈展开时的栈帧链快照。

OOM、StackOverflowError 是 Exception 吗？能 catch 吗？

都不是——它们是 Error（继承 Throwable 的 Error 分支，属于非受检，但归类是 Error 不是 Exception）。能不能 catch：语法上能（catch (OutOfMemoryError e) 合法），但基本没有意义——OOM 时堆已耗尽，你的 handler 分配任何对象都可能再炸，应该做的是让 JVM 快速失败 + 外部监控告警。唯一的灰色地带是 StackOverflowError：递归爆栈后栈已经弹干净，catch 后小心理论上能继续跑（有些解析库拿它实现"深度自适应"），但这是走钢丝，面试答"不推荐依赖"。回收模块 5：OOM 家族按区域分——堆 OOM（对象太多）、元空间 OOM（类太多，回收模块 5 的动态代理滥用）、栈溢出（递归没出口）。

throws Exception（直接抛总类）好不好？

不好，两层坏处：① 契约失效——调用方只知道"可能出错"，不知道哪类错、该怎么应对（重试？降级？终止？），受检异常"精确契约"的价值被抹掉；② 传染扩散——签名 throws Exception 会逼着每一层调用方也写 throws Exception（catch 具体类型也得先 catch Exception），异常体系烂在签名上。正确姿势：底层抛具体类型；需要泛化时在边界层做异常转换（IOException → 业务异常，保留 cause 链，见 3.4）。

Python 的异常体系和 Java 比缺了什么？Python 对比

Python 一切异常继承 BaseException（SystemExit/KeyboardInterrupt 直挂其下，等价于 Java 的 Error 分支；日常异常继承 Exception），但没有受检/非受检之分——任何异常都可以不声明直接抛，你调一个函数前不知道它会炸什么（要么看文档要么看源码）。Java 的受检异常把这个信息放进编译期类型系统，代价是签名僵化。另外 Python 的 else 子句（try 不炸才执行）Java 没有；Java 的受检声明 Python 对应 raise ... from ...（异常链，Java 的 cause）。你会发现在 Python 里你早已习惯"EAFP"（请求宽恕比许可容易：先 try 再说），这正是异常机制的初衷——Java 只是把它做成了强制的。

3.2 自定义异常：项目里的异常体系怎么设计

BusinessException.java标准三层结构（面试可背）
// ① 业务异常基类：非受检（不污染 service 签名），带错误码（比字符串好检索好国际化）
public class BusinessException extends RuntimeException {
    private final int code;                       // 错误码：ERROR_PARAM 之类
    public BusinessException(int code, String message) {
        super(message);                           // message 给人看
        this.code = code;                         // code 给程序看
    }
    public BusinessException(int code, String message, Throwable cause) {
        super(message, cause);                    // ★ 保留 cause：底层案发路径不丢
    }
    public int getCode() { return code; }
}

// ② 具体业务异常：继承基类，一眼可读
public class InsufficientBalanceException extends BusinessException { ... }

// ③ 全局处理器：Web 层统一接（Spring 的 @RestControllerAdvice）
//    controller/service 里 throw new BusinessException(...)，
//    这里统一转成 {"code": 4001, "msg": "余额不足"} 响应
@ExceptionHandler(BusinessException.class)
public Result handle(BusinessException e) {
    return Result.fail(e.getCode(), e.getMessage());

3.4 异常链：别把案发路径弄丢 工程素养

ExceptionChain.java一个构造参数的差别
// ✗ 反面教材：转换异常时丢了 cause
try {
    parseConfig(file);
} catch (IOException e) {
    throw new BusinessException(5001, "配置解析失败");
    // ★ e 被扔掉了！stack trace 只剩这一层的路径，
    //   "为什么 IOException？文件不存在还是权限不够？"——查不到了
}

// ✓ 正确姿势：把底层异常挂到 cause 链上
try {
    parseConfig(file);
} catch (IOException e) {
    throw new BusinessException(5001, "配置解析失败", e);
    //                      e = cause ★ 日志打印的是完整因果链：
    //    BusinessException: 配置解析失败
    //        Caused by: java.io.FileNotFoundException: config.yml (No such file ...)
    //        Caused by: ...
}

排查线上问题时，Caused by 链就是"案发路径的完整监控录像"——丢了它，等于把录像带删了再报警。这也是日志规范里"日志要打异常对象本身（log.error("...", e)），不是 e.getMessage()"的原因：message 只有一句话，异常对象才有完整栈。

一句话回答

三类异常怎么处理？——Error 不 catch（JVM 的病，catch 了也救不了）；受检异常能恢复就 catch（重试/降级），不能就 throws 上抛；RuntimeException 不 catch，修 bug。业务异常体系：非受检基类 + 错误码 + 转换时保留 cause 链 + 全局处理器收口。

1
追问：catch (Exception e) 和 catch (Throwable t) 哪个更不能写？
都别写，但 Throwable 更糟：catch Exception 至少还在"程序问题"的范围内（会把 NPE 这类 bug 也吞掉）；catch Throwable 连 Error 一起吞——OOM/StackOverflow 被拦下后 JVM 带病运行，故障被掩盖得更深。合法场景只有最顶层兜底（main 循环或线程池的 UncaughtExceptionHandler，记完日志让线程体面退出）。
2
追问：finally 里写 return 会怎样？（先剧透，04 节细讲）
编译器允许（只给警告不给错误），但会吞掉 try 里抛出的异常并覆盖返回值——JLS 明文禁止的方向，阿里规约列为禁止项。细节和"finally 一定执行吗"一起在下一节展开，那是笔试最爱。
3
追问：项目里见过哪些"异常驱动流程"的反模式？
用异常当业务分支：解析数字用 Integer.parseInt 的 NumberFormatException 判断"是不是数字"（每秒上万次抛栈采集，CPU 全耗在取证上——06 节的性能账）；或用异常跳出深层循环（当 goto 用）。异常的定位是"异常路径"，正常路径走返回值。
04

try-catch-finally 深挖 笔试最爱

4.1 执行模型：两段式 + 优先级

标准执行流程（无异常）：
  try 全部执行 → finally 执行 → 方法返回

try 里抛异常：
  try 在抛出点【立刻中断】（后面的代码不执行）
  → 异常和 catch 块类型从上往下匹配（★父类在前面 = 后面全废）
  → 匹配成功：执行该 catch → 执行 finally → 方法返回
  → 全不匹配：先执行 finally，然后异常【继续向上抛】

三条优先级铁律（记这个顺序，所有笔试题都是它的变形）：
  ① finally 的执行优先级最高：方法退出前【一定】轮到它（仅两种例外，4.3）
  ② try/catch 的 return：先算好返回值【暂存】，再执行 finally，
     finally 不动暂存值就返回暂存值
  ③ finally 里如果【也有 return / 抛异常】：直接覆盖 ② —— 惨案之源

4.4 最恶劣的坑：finally 吞异常 必考

Swallow.java三行代码静悄悄丢掉一个异常
try {
    throw new RuntimeException("真正的故障");
} finally {
    return 42;    // ★ try 里抛的异常【凭空消失】！
}
// 调用方拿到 42，一切"正常"——线上问题查到怀疑人生
// JLS 语义：finally 里的 return/throw 会【中止】try 里的异常传播
// 编译器只给警告不报错；阿里规约明令禁止 finally 里 return

// 变体二：finally 里抛新异常，同样覆盖原异常
try {
    throw new RuntimeException("原始故障");
} finally {
    throw new IllegalStateException("finally 里的新故障");  // 只能看见这个
}

这也正是 05 节 try-with-resources 要解决的问题之一：资源关闭（在 finally 里）和 try 里抛异常撞车时，谁活下来？手写 finally 只能活一个（后者覆盖前者），Java 7 的官方答案是"两个都留，一个进压栈"。

一句话回答

finally 执行细节？——优先级最高（除 System.exit / JVM 退出 / kill -9 外必执行）；try 的 return 先暂存值再跑 finally（finally 改基本类型追不回暂存，改引用指向的对象立刻可见）；finally 里 return/throw 会覆盖 try 的（吞异常，禁止）；catch 匹配从上到下、父类必须放后面。

try 里有 return，finally 里也有 return，编译器怎么处理？

编译通过但 IDE 会给 "finally block does not complete normally" 警告——JLS 故意没把它定成错误（兼容老代码），但语义上就是错的。字节码层面的真相：编译器生成的 finally 代码会插到每个出口（正常 return 前、athrow 前），finally 的 return 一执行，try 的返回路径直接被跳过。所以"finally 的 return 覆盖 try 的 return"不是什么微妙行为，是编译器把 finally 的代码排在最后、排在出口处。类似的：System.out.println 在 finally 里是安全的（不改变控制流），只有 return/throw/break/continue 这四种"控制流语句"才会吞异常。

Python 的 finally 语义一样吗？Python 对比

一模一样的坑，Python 全都有：finally 里的 return 同样吞掉 try 的异常；finally 里抛异常同样覆盖原异常。而且 Python 还有个 Java 没有的坑：生成器在 finally 里 yield 会 RuntimeError。解药也是同构的——Python 3 的 contextlib.suppress、官方推荐 with 语句管理资源（对应 Java 7 的 try-with-resources，下一节）。两门语言在这点上共享同一套"finally 优先"的语言设计，你踩过的坑可以直接迁移。

try-with-resources：资源管理的官方答案

5.1 痛点：手写关闭的四种姿势，各有各的坑

文件、Socket、数据库连接——用完必须关闭（不关 = 句柄泄漏，回收模块 5 的 native memory）。Java 7 之前的标准写法：

ManualClose.java老写法的三宗罪
// 罪一：close() 本身也会抛异常（throws IOException），
//       在 finally 里还得再套一层 try-catch —— 代码金字塔
BufferedReader r = null;
try {
    r = new BufferedReader(new FileReader(path));
    return r.readLine();
} catch (IOException e) {
    log.error("read fail", e);
    return null;
} finally {
    if (r != null) {                 // 罪二：还得判空（构造可能就没成功）
        try {
            r.close();
        } catch (IOException e) {     // 罪三：这里抛的异常会【覆盖】try 里的原始异常
            log.error("close fail", e);   // —— 4.4 的吞异常坑，真实发生地
        }
    }
}
// 一个"读一行"的意图，写了 12 行，两处陷阱

5.2 Java 7 的答案：语法 + 接口 + 语义三件套

TWR.java同一件事，四行
// ① 资源声明在 try 的括号里，编译器自动生成关闭逻辑
try (BufferedReader r = new BufferedReader(new FileReader(path))) {
    return r.readLine();
}                                  // 无需 finally：close 自动调用、判空、套 catch 全免

// ② 前提：资源类实现 AutoCloseable 接口（Java 7 新增）
public interface AutoCloseable {
    void close() throws Exception;      // 唯一抽象方法
}                                       // 你的类实现它就能进 try 括号（自己写资源类时的钩子）

// ③ 多个资源：分号分隔，【逆序关闭】（后开的先关，对称于 C++ 析构）
try (FileInputStream in = new FileInputStream(src);
     FileOutputStream out = new FileOutputStream(dst)) {
    in.transferTo(out);
}   // 关闭顺序：先 out 后 in —— out 是依赖 in 的数据建起来的，
    // 建立顺序的正序，销毁顺序的逆序（栈式对称）

5.3 精髓：suppressed exceptions（被压制的异常）

手写 finally 的两难（4.4 的坑）：
  try 里抛了 A（比如磁盘读坏了），关闭时又抛了 B（close 失败）
  → 只能活一个：B 覆盖 A，真正的案发原因 A 丢了

try-with-resources 的答案：【一个都不丢】
  try 里的异常 A = 主异常，照常上抛（它才是故障根源）
  close() 里的异常 B = 被压制异常（suppressed），
    挂到 A 身上：a.addSuppressed(b) —— 附带在案卷里，不打断主案

打印出来的 stack trace：
  java.io.IOException: 磁盘读失败（主异常，根因）
      at ...
      Suppressed: java.io.IOException: close 失败   ← 附属案卷
          at ...

★ 面试金句：try-with-resources 比 finally 关资源好在哪？
  ① 不会吞异常（suppressed 全保留 vs 只活一个）
  ② 逆序关闭多资源（依赖顺序正确）
  ③ 代码量 1/3，且不可能忘写关闭逻辑
  这题答出 suppressed，就是"读过 JLS 级"的信号。
一句话回答

try-with-resources？——try 括号里声明的资源（实现 AutoCloseable）自动关闭：编译器生成逆序 close + 判空 + 异常处理，核心优势是 suppressed exceptions——try 的主异常照常抛，close 的异常挂到主异常的 suppressed 列表里，一个不丢（手写 finally 只能活一个）。

Java 9 对它做了什么增强？

允许括号里直接引用已存在的 effectively final 变量：Java 7/8 必须在括号里 new（try (r = new ...) 才合法），Java 9 起 try (r) 就行——当资源来自工厂方法/参数时不用再包一层。配合模块 7 的"effectively final"概念：被引用的变量必须事实上 final（编译器要保证它不被重新赋值，关闭代码才能安全引用它）。

Python 的对应物？Python 对比

with open(path) as f: —— 上下文管理器协议（__enter__/__exit__），你天天在用。语义对齐到令人发指：异常自动传播（__exit__ 返回 False 不吞异常）、多资源逗号分隔、离开作用域自动清理。差别在细节：Python 的 __exit__ 能看到异常对象并选择吞不吞（返回 True = 吞），Java 的 AutoCloseable.close 看不到 try 里发生了什么；Java 用 suppressed 保存"关闭时又炸了"的信息，Python 的 __exit__ 里再抛就直接链式覆盖（raise ... from ... 补救）。另外 contextlib.contextmanager 装饰器用生成器实现上下文管理，Java 没有这么轻巧的玩法（要老老实实实现接口）。

异常的性能与工程规约 素养题

6.1 异常到底贵在哪：fillInStackTrace

new RuntimeException() 的真实成本：

  ① 填充栈轨迹 fillInStackTrace()：
     逐帧回溯当前线程的调用栈（JIT 优化受限，可能还要符号反解）
     栈越深越贵 —— 深调用链里 new 一个异常 = 微秒级
  ② 分配栈轨迹数组、字符串化（getMessage/lazy 打印）

对比：普通对象 new = 纳秒级；异常对象 new = 微秒级（100~1000 倍）

推论：
  ✓ 异常路径慢【无所谓】—— 走到异常路径本来就是小概率故障
  ✗ 用异常当【正常控制流】= 灾难 —— 每秒抛万个异常，CPU 全在做"取证"
    典型反例：Integer.parseInt 靠 NumberFormatException 判断"是不是数字"

  高频创建同款异常的优化姿势（见识题）：
    new StacklessException() —— JVM 内部用（隐藏构造器参数，不填栈）；
    缓存预构建的异常对象 + fillInStackTrace=false —— 重抛时快，
    代价是丢栈轨迹（只有确定不需要案发路径时才用，如中断标记）

6.2 阿里规约的异常条款（挑高频的四条）

规约理由（用前面的原理讲）
不要捕获 Java 类库中定义的继承自 RuntimeException 的运行时异常如 NPE/越界——catch 了 bug 还在，见 3.1"修代码不是接异常"
捕获异常后要么处理要么上抛，禁止空 catch / 只打 e.getMessage()空 catch = 吞异常（比 4.4 更彻底的吞）；只打 message 丢栈轨迹（3.4 的录像带问题）——要 log.error("ctx", e)
finally 里必须对返回值/资源只做回收动作，禁止 return4.4 吞异常；return 覆盖暂存值
不要用异常做流程控制、条件控制6.1 的性能账 + 可读性（异常路径的代码 JIT 少优化）

6.3 rethrow 与 fast-fail 的正确姿势

GoodVsBad.java四种写法段位对比
// 青铜：吞
try { risky(); } catch (Exception e) { }                    // 线上裸奔

// 白银：打了但没打全
try { risky(); } catch (Exception e) { log.error(e.getMessage()); }  // 丢栈轨迹

// 黄金：打全
try { risky(); } catch (Exception e) { log.error("risky 失败, ctx={}", ctx, e); }

// 王者：打全 + 转换成有语义的异常上抛（保留 cause）
try { risky(); }
catch (IOException e) { throw new BusinessException(5002, "数据导入失败", e); }

// 最差变体：捕获后再抛个裸 RuntimeException
catch (Exception e) { throw new RuntimeException(); }       // cause 丢了，人间蒸发
一句话回答

异常的性能账？——贵在 fillInStackTrace（逐帧取证，微秒级，比普通 new 慢百倍），所以异常只走故障路径，禁止当流程控制（反例：用 NumberFormatException 判数字）。工程四红线：不空 catch、不打裸 getMessage、finally 不 return、运行时异常不 catch 修 bug。

IO 家族地图与装饰器 高频

7.1 两个维度切出四象限

java.io 的几十个类看着眼花，其实只有两个维度：字节还是字符（数据当什么看）、进还是出（方向）。四个抽象基类就是四个象限的原点：

                字节（8bit，二进制：图片/压缩包/一切）    字符（16bit，文本：要解码）
输入（读到程序）   InputStream                          Reader
                   read() 返回 int（0~255，-1=结束）      read() 返回 int（字符，-1=结束）
输出（从程序写）   OutputStream                         Writer
                   write(int b)                          write(char[])

命名规律：象限基类 + 功能前缀，见名知义：
  File 前缀   = 数据源是文件        FileInputStream / FileReader
  Byte/Char   = 内存数组当源        ByteArrayInputStream / CharArrayReader
  Object 前缀 = 对象序列化          ObjectInputStream / ObjectOutputStream
  Piped 前缀  = 线程间管道          PipedInputStream（回收模块 6 线程通信）

字节 ↔ 字符的桥：InputStreamReader / OutputStreamWriter（解码用 charset）
  new BufferedReader(new InputStreamReader(System.in, StandardCharsets.UTF_8))
  —— 字节流包进"解码适配器"变成字符流，再包缓冲 —— 这就是下一节的主角

7.2 装饰器模式：为什么 new 要套三层 原理

面试官最爱问："这行代码为什么 new 了三层？"

Decorator.java一行经典
BufferedInputStream bis = new BufferedInputStream(new FileInputStream("a.txt"));
//                                    └── 数据源：真会读磁盘的家伙
//                       └── 装饰者：包着它，加"缓冲"能力

// 核心：BufferedInputStream extends FilterInputStream extends InputStream
//       装饰者【和被装饰者是同一个父类】 —— 套几层都还是 InputStream
bis.read();   // 调到缓冲层的 read：内存缓冲区有就直接给，
              // 没有就一次性找被包裹的真流要 8192 字节（少打扰磁盘）
为什么不设计成 FileInputStream 带 buffered 参数？
  —— 能力组合会爆炸：
     基础流 N 种（File/ByteArray/Socket...）× 增强能力 M 种（缓冲/基本类型/行读...）
     = N×M 个类（FileBufferedInputStream、ByteArrayBufferedInputStream...）

装饰器的答案：基础流实现"读"，增强流实现"包裹后增强"，
  同一父类保证【任意组合、任意层数】—— N + M 个类搞定 N×M 种组合
  ★ 回收模块 3 的设计模式：装饰器 = "不改原类、组合加能力"
    （Python 的 @decorator 是【语法糖/函数包装】，Java IO 装饰器是【GoF 设计模式】
      —— 同名不同物，面试别混；但"包装加能力"的思想一致）

代价：类数量多、new 套娃难读 —— 所以日常代码用
  Files.readAllLines(path) / Files.newBufferedReader(path) 这类工厂方法收口

7.3 缓冲为什么快：一次搬一卡车 vs 一次搬一箱

无缓冲：read() 一次 = 真读一次磁盘/走一次系统调用
  读 1MB：1024 次 read × 1 字节 = 1024 次系统调用（每次都是用户态↔内核态切换）

有缓冲：缓冲层一次进货 8KB（一次系统调用），后续 read 从内存批发
  读 1MB：128 次系统调用 —— 系统调用次数降为 1/8

★ 本质：用"一次多搬"摊薄"每次搬运的固定成本"（系统调用切换）
  这是计算机系统的通用规律（和 CPU cache 行、TCP 滑动窗口、GC 分代同源）：
  —— 慢速边界上，永远批量搬运
一句话回答

Java IO 体系？——两维四象限：字节/字符 × 输入/输出，四个抽象基类（InputStream/OutputStream/Reader/Writer），字节字符互转用 InputStreamReader 桥。功能增强靠装饰器模式（同父类包裹组合，N+M 个类覆盖 N×M 组合），缓冲提效的本质是批量搬运摊薄系统调用成本。

字节流和字符流怎么选？

默认字节流（万物皆字节，通用）；确定是文本且要按字符处理（readLine、编码敏感）才用字符流。坑在编码：字符流不指定 charset 就用平台默认（Windows 的 GBK vs Linux 的 UTF-8——同一个文件两边读出乱码），生产代码必须显式 StandardCharsets.UTF_8。顺便回收模块 6：老 API 里 Reader/Writer 的某些实现（如 FileReader 老版本无法传 charset）逼人用字节流+手动解码，Java 11 后 FileReader 终于能传 charset 了。

序列化选什么？ObjectInputStream 好用吗？追问率高

Java 原生序列化（Serializable + ObjectInputStream）只适合进程内/临时场景：① 不安全——反序列化任意类，历史上 RCE 漏洞重灾区（log4shell 同类攻击面）；② 脆——serialVersionUID 一变就 InvalidClassException，加个字段都心惊；③ 大且慢——带类元数据。生产选择：跨语言/网络 → JSON（Jackson）或 Protobuf（Kafka、gRPC 的选择，二进制小 3~10 倍）；进程内缓存 → Hessian/Kryo。面试能说出"为什么 Kafka 不用 Java 序列化"就是加分：跨语言 + 紧凑 + 版本演化友好。

BIO 之痛与 C10K 高频

8.1 传统网络编程模型：一连接一线程

BioServer.javaTomcat 4 时代的模型
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();          // ① 阻塞：没连接来就睡着等
    new Thread(() -> {                        // ② 每来一个连接，专职伺候
        byte[] buf = new byte[1024];
        try (InputStream in = socket.getInputStream()) {
            int n = in.read(buf);             // ③ 阻塞：对端不发数据就睡着等
            // ... 处理                        // ④ 这个线程就这么被【这个连接独占】
        }
    }).start();
}

每一步都直白可靠，但代价藏在 ③：read() 是阻塞调用——对端不说话，这个线程就干睡着。于是"线程数 = 连接数"成为铁律。

8.2 C10K：数量级一变，模型崩塌

100 个连接：    100 个线程 —— 完全没问题（BIO 的舒适区）
10000 个连接：  10000 个线程 —— C10K 问题（1999 年 Dan Kegel 提出）

三重死法（全部回收模块 6/6B 的知识）：
  ① 内存：线程栈默认 1MB，10000 线程 = 10GB 起步 → OOM
  ② 调度：CPU 核就 8/16 个，上万线程上下文切换，
     切换开销吃掉大部分 CPU（真正干活的时间被挤没了）
  ③ 创建销毁的 churn（虽可用线程池缓，但 1 万并发还是撑不住 1 万线程池）

★ 根因复盘：线程被浪费在【阻塞等待】上 —— 90% 的线程在睡
  （等对端发数据），真正干活的连 10% 都没有。
  破局思路只有一条：让少数线程【不再傻等】——
  把"每连接一个专职服务员（阻塞等）"
  换成"一个服务员同时盯着 10000 张桌子（谁举手了服务谁）"
🐍 Python 对比

你在 Python 里绕过 C10K 的路径就是 asyncio：协程挂在 await 上不占线程，事件循环一个线程轮询所有就绪的 socket——和 Java NIO 的思路完全同源，只是把"就绪通知 + 手动注册"自动化成了语法（await 点即挂起点）。Flask/Django 老 WSGI 模型（一请求一线程/进程）= BIO 思路，FastAPI/uvicorn（ASIO）= NIO 思路——你两个世界都待过，这是理解本节最好的入口。

一句话回答

BIO 的问题？——accept/read 全阻塞，只能一连接一线程；连接数破万（C10K）后内存（1MB 栈 × 1 万）、上下文切换、线程管理全部爆掉。根因是线程浪费在阻塞等待上，解法是"就绪通知"模型：让一个线程只处理【此刻有事件】的连接——NIO。

NIO 三大件：Buffer / Channel / Selector 原理

Java NIO（JDK 1.4，New IO / Non-blocking IO）的世界观转变：从"流"到"通道"。Stream 是单向的水管（读用 InputStream、写用 OutputStream），Channel 是双向的铁道（读写同一条）。

9.1 Buffer：自己管状态的字节数组

BufferDemo.javaflip 是全场的灵魂考点
ByteBuffer buf = ByteBuffer.allocate(1024);   // position=0, limit=1024, capacity=1024
channel.read(buf);                            // 网络数据灌进缓冲区（写模式）

buf.flip();          // ★ 切换到读模式：limit=position（读到哪算哪）, position=0
while (buf.hasRemaining()) {
    byte b = buf.get();                       // 逐字节消费，position 前进
}

buf.clear();         // 复位为写模式：position=0, limit=capacity（数据没擦，会被覆盖）
// compact()          变体：未读完的挪到开头，接着写（半包场景）
Buffer 的四个指针（一个"读写双态"状态机）：
  capacity 容量：分配时定死，永不变
  position 位置：下一个读/写的下标
  limit   界限：第一个不可读/写的下标

写模式 flip 后 →读模式（核心图，必画）：
  写模式（read 进来后）：  [▓▓▓▓▓░░░░░]     position=5 limit=10
                          数据↑   ↑limit(capacity)
  flip()                  [▓▓▓▓▓░░░░░]     position=0 limit=5
  读模式：                 ↑position ↑limit —— 只能读到 5

为什么需要 flip：read() 和 get() 共用 position 一个游标，
  不切状态就会"写到哪从哪接着读"（读到垃圾）。
  真实项目里没人手写这个 —— Netty 的 ByteBuf 用双游标
  （readerIndex/writerIndex 分开）把这个易错点消掉了，这是它好用的点之一。

9.2 Channel：双向、可配非阻塞

Channel vs Stream：
  Stream   单向（输入/输出两个家族）    阻塞为主
  Channel  双向（读写同一对象）         可配置非阻塞（configureBlocking(false)）

  SocketChannel  = TCP 读写通道（可非阻塞）
  ServerSocketChannel = 服务端 accept 通道（可非阻塞）
  FileChannel    = 文件通道（【只能阻塞】—— 文件没有"就绪"概念，磁盘永远可读）

★ 关键体验：非阻塞模式下
  channel.read(buf)  → 没数据时【立即返回 0】，不睡！
  server.accept()    → 没连接时【立即返回 null】，不睡！
  —— "傻等"被消灭了，但新问题出现：没数据你也返回，调用方只能
     【循环重试空转】（busy loop 烧 CPU）……
     谁来告诉我"哪些连接此刻真的有数据"？—— 第三大件登场

9.3 Selector：一个线程管一万连接的指挥家 核心

NioServer.java骨架代码（面试能手写个大概即可）
Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.bind(new InetSocketAddress(8080));
server.configureBlocking(false);                    // ★ 前提：非阻塞才能注册
server.register(selector, SelectionKey.OP_ACCEPT);  // 注册"我对 accept 事件感兴趣"

while (true) {
    selector.select();          // ① 阻塞到【至少一个通道有事发生】（唯一睡觉点，
                                //    睡的是"等事件"，不是"等某个连接的数据"）
    Set<SelectionKey> keys = selector.selectedKeys();  // ② 拿到就绪名单
    Iterator<SelectionKey> it = keys.iterator();
    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();                               // ③ 处理完必须移除（高频坑）
        if (key.isAcceptable()) {                  // 新连接来了
            SocketChannel ch = server.accept();
            ch.configureBlocking(false);
            ch.register(selector, SelectionKey.OP_READ);   // 挂到同一个 selector
        } else if (key.isReadable()) {             // 某连接有数据可读
            SocketChannel ch = (SocketChannel) key.channel();
            ByteBuffer buf = ByteBuffer.allocate(1024);
            int n = ch.read(buf);                  // 此刻读【保证有数据】，不空转
            if (n == -1) { ch.close(); }           // 对端关闭
            else { buf.flip(); handle(buf); }
        }
    }
}
// 一个线程（主循环）伺候了所有连接 —— "谁举手了服务谁"
★ 心智模型：餐厅革命
  BIO   ：每桌一个专职服务员，客人不点菜服务员干站着（阻塞）
  NIO   ：一个服务员看全场，【只有举手的桌子才走过去】
          selector.select() = "等任何一张桌子举手"（这唯一的一觉值得睡）
          selectedKeys()    = "此刻举手桌子的名单"
          注册 OP_READ/OP_ACCEPT = "告诉领班，这张桌子我关心 XX 事件"

一个 selector 线程可挂几万通道 —— C10K 的正解
（Redis 单线程、Netty 的 EventLoop、Nginx worker 全是此模型）
一句话回答

NIO 三大件？——Buffer：带 position/limit/capacity 指针的缓冲区（flip 切读写模式）；Channel：双向通道，可配非阻塞（read 没数据返回 0 而不是睡）；Selector：多路复用器——通道注册感兴趣的的事件，select() 阻塞到"有事件发生"，一个线程轮询处理所有就绪通道。三者合体 = 一个线程管一万连接。

1
追问：selector.select() 也是阻塞，那和 BIO 的 read 阻塞有什么区别？
睡的对象不同：BIO 是"每个线程为自己那个连接睡"（1 万连接 = 1 万个睡着的线程）；NIO 是"一个线程为所有连接的事件睡"（睡一次，醒了就有一批活干）。前者线程数 ∝ 连接数，后者线程数 ≈ CPU 核数。本质：把 N 个"等具体数据"的睡眠合并成 1 个"等任意事件"的睡眠——这就是"多路复用"四个字的字面意思。
2
追问：selectedKeys 处理完为什么要 remove？
selectedKeys 是"已就绪集合"，selector 不会自动清理——不 remove，下一轮 while 还会看到它，同一事件被重复处理（数据早被读走了，read 返回 0，空转+逻辑错乱）。这是手写 NIO 的第一大坑，也是"为什么要用 Netty"的最有力论据（它把这些细节全包了）。
3
追问：NIO 一定比 BIO 快吗？什么时候 BIO 反而好？
不一定。NIO 的优势只在连接多且空闲多的场景（长连接、消息推送、IM）；连接少而忙碌（每连接持续大流量读写，如内网服务间调用），BIO 的"一连接一线程+阻塞"反而更简单高效（没有 select 轮询/事件分发的开销，内核直接唤醒对应线程）。Tomcat 至今保留 BIO（老版本）和 NIO 两种 Connector 就是这个原因——模型没有绝对优劣，只有场景匹配。

多路复用进化史：select → poll → epoll 区分度

Selector 是 Java 的封装，底下操作系统提供的才是本体。面试问"NIO 原理"或"Netty/Redis 为什么快"，最后一公里都在这三个系统调用上：

10.1 三代系统调用

【第一代 select（1983）】
  fd_set 传入【关注名单】，内核遍历所有 fd 找就绪的，拷回结果
  两个致命伤：① 名单上限 FD_SETSIZE=1024（编译期定死）
            ② 每次调用【全量拷贝 + 全量遍历】，O(n)，n=1万时每次都要扫1万个

【第二代 poll（1997）】
  用链表代替定长数组 → 1024 上限解除
  但【每次全量拷贝 + 全量遍历】照旧 —— O(n) 没变，治标不治本

【第三代 epoll（Linux 2.6, 2003）】三个新招：
  ① epoll_create：内核里建一张【常驻注册表】（红黑树）—— 注册一次，不再每次传名单
  ② epoll_ctl：增删改关注项 —— 拷贝只在注册时发生一次
  ③ epoll_wait：只拿【就绪链表】—— 就绪的 fd 由回调机制主动挂上链表，
     wait 返回的就是"已筛好的结果"，O(就绪数) 而非 O(总数)

★ select 是"每次考试全班挨个问一遍谁交卷了"
  epoll 是"交卷的学生自己把卷子放到收件篮，老师只看篮子"

10.2 epoll 为什么快：把 O(n) 干掉

维度select / pollepoll
fd 上限1024 / 无硬限无（受内存）
每次调用全量 fd 拷进内核 + 内核遍历 + 结果拷回注册一次常驻内核；wait 只取就绪链表
复杂度O(总 fd 数)O(就绪 fd 数)
万连接场景每次扫 1 万个，其中 100 个就绪直接拿到那 100 个
触发方式水平触发（LT）LT / 边缘触发（ET）可选
水平触发 LT（Level-Triggered）vs 边缘触发 ET（Edge-Triggered）：
  LT：只要缓冲区【还有】数据没读完，每次 epoll_wait 都继续报告你
      —— 保险，read 少读点也没事（下次还会叫你）
  ET：只在状态【变化】那一刻（无数据→有数据的边沿）报告一次
      —— 这次不读完，下次没人叫你了（数据滞留）
      所以 ET 必须"循环 read 到 EWOULDBLOCK 为止"（配非阻塞 fd）
  Netty 默认 LT（Java 层 epoll 也只暴露 LT）；Nginx/Redis 用 ET
  
★ 面试串联（说这个 = 懂生态）：
  Redis 6.0 前"单线程为什么快"：epoll + 内存操作 + 无锁（单线程免上下文切换）
  Netty 为什么快：epoll(LT) + EventLoop(固定线程绑核) + 零拷贝 + ByteBuf 池化
  Kafka/Netty 的"零拷贝" → 下一节
一句话回答

epoll 比 select 强在哪？——select 每次调用全量拷贝名单+内核遍历全部 fd，O(n) 且上限 1024；epoll 把关注列表常驻内核（红黑树注册一次），就绪事件由回调挂上就绪链表，wait 只取结果，O(就绪数)。触发模式 LT（有数据就报）vs ET（只在变化沿报一次，必须读到 EWOULDBLOCK）。

Java Selector 底层用的什么？跨平台怎么办？加分

取决于操作系统，JVM 自动选择：Linux 2.6+ 用 epoll（默认 EPollSelectorProvider）；macOS/BSD 用 kqueue（epoll 的 BSD 系表亲）；Windows 用 select 家族（IOCP 属 AIO 路线）。所以 Java 的 Selector 是"多路复用"的跨平台抽象——selector.select() 一句代码，在 Linux 上就是 epoll_wait。补充加分点：JDK 还提供 EPollSelectorProvider 显式指定，以及 Linux 上 JDK 17 引入了对 io_uring 的实验支持（下一代异步框架的地基）——说到 io_uring 说明你在跟进技术演进。

Python 的 selectors/asyncio 和这套什么关系？Python 对比

一层窗户纸：selectors 模块就是 Python 版的 Selector 抽象（DefaultSelector 在 Linux 上自动选 EpollSelector，api 和 Java Selector 几乎同构：register/select）；asyncio 的 SelectorEventLoop 就是"selectors + 回调 + 协程语法糖"的组合——你写的每个 await，底层就是"把协程挂到 selector 的就绪回调上"。所以本节学完，你反过来完全看懂了 asyncio 的引擎盖下面。区别在编程模型：Java NIO 给你的是裸事件循环（自己写 while+dispatch），Python 用协程把 dispatch 生成器化了，Java 侧对应物是 Netty 的回调/或 JDK 21 虚拟线程（用同步写法享受异步模型）。

零拷贝：Kafka 吞吐的地基 高频

11.1 先看账单：传统读文件发网络有多贵

场景：把磁盘上 100MB 文件通过 Socket 发出去（文件下载/消息投递，Kafka 每天在做亿次的动作）。传统写法：

Traditional.java四步拷贝 + 四次切换
byte[] buf = new byte[4096];
while (in.read(buf) != -1) {
    out.write(buf);    // 看似两行，底层是 4 次拷贝 + 4 次态切换
}
传统路径（DMA 拷 2 次 + CPU 拷 2 次）：

  磁盘 ──DMA①──► 内核页缓存（Page Cache）──CPU②──► 用户缓冲区(buf)
                                                          │
  Socket 缓冲区 ◄──CPU③────────────────────── 用户缓冲区 ──┘
       │
  网卡 ◄──DMA④── Socket 缓冲区

  系统调用：read（用户↔内核切换 ×2）+ write（×2）= 4 次态切换
  CPU 参与了 ②③ 两次纯搬运 —— 数据在内核/用户间来回倒腾，
  而 Java 代码甚至【根本没碰这份数据的内容】（只是转发）！

11.2 两级优化：mmap 与 sendfile

【优化一 mmap（内存映射）】：把用户态的一块地址【直接映射】到页缓存
  磁盘 ──DMA──► 页缓存 ◄──【映射，同一份内存】──► 用户空间
  拷贝 4→3、切换 4→4（省了一次 CPU 拷贝）
  用户代码像访问内存数组一样访问文件内容（MappedByteBuffer 就是它）
  适合：需要【读取并处理】文件内容（要看到数据）

【优化二 sendfile（Java 的 transferTo/transferFrom）】：连用户态都不路过
  磁盘 ──DMA──► 页缓存 ──DMA──► 网卡   （CPU 零参与，仅 2 次切换！）
  ★ 这才是"零拷贝"名字的本义：CPU 拷贝次数 = 0
  适合：纯转发（文件 → 网络，全程不需要看内容）——Kafka 的场景

一句话分工：
  要看数据 → mmap（少拷一次）
  只转发  → sendfile（CPU 完全不搬运）
（现代网卡还支持 SG-DMA，页缓存地址直接给网卡，连最后一次都能省）
ZeroCopy.javaJava 里的入口
// FileChannel.transferTo：底层在 Linux 自动走 sendfile
try (FileChannel file = FileChannel.open(path, StandardOpenOption.READ);
     SocketChannel socket = ...) {
    file.transferTo(0, file.size(), socket);   // 100MB 转发：CPU 拷贝 0 次
}

// MappedByteBuffer：mmap 的封装
MappedByteBuffer mbb = file.map(FileChannel.MapMode.READ_ONLY, 0, file.size());
byte b = mbb.get(1024);    // 直接按内存访问，缺页时才真正读盘（OS 惰性加载）

11.3 面试串联：谁在用

系统用哪个为什么
Kafkasendfile（broker 端消息投递）消息本来就是"落盘后原样转发给消费者"——纯转发场景，零拷贝 + 顺序写 + 批量 = 百万级吞吐三板斧之一
RocketMQmmap（CommitLog 刷盘）写消息要对内容做处理（校验/索引），需要"看见"数据，用映射少拷一次

⚠ 概念纠偏（说错就露怯）

①"零拷贝"指 CPU 拷贝次数为零，不是"不拷贝"（DMA 硬件搬运照常有）；② Netty 语境的"零拷贝"是应用层概念（ByteBuf 逻辑合并、避免堆内外互拷），与 OS 的 sendfile 是两码事——被追问"Netty 零拷贝"时先分层再作答；③ mmap 不是万能药：映射的页缓存在 OS 手里（缺页、刷盘时机不受你控），断电场景可靠性要靠 fsync 兜底（RocketMQ 同步刷盘的争论点）。

一句话回答

零拷贝？——传统"读文件发网络"= 4 次拷贝（2 DMA + 2 CPU）+ 4 次态切换，纯转发场景 CPU 白搬两次；sendfile（transferTo）让数据不离开内核：磁盘→页缓存→网卡，CPU 零参与（Kafka/Nginx）；mmap 把页缓存映射到用户态，省一次拷贝、适合要看内容的场景（RocketMQ）。

异常体系
  • Throwable → Error（JVM 级，别 catch）+ Exception

BIO → NIO

  • select：1024 上限 + 每次全量拷贝遍历 O(n)

  • 传统 4 拷 4 切；sendfile = CPU 零参与（Kafka/Nginx，纯转发）
