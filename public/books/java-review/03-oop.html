三大特性总览

⬅ 前置依赖模块 1：对象在堆、引用在栈；new 的五步过程（第 5 步"执行构造器"正是本模块要展开的）。模块 2：final 与 static。
➡ 后续去向equals/hashCode 分桶 → 模块 4 HashMap；接口 → 模块 7 函数式接口；匿名内部类 → 模块 7 Lambda 的前身。
特性一句话实现手段面试问法
封装隐藏内部细节，只暴露必要操作private 字段 + public getter/setter好处是什么？（降低耦合、可校验、改实现不影响外部）
继承子类复用父类的字段和方法extends，单继承构造器/初始化顺序、super 语义
多态同一个调用，运行时表现不同行为父类引用 + 子类对象 + 方法重写动态绑定原理、字段有没有多态（没有！）
多态的最小完整示例Java
class Animal {
    public void sound() { System.out.println("某种叫声"); }
}
class Dog extends Animal {
    @Override
    public void sound() { System.out.println("汪汪"); }   // 重写
}
class Cat extends Animal {
    @Override
    public void sound() { System.out.println("喵喵"); }
}

Animal a = new Dog();    // 父类引用 指向 子类对象（向上转型，自动）
a.sound();               // "汪汪" —— 编译时看 Animal 有没有 sound()，
                         //            运行时执行的是 Dog 的实现（动态绑定）

// 三要素缺一不可：继承/实现 + 重写 + 父类引用指向子类对象
🐍 Python 对比

Python 的多态是鸭子类型："会 sound 就能调用"，不需要继承同一父类。Java 是名义类型：必须先"是"Animal 才能用 Animal 的引用接住。Python 支持多继承（MRO 解决冲突），Java 单继承 + 多接口实现——接口就是 Java 对"多继承"需求的官方答案。

类初始化顺序全链路

2.1 结论模板（背熟）超高频★★★

含继承链的完整顺序结构
new Child() 触发的完整初始化链：

 ① 父类静态变量 + 父类静态代码块   ┐ 按源码书写顺序执行
 ② 子类静态变量 + 子类静态代码块   ┘ 【类加载时执行，整个进程只一次】

 ③ 父类实例变量赋值 + 父类构造代码块 ┐ 按源码书写顺序执行
 ④ 父类构造方法体                    ┘【每次 new 都执行】

 ⑤ 子类实例变量赋值 + 子类构造代码块 ┐
 ⑥ 子类构造方法体                    ┘

口诀：静态优先、父类优先、变量/代码块 先于 构造器
本质：保证"父类完全初始化完，才轮到子类"——子类可能用到父类的字段

2.2 经典真题逐行推演超高频易错★★★

先自己算输出，再看注释Java
class Parent {
    static { System.out.println("1 父类静态块"); }
    { System.out.println("3 父类构造块"); }
    Parent() { System.out.println("4 父类构造器"); }
}
class Child extends Parent {
    static { System.out.println("2 子类静态块"); }
    { System.out.println("5 子类构造块"); }
    Child() { System.out.println("6 子类构造器"); }
}

new Child();
System.out.println("---第二次 new---");
new Child();

// 输出：
// 1 父类静态块     ← 类加载阶段，只一次
// 2 子类静态块     ← 类加载阶段，只一次
// 3 父类构造块
// 4 父类构造器
// 5 子类构造块
// 6 子类构造器
// ---第二次 new---
// 3 父类构造块     ← 静态的部分不再执行！
// 4 父类构造器
// 5 子类构造块
// 6 子类构造器

2.3 两个高频变体陷阱难点★★★

① 构造器里调用被重写的方法Java
class Parent {
    Parent() {
        show();                    // 父类构造器调用被子类重写的方法 → 多态！
    }
    void show() { System.out.println("Parent.show"); }
}
class Child extends Parent {
    int num = 42;                  // ⑤ 实例变量赋值发生在父类构造器【之后】
    @Override
    void show() { System.out.println("Child.show, num=" + num); }
}
new Child();
// 输出：Child.show, num=0   ← 不是 42！
// 原因：执行到 show() 时（第④步），子类的实例变量还没赋值（第⑤步才赋），
//       num 是堆零值初始化的 0（回看模块 1 的 new 过程：③ 零值 → ⑤ 构造器）
// 启示：构造器里永远别调用可被重写的方法（Effective Java 第 19 条）
② main 所在类自身的初始化Java
public class Test {
    static int x = print("静态变量", 1);      // 类初始化时执行
    public static void main(String[] args) {
        System.out.println("main 执行");
    }
    static int print(String tag, int v) { System.out.println(tag); return v; }
}
// 输出顺序：静态变量 → main 执行
// main 是静态方法，调用前必须先完成本类的类初始化（<clinit>）
// 这就是"main 之前还能跑代码"的原因：静态变量/静态块都在 main 前执行
💡 <clinit> 与 <init>（衔接模块 5 类加载）

编译器把"静态变量赋值 + 静态块"收集成 <clinit>（类初始化方法，首次使用类时执行一次，JVM 保证线程安全——这是"静态内部类单例"线程安全的原理）；把"实例变量赋值 + 构造块 + 构造器"收集成 <init>（每次 new 执行）。记住这两个名字，模块 5 类加载会回收此伏笔。

03

this 与 super

3.1 this：当前对象的引用★★

this 的四种用法Java
class User {
    private String name;
    User() { this("默认名"); }          // ① 调用本类其他构造器，必须在第一行
    User(String name) {
        this.name = name;               // ② 区分成员变量与参数（最常见）
    }
    User self() { return this; }        // ③ 返回当前对象（链式调用：builder 模式的根基）
    void hello() {
        System.out.println(this.name);  // ④ this.成员 等价直接写 name（隐式 this）
    }
}
// 衔接模块 1：实例方法的局部变量表第 0 号槽就是 this ——
// this 存的是当前对象的【地址】，所以能在方法内拿到对象本身

3.2 super：父类部分的引用★★

super 的三种用法 + 隐式规则Java
class Parent { Parent(int x) {} }
class Child extends Parent {
    Child() {
        super(1);          // ① 调用父类构造器，必须在第一行 → this(...) 与 super(...) 互斥
    }
    void show() {
        super.toString();  // ② 调用父类被重写的方法（往上跳一层）
        // super.x         // ③ 访问被子类遮蔽（shadowing）的父类字段
    }
}

// ⚠ 隐式规则：构造器第一行不写任何 this/super 调用时，编译器自动补 super()（无参）
// 推论 1：父类只有带参构造器时，子类构造器必须显式 super(xxx)，否则编译错误
// 推论 2：Object 的构造器是这条调用链的终点（所有类的最终父类）
⚠ 工程事故高发点

自定义类一旦写了带参构造器，无参构造器就消失了——而 MyBatis、Jackson、Spring 反射创建对象默认调无参构造器，直接炸出 NoSuchMethodException。规矩：实体类要么全不写构造器，要么把无参构造器一起写上。

04

重载 vs 重写（详细版）

4.1 先立地基：方法签名难点★★

方法签名 = 方法名 + 参数类型列表（按顺序）。注意不含返回值——为什么？如果只靠返回值区分两个方法：

返回值为什么不能参与签名Java
int get()   { ... }
String get() { ... }     // 假设允许（实际编译错误）

// 调用方只写 get(); 不接返回值时 —— 编译器无法确定你调的是哪一个！
// JVM 方法表里方法用"类名+方法名+参数描述符"唯一定位，返回值也在描述符里，
// 但【编译期的重载判定】必须保证调用点无歧义，所以语言层面签名不含返回值

4.2 核心对比表超高频★★★

重载 Overload重写 Override
发生范围同一个类中（或继承来的方法与本类新方法）父子类之间
参数列表必须不同（个数/类型/顺序）必须相同
返回类型随意（仅返回值不同 ≠ 重载，是编译错误）相同 或协变（子类返回父类返回类型的子类型，如 Object → String）
访问修饰符随意只能放大不能缩小：protected → public ✅，public → protected ❌
抛出异常随意只能缩小：不能抛出比父类更宽的受检异常（非受检异常随意）
绑定时机编译期静态绑定（按声明类型选方法）运行期动态绑定（按实际对象类型选实现）
多态性与多态无关（静态多态/编译时多态）多态的核心（动态多态）
一张代码看清两者Java
class Calculator {
    // ---- 重载：同类、同名、参数不同 ----
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
    int add(int a, int b, int c) { return a + b + c; }
}
class SuperCalc extends Calculator {
    // ---- 重写：父子、同名、参数相同 ----
    @Override                          // 注解：让编译器校验"你真的在重写"
    int add(int a, int b) { return a + b + 1; }
    // 若手滑写成 add(int a, int b, int c) —— 参数不同，是重载不是重写！
    // 加了 @Override 编译器立刻报错 → 这就是它存在的意义
}

4.3 重写的边界：哪些方法重写不了易错高频★★★

static / final / privateJava
class P {
    static void s() {}
    final void f() {}
    private void p() {}
    void n() {}
}
class C extends P {
    static void s() {}        // ⚠ 不是重写，是【隐藏 hiding】！
                              // 静态方法按"声明类型"静态绑定：
                              // P p = new C(); p.s(); 调的是 P 的 s()
                              // 加 @Override 会直接编译错误——编译器明确告诉你这不是重写

    // final void f() {}      // ❌ 编译错误：final 方法禁止重写（模块 2 讲过）

    private void p() {}       // ⚠ 父类 private 对子类不可见，这只是个"恰好同名的新方法"
                              // 同样不是重写（多态对它无效）

    @Override void n() {}     // ✅ 这才是真重写
}
一句话回答

重载是同类中"同名不同参"的多个方法，编译期按参数静态选定；重写是子类对父类"同名同参"方法重新实现，运行期按对象实际类型动态选定。重写受五条规则约束：参数相同、返回值协变、权限只放大、受检异常只缩小、非 static/final/private。

追问：重载方法的匹配优先级？（byte 实参依次匹配什么？）

编译器按"最具体"原则匹配：① 精确匹配 → ② 自动拓宽（byte→short→int→long→float→double）→ ③ 装箱（int→Integer）→ ④ 变长参数（int...）。例：f(byte) 存在就精确命中；不存在则找 f(int)，再不行 f(long)…装箱和变长是最后手段。这也解释了模块 2 的"二元数值提升"——运算符就是按这套规则找"运算方法"的。

05

多态与动态绑定

5.1 方法看实际类型，字段看声明类型高频易错★★★

字段没有多态！Java
class Parent { int x = 1; int get() { return 1; } }
class Child extends Parent { int x = 2; int get() { return 2; } }

Parent p = new Child();
p.get();   // 2  ← 方法：运行期看实际类型 Child（动态绑定）
p.x;       // 1  ← 字段：编译期看声明类型 Parent（字段访问不发生动态绑定！）

// 为什么：字段访问在编译期就编译成"直接取偏移量"指令（快），
// 方法调用走方法表查找（慢一点但支持多态）
// 这就是"字段遮蔽(shadowing)"而非"字段重写"—— Java 根本没有字段重写的概念

5.2 动态绑定的原理：方法表难点★★

invokevirtual 的查找过程结构
方法表（vtable）示意 —— 每个类一张，子类表复制父类表后覆盖被重写的槽位：

Animal 的方法表            Dog 的方法表（继承 + 重写）
┌─────────────────┐       ┌─────────────────┐
│ Object.hashCode │       │ Object.hashCode │  ← 没动
│ Object.equals   │       │ Object.equals   │
│ Animal.sound    │       │ Dog.sound       │  ← 重写：槽位被替换！
│ Animal.eat      │       │ Animal.eat      │  ← 继承：原样复制
└─────────────────┘       │ Dog.fetch       │  ← 新方法：追加在尾部
                          └─────────────────┘

Animal a = new Dog();
a.sound();
→ 字节码 invokevirtual Animal.sound
→ 运行时发现 a 的实际类型是 Dog → 查 Dog 的方法表 → sound 槽位里是 Dog.sound → 执行

关键：重写方法在表中【占据父类同签名方法的槽位】，
     所以"父类引用调用"总能命中"子类的实现" —— 这就是多态的实现机制
衔接模块 1：对象头里的类型指针 → 指向方法区中 Dog 的类信息 → 类信息里挂着方法表

5.3 向上/向下转型易错★★

转型规则Java
Animal a = new Dog();        // 向上转型：自动、永远安全（Dog 必"是"Animal）
Dog d = (Dog) a;             // 向下转型：必须强转，运行时校验实际类型
Cat c = (Cat) a;             // ❌ 编译通过，运行时 ClassCastException（a 实际是 Dog）

// 安全姿势：转之前用 instanceof 先验（模块 2 讲过 JDK16 模式匹配）
if (a instanceof Dog dog) { dog.fetch(); }
06

接口 vs 抽象类

6.1 对比表超高频★★★

抽象类 abstract class接口 interface
语义is-a：本质是什么（Dog is an Animal）can-do：能做什么（Comparable = 可比较）
继承单继承（一个类只能 extends 一个）多实现（一个类可 implements 多个）
成员变量任意（可有实例状态）只能是 public static final 常量
方法抽象 + 具体（普通方法）皆可JDK7：全抽象；JDK8+：default / static 方法；JDK9+：private 方法
构造器有（供子类 super 调用，不能自身 new）无
典型用途模板方法模式：骨架复用（AbstractList）能力契约/解耦（List、Runnable、Comparable）

6.2 JDK 8 的 default 方法：为什么引入高频★★★

default 与 static 方法Java
interface Log {
    void info(String msg);                       // 抽象方法：实现类必须实现

    default void error(String msg) {             // default：给接口一个【默认实现】
        info("[ERROR] " + msg);                  // 实现类不重写也能用，想改也行
    }
    static Log console() {                       // static：接口的静态工厂
        return msg -> System.out.println(msg);   // （返回 lambda，模块 7 预告）
    }
}

// 为什么引入 default？—— 为了 Lambda 改造集合 API：
// 想给 Collection 加个 forEach 方法，如果是抽象方法，
// 全世界所有自定义集合类一夜之间全编译失败（接口只能加不能改的魔咒）
// default 让"接口进化"不破坏已有实现 → 这是语言兼容性的经典设计
🧩 加分点：菱形冲突

两个接口有同名 default 方法，类同时实现两者 → 编译错误，必须显式重写，并可用 InterfaceA.super.method() 指定调用某个接口的版本。追问"接口为什么不能代替抽象类"：接口无实例状态、无构造器，表达"行为"；抽象类表达"模板 + 状态"，二者是配合关系不是替代关系。

07

equals 与 hashCode：分桶图讲透

📌 衔接模块 1

模块 1 讲过：equals 默认就是 ==（比地址），String/Integer 重写后比内容。本节回答两个遗留问题：① 为什么重写 equals 必须同时重写 hashCode？② 只重写一个分别会发生什么？答案全在哈希容器的工作方式里。

7.1 前置：HashSet/HashMap 是怎么存东西的超高频★★★

哈希容器的两层结构结构
HashSet 底层 = HashMap（元素当 key，value 是固定占位对象）
HashMap 底层 = 数组 + 链表/红黑树（模块 4 详讲）

                table 数组（桶 bucket）
              ┌────┬────┬────┬────┬────┬────┐
              │ 0  │ 1  │ 2  │ 3  │ 4  │... │
              └──┬─┴────┴────┴─┬──┴────┴────┘
                 │             │
                 ↓             ↓
             ┌──────┐      ┌──────┐
             │ 元素A │      │ 元素C │
             └──┬───┘      └──┬───┘      一个桶挂一条链表
                ↓             ↓
             ┌──────┐      ┌──────┐
             │ 元素B │      │ 元素D │
             └──────┘      └──────┘

存/查一个元素的两步：
  第一步【分桶】：hash & (n-1) 算出落在哪个桶 → 用 hashCode！
  第二步【桶内精确比对】：桶内链表逐个 equals → 用 equals！

设计动机：hash 算得快但会冲突（只能"缩小范围"），
         equals 精确但慢（不能全表扫）—— 两步走 = 快 + 准

7.2 官方约定（JDK 文档原文）高频★★★

  1. equals 相等的两个对象，hashCode 必须相等 ← 违反它，哈希容器直接逻辑崩坏
  2. hashCode 相等的两个对象，equals 不要求相等（这叫哈希冲突，合法，只影响性能）
  3. equals 满足：自反 / 对称 / 传递 / 一致 / 非空（x.equals(null) == false）

7.3 只重写 equals，不重写 hashCode → 容器"失忆"超高频难点★★★

事故现场 + 分桶图Java
class Bad {
    String name;
    Bad(String name) { this.name = name; }
    @Override
    public boolean equals(Object o) {            // 只重写了 equals
        return o instanceof Bad b && b.name.equals(name);
    }
    // hashCode 没重写 → 用 Object 默认实现：
    // "把对象地址换算成一个整数" —— 两个不同地址的对象，哈希值几乎必然不同！
}

Set<Bad> set = new HashSet<>();
set.add(new Bad("a"));                    // 对象1：地址哈希(如 1024) → 落进桶 X
set.contains(new Bad("a"));               // 对象2：地址哈希(如 3777) → 落进桶 Y
// 结果 false！内容相等的对象"失联"了

// 分桶图（假设 table 16 个桶，hash%16 简化）：
//   1024 % 16 = 0                       3777 % 16 = 1
//   ┌──0──┐                             ┌──1──┐
//   │Bad(a)│ ← 对象1在这                  │Bad(a)│ ← 对象2被分到这
//   └──────┘                             └──────┘
// contains 的执行路径：hash(对象2) → 定位到 1 号桶 → 桶里没有元素，
//                     【直接返回 false】—— 根本走不到 equals 那一步！
//
// 一句话：equals 说"我们相等"，hashCode 却说"我们住不同小区"——
//         查找只按门牌号走，永远碰不上面

7.4 只重写 hashCode，不重写 equals → 去重失效/性能塌方难点★★★

两种坏法Java
class Bad2 {
    String name;
    Bad2(String name) { this.name = name; }
    @Override
    public int hashCode() { return name.hashCode(); }   // 只重写了 hashCode
    // equals 没重写 → 用 Object 默认 = 比地址（==）
}

Set<Bad2> set = new HashSet<>();
set.add(new Bad2("a"));
set.add(new Bad2("a"));     // 两次 add 都成功！set.size() == 2
// 分桶图：两个对象 hashCode 相同（都按 name 算）→ 落进【同一个桶】✅第一步没问题
//   ┌───── 桶 5 ─────┐
//   │ Bad2("a") → Bad2("a") │   ← 链表上挂了两个！
//   └────────────────┘
// 第二步坏在：桶内逐个 equals 判重 → 默认 equals 比地址 → 两个不同地址
//            → 判定"不重复" → 照样插入 → Set 去重功能报废
//
// 更极端的面试变体：hashCode 写死 return 1;
// → 所有元素挤进同一个桶 → HashSet 退化成"单链表" → 查找 O(n)
// → 编译不报错、逻辑"合法"（约定只要求 hashCode 一致），纯性能灾难

7.5 正确姿势：equals 与 hashCode 成对重写高频★★★

标准模板（IDEA 生成，看懂每一步）Java
class User {
    String name;
    int age;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                   // ① 快捷路径：同一对象直接 true
        if (o == null || getClass() != o.getClass())  // ② 非空 + 精确同类型
            return false;                             //   （getClass 严格；instanceof 允许子类，二选一）
        User user = (User) o;
        return age == user.age                        // ③ 基本类型 ==，引用类型 Objects.equals
            && Objects.equals(name, user.name);        //   （防 name 为 null 抛 NPE）
    }

    @Override
    public int hashCode() {                           // ④ 参与运算的字段必须与 equals 一致！
        return Objects.hash(name, age);               //    equals 用了 name+age，这里也用 name+age
    }                                                 //    少算一个字段 → 7.3 的桶错位；多算 → 冲突变多
}

// Objects.hash 内部：31*x + y 的组合哈希（和 String 同款思路，模块 2 讲过 31）
// 偷懒可用 lombok @EqualsAndHashCode / record 类（JDK16+ 自动生成 equals+hashCode）
一句话回答

哈希容器先按 hashCode 分桶、再在桶内用 equals 精确比对。equals 相等但 hashCode 不同 → 相等对象落不同桶，查找失灵；hashCode 相同但 equals 是默认地址比较 → 桶对了但判重失效，Set 报废。所以两者必须成对、基于同一组字段重写。

🐍 Python 对比

Python 的 __eq__ / __hash__ 同理：只定义 __eq__ 不定义 __hash__，对象直接不可哈希（进 set 报 TypeError）——Python 用"禁用"防止你犯错，Java 用"约定"靠自觉。dataclass 的 @dataclass(eq=True) 自动成对生成，等价于 record。

1
重写 equals 为什么必须重写 hashCode？
约定要求 equals 相等 → hashCode 相等；哈希容器按 hashCode 分桶查找，违反后"相等"对象落不同桶，contains/remove/去重全部失灵。
2
那 hashCode 相等、equals 不等呢？
这是哈希冲突，合法。冲突对象在同一桶内用链表/红黑树挂着，只影响性能不影响正确性。
3
hashCode 全返回 1 行不行？
编译和运行都合法，但所有元素挤一个桶，HashSet/HashMap 退化为链表 O(n)——"正确但灾难"，面试用来考你对两层结构的理解。
4
可变对象做 HashMap 的 key 有什么风险？
put 后修改参与 hashCode 的字段 → hash 变了 → 定位到旧桶找不到 → 内存泄漏式"失踪"。规矩：key 用 String/Integer/record 等不可变对象。

内部类四兄弟

8.1 全景对照高频★★★

类型写法位置持有外部引用？能否 static 成员典型用途
成员内部类类中、方法外是（Outer.this）不能集合迭代器（Iterator 与集合绑定）

8.2 静态内部类：为什么"推荐默认用它"★★

两个经典应用Java
// ① 静态内部类单例（线程安全 + 懒加载，模块 2 埋的 <clinit> 伏笔兑现）
class Singleton {
    private Singleton() {}
    private static class Holder {                    // 外部类加载时 Holder 不加载
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton get() { return Holder.INSTANCE; }
    // 第一次调 get() 才触发 Holder 类加载 → JVM 保证 <clinit> 线程安全
    // → 懒加载 + 线程安全，不需要 synchronized，教科书级方案
}

// ② Builder 模式（避免多参数构造器爆炸）
class User {
    private final String name; private final int age;
    private User(Builder b) { name = b.name; age = b.age; }
    public static class Builder {                   // static：Builder 不需要外部实例
        private String name; private int age;
        public Builder name(String n) { this.name = n; return this; }
        public Builder age(int a) { this.age = a; return this; }
        public User build() { return new User(this); }
    }
}
User u = new User.Builder().name("Tom").age(18).build();   // 链式调用（this 的用法）

8.3 局部变量捕获：为什么必须 final难点★★★

effectively final 的内存原因Java
void method() {
    int count = 0;                                  // 栈上的局部变量
    Runnable r = new Runnable() {                   // 匿名内部类对象【在堆里】
        public void run() {
            // System.out.println(count++);         // ❌ 编译错误：count 必须是 final
            System.out.println(count);              // ✅ 读可以
        }
    };
    r.run();
    // 原因（用模块 1 的图想）：
    //   count 在 method 的栈帧里，方法返回栈帧销毁，count 就没了
    //   但匿名类对象（堆）可能活得比 method 久（被别处持有）
    //   → 编译器把 count【拷贝】一份存进匿名类对象（合成字段）
    //   → 如果允许 count++，改的是自己的拷贝，外面的 count 不动 → 数据不一致
    //   → Java 直接禁止：捕获的变量必须只赋值一次（final 或事实 final）
    // 想在回调里修改值？用数组/AtomicInteger/长度 1 的包装（传引用而非值）
}
🐍 Python 对比

Python 闭包捕获的是变量的引用（cell）而非值的拷贝，所以能在闭包里读写外层变量（改写需 nonlocal 声明）。Java 匿名类/Lambda 捕获的是值拷贝，故要求 effectively final——两种设计，Python 更灵活，Java 更防错。

组合 vs 继承

9.1 is-a 与 has-a高频★★

组合优先于继承Java
// ❌ 继承误用：不是 is-a 关系，只是想复用代码
class ArrayList<E> { ... }
class MyStack<E> extends ArrayList<E> {    // Stack 拿到了 ArrayList 的所有公开方法
    // add(int, E) / remove(int) 这些"破坏栈结构"的方法也被继承暴露了！
    // 继承破坏封装：父类实现变动直接砸进子类
}

// ✅ 组合：把 ArrayList 当零件
class MyStack<E> {
    private final ArrayList<E> list = new ArrayList<>();   // has-a
    public void push(E e) { list.add(e); }
    public E pop() { return list.remove(list.size() - 1); }
    public E peek() { return list.get(list.size() - 1); }
    // 只暴露栈该有的操作，内部用什么都无所谓（哪天换 LinkedList 也不影响调用方）
}

// 判定口诀：能说通 "B 是一种 A" → 继承；"B 有一个 A / B 用 A 实现" → 组合
// Effective Java 第 18 条：复合优先于继承（非 final 的具体类尤其如此）
追问：什么时候必须用继承？

当你需要多态——用父类型引用统一接收不同子类对象时，必须有继承/实现关系（模板方法模式：父类定骨架 abstract 步骤、子类填实现，也是合理的继承）。判断标准不是"想复用代码"（该用组合），而是"需要在父类型的变量里装下子类对象"。

10

高频面试题速查（自测清单）

1. 父子类初始化顺序？静态块执行几次？

父静态→子静态（类加载，仅一次）→ 父实例变量/构造块→父构造器→子实例变量/构造块→子构造器（每次 new）。第二次 new 时静态部分不再执行。

2. 构造器里调用被子类重写的方法会发生什么？

发生多态，执行子类实现——但此时子类实例变量尚未赋值（还是零值），子类方法读到的是默认值（num=0 而非 42）。启示：构造器不要调用可重写方法。同理也不要在构造器里启动线程/注册回调。

3. 重载和重写的区别？

重载：同类、同名、参数必须不同，编译期静态绑定，与多态无关；重写：父子类、同名同参，运行期动态绑定，受"返回值协变、权限只放大、受检异常只缩小"约束。static 方法"重写"是隐藏，private/final 不能被重写。

4. 方法签名包含返回值吗？

不包含。签名 = 方法名 + 参数类型列表。只靠返回值无法区分调用点（调用方可以不接返回值），所以仅返回值不同不构成重载，编译错误。

5. 多态三要素？字段有多态吗？

三要素：继承/实现 + 重写 + 父类引用指向子类对象。方法调用看实际类型（动态绑定/方法表槽位替换）；字段访问看声明类型（编译期定死偏移量）——字段没有多态，子类同名字段只是遮蔽。

6. 接口和抽象类的区别？什么时候用哪个？

接口：can-do 契约，无状态无构造器，多实现，JDK8+ 有 default/static 方法；抽象类：is-a 模板，有状态有构造器，单继承。要定义"行为能力/解耦"用接口；要在多个密切相关的类间"共享代码和状态"用抽象类。两者可配合（AbstractList implements List）。

7. 为什么重写 equals 必须重写 hashCode？只重写一个分别什么后果？

哈希容器两步走：hashCode 分桶 + equals 桶内比对。只重写 equals：相等对象 hashCode 不同（默认地址哈希）落不同桶，contains/remove/去重失灵；只重写 hashCode：桶对了但 equals 比地址，判重失效（Set 里出现重复），若 hashCode 返回常量则全部挤一桶退化 O(n)。正确做法：两者基于同一组字段成对重写（Objects.hash）。

8. 为什么匿名类/Lambda 捕获的局部变量必须 final？

捕获的是值的拷贝（合成字段存进堆里的匿名类对象），栈帧销毁后局部变量没了。若允许修改，改的是拷贝本体，内外不一致——语言直接禁止。需要可变就用数组/Atomic 包装（本质是把"值"换成"引用"）。

9. 静态内部类单例为什么线程安全且懒加载？

外部类加载不触发 Holder 加载；首次 getInstance 才触发 Holder 类初始化，JVM 保证 <clinit>（静态变量赋值）只执行一次且线程安全——借 JVM 的类加载机制白嫖了懒加载 + 线程安全。

10. 组合和继承怎么选？

is-a 用继承，has-a/复用用组合。继承是强耦合（父类实现变化穿透子类、暴露不该有的方法），Effective Java：复合优先于继承。需要多态（父类型引用装子类对象）才必须继承。
