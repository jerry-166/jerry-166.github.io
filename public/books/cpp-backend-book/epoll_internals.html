epoll 内部存储结构与工作流程图解（Linux 内核 eventpoll）

一句话总览：一个 epoll 实例 = 一个 struct eventpoll，内部有三样核心东西：红黑树 rbr（管所有被监听的 fd）、就绪链表 rdllist（管已就绪的 fd）、等待队列 wq（管阻塞在 epoll_wait 的进程）。另外还有第四样容易漏的东西：每个被监听 socket 自己的等待队列 sk_sleep，上面挂着回调 ep_poll_callback —— 数据到达时靠它把事件"推"进 rdllist 并唤醒进程。

图 2 补充　睡在 wq 上的"进程"是谁？—— 是线程，不是 fd




fd 事件是"数据/对象"，它不会睡觉；会睡眠的是正在执行代码的线程（一条执行流）。你的线程调用 epoll_wait 进入内核，内核里用宏 current 指向它的 task_struct。没有事件时，内核对它做三件事：


    

  1. 把状态改成 TASK_INTERRUPTIBLE（可被唤醒的睡眠）；
    2. 

  2. 构造等待节点 wait，令 wait.private = current（节点里登记的是这个线程），挂进 ep->wq；
    3. 

  3. 调 schedule_timeout() 让出 CPU，调度器把它从"运行队列"拿走，CPU 去跑别的线程。
    4. 



唤醒路径反过来：wake_up(&ep->wq) 把节点里的线程状态改回 TASK_RUNNING、放回运行队列；调度器再次选中它时，它从 schedule_timeout() 的下一行内核代码接着跑（不是从头跑），最终从 epoll_wait 返回用户代码。所以 wq 是一张"睡着线程的名单"，不是 fd 名单。




等待队列上面挂着谁什么时候动


ep->wq睡着的线程（wait.private = current，即调用 epoll_wait 的执行流）无事件时线程睡入；wake_up 时唤醒


socket 的 sk_sleep回调节点 eppoll_entry（func = ep_poll_callback）epoll_ctl(ADD) 时注册；数据到达时被执行




独占（exclusive）：多个线程同时对同一 epfd 调 epoll_wait 时，名单上有多个线程；事件到来只唤醒一个等待者，避免"惊群"（一群线程都被唤醒、又只有一个能拿到事件）。

LT 水平触发（Level Triggered，默认）

    
    
      
  • 判据：只要 fd 当前仍然处于就绪状态（缓冲区里还有数据），就一直通知。
    • 
      
  • 内核动作（ep_send_events 末尾）：拷贝完本批后再 poll 一次，仍就绪 → list_add_tail() 把 epi 重新挂回 rdllist。
    • 
      
  • 所以你这次只读了 1 个字节，下次 epoll_wait 立即返回，直到数据被读空、poll 不再就绪，才停止挂回。
    • 
      
  • fd 可以是阻塞的；编程简单，不会漏数据。
    • 
    

  

  

    
ET 边缘触发（Edge Triggered，需 EPOLLET）

    
    
      
  • 判据：只在状态发生变化（新数据到达、回调被触发）时通知一次。
    • 
      
  • 内核动作：拷贝完本批后不挂回 rdllist；没有新的中断回调，就不会再出现。
    • 
      
  • 数据没有丢，还在 socket 接收缓冲区里；但你不再被通知，所以必须：fd 设为非阻塞 + while(read) 循环读到返回 EAGAIN，一次掏空。
    • 
      
  • 通知次数少、配合 EPOLLONESHOT 常用于高并发；写代码要求高。
    • 
    

  





纠正一个常见说法："ET 模式下没读完的数据就丢了" 是错的。丢掉的是"通知"，不是"数据"。另外，LT 重新挂回发生在 本次 ep_send_events 处理过程中（一边拷贝给用户、一边检查挂回），并不是等你用户态处理完才挂。





ET 标准用户态代码：while(read) 读到 EAGAIN 写在哪


这段代码在用户态，是 epoll_wait 返回之后、处理就绪事件的部分；它不在内核 ep_send_events 里，所以在内核代码里找不到。三步：① fd 设为非阻塞；② 注册时加 EPOLLET；③ wait 返回后循环 read 到 EAGAIN（监听 fd 上则是循环 accept 到 EAGAIN）。


#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <errno.h>
#include <sys/epoll.h>
#include <sys/socket.h>
#include <netinet/in.h>

#define MAXEVENTS 64

// ① 把 fd 设为非阻塞 —— ET 模式必须做
static int set_nonblocking(int fd) {
    int flags = fcntl(fd, F_GETFL);
    return fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}

// ③ ET 收到一次可读通知，就一口气读到 EAGAIN
static void read_all_et(int fd) {
    char buf[4096];
    while (1) {
        ssize_t r = read(fd, buf, sizeof(buf));
        if (r > 0) {
            // 处理这 buf 里的数据（演示中省略）
        } else if (r == 0) {
            // 对端关闭连接：close(fd) + epoll_ctl(EPOLL_CTL_DEL)
            close(fd);
            return;
        } else { // r == -1
            if (errno == EAGAIN || errno == EWOULDBLOCK)
                return;        // 读空了！本次事件处理完毕（这是正常信号，不是失败）
            // 其他错误：EINTR 可重试，其余按异常处理
            return;
        }
    }
}

int main(void) {
    int epfd = epoll_create1(0);

    // ② 建立监听 socket（bind/listen 略），设非阻塞并以 ET 注册
    int listen_fd = /* socket(AF_INET,...) + bind + listen */;
    set_nonblocking(listen_fd);
    struct epoll_event ev;
    ev.events = EPOLLIN | EPOLLET;   // 关键：加 EPOLLET
    ev.data.fd = listen_fd;
    epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);

    struct epoll_event events[MAXEVENTS];
    while (1) {
        int n = epoll_wait(epfd, events, MAXEVENTS, -1);
        for (int i = 0; i < n; i++) {
            int fd = events[i].data.fd;

            if (fd == listen_fd) {
                // 监听 fd：循环 accept，直到 EAGAIN（可能同时来了多个连接）
                while (1) {
                    int cfd = accept(listen_fd, NULL, NULL);
                    if (cfd < 0) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK)
                            break;              // 现存连接取空
                        break;                  // 其他错误
                    }
                    set_nonblocking(cfd);
                    ev.events = EPOLLIN | EPOLLET;
                    ev.data.fd = cfd;
                    epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, &ev);
                }
            } else if (events[i].events & EPOLLIN) {
                read_all_et(fd);                // 读循环在上面
            }
        }
    }
}


    

  • 为什么要循环读：read 一次最多返回一个 buf（4096 字节），接收缓冲区可能有多个 buf 的数据，一次读不完。
    • 

  • EAGAIN 是什么：非阻塞 fd 在"没有数据可读"时不等待，立刻返回 -1 并置 errno=EAGAIN（等价 EWOULDBLOCK）；在 ET 读循环里它是"读空"的正常信号，不是错误。
    • 

  • 为什么必须非阻塞：最后一次 read 注定面对空缓冲区，阻塞 fd 此时不会返回 EAGAIN，而是睡死（见下节）。
    • 

  • accept / write 同理：监听 fd 可能同时到达多个连接，要循环 accept 到 EAGAIN；ET 下写也要循环写到 EAGAIN（通常配合 EPOLLOUT 动态开关）。
    • 





为什么 LT 可以用阻塞 fd、ET 必须用非阻塞？




先澄清：没数据时不是 del。LT 数据读空后，动作是"不挂回 rdllist"——epi 始终在红黑树 rbr 里，监听关系一直存在，下次新数据到达回调照样把它挂进 rdllist；只有 epoll_ctl(EPOLL_CTL_DEL) 才从红黑树摘除。


关键不是 LT/ET 本身，而是你调用 read 的那一刻，内核能不能保证缓冲区里有数据。


LT 阻塞 fd：每次 read 前都有 epoll_wait 担保"有数据"（缓冲区 10KB，buf=4096）


epoll_wait()  ← 返回：fd7 可读（内核 poll 已确认缓冲区有数据）
  read(fd7)  → 立即读到 4096，剩 6KB
epoll_wait()  ← LT 仍就绪，已挂回 rdllist，立即返回
  read(fd7)  → 立即读到 4096，剩 2KB
epoll_wait()  ← LT 仍就绪，已挂回 rdllist，立即返回
  read(fd7)  → 立即读到 2048，剩 0
epoll_wait()  ← poll 发现不再就绪，不挂回；在此睡眠，不会再调 read


每一次 read 之前都有一次 epoll_wait 返回了这个 fd（内核已确认缓冲区有数据）；数据被读空时，你不会再调 read，而是进 epoll_wait 睡觉。永远不会在空缓冲区上发起 read，阻塞语义一次都触发不了。典型写法是"wait 返回一次 → read 一次 → 回 wait"，让 epoll 替你判断还有没有数据。


ET 阻塞 fd：最后一次 read 注定面对空缓冲区


epoll_wait()  ← 只通知一次：fd7 可读
  read(fd7)  → 4096，剩 6KB
  read(fd7)  → 4096，剩 2KB
  read(fd7)  → 2048，剩 0
  read(fd7)  → 非阻塞 fd：立刻返回 -1 / EAGAIN → break，正常结束
  read(fd7)  → 阻塞 fd：睡死在 fd7 的 sk_sleep 上，只等 fd7 新数据


ET 只通知一次，你必须自己连续读、探测"空"的边界，于是必然发起一次"此刻没有数据"的 read：非阻塞 fd 立刻返回 EAGAIN（绿色），你 break；阻塞 fd 则直接睡在 fd7 自己的 sk_sleep 上（红色）。




睡在 epoll_wait（ep->wq）睡在 read(fd7)（fd7 的 sk_sleep）


谁能唤醒任何被监听 fd 就绪都唤醒只有 fd7 有数据 / 对端关闭才唤醒


醒来处理谁谁就绪处理谁，fd5 / fd9 都不耽误只能处理 fd7，处理完还要回 wait


性质正常的多路复用等待事件循环被单路钉死




线程卡在 read(fd7) 里时，它不在 epoll_wait 里，ep->wq 名单是空的。这期间 fd5 就绪，回调照样把 epi-5 挂进 rdllist 并 wake_up，但名单上没人可唤醒——事件没丢，静静躺在 rdllist 里，等 fd7 来数据、线程从 read 脱身、再次进入 epoll_wait 时才会被处理；fd7 一直不来数据且对端不关闭，就永久卡死。



快递类比：LT 下快递员每次都喊"你有快递"，你下楼只拿一件就回去，有剩的他继续喊，你永远不会在快递架空时下楼；ET 下快递员只在快递刚到的那一瞬间喊一次，你必须守在架前一件一件拿，直到问"还有吗"、对方答"没了"为止——非阻塞 fd 下对方立刻答"没了"（EAGAIN），你走；阻塞 fd 下对方不回答，你就站在架前死等，这期间别的快递员（fd5、fd9）怎么喊你都听不见。


一句话结论：LT 把"何时该读"的判断交给 epoll_wait，read 永远在有数据时被调用；ET 把"读空"的判断交给你自己，最后一次 read 必然面对空缓冲区，因此必须用非阻塞 fd 拿 EAGAIN 作为"读空"信号。（业界实践通常建议所有 fd 都设非阻塞，以规避多线程共享 fd 等边缘竞争；但标准单线程模型下 LT 用阻塞 fd 不会卡。）






三个 API 各自做什么（速查）



  
调用内核动作返回值

  

    epoll_create1(flags)
    建立一个匿名 inode 文件，分配并初始化 struct eventpoll：初始化红黑树根 rbr、就绪链表 rdllist、等待队列 wq。
    epfd（一个文件描述符）
  

  

    epoll_ctl(epfd, op, fd, ev)
    ADD：分配 epitem 并按 fd 插入红黑树（O(log n)，自动去重）；再通过 eppoll_entry 把回调 ep_poll_callback 注册到该 fd（socket）自己的等待队列上。MOD 改掩码，DEL 从红黑树摘除并撤销回调。
    0 成功 / -1 失败
  

  

    epoll_wait(epfd, events, maxevents, timeout)
    rdllist 非空 → 直接取；空 → 进程睡入 wq。就绪后 ep_send_events：从 rdllist 摘下 epi、poll 取真实事件、copy_to_user 拷给用户；LT 下仍就绪则挂回。
    nfds（本次就绪事件数）
  





关于"是不是死循环"：两层循环，别混在一起




第一层：内核 ep_poll 的 for(;;)　这是等待循环，不是忙轮询。每轮把自己置为 TASK_INTERRUPTIBLE，检查"rdllist 非空 / 超时 / 有信号"三个退出条件；都不满足就调 schedule_timeout() 真正睡着、让出 CPU。被中断回调唤醒后再检查一次，条件满足立即 break，它只负责"等到有事发生"，最多处理一批（maxevents）就返回。


第二层：用户代码的 while(1)　这才是事件循环（Reactor 模式）：epoll_wait 返回一批 → for 循环处理这一批 → 再次调用 epoll_wait。你说的"下一次进入函数时发现就绪队列里有值，就直接返回"——正是这一层：LT 下上次没读完的 epi 已被挂回 rdllist（或又来了新事件），所以第二次调用在入口检查处就 goto fetch_events，不会再睡。


时序串起来就是：调用 wait → 没事件 → 睡在 wq（不占 CPU）→ 网卡中断 → 回调挂 rdllist + 唤醒 → for 循环检查到非空并 break → 拷贝一批返回（LT 挂回 / ET 不挂回）→ 用户处理 → while(1) 再次 wait。


两个补充：timeout=-1 无限等待；timeout=0 完全不阻塞、立刻返回；睡眠期间收到信号会返回 -EINTR。还有，epoll 并没有用 mmap 零拷贝，事件仍靠 copy_to_user 拷贝。






延伸一　epoll 是"多线程"吗？—— 它是单线程 Reactor 的地基，也是协程的地基




先纠正一个直觉：epoll 不是多线程模型，它恰恰是"一个线程同时盯上万连接"的机制。一个线程调一次 epoll_wait，就让内核替它盯住所有 fd，哪个就绪处理哪个——这就是经典的 Reactor 单线程模型：Redis（单线程处理命令）、Netty（每个 EventLoop 一个线程 + 一个 epoll）、Nginx（每个 worker 单线程 + epoll）都是这么做的。"多线程 + 阻塞 IO"是另一种模型，epoll 正是为了避免"上万连接 = 上万线程"的内存、切换、锁开销而存在的。


协程和 epoll 不是平行对立，而是上下两层：



  
用户层：协程 async def fetch1() / fetch2() / ... —— 在 await 处暂停、之后可恢复

  
▲ 就绪后恢复　/　遇到 await 挂起 ▼

  
用户态调度层：asyncio 事件循环（单线程，维护就绪任务队列，决定"接下来跑哪个协程"）

  
▲ 通知哪些 fd 就绪　/　等待 IO 时调用 ▼

  
内核层：epoll_wait（红黑树 rbr + 就绪链表 rdllist + 等待队列 wq）——告诉事件循环"哪些 fd 就绪"

  
▲ 网卡中断 → ep_poll_callback → 挂 rdllist + 唤醒




Python asyncio 在 Linux 上的事件循环底层 selector 就是 selectors.EpollSelector：协程 await 网络 IO → 协程挂起 → 事件循环调 epoll_wait → 数据到 → 恢复对应协程。可验证：import selectors; print(selectors.DefaultSelector) 在 Linux 上输出 <class 'selectors.EpollSelector'>。




多线程 + 阻塞 IO单线程 epoll（Reactor）单线程协程（asyncio）


一个连接对应一个线程一个 fd / 一个 epitem一个协程


等待 IO 时线程阻塞，靠内核切换线程睡在 epoll 的 wq协程挂起，底层睡在 epoll


上万连接上万线程，内存/切换/锁扛不住一个线程就行一个线程 + 上万协程


代码形态同步、易写但重回调（容易回调地狱）async/await，看起来同步、实际异步


用多核天然多核开多个 Reactor 线程/进程多进程（GIL 限制）




一句话：epoll 是共同的地基；多线程、Reactor 回调、协程是三种不同的上层用法。协程 = Reactor 事件循环（底层 epoll）+ 用户态任务调度 + async/await 同步写法。epoll 负责把"等待"变成单线程可承受，协程负责把"上万条处理逻辑"变成单线程好维护。






延伸二　看不懂 async/await？看最简单的例子




三个概念就够：


    

  • async def：定义协程函数；调用它得到的是"待执行的协程"，不会立即执行，要靠事件循环驱动（asyncio.run / await / gather）。
    • 

  • await x：我在等 x 的结果，等的时候不占线程，事件循环去跑别的协程，x 好了再回来接着跑。
    • 

  • asyncio.gather(...)：把多个协程同时扔出去跑，等全部完成。
    • 



注意 time.sleep(1) 是整个线程卡住 1 秒；asyncio.sleep(1) 只是这个协程挂起 1 秒，线程去干别的。


import asyncio
import time

async def say_after(delay, word):
    await asyncio.sleep(delay)   # "我等 delay 秒，期间事件循环去跑别的"
    print(word)

# 写法 A：串行（先等 hello，再等 world）
async def main_serial():
    start = time.time()
    await say_after(1, "hello")
    await say_after(1, "world")
    print("耗时", round(time.time() - start, 1), "秒")

asyncio.run(main_serial())

# 写法 B：gather 并发（两个同时等）
async def main_concurrent():
    start = time.time()
    await asyncio.gather(say_after(1, "hello"), say_after(1, "world"))
    print("耗时", round(time.time() - start, 1), "秒")

asyncio.run(main_concurrent())


写法 A 输出：              写法 B 输出：
hello                     hello
world                     world
耗时 2.0 秒               耗时 1.0 秒


差别只在：A 是两个 await 顺序执行（两次等待相加）；B 用 gather 同时挂起（两次等待重叠）。






延伸三　同一个任务：epoll 回调版 vs async 版（单线程并发下载两个网页）


回调版（epoll 风格，用 selectors 手写；Linux 上 selector 就是 epoll）


import socket
import selectors

sel = selectors.DefaultSelector()
remaining = 2

def fetch(host):
    s = socket.socket()
    s.setblocking(False)
    try:
        s.connect((host, 80))      # 非阻塞连接：此刻还没连上
    except BlockingIOError:
        pass
    ctx = {"host": host, "sent": False, "data": b"",
           "req": b"GET / HTTP/1.0\r\nHost: " + host.encode() + b"\r\n\r\n"}
    sel.register(s, selectors.EVENT_WRITE, ctx)   # 先等"可写"=连上

def run():
    global remaining
    while remaining > 0:
        for key, mask in sel.select():
            s, ctx = key.fileobj, key.data
            try:
                if not ctx["sent"]:
                    s.sendall(ctx["req"])          # 连上了，发请求
                    ctx["sent"] = True
                    sel.modify(s, selectors.EVENT_READ, ctx)  # 改成等"可读"
                if mask & selectors.EVENT_READ:
                    chunk = s.recv(4096)
                    if chunk:
                        ctx["data"] += chunk
                    else:                           # 对端关闭，读完了
                        sel.unregister(s); s.close()
                        print(ctx["host"], len(ctx["data"]))
                        remaining -= 1
            except OSError:
                sel.unregister(s); s.close()
                remaining -= 1

fetch("example.com")
fetch("example.org")
run()


async 版（同样的事，读起来就是顺序代码）


import asyncio

async def fetch(host):
    reader, writer = await asyncio.open_connection(host, 80)
    writer.write(b"GET / HTTP/1.0\r\nHost: " + host.encode() + b"\r\n\r\n")
    await writer.drain()
    data = b""
    while True:
        chunk = await reader.read(4096)
        if not chunk:
            break
        data += chunk
    writer.close()
    await writer.wait_closed()
    return data

async def main():
    results = await asyncio.gather(fetch("example.com"), fetch("example.org"))
    for host, data in zip(("example.com", "example.org"), results):
        print(host, len(data))

asyncio.run(main())




回调绕在哪？逻辑简单时回调确实不难（"看着还行"是对的），痛点在复杂度上来后才显现：


    

  1. 一条线性流程被切碎："连接 → 发请求 → 读响应 → 结束"本是直线，被拆成"等可写、等可读、关闭"好几段，你要在脑子里拼回来。
    2. 

  2. 状态要自己管：发了吗（sent）、读了多少（data）、host 是谁——全得塞进 ctx 字典在回调间传递；async 里就是普通局部变量。
    3. 

  3. 循环/条件难写："循环读到完"在回调里要靠多次进出 select + 状态机；async 里就是一个普通 while True。
    4. 

  4. 错误处理分散：每个回调都要重复 try/except；async 里一个 try 包住整段。
    5. 

  5. 复杂逻辑变"回调地狱"：加超时、重连、"读完 A 再请求 B"，就会出现回调里注册回调、回调里再套回调，缩进越来越深。
    6. 



一句话：async/await 没让你多做任何事，它只是把"被回调切碎的流程"重新写回你熟悉的同步线性样子；而去 epoll 注册、切换、唤醒的脏活，全由 asyncio 在每一个 await 背后替你干了。
