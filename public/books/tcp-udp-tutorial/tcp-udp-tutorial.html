TCP 与 UDP

一个追求"可靠有序"，用握手、确认、重传、窗口把数据稳稳送到；一个追求"简单快"，不连接、不保证、不排队，发出去就不管。它们没有优劣，只有取舍——本教程聚焦连接、报文与可靠性机制。

先定位：传输层在干什么

网络层 IP 只负责把数据从一台主机送到另一台主机，它是不可靠、尽力而为的。但一台主机上同时跑着几十个进程，真正需要通信的是"进程"。传输层用端口（Port）区分进程，并提供两种截然不同的服务：TCP 与 UDP。

数据封装：从应用消息到以太网帧
应用数据（HTTP / DNS / 视频……） └─ 加上 TCP 头 / UDP 头（含源端口、目的端口）→ 段 Segment / 数据报 Datagram └─ 加上 IP 头（源 IP、目的 IP）→ 包 Packet └─ 加上 帧头帧尾（MAC 地址）→ 帧 Frame，发到物理网络
TCP · 传输控制协议
可靠的字节流通道

面向连接、可靠交付、有序、全双工、点对点、有流量与拥塞控制。代价是开销大、延迟高。适合"一个字节都不能错"的场景

UDP · 用户数据报协议
极简的报文通道

无连接、不保证可靠、不保证顺序、无拥塞控制、面向报文。开销极小、延迟极低。适合"快比准重要"或自己做可靠性的场景

一句话抓住本质差异

  • TCP 把"可靠性"做进了协议：丢了会重传、乱了会重排、发快了会减速，应用层完全不用操心
  • UDP 只做"收发"这一件事：丢包、乱序、重复都可能发生，要不要处理、怎么处理全部交给应用自己决定
01 / TCP

TCP：面向连接的可靠字节流

TCP（Transmission Control Protocol）在不可靠的 IP 之上，通过一整套机制提供可靠、有序、无差错、不重复、不丢失的数据交付。理解 TCP 的关键是抓住它的五个关键词：面向连接、可靠、字节流、全双工、点对点。

面向连接
先握手再通信

数据传输前必须先建立连接（三次握手），结束后要释放（四次挥手），连接有明确的生命周期

可靠交付
数据一定送达

通过确认、重传、校验、序号、流量控制保证数据无差错、不丢失、不重复、按序到达

字节流
无报文边界

应用数据被看成无结构的字节流，TCP 不保留应用层消息边界（这是"粘包"的根源）

连接建立：三次握手

三次握手的本质是双方互相确认收发能力、同步初始序列号（ISN）、协商 MSS/窗口等参数。

  • SYN（客户端 → 服务器）：SYN=1，序列号 seq=x，进入 SYN_SENT。"我想连接，我的起始序号是 x"
  • SYN+ACK（服务器 → 客户端）：SYN=1、ACK=1，seq=y、ack=x+1，进入 SYN_RCVD。"我也准备好了，确认你的序号"
  • ACK（客户端 → 服务器）：ACK=1，ack=y+1，双方进入 ESTABLISHED，连接建立，可以带数据

为什么是三次，不是两次或四次？

  • 防止历史失效连接：一个早已失效、在网络中滞留的旧 SYN 到达时，服务器要靠客户端的第三次回复才能决定要不要真建连——想连就回 ACK，发现是无效连接就回 RST 拒绝（详见下方剧本）
  • 双向能力都要确认：需要确认双方"能发也能收"，两次只能确认客户端的发送和服务器的接收，无法确认客户端的接收
  • 同步双方 ISN：序列号是可靠传输的基础，需要一来一回让双方都知道对方的初始序号，三次刚好闭环，四次没有额外信息

场景剧本：一个"迟到的旧 SYN"，两种握手的不同结局

背景：客户端早先发过一个连接请求 SYN，但它在网络里卡住了；客户端等不到回应，已经超时放弃（程序都关了）。过了一会儿，这个旧 SYN 才慢悠悠到达服务器。

假如只有两次握手
服务器收到 SYN 就"当真"了

回完 SYN+ACK 后立即认为连接建立，分配资源、开始干等数据。但客户端早已放弃，收到 SYN+ACK 只会觉得莫名其妙。服务器白等一场，资源被白白占用

实际的三次握手
服务器先"半信半疑"

回 SYN+ACK 后只是 SYN_RCVD 半连接，暂不真正建连。客户端发现自己根本没发起连接，第三次不回 ACK，而是回 RST（复位），服务器收到立刻释放，连接不会建立

关键澄清：不是"ACK 能拒绝"，而是客户端在第三次回复时二选一——确实想连接才回 ACK（连接建立），发现是无效连接就回 RST（连接取消）。服务器把"最终决定权"留给了客户端的第三次回复，这就是必须三次的原因。

"那攻击者不就能决定连接了吗？"——他只能决定自己，控制不了别人。

  • 客户端能决定的只是"我自己要不要建立这个连接"。攻击者用自己的 IP 建连，本来就是正常访问能力（网站本就对所有人开放），他建的是自己的连接，不危害他人；他不回 ACK 只会让自己建不成，半连接超时释放
  • 他无法冒充别人完成连接：若伪造受害者的源 IP，SYN+ACK 会发给受害者，攻击者收不到、拿不到正确确认号，第三次握手无法完成——这正是三次握手防"伪造连接"的价值

类比敲门：你能决定自己敲不敲门、应不应声，但你替不了别人应声，也强迫不了屋里的人开门；有人冒充你时，暗号（序列号）对不上，门不会开。

延伸：SYN 洪水攻击（SYN Flood）

你的观察是对的：服务器收到任何 SYN 都必须回 SYN+ACK，因为它在这一步无法分辨对方是真实用户还是攻击者——这是 TCP 协议的固有设计，没有"先校验再决定回不回"的机会。

① 被占用的到底是什么资源？每收到一个 SYN，服务器就要在半连接队列里创建一条记录（保存对方 IP/端口、自己的初始序号、MSS、时间戳等状态），这是要占内存的。攻击者用海量 SYN 把队列填满，真实用户的 SYN 就排不进来了。

② SYN Cookie 怎么工作（核心是"先不记账，回头再验证"）：

  • 收到 SYN 时不创建半连接记录、不占内存，而是把该记的状态（对方信息、MSS）用一个只有服务器知道的密钥做哈希，编码成服务器的初始序列号，随 SYN+ACK 发出去，然后就把它"忘掉"
  • 真实客户端会回 ACK，且 ACK 号 = 服务器序列号 + 1。服务器拿回序列号、重新计算并验证：能对上，说明是自己之前回应过的合法连接，这时才分配资源建立连接；攻击者伪造的 ACK 算不出正确 cookie，直接被丢弃

"海量伪造 ACK，会不会碰巧蒙对一个？"——工程上不可行。

  • Cookie 是 32 位（约 42.9 亿种可能），由服务器密钥 + 对方 IP/端口 + 时间戳哈希生成。攻击者不知道密钥，无法离线计算，只能在线一个一个发 ACK 去试，平均要发约 20 亿次
  • 关键在于不能像破解密码哈希那样本地高速爆破：本地每秒能算几十亿次哈希，但这里每个猜测都要发一个真实网络数据包，服务器验证失败即丢弃，发送速率受网络和防火墙限制，还会被限流拉黑
  • Cookie 含时间戳、会随时间变化，相当于"移动靶"；且源 IP 也参与计算，攻击者从自己的 IP 无法冒充受害者的 cookie。因此蒙中概率约等于零，且无法规模化

③ 其他防御：增大半连接队列、缩短半连接超时；首包丢弃指队列满时把新到的第一个 SYN 直接丢掉——真实客户端没收到回应会重传 SYN，第二次再处理；而攻击者往往只发一次、不重传，从而被过滤。

④ 和"防止历史失效连接"是一回事吗？不是。前者针对的是无意的、合法但延迟的旧 SYN，属于协议正确性问题，靠三次握手闭环；SYN Flood 针对的是恶意的、故意制造的海量半连接，属于资源耗尽的安全问题，靠 SYN Cookie 等防御。两者都涉及"不能收到 SYN 就立刻相信对方"，但动机和机制完全不同。

连接释放：四次挥手

TCP 是全双工，两个方向的数据流要分别关闭，因此比握手多一步。

  • FIN（主动方 → 被动方）：FIN=1，seq=u，进入 FIN_WAIT_1。"我没有数据要发了"（但还能接收）
  • ACK（被动方 → 主动方）：ack=u+1，主动方进入 FIN_WAIT_2，被动方进入 CLOSE_WAIT。此时被动方可能还有数据没发完
  • FIN（被动方 → 主动方）：数据发完后，被动方发 FIN=1，进入 LAST_ACK。"我也发完了"
  • ACK（主动方 → 被动方）：主动方确认后进入 TIME_WAIT，等待 2MSL 后关闭；被动方收到即 CLOSED

为什么需要 TIME_WAIT，等待 2MSL？

  • 保证最后一个 ACK 能到达，且不会无限循环：主动方发出最后一个 ACK 后进入 TIME_WAIT。若 ACK 丢失，被动方会超时重传 FIN，主动方收到后重发 ACK 并把 2MSL 计时器重新开始。但被动方的 FIN 重传有次数上限（系统参数控制，通常十几次），超过后它就放弃并关闭，不会无限重发；主动方等完最后一个 2MSL 也会关闭。现实中网络不会持续 100% 丢包，一般一两次就成功了
  • 让旧报文在网络中自然消亡：一个连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识，关闭后这个四元组可能被复用。若旧连接有报文延迟未到，新连接又用了相同四元组，旧报文会被新连接误当成自己的数据。等 2MSL 让旧报文全部超过生存时间被丢弃，再复用四元组就不会串数据

第二条的具体画面：假设你关闭了一个连接，客户端立刻又用同一个端口连同一台服务器（相同四元组）。此时旧连接里一个数据包还堵在路由器上，几秒后突然到达——如果没有 TIME_WAIT，新连接会把这个"前一段关系的旧消息"误认为是自己的数据。2MSL 足够保证：在新连接建立前，旧消息已经在网络里"过期作废"。

TCP 头部：可靠性都写在字段里

TCP 头部最小 20 字节，带选项可到 60 字节。关键字段：

源/目的端口
各 16 位，标识通信的两个进程，与 IP 共同确定唯一连接
序列号 Seq
32 位，本报文段数据第一个字节的编号，用于排序与去重
确认号 Ack
32 位，期望收到的下一个字节序号，累计确认
数据偏移
4 位，头部长度（决定选项结束、数据开始的位置）
控制位 Flags
SYN 建连、FIN 断连、ACK 确认、RST 复位、PSH 尽快上交、URG 紧急
窗口大小
16 位，接收方当前能接收的字节数，用于流量控制
校验和
覆盖伪首部+头部+数据，发现传输差错
选项
MSS、窗口扩大、时间戳、SACK 选择确认等

TCP 如何做到可靠：四大机制

序列号 + 累计确认

每个字节都有序号，接收方回 ACK 告知"序号之前的都收到了"。序号解决乱序（缓存重排）、重复（去重），ACK 让发送方知道哪些已送达

超时重传

发出后启动定时器，RTO 内没收到 ACK 就重传。RTO 根据 RTT 动态计算（RTT 波动大就放大），既不能太短造成误重传，也不能太长等太久

快速重传

不必等超时：接收方每收到失序报文就重复 ACK 同一个序号，发送方收到 3 个重复 ACK 立即重传丢失的段，显著缩短等待

校验和 + 数据确认

校验和发现损坏段直接丢弃，配合重传补齐；SACK 选项还能让发送方精确知道哪些块已收到、只重传缺失部分

流量控制：别把接收方撑爆

流量控制是点对点的速率匹配，靠滑动窗口实现。接收方在 ACK 中通过窗口字段告诉对方自己的接收缓冲区还剩多少空间，发送方的发送窗口不能超过它。

  • 窗口随接收方处理速度动态变化：应用读得慢，窗口缩小；窗口为 0 时发送方停止，并用持续定时器探测，防止窗口更新丢失造成死锁
  • 滑动窗口让"已确认 / 已发未确认 / 可发送 / 不能发"四段在字节流上滑动，发送方无需停等，可连续发送，提高吞吐

拥塞控制：别把网络堵死

流量控制只管接收方，但网络本身也会拥堵。拥塞控制是全局的，TCP 维护一个拥塞窗口 cwnd，实际发送量取 cwnd 与接收窗口的较小值。四个经典算法：

  • 慢启动：连接开始 cwnd 从 1 个 MSS 起，每过一个 RTT 翻倍（指数增长），试探网络容量，到达慢启动阈值 ssthresh 后进入拥塞避免
  • 拥塞避免：cwnd 改为每个 RTT 线性 +1，谨慎增长，避免再次触发拥塞
  • 快重传：收到 3 个重复 ACK，立即重传，不等超时
  • 快恢复：把 ssthresh 和 cwnd 减半（而非回到 1），直接进入拥塞避免——因为收到重复 ACK 说明网络仍能通，不必慢启动；超时才认为是严重拥塞，cwnd 回到 1

一句话区分：流量控制解决"接收方接不住"，拥塞控制解决"网络扛不住"；前者看接收窗口，后者看拥塞窗口。

字节流与"粘包"问题

为什么会粘
TCP 不认消息边界

三次 send 的数据可能被合并成一个段发出（Nagle 算法、MSS 合并），也可能被拆开。接收方按字节读取，不知道应用层一条消息到哪结束

怎么解决
应用层自己定边界

固定长度；特殊分隔符（如 \r\n）；消息头带长度字段（最常用，如"4 字节长度 + 消息体"）。注意 UDP 面向报文，天然不粘包

02 / UDP

UDP：无连接的极简报文

UDP（User Datagram Protocol）几乎只在 IP 之上加了复用/分用（端口）和差错检测两件事，其余什么都不保证。它的设计哲学是"快、简单、把控制权交给应用"。

无连接
想发就发

没有握手挥手，不需要维护连接状态，首次发送无建立延迟，系统资源占用少

面向报文
保留边界

应用交下来一个报文，UDP 原样加头发送，不拆分不合并；接收方一次读一个完整报文，不会粘包

尽力而为
不保证交付

可能丢、可能乱、可能重复，没有确认重传；也没有拥塞控制，发送速率不受网络状况调节

UDP 报文结构：8 字节头部

源端口（16 bit）
可选，不需要回复时可填 0
目的端口（16 bit）
目标进程，复用/分用的依据
长度（16 bit）
整个 UDP 报文（头部+数据）的字节数，最小 8
校验和（16 bit）
覆盖伪首部+头部+数据，检测出错；IPv4 可选、IPv6 强制，出错即丢弃且不通知

对比 TCP 最小 20 字节头部与众多机制，UDP 固定 8 字节，首部开销极小。

UDP 的真正优势

  • 延迟低：无连接建立、无确认等待，适合对实时性极敏感的场景，丢一帧无所谓，重传反而造成卡顿
  • 支持多种通信模式：TCP 只能一对一；UDP 可一对一、一对多（广播）、多对多（组播），天然适合服务发现与直播分发
  • 无连接状态：服务器能支撑更多客户端，不会因连接数耗尽资源
  • 应用可自定义可靠性：TCP 是"全家桶"，确认、重传、有序、拥塞控制捆绑在一起没得选；UDP 是"裸底座"，可以像点菜一样只给自己需要的那部分消息加可靠机制（详见下方示例）

举例：一款 FPS 游戏怎么"点菜式"使用 UDP

游戏里同时存在两类消息，它们对可靠性的要求完全相反，于是分别处理：

消息类型怎么处理为什么
位置 / 移动 / 朝向（每秒几十次）不可靠 UDP，直接发，不确认不重传丢了无所谓，下一帧就有新位置；重传旧位置反而造成"瞬移"卡顿
开枪 / 命中 / 拾取 / 技能 / 聊天自定义可靠通道：序号 + ACK + 超时重传这些一条都不能丢，但不需要全部字节严格有序

注意它没有照搬 TCP 的拥塞控制、字节流、全量有序——这些对游戏反而是负担，只保留"关键消息可靠"这一项即可。

最小可靠 UDP 示意（Python，体现"两类消息"的区别）
import socket, time sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM) seq = 0; pending = {} # 待确认的可靠消息：序号 -> (数据, 目标, 发送时间) def send_unreliable(data, addr): # 普通消息：发出去就不管 sock.sendto(data, addr) def send_reliable(data, addr): # 关键消息：编号 + 记账 + 重传 global seq; seq += 1 pkt = f"REL|{seq}|".encode() + data pending[seq] = (pkt, addr, time.time()); sock.sendto(pkt, addr) # 收到 ACK 就删除；定时器扫到超时（如 200ms）的就重发 def tick(): now = time.time() for k,(pkt,addr,t) in pending.copy().items(): if now - t > 0.2: sock.sendto(pkt, addr); pending[k]=(pkt,addr,now) # 发送玩家位置：send_unreliable；发送开枪命中：send_reliable

典型应用场景

实时音视频
通话 / 直播 / 会议

WebRTC、RTP/RTCP 基于 UDP。人耳对少量丢包不敏感，重传旧帧没有意义，重点是持续低延迟

基础设施协议
DNS / DHCP / SNMP

DNS 一次请求一次响应；DHCP 让设备刚接入时自动获取 IP，客户端此时还没 IP，必须无连接通信（详见下方）

在线游戏
状态同步

玩家位置等高频更新，新数据永远比旧数据重要，用 UDP 快速广播，配合自定义可靠通道处理关键消息

DHCP 是什么：接入网络时自动"领身份证"

DHCP（动态主机配置协议）让设备连入网络时自动获取 IP 地址、子网掩码、默认网关、DNS 等配置，不用手动填写。早年每台电脑都要手工配 IP，既麻烦又容易冲突。

它靠 DORA 四步完成，全程 UDP 广播（客户端 68 端口、服务器 67 端口）：

  • Discover：客户端广播"网络里有 DHCP 服务器吗？"（此时源 IP 是 0.0.0.0，因为自己还没有地址）
  • Offer：服务器回应"我可以分给你这个 IP"
  • Request：客户端广播"我就用这个 IP"
  • Acknowledge：服务器确认"归你了，租期多久"，配置完成

为什么只能用 UDP：客户端一开始没有 IP，TCP 三次握手根本无法进行，而且第一步要广播找服务器，TCP 不支持广播。

在 UDP 上做"可靠"：不是退回 TCP

  • QUIC（HTTP/3）：内置 TLS 1.3、独立流（流间不阻塞）、连接 ID 支持网络切换，把 TCP 想做但受限于内核的改进做在用户态
  • KCP / UDT / ENET：游戏与自定义场景常用，以时间换效率，重传策略更激进、可配置，延迟表现优于 TCP
  • RTP/RTCP：RTP 传媒体流，RTCP 周期性反馈丢包与质量，应用据此调码率，而非逐帧重传

为什么 HTTP/3 宁可在 UDP 上重造可靠性？TCP 实现在操作系统内核，部署与升级受限于操作系统；UDP 是用户态，协议可随应用快速迭代。更重要的是 TCP 的队头阻塞（一个包丢失，所有流等待）在多路复用场景下无法解决，而 QUIC 各流独立，丢包只影响自己。

03 / COMPARISON

横向对比与选型

把两者放在同一组维度下，差异本质是"把可靠性做进协议，还是交给应用"。

维度TCPUDP
连接面向连接，三次握手无连接，直接发送
可靠性可靠：不丢、不重、有序尽力而为：可能丢、乱、重

选型决策

  • 数据必须完整正确、能容忍延迟：用 TCP——文件、网页、交易、登录、命令交互
  • 实时性优先、允许少量丢失：用 UDP——通话、直播、游戏状态、直播推流
  • 需要广播/组播或客户端尚无 IP：只能 UDP
  • 需要可靠但 TCP 的机制不满足：UDP + 自定义可靠层（QUIC/KCP），而非硬套 TCP

高频面试题速答

为什么三次握手？

确认双向收发能力、同步双方 ISN、防止历史失效连接，两次不够、四次冗余

为什么四次挥手？

全双工两个方向分别关闭；被动方收到 FIN 时可能还有数据，先 ACK，发完再 FIN

TIME_WAIT 作用？

等 2MSL 保证最后 ACK 可达、可处理重传 FIN，并让旧报文在网络中消亡

TCP 粘包怎么处理？

字节流无边界，应用层定界：固定长度、分隔符、长度字段

UDP 如何可靠？

应用层自行加序号、确认、重传、流控，或直接用 QUIC/KCP

一句话记忆：TCP 像打电话——先接通、确认对方在听、按顺序说、没听清会重复，挂断还得互相道别；UDP 像寄明信片——写好就投、不用对方在不在、可能寄丢也可能顺序乱，但快、便宜、一次能寄给很多人。
