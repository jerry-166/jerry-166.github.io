# 第一块：压测全展开（6 个子问题逐一映射）

## 1.1 你是通过什么压测的？

**自研 Python 压测脚本**，不是 JMeter/Locust 这类现成工具。脚本家族放在 `work/stage-4/loadtest-reattack/`（work 目录不入库，脚本逻辑从设计文档可完整还原）：

```
rerank_ab.py          ← A/B 归因实验专用（40@10，只动 rerank 开关）
scenario2_search.py   ← 5 模式并发检索
scenario2_hybrid_ep.py
scenario3_faq_loop.py ← 自进化闭环 50 轮
scenario1_reduced.py  ← 导入链路回归
```

以 `rerank_ab.py` 为例的结构还原（后续 LightRAG 对比脚本 `bench_lightrag.py` 就是“结构照抄、改 endpoint"）：

```python
B = 'http://localhost:8003'              # 被测服务
ep = '/api/milvus/query'                 # 被测端点
QUERIES = [...20 条真实中文 query...]     # query 集
# 参数：n=40 请求、conc=10 并发、top_k=10、预热 2 次、客户端超时 300s
# 并发模型：线程池（10 worker），每 worker 循环取任务发 HTTP
# 旁路：RSS 采样线程（定时读后端进程内存 → 曲线，测泄漏）
# 输出：JSON {p50, p95, p99, max, QPS, err, wall}
```

**为什么自研而不是用工具**（这是面试加分点，主动讲）：

| 需求 | 自研脚本能做 | 现成工具的摩擦 |
|---|---|---|
| 业务语义压测 | 直接复用登录 token、知识库 API、`use_rerank` 参数开关 | JMeter 要拼 HTTP 采样器 + 变量管理，改 payload 繁琐 |
| A/B 归因实验 | 代码里一行开关切换，两组跑同一脚本 | 工具里做“同脚本两配置对比”反而绕 |
| 内嵌观测 | RSS 采样线程、审计对账（2,639 事件窗口核对）直接写进脚本 | 工具不会懂你的业务审计事件 |
| 复用性 | LightRAG 对比 = 改 3 行（base_url/endpoint/body 字段映射） | — |

**诚实代价**（面试官可能反问）：自研脚本没经过大厂级验证，自身就是 bug 来源之一——基线轮 keyword 7.5% “错误率”其实就是**脚本自己的 token 过期 + 客户端超时**，不是服务错误；复验轮改了 300s 超时阈值才清零。**压测工具自身的正确性也要被验证**，这本身就是个认知。

## 1.2 你是怎么设计这个压测的？

设计逻辑分四层：

**① 为什么是 5 种模式？**——检索路径全覆盖，每条路径的依赖不同，压测同时是架构回归：

| 模式 | 走的路径 | 独有的依赖 |
|---|---|---|
| native | 原文向量 | Milvus + embedding |
| advanced | 摘要+子问题向量 | 两个增强集合 + embedding |
| hybrid_vec | 三路 RRF | 上面全部 + 融合逻辑 |
| keyword | BM25 | jieba 分词 + 内存模型（不碰 embedding） |
| hybrid_endpoint | 向量+BM25+rerank | 全链路 |

**② 场景分层**——不只压检索，一个 Stage 4 压了四件事：批量导入（吞吐）、并发检索（延迟）、自进化闭环 50 轮（长时运行正确性）、审计对账（可观测性自证）。

**③ 公平性铁律**（做 before/after 和对比的前提）：同一数据集（KB17=110 docs/1999 chunks）、同一环境（12 核/15.6GB、Zilliz、litellm 代理）、同一参数、基线数据不动（`loadtest/` 与 `loadtest-reattack/` 分目录保存）。

**④ 环境净化**——压测前停掉本地 milvus docker 容器（检索实际走 Zilliz Cloud，本地容器纯吃内存）；第一轮误入此坑，内存吃爆、单组超时 44.5%、RSS 失控涨到 5.4GB，数据全废。**教训：压测环境里每个常驻进程都要能回答“为什么它在”。**

## 1.3 压测哪些指标？每个指标的意义（词→概念映射）

| 指标 | 定义 | 为什么看它 |
|---|---|---|
| **p50**（中位数） | 一半请求快于此值 | “典型用户体验” |
| **p95 / p99** | 95%/99% 请求快于此值 | **长尾**——用户说“卡”的来源；平均数会被长尾拉爆或掩盖问题，分位数不会 |
| **QPS** | n / wall（完成请求数/总时长） | 吞吐上限 |
| **错误率** | err / n | 正确性红线（本项目要求 0） |
| **wall time** | 压测总耗时 | 整体放行/收尾判断 |
| **RSS** | 后端进程常驻内存采样曲线 | **泄漏检测**：健康形态是“涨后趋平”（如 908→1315MB 后稳定），持续线性上涨 = 泄漏 |

**关键心法（面试深水区）**：为什么 p50 降了还不算赢？——本项目 p50 从 109→70s 的同时 p95 从 192→90s（-53%），**p95 降幅大于 p50**，说明修复消灭的是长尾（超订阅把单请求放大到 100s+ 的那批），而不只是整体位移。看分位数组合的“形状变化”比看单一数字信息量大得多。

## 1.4 参数怎么选的？为什么？

| 参数 | 值 | 选择理由 |
|---|---|---|
| 请求数 n | 40 / 200 | 40 条 × 20 个 query 双循环 = 800 采样点算分位数，够稳定又不至于跑太久；200 用于 keyword/hybrid_endpoint 这类预期更慢的模式分桶看 |
| 并发 conc | 10 / 20 | ① 匹配真实内部工具型使用（几十人团队，峰值同时在线检索 ~10）② **10 并发正好是触发超订阅的最小剂量**（10×12=120 线程）——后来反推：并发 <核数时超订阅不严重，这也是 keyword 组 20 并发反而幸存于崩溃的边际效应 |
| top_k | 10 | 检索默认值，对齐生产配置 |
| 预热 | 2 次 | 排除冷启动噪声（模型懒加载、连接池建立、DNS、TLS 握手），否则第一发 100s+ 会污染 p99 |
| 客户端超时 | 300s | 必须 > 最慢真实响应（max 101.6s）+ 余量；设小了会把“慢”误报成“错”（基线轮的教训） |
| 模式开关 | rerank=True 全开 | 主路径全开才是真实负载；rerank 关单独作为 A/B 对照组 |

**loadtester 用户（u14）**：专用测试账号，避免压测流量混进真实用户数据，也保证知识库可见范围确定性。

## 1.5 这些参数适合企业场景吗？换个场景怎么用？

诚实回答：**当前参数适配“内部工具型 RAG”（几十用户、峰值并发 ~10），不适合直接平移到 C 端**。换场景的三步迁移法：

1. **重新定并发模型**：C 端场景要先做流量画像（DAU、峰值 QPS、请求到达模式）。**关键概念——开环 vs 闭环**：
   - 我们的脚本是**闭环**（closed-loop）：固定 10 个 worker，完成一个补一个，实际到达率随服务变慢而下降；
   - 生产真实流量是**开环**（open-loop）：请求按泊松到达，服务再慢流量照来，**队列只增不减**。
   - 开环下超订阅的后果比我们测到的更严重（排队无上限）。业界工具里 wrk2、vegeta 支持恒定速率开环；k6 用 `constant-arrival-rate` executor。
2. **指标目标换挡**：内部工具看 p50/p95；C 端要盯 p99 和错误预算（SLO，如 99% 请求 <8s），并加饱和度指标（队列深度、线程池活跃数）。
3. **数据集与预热换挡**：query 集要换成真实分布（不能全是自己写的 20 条）；预热后还要跑稳态时长（≥30min）看泄漏和缓存命中率。

## 1.6 有没有用过别的压测工具？（业界工具生态映射）

| 工具 | 语言/模型 | 生态位 | 如果当时用它 |
|---|---|---|---|
| **JMeter** | Java 线程组 | 企业最普及，协议全（JDBC/JMS/MQTT），报表全 | 重：GUI 编排业务 payload（token→查 KB→带 rerank 开关）成本高于写 Python；适合协议层通用压测 |
| **Locust** | Python，gevent 协程“用户模拟" | **代码即压测**，分布式 master/worker | 理论上是最合理替代：也是 Python、也写代码。没选它是因为当时脚本已在（Stage 4 复用原则），且需要嵌 RSS 采样/审计对账这类业务观测 |
| **k6**（Grafana） | Go 引擎 + JS 脚本 | 性能好，thresholds 断言直接进 CI/CD | CI 阶段回归压测的好选择；业务语义（动态 token）可用 JS 处理 |
| **wrk / wrk2** | C | 单机极高并发；**wrk2 专门解决 coordinated omission** | 只测 HTTP 层，业务语义弱；但 wrk2 的开环恒速率是测超订阅的正确姿势 |
| **ab / hey** | C / Go | 一行命令快速烟测 | 功能太薄（无分位数对比、无场景编排） |
| **Gatling** | Scala DSL | 高性能、报表漂亮 | 学习成本 + JVM 栈不匹配 |

**面试深水区概念——coordinated omission（协调遗漏）**，Gil Tene（wrk2 作者）提出：闭环压测里，前一个请求慢了，后续请求自动顺延，**等于把最忙时刻的样本自动跳过了**，测出的分位数系统性偏乐观。我们的脚本就是闭环模型，所以 70s 的 p50 在真实开环流量下只会更糟。能主动讲出“我知道我的压测方法的系统性偏差是什么”，比“我用了很牛的工具”高一个层级。

# 一、压测客户端的线程、GIL、wall、RSS 采样

## 1.1 GIL 下 10 线程发 HTTP 算并发吗？——先纠正一个心智模型

你的困惑来自一个常见误解：**“GIL 同一时间只有一个线程执行字节码”是对的，但线程的时间不是都花在执行字节码上**。

把一个压测线程的生命周期拆开看：

```
worker 线程处理一个请求的时间构成：
┌──────────────────────────────────────────────────────┐
│ 拼请求体/设 header（执行字节码）      ~0.1ms         │
│ socket.send()（执行字节码）           ~0.01ms        │
│ ████████ 等服务器响应（IO 等待）████████ ~70,000ms   │ ← 99.9999% 的时间在这
│ 解析响应/记耗时（执行字节码）         ~0.1ms         │
└──────────────────────────────────────────────────────┘
```

关键机制：**线程进入 IO 等待（等 socket 上有数据回来）时，会释放 GIL**。这是 CPython 的设计：GIL 只互斥“执行 Python 字节码”这件事，`recv()` 这种系统调用等待期间 GIL 是放开的，别的线程可以拿去跑字节码。

所以 10 个 worker 的真实图景是：

```
时刻 →   t1     t2     t3    ......  t70000
线程1: [拼包]██IO等待████████████████[解析]
线程2:   [拼包]██IO等待███████████████[解析]
线程3:     [拼包]██IO等待█████████████[解析]
...
线程10:          [拼包]██IO等待███████[解析]
        ↑
   每个线程只在"拼包/解析"的瞬间需要 GIL，
   这些瞬间加起来不到 1ms，10 个线程排队用 GIL 毫无竞争压力
```

**结论：10 线程 → 10 个同时在途（in-flight）请求 → 这是真并发**。GIL 在这里不是瓶颈，因为字节码执行时间占比趋近于零。

再补两个概念区分（面试高频）：

| 概念 | 定义 | 需要什么 |
|---|---|---|
| **并发（concurrency）** | 多个任务*交替推进*，都有进展 | 单核即可（时间片轮转） |
| **并行（parallelism）** | 多个任务*同一时刻*同时执行 | 必须多核 |

压测客户端需要的是**并发**（10 个请求同时在路上），不需要并行（10 个线程同时算东西）。GIL 只杀死并行，不杀死并发。

**反例对照**（帮你建立判断力）：什么情况下线程压测客户端会被 GIL 卡住？——如果每个请求要本地做 CPU 密集计算（比如对 payload 做 100ms 的哈希签名、或者 JSON 序列化一个 50MB 的响应）。那时 10 线程的字节码执行时间占比从 0.0001% 涨到 30%+，GIL 争用会让发压端自己先慢下来——**压测端先于被测端饱和，测出来的数据全是客户端自己的瓶颈**。业界用 Go（wrk）或者多进程（Locust 分布式 worker）就是为了避免这个。

## 1.2 为什么不用 semaphore？——先澄清 semaphore 是什么

**Semaphore（信号量）**：一个计数器 + 等待队列。`acquire()` 计数减一，满了就挂起；`release()` 计数加一，唤醒等待者。它的用途是**限制“同时进入某段代码”的并发数**。

你的直觉其实指向了一个真实的设计点，只是它在线程池模型里已经内置了：

```
设计 A（本项目脚本）：固定 worker 线程池
  ThreadPoolExecutor(max_workers=10)
  → worker 数 = 并发上限，天然封顶
  → 任务数(40) > worker 数(10)：多的任务在池的队列里等
  → "并发 10"这个约束由池的物理结构保证，不可能超

设计 B（asyncio 风格）：全量任务 + Semaphore 限流
  sem = asyncio.Semaphore(10)
  async def one(i):
      async with sem:          # ← 并发闸门在这
          await client.post(...)
  await asyncio.gather(*[one(i) for i in range(40)])
  → 40 个协程全创建，但同时只有 10 个能过闸
```

两种设计等价地实现“并发上限 10”，只是闸门的位置不同：**设计 A 的闸门是 worker 数（结构性），设计 B 的闸门是 semaphore（逻辑性）**。

什么时候必须用 semaphore？——当“任务单元”和“并发资源”不是一对一的时候。比如一个逻辑请求要并发打 3 个 API（embedding + BM25 + Milvus），你想限制的是*总在途 HTTP 连接数*而不是*逻辑请求数*——这时共享一个 semaphore 才能限住总量。本项目实际代码里也有真实用例：`_get_rerank_executor` 的 `RERANK_MAX_CONCURRENCY` 本质上就是给 rerank 这个临界资源装了个“池型 semaphore”。

一句话总结：**线程池的 max_workers 就是线程世界的 semaphore，不是“没用”，是“换了个形态已经在用”**。

## 1.3 wall 是什么？——不是“钟墙”，是“挂钟”

wall = **wall clock time（挂钟时间）**：盯着墙上挂钟看的真实流逝时间。

它有个必须配对理解的概念：

| | wall time | CPU time |
|---|---|---|
| 含义 | 从开始到结束，现实世界过了多久 | 所有线程占用 CPU 的累计时间 |
| 例子 | 压测跑了 294.4s | 可能是 1800s+（多线程叠加） |
| 测什么 | 用户/运维视角的“多久” | 机器视角的“烧了多少算力” |

在压测报告里：`wall = 第一个请求发出 → 最后一个响应落地` 的总时长，`QPS = n / wall`（40 请求 / 294.4s = 0.14）。注意这里有个细节：**wall 含排队时间**——闭环压测里后面的请求在池队列里等，等待时间也被 wall 摊进去了，所以 QPS 反映的是“该并发下的稳态吞吐”。

面试可延伸：`wall ≈ CPU time`（单线程且无等待）；`wall << CPU time`（并行良好）；`wall >> CPU time`（全在等 IO/锁——本项目后端就是这种，等远程 embedding/Zilliz/torch）。

## 1.4 为什么开旁路 RSS 采样线程？

拆成三个子问题：

**RSS 是什么？**——Resident Set Size（常驻内存集）：进程此刻真实占着的物理内存。区别于虚拟内存（VSS，含未映射的保留地址，虚胖）。Windows 上用 `psutil.Process(pid).memory_info().rss` 读取。

**为什么必须是“曲线”而不是前后两个点？**——因为泄漏的判据是**形态**，不是数值：

```
健康曲线                          泄漏曲线
       ┌────────────── 趋平                ┌─┐  ┌─┐ ┌┐ ┌ 持续线性上涨
      /                                /  |/  |/ |// /
     /  ← 缓存填充期（BM25语料、      /   ↑   ↑  ↑
    /     模型加载，涨是正常的）      每轮压测涨一截，下不来了
___/
```

本项目实例：8-21 基线轮 RSS 838→928MB 后趋平 = 无泄漏；污染轮（本地 milvus docker 没停）RSS 一路失控涨到 5.4GB = 环境异常的铁证。**单看“结束时的 RSS 数字”两种情况可能都是 900MB，只有曲线才能区分“涨到位了”和“还在涨”。**

**为什么是独立旁路线程，不顺便做？**——两个原因：① 采样必须**覆盖整个压测窗口**（发压期间持续每 N 秒采一次），它天然和发压循环并行，只能独立成线程；② 采样不能挤占发压资源——如果串在 worker 循环里做，采样间隔会插进请求间隔，改变实际负载模式，数据失真。

# 三、JMeter 经验的映射

对，1.5 节（开环/闭环）回答的正是你这个问题的一半。你用过 JMeter 测秒杀，这经验可以直接映射过来，还能串出一条好讲的故事线：

| | 你的秒杀压测 | 本项目 RAG 压测 |
|---|---|---|
| JMeter 线程组 ↔ 手写线程池 | Thread Group 设 200 线程 = 200 并发用户 | `ThreadPoolExecutor(max_workers=10)` |
| 请求形态 | **高并发 × 短请求**（几 ms~几十 ms 的事务） | **低并发 × 长请求**（70s 级端到端） |
| 关键指标 | TPS、错误率、吞吐拐点 | p50/p95 长尾、错误率 0 |
| 典型瓶颈 | 连接池、DB 锁、库存超卖 | 事件循环阻塞、线程超订阅 |
| 流量模型 | 秒杀本质是**开环冲击**（瞬时洪峰，服务慢了流量照来） | 本项目脚本是**闭环**（服务慢，到达率自动下降） |

所以你其实已经摸过压测光谱的两端了。面试如果被问“用过什么压测工具”，可以这么串：“JMeter 做过秒杀场景的高并发冲击测试，后来在 RAG 项目里因为要嵌业务语义（动态 token、rerank 开关、A/B 分组、审计对账）改用自研 Python 脚本——两者本质都是‘固定并发模型 + 分位数统计’，区别在业务编排自由度。” 这个回答比“我用过 JMeter”值钱得多，因为它证明你看到了工具背后的共性。
