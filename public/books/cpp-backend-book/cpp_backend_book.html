0.1 C++ 类的长相：逐行对照 Python

第 1 章会出现一个 FileGuard 类，先把它拆开，每行和 Python 摆在一起看：

class FileGuard {                     // Python: class FileGuard:
public:                               //   （Python 没有 public/private，全公开）
    FileGuard(const char* path)       //   def __init__(self, path):
        : f_(fopen(path, "r")) {}     //       self.f = open(path, "r")
    ~FileGuard() {                    //   （Python 没有可靠对应物！__del__ 时机不定）
        if (f_) fclose(f_);           //   ~FileGuard = 对象销毁时"编译器自动调用"的函数
    }                                 //   ——不是你手动调的，这是 RAII 全部魔法的来源
private:                              //   private = 只有类内部代码能碰，外面碰编译报错
    FILE* f_;                         //   self.f —— 成员变量（C++ 必须先声明类型）
};
C++ 写法Python 等价物含义
FileGuard(...)（和类同名的函数）__init__构造函数：对象出生时自动执行
~FileGuard()（名字前带 ~）（无；__del__ 最接近但不可靠）析构函数：对象死亡时编译器保证自动调用——所以「资源释放」可以搭它的便车
f_（写在类底部的变量声明）self.f成员变量。区别：C++ 要先声明类型，Python 随用随挂
public: / private:（无，靠约定 _x）访问控制：private 后面的成员/函数只有类内部能用
成员函数里直接写 f_成员函数里写 self.fC++ 的 this 是隐式的，写成员名自动指「当前这个对象的」
🔧 所以 RAII 类到底在干嘛

就是写一个「构造时拿资源、析构时放资源」的普通类。因为析构是编译器保证调的（函数正常结束、提前 return、抛异常都会调），所以资源必然被释放——你只是把「释放动作」塞进了一个必然被执行的函数里。FileGuard 翻译成 Python 思路就是：「__init__ 里 open，__del__ 里 close」——但 Python 的 __del__ 时机不确定所以没人这么干，C++ 的析构时机是语言保证的，所以这么干成立。

0.3 栈对象 vs 堆对象：同款类的两种活法

C++ 造对象有两种姿势，直接决定析构时机（Python 没这个选择困难——对象全在堆上，死活归 GC）：

void demo() {
    FileGuard g("a.txt");           // 姿势一：栈对象。g 这个对象本体就活在栈帧里
                                    // 函数结束 → g 自动静音析构（fclose 自动执行）
    FileGuard* p = new FileGuard("b.txt");
                                    // 姿势二：堆对象。p 只是个指针（在栈上），
                                    // 对象本体在堆上，函数结束它不会自动死
    delete p;                       // 必须手动 delete 才触发析构；忘了 = 泄漏+文件没关
}   // g 在这里自动析构；p 指向的堆对象若没 delete，就永远漂在堆上
🔧 记住这张对照

栈对象（T obj(args);）：作用域结束自动析构——RAII 专用姿势，第 1 章例子里 FileGuard g("a.txt") 就是它。堆对象（T* p = new T(args);）：活得比函数长，但必须手动 delete；「把裸 new 交给智能指针管」（第 2 章）本质就是让它也自动死。Python 里 g = FileGuard("a.txt") 看着像姿势一，实际对象在堆上——C++ 的「对象直接住栈上」是 Python 没有的概念。

第 1 章 · 内存模型：对象的出生地P0 详讲 · 高频

1.1 内存五区：一栋公寓楼

为什么出现这个问题：C++ 允许你直接操作地址，所以「变量放哪」不再是可以无视的实现细节——放哪一区，直接决定了它的寿命和谁来管。

🏠 比喻：一栋公寓楼

把进程的虚拟地址空间想成一栋楼：代码区是物业办公室（只读，谁都不许改）；常量区是图书馆藏书（"hello" 这种字面量，只读共享）；全局/静态区是大堂储物柜（程序启动就分配好，退出才收回）；栈是前台的一摞抽屉（函数进来推一格、出去弹一格，自动管理，但很小）；堆是地下自助仓库（想要多大自己申请，用完必须自己还，没人替你打扫）。

int g = 1;                 // 全局/静态区：大堂储物柜，main 之前就有
const char* s = "hello";   // "hello" 在常量区（图书馆），指针 s 本身在栈

void f() {
    int a = 10;            // 栈：前台抽屉，f 结束自动弹掉
    static int cnt = 0;    // 静态区：虽然写在函数里，住的是大堂储物柜
    int* p = new int(20);  // 20 在堆（自助仓库）；指针 p 在栈
    delete p;              // 堆上的必须自己还，否则泄漏
}
🎭 面试作答

30 秒版：「进程内存分五区：代码区存指令、常量区存字面量、全局静态区存全局和 static 变量、栈管函数局部变量、堆管动态分配。核心区别是栈由编译器自动管理、空间小、分配快；堆由程序员手动管理、空间大、分配慢，容易泄漏。」

1.2 栈 vs 堆：为什么一个快一个慢

🔧 机制

栈分配 = 把栈顶指针挪一下（一条 CPU 指令，纳秒级），回收 = 指针挪回去，天然 LIFO。堆分配慢在「找地方 + 记账」，这两个词下面拆开讲。

🏠 比喻：堆分配器是二房东，OS 是大房东

你的程序找 malloc/new 要内存，但分配器（如 glibc 的 ptmalloc）这个「二房东」手里得先有房。它的进货渠道是操作系统：以页为单位整批进货（Linux 一页 4KB，底层走 brk 或 mmap 系统调用）。所以每次 new 背后有两层：多数时候二房东库存里还有空房，直接从库存划一块给你——纯用户态操作，不惊动 OS，其实不算慢；库存不够了，才跑一趟大房东再进一批页——这一趟是系统调用，要陷进内核、做权限检查，才是真正的慢。这就是「可能还要向 OS 要新页」的意思：不是每次都要，是要跨用户态/内核态边界进货时才贵。

记账：划给你的每块内存都要记下大小（一般写在块头几个字节里），否则 free/delete 时不知道该还多少、还给谁。

合并防碎片：你还了一间 1KB，左边邻居是空的 2KB，右边是空的 3KB——二房东立刻拆墙把三间拼成 6KB 大间。不合并的话，仓库里全是零碎小隔间：明明总空余 5KB，却放不进一个 4KB 的请求（连续内存才是一块可用内存）。free 时的合并逻辑就是干这个的。

对照栈为什么快：栈根本不用找地方（位置由调用层次定死）、不用记账（弹出即回收）、不用进货（栈空间程序启动时 OS 一次性划好 8MB）——三个慢因全躲开了。

栈堆
管理编译器自动（函数返回即回收）程序员手动（new/delete）
大小小，Linux 默认约 8MB，超了栈溢出大，受限于虚拟内存
速度极快（移指针）慢（查找+记账）
生命周期随函数调用栈帧任意，delete 才死
典型风险返回局部变量地址（悬垂指针）泄漏、双删、野指针
⛔ 反例：返回栈上地址 = 送别人一个已退房的房号
int* bad() {
    int x = 42;
    return &x;   // x 随栈帧销毁，返回的是已退房的房号
}                // 调用方拿到悬垂指针，读到的值是垃圾

1.3 new/delete vs malloc/free：四维区别

malloc/free 是 C 时代的库函数，new/delete 是 C++ 的运算符——这一条是所有区别的根。

  1. 构造与析构：new 会调构造函数、delete 调析构函数；malloc 只给一块裸内存（类比：malloc 交毛坯房，new 交精装房还配管家）；
  2. 类型安全：new 返回具体类型指针，malloc 返回 void* 要手动 cast；
  3. 失败行为：malloc 失败返回 NULL，new 失败默认抛 std::bad_alloc 异常；
  4. 可重载：new/delete 是运算符，可以按类重载定制分配策略；malloc 不行。

底层关系：new 通常在内部调用 malloc 拿内存，然后在这块内存上调构造函数。另外 new T[n] 数组版必须配 delete[]——配错是未定义行为（数组版会在头部多记一个元素个数）。

1.4 内存泄漏与 RAII：C++ 的独门哲学

内存泄漏 = 堆上申请了、丢了地址、永远没还。C++ 没有垃圾回收（Python 有引用计数 + 分代 GC 兜底），那大项目怎么活？答案是 RAII。

🏠 比喻：地弹簧门

裸 new/delete 像普通门——进门的人（申请资源）必须记得随手关门（释放），忘了就敞一宿。RAII 像地弹簧门：把「关门」这个动作绑定在「门开着的这段时间」上——资源的一生绑定对象的一生：构造函数里拿资源，析构函数里放资源。函数无论正常 return、提前 return 还是抛异常，栈上对象一定被析构，资源一定被释放。

// RAII 最小实现：一个抱住文件的类
class FileGuard {
public:
    FileGuard(const char* path) : f_(fopen(path, "r")) {}   // 构造 = 开门时拿资源
    ~FileGuard() { if (f_) fclose(f_); }                    // 析构 = 地弹簧自动关门
    FileGuard(const FileGuard&) = delete;                   // 禁拷贝（防双关门）
    FileGuard& operator=(const FileGuard&) = delete;
private:
    FILE* f_;
};

void work() {
    FileGuard g("a.txt");   // 之后无论 return 还是抛异常，fclose 必然执行
    // ... 可能中途 return / throw，都不用管
}
🎭 面试作答

「什么是 RAII？」30 秒版：「Resource Acquisition Is Initialization——把资源的生命周期绑定到栈对象的生命周期：构造时获取、析构时释放。因为 C++ 保证栈对象在离开作用域时（包括异常展开时）必定析构，所以资源不会泄漏。Python 里的 with 语句、Java 的 try-with-resources 就是同一思想的语法糖，但 C++ 是语言级保证，智能指针、lock_guard 全是 RAII 的应用。」

加分一句：泄漏检测工具 valgrind / AddressSanitizer（编译加 -fsanitize=address），面试提一句即可。

2.1 为什么出现：裸指针三宗罪

裸指针 = 「借了不还、还了再用、没人记得还」的温床：忘 delete（泄漏）、delete 两次（双删崩溃）、delete 后继续用（悬垂指针）。既然 RAII 能绑资源，把「堆上的对象」也交给一个栈上的管家对象抱着，就得到智能指针——本质上智能指针 = 抱着裸指针的 RAII 壳。<memory> 头文件三件套按所有权模型分工：

所有权模型一句话Python 类比
unique_ptr独占一根枪只能一个人扛无（最接近「唯一持有者」约定）
shared_ptr共享（引用计数）多人合租，最后一手关灯引用计数（sys.getrefcount 的手动挡）

2.2 unique_ptr：独占，零开销

🔧 机制

禁止拷贝（拷贝构造/赋值 = delete），只允许 move——所有权只能「移交」不能「复制」。不引入任何额外内存：sizeof(unique_ptr<T>) == sizeof(T*)（默认删除器时）。析构时自动 delete。它就是「带自动关门的裸指针」，不用它没理由用裸 new。

auto a = std::make_unique<int>(42);
// auto b = a;                  // 编译错误！独占，不许拷贝
auto b = std::move(a);           // OK：移交所有权，a 变 nullptr

裸 new/delete、指针的拷贝，在 unique_ptr 面前都是历史写法——面试被问「现代 C++ 怎么管内存」，第一句就该是它。

2.3 shared_ptr：引用计数与控制块

共享所有权的核心是引用计数：每拷贝一次 +1，每析构一次 −1，减到 0 的那个实例负责 delete 对象。

🏠 比喻：合租房的灯

每个室友（shared_ptr 实例）搬进来，门口计数牌 +1；搬走 −1。最后一个走的人负责关灯（delete 对象）。但灯开关（控制块）是独立于房间（对象）的一块小牌子——牌子上有两个数字：强计数（几个室友）和弱计数（几个只留电话的人）。强计数到 0 关灯拆房间；强弱都到 0，连牌子一起拆。

shared_ptr 的两块内存：对象 + 控制块
make_shared 把两块合并成一次分配；先 new 再构造 shared_ptr 则是两次分配
被管理对象控制块（计数所在）
⛔ 高频追问：shared_ptr 线程安全吗？

标准答案分两截：① 控制块的计数是原子的——多个线程各自持有自己的 shared_ptr 副本拷贝/析构，计数不会乱；② 对象本身和同一个 shared_ptr 实例不保证——多线程读写同一个 sp 变量（如一个线程赋值一个线程析构）、或并发调用被管对象的成员，都要自己加锁。一句话：「计数安全，对象不安全」。

展开：make_shared 为什么比 shared_ptr<T>(new T) 好
  • 一次分配：make_shared 把对象和控制块合在一块内存（上图右半合并），shared_ptr<T>(new T) 是两次堆分配（先 new 再控制块）——分配次数减半、缓存局部性更好；
  • 异常安全：C++17 前 f(shared_ptr<T>(new T), g()) 若 g() 抛异常可能泄漏（求值顺序漏洞），make_shared 无此问题；
  • 代价：对象和控制块同块 → 只要有 weak_ptr 活着（弱计数 > 0），整块内存都不能还，对象那部分也跟着陪葬（不析构但占内存）。所以「弱引用长命」的场景有人反而用两次分配版。

2.4 循环引用：引用计数的死穴，weak_ptr 解药

引用计数有个天生缺陷：两个人互相指着对方说"他还在用我"，于是谁都不肯走。

struct Son;                       // 前置声明
struct Father {
    std::shared_ptr<Son> son;     // 父持子：强引用
    ~Father() { std::cout << "~Father\n"; }
};
struct Son {
    std::shared_ptr<Father> father;  // 子持父：也是强引用 —— 死穴在这
    ~Son() { std::cout << "~Son\n"; }
};

int main() {
    auto f = std::make_shared<Father>();   // f 强计数 1
    auto s = std::make_shared<Son>();      // s 强计数 1
    f->son = s;      // s 强计数 2
    s->father = f;   // f 强计数 2
}   // main 结束：f、s 局部变量析构，各自强计数 2-1=1 —— 永远到不了 0！
    // 两个析构函数都不会打印：内存泄漏，且无声无息
🔧 机制与解药

强计数到 0 才 delete，而这对父子各自被对方多持 1 次，形成死锁式的"计数永远 ≥ 1"。解药：把"所有权"的一端降级为"观察权"——子改持 weak_ptr<Father>，它不增加强计数（只加弱计数）。父的强计数只剩 main 里那 1 份，main 结束即归 0 → 触发链式析构，各自把对方释放掉。

struct Son {
    std::weak_ptr<Father> father;   // 只留电话不留钥匙：不拥有，不计数
    void callDad() {
        if (auto f = father.lock())   // lock() 尝试升级回 shared_ptr
            /* f 活着，安全使用 */;
        // lock() 失败返回空 shared_ptr —— 说明 Father 已经死了
    }
};
🎭 面试作答

「讲讲智能指针 / 循环引用」60 秒版：「智能指针是 RAII 套在裸指针上的壳，分三种所有权模型：unique_ptr 独占且零开销、不能拷贝只能 move；shared_ptr 用引用计数共享，控制块里存强/弱两个原子计数，强计数归零释放对象；weak_ptr 只观察不计数，用来打破循环引用——典型就是父子节点互相持有，只要一端降级为 weak 就解开了，用的时候 lock() 临时升级。shared_ptr 线程安全要分清：计数是原子的，但对象本身不安全。生产上默认 unique_ptr，确实需要共享才 shared_ptr，并且优先 make_shared。」

🧑‍🎓 常见追问（能答上就是加分）

Q：weak_ptr 怎么知道对象死没死？ 控制块还活着（弱计数 > 0），lock() 原子地检查强计数并尝试 +1，成功拿到 shared_ptr，失败返回空——所以控制块必须活得比对象久，这就是 2.3 图里"强弱都到 0 才拆牌子"的原因。

Q：类内部要拿到管理自己的 shared_ptr 怎么办？ 直接 shared_ptr<T>(this) 会造出第二个控制块→ 双删。正确做法：继承 std::enable_shared_from_this<T>，调 shared_from_this()（内部存了 weak_ptr）。

第 3 章 · 虚函数：行为谁做主P0 详讲 · 超高频（C++ 面试的钉子户）

3.1 为什么出现：静态绑定 vs 动态绑定

场景：你写了一个通用的 draw(Shape* s) 函数，希望传 Circle 就画圆、传 Square 就画方。函数参数类型是 Shape*（编译期确定），实际对象是 Circle（运行期才知道）——调谁的 draw？C++ 默认的答案是静态绑定：看指针/引用的声明类型，编译期就定死调 Shape::draw。要改成「看实际对象类型」，必须显式声明 virtual，切换到动态绑定。

🏠 比喻：说明书 vs 查户口

静态绑定 = 看说明书（声明类型）：「这东西登记的是 Shape，那就按 Shape 的说明书办事」，编译期一锤定音，快但死板。动态绑定 = 查户口（实际对象）：先到对象家里翻出户口本（vptr 指向的 vtable），按真实身份办事。查户口要多跑一趟（两次内存间接跳转），这就是动态绑定的成本。

🔧 Python 对照（你熟的那套）

Python 里每个方法调用都是动态绑定：obj.draw() 运行时查 type(obj) 的 MRO。C++ 反过来：默认全是静态绑定，只有标了 virtual 的函数才走查表——「C++ 是手动挡的 Python 动态派发」。代价换收益：非虚调用可内联、零开销；虚调用多两次间接寻址。

🔧 展开：「Python 每次都查」「C++ 静态绑定」具体在干什么

Python——是的，每次都查。obj.draw() 每执行一次，解释器都走一遍「取 type(obj) → 沿 MRO 找 draw → 取到函数对象 → 调用」。哪怕循环里调一万次，这个查找动作每次都发生（CPython 内部有 inline cache 加速，但语义上就是每次查）。因为 Python 变量只是名字、对象一出生类型就焊死，所以只能每次按真实类型现场查。

C++ 静态绑定——不是「在 vtable 里说明是什么类型」，而是压根不查表。编译器生成机器码时，直接把目标函数的地址写死在 call 指令里：它看到 s 的声明类型是 Shape*，就生成「call Shape::draw 的固定地址」。运行时不管 s 实际指向 Circle 还是 Square，都跳那个写死的地址。所谓「编译期定死」= 查表动作在编译期就完成了、结论被烧进了机器码。

C++ 动态绑定（标了 virtual）：call 的目标不再是写死的地址，而是一小段「取对象头部 vptr → 取 vtable 第 N 格 → 跳过去」。查不查表，就这一个差别。

Shape* s = new Circle;
s->draw();
// draw 没标 virtual 时，编译器生成的指令大意：
//   call 0x4012a0        ← Shape::draw 的地址，编译期写死。s 是谁？不关心
// draw 标了 virtual 时：
//   mov rax, [rdi]       ← 取对象头 8 字节，即 vptr（rdi 是 this/s）
//   call [rax+0]         ← 跳到 vtable 第 0 格里存的地址（Circle::draw）
// Python 语义上每次都做的是第二种查找，只是查的字段是 type(obj) 而非 vptr

3.2 vtable/vptr 机制：多态的三个角色

🔧 机制
  1. 每个「有虚函数的类」一张虚函数表（vtable）：编译期生成，放在只读数据段，存的是该类各虚函数的实际地址——类比 Python 的 type.__dict__（类级、全类共享一份）；
  2. 每个对象一个虚表指针（vptr）：藏在对象头部（前 8 字节，64 位），构造时由该类的构造函数设成指向自己类的 vtable——类比 Python 每个对象的 ob_type；
  3. 虚调用三步：取对象的 vptr → 在 vtable 里按槽位（slot）找到函数地址 → 间接调用。槽位在编译期已按声明顺序定死。
一次虚调用的完整链路：s->draw() 实际发生了什么
Shape 声明两个虚函数 draw/area；Circle 重写了两者；Square 只重写 draw
⛔ sizeof 三连（面试数字题）
  • 空类 sizeof = 1：不为 0 是为了保证不同对象地址不同（各占至少 1 字节）；
  • 空类 + 一个虚函数 = 8（64 位）：多出的 8 字节就是 vptr（不是虚表！虚表全类一份，对象里只存指针）；
  • 有成员再加虚函数：成员大小向 8 对齐后 + 8。虚函数个数不影响对象大小（表在类级）。

3.3 虚析构函数：为什么基类析构必须 virtual

这是虚函数考点的最高频变体。场景：你用多态方式管理对象（几乎总是如此，如容器里放 unique_ptr<Shape>），delete 的是基类指针——如果基类析构不是 virtual，静态绑定生效：只调基类析构，派生类析构被跳过，派生类申请的资源全泄漏。

struct Base {
    ~Base() { puts("~Base"); }              // ❌ 非虚析构
};
struct Derived : Base {
    int* big_ = new int[1'000'000];
    ~Derived() { delete[] big_; puts("~Derived"); }
};
Base* p = new Derived;
delete p;     // 只打印 ~Base！Derived::~Derived 没执行 → big_ 泄漏 4MB
// 修复：Base 里写 virtual ~Base() = default;  → 先 ~Derived 再 ~Base ✅
🔧 机制

析构函数走的是和普通虚函数一样的 vtable 槽位。虚析构时，编译器生成的 delete 序列是：查 vptr → 调最派生类的析构 → 析构函数自动沿继承链逐层向上调基类析构（所以你从没手动写过 ~Base() 调用）。一句口诀：「要么基类析构 virtual，要么保证不被多态地 delete」——后者的检查人是编译器管不了的，所以工程上一律给多态基类虚析构。

🧑‍🎓 追问：构造函数为什么不能是虚的？

因果倒置：虚调用依赖 vptr，而 vptr 是构造函数运行时才设置的——蛋还没下就想靠孵蛋器？反过来析构可以虚，因为析构时对象（和 vptr）已经完整存在。

⛔ 展开：构造/析构函数里调虚函数，调的是「当前层」的版本
struct Base {
    Base() { draw(); }              // 构造函数里调虚函数！
    virtual void draw() { puts("Base::draw"); }
};
struct Derived : Base {
    int* cache_ = new int[100];     // Derived 自己的成员
    void draw() override { puts("Derived::draw"); cache_[0] = 1; }
};
Derived d;   // 打印 Base::draw，不是 Derived::draw！

逐步看 Derived d; 内部的时序：① 先跑 Base 的构造函数，此刻 vptr 被设成指向 Base 的 vtable——对象现在「还是个 Base」；② Base() 里调 draw() → 查表查到的自然是 Base::draw；③ Base 构造完，才轮到 Derived 的部分：vptr 改指 Derived 的 vtable、初始化 Derived 的成员、跑 Derived 的构造函数体。析构完全倒序：一进 ~Derived() 之后再往上走，vptr 也逐层改回去——在 ~Base() 里调 draw() 同样只会到 Base::draw。

为什么这样设计：Base() 执行时 Derived 的成员（cache_）还是垃圾，若调到 Derived::draw（它一上来就写 cache_[0]）等于访问未初始化内存。语言规定「构造到哪层，就当哪层用」，用失去多态换安全。

Python 对照（重要差异）：Python 的 __init__ 里调 self.draw() 会调到子类版本——因为 Python 对象一出生 ob_type 就焊死成 Derived，不存在「先当父类再变子类」的过程。所以「父类 __init__ 调了可被重写的方法、子类一重写父类初始化就被劫持」是 Python 的经典坑；C++ 用「构造期不做多态」直接把这类坑堵死了。两边是同族坑的两种处理。

3.4 构造/析构顺序：对仗工整的两个清单

顺序记忆法
构造① 基类（按继承声明顺序）→ ② 成员变量（按类内声明顺序，不是初始化列表顺序！）→ ③ 本类构造函数体先打地基，再装家具，最后拎包入住
析构完全倒序：① 本类函数体 → ② 成员（声明倒序）→ ③ 基类退房反着来：先搬自己东西，再拆家具，最后拆地基
⚠️ 展开：什么是「初始化列表」+ 那个经典坑（零基础版）

初始化列表 = 构造函数参数括号后面、花括号前面，以冒号开头的那一串，作用是「成员出生时就带值」：

class A {
    int b;        // ←「声明顺序」指的是这里：成员在 class 里的书写先后
    int a;        //    先写 b 后写 a → 编译器永远先造 b、后造 a
public:
    A() : a(1), b(a) {}   // ← 冒号后这串就是「初始化列表」
};

相当于 Python 在 __init__ 里写 self.a = 1。但 C++ 有条反直觉规则：实际初始化顺序只看 class 里的声明顺序，初始化列表里写的先后不算数。上例虽然列表里 a 写在前，真实执行却是——第一步 b(a)：此刻 a 还没轮到初始化、值是垃圾，b 被填了垃圾；第二步 a(1)：a 这才变成 1。结果 b 里躺着垃圾——这就是那条「未定义行为」的坑。修法：让声明顺序和依赖关系一致（int a; int b;），或别用成员初始化成员。

和「构造函数体里赋值」的区别：列表是初始化（出生即带值，一步到位）；函数体里写 a = 1; 是先默认初始化、再赋值（两步，类类型成员白付一次默认构造）。const 成员和引用成员只能用列表初始化（它们出生后不可再赋值）。面试答「区别」时就答这两条 + 声明顺序坑。

为什么语法长这么怪（对比 Python 的 A(a=1, b=a)）——三个疑问一次答清：

  • { } 是函数体，不是返回值：构造函数没有返回值。A() : a(1) { } 的 { } 相当于 Python def __init__(self): 冒号后面的 body。执行顺序：先跑列表（成员全部出生带值）→ 再跑函数体（后续逻辑：校验、计算、打印）。{ } 空着 = 函数体啥也不干，纯靠列表。
  • 为什么初值放"外面"而不塞进参数括号：C++ 把「成员出生」和「出生后干活」拆成两个阶段，列表专管前者。非拆不可的原因：const 成员、引用成员、没有默认构造的成员类型必须出生那一刻就带值——函数体里的 a = 1; 对它们属于「先出生再赋值」，直接非法。Python/Java 的字段都是先出生（None / null）再随便赋值，所以根本用不上这个语法。
  • 为什么声明顺序说了算、列表顺序不算：析构必须按构造的严格倒序（后出生的先死——否则可能出现「a 还被 b 依赖着，a 先死了」）。但一个类可以有多个构造函数，每个构造函数的列表顺序可以写得不一样——若按列表顺序构造，同一类的对象构造顺序就不唯一，编译器要生成的析构顺序就没了唯一依据。所以语言锚定一个全类唯一不变的东西：成员声明顺序。列表只是「给谁塞了初值」的购物清单，不是执行顺序。工程规矩：列表书写顺序永远抄声明顺序，肉眼顺序 = 实际顺序，坑就消失了。
🎭 面试作答

「讲讲虚函数机制」60 秒版：「虚函数解决的是『基类指针调用派生类实现』的多态问题。实现上是三层结构：每个含虚函数的类有一张编译期生成的 vtable，存该类各虚函数的实际地址；每个对象头部藏一个 vptr，构造时指向本类的 vtable；虚调用就是取 vptr、查表、间接调用三步。所以有虚函数的类 sizeof 会多 8 字节——那是 vptr 不是虚表，虚表是类级共享的。基类析构必须 virtual，否则 delete 基类指针只会执行基类析构，派生类资源泄漏。C++ 默认静态绑定，这点和 Python 正好相反——Python 每次调用都查类型，C++ 只在 virtual 时查表。」

P2 一句话区：纯虚函数 virtual void f() = 0 定义抽象类（不能实例化）；override 显式标记重写、final 禁止再重写/继承；菱形继承与虚继承见附录 A。

4.1 深浅拷贝与三/五法则

🔧 先补课：拷贝构造 / 拷贝赋值 / 移动构造 / 移动赋值是四个什么函数

先别管深浅，这四个名字 = 「构造 vs 赋值」×「复印 vs 搬家」两个维度的组合。它们都是类里的特殊成员函数，你不写编译器就默认给一份（默认版对指针成员做浅拷贝——这正是问题的起点）。你不手动调用它们，编译器在你写出对应代码时自动调：

四个函数长这样你写出什么代码会触发它干了什么
Buf(const Buf& o)
拷贝构造		Buf b = a;
或按值传参 f(a)		用旧对象造出一个新对象（复印一份）
Buf& operator=(const Buf& o)
拷贝赋值		b = a;（b 早就存在）把旧对象内容抄进一个已有对象（贴到旧纸上）
Buf(Buf&& o)
移动构造		Buf c = std::move(a);用旧对象造新对象，但不复印——把家当直接搬走（4.2 详讲）
Buf& operator=(Buf&& o)
移动赋值		c = std::move(a);把旧对象家当搬进一个已有对象

Python 对照（关键！）：Python 的 b = a 只是把名字 b 挂到 a 指的那个对象上——既没复制对象也没复制引用，只是起了个别名；想真复制得 copy.deepcopy(a)。C++ 的 Buf b = a; 是真·复制出一个新对象（必然跑拷贝构造），想「起别名」得写 Buf& r = a;（引用）。分清这一条，四个函数就只剩两个维度了：造新的（构造）还是灌进旧的（赋值）× 复印（copy）还是搬家（move）。

右边的东西
有名字（左值）没名字（右值 / 被 move）
左边的变量还不存在
（首次亮相）		拷贝构造
Buf b = a;		移动构造
Buf c = std::move(a);

常见误解校准：「有名字=拷贝、没名字=构造」把两件事混成了一句。右边有没有名字，决定拷贝还是移动；左边存不存在，决定构造还是赋值——两个独立的问题，对着上表十字定位。另注意：inner(x) 传参本质是「用 x 构造参数 s」（参数是个新对象），走的也是拷贝/移动构造——这正是 4.3 完美转发要解决的问题。

场景：一个对象内部有 int* data_ 指向堆内存。默认拷贝（拷贝构造/拷贝赋值）是逐成员复制——指针被复制的是地址，不是地址上的东西。于是两个对象指向同一块堆内存，析构时 delete 两次，崩溃。

🏠 比喻：合租 vs 分居

浅拷贝 = 合租：两个人共用一个冰箱（堆内存），退租时都想把冰箱搬走（双删）。深拷贝 = 分居：搬走前新买一台一模一样的冰箱（重新分配并复制内容），各搬各的。移动 = 直接把整个房子过户：原房主拿到钥匙就跑（见 4.2）。

class Buf {
public:
    Buf(size_t n) : data_(new int[n]), n_(n) {}
    // 深拷贝：分居，新买冰箱
    Buf(const Buf& o) : data_(new int[o.n_]), n_(o.n_) {
        std::copy(o.data_, o.data_ + o.n_, data_);
    }
    Buf& operator=(const Buf& o) {   // 赋值：先自检、再释放旧的、再深拷
        if (this != &o) { delete[] data_; /* …同上… */ }
        return *this;
    }
    ~Buf() { delete[] data_; }        // 析构：退租关灯
private:
    int* data_; size_t n_;
};
🔧 三法则 / 五法则（Rule of Three / Five）

如果你需要手动写 析构函数、拷贝构造、拷贝赋值中的任何一个，那几乎肯定三个都需要（典型信号：类直接管理裸资源）。C++11 追加移动两件套成五法则：析构 + 拷贝构造 + 拷贝赋值 + 移动构造 + 移动赋值。现代答案是 Rule of Zero：类里只用 string/vector/智能指针管资源，五个全不用写——编译器生成的版本全部正确（还能白得移动语义）。

P2 一句话区：RVO/NRVO（返回值优化）——函数按值返回局部对象时，编译器直接在调用方的内存上构造，连 move 都省了；C++17 起 PRV（纯右值）场景强制省略拷贝。被追问再展开，见附录 A。

4.2 右值引用与 move 语义：搬家 vs 复印

为什么出现：临时对象（如函数返回的 string、字面量拼出来的串）马上就要销毁，深拷贝它纯属浪费——反正原主一会儿就死了，直接把家当搬走。C++11 用「右值引用 &&」把「即将死亡的值」标记出来，让重载决议选中「搬家版」构造/赋值。

🏠 比喻：退租甩卖

租客 A 明天就退租（右值，将亡值），他的冰箱对你（新对象）有两条路：复印（深拷贝：买台一样的，A 的冰箱随他扔）或过户（move：直接把 A 的冰箱搬走，A 房间留个空壳）。std::move 不是搬东西的动作，只是给 A 盖了个「明天退租」的章（把左值强制转型成右值引用），真正搬家发生在搬家公司的合同里（移动构造/移动赋值）。搬完之后 A 是「有效但未指定」状态——能析构、能重新赋值，但别假设里面还有东西。

std::string a = "一串很长很长的........................文本";
std::string b = a;              // 拷贝：a 原封不动，b 深拷贝一份（O(n)）
std::string c = std::move(a);   // 移动：c 掏空 a，只偷指针+长度（O(1)）
// 此后 a 变空壳（实现相关，通常是空串）——别再用它的内容

// vector 扩容时的收益（连接第 6 章）：
// C++11 起，vector 增容搬元素用移动而非拷贝——string 列表扩容从 O(n·串长) 降到 O(n)
展开：零基础版——「左值/右值」是啥？std::move 到底干了啥？搬家的代码长什么样？

先补两个词。左值：有名字、之后还要用的东西（变量 a）。右值：没名字的临时值——"hello" + " world" 拼出来的临时串、函数按值返回的临时对象，用完这一行就销毁。

std::string a = "hello";              // a 是左值：有名字，后面还要用
std::string t = "hello" + " world";   // 右边先拼出临时串（右值）再拷给 t
                                       // 临时串马上要销毁——深拷贝它纯属浪费

std::move 的真身（它真的什么都没搬）：它只是一次强制类型转换，把 a 的「标签」从左值改成右值引用：

std::string c = std::move(a);
// std::move(a) 等价于 static_cast<std::string&&>(a) —— 只改标签，一个字节都没动
// 改标签的唯一作用：让编译器在「拷贝构造 vs 移动构造」二选一时选中移动版

真正的搬运发生在移动构造函数里（库作者写好的），代码大意就三步：

string(string&& o) {      // 移动构造：参数是「将亡值」的引用
    data_ = o.data_;       // ① 偷指针：把指向堆内存的指针拿过来，不复制内容
    size_ = o.size_;       // ② 偷长度
    o.data_ = nullptr;     // ③ 源置空：防止 a 析构时把这块内存 free 掉（现在归 c 了）
}
// 所以是 O(1)：只做了三次赋值，一个字节的内容都没复制
// a 变「空壳」也是 ③ 造成的：指针被拿走，它手里什么都没有了

串起来看全程：std::move(a) 盖章 → 编译器选移动构造 → 移动构造偷指针并置空 → a 成空壳。「盖章 → 选中搬家合同 → 搬家公司进场」三步分别发生在三个地方。

⛔ 高频陷阱

对同一个对象 move 两次 = 第二次从空壳里搬，通常搬出空/垃圾。move 完的对象只能析构或重新赋值。const T&& 万万不能当移动参数——const 挡住了「掏空」操作，重载决议反而落回深拷贝版本。

🔧 右值引用的价值不在单个参数，在「重载配对分流」

单独看 void f(string&& x) 没什么用——它只是「只接收将亡值」的门槛。真正的价值是同一个函数名配两个版本，让编译器自动分流：

void push_back(const string& x);   // 版本一：左值走这 → 拷贝（源还要用，不敢动它）
void push_back(string&& x);        // 版本二：右值走这 → 移动（源是将亡值，放心偷）

vec.push_back(a);                  // a 有名字（左值）→ 编译器自动选版本一
vec.push_back(make_str());         // 返回值没名字（右值）→ 自动选版本二（偷指针）

没有 && 那个版本时，右值也只能进 const& 版被深拷贝——白扔了「源反正要死」的情报。所以记忆口径：右值引用不是「保证不拷贝不移动」，恰恰是给「移动版函数」一个存在的签名锚点，让编译器有地方把将亡值分流过去。vector::push_back、string 拼接、容器插入全是这套双版本。

🎭 面试作答

「什么是 move 语义」30 秒版：「move 语义解决临时对象被无谓深拷贝的问题。右值引用 T&& 绑定将亡值，让类提供『搬家版』构造/赋值：不复制资源，只偷指针，源对象留空壳，O(n) 变 O(1)。std::move 本身不移动任何东西，只是把左值 cast 成右值引用、触发重载决议选移动版。典型收益场景是 vector 扩容和容器传大对象。」

4.3 完美转发：把参数「原样」传下去

场景：你写一个中间人函数（工厂、包装器、线程池投递），收到参数后要转交给真正的构造函数/处理函数。麻烦来了：

void inner(std::string s);              // 真正干活的函数（按值接收）

void wrapper(std::string&& x) {          // 中间人：哪怕参数类型写成右值引用
    inner(x);                           // ❌ 这里走的还是拷贝！
}
// 为什么？C++ 规定：只要一个东西「有名字」，它就是左值——
//   x 虽然类型是 string&&，但它有名字，所以 inner(x) 匹配的是拷贝版
//   右值传进来，过一道手就「降级」成左值，白白浪费了

解法是两个配件配合：

template <typename T>
void wrapper(T&& x) {                    // ① 万能引用：模板推导语境下的 T&&，
                                         //    左值来了推导成 T&，右值来了推导成 T&&
    inner(std::forward<T>(x));           // ② forward：按推导出的原始属性转交——
}                                        //    x 原来是右值 → 转出去还是右值（走移动）
                                         //    x 原来是左值 → 转出去还是左值（走拷贝）
// 对比 std::move(x)：无条件转右值（左值来了也被强搬，会出事故）
// std::forward<T>(x)：有条件转——「原样转交」，这就是「完美」二字的含义
🎭 面试作答（30 秒）

「完美转发解决的是参数过中间人函数时右值降级成左值的问题。万能引用 T&& 在模板推导下左值右值都能绑、并记住原始属性；std::forward<T>(x) 据此原样转交。一句话区分：move 是无条件转右值，forward 是有条件转。」

4.4 lambda：匿名函数对象

int base = 10;
auto f1 = [base](int x) { return base + x; };     // 按值捕获：拷贝一份进闭包
auto f2 = [&base](int x) { return base + x; };    // 按引用捕获：用原变量（注意悬垂！）
auto f3 = [=](int x) { return base + x; };        // 全部按值
auto f4 = [=, &base](int x) { return base + x; };// 默认按值，base 例外按引用
// 本质：编译器生成一个匿名类，捕获变量 = 该类的成员变量，lambda 体 = operator()
//        [base] 等价于 class __F { int base; int operator()(int x) const {...} };
展开：看不懂「匿名类 / operator()」的从这里进（零基础版）

先补一个 C++ 前置知识：这个语言里「能加括号调用的东西」除了函数，还有一种——给类定义一个名字就叫 operator() 的成员函数，这个类的对象就能当函数用，术语叫「仿函数」：

struct Adder {                       // 一个普通类，没什么特别
    int base;                        // 成员变量：肚子里记住一个数
    Adder(int b) : base(b) {}        // 构造：把数存进肚子
    int operator()(int x) const {    // 关键：成员函数硬取名叫 operator()
        return base + x;             //   用肚子里的数 + 参数算结果
    }
};
Adder f(10);      // 造一个对象，肚子里存着 10
f(5);             // 对象居然能加括号调用！= f.operator()(5) = 15

现在把 lambda 和 Adder 摆在一起，逐项对应：

auto f1 = [base](int x) { return base + x; };
// 编译器在背后替你生成的，就是 Adder 那样的一个类：
//   [base]        → 类里多一个成员变量 int base（按值捕获 = 拷贝一份存进对象肚子）
//   [&base]       → 成员变成 int& 引用（不拷贝，直连原变量）
//   (int x){...}  → operator() 的参数表和函数体
//   f1(5)         → 调 f1.operator()(5)
// 「匿名类」= 这个类没名字、你没写过、编译器自动生成——所以叫匿名

所以「lambda 本质是匿名类」展开就一句：你写 lambda，编译器替你写一个只此一处的小仿函数类；捕获的变量变成它的成员变量，lambda 体变成它的 operator()。这也顺带解释了悬垂捕获为什么危险：按引用捕获 = 成员是个引用、绑着外面的局部变量；局部变量随栈帧销毁后，f1 这个对象还活着，但它肚子里的引用指的东西没了——再用就是访问废墟。

⚠️ 两个高频追问

① 悬垂捕获：按引用捕获局部变量后，lambda 活得比它长（如存起来异步执行），变量随栈帧销毁 → 引用失效。异步回调默认按值捕获。

② mutable 是干嘛的——先看现象再讲原因：

int hits = 0;
auto bad = [hits]() { return ++hits; };          // ❌ 编译错误！
auto ok  = [hits]() mutable { return ++hits; };  // ✅ 加 mutable 才编译通过
// 原因回到上面的仿函数对照：[hits] 生成的类是
//   struct __F { int hits; int operator()() const { ... } };
//                                    ↑ 这个 const =「承诺不改任何成员变量」
// ++hits 要改成员 hits → 和承诺冲突 → 编译器拒绝
// mutable = 把 operator() 的 const 撤掉 → 承诺作废 → 能改了
// 注意：改的永远是闭包肚子里的那份副本，外面的 hits 毫发无损

「hits 明明没写 const，哪来的冲突？」——冲突不来自 hits 本身，来自函数签名末尾那个 const：int operator()() const 的尾部 const 修饰的是隐含的 this 指针（把它变成 const __F*）。函数体里的 hits 其实是 this->hits——经过 const 的 this 一看，它眼里的 hits 就是 const int，++ 不了。一句话：成员没变 const，是「从 const 成员函数里看出去」它变 const 了。这条规则对所有成员函数生效：const 成员函数里改任何普通成员，报的都是同一个错。

5.1 static 四连问：一个关键字，四种身份

位置效果一句话

void visit() {

class Conn {

5.3 四种 cast：为什么弃用 C 风格强转

cast用途检查时机一句风险评级
static_cast数值转换、上行转换（派生→基类）、void* 还原编译期常用；下行转换（基类→派生）它能转但不查真实类型，转错=UB
dynamic_cast多态类型的下行/交叉转换运行期（RTTI）指针失败返回 nullptr、引用失败抛 bad_cast——代价是查 RTTI；要求基类有虚函数（没有 vtable 没得查）
const_cast加/去 const编译期唯一能去 const 的；但改真正只读对象仍是 UB——合法用途是「对接忘了写 const 的老 API」
reinterpret_cast位模式重解释（指针↔整数、不相关指针互转）无检查核弹级：说「我知道我在干嘛」；网络协议解析/硬件映射才用

光看表没用，每种 cast 配一段「什么场景、写出什么代码、会发生什么」：

// ① static_cast：日常"讲道理"的转换（数值、void* 还原）
double d = 3.9;
int i = static_cast<int>(d);          // 3，砍小数——等价 Python 的 int(d)
void* raw = malloc(64);
int* p = static_cast<int*>(raw);      // malloc 返回 void*，必须还原回具体类型才能用

// ② dynamic_cast：多态类型"验明正身"的下行转换（基类指针 → 子类指针）
Shape* s = new Circle;                // 你手里是基类指针，但想调 Circle 独有的方法
if (Circle* c = dynamic_cast<Circle*>(s))    // 运行期查户口：s 真是 Circle 吗？
    c->setRadius(5);                  // 是 → 转换成功，安全调 Circle 独有方法
// 若 s 实际是 Square → 返回 nullptr，if 不进——不崩、可控降级
// 这就是它比 static_cast 强的地方：static_cast 也能转基类→子类，但它不查，
// 转错了照样给你个假指针，一用就未定义行为

// ③ const_cast：专门加/去 const（唯一合法高频场景 = 接忘写 const 的老 API）
void oldApi(char* s);                 // 十年前的老代码，参数忘了写 const
const char* msg = "config";
oldApi(const_cast<char*>(msg));       // 不转编译不过；前提是你确信 oldApi 不改内容

// ④ reinterpret_cast：按位重解释，网络协议解析才用
uint8_t packet[4] = {0x12, 0x34, 0x56, 0x78};
uint32_t* asInt = reinterpret_cast<uint32_t*>(packet);  // 这 4 个字节直接当 int 读
// 「这段字节流按头部结构体解释」——网络/二进制协议解析的日常，别处别用

5.5 * / & / &&：同一个符号的三种角色

这三个符号最混淆的根源：同一个符号在「声明里」和「表达式里」是两个完全不同的东西。判断角色只看位置：

符号写在声明里（类型位置）写在表达式里（语句位置）
*指针类型：int* p;（p 是存地址的变量）解引用：*p（顺着地址取里面的东西）
&左值引用（别名）：int& r = a;取地址：&a（拿到 a 的地址，类型 int*）
&&右值引用（绑将亡值，见 4.2）；模板推导语境下成万能引用（见 4.3）（表达式里没有对应用法）
int a = 10;
int* p = &a;     // & 在表达式里：取 a 的地址，塞给 p（* 在类型里：p 是指针）
int& r = a;      // & 在类型里：r 是 a 的别名，此后 r 就是 a
int b = *p;      // * 在表达式里：顺着 p 里的地址取值 → 10

指针的问题清单（被问「指针有什么坑」的答题弹药）：① 可能为空（用前必须判空，引用天生免检）；② 可能悬垂（指向的对象已死：返回局部变量地址、delete 后继续用）；③ 可被随意拷贝（两个指针指向同一块堆内存，双双 delete = 双删崩溃）；④ 算术越界（p+10 没人检查）。

第 6 章 · STL 容器高频P0 详讲 · vector/map/迭代器失效是钉子户

6.1 vector：三指针与扩容倍增

🔧 机制：vector 就是三个指针

vector 内部只有三个指针：_start（数据开头）、_finish（已用末尾）、_end_of_storage（容量末尾）。size() = _finish - _start，capacity() = _end_of_storage - _start。连续内存是它一切特性的根：随机访问 O(1)、缓存友好、但中间插删要搬移元素。

扩容：push_back 时 size == capacity，就申请一块更大的内存（GCC 2 倍、MSVC 1.5 倍），把旧元素搬过去（C++11 起用移动，呼应 4.2），释放旧内存。为什么倍增而不是 +1：若每次只加 1，n 次 push_back 总搬运量 1+2+…+n = O(n²)；倍增让总量收敛到 O(n)，单次均摊 O(1)——和 Python list 扩容、Redis 字典渐进 rehash 是同一个思想。

⚠️ 扩容 = 全体迭代器/指针/引用作废

旧内存整块释放，所有指向旧元素的迭代器、指针、引用全部悬垂。这是「vector 插入会使迭代器失效」的根因，也是 6.2 大全表的第一行。

7.2 条件变量与虚假唤醒

场景：消费者线程要等队列非空。忙等（while 轮询）烧 CPU；睡眠固定时间又慢。条件变量 = 「排队取号睡觉，柜台按号叫醒」：wait 时原子地「放锁 + 睡觉」（放锁是关键，抱着锁睡觉谁也生产不了），被 notify 后醒来重新抢锁、从 wait 处继续。

std::mutex m;
std::condition_variable cv;
std::deque<int> q;

void consumer() {
    std::unique_lock<std::mutex> lk(m);       // 必须 unique_lock（wait 要操作锁）
    cv.wait(lk, []{ return !q.empty(); });    // ← 等价于 while(!pred) wait(lk);
    int x = q.front(); q.pop_back();
}
void producer(int v) {
    { std::lock_guard<std::mutex> lk(m); q.push_back(v); }
    cv.notify_one();                          // 出锁后再叫号，减少被叫醒又抢不到锁的空转
}
🔧 看不懂 producer 里的裸花括号？——那是 Python 的 with 块
void producer(int v) {
    { std::lock_guard<std::mutex> lk(m); q.push_back(v); }
    //↑ 这对花括号 = 一个「局部作用域块」：块里声明的变量，出块就销毁
    cv.notify_one();
}

C++ 允许在任何地方用一对 { } 圈出一块作用域。这行代码的完整含义：lock_guard 在块内构造（= 加锁），push_back 干活，然后出块 → lk 析构 → 自动解锁。等价的 Python 写法就是：

def producer(v):
    with lock:            # 进块加锁
        q.append(v)
    # 出块自动解锁
    cv.notify()

为什么要圈这么小：精确控制锁的持有范围——数据塞完立刻放锁。notify 特意留在块外：它不碰队列、不需要锁；而且若抱着锁 notify，被叫醒的消费者立刻抢锁必然失败、白醒一场。先放锁再叫号，被叫醒的人才有机会直接拿到锁——这就是注释「出锁后再叫号」的意思。

⛔ 为什么必须用循环/谓词（虚假唤醒）

两个原因：① OS 层虚假唤醒——pthread 实现允许没 notify 也醒（性能原因），醒了队列可能还是空的；② 丢失/抢占唤醒——notify_one 叫醒多个等待者抢锁时，别的消费者可能抢先把你等的那条数据拿走了（惊群后白醒）。所以醒来后必须重查条件，不满足接着睡。wait(lk, pred) 就是官方封装的 while 循环。

🧑‍🎓 高频追问：为什么 wait 必须持锁？

等待的条件本身（队列）是共享数据，不持锁地「查条件→睡觉」两步之间可能被生产者插队：刚查完空、还没睡下，对方塞了数据还 notify 了——然后你才睡下，这个唤醒就丢了，可能永远睡死。wait 的「放锁+睡觉」原子性就是为了关死这个窗口。这也是「为什么 wait 要把锁交出去」的镜像答案：不放锁，生产者进不了临界区，永远没法 notify。

7.3 atomic 与 CAS：无锁计数器

为什么 counter++ 多线程不安全：它看着是一行，实际是「读-改-写」三条机器指令：

counter++;   // 编译成三条指令：
             //   ① 从内存把 counter 读进寄存器
             //   ② 寄存器里的值 +1
             //   ③ 把寄存器写回内存

两个线程的各三条指令可以任意交错，丢更新就丢在交错上：

counter 初始 5，A、B 各执行一次 ++，期望结果 7
线程A                     线程B
① 读到 5
                          ① 读到 5        ← B 也在 5 的基础上读
② 加 1 → 6
                          ② 加 1 → 6
③ 写回 6
                          ③ 写回 6        ← 两次 ++ 只涨了 1，B 把 A 的更新覆盖了
🔧 和 Redis 什么关系——同一个问题的两种命运

「读-改-写不是原子的」这个问题你在 Redis 那里见过：为什么 Redis 的 INCR 是原子的？因为 Redis 单线程执行命令——一个 INCR 的读改写独占完成，中间插不进另一个客户端的 INCR，相当于「天然有人排队，三步不被打断」。C++ 多线程没有这个保护，得自己造原子性：mutex = 自己拉排队栏杆把三步圈起来；atomic = CPU 原子指令把三步焊成真·一条指令。一句话：Redis 靠单线程躲开、C++ 靠原子指令/锁解决——同一个问题的两种工程解。

所以解法分两档：

  • mutex：互斥整段代码，重（涉及内核态 futex 切换）；
  • atomic：单个变量的原子读改写，CPU 单指令级（x86 的 lock 前缀），轻。std::atomic<int> 的 ++、load()、store() 都是原子的。
🔧 CAS（Compare-And-Swap）：无锁结构的积木

compare_exchange_weak/strong(expected, desired)：值还等于 expected 就换成 desired 返回 true，否则把当前值写回 expected 返回 false。典型用法是自旋重试：读旧值 → 算新值 → CAS 装入，失败说明被人抢了，重读重试。乐观锁思想——和 MySQL 的 CAS 更新、Redis 的 WATCH/Lua 是同一族。ABA 问题一句话带过（值变回去了但中间换过人，加版本号解决），见附录 A。

内存序（memory_order）：atomic 才有的深水区。面试安全答法：「我知道有 relaxed / acquire-release / seq_cst 三档，平时全用默认 seq_cst（顺序一致、最稳），只有压测确认同步开销成为瓶颈才考虑降档——降档需要严格论证，一般交给库作者。」这句既诚实又不掉分。

7.5 线程安全单例：现代标准答案只有一行

class Singleton {
public:
    static Singleton& instance() {
        static Singleton inst;      // ← Meyers 单例：C++11 起局部 static 初始化线程安全
        return inst;                //    标准保证：并发首次调用也只初始化一次（编译器用锁/守护变量实现）
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() = default;
};
🔧 为什么不用「双重检查锁」了

老答案 DCLP（Double-Checked Locking）在 C++11 前是错误的：instance = new T 是「分配→构造→赋指针」三步，无内存序约束下别的线程可能看到「指针非空但对象没构造完」。C++11 用 atomic + acquire/release 才能写对，但既然局部 static 已被标准保证线程安全，现代答案就是上面那一行。面试若被追问 DCLP，答出「三步重排序问题 + C++11 局部 static 由标准兜底」即是满分。

线程基础一句话带过：std::thread 构造即启动；不 join 就析构会 std::terminate，要么 join 要么 detach；detach 后线程对象不再管它（野线程，资源随进程回收）。async/future 属 P2，见附录 A。

8.3 函数重载与 extern "C"：name mangling

🔧 机制

为什么 C++ 能重载而 C 不能：链接器只认符号名。C 的符号名就是函数名——两个 max 必撞。C++ 编译器把参数类型编码进符号名（name mangling），如 max(int,int) → _Z3maxii、max(double,double) → _Z3maxdd——链接器眼里是两个不同符号。这也解释了：① 重载不算「同名函数」而是「不同符号」；② 函数返回值不参与编码（mangling 只看参数，返回值不同的重载会撞符号）。

extern "C" = 告诉编译器「这段代码按 C 规则出符号、别 mangle」：C++ 调 C 库（如 dlfcn）、或写要被 C/dlsym 调用的插件导出函数时必须加。#ifdef __cplusplus extern "C" { #endif … 是头文件通用写法。

🔧 展开：inline 到底是啥意思（两层含义 + 相关词）

第一层（字面义：内联展开）：普通函数调用有开销（压参数、跳转、返回）。inline 的原始设想 = 把函数体原地复制到调用处，省掉调用开销——类似 #define 宏的文本替换，但有类型检查。现实：现代编译器根本不理会你写不写 inline，它自己按函数大小/优化级别决定谁内联。这层含义已名存实亡。

第二层（现代真实作用：ODR 豁免）：回到 8.1 的 multiple definition——在头文件里定义的函数会被 N 个 .cpp include，每个 .o 里都有一份定义，链接时撞车报错。inline 关键字是对链接器说：「这个符号允许在每个 .o 里各存一份，链接时随便挑一份用，别报错」。现代 C++ 写 inline 基本都是为了这层。

「撞车」撞的是什么——不是运行时阻塞：函数代码执行时根本没有互斥，一万个线程同时调同一个函数毫无问题（代码段只读、全场共享）。撞车发生在链接期：链接器的规矩是「一个符号全程序只许一份定义」，它看到 foo 在 100 个 .o 里各有一份，不知道该信谁的，干脆报 multiple definition 拒绝工作。inline 就是出示合法证明：「这 100 份一模一样，随便挑一份，别报错」。是链接器记账规矩的问题，与运行时行为无关。

「不是有导入路径吗？看路径挑一份不就行了」——不行，两个原因：① include 路径只决定预处理期文本从哪个文件复制过来——100 个 .cpp include 的是同一个头文件，复制出来的 100 份定义一字不差，链接器眼里它们不是「100 个候选」，是「同一份的 100 个复印件」，路径信息早在编译完成后就丢了（.o 里的符号只有名字如 _Z3foov，不带出身）；② 这条报错真正要防的是意外的同名冲突——两个程序员各自在自己的 .cpp 里写了 void init()，内容完全不同，链接器没有任何信息判断你想调哪个：挑哪个都是猜。既然「相同副本」和「不同实现撞名」从符号上看无法区分，唯一安全的策略就是一律报错，让相同的（inline 豁免）和不同的（改名）都由程序员显式表态。

要不要自己写：函数定义写在 .cpp 里——不用；定义写在头文件里（会被多个 .cpp include）——必须写（或利用类内定义的隐式 inline）；单纯想优化内联——不用写，写了也基本被无视。

相关词（面试黑话全家桶）：

  • ODR（单一定义规则）：每个符号全程序只允许一份定义——inline 是给这条规则开的合法例外通道；
  • inline variable（C++17）：变量也能 inline——头文件里定义全局变量不再撞链接；
  • 隐式 inline：类内直接写函数体的成员函数自动带 inline 属性——所以头文件的 class 里写函数体不报 multiple definition；
  • 强制内联：[[gnu::always_inline]] / MSVC __forceinline——逼编译器真内联（极少用）。

P2 一句话区：模板必须放头文件（实例化点需要看到完整定义）；动态库符号可见性 -fvisibility=hidden。

🏠 比喻：三种餐厅服务员

select = 服务员每上一轮菜都挨桌问一遍「好了吗？」——桌子还限 1024 张，人越多越累（每次全量拷贝+全表扫描）。poll = 同样挨桌问，但桌子数不限了。epoll = 前台登记制：客人入座登记（epoll_ctl ADD），服务员坐等叫号屏（就绪链表）——哪个桌好了屏上显示哪个（wait 直接返回就绪列表），一万桌也只看屏不看全场。

🔧 epoll 三个 syscall
  1. epoll_create1()：开一个 epoll 实例（内核里的「登记簿」：红黑树存所有被监听 fd + 就绪链表）；
  2. epoll_ctl(ADD/MOD/DEL)：登记/改/删一个 fd 及其关注事件——数据结构在内核常驻，不用每次重传；
  3. epoll_wait()：等就绪链表非空，返回就绪事件数组。fd 就绪时，内核把它挂进就绪链表（这是内核内部的动作，不涉及你的代码）——这就是「O(1) 拿就绪」的来源。
🔧 一次 epoll 服务的完整时间线（把理解对齐到这个流程上）
【启动期：注册一次，之后不再重复传 fd 列表 —— 这是 epoll 独有的】
线程   epoll_create1()             → 开一个 epoll 实例（内核登记簿）
线程   epoll_ctl(ADD, listen_fd)   → 把要盯的 fd 登记进登记簿
线程   epoll_ctl(ADD, conn_fd) ...

【运行期：事件循环，每一轮】
线程   epoll_wait(...)             → 线程在这里睡着（不耗 CPU）
内核   网卡收到数据 → 硬件中断 → 数据放进某 fd 的接收缓冲区
内核   该 fd 就绪 → 挂进这个 epoll 实例的就绪链表 → 唤醒睡着的线程
线程   wait 返回 → 手里拿到「就绪事件数组」（只有就绪的，不是全量）
线程   逐个处理事件：read / write / accept（新连接再 epoll_ctl ADD 进登记簿）
线程   处理完 → 回到 epoll_wait 继续睡，循环

常见误解逐条校准：

  • ❌「通过 socket 与 OS 进行连接」→ ✅ 你的代码（用户态）和内核的通道是系统调用——上面每一行线程动作都是一次 syscall。socket 本身就是内核里的对象，fd 只是它的编号（把手）；
  • ❌「内核把 fds 交给代码/回调」→ ✅ 没有回调到你的代码。你的线程睡在 epoll_wait 里，被内核唤醒后 wait 返回就绪列表，线程自己消费。「回调」只发生在内核内部挂链表那一步；
  • ✅「唤醒线程，让线程消费就绪列表」→ 完全正确，这就是 epoll 的核心；
  • ❌「三者都在一开始注册到内核」→ ✅ 只有 epoll 注册一次。select/poll 每一轮都要把全量 fd 拷进内核、扫完再拷回来——正是它们 O(n) 慢的根源（对比表第 2 行）；
  • △「IO 操作放入事件队列，线程切走」→ ✅ 纠正表述：不是「IO 操作在队列里」，是「就绪的 fd 事件在就绪列表里」。线程消费事件时做的是非阻塞读写（通常立刻完成）；只有耗时的业务逻辑才丢给线程池，然后事件循环线程回去继续 wait。

LT 水平触发（默认）ET 边缘触发

展开：一个具体场景把 LT/ET 的区别演出来（100 字节 / 每次只读 40 字节）

设定：fd 的接收缓冲区里来了 100 字节，你的 buf 一次只能读 40 字节。

LT 的剧本（水位高于线就一直响）：

第 1 轮 wait: 缓冲区 100 > 0 → 通知！  read → 读到 40，剩 60
第 2 轮 wait: 剩 60 > 0     → 又通知！ read → 读到 40，剩 20
第 3 轮 wait: 剩 20 > 0     → 又通知！ read → 读到 20，剩 0
第 4 轮 wait: 空了          → 安静
// 你每次只读一点也无所谓——没读完，下轮 wait 还会追着你提醒

ET 的剧本（上涨沿只响一声）：

第 1 轮 wait: 数据从 0→100 的瞬间 → 通知一次！
  如果你只 read 一次 40 字节就回去 wait……
第 2 轮 wait: 没有新数据到来 → 不通知！
  剩下的 60 字节永远躺在缓冲区里，这个连接被「饿死」
正确姿势：收到通知后循环 read 直到读空：
  read 40 → read 40 → read 20 → read 返回 EAGAIN（空了）→ 才回去 wait

为什么 ET 必须配非阻塞 fd：循环读靠什么知道「空了」？非阻塞 read 空了会立刻返回 EAGAIN（暂时没数据）；阻塞 read 空了会把线程卡死在原地等数据——一个 fd 卡住，整个事件循环全停摆。这就是上表「fd 要求」那一格的由来。

校准一个常见误解：阻塞模式压根没有 EAGAIN——空了就挂起等数据，不会给你返回值。「只读一次 40 剩 60 被饿死」的风险两种模式共有（都源于只读一次就走）；ET 配阻塞的独特死法是：循环读用来「确认空了」的最后一次 read 恰好碰上空缓冲 → 线程被钉死在内核里等新数据 → 整个事件循环停摆，所有连接全卡。

ET 图什么：每个事件只唤醒一次，高并发下事件量减半（省掉 LT「没读完反复提醒」的唤醒）——nginx 用的就是 ET。

展开：菱形继承与虚继承 / volatile（vs Java）/ RVO 三个高频追问详解

① 菱形继承与虚继承——和 Python MRO 不是一回事：

struct A { void f(); int x; };
struct B : A {};           // 普通继承：B 肚子里有一份 A
struct C : A {};           // C 肚子里也有一份 A
struct D : B, C {};        // D 肚子里有两份 A！
                           // d.f() → 编译报「请求歧义」：从 B 来的还是从 C 来的？
                           // d.x  → 两份实实在在占两份内存（数据冗余）

struct B : virtual public A {};   // 虚继承：手动标记
struct C : virtual public A {};   // → D 里 A 只有唯一一份（由最终类 D 负责构造）
struct D : B, C {};        // d.f() 不再歧义，d.x 只有一份

和 Python MRO 的本质区别：Python 的菱形只冲突方法查找顺序——MRO（C3 线性化）自动排一条链 D→B→C→A，查到第一个就用，全程自动，且数据天生只有一份（所有类共享布局）。C++ 的菱形先撞数据冗余：两份 A 的成员变量实打实占两份内存，方法调用默认不会自动二选一——直接编译报错，要你显式写 d.B::f() 消歧；虚继承解决的是数据合回一份（代价：对象里多一个 vbptr 偏移指针，运行期才能定位那个唯一子对象），方法选谁仍靠 virtual 函数或显式指定。一句话：Python 自动调解方法之争、数据天生一份；C++ 默认数据翻倍+编译报错，虚继承手动把数据合回一份。所以答案是：对，虚继承必须自己写，没有任何自动成分。

那方法到底选谁——按「候选个数」分三种情况：

  • 只有一个候选：f 只在 A 定义（B、C 都没碰）→ 调 A::f，不歧义——虽然普通继承下 D 肚子里有两份 A 子对象，但函数是同一个。只有 B 重写了 f → 调 B::f（B::f 支配 A::f），也不歧义；
  • 两个候选：B、C 都重写/新增了 f → B::f 和 C::f 打架，编译器拒绝猜，报「请求歧义」——必须显式 d.B::f() 或 d.C::f()；
  • 虚继承已加 + f 是 virtual：数据合成一份了，但方法解析规则一点没变——B、C 都重写时照样歧义、照样要显式指定。虚继承管数据，virtual 管行为，两套开关各管各的。

对比 MRO：Python 永远自动挑链上第一个，绝不报错；C++ 只在唯一候选时自动，有竞争就甩给你。设计哲学差异：Python「总得选一个」、C++「猜错比报错贵」。

② volatile：C++ 和 Java 同名不同义：

你记的 Java 比喻「每个工人有自己的记忆板」——记忆板的真身是 CPU 每个核心的私有缓存（L1/L2 cache，寄存器算一部分）：每个核改了变量先记在自己缓存里，别的核看不见 → 可见性问题。Java volatile = 「写立刻刷回主存 + 读都从主存拿 + 禁止指令重排」= 解决可见性 + 有序性，是真正的线程同步工具（但依然不保证原子性）。C++ volatile 只做一件事：「别把这个变量缓存进寄存器，每次都真读写内存」——它防的是编译器优化（比如把连续两次读合并成一次），设计给内存映射硬件/信号处理用；不管多核缓存一致性、不管原子性、不管顺序——拿它做线程同步是经典错误。跨语言对齐：Java volatile ≈ C++ 的 std::atomic（acquire-release 语义那族），和 C++ volatile 不是一回事。

③ RVO/NRVO（返回值优化）：

Buf make() {
    Buf local(1024);     // 局部对象
    return local;        // 朴素世界：local 拷贝→返回值临时对象，临时再拷贝→外部变量（两次深拷）
}
Buf b = make();          // RVO：编译器直接把 local「造在 b 的内存上」——零拷贝零移动

原理：编译器早知道 local 的最终归宿是 b，于是把「构造 local」这一步直接落到 b 的地址上——return 和「搬运到外部」两步根本不发生，是空间上的合谋，不是「先造好再搬运」。NRVO 的 N = Named：local 这种有名字的局部变量也享受（无名临时的版本叫 RVO，C++17 起纯右值场景强制省略拷贝、不再是可选项）。校准一下之前的理解：「有名字是左值、返回时要拷贝/移动」是没有 RVO 时的朴素规则；有 RVO 时编译器直接跳过整场搬运。这也回答了「按值返回大对象安不安全」——现代 C++ 安全，放心 return。

string 的 SSO？小串优化：短字符串（libstdc++ 15 字节、MSVC 15/23 字节）直接存在 string 对象内部，不走堆——大量小串场景省掉堆分配，这就是 string sizeof 通常 32 字节的原因。

为什么 vector 扩容倍率是 2 或 1.5？倍增让 n 次追加的总搬运量收敛 O(n)（均摊 O(1)）；1.5 倍（MSVC）相对 2 倍（GCC）能更早释放的旧内存被复用（2 的幂永远对不齐旧块）——两种都是工程折中。

② rehash 为什么不像 Java HashMap 那样高低位分流迁移——好问题，答案在桶数的设计哲学：

  • Java HashMap：容量恒为 2 的幂，定位桶用 hash & (n-1)。扩容翻倍 = 哈希值多暴露一个二进制位，每个节点只看新增那一位：0 留原桶、1 去「原桶+旧容量」——不用重算哈希、一次遍历分完，常数极小。代价：2 的幂对劣质哈希函数不友好（低位相同就全撞一个桶）。
  • std::unordered_map（libstdc++）：桶数取素数——素数取模能把劣质哈希打散（哈希值只在低位有区分度时，模素数仍能分散）。代价：扩容后模数变了，每个节点的桶号必须全部重算重挂，「看一位定位」这招在素数桶下不存在。

所以不是没想到，是「迁得快」和「容错劣质哈希」二选一：Java 选 2 幂桶+快速迁移（赌哈希好——它自带扰动函数兜底）；标准库选素数桶+全量重挂（对用户随手写的哈希更宽容）。两边复杂度都是 O(n)，差的是常数。追求极致的 absl::flat_hash_map 走第三条路：2 幂桶+开放寻址+元数据字节。面试答出这层取舍即满分。

问题一句话答案
CAS 的 ABA 问题？值从 A 改成 B 又改回 A，CAS 只比对值发现「没变」其实变过两次；解法是附版本号/时间戳一起比对（tagged pointer）。
async/future/promise？async 启动异步任务返回 future（一次性取结果容器），promise 是手动版（塞值的一端）；std::packaged_task 包装可调用对象打包异常传递——线程安全的「占位结果」三件套。
什么是惊群？一个事件唤醒所有等在 accept/epoll 上的进程但只有一个能处理，其余空转；缓解：内核 accept 的 wake-one、SO_REUSEPORT 按哈希分流、EPOLLEXCLUSIVE。
零拷贝是什么？传统读文件发送要「内核缓冲→用户缓冲→socket 缓冲」4 次拷贝 4 次切换；sendfile/splice 让数据全程留在内核，mmap 把内核缓冲映射进用户态——省拷贝省切换。
大端小端？怎么判断？低字节存低地址=小端（x86/ARM 默认）；网络字节序=大端。判断：联合体或 *(char*)&x == x & 0xff；转换 htons/htonl/ntohs/ntohl（host↔network short/long）。
TCP 怎么保证可靠？（跨语言常问）序号+确认应答、超时重传（RTT 自适应）、滑动窗口流量控制、拥塞控制（慢启动/拥塞避免/快恢复）、校验和——五大件按需展开。
