## A1 · 第2轮

## Q3 BEIR 三指标详解（附手算，这是面试硬通货）

先建立输入：BEIR 评估喂两样东西——每个 query 的**检索结果排名**（你的系统返回的有序列表）+ **qrel**（人工标注的 query→relevant doc 对照表）。CRUD-RAG 是 **1-to-1 qrel**：每个 query 恰好 1 个 relevant doc。

### Recall@10 —— “找到没有”

```
= 前10个结果中包含 relevant doc 的 query 占比
例: query 的标准答案是 crud_042
   你的 top10 里有 crud_042 → 该 query recall = 1
   没有                            → 0
300 个 query 取平均
```
graph 实测 **0.880** = 264/300 的 query 在返回结果里押中了标准 doc，12% 押空。

### MRR@10 —— “第一条对的排多前”

```
= 第一个命中的 relevant doc 的排位倒数,再对所有 query 取平均
例: crud_042 排第 1 → 1/1 = 1.0
    crud_042 排第 4 → 1/4 = 0.25
    不在前 10      → 0
```
衡量“用户只看第一条”场景（问答、搜索框自动补全）的质量。

### nDCG@10 —— “整条排序的质量，越靠前越值钱”

分两步：
```
① DCG@10 = Σ rel_i / log₂(i+1)     i=排位(1-based)
   relevant doc 排第1位 → 1/log₂(2) = 1.0
   排第3位            → 1/log₂(4) = 0.5
   排第10位           → 1/log₂(11) ≈ 0.289
② nDCG = DCG / IDCG    (IDCG=理想排序下的DCG)
   1-to-1 qrel 时理想就是 relevant doc 排第1,IDCG=1
```
log 折损的含义：用户注意力随排位衰减，排在第 10 的价值只有第 1 的 29%。多级相关度标注（如 NFCorpus 的 1/2/3 级）时，nDCG 还能表达“更相关的该排更前”，是三指标里信息量最大的。

### 三个数字放在一起读（数据指纹法）

| 模式 | nDCG@10 | Recall@10 | MRR@10 | 指纹解读 |
|------|--------:|----------:|-------:|---------|
| graph | 0.877 | 0.880 | 0.877 | **三个几乎相等** → graph 每 query 只返回 ~1 个 chunk：命中必排第 1（三项全 1.0），miss 全 0——纯押注型分布 |
| native off | 0.988 | 1.000 | 0.988 | Recall 满 + nDCG=MRR 略低 → 全命中，个别 relevant doc 排位靠后 |
| C轮1 native_on（KB17） | 0.389 | 0.525 | 0.441 | nDCG < Recall → **找得到但排不前**：rerank 把部分 relevant doc 挤到 10 名外的指纹 |

**面试金句**：“我不只报指标，我读指标之间的形状——三个指标的关系能反推结果分布特征，graph 三值相等就是‘单 chunk 押注’的指纹，这直接引出了 avg_chunks 1 的洞察。”

## A2 · 第2轮

## Q4 诚实声明四要素：每个词拆开

评估报告的可信度 = 数字质量 × **偏差透明度**。四个要素各自回答一个“这数字能信到什么程度”的问题：

**① self-judge 偏差**：RAGAS 的 judge（给 faithfulness 等打分的 LLM）和生成 answer 的 LLM 是同厂/同模型家族时，相当于**自己改自己的卷子**——judge 对自家风格的输出评分偏高（faithfulness 尤甚）。本项目：judge = GLM-4-Flash，answer 生成 = glm-4-air，同厂不同型号，偏差风险仍在。业界做法：换更强的独立 judge（GPT-4/Claude）或人工抽检 20% 交叉验证——报告声明了这是未做的改进项。

**② gt 来源**：ground truth（标准答案）怎么造的决定上限。本项目出现过三代：人工标注（CRUD-RAG，最可信）→ LLM 从文档生成（KB17 supplement 32 条，可能有遗漏和表述偏差）→ **检索结果反推**（C 轮1 的 qrel 拿 native 召回的 contexts 反查 chunk_id——最弱，见下条）。不声明来源，读者无法判断“0.969 的 faithfulness”到底有多硬。

**③ 样本局限**：32 条（KB17）/300 条（CRUD-RAG）样本能不能代表真实流量？KB17 的 query 是 LLM 从文档主题生成的模板化问句（“X 的内部机制”），不是真实用户分布；CRUD-RAG 是新闻问答，和企业知识库场景有偏移。结论的泛化边界由样本决定。

**④ qrel 构建偏差**：qrel 怎么造的决定 BEIR 指标可信度。**本项目踩过的典型坑**（C 轮1）：qrel 用 native rerank-off 的召回反查构建 → native 既是考官又是考生（**循环论证**）→ rerank 后 nDCG 反降（0.585→0.389）不是 rerank 差，是 qrel 只标了 native 召回的那几份、rerank 挪了它们的位。C 轮2 换数据集自带的人工 1-to-1 qrel 才消除。

**面试价值**：“评估体系的成熟度不看指标多高，看偏差声明多全”——这四条证明你知道自己数字的边界在哪，比多 0.01 的指标值钱。

## A3 · 第2轮

## Q6 “过滤得狠=留下的都相关”，为什么指标反而全降？

你的直觉方向是对的——这正是 graph 的**设计目标**。但有两个概念错位 + 一个数据集错配，拆开：

### 错位一：0.9 不是“90% 相关的概率”，是来源分层标记

```python
base = 0.9 if ch["id"] in high_confidence_set else 0.75   # retrieval_strategies.py:648
```
0.9 的含义是**“这个 chunk 来自关系直查路径（路径 B）”**，0.75 是“来自实体兜底路径”——它们是**规则打分的标签**，不是模型校准的相关性概率。真正做相关性判断的是 LLM 关系重排打的分，而 LLM 会错。

### 错位二：“留下的都相关”要求三环全对，实测三环都有误差

```
环1: 锚点对吗?    实测精确匹配率仅 61%(41 个锚点 PG 匹配 25 个)
环2: 关系真吗?    LLM 抽取的关系本身有噪声(evidence 可能弱相关)
环3: 重排准吗?    LLM 打分有判断误差
      ↓ 三环级联,误差相乘
最终 ~12% 的 query 押错
```
锚点错 → 扩展出的关系全错 → 关系直查回来的 0.9 分 chunk **和问题完全无关**——高分层里也混着不相关的（所以 RAGAS context_precision 0.918 也不是 1.0）。

### 错位三：1-to-1 qrel + 只返回 1 个 chunk = 单次押注，没有容错

CRUD-RAG 每个 query **恰好 1 个标准 doc**。graph 平均只返回 1 个 chunk，等于**每次全部筹码押一只**：押中三项指标全 1.0，押错全 0（这正是 Q3 里“三个指标几乎相等”的指纹）。native 返回 10 个是分散押注，容错空间大。**12% 押错率 × 押错即清零** → Recall 0.880。

### 数据集错配（最重要的场景解释）

CRUD-RAG 是**单跳事实问答**：每条 query 的答案就在 1 篇新闻里，query 和那篇新闻的词汇/语义高度重叠——**向量检索直接命中，graph 的主场（多跳关联、query 与答案 doc 低重叠）在这个数据集里根本不存在**。native Recall 1.000 不是 graph 的失败参照，是这个数据集的“送分题”属性。

### 结论收束

不是“高置信过滤导致低分”，而是：**押注式检索的 miss 代价被 1-to-1 qrel 放大 + 三环级联误差 12% + 数据集不给多跳场景**。三个变量里我们用架构回应了“押注量”（兜底补 native 召回，avg 1→9），用数据洞察定位了“关系密度”（0.6/entity，导入侧修复方向），“数据集错配”则如实声明——graph 的价值主张要在多跳场景验证，这是后续实验方向。
