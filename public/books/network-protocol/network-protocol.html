00 / OVERVIEW

先看全局：它们到底在解决什么问题

协议不是凭空发明的。把五个名词放在"连接模型"这一个维度上，演进逻辑会异常清晰。

HTTP
请求-响应

客户端不发，服务器永远不能说话。明文传输，每次请求都要重新建立连接（早期）

HTTPS
加密通道

在 HTTP 与 TCP 之间插入 TLS 层，解决窃听、篡改、冒充三大安全问题

SSE
服务器推送

基于 HTTP 的长连接，服务器可以持续单向推送文本事件，自动重连

WS
全双工

一次 HTTP 握手后升级为独立协议，双方随时互发文本或二进制数据

MCP
语义标准

不发明新传输，而是在 HTTP/SSE/stdio 之上定义 AI 与工具之间的标准消息语义

0.1一条主线：连接的"自由度"在不断提高

  • HTTP/1.0：一请求一连接，TCP 握手成本被重复支付。短连接
  • HTTP/1.1：Keep-Alive 让连接复用，但请求必须排队，存在队头阻塞。长连接
  • HTTP/2：二进制分帧 + 多路复用，一个连接上并发跑多个请求，但 TCP 层队头阻塞仍在。连接复用
  • HTTPS：以上所有能力不变，只是通道变成加密的。安全
  • SSE：在一条 HTTP 长连接上，把"一次响应"变成"源源不断的响应流"。单向流
  • WebSocket：彻底摆脱请求-响应模型，连接双方完全平等。双向流
  • MCP：传输层已经够用，缺的是"AI 怎么发现工具、调用工具、拿回结果"的统一约定。应用层标准
协议栈视角：它们分别处在哪一层
┌─────────────────────────────────────────────────────┐ │ MCP（应用语义：工具/资源/提示词，JSON-RPC 2.0） │ ├─────────────────────────────────────────────────────┤ │ HTTP / HTTPS / SSE / WebSocket（应用层通信协议） │ ├─────────────────────────────────────────────────────┤ │ TLS（仅 HTTPS / WSS / Streamable HTTP 需要） │ ├─────────────────────────────────────────────────────┤ │ TCP（HTTP/HTTPS/SSE/WS） · UDP+QUIC（HTTP/3） │ ├─────────────────────────────────────────────────────┤ │ IP / 链路层 / 物理层 │ └─────────────────────────────────────────────────────┘

注意一个关键事实：MCP 不是 WebSocket 的替代品，SSE 也不是 HTTP 的对立面。它们大量复用彼此——MCP 的远程传输就建立在 HTTP 与 SSE 之上。理解这一点，后面的内容会顺很多。

01 / HTTP

HTTP：一切的起点，"请求-响应"模型

HTTP（HyperText Transfer Protocol，超文本传输协议）是浏览器与服务器之间最基础的应用层协议。它的核心模型只有一句话：客户端发起请求，服务器返回响应，一问一答，服务器从不主动说话。

1.1连接是如何建立的：TCP 三次握手

HTTP 本身不负责建立连接，它把这件事交给下层的 TCP。在任何 HTTP 报文发出之前，客户端与服务器必须先通过"三次握手"建立一条可靠的 TCP 连接。这也是为什么早期 HTTP 每请求一连接的代价极高——每次都要重新握手。

为什么是三次，不是两次？核心目的是确认双方的发送和接收能力都正常，并同步初始序列号（ISN），防止历史失效的连接请求突然又传到服务器造成错误连接。

  • SYN（客户端 → 服务器）："我想建立连接，我的初始序列号是 x"
  • SYN+ACK（服务器 → 客户端）："收到，我的初始序列号是 y，同时确认你的 x"
  • ACK（客户端 → 服务器）："确认你的 y，可以开始传数据了"

1.2通讯结构：请求报文与响应报文

TCP 连接建立后，HTTP 报文以纯文本（HTTP/1.x）的形式在连接中流动。报文结构高度规整，这是后面所有协议的基础。

GET /api/users?id=42 HTTP/1.1 // 请求行：方法 + 路径 + 版本 Host: example.com // 请求头：目标主机（虚拟主机必需） User-Agent: Mozilla/5.0 ... // 客户端身份 Accept: application/json // 能接受的内容类型 Connection: keep-alive // 希望复用连接 Cookie: session=abc123 // 携带状态（HTTP 本身无状态） // 空行：头部结束的标志 {"name":"yujie"} // 请求体（GET 通常没有，POST/PUT 才有）
HTTP/1.1 200 OK // 状态行：版本 + 状态码 + 原因 Content-Type: application/json // 响应头：内容类型 Content-Length: 23 // 内容长度 Set-Cookie: token=xyz; HttpOnly // 下发 Cookie // 空行 {"id":42,"name":"yujie"} // 响应体：真正的内容
请求方法
动作语义

GET 取数据、POST 提交、PUT 整体更新、DELETE 删除、PATCH 部分更新

状态码
结果分类

2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误

无状态
不记你是谁

每个请求相互独立，服务器不保留上下文。状态靠 Cookie / Token 在请求中反复携带

1.3HTTP 版本演进：连接复用的三级跳

HTTP/1.0 — 短连接，一次一断

每个请求都要新建 TCP 连接，响应完立即关闭。一个含 40 个资源的网页要握手 40 次，延迟和开销巨大。

HTTP/1.1（1997，至今广泛使用）— 长连接 + 管道化

  • Keep-Alive：默认在一个 TCP 连接上串行处理多个请求，省去重复握手。连接复用
  • Pipelining（管道化）：允许连续发多个请求不等响应，但响应必须按序返回，且默认被浏览器关闭
  • 队头阻塞（HOL Blocking）：前一个请求没处理完，后面的请求全部排队干等——这是 1.1 最核心的结构缺陷

HTTP/2（2015）— 二进制分帧 + 多路复用

  • 把报文拆成带流 ID的二进制帧，在一条 TCP 连接上并发交错传输多个请求/响应，彻底解决 HTTP 层队头阻塞
  • HPACK 头部压缩（请求头大量重复，压缩后显著省带宽）、服务器可主动推送资源
  • 局限：TCP 层的队头阻塞仍在——一旦某个 TCP 包丢失，所有流都要等重传

HTTP/3（2022）— 基于 QUIC，跑在 UDP 上

  • 用 QUIC（基于 UDP）替代 TCP，流之间互不阻塞，一个流丢包不影响其他流
  • 连接迁移：手机在 WiFi 与 4G 间切换，连接不断（靠 Connection ID 而非 IP:端口 标识）
  • QUIC 内置 TLS 1.3，加密是默认而非可选

1.4HTTP 的三个结构性缺陷（后续协议的由来）

安全缺陷
明文传输

数据在网络中"裸奔"，可被窃听、篡改、冒充 → 引出 HTTPS

交互缺陷
服务器不能主动推

实时数据只能靠轮询反复问，浪费请求、延迟高 → 引出 SSE / WebSocket

语义缺陷
缺少应用语义

只定义"怎么传"，不定义"传什么、双方能力如何协商" → 上层标准（如 MCP）补齐

02 / HTTPS

HTTPS：给 HTTP 装上一把"加密锁"

HTTPS 不是一个新协议，而是 HTTP + TLS（Transport Layer Security，前身是 SSL）。它在 HTTP 与 TCP 之间插入了一个安全层：连接建立时先协商出密钥、验证服务器身份，之后所有 HTTP 数据都加密传输。

明文 HTTP 与 HTTPS 的差别
HTTP ： 应用数据 ──直接──> TCP ──> 网络（任何人都能抓包看到内容） HTTPS： 应用数据 ──> TLS 加密 ──> TCP ──> 网络（抓到的只是密文）

2.1连接建立：TLS 握手全过程

TCP 三次握手完成后，并不立刻传 HTTP 数据，而是先进行 TLS 握手：协商加密套件、验证服务器证书、交换密钥材料，最终生成双方共享的"会话密钥"。下面以 TLS 1.2 为例（最经典、面试最爱问）。

ClientHello

客户端发起：我支持的 TLS 版本、加密套件列表、一个客户端随机数（Client Random）

ServerHello + 证书

服务器选定加密套件，返回服务器随机数（Server Random）和自己的 CA 证书（含公钥、域名、颁发者、有效期）

验证证书 + 密钥交换

客户端用系统内置的 CA 根证书验证服务器证书真伪；随后生成 Pre-Master Secret，用服务器公钥加密后发回（或用 ECDHE 交换参数）

生成会话密钥

双方用三个随机数（Client Random + Server Random + Pre-Master Secret）各自算出相同的会话密钥，之后通信用对称加密

Finished，开始加密通信

互发 Finished（握手记录的摘要，用会话密钥加密）验证一致性，随后才开始传加密的 HTTP 数据

2.2TLS 1.3 的关键改进：握手只要 1-RTT

  • 砍掉一半往返：TLS 1.2 要 2 个 RTT，TLS 1.3 把密钥协商提前到 ClientHello 中，只需 1-RTT；会话恢复时甚至 0-RTT（首包就能带数据）
  • 只保留安全的算法：移除 RSA 密钥交换（不支持前向保密）、CBC、SHA-1 等，强制使用 ECDHE + AEAD（AES-GCM / ChaCha20-Poly1305）
  • 前向保密（Forward Secrecy）：每次连接用临时密钥协商，即使服务器长期私钥将来泄露，也无法解密历史流量

2.3密码学三件套：各自负责什么

为什么握手同时用到非对称加密和对称加密？因为它们各有优劣，TLS 让它们分工协作。

对称加密
加密实际数据

同一把密钥加解密（AES、ChaCha20）。速度快，但密钥如何安全地交给对方是难题 → 用于握手后的通信

非对称加密
安全交换密钥

公钥加密、私钥解密（RSA、ECDHE）。无需事先共享密钥，但慢 → 只在握手阶段用它安全地协商出会话密钥

哈希 / MAC
保证完整性

SHA-256、HMAC 生成指纹，数据被改动一个字节指纹就对不上 → 防止传输中被篡改

2.4证书体系：凭什么相信对面是真服务器

加密只解决"内容不被看见"，但攻击者可以冒充服务器。身份认证靠 PKI（公钥基础设施）与 CA（证书颁发机构）。

// 证书链：从根到叶子，逐级签名 根 CA 证书（DigiCert / GlobalSign，操作系统和浏览器内置，自签名，信任的起点） └── 签名 ──> 中间 CA 证书（根 CA 不直接签服务器证书，隔离风险） └── 签名 ──> 服务器证书（含 example.com 与公钥，发给浏览器）
  • 浏览器用内置根 CA 的公钥逐级验证签名：只要链上任何一环对不上、过期、域名不符，浏览器就亮红警告
  • 关键机制是数字签名：CA 用自己的私钥对证书内容的哈希签名，任何人都能用 CA 公钥验证，而伪造签名需要 CA 私钥

2.5HTTPS 如何保证安全：三大目标

机密性

对称加密，中间人抓到的只是密文

完整性

MAC/AEAD 校验，数据被改立刻发现

身份认证

CA 证书验证，防止中间人冒充

常见攻击与 HTTPS 的应对

  • 中间人攻击（MITM）：攻击者夹在中间转发 → 证书认证 + 密钥协商使其无法冒充
  • 降级攻击：诱导使用旧版弱加密 → 客户端与服务器要求最低版本，TLS 1.3 直接删除弱算法
  • 注意：HTTPS 只保证传输过程安全，不保证服务器本身不被攻破，也不隐藏你访问了哪个域名（SNI 可见，ECH 仍在普及）
03 / SSE

SSE：让服务器"开口"的第一步

SSE（Server-Sent Events，服务器发送事件）是 HTML5 标准的一部分。它让服务器能通过一条普通的 HTTP 长连接，持续地、单向地向客户端推送文本事件。典型场景：股票行情、新闻推送、AI 生成内容的逐字流式输出。

3.1为什么需要它：三种"获取实时数据"的方式

客户端每隔几秒发一次请求问"有新数据吗"。实现简单但浪费严重：大量请求拿到的都是空响应，且数据有延迟（最坏要等一个轮询间隔）。

服务器收到请求后不立即响应，而是挂起，直到有新数据才返回；客户端收到后立刻再发下一个请求。减少了空请求，但每次消息仍要重新建立/完整走一遍 HTTP 响应。

一次请求建立连接，服务器持续不断地往这一条响应里写事件，连接长期保持。这才是真正的"推送"。

3.2连接如何建立：它就是一个特殊的 HTTP 响应

SSE 极其巧妙地复用了 HTTP，不需要任何新协议。客户端用浏览器原生 EventSource 发起一个普通 GET，服务器返回时声明特殊的 Content-Type，然后这个响应永远不结束。

客户端（浏览器原生 API，无需任何库）
const es = new EventSource('/api/stream'); // 发起 GET，自动保持连接 es.onmessage = (e) => { // 监听默认消息事件 console.log('收到:', e.data); // e.data 是文本内容 }; es.addEventListener('update', (e) => { // 也可监听自定义事件名 render(e.data); };
服务器响应（关键：text/event-stream）
HTTP/1.1 200 OK Content-Type: text/event-stream // 关键：事件流类型 Cache-Control: no-cache Connection: keep-alive

3.3通讯结构：事件的文本格式

响应体里是一个接一个的纯文本事件，每个事件以两个换行符 \n\n 结束。字段非常简单：

data:
消息内容，可有多行 data 唯一必需的字段
event:
自定义事件类型名 不写则默认 message
id:
事件 ID，用于断线重连时断点续传 浏览器自动记录
retry:
重连等待的毫秒数，由服务器指定 如 retry: 3000
: 注释
以冒号开头的行会被忽略，常用于保活心跳 : keep-alive
实际的事件流长这样
id: 1 event: update data: {"price": 102.5, "stock": "AAPL"} // 空行 → 一个事件结束，推送给客户端 id: 2 data: 另一条消息的第一行 data: 另一条消息的第二行 // 多个 data 会用 \n 拼接 // 事件结束

3.4自动重连：SSE 被低估的能力

  • 网络中断时，EventSource 会自动重新发起连接，无需手写重连逻辑（这是它比 WebSocket 省心的地方）
  • 重连时浏览器自动带上 Last-Event-ID 请求头，值为最后收到的 id；服务器据此补发断线期间漏掉的事件，实现断点续传
  • 以冒号开头的注释行充当心跳，防止代理因超时而关闭连接

3.5SSE 的能力边界

优势
简单、自动、走 HTTP

原生 API、自动重连、天然穿透防火墙和代理、基于 HTTPS 即可加密；只做"服务器推送"时比 WebSocket 轻量得多

局限
单向、纯文本

只能服务器 → 客户端；只能传文本（二进制要自己 Base64）；HTTP/1.1 下浏览器对同域名有 6 个连接数限制

如果你需要双向实时通信（聊天、协同编辑、在线游戏），SSE 就不够了——这正是 WebSocket 要解决的问题。

04 / WEBSOCKET

WebSocket：彻底的全双工通信

WebSocket 是一个独立的、基于 TCP 的全双工协议（RFC 6455，2011）。它先用一次 HTTP 请求"敲门"，服务器同意后连接"升级"，此后双方完全平等，任何一方都可以随时主动发送文本或二进制数据，不再有请求与响应的概念。

协议标识：ws:// 与 wss://（加密）
ws://example.com/chat // 明文，类似 http:// wss://example.com/chat // 走 TLS 加密，类似 https://，生产环境必用

4.1连接建立：借 HTTP 完成"升级握手"

WebSocket 复用 HTTP 完成握手，这样可以轻松穿透代理、复用 80/443 端口。握手只需要一个来回，服务器返回 101 后，这条 TCP 连接就不再说 HTTP，而是改说 WebSocket。

握手请求（本质是一个带 Upgrade 的 HTTP 请求）
GET /chat HTTP/1.1 Host: example.com Upgrade: websocket // 我想升级为 WebSocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZQ== // 浏览器随机生成的 16 字节 Base64 Sec-WebSocket-Version: 13
握手响应
HTTP/1.1 101 Switching Protocols // 同意升级，关键状态码 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBi... // 对 Key 的计算结果，证明服务器懂 WebSocket

Sec-WebSocket-Key / Accept 是怎么回事？浏览器随机生成 Key，服务器把它与一个固定魔串（258EAFA5-E914-47DA-95CA-C5AB0DC85B11）拼接后做 SHA-1 再 Base64，得到 Accept。这不是加密，而是防止服务器误把普通 HTTP 响应当成 WebSocket 握手，同时验证对方确实支持该协议。

4.2通讯结构：数据以"帧"为单位

升级后，双方收发的是 WebSocket 帧（frame）。帧可以是文本、二进制，也可以是控制帧（关闭、心跳）。帧头是二进制的，结构如下：

FIN（1 bit）
是否为消息的最后一帧 大消息可拆成多帧
Opcode（4 bit）
帧类型：0x1 文本、0x2 二进制、0x8 关闭、0x9 Ping、0xA Pong
Mask（1 bit）
是否掩码。浏览器发往服务器的帧必须掩码，用随机密钥异或，防止中间代理缓存投毒
Payload len
数据长度，7 bit 起；超长用扩展位（16/64 bit）
Masking key
4 字节掩码密钥（仅掩码帧）
Payload data
真正的应用数据，文本或二进制

4.3心跳与关闭：保持连接健康

Ping / Pong
心跳保活

WebSocket 是长连接，可能被 NAT 或代理静默断开。一方发 Ping，对方必须回 Pong，从而探测连接是否存活、维持链路。通常应用层还会定时发心跳

关闭握手
优雅断开

任一方发 Close 帧（可带状态码和原因），对方回 Close 后再关闭 TCP，比直接断开更可靠，避免数据丢失

4.4客户端 API 与通信时序

const ws = new WebSocket('wss://example.com/chat'); ws.onopen = () => ws.send('你好'); // 连接建立后可随时发送 ws.onmessage = (e) => console.log(e.data); // 随时接收，无需请求 ws.onclose = () => reconnect(); // 注意：WebSocket 不自动重连，需自己实现

4.5WebSocket vs SSE：怎么选

维度SSEWebSocket
通信方向服务器 → 客户端，单向双向，全双工
数据类型仅文本（UTF-8）文本 + 二进制
断线重连浏览器自动需手写
协议复杂度就是 HTTP，简单独立协议 + 帧结构，稍复杂
典型场景行情、通知、AI 流式输出聊天、协同编辑、游戏、实时白板

4.6安全：wss 与应用层防护

  • 生产环境一律用 wss://：它在 TLS 之上，享有 HTTPS 的全部保护（加密、完整性、身份认证）
  • 校验 Origin 头：服务器只接受白名单来源的握手，防止恶意网页借用户浏览器发起跨站 WebSocket 连接（类似 CSWSH）
  • 握手阶段仍可使用 Cookie/Token 鉴权；帧掩码只防代理投毒，不是安全措施，真正的安全靠 TLS 与鉴权
05 / MCP · MODEL CONTEXT PROTOCOL

MCP：为 AI 应用定义"连接的标准语言"

MCP（Model Context Protocol，模型上下文协议）由 Anthropic 于 2024 年 11 月开源。它要解决的问题完全不同：传输层（HTTP/SSE/WebSocket）已经足够强大，但 AI 应用想接入数据库、文件、第三方工具时，每个集成都要写一套定制对接。MCP 像"AI 世界的 USB-C 接口"，用一套标准约定让任意 AI 客户端发现并使用任意工具服务器。

5.1 USB-C 类比 5.2 架构三角色 5.3 完整交互流程 5.4 传输方式 5.5 JSON-RPC 5.6 生命周期 5.7 三大原语 5.8 vs Function Calling 5.9 为什么不是裸 Shell 5.10 工程实践 5.11 安全机制 5.12 三步开发 5.13 面试实战

5.1MCP 是什么：AI 领域的"USB-C"

原话 · 概念卡片

"MCP 全称 Model Context Protocol，模型上下文协议，是 Anthropic 在 2024 年 11 月发布的开放标准。核心目标是让大模型能够标准化地连接外部数据源和工具。MCP 就是 AI 领域的 USB-C，让模型和外部世界的连接变得即插即用。"

在统一标准出现之前，M 个模型要接 N 个外部系统，就得写 M×N 套定制集成；有了 MCP，模型侧和工具侧各自接一次协议即可，集成成本从 M×N 降到 M+N——而且接入新工具不用动模型侧的代码。

MCP 解决的集成复杂度问题：M×N → M+N
// 接入之前：每个模型 × 每个工具，都要单独定制对接 模型A ──定制──┐ ┌── GitHub 模型B ──定制──┼── 各写各的 ──┼── 数据库 模型C ──定制──┘ └── 文件系统 / …… // M × N 套胶水代码 // 接入之后：双方各实现一次统一协议 模型A ─┐ ┌─ GitHub 模型B ─┼── 统一的 MCP 协议 ──┼─ 数据库 模型C ─┘ └─ 文件系统 / …… // M + N 次接入，即插即用

MCP 带来的三大好处

好处一
标准化数据接入

外部数据源（Gmail、日历、本地文件、远程服务……）都通过同一套协议接入，不再一源一套代码

好处二
增强模型实时能力

模型不再只靠训练时的旧知识，可以实时读取最新的数据与上下文

好处三
降低集成复杂度

工具方只实现一次 Server，就能被所有支持 MCP 的客户端使用，模型侧代码零改动

关键认知：MCP 不发明新的传输协议。它是一个应用层语义协议，规定消息长什么样、连接如何初始化、能力如何协商；而消息的实际传输，本地用 stdio，远程用 Streamable HTTP（其中可选地用 SSE 做流式）。这正是整条演进线的收口——它站在前面所有协议的肩膀上。

5.2架构：Host、Client、Server 三种角色

┌────────────────────────────────────────────┐ │ MCP Host（宿主：Claude Desktop / IDE / 你的应用）│ │ 里面运行着多个 MCP Client（每个 Server 对应一个）│ └───────┬───────────────────────┬────────────┘ │ 1:1 连接 │ 1:1 连接 ┌───────▼────────┐ ┌───────▼────────────┐ │ MCP Server A │ │ MCP Server B │ │ GitHub 工具 │ │ 数据库 / 文件系统 │ └────────────────┘ └────────────────────┘
  • Host（宿主）：运行 AI 模型的应用，负责编排、权限管理、用户交互，出于安全隔离原则，一个 Server 对应一个独立 Client
  • Client（客户端）：Host 内部与单个 Server 保持 1:1 会话的连接器
  • Server（服务器）：对外暴露工具、资源、提示词，实际去对接 GitHub、数据库、文件系统等

进阶：一个 Client 能同时连多个 Server 吗？怎么管理？

原话 · 高频问答

"可以，MCP 设计上就支持一个 Client 同时连多个 Server。每个 Server 提供不同能力，Client 会维护一个 Server 列表，每次请求前先聚合所有 Server 的工具列表给模型。模型选择调用哪个工具时，Client 根据工具归属把请求路由到对应的 Server。Cursor 里配置多个 MCP Server 就是这个原理。"

① 维护列表
Server 列表

Client 持有所有已连接 Server 的注册信息，每个 Server 提供不同领域能力

② 聚合能力
工具列表聚合

每次请求前，把所有 Server 的工具列表聚合成一份清单交给模型挑选

③ 按归属路由
请求路由

模型选定工具后，Client 根据工具归属于哪个 Server，把调用请求转发过去

5.3完整交互流程：一次查询背后的两个阶段

把用户、MCP Client、MCP Server、LLM四个角色放进同一张时序图，MCP 的运行方式一目了然：初始化阶段负责建立连接、拿到工具清单；查询处理阶段则是一个"LLM 返回工具调用 → Client 执行 → 结果回传 LLM"的循环，直到 LLM 给出最终的文本响应。

初始化阶段：拿到工具清单

用户启动客户端 → Client 连接服务器并确认连接 → 请求可用工具列表 → Server 返回工具列表和描述。工具信息此后缓存在会话内，不用反复发现

查询处理：把工具信息带给 LLM

用户输入查询后，Client 把查询和可用工具信息一起发给 LLM——工具的名称、参数描述就是模型的"菜单"

循环（loop）：工具调用闭环

LLM 返回的是工具调用 → Client 执行工具调用 → Server 返回工具执行结果 → Client 再把查询和工具结果一起发给 LLM，让它继续推理

分支（alt）：文本响应即结束

LLM 返回的是文本响应 → Client 显示响应给用户，整个查询处理流程收尾

这个"推理 → 行动 → 观察 → 再推理"的循环，正是 Agent 系统里经典的 ReAct 模式；MCP 在其中扮演的角色，是把"行动"这一步标准化——工具怎么发现、怎么调用、结果怎么回传，都有统一约定。

5.4传输方式：stdio、Streamable HTTP 与已废弃的 HTTP+SSE

MCP 目前官方指定的两种传输是 stdio 与 Streamable HTTP；历史上还存在过 HTTP+SSE 双通道方案（已废弃）。三种方式的定位完全不同：

stdio 传输
本地进程间通信

MCP Client 直接启动 MCP Server 进程，通过标准输入输出交换数据。优点是零网络开销、部署简单，适合本地开发和桌面应用场景，Claude Desktop 就是用这种方式

Streamable HTTP
远程服务，单一端点

Server 独立部署，走网络协议，支持远程调用和多客户端并发。单一 HTTP 端点，POST 发 JSON-RPC，响应可直接返回 JSON 或升级为 SSE 流；无状态、可负载均衡。生产环境、微服务架构、需要集中管理的场景用它

HTTP+SSE（已废弃）
双通道历史方案

早期版本用两条连接：GET 先建立独立的 SSE 通道收消息，POST 另发请求。长连接阻碍负载均衡和水平扩展，已被 Streamable HTTP 取代，仅作兼容了解

注意：MCP 传输层的一次重要演进

  • 最早版本（2024-11-05）使用"HTTP + 独立 SSE"两条连接的传输，该独立 SSE 传输已被废弃
  • 2025-03-26 版本起由 Streamable HTTP 取代：一个端点、按需用 SSE 流式、支持无状态部署、支持 JSON-RPC 批处理，并加入了完整的 OAuth 授权框架
原话 · 高频问答（怎么选）

"stdio 方式是本地进程间通信，MCP Client 直接启动 MCP Server 进程，通过标准输入输出交换数据。优点是零网络开销、部署简单，适合本地开发和桌面应用场景，Claude Desktop 就是用这种方式。HTTP 方式走网络协议，Server 独立部署，支持远程调用和多客户端并发。生产环境、微服务架构、需要集中管理的场景用 HTTP。一般本地工具用 stdio，线上服务用 HTTP。"

5.5通讯结构：一切都是 JSON-RPC 2.0

MCP 的消息格式严格遵循 JSON-RPC 2.0，只有三类消息：请求（有 id，必须回应）、响应（带 result 或 error）、通知（无 id，不回应）。

客户端 → 服务器：请求（带 id）
{ "jsonrpc": "2.0", "id": 1, // 有 id 才是请求，响应靠它匹配 "method": "tools/call", // 要调用的方法 "params": { "name": "get_weather", "arguments": {"city": "北京"} } }
服务器 → 客户端：成功响应 / 错误响应
{ "jsonrpc":"2.0", "id":1, "result": { "content":[ {"type":"text","text":"晴 22℃"} ] } } { "jsonrpc":"2.0", "id":1, "error": { "code": -32602, "message": "参数错误" } }
通知（无 id，不需要回应，如初始化完成通知）
{ "jsonrpc":"2.0", "method":"notifications/initialized" }

5.6连接生命周期：从 initialize 到关闭

建立传输后，必须先完成 initialize 握手：协商协议版本、交换双方能力（capabilities），之后才能正常调用。这与 TLS 握手"先协商后通信"的思想一脉相承。

initialize 请求

客户端声明协议版本、自己的能力（是否支持采样、根目录等）、客户端信息

initialize 响应

服务器返回选定的协议版本、自身能力（提供哪些 tools/resources/prompts）、服务器信息

initialized 通知

客户端发无 id 通知，握手完成，会话正式就绪

正常交互

列出工具、调用工具、读取资源；服务器也能反过来请求客户端（如让 LLM 做采样）

shutdown / 断开

HTTP 下可结束会话；stdio 下终止子进程

5.7三大能力原语：Tools、Resources、Prompts

Tools 工具
可执行的函数

模型可调用的函数（带 JSON Schema 描述参数），如 search_web、run_query。会产生副作用，通常需用户授权

Resources 资源
可读取的数据

供模型读取的上下文数据，用 URI 标识，如文件、日志、数据库记录，类似 GET

Prompts 提示词
预制的模板

服务器提供的可复用提示词模板，用户可在交互中选用

追问：Tools 和 Resources 有什么本质区别？

原话 · 高频问答

"Resources 是只读的数据，模型拿来参考用，不会产生副作用；Tools 是可执行的动作，会真正改变外部状态。打个比方，Resources 像是给模型看的文档，Tools 像是给模型用的遥控器。Resources 模型可以随时读，Tools 执行前通常要用户确认授权，因为可能会发邮件、删文件这种不可逆操作。"

5.8MCP vs Function Calling：互补，不是替代

这是 MCP 被问得最多的一组对比。先给结论——两者根本不在一个层次上：

原话 · 高频问答

"不能，两者层次不同。MCP 是通信协议，解决的是'怎么标准化地和外部系统交互'；Function Calling 是模型能力，解决的是'模型怎么理解并产出工具调用请求'。没有 Function Calling，模型压根不知道什么时候该调工具、调哪个工具；没有 MCP，每个模型都要单独适配外部系统。它们是互补关系，不是替代关系。"

维度MCPFunction Calling
本质通信协议（开放标准）模型能力（厂商训练出来的）
解决的问题怎么标准化地和外部系统交互模型怎么理解并产出工具调用请求
类比USB-C 通用接口标准厂商私有的充电接口
缺失对方会怎样没有 FC，模型不知道何时调、调哪个工具没有 MCP，每个模型都要单独适配外部系统
关系互补关系，不是替代关系

先搞懂 Function Calling 本身是怎么跑的

以"天气查询 + 时间查询"两个工具为例，一次典型的工具调用流程是这样闭环的：

用户提问

例如"北京今天多少度？"——问题进入程序（应用层）

程序根据用户问题调用大模型

请求里会带上工具信息：天气查询，参数：地点；时间查询，参数：无

大模型判断是否需要调用工具

否 → 直接给出回复；是 → 输出工具名称、解析工具入参（结构化的调用意图）

程序根据工具名称、入参调用工具

真正执行的是程序，不是模型；工具输出工具调用结果

带着结果再问一次大模型

程序根据工具结果、用户问题再次调用大模型，由模型综合出最终回复，返回给用户

工具选择的机制，本质上是意图识别：工具 Schema 被注入 System Prompt，由模型来决定调哪个工具、传什么参数——所以工具描述的质量直接影响选择的准确率。

如果模型本身不支持 Function Calling，还能用 MCP 吗？
原话 · 回答 "能用，但得换个方式。MCP 只是通信协议，不依赖 Function Calling。没有 Function Calling 能力的模型，可以用 Prompt 引导的方式让模型输出结构化的工具调用意图，应用层解析这个意图再走 MCP 协议调用工具。效果会差一些，因为模型输出格式不够稳定，但技术上完全可行。"

5.9灵魂拷问：AI 都能执行 Shell 了，为什么还需要 MCP？

表面上看，让模型生成并执行 Shell 命令几乎"万能"：curl 取数据、jq 解析、mysql -e 查库、rm 删文件，什么都能干。但 Shell 的"万能"恰恰是它的危险所在——它是一条没有边界、没有契约的通道。

裸 Shell 方式的五个结构性问题

  • ① 没有契约，靠字符串拼命令：模型在一段自由文本里拼命令、拼参数，一个文件名或变量里带上 ; rm -rf ~ 就可能造成命令注入；返回的是自由文本和退出码，模型要自己解析，格式一变就失败
  • ② 权限无边界：能执行 Shell 就等于拿到当前用户的全部权限——读任意文件、改 .ssh、删家目录、连内网。"查个订单"和"删掉整个数据库"用的是同一把钥匙
  • ③ 依赖环境、不可移植：机器上有没有 curl/jq/python、shell 是 bash 还是 zsh，行为都不同；Windows 上这些命令根本不存在，同一段操作在不同机器上结果不可预期
  • ④ 黑盒、难审计：命令执行后留下的是零散的系统日志，意图、参数、副作用混在一起，事后很难回答"AI 到底做了什么、改了哪些东西"
  • ⑤ 服务保证弱：没有关于超时、重试、取消、结构化错误的标准约定，失败只是一个非零退出码加一段 stderr，模型只能猜原因

MCP 的思路不是"让命令更安全"，而是把安全边界从系统层上移到"工具契约"层：不暴露"任意命令"，只暴露一个个语义明确、参数有类型、权限可控制的工具。

标准化 · 契约
按 Schema 调用，而非拼命令

每个工具用 JSON Schema 声明参数类型和返回结构，模型填的是结构化字段（order_id 是整数），不存在字符串拼接，命令注入面被从结构上消灭

权限边界 · 最小权限
只有被显式暴露的操作

模型能做的只有"查询订单""创建 issue"这类窄操作，根本没有"执行任意命令"这个能力；删文件、发消息等敏感操作单独授权，天然最小权限

隔离 · 可审计
独立进程 + 结构化日志

工具在独立进程/沙箱/远端服务运行，模型不直接触达系统；每次调用是一条结构化记录（谁、调了什么、参数、结果），审计清晰可回放

可组合 · 服务保证
一套协议接任意服务

结构化结果与类型化错误码、超时/取消/进度通知、能力协商；不依赖本地 shell，Server 可用任意语言编写、可远程部署、可水平扩展

同一个任务，两种方式的对比：查询订单 #1024

方式 A：裸 Shell（无界、脆弱）
curl -s "https://api.shop.com/orders/$ORDER" | jq . # 风险：ORDER 被污染 → 命令注入；机器上没装 jq/curl； # Token 来源不明；返回格式变了模型解析失败；Windows 上无法运行
方式 B：MCP（有契约、有边界）
// 请求：参数被 Schema 约束为整数，注入无门 { "method":"tools/call", "params":{ "name":"get_order", "arguments":{ "order_id": 1024 } } // 响应：结构化结果，鉴权由 Server 统一管理 { "result":{ "content":[ {"type":"text","text":"订单已发货"} ], "structuredContent":{ "id":1024, "status":"shipped" } } }

MCP vs 裸 Shell：一张表看清差异

维度裸 ShellMCP
调用方式模型自由拼命令按 Schema 选择并调用工具
输入字符串拼接（易注入）结构化 JSON，类型受限
输出自由文本 + 退出码结构化 content + 类型化错误码
权限范围当前用户的全部权限仅被显式暴露的工具
命令注入高风险无字符串拼接，注入面被消灭
环境依赖依赖 OS 上的命令与 shell协议级跨平台，不依赖本地 shell
审计零散系统日志，难还原每条调用结构化留痕
运行位置直接在目标机器上独立进程/沙箱/远端服务
安全边界在哪靠外挂：系统沙箱 + 命令白名单内置：边界做在工具契约层

一句话总结：Shell 交给 AI 的是"一把万能钥匙"，能开所有门也包括你不想让它开的；MCP 交给 AI 的是"一串只能开特定锁、每次使用都登记、还能随时收回的钥匙"。Shell 并非不能用，而是它的安全要靠应用方自己搭沙箱、配白名单，容易漏；MCP 把这些做成了协议默认。

5.10工程实践：容错、规模与工具治理

如果 MCP Server 挂了或者响应超时，大模型那边会怎么处理？

原话 · 高频问答

"这个得看 MCP Client 的实现。一般会有超时机制，比如 30 秒没响应就返回错误。大模型拿到错误信息后，要么告诉用户工具调用失败了，要么换个方式回答。好的实现会做重试和熔断，避免一个工具故障拖垮整个对话。实际开发中建议在 MCP Server 侧做好健康检查和优雅降级。"

一个 Server 能注册多少个工具，有上限吗？

原话 · 高频问答

"协议本身没有硬性限制，但工具太多会有问题。大模型需要理解每个工具的描述来决定调用哪个，工具列表会占用大量 context window，还可能导致模型选错工具。实践中建议一个 Server 控制在 10-20 个工具以内，功能相近的可以合并，差异大的拆成多个 Server 按领域划分。"

高可用部署

  • 无状态部署 + 负载均衡：Streamable HTTP 天然亲和水平扩展，Server 可以多实例后挂网关分流
  • 优雅降级：工具失败时把超时/错误信息交回模型，由模型决定是告知用户失败还是换一种方式回答，而不是让整个会话崩掉

5.11安全机制：MCP 如何防止 AI 被滥用

MCP 让 AI 能操作真实系统，风险远高于读网页，因此它在设计上系统性考虑了安全。三道基础边界如下：

原话 · 安全机制卡片

"MCP 在设计上考虑了安全边界：1）权限隔离：每个 Server 只能访问自己管辖的资源，一个连数据库的 Server 没法读本地文件；2）用户确认：敏感操作需要用户手动授权，模型不能静默执行删库这种高危动作；3）传输安全：HTTP+SSE 模式支持 TLS 加密，防止中间人攻击。不过目前 MCP 还没有统一的认证授权标准，跨组织部署时得自己实现 OAuth 或 API Key 校验。"

注意知识时效性：上面"没有统一的认证授权标准"反映的是早期（2024 版）生态的状态；2025-03-26 版规范已引入基于 OAuth 2.1 的完整授权框架。面试时建议按"早期靠自建 OAuth/API Key → 新版本协议内置授权"的演进线来答，能体现你跟进了规范更新。

规范层面的完整安全设计

  • 传输安全：远程传输必须走 HTTPS（TLS），防止窃听与篡改；本地 stdio 只在本机通信
  • 授权框架：2025-03-26 版本引入基于 OAuth 2.1 / 授权码流程的授权，支持资源服务器（MCP Server）与授权服务器分离，支持 PKCE；用 Token 而非密码访问
  • 用户同意与最小权限：工具调用前由 Host 向用户展示"将要做什么"并请求确认；按能力（scope）最小授权，敏感操作（删文件、发消息、转账）必须显式批准
  • 隔离原则：每个 Server 独立 Client、独立权限，互不串通；不可信的 Server 无法诱导客户端访问其他 Server
  • 混淆代理防护（Confused Deputy）：明确区分"用户身份"与"工具会话"，防止恶意 Server 借 Host 的高权限去访问别的资源

多租户共用 Server 时，数据与权限必须按租户隔离，防止越权读写

范式差异
与传统 API 安全的区别

传统 API 的调用方是人/程序，MCP 的调用链多了"模型"这一环，授权、审计、注入面都要重新设计

三个高频追问

如果用户授权了一个工具，后端服务还需要再授权吗？
要区分两层授权：用户确认（Host 层）解决的是"AI 可以不可以做这件事"；后端鉴权（OAuth scope / API Key）解决的是"这次请求的身份有没有权限访问该资源"。前者不能替代后者——用户点了"同意"，不代表后端就该放开校验，两者是串联关系。
MCP Server 被攻破了怎么办？
思路是最小化爆炸半径：权限隔离让单个 Server 只能碰自己管辖的资源；审计日志让异常调用可被发现与回放；密钥可轮换、实例可下线重部署。这也是为什么"每个 Server 只授权自己需要的资源"如此重要——被攻破时损失被圈死在一小块。
stdio 模式下 Client 直接 fork Server，有什么风险？
子进程继承当前用户的全部权限：stdio 模式下 Server 以你的身份在本机运行，Server 代码如果不可信，等于把你的账户交了出去（读任意文件、改配置、连内网都做得到）。所以 stdio Server 必须只安装可信来源的实现，这也呼应了"权限隔离"的设计——能被 fork 的进程，权限边界只能靠来源可信来保证。

5.12动手开发：三步实现一个 MCP Server

自己写一个 Server 并不复杂，标准路径就三步：能力定义 → 协议层 → 业务逻辑。官方提供 Python、TypeScript 等 SDK，"继承几个类、实现几个方法"就能跑起来。

第一步：能力定义

决定 Server 要暴露什么——Resource（只读数据）、Tool（可执行动作）、Prompt（提示词模板），以及各自的名字、参数 Schema、描述文案

第二步：协议层

用官方 SDK 接入 JSON-RPC 2.0 消息循环，initialize 握手、能力协商、tools/list、tools/call 这些协议细节 SDK 已全部封装

第三步：业务逻辑

在每个工具的回调里写真正干活的部分：查库、调 API、读文件——这是你唯一需要认真写的代码

示意：用官方 Python SDK（FastMCP）写一个最小的天气 Server
from mcp.server.fastmcp import FastMCP mcp = FastMCP("weather") # ① 能力定义：声明 Server 名字 @mcp.tool() def get_weather(city: str) -> str: # ② 协议层：SDK 自动生成 Schema、处理 JSON-RPC return f"{city} 晴 22℃" # ③ 业务逻辑：真正干活的地方 mcp.run() # 默认 stdio 传输，一行启动

把这个文件配置进 Claude Desktop 或 Cursor 的 MCP 设置里，客户端就能发现 get_weather 这个工具，并按 Schema 传参调用——整个接入过程不需要写一行协议代码。

这是 MCP 最高频的开场题。面试官期待的不是背定义，而是一段 60–90 秒、结构清晰、有层次的回答：是什么 → 怎么跑 → 和 Function Calling 什么关系 → 落地要注意什么，并且每个点都留得住追问的余地。下面这段参考回答覆盖了本章绝大部分知识点，高亮短语都是可点击的"知识钩子"——每个钩子链接到本教程的一个模块，钩子背后就是你可以继续深挖、应对追问的一块知识。

面试参考回答 约 380 字 · 正常语速 90 秒 · 11 个知识钩子
了解过 MCP 吗？

了解过。MCP 全称 Model Context Protocol，模型上下文协议，是 Anthropic 在 2024 年 11 月发布的开放标准，核心目标是让大模型能够标准化地连接外部数据源和工具，常被比作 AI 领域的 USB-C，让模型和外部世界的连接变得即插即用，价值集中在标准化数据接入、增强模型实时能力、降低集成复杂度。架构上分为 Host、Client、Server 三种角色，而且一个 Client 可以同时连多个 Server——Client 维护 Server 列表，每次请求前先聚合所有 Server 的工具列表给模型，模型选定工具后再按归属路由到对应 Server，Cursor 配置多个 MCP Server 就是这个原理。交互分两个阶段：初始化阶段拿工具清单，查询处理阶段走"工具调用循环"，直到 LLM 给出最终文本响应。Server 对外暴露 Tools、Resources、Prompts 三类能力——Tools 像给模型用的遥控器，执行前要用户确认授权；Resources 像给模型看的文档，只读无副作用。消息格式是 JSON-RPC 2.0，连接建立后要先走 initialize 握手协商版本、交换能力。传输上本地用 stdio，零网络开销，Claude Desktop 就是这种方式；线上用 Streamable HTTP，无状态、可负载均衡，旧的 HTTP+SSE 双连接模式已被废弃——一句话，本地工具用 stdio，线上服务用 HTTP。它和 Function Calling 是互补关系，不是替代关系：MCP 是通信协议，解决怎么标准化地和外部系统交互；Function Calling 是模型能力，解决模型怎么理解并产出工具调用请求；就算模型不支持 Function Calling，也能用 Prompt 引导让它输出结构化的工具调用意图，应用层解析后再走 MCP 调用工具，技术上完全可行。工程实践上有两个容易忽略的点：工具列表会占用大量 context window，建议一个 Server 控制在 10-20 个工具以内；Server 挂了或超时要靠 Client 的超时、重试和熔断兜底，Server 侧做好健康检查和优雅降级。安全上 MCP 设计了权限隔离、用户确认、传输安全三道边界，每个 Server 只能访问自己管辖的资源，敏感操作需要用户手动授权，新版本还引入了 OAuth 2.1 授权框架。最后，自己开发一个 Server 只要三步——能力定义、协议层、业务逻辑，用官方 Python 或 TypeScript SDK，继承几个类、实现几个方法就能跑起来。

回答动线：是什么（定位/价值）→ 怎么跑（架构/流程/消息/传输）→ 和 Function Calling 什么关系 → 落地要注意什么（实践/安全）→ 我上手过（开发）。

6.1选型决策：什么场景该用谁

  • 普通接口、网页资源：HTTP/1.1 或 HTTP/2，生产环境一律 HTTPS
  • 只需要服务器推送、客户端不回话：优先 SSE（自动重连、简单），如 AI 逐字输出、行情
  • 需要双向高频实时交互：WebSocket（wss），如聊天、协同编辑、多人游戏
  • AI 应用要接入外部工具/数据源：直接用 MCP，别再造私有对接协议；本地用 stdio，远程用 Streamable HTTP

6.2贯穿全文的一条演进主线

第一步：让连接可复用（HTTP 版本演进）

短连接 → Keep-Alive → 多路复用 → QUIC，解决"连接开销与队头阻塞"

第二步：让通道安全（HTTPS）

插入 TLS 层，用非对称加密协商密钥、对称加密传数据、CA 证书认证身份

第三步：让服务器能主动说话（SSE）

把一次 HTTP 响应变成持续的事件流，单向推送，自动重连

第四步：让双方完全平等（WebSocket）

一次升级握手后全双工，文本与二进制帧随时互发

第五步：让连接有统一语义（MCP）

复用前面所有传输，在其上标准化"能力协商 + 工具调用 + 授权"，连接的进化从"传得更快更安全"走向"传得更有意义"

一句话记忆：HTTP 定了"怎么问怎么答"，HTTPS 让问答"只有双方听得懂"，SSE 让服务器"能主动念叨"，WebSocket 让两边"随时畅所欲言"，MCP 则让 AI 与工具之间"用同一套术语对话"。
