## A1 · 第2轮

# 第三块：名词解释——Milvus 瞬态重试 + BM25 多桶重构

## 3.1 BM25 多桶重构（先讲 BM25 和“桶”是什么）

**词→概念映射**：
- **BM25**：经典关键词相关性打分函数（TF-IDF 的改良版）。对 query 分词后，按每个词在文档中的词频（TF，带饱和曲线：出现 10 次不比 5 次相关两倍）和稀有度（IDF）加权求和。本项目用 `rank_bm25` 库的 BM25Okapi + jieba 中文分词，作为向量检索之外的**关键词召回路**（专有名词、型号、错误码这类 query 向量容易输给 BM25）。
- **桶（bucket）**：BM25 是**统计模型**，算 IDF 必须先看到整个语料。为了隔离和多实例复用，语料按 `user_id:kb_id` 分桶，每桶独立建一个 BM25Okapi 模型，缓存在内存（`_models` dict）。

**旧设计为什么有 bug**（这是重构的动机，必须讲清）：

```
旧路径：用户检索【不带 KB 过滤】时
  → 懒构建 "user:_all" 聚合桶（该用户所有 chunk 拼一个大模型）
  → 聚合模型缓存按 user 缓存
  ⚠ bug：增量写入新 chunk 时，只失效了 (user:kb) 单桶，
    "user:_all" 聚合缓存没跟着失效
  → 后果：新导入的内容在"全局搜索"下检索不到（缓存与数据不一致）
```

**新设计**（`bm25_client.py` 现行实现）：

```
检索：_candidate_bucket_keys() 按过滤条件定位候选桶（三种路径）
  ├─ 指定 KB 集合 → _buckets_for_kbs()（覆盖属主桶+增量写入桶）
  ├─ 指定单 KB → 直查该桶；查不到（共享场景：检索者非属主）→ 按 KB 定位
  └─ 无过滤 → 该用户的所有桶，逐桶检索
多桶检索：每桶独立打分 → 桶内 top 截断 → 跨桶按 doc_id 去重（保高分）→ 全局 top
  ⚠ 明确不构建跨桶聚合模型（注释里写明：聚合缓存无法随增量写入正确失效）
  注意：各桶独立拟合 IDF，跨桶分数不完全可比 → 上层 RRF/rerank 负责统一重排
```

**为什么这个设计是自洽的**（面试升华点）：它放弃了“跨桶绝对可比的分数”，换取“**缓存失效的正确性**”——因为上层本来就有 RRF（只看排名不看分数）和 BGE 精排兜底，BM25 层分数的跨桶可比性是伪需求。**用架构里已有的下游能力，换取上游失效逻辑的正确性**，这是很典型的工程权衡。

**配套三件套**（同一次重构带出来的）：
1. **分词缓存落 PG**：`document_chunk.tokenized` 列（TEXT 空格连接 + LZ4 压缩），分词结果 chunk 粒度持久化，写路径 `ON CONFLICT DO UPDATE` 自动置脏失效——**单一事实源，无旁路一致性问题**；
2. **LRU 双上限**：桶数 ≤16 / 总 chunk ≤100k，`OrderedDict` 逐出最久未用桶（重建成本因 PG 缓存而降到毫秒级）；
3. **审计埋点**：`bm25.cache.lru_evict` / `bm25.cache.tokenize_batch`（含 cache_hit/miss/elapsed_ms），逐出和分词开销可观测。

**压测证据**：keyword 模式 200 请求 @ 20 并发，修复前 p50=203s（基线轮还带 7.5% 假错误率），复验 p50=158.8s、**200/200 全成功**——“BM25 多桶重构扛住 20 并发 200 请求零失败”。

## A2 · 第3轮

# 五、BM25 聚合缓存两句话的完全展开

这两句话都指向同一个 bug。先铺一个前置概念，再用具体例子把 bug 演出来。

## 5.1 前置：为什么“跨桶分数不可比”（IDF 是罪魁）

BM25 给文档打分 = 对 query 里每个词累加贡献，每个词的贡献里有个 **IDF 因子（逆文档频率）= log(语料总文档数 / 含该词的文档数)**——衡量“这个词多稀罕”。**IDF 是基于统计语料算出来的**，语料变了 IDF 就变：

```
桶 A（技术文档库，1000 篇）：词"部署"出现于 800 篇
  → IDF(部署) = log(1000/800) ≈ 0.22   ← 烂大街，几乎不加分
桶 B（财务制度库，1000 篇）：词"部署"出现于 20 篇
  → IDF(部署) = log(1000/20) ≈ 3.9     ← 很稀有，强加分

同一个 query"部署流程"打两桶：
  文档 a（桶A，真讲部署流程）得分 8.0
  文档 b（桶B，只是提了一嘴"部署"）得分 15.2
  → 直接比分数：b "赢"了 —— 但 b 明显不如 a 相关
  → 因为两个分数用的是两套不同的 IDF 尺子
```

这就是“各桶独立拟合 IDF，跨桶分数不完全可比”的全部含义。**不是实现缺陷，是 BM25 的统计本质**：分数的量纲绑定语料。

## 5.2 旧设计为什么有 bug——用一次真实操作演出来

旧设计的内存结构长这样：

```
_models = {
  "5:17":  BM25模型（用户5的KB17语料建的）,
  "5:18":  BM25模型（用户5的KB18语料建的）,
  "5:_all": BM25模型（用户5的【所有KB拼在一起】的语料建的）  ← 聚合桶
}
```

聚合桶 `_all` 存在的理由：用户**全局搜索**（不带 KB 过滤）时一次查一个模型，分数还全局可比（毕竟是一套 IDF）——看起来又快又对。

**然后 bug 来了**——用户 5 往 KB17 导入一批新文档：

```
【写入路径】import 新 chunks（属于 user5/KB17）
  ├─ _corpus["5:17"] 加入新 chunks                      ✓
  ├─ _invalidate_model("5:17")   ← 单桶模型缓存失效      ✓
  └─ _corpus["5:_all"]？_models["5:_all"]？
      没有任何代码通知它们                            ✗ ✗ ✗

【读取路径】用户 5 做"全局搜索"（不带 KB 过滤 → 路由到 "5:_all"）
  → 命中 _models["5:_all"] 的【旧缓存模型】
  → 旧模型的语料里没有刚导入的 chunks
  → 新内容检索不到 —— 数据明明导入成功了，搜索就是看不见
```

**“无法随增量写入正确失效”的准确含义**（比你引用的那句话更狠）：技术上*可以*修——每次写 `(5:17)` 桶时联动 `_invalidate_model("5:_all")` 就行。但这是一条**隐式纪律**：项目的写路径不止一处（单条 add、批量 add、update、删除、KB 克隆……），每一处都必须记得联动失效 `_all`。写路径越多，漏一处的概率越大，漏一处 = 脏缓存 = 静默的数据不一致（最难查的那类 bug：不报错、不崩溃、只是“搜不到该搜到的东西”）。**正确性依赖程序员在每个写点的纪律，而不是靠结构保证——这就是“无法正确失效”的判决理由。**

## 5.3 新设计：拿“可比性”换“正确性”的交易

新设计直接**消灭了 `_all` 聚合桶**（现在代码里 `_candidate_bucket_keys` 的注释明确写着“不再构建 user:_all 聚合模型”）：

```
全局搜索（无 KB 过滤）= 遍历该用户所有桶：
  for key in [5:17, 5:18, ...]:
      scores = 该桶模型打分            ← 各桶自己的 IDF 尺子
      取桶内 top-N
  跨桶按 doc_id 去重（同文档出现于多桶时保留高分）
  → 合并出全局 top
```

这笔交易的账本：

| | 旧设计（聚合桶） | 新设计（逐桶+合并） |
|---|---|---|
| 分数跨桶可比？ | ✅ 一套 IDF，天然可比 | ❌ 各桶各的尺子 |
| 缓存正确性？ | ❌ 靠写路径纪律维持，漏一处就脏 | ✅ **结构上不可能脏**：每桶的失效只关自己，写哪个桶就失效哪个桶，没有任何“联动”需求存在 |
| 全局搜索代价 | 查 1 个大模型 | 查 K 个小模型再合并 |

**为什么敢放弃可比性**——因为下游早就备好了不怕量纲混乱的组件：

1. **RRF 融合**：`score(d) = Σ 1/(k + rank)`——**只看排名，根本不看分数值**。文档 a 在桶 A 排第 1、文档 b 在桶 B 排第 1，贡献完全一样，8.0 分还是 15.2 分与它无关。RRF 天然免疫量纲问题（这正是它在混合检索界流行的核心原因）。
2. **BGE 精排**：拿到合并后的候选集，对 (query, doc) **用同一个模型重新打分**——统一量纲的最后裁决，BM25 层的分数只是“入场券”。

所以那句“放弃了跨桶绝对可比的分数，换取缓存失效的正确性”翻译成大白话就是：**BM25 层的分数可比性是个伪需求（下游只用排名和重打分），而缓存正确性是真需求（脏缓存 = 静默丢数据）——拿一个没人要的东西换一个致命的东西，这买卖稳赚。**这是“用架构里已有的下游能力，换取上游失效逻辑的结构性正确”的最纯粹案例。

# 一、属主桶 vs 增量写入者桶

## 1.1 先看分桶键是谁决定的——写入时刻的“操作者”

关键代码在导入管线（实锤）：

```194:198:backend/api/processing.py
                search_client.index_chunk(
                    chunk_id=chunk_id,
                    user_id=current_user["id"],      ← 传的是"当前操作者"，不是 KB 属主
                    document_id=file_id,
                    knowledge_base_id=doc["knowledge_base_id"],
```

桶键 = `f"{user_id}:{kb_id}"`。**user_id 用的是“此刻是谁在上传”**——这是全部故事的源头。

## 1.2 两种桶怎么诞生的——一个具体场景演出来

设定：用户 5（张三）有知识库 KB17，并把**写权限**共享给了用户 8（李四）。

```
张三自己往 KB17 上传文档：
  index_chunk(user_id=5, kb_id=17) → chunk 进桶 "5:17"
  ← "5:17" 就是【属主桶】（写入者恰好是属主）

李四往张三的 KB17 上传文档（共享写权限）：
  index_chunk(user_id=8, kb_id=17) → chunk 进桶 "8:17"
  ← "8:17" 就是【增量写入者桶】（写入者不是属主）
  同一个 KB 的数据，此刻散落在两个桶里！
```

**为什么写路径不解析“这个 KB 的属主是谁”再统一入桶？**——省一次查询。写路径高频（每个 chunk 都要走），每次都去 PG 查 `knowledge_base.owner` 是白付的往返；而“桶散落”的问题可以留给**读路径一次性解决**（读远少于写，或者说读写比在这个系统里不高）。

## 1.3 读路径怎么把散落的桶找齐——之前贴过的 `_candidate_bucket_keys` 现在能真正看懂了

```300:328:backend/services/bm25_client.py
    def _candidate_bucket_keys(self, user_id, filters) -> List[str]:
        kb_id = filters.get("knowledge_base_id") if filters else None
        kb_ids = filters.get("knowledge_base_ids") if filters else None

        if kb_ids:
            kb_set = {int(k) for k in kb_ids if k is not None}
            return self._buckets_for_kbs(kb_set)          ← 按 KB 维度收齐所有桶

        if kb_id is not None and kb_id != 0:
            key = self._bucket_key(user_id, kb_id)
            if self._corpus.get(key):
                return [key]
            # 回退：该 KB 的桶按属主（或增量写入者）分桶，检索者非属主（共享 KB）
            return self._buckets_for_kbs({int(kb_id)})     ← 找不到自己的桶 → 按 KB 收齐
```

三个角色视角把三条路径走一遍：

| 谁在搜 | 走哪条路 | 找到什么 |
|---|---|---|
| 张三（属主）搜自己的 KB17 | 直查 `5:17` 命中 | 只有属主桶——**李四写的在 `8:17`，漏了？！** |
| 李四（共享者）搜 KB17 | 直查 `8:17`——如果李四没传过任何东西，桶不存在 → 回退 `_buckets_for_kbs({17})` | 按 kb 后缀匹配，收齐 `5:17` + `8:17` |
| 任何人带 KB 列表过滤 | `_buckets_for_kbs` | 同上，按 KB 收齐 |

注意第一行那个尖锐的问题：**属主直查自己的桶会漏掉增量写入者桶吗？** 看代码：属主路径是 `if self._corpus.get(key): return [key]`——命中就**只返回属主桶**。这意味着运行期属主搜 KB17 确实可能看不见李四刚传的内容（桶 `8:17` 没进候选）……**直到重启**。

## 1.4 重启的“归化”现象——补上这个系统最漂亮的一块拼图

`load_from_database` 的注释（前面贴过）现在完全能读懂了：

```399:406:backend/services/bm25_client.py
            # document_chunk 无 user_id 列：JOIN knowledge_base 取属主，
            # 保证重启加载后的分桶键与 index_chunk(user_id=KB 属主) 一致
            rows = db.fetchall(
                """
                SELECT dc.*, kb.user_id
                FROM document_chunk dc
                LEFT JOIN knowledge_base kb ON dc.knowledge_base_id = kb.id
                """
            )
```

重启加载时**不信任内存里的桶布局**，直接按 PG 权威数据 + 属主 JOIN **重新分桶**——李四写进 `8:17` 的所有 chunk 重启后全部归化进 `5:17`（属主桶）。两个运行期的桶，重启后合成一个。

把整个机制拼成一句话：

> **内存桶布局是运行期的、允许散乱的索引组织；PG 是唯一权威。写路径贪快（谁写进谁的桶），读路径兜底（按 KB 维度收齐），重启归化（按属主重分）。散乱有界：最多到下次重启。**

这也解释了 `delete_chunk` 为什么“需要在所有桶中查找”——删除时你手里只有 `(chunk_id, user_id)`，那个 chunk 可能是属主写的（在属主桶）也可能是任何共享者写的（在别人的增量桶），除了按 chunk_id 扫遍所有桶没有更便宜的定位法。

**业界对照**：这就是多租户索引的经典权衡——**按“写入者”路由（write-locality，写快读散）vs 按“数据属主”路由（read-coherent，写要解析）**。ES 里对应 `routing` key 的选择（按租户路由保证同租户文档落同一 shard）；数据库领域对应按 tenant 分 schema 还是共表加列。本项目的答案是“写按操作者、读按 KB 收、重启归一”——单机场景的低成本解。

## Q4 · 第6轮 · 追问

为啥选择pg+lru而不是pg+redis？

## A4 · 第6轮

# 二、为什么 BM25 缓存选“PG + 内存 LRU”而不是“PG + Redis”

这个问题有个隐蔽的陷阱：它假设 Redis 是那个“更高级”的选项。正确答案是——**Redis 存不了 BM25 模型，因为 Redis 存的是数据，而 BM25Okapi 是计算对象**。展开讲：

## 2.1 BM25Okapi 到底是什么性质的东西

回看它的成分（前几轮讲过）：IDF 权重表 + 每篇文档的词频 dict + doc_len 列表——**外加一个 `get_scores(query_tokens)` 方法**。它不是“存起来等查的数据”，是“驻留在内存里、每次搜索都要对它跑计算的执行体”：

```
一次搜索的姿势：
  tokens = jieba(query)
  scores = model.get_scores(tokens)   ← 对模型做 CPU 计算，遍历它的内部结构
```

Redis 的世界是什么样的：**一切皆字节串**。你能放进去的只有序列化后的 blob。于是“把 BM25 模型放进 Redis”的真实含义是：

```
写入：pickle(model) → MB 级 blob → SET bm25:model:5:17 <blob>
使用：GET bm25:model:5:17 → 网络传输 MB 级 → unpickle → 还原成内存对象 → 才能算
```

## 2.2 三个数字把这条路判死刑

| 环节 | 耗时量级 |
|---|---|
| 进程内存 dict 查找 `_models[key]` | **~100ns** |
| 本机 Redis GET（含 RTT） | ~0.5-1ms（**慢 5000-10000 倍**） |
| MB 级 blob 反序列化（unpickle） | 几十 ms |
| **而重建一个 BM25Okapi（有 PG 分词缓存后）只要毫秒级！** | ← 最讽刺的一行 |

对，你没看错：因为分词结果已经持久化在 PG、统计拟合是纯内存毫秒级计算，**“每次从 Redis 拉回来”比“当场重建一个”还慢几十倍**。Redis 化 BM25 模型在每一个环节都是负收益——传输慢于重建、反序列化慢于重建、还要白背一个 Redis 依赖。

## 2.3 真正的分工：这个项目其实是“按对象性质分引擎”

关键认知：**“可共享的数据”和“进程私有的计算对象”本来就是两种东西，应该分开对待**：

| 东西 | 性质 | 引擎 | 理由 |
|---|---|---|---|
| 分词结果（token 串） | **数据**：纯字节、可序列化、贵在产生（jieba 秒级） | **PG**（`tokenized` 列） | 跨重启、跨实例、事务失效、跟行走 |
| BM25Okapi 模型 | **计算对象**：含方法、贵在使用（每搜必算）、重建便宜 | **进程内存 + LRU** | 计算必须发生在进程内（CPU 局部性），序列化进出比重建还贵 |
| 搜索结果缓存 | **数据**：JSON 可序列化、贵在产生（全链路 10-70s） | **内存 LRU + Redis 两级**（`cache.py`） | 多实例可共享命中、值钱到值得跨进程 |

第三行是决定性的证据：**这个项目根本不是“没用 Redis”，`cache.py` 里 L2 就是“内存 LRU → Redis 两级读取、双写”**（L1 是 PG embedding 缓存）。所以选择不是“PG+LRU vs PG+Redis”二选一，而是**同一套判断式应用了三次，得出三个不同答案**：

```
判断式：这东西是数据还是计算对象？重建成本 vs 序列化+传输成本谁高？需要跨进程共享吗？
  分词结果   → 数据 + 重建贵（秒级）+ 要共享 → PG
  检索结果   → 数据 + 重建极贵（秒-十秒级）+ 要共享 → Redis（+内存前置）
  BM25模型  → 计算对象 + 重建极便宜（毫秒）+ 进程私有 → 纯内存 LRU
```

**GIL 在这里也补一刀**：就算你想“共享”模型给别的进程，别的进程拿到序列化 blob 还得还原成自己的内存对象自己算——多进程各自持一份模型是绕不开的（计算不可能远程发生，除非换计算引擎）。既然每进程必然各持一份，Redis 就只剩“帮邻进程省一次重建”的价值——而重建才毫秒级。价值为零。

## 2.4 那“真想跨进程共享关键词检索”怎么办？——换引擎，不是塞 Redis

如果哪天多实例部署、内存里 N 份 BM25 模型 + N 份语料镜像撑不住了，正确动作是把**整个关键词检索的计算**外置到一个共享引擎——**Elasticsearch**（倒排索引 + TF-IDF/BM25 打分本来就是它的看家本领，天然跨进程、分片、容错）。本项目**已经有这个逃生门**：`elasticsearch_client.py` 是完整实现的第二后端（`SEARCH_BACKEND` 可切 `bm25`/`es`，接口对齐——`index_chunk`/`search`/过滤语义注释里明写“与 BM25/Milvus 对齐”）。业界同类：Solr、OpenSearch、Vespa。

一句话收束（面试可背）：

> **“缓存引擎跟着对象性质走：能序列化的数据按价值分层进 PG/Redis；不能序列化（或序列化比重建还贵）的计算对象留在进程内用 LRU 管生命周期。真到了要跨进程共享计算的时候，答案不是把计算对象塞进缓存，是把计算本身换成引擎（ES）。”**
