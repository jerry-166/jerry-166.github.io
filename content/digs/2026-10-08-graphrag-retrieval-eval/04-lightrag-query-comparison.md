## Q5 LightRAG 对比修正（含口径炸弹，务必读完）

先认错：上一轮“keyword 提取 + 实体抽取 + 图遍历 + **多段生成**”的表述不准确——“多段生成”是错的（LightRAG 生成就是 1 次），且你的质疑完全成立：**我们也要 LLM 抽锚点**。真实的差异不在“要不要抽”，在下面这张表：

### 两边查询路径逐步骤对照（修正版）

| 步骤 | 我们 native(rerank关) | 我们 graph | LightRAG naive | LightRAG hybrid |
|------|---------------------|-----------|----------------|-----------------|
| keyword/实体抽取 | **零 LLM**（BM25 用 jieba 分词） | LLM 锚点提取 ×1（输出≤300 token，**极短**） | 无 | LLM keyword 抽取 ×1（高/低层关键词） |
| 向量检索 | Milvus ANN ~100ms | Milvus 实体向量 ~100ms | PGVector ~1s | PGVector ~1s |
| 图遍历 | 无 | **PG 一跳 SQL，毫秒级** | 无 | 实体+关系文本收集，秒级 |
| 精排 | rerank 开时 BGE（**本地模型，非 LLM**） | BGE 本地（统一 reranker） | 无独立精排 | 无独立精排 |
| **生成答案** | **无——agent 层负责** | **无——agent 层负责** | **LLM 生成，长输出** | **LLM 生成，长输出** |

三个真实差异：**a)** LLM 调用次数其实相近（graph 2 次 vs hybrid 2 次），差别在**输出长度**——我们两次都是 ≤800 token 的结构化短输出，LightRAG 的生成是几百到几千 token 长输出，延迟差一个量级；**b)** 检索/生成**分离 vs 耦合**——我们是 agent 架构，检索是独立工具，LightRAG /query 是检索+生成捆绑的单体；**c)** 精排架构——BGE 本地 CrossEncoder（非 LLM）vs LightRAG 无独立精排。

### 口径炸弹（本轮核实坐实）

我查了 B 轮压测脚本 `work/lightrag-vs/bench_lightrag.py:50-58` 和端点实现 `backend/api/search.py:217-226`：

```
本项目压测端点: POST /api/milvus/query
  文档字符串原文: "纯向量检索 — Query → Embedding → Milvus ANN Search
                  → [可选] Rerank → Top-K"        ← 不含生成!

LightRAG 压测端点: POST /query
  LightRAG 的 /query 返回完整答案文本            ← 含生成!
```

**B 轮 23.5× 是“我们的纯检索 1.8s”对比“LightRAG 端到端（含生成）43.3s”**。而 B 轮报告写“本项目查询单步（embed+Zilliz检索+BM25+生成）”——与压测事实不符（native 链路无 BM25、压测端点无生成）。**如果面试官问“你们 1.8s 含生成吗”，照背报告原话就露馅。**

### 修正后的讲法（三层，都能站住）

1. **字面诚实**：“23.5× 是本项目检索服务延迟 vs LightRAG 端到端查询延迟——我们的架构把检索和生成解耦，检索是独立服务；LightRAG 的最小查询单元就是含生成的完整答案。”
2. **架构主张（真实优势）**：检索生成分离 → 检索可缓存（L2 缓存）、可独立扩缩、agent 可编排多工具；LightRAG 单体查询每条都要跑完整 LLM 流水线。这是 agent 架构 RAG vs 单体 RAG 的哲学差异，4.3×/23.5× 都是它的表现。
3. **数量级修正（被追问时）**：两边生成用同模型（gpt-4o），生成耗时相当；剔除生成后 LightRAG 残余的 keyword 抽取 LLM + PGVector + 图操作估算仍是秒到十秒级 vs 我们 1.8s——架构级差距存在，但**不是 23.5×，约 5-10×（估算值，未插桩，如实标注）**。graph 对比（9.9s vs 42.9s）我们含 2 次 LLM 不含生成，同样要声明。

**评估缺口**：本项目“检索+生成”的端到端 p50（/api/agent/chat）没有单独压测过——被问就如实说“这是已知评估缺口，检索和生成分离的架构下我们分别度量”。

## Q1 新问题：LightRAG 第 3 步“怎么合并的？”

基于 LightRAG 论文（arXiv:2410.05779）和开源实现的描述（标注：**论文级知识，本项目未对其内部插桩**）：

```
LLM 抽 keywords(high-level + low-level)
   │
   ├─ low-level → 向量匹配实体(PGVector) → 取实体 + 它们的关联边
   │                                          │ 每条边格式化成文本:
   │                                          │ "head —relation→ tail | description | 来源chunk"
   ├─ high-level → 匹配社区(聚类摘要) → 取社区报告文本
   │
   ▼
合并 = 三类候选(实体文本/关系文本/原文chunk)各自按与query的相似度排序
       → 各自截断 top-N → 格式化成带小标题的文本段
       ("---Entities---/---Relationships---/---Sources---")
   ▼
整个拼接文本作为 context,一次 LLM 调用生成长输出答案
```

**和我们 graph 的合并对照（这段值得背，是 faithfulness 差异的架构根因）**：

| | LightRAG | 我们 graph |
|---|----------|-----------|
| context 成分 | **三种异质文本混装**：实体描述 + 关系描述 + 原文 chunk | **只有原文 chunk**（图只用来“定位”chunk，不做 context 素材） |
| 合并逻辑 | LLM 生成的结构化文本再文本化，相似度排序截断 | chunk_ids 去重截断（limit×2）+ score 分层（0.9/0.75），机械可解释 |
| 后果 | 生成 LLM 拿到的是“二手描述”，可能基于关系描述发挥 → C 轮1 faith 0.768-0.798 | 生成 LLM 只见原文，faithfulness 可控 → C 轮1 我们 0.94-0.97 |

一句话：“LightRAG 把图数据**文本化后喂给 LLM**，我们用图**定位原文后只喂原文**——这是我们 faithfulness 领先 +21% 的架构解释。”
