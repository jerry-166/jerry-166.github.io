# 高并发抢购系统追问深挖：数字出处、单 Key 分段、延迟双删与库存分段三代价

> 本文是《高并发抢购系统：从 0 到 1 的工程级设计》的追问深挖篇——正文定稿后围绕报告的六个追问和库存分段三代价的工程化缓解，先给结论再给推导。

## 一、MySQL 单行热点 1~3k TPS 是什么意思

指每秒最多完成约 1000~3000 次「对同一行的 UPDATE + COMMIT」，其余全部在行锁上排队。三个成本叠加：

1. **行锁串行**：InnoDB 对同一行的排他锁互斥，100 个事务同时改一行 = 物理上串行执行，这是硬上限；
2. **每次提交的固定成本**：`innodb_flush_log_at_trx_commit=1` 时，每个事务提交都要 fsync 一次 redo log（磁盘往返毫秒级）；
3. **连接占用放大**：排队事务每个都占一个连接，几十个连接的池几秒耗尽——表现为全站雪崩而非「慢一点」。

关键对比：更新不同行（无锁冲突）时单机轻松几万 TPS。1~3k 是「所有请求打同一行」特有的数字，不是 MySQL 整体能力——这正是秒杀库存的处境。

## 二、Redis 10w / Nginx 5w 这些数字哪来的

行业经验值，用于数量级估算，不是官方某次测试的精确结果：

- Redis 10w+：官方 redis-benchmark 的公开常识，业务带 Lua 与网络往返保守按 8~10w；
- Nginx ~5w：社区压测共识，4 核反代 3~5w，受 TLS、日志、body 大小影响；
- MySQL 1~3k：单行热点压测典型区间，取决于 commit 参数。

面试答法：「官方 benchmark + 社区经验的数量级估计，用来推导架构方向；真实容量以我们自己的全链路压测为准。」能区分「估算」和「实测」本身就是工程素养加分项。

## 三、CPU 核数规划：工程级设计必须落到机器规格

| 组件 | 吃 CPU 吗 | 真正瓶颈 | 典型做法 |
|---|---|---|---|
| Redis | 几乎不吃（命令处理单线程） | 内存容量 + 网络带宽 | 8~16C 够用，CPU 常年 <20% |
| Nginx | 吃 | 网络 IO | worker_processes = 核数 |
| 应用（FastAPI） | 吃 | 视 IO/CPU 密度 | worker 数 ≈ 核数（多进程绕 GIL） |
| MySQL | 吃 | 内存优先 | 加内存到 Buffer Pool（50~70%）比加核更值 |

k8s YAML 的 requests/limits 就是机器规格规划的落地：8 核机器给秒杀 Pod 保底 1 核，防止混部时被其他业务挤占。

## 四、单 Key 要不要分段：对一半，错一半

推理链「不是 big key → 单线程串行处理 → 不会有并发冲突 → 不需要分段」——前三步对，最后一步错。

错误在于**把「正确性没问题」和「吞吐没问题」划了等号**。单线程确实免费保证了正确性（同一 key 的命令天然串行、永不冲突），但「串行」本身有速率上限——单线程跑满一个核，一秒约 10 万条命令，50w QPS 打过来 40w 只能在 TCP 缓冲区排队。

Redis Cluster 扩展为什么帮不了忙：按 slot 路由，key 只属于一个 slot、一个节点——加节点不改变归属，流量汇回同一节点。

判断标准：

- 单 key QPS 低于单节点能力一半（<5w）：不用分段，常规业务直接单 key；
- 秒杀 50w 单 key：远超上限且集群扩容无效，必须分段，段数 = 并行度；
- 优先级：本地售罄标志 > 分段（售罄后 99% 流量不出实例，内存 boolean 直接拒）。

面试金句：**单线程保证了正确性是免费的，但吞吐是有价的——分 key 解决的是吞吐，不是冲突。**

## 五、削峰的数字账怎么算

1. 成功请求数 = 库存数 = 1 万（其余 49 万被各层拒绝，只有成功者要生成订单）；
2. 不经 MQ 直接写库：1 万个订单事务（INSERT 订单 + INSERT 防重 + UPDATE 同一库存行）挤在 1~2 秒内，第三条就是单行热点（上限 1~3k TPS）→ 排队 3~10 秒，行锁串行期间连接池被等待事务占满，连快速失败路径都被拖死；
3. 经 MQ：生产端 1 秒内全写入（顺序 append 磁盘日志，单机百万级/秒）；消费者固定 2k/s → 5 秒消化完，2k < 热点上限 3k 安全；
4. 用户视角：下单立刻返回「排队中」，P99 从「连接超时/报错」变成「多等 5 秒」。

一句话：**削峰削的不是请求（照样 50w/s 涌入），削的是 DB 的瞬时写入需求**——把时间上集中、总量有限的写入摊平成 DB 能承受的速率。

## 六、延迟双删与订阅 binlog

「先更新 DB 再删缓存」的竞态窗口：读请求 T1 未命中 → 读 DB 得 v1；写 T2 更新 DB 为 v2 → 删缓存（空删，此时缓存还没有 v1）→ T1 回填 v1——**DB 已是 v2，缓存钉死在 v1**。

| 方案 | 做法 | 原理 | 缺点 |
|---|---|---|---|
| 延迟双删 | 删缓存 → 更新 DB → 等 N 秒 → 再删一次 | 第二次 DEL 落在所有在途读完成回填之后，旧值被清掉，下次读加载 v2。N = 一次回源耗时 + 余量（经验 1~2s，实践用延迟消息而非 sleep 占线程） | N 靠估（读耗时动态）；第二次 DEL 也可能失败（需重试队列）；N 秒内读到旧值 |
| 订阅 binlog（Canal/Debezium） | 业务只写 DB 完全不碰缓存；Canal 伪装从库解析 binlog → 投 MQ → 缓存维护服务删 key | 伪装 MySQL 从库接收 binlog 得到「哪个表哪行变了」；事务提交必产生 binlog → 可靠、零侵入、按事务顺序 | 链路长（DB→Canal→MQ→消费者，几十 ms~秒级）；多一套中间件运维 |

适用边界：这套讨论只针对常规读缓存数据（商品信息等）；秒杀库存主存储本来就在 Redis（方向 Redis→DB 异步入账），不存在「删缓存」问题。

## 七、Deployment 多副本 + HPA 是什么意思

- **Deployment**：k8s 描述「我要 N 个一模一样实例」的对象，replicas: 8 = 8 个无状态 Pod 分摊流量，任何一个挂了自动再拉一个，永远维持 8 个；
- **HPA**（Horizontal Pod Autoscaler）：持续监控 Pod 的 CPU/内存利用率，超阈值（如 60%）自动把 replicas 从 8 提到 16，低谷缩回；
- **为什么秒杀手动扩容为主**：HPA 全流程 = 指标采样（15s 一轮）+ 决策 + 调度 + 拉镜像 + 启动 + 预热 = 30s~2min，而秒杀尖峰只持续几秒——扩出来的 Pod 上线时活动已经结束。

原则：**尖峰类流量的所有准备动作，都必须发生在尖峰之前。**

## 八、库存分段三代价的工程化缓解

统一思路：**请求层把错误吞掉（重试/闸门），收尾层把碎片归位（合并），数据层把账算清（守恒+流水）。**

### 代价 1：碎片（假售罄 → 少卖）

请求层三件事：

1. 返回码区分语义：1 成功 / 0 本段空（可换段重试）/ 全局售罄（放弃）——混淆两种「失败」是重试风暴之源；
2. 本地路由表：内存数组标记疑似空段，选段时跳过，标记带短 TTL（1~2s）自愈（段会被关单流程回补，不能永久拉黑）；
3. 重试上限 3 次：每次 ≈1ms Redis 往返，3 次全空概率上等价全局售罄。重试耗尽返回**软失败（429）而非写死全局售罄**——请求层没有资格下全局结论，该结论只能由后台基于 Σ段余量下。

收尾层段合并四步纪律（顺序即安全），触发条件 Σ余量 < 5% 或流量回落：

1. 冻结路由：路由表标记段 1..N-1 为 draining，新请求只去段 0；
2. 排空在途：等 1~2 秒宽限期，让已选段的请求执行完；
3. 逐段 CAS 置零：每段 `if GET==v then SET 0`——期间有扣减（v 变了）就重读重试，保证不丢不多；
4. 归集：捕获的 Σv 加到段 0。不变量：每步 Σ(所有段余量) 守恒——合并只搬运库存，不创造不销毁。

> 金句：**碎片导致的是少卖，不是超卖。少卖可恢复（货还在段里），超卖不可恢复（资金损失）——这个不对称性就是分段方案被工业界接受的全部理由。**

### 代价 2：判重集合必须全局唯一

两难：判重集合跟着段走 = 一人 N 单；不分段 = 判重自己变成热点 key，且 Cluster 模式下 Lua 脚本不能跨 slot（CROSSSLOT 报错）。

解法是**维度转换**：判重从「SKU 的集合」换成「用户的 key」：

```
SETNX gate:{skuId}:{userId} 1 EX 活动时长
```

key 含 userId → 不同用户 hash 到不同 slot → 判重流量自动摊到整个集群，热点问题用维度转换消解而不是硬扛。顺序纪律：闸门先行（SETNX 通过才碰库存段）；换段重试期间不释放闸门（一旦释放，同一用户两个并发请求可能各占一段 → 双单）；确定放弃时也不主动删，交 TTL 自然过期。

崩溃窗口定性：SETNX 成功后扣减前宕机 → 用户被「幽灵闸门」挡到 TTL 过期——**体验问题而非正确性问题**（正确性锚点在 DB 唯一索引），失败时 best-effort DEL 自愈。

最终锚点不变：DB 防重表唯一索引 `(user_id, sku_id, activity_id)`——Redis 层所有设计都是性能优化，唯一索引才是正确性本身。

### 代价 3：对账复杂度上升

库存状态从「一处」散成 N 段 + 在途请求 + 回补流水 + 合并中间态，守恒式变长了。先把恒等式写全：

```
total = Σ(各段余量) + 未关闭订单数(含在途) + 已回补数
```

每次段变动写流水（XADD 到 Redis Stream：段号/用户/Δ/序号），对账 = 流水重放核验；对账窗口避开流量尖峰，否则在途数制造假差异。

分层对账：

| 层级 | 时机 | 内容 |
|---|---|---|
| L0 实时 | 消费链路内 | DB 条件更新 affected=0 → 订单挂起 + 告警 |
| L1 准实时 | 每 30s | 守恒恒等式核对 + 段活性指标：某段长期 0 扣减而其他段在动 = 路由 bug |
| L2 T+1 | 活动后 | Redis 扣减流水 vs MQ 消息 vs DB 订单三方核对 |

修复纪律（发现差异后怎么修才是出错重灾区）：

- 方向固定：以 DB 为准回补 Redis，永不反向覆盖 DB（DB 是资金安全的最终记录者）；
- 修复前先冻结：标记该 SKU/段 draining、暂停售卖，修完再恢复；
- 修复动作幂等 + 审计：人工调拨双人复核，留操作日志。

```python
async def seckill(user_id: int, sku_id: int):
    if local_sold_out(sku_id):                     # ① 本地售罄标志：0 网络开销直接拒绝
        raise SoldOut()

    # ② 用户闸门：key 含 userId → Cluster 下散列到不同节点，判重流量天然无热点
    #    SETNX 原子性 = 同一用户同一时刻只有一个请求能通过
    ok = await redis.set(f"gate:{sku_id}:{user_id}", 1, nx=True, ex=ACTIVITY_TTL)
    if not ok:
        raise HTTPException(409, "每人限购一件")

    for _ in range(3):                             # ③ 换段重试上限 3：防长尾延迟
        seg = pick_segment(sku_id)                 # 本地路由表选段，跳过空段标记
        ret = await redis.evalsha(SEG_SHA, 1, f"stock:{sku_id}:{seg}")
        if ret == 1:
            return await write_local_message(...)  # 成功 → 写消息表，异步落库
        mark_seg_empty(sku_id, seg, ttl=2)         # 标记短 TTL 自愈（段被关单回补后恢复可选）

    # ④ 软失败：请求层不写死全局售罄——售罄判定是后台基于 Σ段余量 的职责
    raise HTTPException(429, "太火爆了，请稍后再试")
```

## 小结

三代价的关系：**碎片靠「重试+合并」在请求和收尾层消化，判重靠「维度转换」避开热点，对账靠「守恒式+流水」把复杂度变成可计算的账**——复杂度没有被消灭，是被变成了三条各司其职的防线。
