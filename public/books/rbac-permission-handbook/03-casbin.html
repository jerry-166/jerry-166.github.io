01

定位：一个嵌入式权限库 ★★★★

回答"Casbin 是不是和我们写的一样，只是抽成了模块"——正是如此。Casbin 的模型与你手写的 RBAC 没有本质区别，它把"表结构 + 匹配逻辑 + 角色继承 + 多存储/多实例"这些通用能力抽成了一个库。

维度若依自研Casbin
形态框架内的表 + 代码引入的一个依赖库（Java 用 jCasbin，Spring Boot 用 casbin-spring-boot-starter）
运行位置应用进程内应用进程内（函数调用，不是独立服务）
判断调用@ss.hasPermienforcer.enforce(sub, obj, act) 或 @Enforce
支持模型RBAC + data_scopeRBAC0-3、ABAC、RESTful、域租户等，模型可换
一句话

Casbin 是"你调用的一个函数"（库）；OPA 是"你咨询的一个服务"（进程）。这是两者最根本的区别。

02

PERM 元模型：model.conf 与 policy 核心

Casbin 的核心是 PERM 元模型，把"规则"和"数据"彻底分开。你理解的"事先规定好规则、类似 SQL，校验时传入已有的和需要的权限判断 true/false"——完全正确。

2.1 model.conf：规则模板（开发写一次，全项目一份，十几行）

model.conf（RBAC + 角色）
# 请求：谁(sub) 对什么资源(obj) 做什么动作(act)
[request_definition]
r = sub, obj, act

# 策略：策略行也是 三元组 p = sub, obj, act
[policy_definition]
p = sub, obj, act

# 角色关系：g = 用户, 角色（RBAC 的用户-角色绑定）
[role_definition]
g = _, _

# 决策结果：存在任一满足的策略即放行（等价 EXISTS）
[policy_effect]
e = some(where (p.eft == allow))

# 匹配器：相当于 SQL 的 WHERE 条件
[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act

2.2 policy：策略数据（每条授权是一行）

policy.csv（演示用；生产存数据库）
# p, 主体, 资源, 动作  —— 角色权限
p, publisher, material:list, query
p, publisher, material:list, add
p, admin, material:list, export

# g, 用户, 角色  —— 谁是什么角色
g, u101, publisher
g, u102, admin

2.3 enforce：一次判断的过程

输入请求
enforce("u101", "material:list", "query")
→

u101 → publisher
→
matcher 匹配

图 3-1　matcher 类似 WHERE，enforce 等价"是否存在满足条件的策略行"（EXISTS）
五个关键字速记
  • r（Request）：一次鉴权请求 (sub, obj, act)；
  • p（Policy）：策略行，授权事实；
  • g（Grouping/Role）：用户-角色、角色-角色（继承）关系；
  • e（Effect）：多条策略如何合并（some allow / deny-override）；
  • m（Matcher）：布尔表达式，相当于 WHERE。
03

规则和策略谁来写？是自动化的吗？

这正是"model config 会不会太多、谁写入"的疑问。答案是两部分人、两种生命周期：

model（模型/规则）policy（策略数据）
是什么规则模板，定义请求结构、匹配逻辑（那十几行）一条条授权事实：谁是什么角色、角色有什么权限
谁写开发写一次，随代码版本走，基本不变运行时产生：管理员后台授权、业务动作（分享/转派）
怎么写model.conf 文件，代码库管理调 addPolicy() / addRoleForUser()，经 Adapter 落库
类比若依相当于你写的 @ss 判断逻辑相当于 sys_role_menu / sys_user_role 里的数据
所以"我是谁我能干嘛"不会写进 model

model 只放规则模板（空的判断逻辑），"u101 是 publisher、publisher 能 query"这些具体关系全部是 policy 数据，运行时由后台授权写入，model 不会膨胀。这与若依"代码里写逻辑、库里存授权"是同构的。

04

casbin_rule：一张 EAV 表装下所有关系

你的观察很准：Casbin 最直观的特点是把用户-角色、角色-权限等多张中间表合并成一张通用表。这是经典的 EAV（Entity-Attribute-Value，实体-属性-值）模型。注意是 EAV，不是 EVA。

casbin_rule（JDBC Adapter 自动建表）
CREATE TABLE casbin_rule (
  id    BIGINT PRIMARY KEY AUTO_INCREMENT,
  ptype VARCHAR(10),   -- 策略类型：p / g / g2 ...
  v0    VARCHAR(256),  -- 语义由 ptype 和 model 决定
  v1    VARCHAR(256),
  v2    VARCHAR(256),
  v3    VARCHAR(256),
  v4    VARCHAR(256),
  v5    VARCHAR(256),
  KEY idx_ptype (ptype)
);
ptypev0v1v2含义
ppublishermaterial:listquery角色 publisher 对 material:list 有 query 权限
padminmaterial:listexportadmin 可导出
gu101publisher—u101 属于 publisher 角色
gsenior_publisherpublisher—角色继承：高级投放者继承投放者
轻便的代价（面试要会说）
  • 无外键约束：v0/v1 是字符串，引用的角色/用户被删了，策略行不会自动删除（产生"孤儿策略"，第 10 章）；
  • 语义不直观：同一列 v1 在 p 行是"资源"、在 g 行是"角色"，DBA 直接查表看不懂；
  • 反向查询困难：查"某资源被授权给了谁"需要按 v1 扫，且不能用业务 JOIN；
  • 海量实例策略膨胀：把每条素材的分享都写进 casbin_rule，行数随业务暴涨；
  • 业务表不消失：Casbin 只合并了"关系中间表"，user/role/业务实体表仍然在业务库里。
05

角色继承：RoleManager 内存图可达性

5.1 什么是角色继承

角色继承（RBAC1）指角色可以有父子层级，子角色自动拥有父角色的全部权限。例如"高级投放者"继承"投放者"，再加"审批"权限。这样不必在每个角色上重复配置公共权限。若依的角色是扁平的，没有继承。

策略里表达继承
g, senior_publisher, publisher   // 高级投放者 继承 投放者（g 行连接两个角色）
g, u103, senior_publisher        // u103 是高级投放者
p, publisher, material:list, query
p, senior_publisher, material:list, approve

那么 u103 能 query 吗？能——它沿继承链 senior_publisher → publisher 间接拥有了 query。

5.2 RoleManager 内存图与可达性

Casbin 把所有 g 关系加载到内存，构建一个有向图（邻接表）。enforce 时，从用户节点出发，沿 g 边做 BFS/DFS，只要某个"可达角色"命中策略就放行。

图 3-2　g 关系构成内存有向图，鉴权 = 从用户节点求"可达角色"，等价于图上的可达性分析
用 SQL 类比：递归 CTE

角色继承图的可达性，在关系数据库里对应递归 CTE（WITH RECURSIVE 逐层查父角色）；Casbin 在内存里做同样的事但快得多。默认最大深度 10 防止循环继承（A 继承 B、B 又继承 A）导致死循环。

06

页面 / 行级 / 字段级在 Casbin 里怎么落地

你说"policy 好像不能做行级、字段级"——这是误会，都能做，只是两种做法。

6.1 页面 / 接口级（RBAC）

资源放权限码或路径：p, publisher, material:list, query，请求时 enforce("u101", "material:list", "query")。最简单。

6.2 行级：路线 A（实例策略，等价 resource_owner）

把具体资源实例写进策略，v0 放用户/组，v1 放具体资源：

行级实例策略（把 resource_owner 搬进 casbin_rule）
p, u101, material:M100, manage      // u101 管 M100
g, u101, g5                          // u101 属于 G5 组
p, g5, material:M100, view           // G5 组可看 M100
p, g5, game:G1, view                 // G5 组对游戏 G1 有权限

enforce("u101", "material:M100", "view")  // 沿 g 到 g5 命中 → true
  • 反向查询（"u101 能看哪些素材"）：用 getImplicitPermissionsForUser("u101") 拿到全部隐式权限（含继承和组），不需要自己写递归；
  • 代价：分享关系随业务增长，casbin_rule 膨胀，且要持续同步（第 9 章）。

6.3 行级：路线 B（ABAC matcher，不存实例）

在 matcher 里直接比较对象属性，请求把资源对象传进来，策略表里不存任何素材实例：

ABAC matcher（海量数据用这个）
// model.conf 的 matcher：
m = r.sub.id == r.obj.ownerId || r.obj.groupId in r.sub.groupIds

// Java 调用：sub 和 obj 是带属性的对象
User u = new User("u101", List.of("g5"));
Material m = new Material("M100", "u102", "g9");
enforcer.enforce(u, m, "view");   // 比较 ownerId/groupId，false

6.4 字段级：obj 填字段标识 + 批量取集合

把字段当作资源：p, admin, field:user:phone, read。不要在每个字段上 enforce 一次（那是 n 次调用），而是请求开始时一次取权限集合，给 Jackson 过滤：

字段级正确用法：一次取集合，复用 n 行
// 一次拿到当前用户全部（隐式）权限，含字段权限码
List<String> perms = enforcer.getImplicitPermissionsForUser("u101")
                       .stream().map(a -> a[1]).toList();
Set<String> permSet = new HashSet<>(perms);
// Jackson 序列化时每个字段 permSet.contains("field:user:phone")，O(1)
行级路线路线 A 实例策略（ACL）路线 B ABAC 属性匹配
策略表存什么每条"人↔素材"关系（即 resource_owner）不存实例，只存规则
适合不规则分享、转派、多人多组协作规整归属（本人/本组/部门），海量数据
同步成本高（数据随时变要同步）零（属性就在业务表里）
聚合查询反查 casbin_rule 或仍走业务表由业务库按属性条件查询
你总结的两种策略，结论

海量、规整的行级走 ABAC matcher（不写 EAV），聚合查询走业务表；不规则的逐资源分享才走 实例策略（写进 EAV，等价 resource_owner），并接受同步成本。两者也可混用。

07

持久化：Adapter（含多数据库问题）

Enforcer 默认把策略放内存；要持久化就配一个 Adapter（适配器）。它是可插拔的，官方/社区提供 File、JDBC、MongoDB、Redis、JPA、MyBatis 等实现。

JDBC Adapter（策略存 MySQL，自动建表）
// 一个 Enforcer 绑定一个 model 和一个 Adapter
JDBCAdapter adapter = new JDBCAdapter(
    "com.mysql.cj.jdbc.Driver",
    "jdbc:mysql://host:3306/authz?useSSL=false",
    "user", "pwd", true);   // true=自动建 casbin_rule

Enforcer e = new Enforcer("model.conf", adapter);
e.loadPolicy();   // 启动时把 casbin_rule 全量加载进内存
e.addPolicy("publisher", "material:list", "add"); // 同时写库

回答："能适配多个数据库吗？"

  • 跨数据库类型：JDBC Adapter 可接任何 JDBC 数据库（MySQL/PG/Oracle/达梦）；MongoDB 用 Mongo Adapter；Redis 用 Redis Adapter——换数据库就是换 Adapter。
  • 一个 Enforcer 同时连多个库？标准模型里一个 Enforcer 绑定一个 Adapter（一个库）。若策略分散在多库，推荐做法是把策略集中到一个独立的权限库，各业务服务共享；或为不同库建多个 Enforcer，但这会让决策分散、不推荐。
  • 为什么集中：权限是横切关注点，独立 authz 库便于审计、统一同步，也和第四册 OPA 的"策略集中"思路一致。
08

多实例同步：Redis Watcher（A/B 实例是什么）

8.1 先回答 A、B 实例是什么

就是同一个后端服务部署的多个副本（为了高并发/高可用，在多台机器或多个容器里跑的 N 个实例，如 k8s 里 3 个 Pod）。每个实例各自持有一个 Enforcer，策略在每个实例的内存里各有一份。

图 3-3　A 改策略 → 落库 + Redis 广播；B 收到通知后 reload 内存（push 模式）

8.2 回答："直接用 Redis 还需要 Watcher 吗？"

策略存放每次鉴权多实例一致性
内存（Enforcer 自带）内存判断，纳秒级，最快各副本内存独立 → 需要 Watcher：改后广播 reload，否则别的实例一直用旧策略
直接查 Redis每次一次网络 IO（毫秒级）不需要 Watcher：所有实例查的是同一个 Redis，天然一致
DB 直查每次查库，最慢天然一致但压力大

所以你的判断完全正确：用内存 + Watcher 换取"决策零网络开销"，代价是要处理多实例同步；直接查 Redis 就没有同步问题，但每次决策都有网络成本。WatcherEx 支持增量更新（只传变化的策略行，而非全量 reload）。

注意：Watcher 是 push，内存还有过期窗口

广播到 reload 完成有秒级延迟，期间个别实例可能用旧策略。对权限要求即时生效的场景（如立即踢人），可叠加短 TTL 或对关键操作直查库。

09

Adapter 怎么从业务表同步：四种模式

回答"Casbin 只当鉴权引擎、策略由 Adapter 从业务表同步，是已有机制还是异步任务"——基础的读写能力是现成的（loadPolicy/savePolicy 是接口），但"从你已有的业务表映射"需要自己实现或选一种同步模式：

① 自定义 Adapter 直读
实现 loadPolicy 直接查你现有业务表（sys_role_menu 等），转成 Casbin 策略。业务表是权威，只读，零同步。
② 双写/领域事件
授权操作时业务表与 casbin_rule 一起写（事务/发领域事件 addPolicy），实时一致，有双写复杂度。
③ 定时任务 / CDC
定时全量/增量对账；或用 Canal 监听 binlog，业务表变更自动转换成策略变更（异步，最终一致）。
④ ABAC 免同步
行级用属性 matcher，根本不存实例策略，业务数据变化无需同步（最省心）。
图 3-4　策略来源四模式：直读、双写、CDC、免同步——按数据量和实时性选择
实践建议

功能权限（角色-权限）用模式①或②；海量行级权限用模式④（ABAC）或让业务表做权威（模式①）；模式③用于"Casbin 不是唯一写入入口、可能有其他系统改库"的兜底同步。

10

孤儿策略：EAV 无外键怎么清理

因为 casbin_rule 没有外键，当一个用户/角色/素材被业务删除，对应的 p/g 策略行不会自动消失，成为孤儿策略（占空间、可能被误判）。两道防线：

  1. 联动清理（首选）：业务删除用户/角色/资源时，在同一事务里调用 removePolicy()/removeFilteredPolicy() 删掉相关策略；
  2. 定时对账兜底（你说的定时任务，正确）：跑一个离线任务，定期扫 casbin_rule，检查主体/资源是否还存在于业务表，不存在就删除。运维手工删只能兜底零星问题，不能作为常规手段。
反向查询为什么不靠 ABAC

ABAC matcher 只能判"给定的资源能不能访问"（正问），它不能回答"这个用户能访问哪些资源"（反问）——因为资源没存进策略。反向查询要么用实例策略 + getImplicitPermissionsForUser，要么直接在业务库按归属字段/resource_owner 做查询。这也是为什么聚合查询通常仍走业务表。

11

代码织入：注解 + AOP，而不是到处写 enforce

回答"Casbin 鉴权是不是靠装饰器装饰在每个接口上、Jackson 字段时怎么办"——对，织入点只写一次，三个层级位置不同：

接口级
自定义 @RequirePerm 注解 + 一个 AOP 切面，切面里调 enforce；写一次注解，所有接口复用
行级
在查询层处理：ABAC 拼条件 / 资源实例反查；不在每个接口重复写
字段级
@FieldPerm + 全局 Jackson BeanSerializerModifier，注册一次，序列化自动裁字段
图 3-5　接口在 AOP 切面、行级在查询层、字段级在序列化层——各注册一次，不是每处手写 enforce
接口级注解 + AOP（只写一个切面）
@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface RequirePerm { String value(); }

@Aspect @Component
public class PermAspect {
    @Autowired Enforcer enforcer;
    @Before("@annotation(rp)")
    public void check(JoinPoint jp, RequirePerm rp) {
        String user = SecurityUtils.userId();
        if (!enforcer.enforce(user, rp.value(), "access"))
            throw new AccessDeniedException("403");
    }
}
// 接口上：@RequirePerm("material:list:add")  —— 与若依 @PreAuthorize 几乎一样

字段级的 Jackson 修饰器代码与第二册完全一致，只是把 perms.contains() 换成 Casbin 一次取好的权限集合即可。批量判断可用 batchEnforce(List<请求>) 一次处理多个对象。

12

本册小结与自测

12.1 必须带走的 8 句话

  1. Casbin 是进程内库（不是服务），把 RBAC 表和判断逻辑抽成可配置组件；核心调用 enforce。
  2. PERM：model.conf（r/p/g/e/m 规则模板）与 policy（授权数据）分离；matcher 类似 WHERE，enforce 等价 EXISTS。
  3. model 开发写一次；policy 由后台授权/业务动作运行时写入（addPolicy）。
  4. casbin_rule 是 EAV 表（ptype+v0~v5），合并多表但代价是无外键、反查难、可能膨胀。
  5. 角色继承用 g 构成内存有向图，BFS 求可达角色，默认深度 10 防环；等价 SQL 递归 CTE。
  6. 行级两条路：实例策略（ACL，适合分享，会膨胀）/ ABAC matcher（不存实例，适合海量）；字段级 obj 填字段码。
  7. 持久化靠可插拔 Adapter（一 Enforcer 绑一库）；多实例内存同步靠 Watcher（Redis 广播 push）；直查 Redis 则免 Watcher。
  8. 织入点：接口注解+AOP、行级在查询层、字段级 Jackson；策略来源四模式、孤儿靠联动+定时对账。
