Redis 缓存与性能专题（你的问题 3/5）

你提到"用 Redis 缓存登录用户权限/组信息"、"合并让我想到 Redis Set"——方向完全正确，这正是生产标准做法。

3.1 用 Redis Set 存权限，天然契合

权限/组用 Redis Set 存储
# 登录时把用户的角色、权限码、组分别写入 Set
SADD perm:u101 material:list:query material:list:add field:user:phone
SADD group:u101 g5 g9

# 鉴权：SISMEMBER 是 O(1)，等价于 Set.contains
SISMEMBER perm:u101 material:list:add      # 1=有权限

# 多角色权限合并（多对多的并集）：SUNION 由 Redis 算好
SINTER/SUNION perm:role:publisher perm:role:admin
回答"合并多个字段权限是不是想到 Redis Set"

对。一个用户有多个角色、每个角色有多条权限，聚合是"多个集合的并集"，Redis 的 Set + SUNION/SINTER 正是为集合的并交差设计的，SISMEMBER 判断是 O(1)。可以在登录时一次性聚合到一个用户权限 Set，之后所有判断都查它。

3.2 缓存什么、不缓存什么

数据是否缓存原因
用户的角色/权限码/组缓存 Redis（或本地内存）读多写少、变更低频，命中率极高
行级数据归属（百万素材）一般不缓存，走业务库/索引海量、实时变化、命中率低，缓存反而不一致
字段权限集合随权限码一起缓存低频，和功能权限同生命周期

3.3 授权变更后的缓存一致性

  • 管理员改了某角色权限：删除该角色下所有用户的权限 key（或用统一版本号 key 使其失效），下次请求回源重建；
  • 三种传播范式：失效拉取（删 key 让其重查）/ 主动推送（Watcher 广播）/ 周期轮询（TTL/轮询）；
  • 关键止血操作可短暂绕过缓存直查库，保证权限即时收紧。

完整专业术语表（面试能听懂、说得对）

一、通用权限模型

术语含义
ACL访问控制列表（Access Control List）：直接记录"主体对某资源有什么权限"，resource_owner 就是一张通用 ACL 表。
RBAC0~3基于角色：0 基础（用户-角色-权限）；1 角色继承；2 约束/互斥；3=1+2。
ABAC基于属性：用主体/资源/环境属性写规则（如 owner_id==user.id）。data_scope 是其简化版。
ReBAC基于关系：用主体-资源关系图判断（Google Zanzibar/OpenFGA）。
resource_owner通用资源归属表：resource_type/resource_id/owner_type/owner_id/perm，支持多对多、多层范围。
功能/行级/字段级权限三层：能否访问页面按钮 / 看到哪些行 / 看到哪些列。

二、若依（RuoYi）

术语含义
sys_menu菜单与权限点合一的表；前端读路由字段，后端读 perms。
M/C/F菜单类型：M=目录（无页面）、C=菜单页、F=按钮（Function）；扩展 I=字段。
perms权限码字段，三段式如 material:list:add，超管 *:*:*。
@PreAuthorize("@ss.hasPermi(...)")Spring Security 注解，调用名为 ss 的 PermissionService 做权限 Set.contains。
data_scopesys_role 字段，数据范围五档：1全部/2自定义/3本部门/4本部门及以下/5仅本人。
@DataScopeAOP 注解，切面按 data_scope 拼 WHERE 片段，注入 BaseEntity.params.dataScope。
sys_role_dept仅 data_scope=2 自定义时使用，挂角色能看的部门。
del_flag逻辑删除标记（软删），保留审计。
ruoyi-generator代码生成器，表驱动：建表→生成 CRUD + menu.sql。
@Sensitive数据脱敏（如 138****1234），不是字段级鉴权。

三、Casbin

术语含义
PERM元模型：Policy(策略)/Effect(合并)/Request(请求)/Matchers(匹配)。
model.conf模型/规则模板：定义 r、p、g、e、m，开发写一次。
policy策略数据，一条条授权事实（演示 policy.csv，生产落库）。
r / p / g / e / m请求 / 策略 / 角色分组 / 决策合并 / 匹配器（类似 WHERE）。
Enforcer执行器，核心方法 enforce()、batchEnforce()、addPolicy()。
casbin_ruleJDBC Adapter 自动建的 EAV 表：ptype + v0~v5 合并所有关系。
EAVEntity-Attribute-Value 实体-属性-值通用表（注意不是 EVA）。
Adapter持久化适配器（File/JDBC/Mongo/Redis…），一个 Enforcer 绑一个。
Watcher多实例同步器，策略变更经 Redis Pub/Sub 广播，其他实例 reload。
RoleManager角色关系内存有向图，鉴权时 BFS 求可达角色，默认深度 10 防环。
getImplicitPermissionsForUser取用户含继承/组的全部隐式权限（用于反向查询）。

四、OPA

术语含义
OPAOpen Policy Agent，CNCF 毕业的独立策略引擎，Go 编写，默认 8181。
RegoOPA 的声明式策略语言（Datalog 谱系），import rego.v1 为新语法。
input每次请求传入的 JSON（用户、动作、资源）。
dataOPA 内存中的全局事实（策略 + 配置数据）。
Bundle策略发布物：.rego+.json 打成的 .tar.gz（可签名），托管于 HTTP/S3/Git。
PEP/PDP/PIP/PAP执行点 / 决策点(OPA) / 信息点(业务库) / 管理点(Git+CI)。
http.sendRego 在决策中主动发 HTTP 回调业务服务取实时数据。
Partial Evaluation部分求值：把数据集合标 unknown，输出残余查询条件并可翻译成 SQL。
visible_fields / filtersOPA 一次返回的字段集合 / 行级过滤条件。
ext_authzEnvoy 外部鉴权接口，把网格请求鉴权外接到 OPA。
Sidecar边车部署：每个业务 Pod 旁挂一个 OPA。

选型决策树

开始：要做权限系统
└─ 是 K8s / Service Mesh / 多语言微服务、要统一策略与合规审计？
是 → 【OPA】（Sidecar/Envoy ext_authz，Rego 写策略，Bundle 发布）
└─ 否，是普通应用服务但想引入成熟库、少造轮子？
是 → 【Casbin】（引入 SDK，需要行级就用 ABAC matcher 或实例策略）
└─ 否，是单体 Java 后台、团队熟悉 SQL、只要常规 CRUD 权限？
是 → 【若依式自研】（sys_menu + 权限码 + data_scope，必要时加 resource_owner）
行级数据无论选哪套：规整归属（本人/本部门/本组）→ 规则型（data_scope / matcher / 部分求值）；不规则逐资源分享 → resource_owner/实例策略；海量数据 → 条件下推到数据库，绝不逐行鉴权。

06

面试口述稿（可直接背诵）

30 秒电梯版（Q4 原题）

"我们做的是页面级 RBAC：用户—角色—权限三层，权限不单独建表，而是以页面/模块的权限码字典形式维护。用户登录后聚合权限放进 Redis Set，访问时在接口上用注解判断权限码是否命中，控制页面显示和按钮操作。权限用 MongoDB 承载是因为这类授权数据写多读少。"

3 分钟完整版（含数据权限）

"我把权限分成三层。第一层功能权限是页面、按钮、接口，用 RBAC，权限码三段式，注解 + AOP 校验，登录后权限集合缓存在 Redis。第二层行级数据权限分两种：规则型，像若依的 data_scope，按本人、本部门、部门及以下、自定义、全部在查询时拼 WHERE；关系型，针对'把某个素材分享给某个组'这种不规则授权，用一张通用 resource_owner 表，记录 resource_type、resource_id、owner_type（user/group/dept）、owner_id 和权限，多个组授权就是多条记录，查询时 IN 求并集并去重。第三层字段级，在 JSON 序列化时根据字段权限码决定是否输出该列，比如手机号只对高管可见。

如果不想自己造轮子，功能层可以用 Casbin——它是个进程内库，用 model.conf 定义规则、policy 存授权，多实例用 Redis Watcher 同步；更复杂的多语言微服务和 Service Mesh 场景用 OPA，它是独立策略服务，用 Rego 写策略、Bundle 热发布，海量行级数据靠部分求值把规则翻译成 SQL 条件下推到数据库。"

07

高频追问弹药（你当时卡住的点）

用户必须授权到个人吗？能分组吗？

能分组。角色（role）管功能权限，用户组（group）或部门（dept）管横向数据归属；用户和组/角色都是多对多，用中间表。一个用户可属多个组，授权可以落在组上，组内成员继承。

两个组都对同一个游戏有权限怎么办？

在 resource_owner 里为每个组各写一条授权记录；查询时用 owner_id IN (用户所在的所有组) 做并集，DISTINCT 去重即可，天然支持任意多个组。

多对多关系怎么用表维护？

经典做法是三张实体表 + 一张中间表（中间表存双方主键，联合主键）。Casbin 把这些中间关系合并进一张 EAV 表（casbin_rule）；OPA 则把关系表达成 Rego 里的 data 映射，海量数据仍放业务库。

权限缓存怎么保证改了权限能生效？

授权变更时删除对应用户/角色的 Redis 权限 key，下次请求回源重建（失效拉取）；多实例可用 pub/sub 广播（Casbin Watcher 的 push）或轮询（OPA Bundle 的 pull）。关键操作可临时直查库。

行级权限数据量大，怎么避免逐行校验？

不逐行。规则型把条件下推成 SQL WHERE（若依 @DataScope、OPA 部分求值）；关系型用 resource_owner JOIN/IN 一次查询；Casbin ABAC 用属性比对、实例策略用 getImplicitPermissionsForUser 反查。字段级也是一次取权限集合，序列化时 O(1) 判断。

Casbin 和 OPA 分别是什么？一句话区别？

Casbin 是进程内的权限库（函数调用 enforce，三元组出 bool）；OPA 是独立的策略服务（HTTP 调用，任意 JSON 输入输出，Rego 写策略，Bundle 热发布）。前者轻、单体友好；后者强、适合多语言微服务和 Service Mesh。
