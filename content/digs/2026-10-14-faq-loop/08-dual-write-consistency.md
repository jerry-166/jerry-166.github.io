### ⑰ Milvus“可重建”——怎么重建？手动？

```
for faq in db.fetchall("SELECT id, kb_id, question FROM faq"):
```

## 1. 当前系统的真实行为：三条写路径的失败处理

先把你问的“PG 首先要确保落库”落实——**当前系统的顺序和语义是对的**：

```
① add_faq（PG INSERT）
   ├─ 失败 → return None → 接口报"FAQ 写入失败"→ 整体失败，无任何半成品 ✓
   └─ 成功 ↓
② insert_faq_vector（Milvus，先删后插）
   ├─ 失败 → 内部 logger.error + return False
   │         ⚠ 但调用方没接返回值 → 接口照样返回成功
   └─ 成功 ↓
③ audit + bump 缓存 + 返回 created
```

三个设计决策的定性：

- **“PG 先行，派生物跟随，派生物失败不回滚 PG”**——正确。为什么不回滚：FAQ 记录本身是有效资产（用户补全的知识），向量只是“可召回性”的加速器。为加速器失败丢弃资产不对；而且**回滚本身也会失败**（补偿事务的补偿没有终点），复杂度失控。正确语义是：接受“暂时不可召回”，用修复机制最终补上——**可用性换一致性，最终一致**。
- **PG 写失败 = 整体失败**——这是“权威源先行”的直接收益：权威源失败时系统里没有任何残留状态。反过来（Milvus 先写、PG 后写）会制造“用户看到失败但孤儿向量已存在”的更糟局面。
- **但失败被静默了**——`insert_faq_vector` 的 `False` 无人消费，**这是当前实现的真实缺陷**（不是设计选择，是漏检查）。修复它只需要：`if not client.insert_faq_vector(...)` → 入修复队列（下面讲）。

## 2. 不一致三型 + “怎么知道失败了”

双写失败的不一致按形态分三型，**检测难度完全不同**——这是回答你“怎么知道”的钥匙：

| 类型 | 产生路径 | 危害 | 检测方式 |
|---|---|---|---|
| **缺失**（PG 有，Milvus 无） | 创建/merge 时向量写失败（如上，静默） | candidate 攒不了热度；**active 缺失 = 直返功能失效** | **只能主动对账**——看不见的东西不会自己报警，召回时它根本不出现，无任何被动信号 |
| **残留**（PG 无，Milvus 有） | 删除时 `delete_faq_vector` 失败（warning，“PG 已删”） | 轻：浪费召回名额（命中→`get_faq` 查不到→放行） | **可被动发现**——孤儿命中时能“看见”它，顺手记录/清理 |
| **过期**（两边都有但内容不一致） | 当前**不存在活路径**（见第 4 节）；未来编辑接口若漏重写向量则成真 | **最隐蔽**：不报错、看似在工作，但“用户按旧问题召回，拿到新问题的答案”——语义错位 | 水位比对：PG `updated_at` vs Milvus `created_at` |

关键洞察：**缺失型无法被动检测**。残留型好歹会在召回时露脸（命中了但查无此人），缺失型是“该出现的东西没出现”——没有任何请求会为一条不存在的向量报警。所以：

> **被动自愈只能抓残留；缺失必须靠主动对账。** 没有定时对账的系统，缺失型不一致会静默累积。

## 3. 修复机制设计（“怎么重建”的完整方案）

你说“定时任务或者线程去做吧”——对，而且正确答案是**三层机制各管一段**，不是单选：

```
第一层：失败即时转作业（同步，感知已知失败）
  insert_faq_vector 返回 False（或 delete 失败）→ 不再只写日志
  → INSERT INTO repair_queue(resource_type, pg_faq_id, op, retry_count, failed_at)
  → 返回用户依然成功（PG 资产在，只是"稍后可召回"）

第二层：修复 worker 消费队列（异步，修已知失败）
  两种宿主形态，你说的两种都成立：
  ├─ 常驻线程/后台任务：监听队列，指数退避重试（30s→2min→10min...）
  └─ 定时任务（APScheduler）：每 N 分钟扫 retry_count 未超限的作业
  → 修复动作全部幂等：缺失=重算 embedding+先删后插；残留=delete_faq_vector
     （删不存在的 id 也返回成功 → 重试安全）
  → retry_count 超限 → 标记 dead + 告警人工介入（死信）

第三层：定期全量对账（定时，发现未知失败）★ 关键兜底
  PG 侧：SELECT id, updated_at FROM faq（按 updated_at 水位增量拉）
  Milvus 侧：按 kb_id query 拉全量 pg_faq_id + created_at
  差集计算：
    PG 有 Milvus 无          → 缺失 → 生成修复作业
    PG 无 Milvus 有          → 残留 → 生成清理作业
    PG.updated_at > Milvus.created_at → 疑似过期 → 生成重写作业
  → 对账本身写 audit（对账任务也要被观测——上轮"假对账"的教训）
```

**为什么必须三层**：第一层抓“当场知道”的失败（写失败返回了 False）；第三层抓“当场不知道”的失败（进程在写日志前崩溃、网络分区后不知情、历史存量脏数据）。**只有第一层没有第三层 = 只修看得见的病，不体检**。第二层是执行器，两种宿主（线程 vs 定时）取舍：

| | 常驻线程（队列消费者） | 定时任务（间隔扫描） |
|---|---|---|
| 修复延迟 | 秒级（即时重试） | 分钟级（=扫描间隔） |
| 空转浪费 | 无（队列空就睡） | 有（大多数时刻无作业） |
| 基建 | 要队列 + worker 生命周期管理 | APScheduler 一个 cron |
| 适用 | 失败频繁、延迟敏感 | 失败稀少（我们的场景） |

实践正解是混合：**作业队列管“快路径修已知”，定时对账管“慢路径找未知”**——和缓存那轮的“版本失效是快路径、TTL 是慢路径兜底”完全同构（双保险思想的第二次出现）。

## 4. 你的“幂等导致不更新”担忧：先纠偏，再确认它什么时候成真

**你把两层幂等的语义套错了**，拆开看：

```
集合级幂等（create_collections，启动时）：
  "集合已存在 → 直接获取，不重建"          ← 存在即跳过 ✓ 你说的是这个
  对 schema 正确（表结构不需要变），跳过没问题

文档级幂等（insert_faq_vector，运行时）：
  delete_faq_vector(pg_faq_id) → insert(新值)   ← 先删后插，覆盖式！
  不存在"发现 ID 一样就不更新"的代码路径
  每次调用都写入最新值 → 重复执行收敛到同一结果（这才是幂等的正确实现）
```

这两种幂等有正式名字：**覆盖式幂等（PUT 语义）vs 跳过式幂等（PUT-if-absent）**。跳过式的致命伤正是你指出的：源数据变了，派生物永远停在第一次的值——**幂等保证“重复执行结果一致”，不保证“结果与源一致”**。幂等 ≠ 新鲜。当前代码的文档级写入是覆盖式，所以你担心的“同 ID 不更新”在机制上不成立。

**但你的担忧在两个地方真实成立**（这才是有价值的部分）：

1. **当前系统靠“功能边界”而非“机制”规避了过期**：Milvus 只存 question 向量，而 question 创建后不可编辑（无接口）；answer/status/热度这些会变的字段全在 PG（`try_faq_hit` 命中后回 PG 查最新）。**schema 把“易变字段”和“派生向量”分离，蒸馏升格改 answer 天然不碰 Milvus**——这是设计上的聪明，但它有个前提：所有能改 question 的路径都必须显式重写向量，**漏一条路径，过期就成真**。
2. **未来加编辑接口（缺口 C1）的那天**：如果 `edit_faq` 里只 UPDATE PG 忘了调 `insert_faq_vector`，场景成真——用户按旧问题召回，命中后返回新问题的答案，**不报错、看似工作，纯语义错位**，比对缺失难发现一个数量级。

**结构性防法**（不是靠“记得写”的纪律）：

- **把双写封进同一个服务方法**：`edit_faq()` 内部同时做 UPDATE PG + 重写向量，外部永远不暴露裸 UPDATE——调用者想漏都漏不掉。这就是你第一条总复习图元层总纲的那句话：**正确性靠结构不靠纪律**。
- **对账水位兜底**：第三层对账里的 `PG.updated_at > Milvus.created_at` 比对，能把漏路径的过期条目筛出来——Milvus 集合 schema 里 `created_at` 字段此刻就有了用武之地（为对账而生的字段，当时可能都没意识到）。

## 5. 业界对照：这个问题有一整条解法谱系

```
强 → 弱
① 分布式事务（2PC/XA）     两存储原子提交。重、吞吐差、协调者单点——微服务时代基本弃用
② Outbox 模式 ★业界标准     业务变更 + 事件记录写在【同一个 PG 事务】里落库
                            → 独立进程轮询/CDC 事件表 → 驱动 Milvus 更新
                            → 事件与业务同事务=必不漏发；消费者幂等=可重试
③ CDC（Debezium/Canal）     订阅 PG binlog → Kafka → 消费者更新派生物
                            不侵入业务代码，最彻底，基建最重
④ 定期对账                  兜底，最终一致（金融日终对账、ES reindex 校验同思想）
⑤ 我们现状                  权威源先行 + 派生物失败降级不回滚 + 手动重建
                            = 最简版，缺②的事件表和④的定时器
```

值得你注意的一点：**项目的 `audit_log` 差一步就是 Outbox**。Outbox 的核心是“事件与业务变更同事务落库，事后必有消费者处理”——`audit.log` 记录了每次 `faq.candidate_create / delete`（带 resource_id），结构上就是事件表；它和业务写入之间差一个“同事务包裹”（现在 audit 是独立调用，业务成功 audit 失败不回滚——审计作为旁路的有意设计），以及差一个“消费事件去修数据”的 worker（现在 audit 只被人看，不被机器消费）。**演进到 Outbox 的最短路径：让 repair worker 消费 audit 里的 faq 写事件**——审计表从“只写不读的账本”变成“修复系统的触发器”，审计的第三个机器消费方（前两个：人工审计视图、未来的反刷规则引擎）。整个项目的模块咬合又多一环。

## 记忆锚（5 句）

1. **“缺失不会报警，残留会露脸”**——被动自愈只能抓残留，缺失必须主动对账；没有定时对账的系统，缺失型不一致静默累积。
2. **“权威源先行，派生物失败不回滚”**——资产和加速器分开对待；回滚补偿自身也会失败，最终一致才是正解。
3. **“快路径修已知，慢路径找未知”**——失败转作业（即时）+ 定时对账（兜底）双保险，和缓存“版本+TTL”同构。
4. **“幂等 ≠ 新鲜”**——覆盖式幂等（先删后插）保新鲜，跳过式幂等（存在即跳过）必过期；当前靠 schema 分离易变字段规避，编辑接口落地日就是机制必须补齐时。
5. **“audit 差一步就是 Outbox”**——事件表已有、消费者缺失；补一个 repair worker，审计从账本变触发器。
