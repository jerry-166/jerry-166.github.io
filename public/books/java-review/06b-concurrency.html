开场：一个作坊的烦恼

先别管任何术语。想象你开了个小作坊，雇了一个工人，给他一块白板（就是内存）：所有任务、数字、状态都写在白板上，他干完活把结果写回白板。一切都好——因为只有一个视角，他看到的就是全部真相。

后来生意好了，你雇了第二个、第三个工人（多线程）。他们还是共用同一块白板。麻烦从这一刻开始，而且所有的麻烦都可以归结为下面这三句话：

麻烦一 · 可见性工人干活前习惯把白板上的数抄到自己的便利贴上算。你改了白板，他还在看自己那张旧便利贴。
麻烦二 · 原子性"把白板上的 5 改成 6"其实是三步动作：看一眼 → 心算 → 写回去。三步中间被别人插一脚，就乱了。
麻烦三 · 有序性每个工人会自作聪明调整干活顺序。一个人的时候结果没差，多人的时候就互相穿帮。

Java 的整个并发工具箱，就是围绕这三个麻烦打造的。更妙的是，工具之间有一条清晰的演进链——每个新工具都是上一个工具"没解决的问题"逼出来的：

📌 和 Python 的关系（你的背景）

CPython 有 GIL——相当于作坊规定"任何时刻只许一个工人动白板"，三个麻烦被这个规定大幅压制（但没消灭：x += 1 照样丢更新，因为它也是三步）。Java 没有这个规定，三个麻烦全部裸露，全部要你自己处理。这也是为什么 Java 并发是面试重灾区而 Python 不是——不是 Java 程序员更厉害，是 Java 把问题交给了你。

01

第一幕 可见性：改了，他看不见 高频

① 为什么出现多核 CPU 各自带缓存 + 编译器优化，允许"改了不立刻生效"。
② 什么场景一个线程改开关变量，另一个线程的循环永远感知不到。
③ 怎么发生三层解剖：没写回 → 没重读 → JIT 直接把读优化没了。
④ 解决了什么volatile：立刻可见。✗ 但 i++ 依然丢 → 第二幕。

1.1 惨案现场

StopFail.java一段可能永远不结束的程序
public class StopFail {
    // 一个开关。主线程负责关，worker 线程负责看
    static boolean running = true;          // 注意：没有 volatile

    public static void main(String[] args) throws Exception {
        Thread worker = new Thread(() -> {
            while (running) { }             // 只要开关还开着就空转
            System.out.println("worker 停下了");
        });
        worker.start();

        Thread.sleep(1000);                 // 确保 worker 已经跑起来
        running = false;                    // ★ 主线程关掉开关
        System.out.println("主线程已把 running 改成 false");
        worker.join(3000);                  // 最多等 3 秒
        System.out.println("worker 状态: " + worker.getState()); // 很可能还是 RUNNABLE
    }
}

按直觉：主线程把 running 改成 false，worker 下一圈检查就该退出。实际运行大概率是：worker 永远转下去。主线程明明改了，worker 就是"看不见"。

1.2 解剖：到底哪里断了？

直觉的假设是"改了 = 所有人都看得到新值"。这个假设在两层上都不成立。我们一层层往下挖：

第一层：主线程改了，但可能还没写到"公共区域"

真实的硬件世界里，CPU 每个核都有自己的一块高速缓存（比内存快几十倍）。改一个变量，硬件的默认策略是：先改自己核的缓存，什么时候写回内存，看心情（等这行缓存要被挤掉时才回写）。这个设计是为了快——每次写都直连内存，CPU 得闲死。

第二层：worker 每次都在读，但读的是自己核的缓存

同理，worker 线程跑在另一个核上，它读 running 时，默认也是从自己核的缓存里拿——而它这边的缓存里 running 一直是 true（第一次读进来的），没人通知它"这行数据已经变了"。

🗺 类比：白板与便利贴

主内存 = 教室的大白板（所有人共用）；CPU 缓存 = 每人手里的便利贴（自己看得快）。规则默认是：要改数，先抄到便利贴上改；改完不马上抄回白板；要看数，先看便利贴上有没有，有就不去白板。于是：主线程在自己便利贴上把 flag 改成 false，worker 看的是自己那张写着 true 的旧便利贴——两个人都没错，错的是"没有同步机制"。

第三层（更隐蔽）：JIT 会把读直接优化掉

还有更狠的。worker 循环里每一次都在读 running，但 JIT（即时编译器）盯了一会儿发现：循环体内没有任何代码修改 running，于是它"好心"做了个优化——把循环变成等价的 if (running) while (true) { }：只读一次，之后根本不再读。这不是 bug，是 JVM 允许的合法优化——在它的世界观里，没有同步动作就代表"没人会改它"。

⚠ 为什么"我本地跑能停下来"不能证明没问题

解释执行（JIT 还没介入）时每次循环真的去读内存，程序可能"碰巧"停了；JIT 编译后就是真死循环。并发 bug 的可恶之处：它看运行时机和优化程度的心情。"跑了几次没复现"在并发问题面前毫无证明力。

1.3 武器登场：volatile

现在需求很明确：我需要一个开关，告诉 JVM——"这个变量，写的人要立刻刷到主存，读的人必须每次去主存拿最新值，编译器不许把它优化掉"。这个开关就是 volatile 关键字：

StopFixed.java加一个词，世界恢复正常
public class StopFixed {
    static volatile boolean running = true;   // ★ 就加这一个词

    public static void main(String[] args) throws Exception {
        Thread worker = new Thread(() -> {
            while (running) { }                // 现在：每次循环都会从主存重新读
            System.out.println("worker 停下了"); // 1 秒后必然打印
        });
        worker.start();
        Thread.sleep(1000);
        running = false;                      // 写：立刻刷回主存
        worker.join();
    }
}

volatile 做的事用一句话说：把这个变量的读写从"便利贴模式"切换到"白板模式"。具体拆开是三件事：

  1. 写操作：不等缓存被挤掉，立刻刷回主内存；
  2. 连带通知：硬件层面广播"这行数据我改了"，让其他核把相关的旧缓存作废（下文"凭什么"细讲）；
  3. 读操作：每次都强制从主内存重新读，且 JIT 被禁止做"只读一次"的优化。
🔍 凭什么"作废别人缓存"就能保证一致？——MESI 一句话

多核 CPU 之间有个硬件协议叫 MESI 缓存一致性协议：每个缓存行有四个状态（改过/独占/共享/无效），核心规则是——一个核要改某数据前，必须先在总线上广播"我要独占它"，其他核听到就把自己的这行缓存标记为无效。所以"作废"不是 Java 做的，是 CPU 之间的硬件级通信。volatile 只是每次读写都主动触发这套机制，普通变量则任由硬件"看心情"同步。到这里就够了，再往下（总线嗅探、缓存行伪共享）面试也不问，问了你也答得上来这句。

1.4 内存屏障：volatile 凭什么还能"禁止重排"？（补完最后一块拼图）

很多资料说"volatile 保证可见性和有序性，因为它插入了内存屏障"——然后就没有然后了，屏障本身是什么从来没人讲。把屏障想象成插在指令流中间的一条警戒线：

没有屏障时，CPU/编译器为了快，可以把指令搬家（重排）：

   你写的代码              CPU 实际可能执行的顺序
   ──────────              ──────────────────────
   A: 普通写 x = 1    ─┐
   B: volatile写 flag=true │ 可以被换成：先执行 B 再执行 A（A 被搬到 B 后面）
                        │
有了屏障（警戒线）：
   A: 普通写 x = 1
   ┄┄┄┄┄ StoreStore 屏障 ┄┄┄┄┄   ◄─ 警戒线：线前的写不许搬到线后
   B: volatile写 flag=true
   ┄┄┄┄┄ StoreLoad 屏障 ┄┄┄┄┄   ◄─ 最强的线：谁都别想过（成本也最高）

它不是什么抽象概念，就是CPU 真实提供的一类指令（fence 指令），编译器在 volatile 读写的前后插入它们。四种屏障各管一个方向：

屏障插在哪管什么（不许谁越过警戒线）
StoreStorevolatile 写之前前面的普通写不许搬到 volatile 写之后
StoreLoadvolatile 写之后volatile 写之后的读不许搬到写之前（最贵、最强）
LoadLoadvolatile 读之后volatile 读之后的读不许搬到读之前
LoadStorevolatile 读之后volatile 读之后的写不许搬到读之前

为什么要管这么细？回头看 1.1 的惨案延伸：光"flag 可见"还不够——如果 x=1 这个普通写被搬到了 flag=true 后面，别人看到 flag 变了、回头读 x 却读到 0，等于白干。屏障保证"写完所有准备数据，最后才举旗"，举旗（volatile 写）本身成了一个公告点：公告之前的所有写入，看到公告的人都能看到。

一句话回答

volatile 是什么？——把一个变量的读写从"各自缓存看心情同步"切换为"每次写立刻上白板并作废别人的便利贴、每次读强制看白板"，并在读写点插入警戒线（屏障）不许指令乱搬。

⚠ 边界：volatile 解决了什么，没解决什么
✅ 解决
  • 可见性：写立刻所有人可见
  • 有序性：屏障禁止关键位置重排
  • 状态开关、一写多读的标志位
✗ 没解决
  • i++ 这种多步操作依然丢更新——三步还是三步，volatile 只保证每步读到的是新值，不保证三步不被打断
  • → 这就是下一幕的惨案
volatile 修饰的 i++ 为什么还是丢？用便利贴说一遍

i++ = 拿到便利贴（读，现在保证是最新的 5）→ 心算 6（在你手里）→ 写回白板 6。两个线程先后拿到同一张写着 5 的便利贴（都合法——第二个拿的时候第一个还没写回），都算出 6，都写回 6。两次加法，结果只加了 1 次。volatile 解决的是"看到的是不是最新的"，不解决"看到之后到写回之前，别人改没改"——这中间的空档就是原子性问题。

Python 里有这个惨案吗？Python 对比

Python 程序员几乎撞不上：GIL 保证同一时刻只有一个线程在执行字节码，而且 CPython 的变量读写本身是单条原子字节码，flag 语义下不存在"改了看不见"（全局锁 = 全局同步点）。所以 Python 里根本没有 volatile 这个概念。你的肌肉记忆里"改了就是改了"，到 Java 里要重新长一根神经。

02

第二幕 原子性：改到一半被抢白板 高频

① 为什么出现"改一个数"在人眼里是一步，在机器眼里是多步，多步就能被打断。
② 什么场景计数、先查再改（if 后 set）、一次改两个变量——全是复合操作。
③ 怎么发生i++ 拆成取数-算-放回三步，两线程交错推演一遍全懂。
④ 解决了什么synchronized 会议室：三性全包。✗ 但开会（挂起）贵 → 第四幕。

2.1 惨案现场

CounterFail.java两个线程各加 10 万，结果少了
public class CounterFail {
    static int count = 0;

    public static void main(String[] args) throws Exception {
        Runnable task = () -> {
            for (int i = 0; i < 100000; i++) {
                count++;                 // 看起来一步，其实是三步
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println(count);       // 期望 200000，实际每次都不同，且 < 200000
    }
}

2.2 解剖：把 i++ 拆开看

count++ 这一行代码，编译成字节码是三条指令（对应模块 1 讲过的操作数栈操作）：① 取数（getstatic，把 count 的值搬到自己的栈上）→ ② 算（加 1）→ ③ 放回（putstatic，把结果写回去）。把两个线程的执行交错排一下，惨案就现形了：

时刻   线程 A                     线程 B                  白板上的 count
────────────────────────────────────────────────────────────────────
 t1   ①取数：读到 5                                        5
 t2                              ①取数：读到 5             5   ← B 读的还是 5！
 t3   ②算：5+1=6                                          5
 t4                              ②算：5+1=6                5
 t5   ③放回：写 6                                          6
 t6                              ③放回：写 6                6   ← 覆盖！
────────────────────────────────────────────────────────────────────
结果：两次自增，白板只涨了 1。t2 那一步"读到 5"就是致命空档。

注意：这里没有任何一行代码"写错"，也不需要什么罕见优化——两个线程正常、合法地交错执行，结果就是错的。这比第一幕的惨案更普遍：连 JIT 优化都不需要参与。

🗺 类比：白板上改数字

“把白板上的 5 改成 6”在你眼里是一个动作，实际是三个：扭头看一眼（取数）→ 心里算（加 1）→ 转身写（放回）。两个工人同时做这个动作：都扭头看到了 5，都心算出 6，都转身写下 6——白板上明明该是 7。麻烦不在"写"这个动作本身，在看到和写回之间存在时间差。

2.3 这类问题远不止 i++

凡是"一步的逻辑，多步的实现"都中招，面试和实战最常见的三种：

类型样子哪里被插队
读-改-写count++ / x += 1读和写之间，别人的写被你覆盖
先查后做（check-then-act）if (map.get(k) == null) map.put(k, v);检查完到放入前，别人已放入 → 两次初始化
多变量联动low = 0; high = size - 1;（两个变量必须同时变）改了 low 还没改 high，别人读到"一半新一半旧"的组合

2.4 武器登场：synchronized（会议室）

需求也很明确：把"看-算-写"这三步打包成一个不可分割的整体，执行期间别人不许插队。最直接的思路：给这段代码配一个会议室，谁要执行这段代码，先拿会议室钥匙，拿不到就在外面等，干完出来把钥匙还了——同一时刻会议室里只有一个人。

CounterFixed.java三步被打包成一步
public class CounterFixed {
    static int count = 0;
    static final Object LOCK = new Object();   // 一把明确的、大家共用的钥匙

    public static void main(String[] args) throws Exception {
        Runnable task = () -> {
            for (int i = 0; i < 100000; i++) {
                synchronized (LOCK) {       // 进会议室：拿钥匙
                    count++;                // 三步在会议室里，外面没人能插队
                }                           // 出会议室：还钥匙
            }
        };
        // ... 两线程各跑 10 万次，结果必然 200000
    }
}

2.5 会议室凭什么包治三性？（不是巧合，是三条保证）

很多人背"synchronized 保证原子性、可见性、有序性"，但说不清为什么一把锁能捎带管了另外两件事。拆开看它实际承诺的三条，三性全是推论：

  1. 一次只进一个人（互斥）→ 三步没人插队 → 原子性 ✓
  2. 进门的人，看到的一定是上一个人留下的最终状态（JMM 规定：解锁前的所有写，对后续拿到同一把锁的人可见）→ 上一个人出门前必须把白板刷新 → 可见性 ✓
  3. 会议室里永远只有一个人 → 他看自己一个人的代码，怎么重排都是 as-if-serial（单人视角）→ 有序性 ✓（临界区内）
🔍 凭什么"出门前必须刷白板"？——谁规定的？

不是硬件自动的，是 JMM（Java 内存模型）的明文规定：对同一个锁，解锁操作 happens-before 后续的加锁操作。JVM 在生成解锁指令时插入屏障强制把工作内存刷回主存，加锁时强制重新读主存。你可以把 JMM 理解成"作坊的安全生产规范"——它规定了各种同步工具（锁、volatile、线程 start/join）必须满足的可见性承诺，HotSpot 按规范实现。第一幕的 volatile、这一幕的锁，背后都是这份规范的具体条款。

2.6 用会议室：最容易踩的三个坑

LockTraps.java钥匙给错了人，会议室白建
// 坑一：每人自带一把钥匙 —— 两个线程各 new 一个 Task，synchronized 修饰的
// work() 锁的是 this（各自的实例），等于两个会议室各进各的，互斥完全失效
class Task implements Runnable {
    public synchronized void work() { count++; }   // 锁 this
}
new Thread(new Task()).start();   // 线程1 进的是 task1 的会议室
new Thread(new Task()).start();   // 线程2 进的是 task2 的会议室 —— 没互斥！
// 修：static synchronized（锁类对象，全局一间会议室）或锁共享的 LOCK

// 坑二：每次现造一把新钥匙 —— 锁对象每次都是新的，等于每次换个会议室门
synchronized (new Object()) { count++; }          // ❌ 锁了个寂寞
// 修：private static final Object LOCK = new Object();

// 坑三：一把钥匙开两扇门 —— 加锁的对象和解锁的对象不是同一个
synchronized (LOCK_A) { ... } 里再 synchronized (LOCK_B)，语义混乱且容易死锁

判断口诀只有一句话：所有需要互斥的代码，必须竞争同一把钥匙（同一个对象）。实例方法锁 this、静态方法锁类对象、代码块锁括号里那个——先想清楚"我的这些线程，抢的是同一间会议室吗？"

2.7 会议室的内部构造（底层，讲到够用）

每个 Java 对象头里有一小块空间（Mark Word），会根据"这间会议室的火爆程度"切换形态——这就是著名的锁升级，用人话讲就是会议室的三档管理策略：

第 1 档 · 偏向锁：会议室只被同一个人反复用
   ── 在门上挂个牌子"XX 专用"，他来了直接进，连登记都免了
   ── 实现对象头里记下线程 ID，同一线程再来：验牌直接进（最快）

第 2 档 · 轻量级锁：来了第二个人，但两人错峰用
   ── 牌子作废，改用"占位条"：谁进谁把门牌摘下来挂自己工位上
   ── 后来者在门外【原地等一小会儿】（自旋），不走去睡觉
   ── 适合：进去的人很快出来，等一下就轮到了

第 3 档 · 重量级锁：真竞争，一堆人抢
   ── 自旋变成白烧 CPU，改为正式排队：
      抢不到的线程被操作系统【挂起睡觉】，轮到再被叫醒
   ── 挂起/唤醒要走内核（用户态↔内核态切换，微秒级）—— 这是"重"的来源
   ── 实现对象头指向一个 Monitor（C++ 结构：持锁线程/阻塞队列/等待区/重入计数）

只能升不能降：无锁 → 偏向 → 轻量 → 重量（JDK6 引入；JDK15 起默认废弃偏向，
因为撤销牌子需要全局停下来，现代应用普遍多线程，不划算）
📌 面试叙述框架

先纠偏再展开："synchronized 并不天然重——JDK6 之后它有自适应的锁升级，低竞争时停留在偏向/轻量级（自旋等一下就过去），真竞争才膨胀成重量级挂起排队。'synchronized 就是慢'是十年前的过时印象。"

⚠ 边界：会议室解决了什么，没解决什么
✅ 解决
  • 原子 / 可见 / 有序，三性全包
  • 可重入（同线程重复拿自己的锁不死锁）
  • 绝大多数场景的正确选择
✗ 没解决
  • 太贵：高竞争下挂起+唤醒（内核切换），为一句 i++ 开会不值
  • 等锁时不能被中断、不能超时、不能试一下就走
  • → 短平快的临界区需要更便宜的方案 → 第四幕 CAS
"可重入"是什么意思？为什么必须有？

同一个人已经拿着会议室钥匙，又想进另一间需要同一把钥匙的会议室（A 方法加锁后调用 B 方法，B 也加了同一把锁）——如果他进不去，就被自己锁死在门口（死锁）。可重入 = 钥匙认人不认次数：同一线程可以反复进入，内部计数器 +1，出来一次 -1，归零才真正还钥匙。任何生产级锁都必须可重入，否则正常的方法调用链都会把自己玩死。

第三幕 有序性：眼看不一定为实 难点

① 为什么出现编译器和 CPU 为了快，会调整指令顺序（重排）——单人没事，多人穿帮。
② 什么场景初始化标志+数据、DCL 单例——"先准备数据再举旗"的代码被打乱。
③ 怎么发生三个搬代码的家伙 + 一张两线程交错时序表。
④ 解决了什么happens-before 判断标准 + volatile 屏障封堵 → DCL 收官。

3.1 惨案现场

线程 A 执行：                线程 B 执行：
  a = 1;    // 先准备数据       if (b == 2) {          // 看到旗子举起
  b = 2;    // 再举旗           assert a == 1;         // 却发现数据没准备好！
                              //（b==2 成立，a 却是 0 —— 断言失败）

逻辑上"举旗之前数据必然就绪"，但线程 B 亲眼看到了反例。
这不是 B 眼花，是 A 那两行的执行顺序被偷偷换过了。

3.2 解剖：谁在动你的代码

你写的代码顺序，和 CPU 实际执行的顺序，经常不一样。有三个家伙都有权限搬动你的指令，动机只有一个——快：

搬手它干了什么举例
编译器/JIT重排字节码/机器码顺序把你先写的 load 挪到 store 后面（读内存很慢，先让它排队）
CPU 乱序执行一条指令等数据时，先执行后面不依赖它的指令食堂打饭：你等红烧肉，先让后面的人打汤
写合并/缓存多次写合并成一次生效便利贴上改三次，最后才抄回白板一次

为什么单人没事？有一条铁律保护单线程：as-if-serial——无论怎么搬，单线程的执行结果必须和顺序执行一模一样（编译器会分析依赖，有依赖的绝不搬）。所以你看自己代码永远"正常"。多线程为什么穿帮？as-if-serial 只分析单线程内部的依赖，它不知道线程 B 依赖"a 在 b 之前"这种跨线程的约定——这个约定它看不见，就顺手搬了。

重排不能禁绝（性能崩溃），可见性逐个分析不现实。JMM 的解法是立一份契约，名字叫 happens-before（先行发生）。它的大白话定义：

happens-before 不是"物理上谁先执行"（快递实际怎么运输、走哪条线、哪个先装车，你不关心也不可控），而是承诺："只要 A happens-before B，那么 A 产生的效果，B 一定看得见"（你在 A 时刻下的单，B 时刻查物流必然查得到）。至于中间是直飞还是绕路——随它去，反正结果给你保证。它是"可见性的保证书"，不是"执行顺序的描述"。

没有 happens-before 关系的两个操作（比如上面的 a=1 和线程 B 的读），JMM 一律不做任何承诺——读新读旧、顺序乱不乱，都合法。这种"无保证区域"有个正式名字：数据竞争（data race），写出 data race 的程序等于把命运交给编译器的心情。

四条最常用的规则（一共八条，这四条覆盖 90% 的面试题）：

规则大白话
程序顺序单线程里，按代码顺序前面的操作 hb 后面的（as-if-serial 的契约版）
锁规则同一把锁：上一个人解锁 hb 下一个人加锁（第二幕"进门看到最新"的法源）

用法示范（第二幕遗留的问题现在能正式回答了）："线程 A 锁内改了 x，解锁；线程 B 加同一把锁后读 x，能读到吗？"——写 x hb 解锁（程序顺序），解锁 hb 加锁（锁规则），加锁 hb 读 x（程序顺序），三段用传递性一串：写 x hb 读 x，能读到。以后遇到任何可见性问题，别凭感觉，拿规则串一遍。

3.4 收官之战：DCL 单例——第一幕+第三幕知识的合体应用

懒汉式单例最著名的写法（双重检查锁），是"为什么需要 volatile"的最佳实战。先看代码：

Singleton.java每一行都不能少
public class Singleton {
    private static volatile Singleton instance;   // ★ volatile 在这里救命

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                    // ① 第一次检查（不拿锁的快路径）
            synchronized (Singleton.class) {       // ② 拿会议室钥匙
                if (instance == null) {            // ③ 第二次检查（拿到钥匙后再确认）
                    instance = new Singleton();    // ④ 惨案发生地
                }
            }
        }
        return instance;
    }
}
// 两次检查各自的作用：
// ① 让"对象已存在"之后的每次调用完全无锁（性能大头）
// ③ 防止等钥匙期间别人已经建好（两个线程同时通过①，一个建完，另一个进
//    会议室后若不复查会再建一个）——正确性

问题出在 instance = new Singleton() 这一行。它看起来一步，实际三步：a. 分配内存 → b. 构造函数初始化字段 → c. 把地址赋给 instance。b 和 c 之间没有单线程依赖（赋值不依赖字段内容），所以 JIT 可以合法地把顺序换成 a → c → b。换完之后：

线程 A（拿着钥匙）                    线程 B（在 ① 处张望）
 a. 分配内存
 c. instance = 地址 ────────────────► B 看到 instance != null！
    （对象还没初始化，字段全零值）        直接 return instance
                                        → 拿到一个【半成品】→ 用字段就 NPE
 b. 初始化字段（晚了）

volatile 的屏障此时干什么（回收第一幕的表）：
 写 instance 之前有 StoreStore 屏障 —— b（普通写）不许搬到 c（volatile 写）之后
 ⇒ 线程 B 要么看到 null（老实去拿钥匙），要么看到完整对象。
 半成品状态被屏障封死在门内。
一句话回答

DCL 为什么必须 volatile？——new 不是原子操作且"赋值"和"初始化"可被重排，无 volatile 时其他线程可能拿到"地址已赋、字段未初始化"的半成品；volatile 写前的屏障把初始化焊死在赋值之前。

还有别的单例写法吗？不想操心 volatile 行不行？

行，而且更推荐背这个——静态内部类（原理是模块 5 的钩子：类加载的 clinit 由 JVM 保证只执行一次、多线程下天然互斥，等于 JVM 替你加了锁）：

private static class Holder { static final Singleton INSTANCE = new Singleton(); }
public static Singleton getInstance() { return Holder.INSTANCE; }

懒加载由"内部类第一次被引用才加载"实现，线程安全由"clinit 加锁"实现，零锁代码零 volatile。防御要求最高的场景（防反射、防反序列化再建实例）用枚举——JVM 层面禁止反射创建枚举实例，是 Effective Java 的推荐答案。

第四幕 CAS：乐天派的不排队方案 高频

① 为什么出现重量级锁排队 = 挂起+唤醒（微秒级），而 i++ 本身只要纳秒——为纳秒的活付微秒的排队费，不划算。
② 什么场景高并发计数、状态开关转换、并发容器的内部实现——全是"读-改-写"就一句的短活。
③ 怎么发生CAS = CPU 一条原生指令："还是我看到的那个值吗？是就换，不是就失败"。失败就重看一眼重来。
④ 解决了什么无锁的原子更新 + 原子类全家桶。✗ ABA / 自旋烧 CPU / 只能管一个变量。

4.1 惨案现场：会议室太贵了

第二幕的结尾留了个钩子：为一句 i++ 开会议室，到底贵在哪？算一笔账。把一个线程"挂起睡觉再叫醒"（重量级锁排队），需要用户态↔内核态来回切换，开销在微秒级（1~10μs）；而 i++ 这句活本身，纳秒级（~1ns）就干完了。也就是说：

干活的成本：        ████████ 1 纳秒
排队（挂起+唤醒）的成本： ████████████████ 1000+ 纳秒（微秒级）

→ 活儿越短，"开会"越荒谬。10 个线程挤在会议室门口，
  每人等 1 微秒就为了改 1 纳秒的数 —— CPU 大部分时间在办理"排队手续"。

而现实中这种"短到荒谬"的临界区到处都是：计数器、限流、状态标志翻转、
并发容器内部的一次指针替换 —— 全是"一句读-改-写"。

直觉的出路：既然活儿这么短，抢不到就别去睡觉了，原地重试一下——指不定下一纳秒就轮到了。这个"原地重试"的思路要成立，必须有一个前提："看一眼旧值 → 换成新值"这两步能被硬件打包成不可分割的一步。这个前提 CPU 真的提供了，它叫 CAS。

4.2 换个脑子：悲观派与乐观派

在见代码之前，先把两种世界观摆出来——它们贯穿整个并发、数据库、分布式，不只是 Java：

悲观派（synchronized）乐观派（CAS）
世界观冲突一定会发生，先锁门再说冲突大概率不发生，先干，撞了再重来
作坊里的形象会议室：进门前先拿钥匙白板前直接动手，写回时核对一下
没冲突时照样付拿钥匙/还钥匙的手续费零额外开销，一次成功
有冲突时后来的人睡觉，被叫醒再试后来的人当场失败，重看一眼重试
适合临界区长、竞争激烈临界区极短、竞争温和
🗺 类比：多人协作文档的"保存冲突"

你打开一份共享文档时它显示版本 5。你改了半天点保存，系统核对："现在还是版本 5 吗？"——是，你的修改直接生效；不是（有人已经存过版本 6 了），你的保存被拒绝，需要重新拉最新版再改一遍。注意这个设计的精髓：拒绝你的时候告诉你"有变化"，但不锁文档、不妨碍别人编辑。Git 冲突、数据库乐观锁（UPDATE ... WHERE version=5）、CAS，全是这一个思想的不同马甲。

4.3 武器登场：CAS 的三件套

CAS（Compare-And-Swap，比较并交换）的完整定义就一句话：

CAS(内存位置 V, 我记下的旧值 A, 想写成的新值 B)
   ├─ 此刻 V 里的值 == A ？  →  把 V 写成 B，返回 true（我赌对了，没人动过）
   └─ 此刻 V 里的值 != A ？  →  什么都不做，返回 false（有人插队了，我重来）

整个"核对+替换"由 CPU 一条指令完成（x86 上是 lock cmpxchg），
硬件保证核对和替换之间【没有任何人能插一脚】 —— 原子性的来源

用它重写计数器，就是 JDK 里 AtomicInteger.incrementAndGet() 的真实逻辑（简化后）：

AtomicInteger.java（JDK 源码简化）注意：还是三步，但最后一步带"核对"
public final int incrementAndGet() {
    int current, next;
    do {
        current = this.get();      // ① 看一眼：读到现在的值（比如 5）
        next = current + 1;        // ② 心算：5 + 1 = 6
    } while (!compareAndSet(current, next));  // ③ 换！核对"还是 5 吗"
                                              //    不是 5 → 整个重来（回到①）
    return next;
}

对照第二幕的解剖：i++ 还是"取数 → 算 → 放回"三步，volatile 版失败在第三步是无脑覆盖；CAS 版的第三步是带着核对的条件覆盖——"只有白板上还是我记下的那个 5，我的 6 才允许写上去"。像在便利贴背面写上"我对的是 5"，柜台收单时核对一遍，对不上就打回重写。这样即使中途被人插队，也不会把别人的成果覆盖掉——要么成功，要么完好无损地失败重来。

4.4 凭什么有效：硬件的原子指令

🔍 "比较和交换之间没人插队"是谁保证的？

不是 Java，是 CPU。x86 提供 lock cmpxchg 指令：LOCK 前缀让这个核独占那个缓存行再执行比较交换——正是第一幕讲过的 MESI 协议那套硬件广播机制（"我要独占，其他核把旧便利贴作废"）。Java 里 Unsafe.compareAndSwapInt() 是个 native 方法，直接映射到这条指令。所以 CAS 的原子性和 volatile 的可见性，硬件根源是同一套：一个是"独占地改"，一个是"改完立刻广播"。

4.5 原子类全家桶：CAS 的产品化

JDK 把"volatile + CAS + 自旋"这个组合封装成了一整包工具（java.util.concurrent.atomic 包），按场景选：

类管什么典型用法
AtomicInteger / AtomicLong一个数字的原子读改写计数器、发号器（incrementAndGet）
AtomicReference<V>一个对象引用的原子替换原子地换掉整个配置对象/链表头
AtomicStampedReference<V>带版本号的引用ABA 的解药（见 4.6 洞一）
LongAdder高并发纯计数专精统计计数、热点计数（见 4.6 洞二）
AtomicIntegerFieldUpdater给已有字段"加装"原子操作不能改类定义时（少见，知道即可）

AtomicReference 顺便解决了"只能管一个变量"的一部分：两个变量要联动原子地变，就把它们打包进一个不可变对象（final 字段），用一次 CAS 整体换引用——旧引用换成新引用是原子的，两个字段作为整体一起被换掉，不存在"换了一半"。

4.6 乐观派的三个洞

CAS 不是银弹，它有三个天生的坑，面试常拿它们当追问：

洞一：ABA——"没人动过"和"动过又改回来了"分不清

CAS 只核对"现在是不是我记的值"，它不知道这个值中间经历过什么。

🗺 类比：冰箱里的可乐

你出门前冰箱里有一罐可乐，回来看到还是一罐可乐，于是断定"没人动过"。真相：室友喝掉了，又买了一罐同款放回去。对"喝没喝过"这件事，你的检验完全失效。变量从 A 被改成 B 又改回 A，CAS 的持有者毫无察觉——值相同 ≠ 没被动过。

纯数字计数无所谓（A→B→A 再 +1 结果也无所谓）。要命的是引用场景：无锁栈的经典事故——线程 1 记下栈顶是节点 A，准备 CAS 换成 A.next；期间 A 和 B 都被弹出又 A 被重新压入，线程 1 一核对"栈顶还是 A？"——成功！但此时 A.next 已经变了，栈被接歪了。解药：加版本号——AtomicStampedReference 每次修改都盖一个新戳，CAS 同时核对值和戳，可乐上贴生产日期，看罐子不看日期的时代结束了。（Java 有 GC 兜底，引用复用问题比 C++ 少得多，但面试必须能讲清。）

洞二：自旋烧 CPU——竞争一激烈，全员空转

失败重试是 do-while 死循环。10 个线程挤一个 AtomicLong，竞争激烈时大量线程在循环里空烧 CPU，成功者只有少数——乐观派对"高竞争"过敏。解药：LongAdder——别挤一个柜台，开一排柜台：

AtomicLong（单柜台）：                    LongAdder（柜台阵列）：
        ┌────────────┐                    ┌──────┐ ┌──────┐ ┌──────┐
 t1..t10 ──►│  count 递增 │ 全员排队重试      │base  │ │Cell[0]│ │Cell[1]│ ...
        └────────────┘                    └──────┘ └──────┘ └──────┘
  10 个线程挤 1 个热点                       不同线程被散到不同 Cell 各自加
  失败率 ∝ 竞争人数                          读时 sum = base + 所有 Cell 之和

思路：把"一个热点变量"拆成"一叠分片"，写压力被摊薄，
     冲突概率随分片数下降 —— 空间换时间。
代价：sum() 是"汇总瞬间的近似值"（弱一致），不适合要求精确读的场景。
选型口诀：写多读少用 LongAdder，读写均衡/要精确瞬时值用 AtomicLong。

洞三：只能管一个变量、一段"能重来"的逻辑

CAS 的本质是原子地换一个值。如果临界区是多步逻辑（查两张表、再发一条消息），"失败了整个重来"要么做不到（消息已发出，没法收回），要么重来成本比排队还贵。这时乐观派就该让位——老实回第二幕的会议室。一句话：CAS 是"读-改-写一句"的极致优化，不是锁的替代品。

一句话回答

CAS 是什么？——CPU 一条原生的"比较并交换"指令：写回前核对该值没被别人动过，没动过才生效，动过就整个重来。悲观锁（synchronized）先锁门再干活，CAS（乐观派）先干活、提交时核对，失败重试。

⚠ 边界：CAS 解决了什么，没解决什么
✅ 解决
  • 短临界区的原子更新，无需挂起排队
  • 原子类全家桶 / 并发容器内部的地基
  • 高竞争计数：LongAdder 摊薄热点
✗ 没解决
  • 复杂临界区（多步、不可重来的逻辑）→ 仍需锁
  • "抢不到就排队、轮到了叫醒"这套管理 CAS 完全没有
  • → 锁、信号量、门栓都需要排队机 → 下一幕 AQS
synchronized 和 AtomicInteger 怎么选？

看临界区的长度和可重来性：临界区就一句"读-改-写"、重试无副作用 → 原子类（无锁、高吞吐）；临界区有多步逻辑、或包着一组必须整体完成的操作 → 锁。另外注意很多场景两者结合：并发容器内部节点替换用 CAS，宏观操作加细粒度锁。

CAS 的自旋和第二幕"轻量级锁自旋"是一回事吗？

思想同源（抢不到不睡觉、原地重试）、实现不同层：AtomicInteger 里的自旋是你自己代码里的 do-while（Java 层）；轻量级锁的自旋是JVM 在 synchronized 内部替你做的。可以看成同一个"乐观等待"模式在两个层面的复用——面试这么串一句，比背两个孤立概念高一个段位。

Python 里见过这个思想吗？Python 对比

你没写过裸 CAS（CPython 内部才碰得到），但你一定用过它的马甲：Git 冲突（版本对不上就拒绝合并）、数据库乐观锁（UPDATE t SET v=?, version=version+1 WHERE id=? AND version=?，影响行数为 0 就是"被插队了，重来"）、Redis 事务的 WATCH/MULTI。思想是通用的：提交时核对，失败重来。

第五幕 AQS：公共排队叫号机 难点

① 为什么出现锁、信号量、门栓……全都需要"抢不到就排队挂起、轮到了叫醒"，这套逻辑每个工具自己写一遍 = 重复且容易写错。
② 什么场景ReentrantLock / Semaphore / CountDownLatch / 线程池的 Worker——JUC 半壁江山的地基。
③ 怎么发生一句话：一个 volatile int state（CAS 抢）+ 一条双向等待队列（抢不到入队睡觉，释放时叫醒队头）。
④ 解决了什么统一排队基建 + 比 synchronized 多的四样能力。✗ "等条件成立"要另一套 → 第六幕。

5.1 这幕的"惨案"不是 bug，是重复劳动

先自己动手造一个锁，感受一下坑有多深。第四幕学完 CAS，你可能会写出这样的东西：

SpinLock.java能跑，但三处硬伤
class SpinLock {
    private volatile int state = 0;                 // 空闲 0 / 占用 1

    public void lock() {
        while (!cas(0, 1)) { }                      // 抢不到就原地死等
    }
    public void unlock() {
        state = 0;                                  // 走的时候开门
    }
}

功能上它能互斥，但三个硬伤立刻暴露：

  1. 等的人烧 CPU：抢不到的线程在 while 里空转，第四幕刚讲过"自旋对高竞争过敏"；
  2. 没有先来后到：新来的线程可能永远抢过老实的排队者——某个线程饿死；
  3. 不可重入：拿着锁的线程再调一个内部也 lock 的方法，直接把自己锁死。

要修这三个洞，你需要：一个排队的队列（解决先来后到）、一套挂起/唤醒的办法（解决烧 CPU）、一个重入计数（解决自锁）。写完这一套，你会发现——信号量需要一模一样的一套，倒计时门栓需要一模一样的一套，线程池的工作队列也需要。每个同步工具都自带一套排队机，明显是浪费。

于是 Doug Lea（JUC 的作者）把"排队、挂起、唤醒、取消、容错"这一整套通用骨架抽出来写成一个类，各种同步工具只需要回答两个问题："什么算抢到？什么算放掉？"——这就是 AQS（AbstractQueuedSynchronizer，抽象队列同步器）。名字吓人，拆开就是四个词：抽象（模板，等你来填空）、队列（排队的地方）、同步（协调多线程）、器（一个类）。

5.2 AQS 只有两大零件

零件一：state —— 一个 volatile int（含义由子类定义）
   ReentrantLock:    state = 重入次数        （0 空闲，2 = 持有者进来了两层）
   Semaphore:        state = 剩余许可证数    （5 = 还能放 5 个人同时进）
   CountDownLatch:   state = 还没倒数的门闩数（3 = 还有 3 个计数没完成）
   共同点：改 state 全靠 CAS（第四幕），读靠 volatile 可见性（第一幕）

零件二：CLH 双向等待队列 —— 抢不到的人在哪等
   抢锁失败的线程被包成一个 Node，挂到队列尾巴上
   Node 里的线程用 LockSupport.park() 挂起 ——【真正去睡觉，不烧 CPU】
   持锁者释放时，叫醒（unpark）队列头部第一个还睡着的 → 它醒来重新抢
🗺 类比：银行叫号机

state = 柜台窗口数（还剩几个窗口空着）；队列 = 取号等待区（取了号的人坐在椅子上睡，不是站着干耗——这就是 park 挂起比自旋文明的地方）；park() = 叫号前你先眯一觉；unpark() = 广播叫号，被叫醒的人站起来去窗口办业务（重新尝试 CAS 抢 state）。叫号机不关心你办什么业务——业务你自己填（tryAcquire），排队的规矩它统一包办（acquire）。

5.3 骨架与血肉：模板方法的分工

AQS 的用法是"继承它，填两个空"。它把方法分成两层，分工极其清楚：

层方法谁写管什么
血肉（业务）tryAcquire() / tryRelease()你（子类）"什么算抢到、什么算放掉"——state 怎么变、什么条件下算成功
tryAcquireShared() / tryReleaseShared()你（子类）共享模式的版本（允许多人同时"抢到"，如信号量）
骨架（通用）acquire() / release()AQS（父类）调你的 tryAcquire，失败 → 入队 → park 挂起；释放 → 叫醒队头
队列维护、取消、中断处理AQS（父类）所有容易写错的脏活

这正是设计模式里的模板方法模式：父类定流程（"先试抢 → 不行就排队睡 → 被叫醒再试"），子类填空（"试抢怎么算成功"）。你写过的每一个 ReentrantLock.lock()，进到源码里都是 sync.acquire(1) → tryAcquire(1)（ReentrantLock 填的空）→ 失败则排队睡觉。

5.4 实战解剖：ReentrantLock 就是 AQS 的一道填空题

ReentrantLock 核心逻辑（简化）可重入 = owner 是自己就 state+1
// tryAcquire 的填空：什么算抢到？
boolean tryAcquire(int acquires) {
    int c = getState();
    if (c == 0) {                                  // 空闲
        if (cas(0, acquires)) {                    // CAS 抢
            owner = currentThread();               // 门上挂牌：谁在用
            return true;
        }
    } else if (owner == currentThread()) {         // 已持有且是自己 → 可重入！
        setState(c + acquires);                    // 只加计数，不用 CAS（独占中没人能改）
        return true;
    }
    return false;                                  // 抢不到 → AQS 骨架让你排队睡觉
}

// tryRelease 的填空：什么算放掉？
boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (owner != currentThread()) throw new IllegalMonitorStateException();
    if (c == 0) { owner = null; setState(0); return true; } // 计数归零才真放锁
    setState(c); return false;                     // 重入层没退完，还占着
}

公平与非公平的区别只有一句话：非公平版 tryAcquire 开头先"无礼地"直接 CAS 插一次队（if (c == 0) → cas，不看队列）；公平版先问一句 hasQueuedPredecessors()——"队列里有人排队吗？有人我就老老实实去队尾"。

🔍 为什么默认是非公平？插队不是不讲武德吗？

吞吐量。刚释放锁的瞬间，如果队列里的人还睡着（唤醒要花微秒），而恰好有个新线程刚到（CPU 正热着），非公平直接把锁给它——省掉一次挂起+唤醒的往返。代价是排队的老线程可能一直被插队（饿死）。公平锁先来后到，但每次都要走"唤醒队头"的慢流程，吞吐明显更低。公平是奢侈品，默认卖性价比——这也呼应一个更大的原则：并发工具的性能大头往往不在"抢锁"本身，而在"等待者的管理方式"。

5.5 synchronized vs ReentrantLock：什么时候用谁

5.6 手撕加分：20 行用 AQS 造一把锁

Mutex.java面试现场手写版（非重入）
class Mutex {
    private final Sync sync = new Sync();

    // 继承 AQS，只填两个空："什么算抢到 / 什么算放掉"
    private static class Sync extends AbstractQueuedSynchronizer {
        @Override
        protected boolean tryAcquire(int acquires) {
            return compareAndSetState(0, 1);   // 抢到 state 0→1 就算赢
        }
        @Override
        protected boolean tryRelease(int releases) {
            setState(0);                        // 此时独占，直接写，无需 CAS
            return true;
        }
    }
    public void lock()   { sync.acquire(1); }   // 抢不到？骨架让你排队睡觉
    public void unlock() { sync.release(1); }   // 释放时骨架自动叫醒队头
}

这就是 AQS 设计的漂亮之处：你写的 8 行是业务判断，排队挂起唤醒那些最容易写错的 800 行，父类全包了。Semaphore 的空是"state 是许可证数，减到 -1 就算抢不到"；CountDownLatch 的空是"state 减到 0 才放行"——同一台叫号机，换个业务规则而已。

一句话回答

AQS 是什么？——一个"volatile state（CAS 改）+ CLH 双向等待队列（park 挂起 / unpark 唤醒）"的公共排队机：子类定义 state 的含义和抢放规则（tryAcquire/tryRelease），排队挂起唤醒的通用骨架它全包。ReentrantLock、Semaphore、CountDownLatch 都是它的填空题。

⚠ 边界：AQS 解决了什么，没解决什么
✅ 解决
  • "抢不到就排队、轮到了叫醒"的统一基建
  • 可中断 / 超时 / 公平 / 多条件队列四大能力
  • JUC 各同步工具的地基（一通百通）
✗ 没解决
  • 它只管"排队拿许可"，不管"等一个条件成立"（队列非空、连接归还）
  • 条件等待需要"睡去等信号、醒了重新抢锁"的配合机制
  • → 这套"线程说话"的原语 → 第六幕
队列里挂起的线程，到底是怎么被挂起和唤醒的？

LockSupport.park() / unpark(thread)——JDK 里最底层的"睡觉/叫醒"原语（内部走 Unsafe，对应操作系统的挂起原语）。AQS 入队后循环里 park 自己；持锁者释放时会找到队头第一个有效节点 unpark 它。park/unpark 的细节和它比 wait/notify 先进在哪，第六幕专门讲——AQS 的排队为什么可靠，答案全在那。

为什么等待队列要设计成双向链表？单向不行吗？

三个刚需：① 唤醒时要找后继节点（释放锁叫醒下一个人）——要 next 指针；② 节点取消/超时要把自己从队列里摘掉，得同时改前驱的 next 和后继的 prev——要 prev 指针；③ 排队中的线程要反复检查"我是不是队头"（只有队头才被赋予抢锁资格）——从自己往前看一眼前驱是否是哨兵节点。单向链表做不到 ②③，所以双向。

CountDownLatch 和 AQS 什么关系？追问率高

它就是"共享模式"的填空题：state = 计数值。countDown() = releaseShared（CAS 把 state 减 1）；await() = acquireSharedInterruptibly（tryAcquireShared 的填空是 return getState() == 0 ? 1 : -1;——state 不为 0 就去排队睡觉）。state 减到 0 的那次 release 会把队列里所有等待者一起叫醒——这就是"倒数结束、全员放行"的实现。第九幕还会从"使用者视角"再讲一遍三件套。

第六幕 等与唤醒：线程怎么说话 高频

① 为什么出现线程之间不只是抢资源，还要"打招呼"：队列空了生产者得睡，队列满了消费者得睡，等条件成立再干。
② 什么场景生产者-消费者（最经典）、任务队列、连接池借还——一切"等条件"的协作。
③ 怎么发生wait 进等待区睡觉并交出钥匙，notify 叫醒一个人；Condition = AQS 版等待区；park/unpark = 最底层的睡觉叫醒原语。
④ 解决了什么线程协作时序。✗ 有些数据根本不该共享 → ThreadLocal。

6.1 惨案现场：忙等烧穿 CPU

生产者往队列里放任务，消费者从队列里取。消费者的第一版直觉写法：

BusyWait.java两种写法都不行
// 写法一：死盯着看
while (queue.isEmpty()) { }        // 队列空就一直空转 —— 一个核被烧满，什么都没干

// 写法二：隔一会儿看一眼
while (queue.isEmpty()) {
    Thread.sleep(100);             // CPU 是省了，但任务平均要白等 50ms
}                                  // 睡 1ms？又烧 CPU。左右不是人

两难的根源：消费者不知道"什么时候队列会有东西"，只能反复查看。真正需要的是一种机制——"我先去睡（不占 CPU），等生产者放东西的时候主动叫醒我"。也就是线程之间要能说话：一方睡去等信号，另一方发信号。

6.2 武器登场：wait / notify 三件套

Object 类上挂了三个土生土长的方法（对，是 Object——任何对象都能当"等待区"）：

方法大白话细节（面试坑点）
wait()我去等待区睡觉，钥匙还回前台睡着时不占锁；被叫醒后要重新排队抢钥匙，拿到才从 wait 那行继续往下走
notify()叫醒等待区里的一个人叫谁由 JVM 决定（不确定）；发信号的人自己还在持锁——被叫的人要等他出了临界区才能动
notifyAll()把等待区的人全叫醒全部醒来重新抢钥匙，抢到的干活，没抢到的回去睡
🗺 类比：前台叫号

wait = 跟前台说"条件不满足，我去休息区睡了"，顺手把会议室钥匙还回去（还钥匙是关键！不还，别人永远进不了会议室，条件永远变不了）。notify = 前台朝休息区喊一嗓子"有情况！"。被喊醒的人不能直接冲进会议室——他得重新排队拿钥匙，拿到了，从当初睡着的那行代码继续执行，并且必须重新检查条件（喊你起来不代表条件就是为你准备的）。

🔍 铁律：为什么 wait/notify 必须写在 synchronized 里？

不写会直接抛 IllegalMonitorStateException，但面试要的是"为什么这样设计"。推演一遍不持锁会发生什么：消费者查了队列（空），还没来得及 wait，生产者放了东西并 notify——这声叫醒落空（没人睡着）。随后消费者才睡去，从此没人再叫它——即使队列里一直有货。这就是臭名昭著的丢失唤醒（lost wakeup）。持锁的意义："检查条件"和"睡去"之间不许有人插队改条件、发信号——把这两步打包成原子的，丢失唤醒在结构上就不可能发生。JMM 也给了配套承诺：notify 发生在解锁前 → 被唤醒者重新加锁后必然看到信号发出前的所有改动（第三幕锁规则的又一次应用）。

6.3 两个经典坑（笔试和面试的常驻嘉宾）

坑一：醒来后用 if 还是 while 重查条件？

✗ if (queue.isEmpty()) wait();  take();
   醒来直接往下拿 → 拿的时候可能又空了！

为什么：① notifyAll 叫醒的不止你一个——第一个抢到钥匙的把唯一的元素拿走了，
        你抢到钥匙时队列又空了（条件被别人"用掉了"）；
      ② JVM 允许"没人叫你、你自己醒"（虚假唤醒 spurious wakeup，底层机制决定，
        规范明文允许）。
✓ while (queue.isEmpty()) wait();  take();
   醒来【重新检查】，条件真满足才往下走 —— 一句话：wait 只负责睡，
   条件判断永远是自己的责任，每醒一次查一次。

坑二：notify 还是 notifyAll？

notify 只叫醒一个，但如果这把钥匙的等待区里睡着两种人（生产者等"不满"、消费者等"不空"），notify 可能叫醒的是不该醒的那种——他醒来一查条件不满足，又睡回去了，而真正该醒的人没被叫到，永远睡死。保守正确的答案：notifyAll——全叫醒，让条件自己筛选（配合 while 重查）。代价是多几场钥匙争夺，但换正确性，值。

6.4 手撕：生产者-消费者完整版（面试高频）

BoundedBuffer.java每一行都有讲究
class BoundedBuffer<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int capacity;

    public BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void put(T item) throws InterruptedException {
        while (queue.size() == capacity)   // ① while 不是 if：醒来重查（坑一）
            wait();                        // ② 满：去休息区睡，钥匙还前台
        queue.add(item);
        notifyAll();                       // ③ 叫醒所有人：有货可取了
    }                                      //    （为什么不是 notify？坑二）

    public synchronized T take() throws InterruptedException {
        while (queue.isEmpty())
            wait();                        // 空：去睡
        T item = queue.poll();
        notifyAll();                       // 有空位可放了
        return item;
    }
}

对着代码把整个舞蹈走一遍：消费者 A 发现空 → wait（还钥匙、去睡）→ 生产者 B 拿到钥匙 → 放入元素 → notifyAll（朝休息区喊）→ B 出会议室还钥匙 → A 被唤醒、重新排队拿钥匙 → 拿到 → while 重查：非空 ✓ → 取走元素 → notifyAll（叫生产者可以再放）→ 出门。每一方"睡"之前都还了钥匙，所以另一方总能进得去改条件——这就是这套机制不死的秘密。

6.5 进化版：Condition——AQS 时代的等待区

ReentrantLock 配套的等待机制叫 Condition，方法名换了一套马甲，语义一一对应：

Object（synchronized 配套）Condition（ReentrantLock 配套）语义
obj.wait()condition.await()睡去并释放锁
obj.notify()condition.signal()叫醒一个
obj.notifyAll()condition.signalAll()叫醒所有

Condition 的真正进步在于：一把锁可以开多个等待区。回看 6.3 坑二——生产者和消费者混在一个等待区是 notifyAll 保守的根源。Condition 直接把两种人分开睡：

ArrayBlockingQueue 的思路（简化）两个等待区，精准叫醒
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();  // 生产者睡这屋
private final Condition notEmpty = lock.newCondition(); // 消费者睡那屋

public void put(T item) throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (queue.size() == capacity) notFull.await();  // 满：去"不满屋"睡
        queue.add(item);
        notEmpty.signal();          // 只叫"非空屋"的消费者 —— 精准，不用全员惊动
    } finally {
        lock.unlock();
    }
}
// take() 对称：空了去 notEmpty 睡，取完 signal 不满屋

这就是 JDK 的 ArrayBlockingQueue 内部真实结构（它也是线程池工作队列的候选实现——第八幕会接上）。

6.6 最底层：LockSupport.park / unpark

第五幕欠的账现在还：AQS 队列里挂起线程用的到底是什么？——LockSupport.park() / unpark(thread)，JDK 里最底层的睡觉/叫醒原语（wait/notify 和 Condition 底下也各有实现，AQS 直接用它）。它和 wait/notify 有一个本质区别：

wait/notify：必须先睡后叫。
   你还没睡，我先 notify 了 —— 这声叫唤【凭空消失】，你再睡就没人叫你了
   （就像闹钟只响一次，你还没上床它先响了 —— 丢失唤醒）

park/unpark：叫醒可以提前发，像一张【起床券】。
   unpark(thread) 给目标线程发一张券；线程 park 时先摸口袋：
   有券 → 掏出来直接走人，根本不睡；没券 → 睡，等别人发券
   券不叠加：口袋里最多一张，先发十张也只算一张

   → "先叫后睡"不丢信号。这就是 AQS 敢把"入队"和"挂起"分两步做的底气：
     入队完、还没睡着的瞬间，就算别人已经 unpark 过了，券还在口袋里，
     park 一次看一眼券直接通过 —— 竞态窗口被券填平了。

另外注意 unpark 是按线程点名的（unpark(某个线程)），而 notify 只是"朝等待区喊一嗓子"不知道叫谁——这也是 AQS 能实现"精确叫醒队头"的基础。

一句话回答

wait/notify 是什么？——锁配套的"说话"机制：wait = 释放锁、进等待区睡；notify = 叫醒等待者去重新抢锁。必须持锁调用（防止检查条件到睡去之间被插队导致丢失唤醒），醒来必须 while 重查条件（虚假唤醒 + notifyAll 多人抢条件）。

⚠ 边界：等与唤醒解决了什么，没解决什么
✅ 解决
  • 忙等两难 → 睡觉等信号，CPU 零消耗
  • 生产者-消费者 / 任务队列的完整协作
  • Condition：多等待区精准叫醒
✗ 没解决
  • 前提是"数据要共享"——但有些数据人各一份才对
  • 给不该共享的数据加锁排队 = 白白付出
  • → 换个思路：不共享 → 下一幕 ThreadLocal
sleep 和 wait 到底差在哪？每次都混

四点：① 锁：sleep 抱着钥匙睡（不放锁），wait 睡前还钥匙；② 归属：sleep 是 Thread 的静态方法（跟锁无关），wait 是 Object 的方法（必须配合 synchronized）；③ 唤醒：sleep 定时醒（或被中断），wait 只能被 notify/notifyAll/中断唤醒；④ 用途：sleep 是"我歇会儿"（不涉及协作），wait 是"条件不满足，等消息"（协作）。一句话：sleep 是午休，wait 是等叫号。

既然有 wait/notify，为什么还要发明 Condition？

三个理由：① 多条件队列——一把锁多个等待区，生产者消费者分开睡、精准叫醒（6.5 的核心价值）；② 配套能力——Condition 天生和 ReentrantLock 的可中断、超时能力对齐（await 支持限时和响应中断，wait 的超时版不支持中断区分）；③ 实现统一——Condition 队列和 AQS 的同步队列用的是同一套 Node/park 基础设施，一个被 await 的线程被 signal 后会从条件队列转移到同步队列去排队抢锁，工程上优雅得多。

Python 里怎么写生产者消费者？Python 对比

你几乎从没手写过这套——queue.Queue 内部已经把条件变量（threading.Condition）封装好了，q.put() 满了自动睡、q.get() 空了自动等。Java 也有 ArrayBlockingQueue / LinkedBlockingQueue（就是 6.5 那段代码的成品），实际工程里没人手写 BoundedBuffer——但面试要你手写，考的就是你懂不懂"睡与唤醒的配合细节"（while 重查、锁的交接、丢失唤醒）。

② 什么场景traceId 全链路透传、SimpleDateFormat、Spring 事务绑定连接、用户上下文。

7.1 惨案现场：两种都难受的写法

前六幕的所有武器都默认一件事：数据就是要共享的。但看这个场景——SimpleDateFormat 不是线程安全的（内部有个共享的 Calendar，多线程同时 format 会互相污染，日期串位），你需要每个线程都能安全地用它格式化日期。摆在面前的两条路都难受：

方案一：全局一个 SDF + synchronized
   → 所有线程的日期格式化排队 —— 为"人各一份才合理"的数据开会议室，荒谬

方案二：每次用到就 new 一个
   → 线程安全了，但 SDF 创建成本高（解析格式串、建 Calendar），
     高频调用下 GC 压力大

两个方案的共同错误：都没意识到——
【这个对象根本不需要共享！】每个线程自己有一个，互不干扰，才是天理。

同款场景其实到处都是：Web 服务里"当前登录用户"、日志的 traceId、Spring 事务里绑定的数据库连接——它们都有的共同点：一个线程内全程要带着，线程之间各用各的。你可能会想"当成参数一路传下去"？可以，但十层方法调用层层透传，签名全被污染（这叫参数污染）。需要一个"每个线程自己的随身口袋"。

7.2 武器登场：ThreadLocal

SdfHolder.java一个词，两个世界
public class SdfHolder {
    // 每个线程第一次 get 时，用自己的格式串 new 一个专属于它的 SDF
    private static final ThreadLocal<SimpleDateFormat> SDF =
            ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

    public static String format(Date d) {
        return SDF.get().format(d);    // get() 拿到的永远是【当前线程自己那份】
    }
}

效果：线程 A 和线程 B 各自拿到不同的 SDF 实例，互不干扰，零锁零等待。这就是 ThreadLocal 的定位——它不解决共享问题，而是取消共享。

🗺 类比：工牌挂绳

公司发挂绳（ThreadLocal 对象），每个员工自己往上面挂自己的工牌（value）。谁看挂绳上挂着什么，取决于谁在看——你摸到的永远是自己的工牌。最大的误解在这里：很多人以为 ThreadLocal 是个"中央储物柜"（数据集中存在 ThreadLocal 里），错——挂绳只是钥匙/标签，真正的口袋缝在每个员工自己的衣服里（数据存在每个线程对象身上）。方向是"线程存数据"，不是"ThreadLocal 存线程"。

7.3 底层解剖（面试核心考点）

把 SDF.get() 一步步展开，看清数据到底存在哪：

Thread 类内部有个字段（关键！）：
   class Thread {
       ThreadLocal.ThreadLocalMap threadLocals;   // ← 每个线程自带的口袋
   }

SDF.get() 的执行链：
   ① 拿到当前线程对象          Thread.currentThread()
   ② 打开这个线程自己的口袋      t.threadLocals
   ③ 用 SDF（这个 ThreadLocal 对象）当 key 查表 → 拿到 value

口袋的结构（ThreadLocalMap，一个定制哈希表）：
   Entry extends WeakReference<ThreadLocal> {
       Object value;         // ★ key 是弱引用，value 是普通的强引用
   }

所以多个 ThreadLocal（挂绳 A、挂绳 B）在同一线程口袋里互不冲突；
同一条挂绳在不同线程口袋里各有各的 value —— 二维：线程 × ThreadLocal。

7.4 泄漏链：线程池 + ThreadLocal 的著名事故

为什么 Entry 的 key 要设计成弱引用？弱引用的定义（模块 5 的钩子）：只被弱引用指着的东西，GC 一来就收走。这看起来像"防止泄漏"的善意设计，但配上线程池就出事了。一步一步推：

前提场景：threadLocal.set(一个大对象)，用完把 threadLocal = null 扔了

  线程池的核心线程 ——【几乎永生】（干完活不死，回池子等下一个任务）
        │
        ▼ 强引用（线程对象活着，口袋就活着）
   Thread.threadLocals（口袋）
        │
        ▼ 强引用
   Entry[] 数组
        ├─ Entry.key  → 弱引用 → 外部没人引用 ThreadLocal 了 → GC 把 key 收走
        │              （Entry 变成 key=null 的"脏条目"）
        └─ Entry.value → ★强引用★ → 只要 Entry 活着，这个大对象就永远不可回收

  → 线程不死 / Entry 不被替换 / 没人清理 → value 成了"幽灵数据"，堆里越积越多 → OOM
🔍 弱引用救了 key，为什么救不了 value？这个设计图什么？

如果把 key 也设成强引用：外部 threadLocal = null 之后，Entry 还死死拽着 ThreadLocal 对象——连 key 带一堆 Entry 全都回收不了，泄漏更彻底。设计者的算盘是：key 用弱引用，外部一放手 key 就变 null，ThreadLocalMap 在后续 get/set 时顺手清理 key 为 null 的脏条目（源码里的 expungeStaleEntry），自愈一下。但在"线程永生"的线程池里，没人再碰这张表，自愈代码根本没机会跑——value 的强引用成了漏网之鱼。一句话：弱引用是兜底不是保险，根治只有一个动作——用完 remove()。

正确姿势线程池场景必写
try {
    USER_CONTEXT.set(currentUser);        // 进来：塞自己的
    // ... 十层业务方法里随时 USER_CONTEXT.get() 拿到当前用户，无需透传
    doBusiness();
} finally {
    USER_CONTEXT.remove();                // ★ 出去：掏空口袋，切断 value 的强引用
}                                         //   线程回池子时口袋是空的，下个人接着用

7.5 它撑起了哪些你天天用却没见过的东西

框架用 ThreadLocal 藏了什么为什么非它不可
Spring 事务当前线程绑定的 Connection同一事务里多次 DAO 调用必须拿到同一个连接才能一起提交/回滚——藏在当前线程口袋里，业务代码零感知

一句话回答

ThreadLocal 是什么？——线程私有的随身口袋：数据存在每个 Thread 自己的 ThreadLocalMap 里（ThreadLocal 只是查询用的 key），天生线程隔离、零锁。坑：线程池的线程永生，value 强引用回收不了 → 用完必须 finally remove()。

⚠ 边界：ThreadLocal 解决了什么，没解决什么
✅ 解决
  • "人各一份"数据的零锁隔离
  • 上下文透传（traceId / 用户 / 连接）
  • 非线程安全工具类的复用（SDF）
✗ 没解决
  • 它回避并发问题，不解决共享问题——真要共享还得回前三幕
  • 父线程的口袋，子线程摸不着（跨线程传递要特殊机制）
  • → 线程本身的管理（创建/复用/销毁）还没人管 → 下一幕线程池
ThreadLocal 是用来解决并发安全问题的吗？

不是——这是个经典面试陷阱。它解决的是"数据需不需要共享"的问题：能不共享的，隔离掉（ThreadLocal）；必须共享的，同步好（锁/CAS/原子类）。两条路解决两类问题，混着答会显得概念不清。判断标准：数据天然属于单个线程执行流 → ThreadLocal；数据是全局事实（计数、库存、缓存）→ 同步机制。

子线程能拿到父线程 ThreadLocal 里的值吗？追问率高

普通 ThreadLocal 不能（口袋各是各的）。有个特例 InheritableThreadLocal：创建子线程的瞬间，把父线程口袋里的内容复制一份给子线程。但注意它的死穴：线程池里线程是复用的，不是新创建的——复制只发生在 new Thread 那一刻，池里的老线程早就出生了，永远复制不到。所以"线程池 + 上下文传递"要靠阿里的 TransmittableThreadLocal（在任务提交时做快照、执行时回放）——知道这个链条，比背结论高一个段位。

一模一样的概念：threading.local()，Flask 的 flask.g / request 上下文、SQLAlchemy 的 session 都是靠它做的线程绑定。FastAPI 的 contextvars 是它 asyncio 时代的进化版（协程感知，还能正确处理任务切换——对应解决"池化复用导致上下文错乱"的问题，思想同 TransmittableThreadLocal）。你已经在 Python 里用过这套思路无数次，Java 只是把它讲得更底层（弱引用、泄漏链）。

8.1 惨案现场：线程不是白来的

最直觉的写法："一个请求来了，new 一个线程去处理"：

PerRequestThread.java流量一高就完蛋

    new Thread(() -> process(req)).start();   // 每个请求一个新线程
}

流量小时没事，高峰一来（比如秒杀，每秒 1 万个请求），三宗罪同时爆发：

  1. 创建/销毁的成本：每个线程创建要分配栈内存（默认约 1MB）、向 OS 登记，用完销毁——纯浪费，线程本身可以复用；
  2. 线程数爆炸：1 万个线程 = 10GB 栈内存起步 → OOM；就算内存够，CPU 就那么几个核，上万个线程来回切换，上下文切换的开销超过干活本身；
  3. 没有闸门：系统过载时无法自我保护，上游压力原样灌进数据库。

解法在现实世界早就有了：工厂。养一批固定工人（复用），活儿多了排队（削峰），实在太多就加临时工（弹性），加满了就拒绝接单（自我保护）。这套用工制度写成代码，就是线程池。

8.2 武器登场：七个参数就是一套用工制度

ThreadPoolExecutor 构造器阿里规约：别用 Executors，手动 new
public ThreadPoolExecutor(
    int corePoolSize,                  // 正式工：养着不裁，没活也待命
    int maximumPoolSize,               // 总人数上限：正式工 + 临时工
    long keepAliveTime, TimeUnit unit, // 临时工的"待业容忍期"：闲这么久就裁掉

    ThreadFactory threadFactory,       // 招人手续：起名（查线程 dump 时救命）、设 daemon
    RejectedExecutionHandler handler   // 拒客策略：大厅满 + 临时工满时怎么办
)

四个拒绝策略（保安打发新客的方式）：

策略行为适用
AbortPolicy（默认）抛 RejectedExecutionException，让调用方感知并处理任务不允许丢，有上层兜底逻辑
CallerRunsPolicy让提交任务的人自己干（提交线程自己执行任务）天然反压：上游被拖慢 → 自动少提交 —— 生产系统常用
DiscardPolicy悄悄扔掉新任务，不抛异常任务可丢（如日志刷屏），危险默认别用
DiscardOldestPolicy扔掉队列里等最久的，给新任务腾位新的比旧的值钱（行情推送类）

8.3 灵魂考点：任务提交的四级判定链

面试必背，且80% 的人第一次都答错顺序——不是"人满了就加人"，而是"队排满了才加人"：

execute(task) 提交一个任务，走四级判定链：

 ① 正式工招满了吗？（当前线程数 < corePoolSize）
      └─ 否 → 新招一个正式工，把任务直接交给他（不入队！）
      └─ 是 ↓
 ② 排队大厅塞得下吗？（workQueue.offer(task)）
      └─ 是 → 任务排队，等某个工人干完手头的活来接
      └─ 否（大厅满）↓
 ③ 临时工到上限了吗？（当前线程数 < maximumPoolSize）
      └─ 否 → 新招一个临时工，立刻干活
      └─ 是（人也满）↓
 ④ 拒绝策略 handler.rejectedExecution(task, this)
      （大厅满 + 临时工满 = 五个拒绝条件全中，保安出场）

★ 反直觉点：先排队（②）、后扩容（③）！
  直觉以为"任务多了加人"，实际是"队列都塞不下了才肯加临时工"。
  推论：用无界队列（如 LinkedBlockingQueue 默认构造）时，
       ② 永远为真 → ③④ 永远走不到 → maximumPoolSize 形同虚设！
🔍 为什么设计成"先排队、后扩容"？（面试加分点）

正式工（核心线程）是养着要成本的（内存 + 调度），扩容是最后手段。优先让任务在队列里等——排队是廉价的缓冲（一个引用而已），加线程是昂贵的扩编（MB 级内存 + 上下文切换税）。跟现实一致：活儿多了先让订单排着，真排不下了才招临时工。代价是响应变慢（排队 = 延迟），所以延迟敏感型系统会用 SynchronousQueue（零容量、直接交接）绕过排队——newCachedThreadPool 就是这么配的，任务一来直接给临时工，代价是线程数可能无限膨胀。

8.4 工人的生老病死（把前几幕全部串起来）

线程池里的每个工人（Worker）本质就是一个被管理起来的 Thread，它的一生长这样：

Worker 的主循环（简化）：
   while (true) {
       task = 队列.take();     // 领任务：队列空就【睡在队列上等】
       task.run();             // 干活（注意是 run 不是 start：复用线程，不开新的）
   }

★ take() 阻塞等待 = 第六幕的条件等待（空了睡、有任务被叫醒）
  —— 正式工永远不退出循环，所以核心线程"不死"：没活干就睡在 take() 上，
     零 CPU 消耗（不是空转！），任务一来就被唤醒。

★ 临时工的循环用 poll(keepAliveTime)：
   限时等待 —— 限时间内没等到任务（没人需要我）→ 退出循环 → 线程销毁
   （corePoolSize 范围内的工人用无限期 take，范围外的用限时 poll —— 同一段代码，
     一个布尔参数 allowCoreThreadTimeOut 控制正式工要不要也限时）

★ 五个生命周期状态（ shutdown / shutdownNow 的区别所在）：
   RUNNING  → 收新任务 + 处理队列任务（正常营业）
   SHUTDOWN → 不收新任务 + 【干完】队列里的存量（打烊前进完单）
              —— shutdown() 触发，温和关闭
   STOP     → 不收新任务 + 【丢弃】存量 + 中断正在干活的（掀桌子）
              —— shutdownNow() 触发；返回被丢弃的任务清单
   TIDYING  → 工人全散、队列清空（收拾场地）
   TERMINATED → terminated() 钩子执行完，彻底关门

看到没：线程池的每一块拼图都是前几幕的零件——Worker 领任务靠第六幕的条件等待；内部状态流转靠 CAS（ctl 一个 int 同时打包状态+线程数）；shutdownNow 的"中断干活"需要 Worker 响应中断（所以池里跑的任务要正确处理 InterruptedException，长任务不响应中断就关不干净）。

8.5 参数怎么配：把玄学变科学

业务类型推荐 core原理
CPU 密集（计算、压缩、加密）N 或 N+1（N = 核数）线程多了只是互相抢核；+1 是防某个线程偶发缺页暂停时 CPU 空一拍
IO 密集（调接口、查库、读写文件）经验起点 2N，靠压测调线程大部分时间在等 IO（睡着的工人不占核），可以多养几个把核喂饱

面试更漂亮的答案是承认"公式只是起点"：真正的工程做法是让参数可观测、可调整——setCorePoolSize() 运行时生效（池内自适应），配合监控（活跃线程数、队列深度、任务耗时、拒绝次数）动态调参。把"背公式"升级成"讲闭环"，是中级和高级的分水岭。

8.6 两个必考的坑

⚠ 坑一：为什么阿里规约禁用 Executors 快捷方法？

Executors.newFixedThreadPool / newSingleThreadExecutor 用的是无界队列（LinkedBlockingQueue 默认 Integer.MAX_VALUE 容量）——判定链 ② 永远为真，任务无限堆积 → OOM（还记得 8.3 的推论吗）；newCachedThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE——线程数无限膨胀 → OOM。手动 new ThreadPoolExecutor、显式给有界队列和明确上限，把"失控"变成"可控"。

⚠ 坑二：submit 的异常去哪了？

execute() 里任务抛异常 → 异常打印到控制台（默认 UncaughtExceptionHandler），工人继续领下一个任务，池不会死。submit() 把任务包成 FutureTask——异常被吞进 Future 里，不打日志、不冒泡，只有调 future.get() 时才会以 ExecutionException 抛出。所以线上 submit 不 get 也不记日志 = 故障静默。修法：任务内部 try-catch 打日志，或统一包装。

一句话回答

线程池的任务提交流程？——四级判定链：① 正式工没满 → 直接新招正式工干活；② 没满则入队排队；③ 队满且临时工没满 → 新招临时工；④ 全满 → 拒绝策略。核心是"先排队后扩容"；无界队列会让 maximumPoolSize 失效。

⚠ 边界：线程池解决了什么，没解决什么
✅ 解决
  • 线程复用：创建/销毁成本归零
  • 排队削峰 + 拒绝自保：过载不崩
  • 统一管理：命名、监控、优雅关闭
✗ 没解决
  • 多组工人之间的协调（等 N 个任务全完成再汇总、限制同时在岗人数）
  • 这类"多方协作时序"需要专门的工具
  • → 协作三件套 → 第九幕（收官）
核心线程能被回收吗？怎么"预热"线程池？

默认不回收（睡在 take() 上待命），但 allowCoreThreadTimeOut(true) 可以让正式工也走限时 poll——闲过头同样销毁，适合低频任务省内存。预热：prestartAllCoreThreads() 提前把正式工全招齐（秒杀开闸前先备好人），或空闲期跑几个心跳任务防止刚启动时的创建延迟毛刺。

shutdown 和 shutdownNow 到底怎么选？

看任务可不可弃：日常优雅停机（发布重启）用 shutdown()——不收新任务，把队列里的存量干完再关门，配 awaitTermination(超时) 等它收尾；紧急止损（发现任务有毒）用 shutdownNow()——直接掀桌：存量丢弃（返回给你）、干活中的线程被 interrupt。注意 interrupt 只是"请求停止"，任务里不处理 InterruptedException、不检查中断位的话，照样关不死。

Python 的线程池和这个比？Python 对比

concurrent.futures.ThreadPoolExecutor(max_workers=N) 概念上是"只有正式工 + 无界队列"的简化版：核心数 = 最大数，队列无界（不会拒绝，只会堆积——对应 8.6 坑一的隐患）。Python 里它主要服务 IO 密集（GIL 之下 CPU 密集得用 multiprocessing）。你熟悉的 future.result() 对应 Java 的 submit() 返回 Future + get()——连"异常藏在 future 里"这个坑都一模一样，as_completed 则对应 Java 的 CompletionService。

9.1 先看需求，再看工具

三个非常常见的协作需求，用第六幕的 wait/notify 手写每个都要几十行还容易错。逐个翻译成大白话：

需求一【限流】"这个资源最多 5 个人同时用"（连接池、爬虫并发上限）
需求二【等全完】"我派了 8 个任务出去，全部回来我再汇总"（主线程收拢）
需求三【人齐开会】"10 个线程各算一段，人人都到齐了，一起进入合并阶段"
                  （而且下一轮还能再聚 —— 循环使用）

9.2 三件套逐个登场（全是 AQS 填空题，验证第五幕）

Semaphore（信号量）：坑位数

🗺 类比：公共厕所的坑位

门口挂一块牌子"剩余 5 个坑"（state = 5）。acquire() 进去一个人牌子减 1，减到 0 后再来的人在门口排队（AQS 队列睡觉）；release() 出来一个人牌子加 1、叫醒门口排在最前的。与锁的本质区别：锁是"1 个坑"（独占），信号量是"N 个坑"（共享）——对应 AQS 的独占模式和共享模式（这就是 5.3 表格里 tryAcquireShared 存在的意义）。

RateLimitDemo.java限制同时 5 个爬虫在跑
Semaphore permits = new Semaphore(5);      // 5 个坑位

Runnable crawler = () -> {
    try {
        permits.acquire();                  // 占坑（没坑就排队睡）
        try {
            crawl(url);                     // 同时最多 5 个线程真正在爬
        } finally {
            permits.release();              // ★ 必须在 finally 里还坑（同 unlock）
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
};

注意：acquire/release 不要求同一线程配对（A 占坑 B 还坑也行）——这让它能做"资源池"（借出和归还发生在不同线程）。这也是它和锁的另一个本质区别。

CountDownLatch（倒计时门闩）：一次性倒数

🗺 类比：火箭发射倒计时

发射指挥（主线程）设定倒计时 N（state = N）。N 个检查组各完成自己的检查就 countDown() 一下（倒数 -1）；指挥 await() 站在发射按钮前等——倒数到 0 的那一刻，门打开（AQS 把队列里的等待者全叫醒）。用完即焚：这个门只能过一次，不能重置——第二个回合请再买一个新门。

ParallelGather.java8 个任务并行 + 主线程汇总
int N = 8;
CountDownLatch done = new CountDownLatch(N);
List<Future<Result>> futures = new ArrayList<>();

for (int i = 0; i < N; i++) {
    futures.add(pool.submit(() -> {
        try {
            return queryShard(i);          // 各查各的分片
        } finally {
            done.countDown();              // ★ 查完一个，倒数 -1（finally 保证异常也数）
        }
    }));
}

done.await();                               // 主线程：等 8 个全部倒数完
futures.forEach(f -> merge(f.get()));      // 汇总（此处 get 不会阻塞，任务必已完成）

为什么不用 Future.get() 轮流等？——其实可以（get 也是阻塞到完成），但 latch 的语义是"门"：可以多处、多线程一起 await 这扇门；而且 countDown 的角色不一定是"任务完成"——可以是"某个外部条件到位"。它是表达协调关系的工具，不是取结果的工具。

CyclicBarrier（循环栅栏）：人齐开会

🗺 类比：全员到齐才开会

10 个线程干各自的活，各自干到"检查点"就 await()——在会议室门口等。第 10 个人到达的瞬间，门开，全员一起进（还可指定一个"开会动作"，比如合并各人手里的结果）。Cyclic = 可循环：这一轮开完会，各自回去干活，下个检查点再聚——同一道栅栏用无数次。与 latch 的分工：latch 是"局外一个指挥等 N 个干活的"（角色不对称）；barrier 是"N 个平等的人互相等"（角色对称，缺一不可）。

CyclicBarrier barrier = new CyclicBarrier(10, () -> {
    mergePartialResults();                  // 第 10 个人到齐时，先执行这个"会议议程"
});

// 每个线程：
   partial = computeSegment();              // 各算各的
   barrier.await();                         // 检查点：等满 10 人
   useMerged(partial);                      // 人齐后一起进入下一阶段（下一轮还能再聚）

对比速记：
   Semaphore     谁等谁？没人等谁 —— 抢坑位     可重用 ✓   一对多放行
   CountDownLatch N 个干活的 → 1 个指挥         一次性 ✗   计数减到 0
   CyclicBarrier  N 个平等的人互相等             可重用 ✓   人到齐放行

9.3 死锁：并发世界的绝症

惨案现场：转账

TransferDeadlock.java两行代码酝酿一场死锁
void transfer(Account from, Account to, double amount) {
    synchronized (from) {          // 线程1：先锁 A 账户，再锁 B 账户
        synchronized (to) {        // 线程2：先锁 B 账户，再锁 A 账户
            from.debit(amount);    // 线程1 拿着 A 等 B
            to.credit(amount);     // 线程2 拿着 B 等 A —— 谁也不撒手，永远等下去
        }
    }
}
线程1 ──► 持有 A ──等待──► B ──┐
                              │   等待关系形成一个【环】
线程2 ──► 持有 B ──等待──► A ──┘
两个线程的线程状态都是 BLOCKED，CPU 占用 0%，系统看起来"没病"，
但这两个转账永远不会完成 —— 静悄悄的死亡，连日志都没有

死锁的四个必要条件（缺一不死）

条件大白话怎么破坏（预防手段）
① 互斥资源一次只能一人用（钥匙只有一把）资源本身性质，一般不破坏（能用无锁/读写锁绕开就绕开）
② 持有并等待拿着 A 不放，同时等 B一次性申请全部资源（转账前同时锁定两个账户，要么都拿到要么都不拿）
③ 不可剥夺别人不能抢走你手里的tryLock(超时) 拿不到就放手已持有的，重头再来（第五幕 RLock 的超时能力！）
④ 循环等待等待关系成环★全局有序加锁：所有线程都按固定顺序拿锁（比如按账户 id 从小到大）——环成了链

工程上最常用、成本最低的是破坏 ④：给所有锁对象排个全局次序（id 哈希、字典序），人人按序获取。上面的转账代码修一下：

TransferFixed.java两行修复
void transfer(Account from, Account to, double amount) {
    Account first  = from.id < to.id ? from : to;   // 全局顺序：永远先锁 id 小的
    Account second = from.id < to.id ? to : from;

    synchronized (first) {
        synchronized (second) {      // 所有线程加锁顺序一致 → 等待关系是链不是环
            from.debit(amount);
            to.credit(amount);
        }
    }
}

  • 活锁：都没死、都在动，但互相谦让卡住了——两人走廊相遇，同时左让、同时右让、同时再让……解法：谦让时加随机等待（以太网冲突退避同款思路）；

速查：遇到问题，武器怎么选

一个开关/标志，一写多读
  • volatile：stop 标志、配置热更新开关
一句"读-改-写"
  • 低竞争：AtomicInteger/AtomicReference
  • 高竞争纯计数：LongAdder
  • ABA 敏感：AtomicStampedReference
多步临界区（默认选择）
  • synchronized：写不坏、自动释放
  • 注意同锁（坑：this/新对象/两把锁）
要可中断/超时/公平/多条件
  • ReentrantLock + try-finally
  • 超时等待顺手治死锁（tryLock 放手重来）
任务提交与线程管理
  • 手动 new ThreadPoolExecutor（有界队列+命名+拒绝策略）
  • 反压首选 CallerRunsPolicy
多方协调
  • 限同时人数：Semaphore
  • 主线程等全完：CountDownLatch
  • 平等互等可循环：CyclicBarrier
人各一份的数据
  • ThreadLocal（上下文/SDF/事务连接）
  • 池化场景：finally 里 remove()
死锁了
  • 排查：jstack / Arthas thread -b
  • 预防：全局有序加锁 / tryLock 超时
生产者-消费者
  • 日常：ArrayBlockingQueue / LinkedBlockingQueue
  • 面试手写：wait+while+notifyAll

这本书和模块 6 怎么配合

两本书讲同一批知识，分工不同：6B（本书）建立"为什么"——每个武器背后的惨案、根因、边界，适合第一遍建立因果链；模块 6 是速查地图——按主题罗列的完整 API、参数表、对比矩阵（并发容器、Fork/Join、虚拟线程等本书没展开的主题都在那），适合面试前一夜快速过。建议路线：先通读本书把链子穿起来，再用模块 6 查漏补缺，最后对照它补齐并发容器（ConcurrentHashMap 的分段演进、CopyOnWriteArrayList）等本书一笔带过的主题。

📌 全书回收清单（检验你有没有真读通）

① volatile 的可见性和 CAS 的原子性，硬件根源是同一套机制（MESI 缓存行独占）——第一幕 ↔ 第四幕；② 锁的"进门看到最新"和 notify 后"醒来看到最新"，法源都是第三幕的锁规则（解锁 hb 后续加锁）；③ DCL 需要 volatile，是"有序性"惨案的最著名应用——第三幕；④ AQS 敢分两步"入队再挂起"不出竞态，靠 park 的"起床券"——第五幕 ↔ 第六幕；⑤ 线程池 Worker 没活干睡在队列上，就是第六幕的条件等待——第八幕；⑥ ThreadLocal 的泄漏链要靠模块 5 的弱引用知识才能读透——第七幕。如果这六条你都能自己复述出来，并发这一关，过了。
