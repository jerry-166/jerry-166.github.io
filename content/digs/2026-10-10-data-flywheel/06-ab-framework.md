## 模块五：AB 框架深挖

### Q12 `_current_experiment.set(group)` → `finally: reset(token)` 是什么

```python
token = _current_experiment.set(group)   # 贴标签；返回值 token = "set 之前的旧值"凭证
try:
    return await call_next(request)      # 请求处理（业务代码期间 get() 读到 group）
finally:
    _current_experiment.reset(token)     # 用凭证恢复旧值，无论请求成功还是抛异常
```

**为什么必须 reset**：不 reset 的话，这个标签就残留在执行上下文里。服务复用连接/上下文时，**下一个请求 `get()` 到上一个请求的标签**——用户 B 被错误分到用户 A 的实验组。这就是“幽灵 bug”：没有任何人改配置，但行为变了，排查极难。

**token 是什么**：`set()` 返回一个不透明对象，内部记录“set 之前的值”；`reset(token)` 把变量恢复到那个旧值——可以理解为 **git 的 commit hash / checkout**：每次 set 存档，reset 回滚到存档点。try/finally 配对是 contextvars 的文档级要求，OTel 的 `context.attach()/detach()` 是完全同构的 API。

### Q13 get_runtime 能读值，分流放它里面不也行吗

技术上**可行**，架构上**不该**——你的直觉对了一半，这个“能做但不该做”正是面试的分层论证点：

1. **依赖够不着**：get_runtime 被 reranker/agent 深层代码调用，那里**拿不到 user_id**（user_id 在 JWT 里，只有 HTTP 层解析了）。要拿到就得把 user_id 一路传参穿过所有调用链——0 侵入变 N 侵入。
2. **决策 vs 取值的频率错配**：分流是**一次性决策**（这个请求属于哪组），get_runtime 是**高频取值**（一个请求里被调几十次）。分流塞进 get_runtime = 每次 hash 重算（浪费）+ 决策点从 1 个散布成几十个（任何一处实现差异 → 同一请求前后读到不同组，自相矛盾）。
3. **单一事实源**：中间件决策一次 → 标签进 contextvar → 下游全部只读。决策点唯一，才可能推理“这个请求为什么在 candidate 组”。

一句话总结：**中间件管归属（一次），get_runtime 管取值（随处）**——能做和该做是两回事。

### Q15 白名单 / 灰度发布 / 实验分层——仔细讲

**问题的本质：并发运行多份配置的成本不一样**——这是整个设计的出发点：

| 变更类型 | 两组配置共存的成本 | 处理方式 |
|---|---|---|
| 标量（top_k/温度） | **零**（查表返回不同数字而已） | 进 AB（进程内实验） |
| prompt 版本 | ≈零（DB 里两行模板） | 进 AB |
| 组件类（RERANKER_TYPE / EMBEDDING_MODEL） | **一套配置 = 一个加载好的模型实例**（BGE reranker ~568M 参数），baseline + candidate 两套共存 = 内存翻倍，15.6GB 笔记本直接爆 | 灰度发布（多实例实验） |

**灰度发布（多实例）怎么干**：组件类变更起**两个服务进程**——旧配置实例 + 新配置实例，网关按比例路由流量（蓝绿/金丝雀）。内存成本由多进程分担（每进程一套模型），代价是部署复杂度（多实例、网关路由、监控双份）。

**白名单的执行机制**：`experiment_configs` 表写入时校验 key 是否在 AB-eligible 白名单，不在则**拒绝写入并提示“该参数需走灰度发布”**——把“什么能进实验”做成准入检查，不靠人记规矩。

**实验分层思想（业界正名）**：白名单/黑名单是它的简化版。真正的分层实验（Statsig/LaunchDarkly/字节实验平台的标准设计）解决的问题是**多实验并行时的互相污染**：

```
Layer 1（检索参数层）：实验 A（top_k 10 vs 20）—— 层内互斥：用户只能进 A 的一组
Layer 2（生成参数层）：实验 B（温度 0.3 vs 0.7）—— 层间正交：A 的每组用户在 B 里均匀分布
```

**正交**的保证：两层用独立的 hash 盐值分流，Layer1 分组与 Layer2 分组统计无关——否则两个实验同时改 top_k，效果互相纠缠，谁也归因不了。我们 spec 里“**一个 experiment 只改一类变量**”（§十：调参/重训不同时变）就是单层版的同一纪律——**归因能力优先于实验吞吐**。

### Q16 fail-back：人工处理还是先降级再人工

**顺序：先自动止血，再人工根治**——机器做快速机械动作，人做慢速判断：

```
candidate 异常率 > 5%
   → 自动标 degraded：该实验的请求自动 fallback 走 baseline 配置（用户无感）—— 止血，秒级
   → 连续 N 个周期仍 degraded
   → 自动 rolled_back：从节目单摘除 candidate + 告警 —— 稳定劣化才回滚
   → 人工醒来处理：分析是配置值问题还是代码 bug，修好重新发起实验
```

**为什么要“连续 N 个周期”才回滚**（而不是一次就回滚）：偶发抖动（网络/依赖抖动）也会触发误判——一次就回滚 = 实验频繁被打断；连续 N 个周期是**多数投票防毛刺**，只有稳定劣化才值得回滚。

**为什么 degraded 后必须有 human in the loop**：自动系统只能执行预案（回退），预案之外的决策——“这个 candidate 是修还是弃？根因是什么？”——必须人做。业界完全同构：**K8s liveness probe 自动重启（止血）+ 告警人介入（根治）**、熔断器半开探测自动恢复、SRE 的 error budget 政策——自动化和人工的边界就是“预案内 vs 预案外”。

### Q18 三角色换讲法

广播电台版（比节目单版更直白）：

```
experiment_overrides 表  = 电台节目表：写清"每个频道放什么"
                           加频道 = 节目表加一行，收音机不用动
HTTP 中间件             = 进门发的耳机+自动调台：观众(请求)进门被分到某频道，
                           耳机上贴好频道号(contextvar)——它不管内容
get_runtime             = 耳机本身：业务代码随手按下收听键，
                           自动播放"你被分到的频道"——业务代码不用知道自己几频道
```

三行工程总结：**表存差异（数据）、中间件定归属（一次决策）、get_runtime 取值（随处读取）**——三者各干一件事，加实验组只动表。if-else 版 = 收音机焊死频道，每加频道拆机重焊。

## 3. 幽灵 bug（contextvar 泄漏）真出现了怎么排查

给一个排查剧本（面试可以直接讲）：

**第 1 步·症状识别**：行为与配置“错位”——明明 candidate 只分流 20% 用户，但日志里 baseline 用户打出了 candidate 的行为；且**同一用户稳定复现**（泄漏是确定性的，不是随机的——这是它和“偶发 bug”的区分特征）。

**第 2 步·证据链**（这就是 `[exp=]` 日志前缀铁律的用途）：拿日志里每个请求的实际组标签，**重放分流函数** `hash(user_id) % 100 < split` 算它“应该在”的组——两者错位的请求 = 泄漏受害者。

**第 3 步·定位泄漏源**：用 request_id 串审计事件，看泄漏首次出现在哪个请求之后——contextvar 泄漏是“从某个没 reset 的请求开始，污染后续复用同一上下文的请求”，找到第一个污染者就锁定了肇事代码路径。

**第 4 步·代码走查**：`grep '\.set('` 全部调用点，检查是否都有 `try/finally: reset(token)` 配对——通常肇事者就是一个漏了 finally 的中间件。

**第 5 步·修复验证**：单元测试模拟上下文复用（两个“请求”共用 context 副本），断言第二个请求读到 default。

**预防优于排查**（写进 CI）：① reset 用 `reset(token)` 而非 `set("baseline")`——token 恢复到“set 之前的状态”，嵌套 set 场景才不会恢复错层；② 泄漏测试进回归集。Java 同学排查 ThreadLocal 泄漏是同款剧本（dump 线程的 ThreadLocalMap 找脏数据）——**两个生态、同一个坑、同一套排查法**。

## 4. Q13 三个疑问逐个确认

**疑问 1：中间件分流后，结果存 contextvar，get_runtime 取的就是 contextvar 里的内容？**

**完全正确**。数据流是：

```
中间件（每请求一次）：算出 group → _current_experiment.set(group)   ← 写
业务代码（每请求几十次）：get_runtime() → 内部 _current_experiment.get() → 拿 group 查表 → 返回该组的值   ← 读
```

contextvar 就是“**请求级全局变量**”：同一请求内处处可读，请求之间互相隔离。

**疑问 2：get_runtime 为什么每次都要哈希重算？**

这是我上轮表述造成的误解，澄清：**现在的正确设计里 get_runtime 不做任何哈希**——它只做 `contextvar.get()` + dict 查表，纳秒级。我说的“每次重算 hash”是**反面假设**：“如果把分流塞进 get_runtime 会怎样”——那样它每次都得从 user_id 重新算 `hash(user_id)%100`（因为 get_runtime 是无状态函数，不记得上次算过），一个请求重复算几十次。

**疑问 3：决策点散布的理解**

你的理解方向对，精确化一下：“决策点”= **执行“hash → 选组”这个计算的位置**。两种放法的对比：

- **中间件方案**：这个计算只发生 **1 处**，算一次，结果写进 contextvar；几十个 get_runtime 调用点只是**读结果**。
- **塞 get_runtime 方案**：几十个调用点**各自重算**“我属于哪组”——不是“你选择信任哪个节点”，而是**必须保证几十个节点算出完全一致的结果**。任何一处实现差异或 bug → 同一请求 top_k 用了 candidate 的 20、温度却用了 baseline 的 0.7——**请求内部自相矛盾**，而且这种 bug 极难发现（单看每个值都是“合法”的）。

你说的“中间件只有一个点放 user_id”这个理解可以保留，一句话记法：**分流算一次（中间件），取值读N次（get_runtime）**。

## 6. 分层实验与正交——换个讲法，用数字例子

**先说它解决什么问题**：两个实验同时跑——A 实验（top_k 10→20）、B 实验（温度 0.7→0.3）。如果同一批用户**同时**被 A 和 B 影响，A 看到的效果里混着 B 的功劳——**归因失败**。

**不分层的坏情况**：A、B 的分流如果撞在一起（A 实验组恰好全是 B 实验组的人）→ A 组的提升说不清是谁的。

**分层 + 正交的做法**——每个用户过**两道独立的闸**：

```
第一道闸（Layer 1，检索层）：hash(u + 盐1) % 100 < 50 ? A实验组 : A对照组
第二道闸（Layer 2，生成层）：hash(u + 盐2) % 100 < 50 ? B实验组 : B对照组

关键就在：盐1 ≠ 盐2 → 两次 hash 的"随机源"不同 → 统计独立

以 100 个用户为例：
A实验组 50 人 ┐
              ├─ 这 50 人过第二道闸，B实验组 ≈ 25 人，B对照组 ≈ 25 人
A对照组 50 人 ┘   同样 ≈ 25 / 25
→ B 的效果在 A 的两组里各占一半 → 对比时相互抵消
→ A 两组的差异 = 纯 A 的效果 ✓（归因干净）
```

**“正交”翻译成大白话**：两道闸各分各的，互不打架——用户在第一道被分去哪组，跟他第二道被分去哪组**毫无关系**（数学上叫统计独立）。它就是**控制变量法的工业化版本**：每层只允许变一个因子，层与层之间保证“其他条件统计相同”。统计学出身的面试官会认这个说法：RCT（随机对照试验）里的分层随机化。

**我们 spec 为什么用不上正交但纪律同源**：我们是**单层**——一次只跑一个实验，且一个 experiment 只改一类变量（§十：调参/重训不同时变）。只有一个维度时根本不需要第二道闸，但纪律是同一条：**任何对比的两组之间，除了目标变量，其他一切统计相同**。白名单就是这条纪律的准入检查器。
