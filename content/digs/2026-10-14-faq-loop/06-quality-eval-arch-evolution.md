### ⑧ 快照不追上游 → pull/rebase 怎么设计？

对，设计文档风险区原话就是“若未来出现‘上游修正需同步下游’需求，再加 rebase 能力”。展开成可落地的方案，核心是**给克隆断链补上“血缘追踪”**：

```
现状：clone 时 faq_map 重映射 id，但新行不带 upstream_faq_id → 血缘断了，无从 diff
改造：faq 表加 upstream_faq_id（克隆时写入源 faq id）+ upstream_base_answer（fork 时的快照）
     → pull 的三方合并素材齐了
```

**pull 合并算法（git 三方 diff 的思想，三方 = 上游基线 / 上游现值 / 我的现值）**：

| 情况 | 判定 | 动作 |
|---|---|---|
| 上游改了，我没改 | base≠upstream，mine=base | 快进采纳（fast-forward） |
| 上游改了，我也改了 | base≠upstream，mine≠base | **冲突**——UI 展示双栏 diff，我人工选 |
| 上游改了，我删了 | mine=tombstone | 尊重删除（我的 fork 我做主） |
| 上游没改 | upstream=base | 无事发生 |

**“保证自己的不被覆盖”的实现哲学**：上游变更永远以“建议”形态出现——类似 dependabot 给你提 PR，accept 与否 fork 主人说了算。默认策略 ours-first，自动快进只发生在“我没动过”的条目上（这条本来就没有“我的意志”可保护）。**更务实的轻量替代**：连自动合并都不做，只做“上游有 N 条更新”徽标 + 逐条 diff 查看 + cherry-pick 式单条采纳——FAQ 条目粒度小、人审成本低，逐条选比三方合并算法好维护得多。面试时先讲轻方案、再讲重方案，体现“按复杂度递进交付”的工程判断。

### ⑬ PR 超期提醒：cron vs websocket？

你的二分法对，但结论是**不是二选一，而是分工**——先把一个关键约束看清：**“超期”是时间驱动的事件，检测它本质上必须有个定时器**（没有任何用户动作会触发“这条 PR 满 72 小时了”这个信号）。所以：

| 维度 | Cron 定时扫描 | WebSocket/SSE 推送 |
|---|---|---|
| 职责 | **产生**通知事件（扫超期 PR → 写 notification 表） | **投递**已产生的通知到在线用户 |
| 实时性 | 差（粒度=扫描间隔，如每小时） | 好（秒级到浏览器） |
| 状态管理 | 无状态，重启即恢复 | 要管长连接池、心跳、断线重连、多实例下连接路由（sticky session 或 Redis pub/sub 总线） |
| 用户不在线 | 无所谓（通知已落库，下次登录看） | 必须有落库兜底（推送不能替代持久化通知） |
| 实现成本 | 极低（APScheduler 循环） | 高一个数量级 |
| 复用现状 | 项目已有 APScheduler 类基建思路 | 项目已有 SSE（agent 流式就是 SSE 管道，可复用） |

**混合架构（业界标准形态）**：`Cron 检测超期 → 落 notification 表 → 前端轮询未读数 / SSE 推增量`。cron 管“事件诞生”，SSE 管“事件到达”，落库管“事件不丢”。项目特殊性加分项：SSE 管道是现成的（agent 对话流式就在用），所以增量推送这层不用新建长连接体系——这也是“复用已有基建”的叙事点。

### ⑭ 蒸馏质量自动化评估怎么做？

现状诚实：RAGAS 评的是检索链路（faithfulness / answer relevancy / context precision & recall 评“检索+生成”全链路），蒸馏质量靠“LLM 蒸馏时对照 chunk 核对 + 库主人工 demote 兜底”。自动化分四层，按投入递进：

**1. 蒸馏即时 QA（ingestion-time，性价比最高）**
升格那一刻多跑一次 LLM 判断：`faithfulness(蒸馏答案, 补全原文+chunk 证据)`——蒸馏答案里的每个关键事实能否在原文/证据里找到出处？低于阈值 → 不自动升格，转 pending 人工确认。成本：升格是低频事件，每次多一次调用可忽略。**本质是把“人工 demote 兜底”从事后提到事前**。
**2. RAGAS 直接复用（机制现成）**
RAGAS 的指标定义是通用的——faithfulness = 答案是否被 context 支持。把 `(question, distilled_answer, [chunk 上下文])` 塞进 RAGAS 的评估管道就是现成的蒸馏 QA。项目已有 RAGAS 基建（Stage 7 质量评估页），扩一个评估对象类型即可。
**3. 在线负反馈环（usage-time，最“自进化”的一层）**
直返后的用户行为就是质量信号：**追问率**（直返后用户换个问法重问 = 答案没解决问题）、点赞/点踩、复制事件。负信号累计超阈值 → 自动 demote 或标记复审。妙处在于它和热度模型**同源反向**：热度是正信号（被需要几次），追问率是负信号（被打脸几次）——**同一个“使用产生数据”的哲学，一正一负构成完整的质量画像**。这也是这条简历线“数据洞察驱动迭代”的终极形态。
**4. 回归集（防 prompt 改动引入回退）**
人工标注 20-50 对金标准（问题 + 理想蒸馏答案），蒸馏 prompt/模型一变就跑回归对比——promptfoo / OpenAI evals 的思路，LLM 应用的 CI。防的是“改了 prompt 修好 A 场景，悄悄弄坏了 B 场景”这类静默回退。

**已知坑（面试加分）**：LLM-as-judge 有系统性偏差——打分漂移（同一样本不同轮次分值波动）、位置偏置、自我偏好（judge 偏爱和自己同款的文风）。缓解：rubric 锚定（给分维度写死）、多 judge 投票、固定 judge 模型版本。

## ④ 你的“蒸馏 QA 低分 → WebSocket 推前端，有空再处理”——对，这就是标准模式

你独立想到了 **human-in-the-loop（HITL）** 的完整形态：机器处理高置信度（分数达标自动升格），**低置信度样本路由给人工**（低分不升格 → 生成审核任务 → 异步通知 → 库主有空再处理）。三个点确认 + 升华：

- **“有空再处理”= 异步非阻塞**：提问者不被等待（candidate 继续累计热度，只是 active 生效延后），闭环不卡死——人工介入是旁路不是闸口。
- **通知投递**就是你上一轮问的 cron/SSE 混合架构：审核任务落库（不丢）→ SSE 推徽标（在线即达）。
- 业界同构：内容审核系统（机器初审+人工复审队列）、欺诈检测人工复核、**主动学习**（active learning——模型不确定的样本优先给人标，人标的又反哺模型）。你这个设计等于给蒸馏质量加了“主动学习”的入口，面试可以这么拔高。

## ⑤ 回归集（第 4 点）详解——先给你个意外：你项目里已经做过一次

**问题场景**：蒸馏 prompt 是一段自然语言。某天你想改进它（加一条“保留英文术语”），改完怎么确认它没把别的场景搞坏？prompt 是“用自然语言写的代码”——**改一行影响面不可见，没有编译器和类型系统兜底**，唯一安全网就是评估集。

**做法四步**（软件测试的直接类比）：

```
1. 攒金标准集（20-50 对）         = 单元测试的断言
   每对 = 输入（补全原文 + 上下文）→ 期望输出（人工认可的理想蒸馏答案）
2. prompt 一变，全量样本跑新 prompt  = 跑测试套件（CI）
3. LLM-as-judge 对比新结果 vs 期望   = 断言通过/失败
4. 某样本分数显著下降              = 测试红了 → 回退/调整，不许合并
```

promptfoo / OpenAI evals 就是把这个流程工具化的开源项目：yaml 声明用例和断言，一条 CLI 命令跑分出报告。

**关键联系（这是你的独有弹药）**：Stage 2 的 **03§7 质量对照实验**——A（旧合并 prompt）/ B（CombinedEnhancer 迁移）/ C（独立精简 prompt）三组，LLM judge 打分，C 组子问题相关性 -0.50 超过 0.3 门槛 → **判不通过 → 按设计走回退**（单开委托 A 的合并 prompt）。**这就是一次手工执行的回归测试**：金标准=A 组行为，被测=B/C，断言=差异 ≤0.3，不达标=回退。缺口只是“制度化”：当时是一次性实验，回归集是把它固化成**每次 prompt/模型变更都自动跑**的流程。面试讲法：“我在 Stage 2 已经用一次性版本验证过这套方法论（还顺带发现了 judge 呈现偏置和跨轮漂移），制度化成 CI 是水到渠成的下一步。”
