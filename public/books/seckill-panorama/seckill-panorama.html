一层层砍到「只有库存数量」

秒杀的本质不是「扛住所有请求」，而是一道流量过滤题：越上游拦截成本越低，越靠近数据库的请求越少。库存校验前置到 Redis 单线程原子完成，数据库只通过 MQ 异步承接最终成交的那几百几千笔，其余全部靠缓存、限流和快速失败消化。

01

七层全景架构：每层只做一件事

LAYERED DEFENSE

按请求经过的顺序排开。核心心法：越靠前的拦截越便宜（缓存命中是内存级，限流是计数器级），越靠后的手段越重。

L1 · CLIENT用户端 / 前端
  • 按钮置灰 + 防抖：点击后立即置灰、倒计时结束才恢复，从交互上消灭重复提交
  • 验证码 / 答题 / 滑块：一是防脚本，二是人为拉长耗时，把 0 秒的洪峰摊成几秒的波峰（削峰）
  • 秒杀接口地址动态下发：活动开始前拿不到真实 path，开始时才请求带签名、时效、nonce 的一次性地址，防脚本提前刷
  • 页面 token：进入秒杀页发一次性 token，下单时核销，做接口幂等
  • 静态资源全量 CDN：页面、JS、图片、商品详情静态化版本全部边缘缓存
  • 时间以服务端为准：开始/结束时间由服务端下发（NTP 校时），不信客户端时钟
L2 · EDGECDN + Nginx 集群
  • CDN 缓存：商品详情、图片、静态化页面就近返回，回源率压到极低
  • limit_req 漏桶限流：按 IP + URI 限制每秒请求，平滑突发
  • limit_conn 连接数控制：防止单 IP 占用大量连接
  • 黑白名单 / 地域封禁：恶意 IP、机房 IP 段直接拒绝
  • OpenResty + Lua 分布式限流：Nginx 本地计数器是单机口径，全局配额要放 Redis 用 Lua 统一扣；还可直接读售罄标记，在边缘就返回售罄
  • 动态详情页静态化：库存、价格等动态片段用 ESI / 异步接口，外壳静态化
L3 · GATEWAY网关 / 风控
  • Sentinel 令牌桶/限流：按接口、按服务实例限流，支持热点参数限流（按商品维度）
  • 排队令牌（放量闸）：只放行「库存数 × 小系数」的请求进入交易，其余进排队页或直接返回稍后再试（12306 模式）
  • 设备指纹 + 风控评分：一机多号、群控、IP 画像、行为异常，命中规则拒绝或加验
  • 统一鉴权 / 签名校验：登录态、接口签名、重放攻击校验
  • 线程池隔离：下单接口与普通接口隔离，避免互相拖垮
  • 熔断降级开关：配置中心（Nacos/Apollo）下发预案开关，秒级生效
L4 · ELIGIBILITY业务资格层
  • 预约名单：活动前预约，名单提前加载到 Redis；预约制本身就是一次提前削峰和流量预测
  • VIP / 等级通道：按用户等级分流放量，业务规则前置到内存查询
  • 一人一单（第一层）：Redis Set 记录已购用户，Lua 内 SADD 判重（详见 L5）
  • 布隆过滤器：活动商品 ID、合法活动 ID 预热进 Bloom，非法 ID 请求直接拦截，防缓存穿透
  • 多级缓存：Nginx 本地缓存 → 应用本地缓存（Caffeine，售罄布尔标记、商品详情）→ Redis 分布式缓存
  • 注意缓存边界：库存这类强动态数据不进 CDN/本地缓存；本地只缓存「售罄与否」这种只读布尔态
L5 · CORE (SYNC)核心交易 · 同步通道
  • 库存预热：活动开始前把库存按桶写入 Redis，用户 Set、活动配置全部就位，不临时回源
  • Redis Lua 原子脚本：售罄判断 → 重复判断 → 扣库存 → 登记已购，单脚本一次执行完，单线程天然原子
  • 本地售罄标记：桶售罄 / 商品售罄写入 Caffeine，后续请求不打 Redis 直接失败
  • 库存分桶：单 Key 拆成 N 个桶 Key 分散到 Cluster 不同节点，抗单节点热点（见 04）
  • 写本地消息表：扣减成功后本地事务写订单（待确认）+ 消息表，作为异步通道的可靠凭证
  • 同步通道只做判定：不碰 MySQL、不做复杂逻辑，RT 压到毫秒级
L6 · ASYNC异步通道 · MQ
  • 消息投递：后台任务扫描消息表投递（at-least-once），或直接用 RocketMQ 事务消息
  • 消费幂等：订单号唯一索引 / 防重表，重复消息只生效一次
  • 失败重试：消费失败按指数退避自动重试（RocketMQ 默认 16 次）
  • 死信队列 DLQ：超过重试上限进死信，告警后人工/补偿任务介入
  • 批量合并：库存扣减按商品攒批（N 条或 T 毫秒），N 次 -1 合并成一次 -N，大幅减少 DB 行锁次数
  • 延迟消息：下单即发超时关单延迟消息，到点检查支付状态
L7 · DATA数据层
  • 订单表：(用户, 商品, 活动) 唯一索引——一人一单的数据库兜底
  • 库存表条件更新：
    UPDATE stock SET num=num-1 WHERE id=? AND num>0，靠条件防超卖
  • 垂直分表：商品详情（大文本）与库存（热点小行）拆开，避免大字段拖累热点行更新
  • 水平分表：订单表按用户 ID hash 分库分表；库存表行数少，热点靠 Redis 分桶解决
  • Redis Cluster：每分片一主多从 + 哨兵式故障转移，AOF everysec + RDB
  • 对账：消息表 / 订单 / 库存三方核对，活动结束收敛到最终一致
横切关注点（贯穿七层，不占层级） 全链路监控漏斗（各层 QPS、拦截率、RT、MQ 堆积、Redis 命中率）、全链路压测（容量按 80% 水位规划）、预案开关与演练、链路追踪。
02

核心下单链路时序：同步判定，异步落库

ORDER SEQUENCE

这是整个系统最关键的一张图。同步链路只到 Redis + 本地消息表，MySQL 完全在异步链路。下方同时标注三个「数据可能不一致」的窗口以及各自的兜底手段。

窗口①Redis 已扣、消息表未写

服务在这两步之间宕机/事务回滚：Redis 扣了，但订单根本没创建。用户侧算本次下单失败（可重试）。注意这里没有订单可关，超时关单不适用，只能靠定时对账：活动结束后按「初始库存 − 有效订单数」算应有剩余，Redis 少掉的那部分即悬挂库存，按总量回补（精确不到人）。用户重试时被「已购标记」挡住的话，查无订单就清除标记、回补库存后放行。

窗口②消息表已写、MQ 未投递

本地事务已提交但进程崩溃：后台扫描任务捞出「待发送」消息重投，at-least-once，重复由消费端幂等吃掉。

窗口③MQ 投递后、消费失败

自动重试（指数退避）→ 超过阈值进死信队列 → 告警 + 补偿任务。消息表是最终可追溯的凭证。

Lua 脚本为什么不会超卖

Redis 单线程执行脚本，期间不会插入其他命令。「判断库存 + DECR + SADD」在一个脚本里就等价于加了一把全局锁，不需要应用层自己加锁。

客户端 → 下单服务
① 活动开始后请求动态秒杀地址（带签名、时效）

② 下发一次性 path + 页面 token（防脚本提前刷、防重复提交）

三个窗口的兜底① 扣减后未写库：订单未创建、无单可关，靠定时对账发现悬挂库存并按总量回补，用户侧算失败可重试；② 已写未投递：扫表任务重投；③ 消费失败：自动重试 → 死信。

Lua 脚本示例（单桶；同一桶的库存 Key 与已购 Set 用 hash tag 钉在同一 slot）

-- KEYS[1] = stock:{g1:b3}  桶库存    KEYS[2] = bought:{g1:b3} 已购用户集合
-- ARGV[1] = userId                                           
local stock = tonumber(redis.call('GET', KEYS[1]) or 0)
if stock <= 0 then return 0 end                          -- 0 = 本桶售罄
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 2 end -- 2 = 重复下单
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                     -- 1 = 抢占成功

单线程保证 GET→DECR 之间不会穿插别的请求，所以脚本里不需要二次判断，也不需要分布式锁。桶号要随订单落库，超时回补时知道补回哪个桶。

03

Redis 与落库怎么一致：三方案对比

CONSISTENCY

你的问题是「Redis 和本地消息表要不要同一事务、要不要上 Seata」。结论先行：秒杀通道故意不用强一致分布式事务，用「可靠消息 + 幂等 + 对账 + 回补」做最终一致。

方案机制优点代价 / 问题适用场景
本地消息表
你目前的方案		 本地事务写订单+消息表；后台扫表投递 MQ；消费端幂等 不依赖特殊 MQ；消息有表可查、可重放、可对账 多一次 insert；扫表有秒级延迟；需要自己维护投递任务 通用，RabbitMQ/Kafka 都能做；消息表同时充当事件审计源
RocketMQ 事务消息 发 half 消息（暂不投递）→ 执行本地事务（扣 Redis/写订单）→ commit/rollback；MQ 长时间未收到确认会回查本地状态 无需扫表，延迟低；Broker 帮你做消息可靠性 绑定 RocketMQ；仍需实现本地事务回查接口 阿里系秒杀的标准做法，本质是本地消息表的「Broker 托管版」
Seata 分布式事务 AT：各分支操作 DB 时生成 undo log，TC 协调全局提交/回滚；TCC：Try/Confirm/Cancel 三段业务补偿 强一致 / 接近强一致，业务无感知（AT） AT 不支持 Redis 分支（靠关系库 undo log）；2PC 同步阻塞、持全局锁，峰值吞吐崩塌 支付—订单—库存—账户跨库强一致、非峰值链路；不用于秒杀同步通道
关键纠正：Seata 管不了这条链路 ① Seata AT 模式的分支锁与 undo log 建立在关系型数据库之上，Redis 没有标准的 RM 实现，「Redis 扣库存 + 写消息表」无法用 AT 包成一个全局事务；② 即使硬上 TCC，2PC 同步等待、全局锁持有的模式会让每笔下单串行化，Redis 前置削峰的意义就没了。秒杀的设计哲学是「同步只判定、异步去落库、对账来收敛」，最终一致是主动选择而非妥协。

RocketMQ 事务消息：四步看懂（为什么不需要扫表）

① 发半消息
生产者把消息发给 Broker，Broker 先存起来，消费者完全看不到（half message）
→
② 执行本地事务
生产者去扣 Redis、写订单/消息表（本地事务）
→
③ 成功 Commit
Broker 把半消息变为正常消息，投递给消费者；失败则 Rollback 删除
④ 回查机制（兜底）：如果生产者在第 ②③ 步之间宕机、没来得及发 Commit/Rollback，Broker 等一段时间后会主动回查：「这个事务到底成没成？」生产者查询本地订单/消息表后回答提交或回滚。所以消息不会丢失，也不需要自己写扫表任务。

打个比方：你把信交给邮局，但要求「先别发，等我电话」。本地事办妥了打电话让发（Commit），办不成就销毁（Rollback）；万一你电话断线了，邮局会主动打来问这封信到底发不发（回查）。本地消息表 = 自己雇人逐封检查「哪些信还没打电话」；RocketMQ 事务消息 = 邮局帮你做这件事，所以省掉扫表。

单体架构下落库失败怎么办

  • 消息表写成功后，消费者落库失败 → MQ 重试 + 死信，与单体/微服务无关，这是消费端的事
  • 消息表本身写失败（Redis 已扣）→ 本地事务回滚，Redis 扣减靠超时回补/对账修复
  • 单体也可同步落库，但峰值流量会直接打 DB，主流做法仍是异步

Seata 什么时候才该出现

  • 支付成功 → 订单状态流转 → 库存实扣 → 积分/余额变更，跨多个库且不能错账
  • 清结算、退款这类对一致性要求高于吞吐的链路
  • TCC 可用于库存「预占—确认—释放」，但要自己实现三段接口、侵入性大
04

Redis Cluster 与库存分桶：纠正两个理解偏差

SHARDING

偏差 1「Cluster 已经取代主从了」

Cluster 的结构是 分片 × 主从：16384 个 hash slot 切成若干组分给多个 master，每个 master 依然带 1~2 个 slave 做异步复制，master 挂了由集群投票把 slave 提升为新 master。Cluster 解决的是「容量与写吞吐水平扩展」，主从复制解决的是「高可用与读扩展」，两者是叠加关系。

偏差 2「后端实例负责哪些哈希槽」

槽由 Redis 节点负责，不是后端实例。后端用 smart client（Lettuce/Jedis Cluster）缓存 slot→节点映射，按 CRC16(key) mod 16384 直连目标节点；节点扩容/迁移时返回 MOVED/ASK 重定向。后端实例与槽之间没有固定归属。

为什么要分桶：单 Key 库存就是最大的热点

单 Key stock:g1 无论集群有多少节点，永远落在一个 slot、一个节点上；单线程模型让它成为写串行点，单节点 QPS 有上限（几万级），大促不够。分桶把一个 Key 拆成 N 个 Key，分散到不同节点并行扣减。

关于你说的「聚合重发保证公平」 公平性主要靠选桶策略（用户 hash 均匀分布、售罄借桶），而不是事后聚合。聚合的真正用途是：① 活动结束对账，总销量 = 各桶之和；② 把各桶剩余库存回收/汇总；③ 给 DB 做批量库存同步。不追求绝对公平时，桶间不均衡只影响「某桶先空」，借桶机制处理即可。
05

热点 Key 治理与缓存三兄弟

HOTKEY & CACHE
先纠正：库存 Key 恰恰是头号热点 Key 单线程模型保证了「正确性」，但不等于「没有热点问题」——所有请求打一个 Key，CPU 和网卡全部压在一个节点上，无法水平扩展。单线程是热点的瓶颈，而不是热点的免责牌。库存热点靠分桶（04），其余热点靠下面的手段。

热点发现（事前 + 事中）

  • 事前：运营预估爆款，提前分桶、预热、扩容
  • 事中：Redis hotkeys（LFU 统计）、proxy 层（Codis/Tair）统计、客户端 SDK 上报
  • 监控 QPS 突增自动识别

读热点下沉

  • 商品详情、活动配置、售罄布尔态放 Caffeine 本地缓存
  • 展示用「剩余库存」读从库/副本，允许秒级延迟（不影响扣减）
  • singleflight：同一商品并发请求只放 1 个回源，其余共享结果

写热点打散

  • 库存分桶（核心手段，见 04）
  • 写请求排队令牌，控制进入 Redis 的速率
  • 商业版可用 Tair 的热点 Key 本地缓存/读写增强

查不存在的 Key		 攻击者用不存在的商品 ID / 活动 ID 猛刷，Redis 没有，全部打到 DB ① 布隆过滤器：合法活动/商品 ID 预热，不存在直接拦截；② 空值缓存（短 TTL，如 30s）；③ 入参合法性校验，非法请求在网关就拒 你说的空对象方案有效，但布隆过滤器是第一道，更省内存
雪崩
大面积同时失效		 ① 大量 Key TTL 集中在同一时刻过期；② Redis 集群整体宕机，请求全落 DB ① TTL = 基础值 + 随机抖动；② 核心 Key 活动期内不设 TTL（预热写入）；③ 集群高可用 + 熔断降级，Redis 挂了绝不放流量去 DB，直接返回火爆页/排队页 「库存 Key 不设 TTL 所以雪崩不用担心」只覆盖了一半——宕机型雪崩仍要靠高可用和熔断
击穿
单个热点 Key 过期瞬间		 热点商品详情 Key 过期瞬间，上万并发同时回源 DB ① 互斥锁（分布式锁，只放一个线程重建缓存）；② 逻辑过期（缓存不设物理 TTL，值内带过期时间，过期后异步刷新、旧值继续返回）；③ 秒杀期库存 Key 不 TTL、详情静态化，天然规避 你的判断正确：秒杀期库存 Key 与活动生命周期一致，活动期内不过期/不修改，击穿风险极低；商品详情配合静态化即可

兜底治理：超时关单、对账、降级、熔断与恢复

SAFETY NET

6.1 超时关单与库存回补

主方案：延迟消息

  • 下单时发一条延迟消息（RocketMQ 延迟级别 / RabbitMQ TTL+死信 / Kafka 时间轮）
  • 到点检查订单：已支付则忽略；未支付则关单
  • 关单必须幂等：UPDATE orders SET status='closed' WHERE id=? AND status='unpaid'，影响行数=1 才执行回补
  • 关单前再查一次渠道支付状态，防止「用户正在支付、关单与支付并发」

回补动作（Redis + MySQL 都要补）

  • Redis：Lua 把库存补回原桶（桶号在订单里），SREM 移除已购标记，用户可重新下单
  • MySQL：必须补。两本账是异步推进的——消费者可能已经扣了 DB 库存，关单就要补；若还没扣，消费端看到订单已关闭就不再扣。两种时序都覆盖，按订单状态幂等、只补一次
  • 订单不删除：只把状态从 unpaid 改为 closed。删了就无法对账、无法处理迟到的支付回调，也没有售后凭证
兜底链路 定时任务扫描「未支付且超时」的订单，防止延迟消息丢失（Redis 过期监听不可靠，不做主力）。注意：窗口① 那种订单未创建的情况不在此列——它没有订单可关，靠 6.2 对账回补。

6.2 数据对账：谁是权威源？

要分阶段看，不能一概而论「以 Redis 为主」：

活动进行中 Redis 领先

Redis 是扣减入口，库存数据「领先」DB；DB 通过 MQ 异步追赶。此时修 DB 以 Redis 为准没问题。

活动结束后 有效订单为准

库存的真实去向是有效订单（已支付 + 待支付未超时）。公式：
初始库存 = 有效订单数 + 剩余库存；三方（消息表扣减流水、订单表、DB 库存）核对。

你问的两个「可不可以」，答案都可以 ① 本地消息表可以对账：只要消息表记录了完整明细（商品、桶号、用户、订单号、事件类型、时间，含扣减与回补事件），它就是事件流水（event log），逐条回放即可核对 Redis 与 DB。
② 可以用它同步备用 Redis：备用集群从消息表重放扣减/回补事件，即可重建一致状态；这正是事件溯源（Event Sourcing）思路。Redis 全挂重建时，最简单的公式是「按桶剩余 = 初始库存 − 有效订单」，消息表和订单表都能算出来。

追问：Redis 已经防了超卖，为什么 DB 还要再防一次？

不是两套重复系统，而是「准入闸门」与「账本」的分工：Redis 负责在洪峰里快速判定资格，DB 是最终记账处。下面这些路径都会绕过 Redis 直接碰到 DB，DB 必须自己守住底线：

DB 可能被绕过 Redis 的路径碰到

  • MQ 是 at-least-once，重复消息、消费重试可能重复扣减
  • 消费乱序、批量合并扣减出错
  • Redis 主从切换/故障重建后，库存靠消息重放修复
  • 人工补偿、对账修复任务直接执行 SQL

条件更新就是最后防线

  • UPDATE stock SET num=num-1 WHERE id=? AND num>0 不依赖任何上游，执行失败即扣减失败，账本不可能为负
  • 成本几乎为零：一条带条件的 UPDATE，不增加额外访问
  • 对账时也以 DB 账本为准，Redis 只是加速层

追问：订单表要不要水平分表？（分表不是为锁）

分表解决的是数据量，不是锁竞争

  • 单场秒杀几千单，当然不用分表；但订单表是全平台业务日积月累，年增数亿行，单表超过 1000~2000 万行经验拐点后，B+ 树高度、Buffer Pool 命中率、索引维护、DDL、备份成本都会恶化
  • 分表后主查询路径要跟着走：按 user_id hash 分表，「我的订单」直接定位；商家按商品查订单走异构索引/ES

纠正锁的说法

  • INSERT 唯一索引不冲突时不持 next-key lock，秒杀订单绝大多数是新用户新单，不存在锁等待
  • 「临键锁退化成记录锁/间隙锁」是查询语义：唯一索引等值命中→记录锁、未命中→间隙锁；只有发生唯一性冲突时才加共享 next-key lock，与分表决策无关
  • 真到了行锁瓶颈，先做的是批量合并、库存分桶，而不是分表

分表之前通常先做：冷热数据归档（历史订单归档库）、索引优化、读写分离。

6.3 降级清单（按层级从轻到重）

页面降级

  • 动态详情页 → 静态页
  • 关闭推荐楼层、评价、排行榜
  • 兜底静态「太火爆」页、排队页

读降级

  • 关闭个性化推荐、画像类读
  • 非核心数据延长缓存 TTL
  • 只保留商品 + 下单主链路

写降级

  • 埋点、积分、经验值异步/丢弃/降采样
  • 日志降级到 ERROR
  • 同步写一律改异步

业务降级

  • 按比例放量（如只放 30%）
  • 关闭 VIP 通道、购物车，只留直购
  • 非预约用户直接拒绝

风控降级

  • 复杂评分规则降级为只查黑名单
  • 验证码服务异常用本地题库
  • 降级开关要提前预案演练

Redis 降级（红线）

  • 绝不降级到 DB 扣库存，峰值瞬间打穿 DB
  • 直接熔断返回排队页，或切备用集群
  • 已下单的支付链路不受影响

所有降级项都通过配置中心开关（Nacos/Apollo）一键切换，配合预案提前演练，不允许临时改代码。

6.4 熔断与隔离

熔断（Sentinel）

  • 触发条件：慢调用比例、异常比例、异常数超阈值
  • 打开 → 快速失败（返回火爆页）→ 半开探测 → 恢复
  • 核心依赖：Redis、MQ、风控、下游服务分别配置

隔离

  • 线程池/信号量隔离：下单链路与普通接口互不拖垮
  • 依赖超时时间显式设置，避免无限等待
  • Redis 熔断后只保护 DB，绝不开「直扣 DB」的口子

6.5 快速恢复：K8s 拉起新 Pod 后数据怎么一致

新 Pod 不是从零开始

  • 有状态部署用 StatefulSet + PVC 持久卷（云盘），Redis 数据目录落盘，重启后加载 RDB+AOF 再追增量
  • 作为新从节点加入：自动 PSYNC，全量 + 增量同步到最新
  • 空实例绝不允许直接接流量（库存全满会超卖，是严重事故）

持久化与复制

  • AOF appendfsync everysec（最多丢 1 秒）+ RDB 快照，兼顾恢复速度与安全
  • Cluster 每分片主从异步复制，故障切换可能丢极少量已确认扣减 → 靠消息表重放/对账修复
  • 要求更高：min-replicas-to-write，或同城双活/备用集群 + DTS 同步
恢复顺序 节点/集群恢复 → 用消息表（或按初始库存−有效订单）重放修复库存 → 预热脚本（Lua 缓存、连接池、本地缓存）→ 小流量灰度接入 → 全量恢复。秒杀是计划内活动，服务与容量通常提前扩容（HPA 按 QPS 自定义指标 + 人工预置），恢复预案也提前演练。

6.6 支付链路闭环（下单只是开始）

① 待支付订单
状态 = unpaid，等待付款
→
② 发起支付
调微信/支付宝/银联支付网关，生成支付单
→
③ 渠道异步回调
支付成功后渠道回调 notify_url；前端只做跳转，不能以前端为准
→
④ 验签 + 幂等 + CAS
验签防伪；回调可能多次，按支付单号幂等；UPDATE orders SET status='paid' WHERE id=? AND status='unpaid' 只成功一次
→
⑤ 确认扣减 + 发货
确认 DB 库存（未扣则扣）、发 MQ 触发发货、积分、通知

异常分支

  • 超时未支付：延迟消息关单，回补 Redis + DB（6.1）
  • 回调丢失（钱已付、订单仍 unpaid）：主动调渠道「查单接口」补偿；T+1 与渠道账单对账发现掉单
  • 重复支付：渠道对账发现后自动退款

两个关键原则

  • 关单与支付并发时，以支付为准：CAS 状态机保证已支付订单不会被关；关单执行前主动查一次渠道支付状态
  • 支付—订单—库存—积分跨库且不能错账，这才是 Seata/TCC + 对账的用武之地；秒杀扣减重吞吐走最终一致，支付重账目走强一致

6.7 对账之后：有余货怎么办？超卖了怎么办？

对账结果判定（初始库存 = 有效订单 + 应有剩余）后续保障处理
账平
正常		 有效订单数 + Redis/DB 剩余 = 初始库存 活动正常结束；清理 Redis 活动 Key、售罄标记；归档订单。
有余货
有效订单 < 初始库存		 剩余库存（含超时关单回补的部分）没卖完 ① 最常见：把剩余库存回收为普通库存，商品转为日常正常售卖（秒杀活动改价结束）；
② 运营决定返场/加场：库存继续在 Redis 滚动或重启一场活动；
③ 商家活动：按约定退仓/归还商家；
④ 清理活动期的预热 Key、售罄标记与分桶数据。
超卖
有效订单 > 初始库存		 正常 Lua 链路下不可能发生；出现说明有异常：主从切换丢已扣数据、库存回补重复/错误、幂等失效、人工误操作 事前：DB num>0 条件更新兜底，库存为负直接告警；
事中：发现库存为负/超卖，立即熔断下单、下架商品、停止回补；
事后：① 优先补货——商家紧急补货/调货/预售延期发货，按订单履约（用户无感）；
② 补不了货才砍单——按公示规则（通常砍掉时间最晚的超卖部分订单），全额退款 + 补偿券/现金赔付，规则必须在下单页提前公示；
③ 对账修正库存、复盘根因（回补/切换/补偿链路）。
为什么正常流程下超卖不可能发生 同步链路 Lua 单线程原子扣减（Redis 不会为负），异步链路 DB 条件更新（num>0 不会为负），两道独立防线；回补操作按订单 CAS 幂等只补一次。超卖只可能来自防线之外的异常（主从切换、重复回补、人工改库），所以监控「库存为负」和对账是最后的侦察哨。

对你原方案的逐条修正

CORRECTIONS
误区 1用了 Cluster 就不是主从模式了
正解Cluster = 分片（16384 槽）+ 每分片内部一主多从 + 自动故障转移。两者是叠加关系，高可用仍靠主从复制。
误区 2库存是单线程 + Lua 约束，不需要考虑热点 Key
正解单线程保证正确性，也正是单线程让单 Key 成为写串行点。库存 Key 是最大热点，必须分桶打散到多节点；商品详情/售罄态等读热点走本地缓存与读副本。
误区 3Redis 与本地消息表同时成功，微服务下用 Seata 约束
正解Seata AT 基于关系库 undo log，无法管理 Redis 分支；2PC 同步持锁也扛不住峰值。秒杀通道用本地消息表 / RocketMQ 事务消息做最终一致，配合幂等、重试、死信、对账、超时回补。Seata 留给支付清结算等跨库强一致链路。
误区 4某后端实例对应哈希环的哪个位置、负责哪些槽
正解槽由 Redis 节点负责，后端实例与槽没有归属关系；smart client 按 CRC16 直连节点，MOVED/ASK 重定向。分桶后是「应用层选桶 → 节点扣减自己被路由到的桶」，不存在实例固定包槽。
误区 5库存 Key 不设 TTL，所以缓存雪崩不用担心
正解这只解决了「TTL 集中过期」型雪崩；「Redis 整体宕机」型雪崩依然存在，要靠 Cluster 高可用、熔断后直接返回排队页（绝不打 DB）。
误区 6对账以 Redis 为主更新数据库
正解活动中 Redis 领先、可作为修 DB 的依据；活动结束后以有效订单（支付状态）为准。消息表是审计/事件源，可对账、可重放、可同步备用 Redis——你的这个判断是对的，前提是消息表记录完整明细与回补事件。
补充分桶后 Lua 脚本的跨槽限制
要点Cluster 下一个脚本的所有 Key 必须同 slot。用 hash tag 把「同桶的库存 Key 与已购 Set」绑定（{g1:b0}），脚本只操作单桶；不同桶刻意分散到不同节点分摊压力；一人一单 SADD 跟随用户固定路由的桶。
补充售罄标记是分两级的
要点桶级售罄写应用本地标记（Caffeine），请求不再碰该桶；所有桶售罄才升级为商品级售罄，Nginx/网关也可同步该标记，在边缘直接返回。

你原方案里还缺的 12 个点

GAP LIST

设备指纹是什么、放在哪

前端 SDK 采集 UA、屏幕、时区、Canvas/WebGL 渲染特征、字体列表（App 端还有 OAID/Android ID 等），哈希生成 deviceId；后端把设备、账号、IP、收货地址、行为序列汇总做风险评分。用途：一机多号、群控云手机、模拟器改机、设备黑名单。它是风控系统的一个输入，不是独立防线——指纹可被改机工具篡改，只能提高黄牛成本，需配合行为验证码与人审。

接口地址动态化 + 签名

秒杀真实 URL 活动开始前不暴露，点击后才下发，带时间戳、nonce、签名，防脚本提前刷和重放。

页面 token 做接口幂等

进入秒杀页发一次性 token，提交时核销，重复提交直接拦截，解决「网络重试 + 双击」造成的重复下单。

网关放量令牌（排队闸）

在网关只放行「库存数 × 小系数」的请求，其余进排队页或快速失败，把 Redis 层的压力也提前控住，这是 12306 的核心思路。

库存预热

活动开始前把分桶库存、用户 Set、活动配置、布隆过滤器全部加载到 Redis，避免开始瞬间回源。

一人一单三层防线

页面 token 防重复提交 → Lua 内 SADD 原子判重 → DB 唯一索引（用户+商品+活动）兜底。任何单层失效都不会超量。

DB 热点行的另一种拆法

除了 Redis 分桶，DB 侧库存也可以分桶（1000 件拆 10 行），更新时按用户 hash 路由，把单行行锁变 10 行；配合批量合并扣减，进一步降低 DB 压力。

支付链路闭环（已补到 6.6）

渠道回调验签与幂等、CAS 状态流转、关单与支付并发以支付为准、回调丢失靠主动查单 + T+1 渠道对账、重复支付自动退款。支付—订单—库存—积分的跨库强一致才是 Seata/TCC 的用武之地。

全链路压测与容量规划

活动前压测各层水位（按 80% 预留），含限流阈值、Redis 分桶数、MQ 分区与消费者数、DB 连接池；大促流量还要做流量回放。

监控漏斗与告警

各层 QPS/拦截率、Lua 成功率、售罄率、MQ 堆积、消费延迟、DLQ 数量、Redis 命中率与延迟、库存差异，全部进看板并配告警。

Web 层异步化

Servlet 3.0 异步 / 响应式（WebFlux）避免请求线程在等待 Redis/MQ 时被占满；Tomcat 线程池与连接数要显式调优。

预案开关、灰度与演练

限流值、降级开关、切备用集群等全部配置化，提前演练并准备兜底静态页；时间以服务端 NTP 校准为准。

CHEAT SHEET

「秒杀的核心是流量漏斗：前端防抖+验证码削峰，CDN 扛静态，Nginx 做 IP 限流和黑名单，网关做限流、风控设备指纹和排队令牌，业务资格层用 Redis 查预约名单和一人一单，布隆过滤器防穿透。同步交易链路里，库存提前预热并分桶在 Redis Cluster，用 Lua 脚本原子完成售罄判断、重复判断、扣库存、SADD 登记，成功后写本地消息表（或 RocketMQ 事务消息），立即返回；MQ 消费者幂等创建订单、条件扣减 MySQL 库存，失败重试、超限进死信，库存扣减可以攒批合并。MySQL 做垂直分表、订单唯一索引兜底一人一单。超时未支付用延迟消息关单并按原桶回补。Redis 是分片加主从的 Cluster，AOF 加 RDB，新 Pod 用 PVC 或从节点同步，绝不用空实例接流量。一致性上秒杀通道走最终一致，不上 Seata，靠消息表 + 幂等 + 对账 + 回补收敛；Seata 用在支付清结算链路。异常时按页面、读、写、业务、风控分级降级，Redis 熔断直接返回排队页，绝不降级到 DB，最后靠消息表重放和定时对账兜底。」

秒杀系统全景设计 · 学习复盘笔记 · 所有流量数字均为示例量级 关键词：流量漏斗 / Lua 原子扣减 / 库存分桶 / 本地消息表 / 最终一致 / 对账回补
