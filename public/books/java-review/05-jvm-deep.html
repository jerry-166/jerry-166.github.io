类的生命周期五阶段面试高频★★★★★

一个 .class 文件从"磁盘上的字节"到"可以 new 出对象"，要经历五步。面试标准问法："说说类的加载过程"，答出五阶段 + 各阶段一句话即可拿满分：

类的生命周期Diagram
 .class 文件（磁盘）
       │
       ▼
 ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌───────────┐

阶段 1：加载（Loading）——"搬进来"

  • 通过类的全限定名拿到 二进制字节流（来源不限于磁盘：jar 包、网络、动态代理运行时生成——模块 9 的动态代理就是在这里"无中生有"出类）
  • 把字节流的静态结构转化为方法区的运行时数据结构（类信息进方法区）
  • 在堆中生成一个 java.lang.Class 对象，作为访问方法区类数据的入口（所以 Class 对象在堆，类数据在方法区——模块 1 的两张图在这里接上了）

阶段 2：验证（Verification）——"安检"

确保字节码合法且不危害虚拟机：文件格式（魔数 CAFEBABE）→ 元数据（是否有父类、是否继承 final 类）→ 字节码（类型转换安全）→ 符号引用（引用的目标确实存在）。

阶段 3：准备（Preparation）——"分房子、给零值"易错点

为类静态变量在方法区分配内存并设零值——注意不是你写的初始值！

准备阶段 vs 初始化阶段：同一个变量的两次赋值Java
public static int value = 123;

// 准备阶段后：  value = 0        ← 零值！此时还没执行你写的 123
// 初始化阶段后：value = 123      ← 这时才执行类构造器 <clinit>() 里的赋值

// 例外：编译期常量在"准备"阶段就直接赋值（ConstantValue 属性）：
public static final int CONST = 123;
// 准备阶段后：CONST = 123   ← final + 编译期可确定 → 不用等初始化
⚠ 为什么这是易错点

面试常追问"静态变量的赋值发生在类加载的哪个阶段"——标准答案：零值在准备，业务赋值在初始化。这也解释了一个经典现象：静态代码块里能打印到还没执行赋值语句的静态变量（值为零值），因为赋值语句和静态块按源码顺序在 <clinit>() 里执行。

阶段 4：解析（Resolution）——"符号变地址"

把常量池里的符号引用（如 java/lang/Object 这样的名字描述）替换为直接引用（指针 / 偏移量）。可以发生在初始化之后（晚期绑定），这正是多态的实现基础（模块 3 讲过的方法表分派）。

阶段 5：初始化（Initialization）——"执行你的静态代码"

执行类构造器 <clinit>()：把静态变量赋值语句 + 静态代码块按源码顺序合并执行。重点在下一节展开。

一句话回答

类加载过程 = 加载（搬进方法区+堆里建 Class 对象）→ 验证（安检）→ 准备（静态变量给零值）→ 解析（符号引用变直接引用）→ 初始化（执行 <clinit>，静态赋值+静态块）。常量（static final）在准备阶段就直接赋值，不等初始化。

03

初始化：clinit 与"最优雅单例"的原理高频难点★★★★☆

什么情况会触发初始化？（主动引用 6 种）

JVM 规范严格规定了 6 种"必须立即初始化"的场景，除此之外都不初始化（被动引用）——这是选择题和读代码题的富矿：

主动引用（触发初始化） vs 被动引用（不触发）Java
class Parent { static int a = 1; static { System.out.println("Parent init"); } }
class Child extends Parent { static { System.out.println("Child init"); } }

// ── 主动引用：会打印 "Parent init" ──────────────────────────
new Child();                        // ① new 实例（先初始化 Parent 再 Child）
int x = Parent.a;                   // 读写非 final 静态字段（只有定义它的类初始化）
Parent.doSomething();               // 调用静态方法
Class.forName("Parent");            // 反射
// ⑤ 初始化子类时，父类若未初始化则先初始化（上面的 new Child() 已体现）
// ⑥ main() 所在的类，启动时立刻初始化

// ── 被动引用：一行都不会打印 ────────────────────────────────
int y = Child.a;        // ② 通过子类名访问父类静态字段 → 只初始化 Parent？错！
                        //    访问的还是 Parent.a（静态字段属于定义者），Child 不初始化
Parent[] arr = new Parent[10];   // ③ 定义数组 → 只分配数组对象空间，元素类不初始化
int z = Parent.CONST;   // ④ 访问编译期常量 → 常量在调用方类的常量池里，直接用，
                        //    Parent 根本不会被加载初始化（最反直觉的一个！）
⚠ 被动引用第 4 种最常考

"引用常量不触发定义类的初始化"的原因：编译期常量在编译阶段就被存进了使用者的常量池，运行时根本不需要碰定义类。可以把 static final 理解成"宏替换进了对方的类"。

clinit 的两条铁律

  1. 父类优先：子类 <clinit>() 执行前，保证父类的已执行完（所以静态块输出永远是"父先子后"，呼应模块 3 初始化顺序）
  2. 线程安全：JVM 保证同一个类的 <clinit>() 在多线程下只被一个线程执行一次，其他线程阻塞等待 ← 这条铁律直接催生了一个面试标准答案：
静态内部类单例：为什么它是"最优雅"的懒加载单例Java
public class Singleton {
    private Singleton() {}

    // 关键：静态内部类不会在 Singleton 加载时就初始化（被动引用规则）
    private static class Holder {
        // 第一次用到 Holder 才触发类加载 → <clinit>() 执行 new
        // JVM 保证 <clinit> 只执行一次且线程安全 → 天然的懒加载 + 线程安全，零锁
        static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// 面试话术：既不像饿汉式浪费（未用就建），又不像双重检查锁那样要写
// volatile + 两次判空（模块 6 会展开 DCL），它把并发问题下放给了 JVM 类加载机制。
1
追问：Class.forName 和 ClassLoader.loadClass 的区别？
两者都能把类加载进方法区，但 Class.forName("X") 默认会执行到初始化阶段（跑静态块），而 loader.loadClass("X") 只到加载阶段。JDBC 老写法 Class.forName("com.mysql.jdbc.Driver") 就是靠它执行驱动里的静态注册块。forName 还有个三参重载可以控制是否初始化和类加载器。
2
追问：那接口有 clinit 吗？
接口可以有（接口里允许定义常量初始化表达式，JDK8+ 还有默认方法），但接口初始化不要求先初始化父接口，且只有在真正使用接口的静态成员时才初始化——比类更"懒"。

类加载器与双亲委派面试超高频★★★★★

三层加载器：各管一摊

类加载器层次 + 双亲委派流程Diagram
        ┌──────────────────────────────────────────────┐
        │  Bootstrap ClassLoader（启动类加载器，C++实现） │
        │  加载：JAVA_HOME/lib 核心库（String、Object…）  │
        │  特殊：拿不到它的引用（null），JVM 自身的一部分   │
        └───────────────────▲──────────────────────────┘
                            │ 委派↑ 回传↓
        ┌───────────────────┴──────────────────────────┐
        │  Platform ClassLoader（平台类加载器）           │
        │  JDK 8 及以前叫 Extension（扩展类加载器）       │
        │  加载：平台模块 / lib/ext（javax.* 等）          │
        └───────────────────▲──────────────────────────┘
                            │ 委派↑ 回传↓
        ┌───────────────────┴──────────────────────────┐
        │  Application ClassLoader（应用类加载器）        │
        │  加载：你写的 classpath（业务代码、依赖 jar）    │
        └──────────────────────────────────────────────┘

双亲委派流程（应用程序收到 loadClass("X") 请求时）：
  ① Application 不自己加载，先问上级 Platform
  ② Platform 也不自己加载，先问上级 Bootstrap
  ③ Bootstrap 找不到（X 不在核心库）→ 回复"我搞不定" → Platform 自己找
  ④ Platform 找不到 → 回复"我搞不定" → Application 在 classpath 里找
  ⑤ 谁先找到谁定义这个类；都找不到 → ClassNotFoundException

一句话：孩子收到活儿先往上报，父辈干不了的才传回来自己干。

为什么要双亲委派？两个原因必背

  1. 安全：你自己写一个 java.lang.String 放进 classpath，加载请求会被委派给 Bootstrap，它加载的是 JDK 官方的 String，你的"假 String"永远没机会运行 → 防止核心 API 被篡改
  2. 一致性（类的唯一性）：JVM 里类的身份 = 类加载器 + 全限定名。同一个类只被同一个加载器加载一次，保证你在代码里 instanceof、强转不会因为"加载了两个同名类"而失败
一句话回答

双亲委派 = 子加载器收到加载请求先层层上交，父级无法完成才自己加载。目的：①防止核心类被替换（安全）；②保证类只被加载一次（类的唯一性由"加载器+全限定名"共同决定）。

打破双亲委派的三个经典场景难点·加分项

1
JDBC 为什么必须打破？
核心矛盾：DriverManager 在核心库（Bootstrap 加载），而 MySQL 驱动 jar 在你的 classpath（Application 加载）。Bootstrap 是"祖宗"，按委派规则永远看不到孙子的 jar。解法：引入线程上下文类加载器（Thread Context ClassLoader），让核心代码"反向"借用应用加载器去加载驱动实现（SPI 机制的原理）。这是父级代码调用子级加载器的经典破坏。
2
Tomcat 为什么打破？
一个 Tomcat 部署多个应用，两个应用依赖不同版本的同一个库 → 必须互相隔离。Tomcat 给每个 webapp 配一个独立的 WebappClassLoader，优先加载自己应用下的类（先自己找，找不到再委派）——把"先委派"改成"先自查"，实现应用隔离。但核心库依然委派，防止篡改。
3
热部署 / OSGi 呢？
改了代码不重启就能生效 = 丢弃旧 ClassLoader、新建一个重新加载类（旧类对象等 GC 回收）。因为"类身份=加载器+类名"，新加载器加载出的类是"新类"，替换引用即完成热替换。JDK 9 模块化后，加载器结构变为"平台模块各有其类加载器"，也属于对经典三层结构的改造。
自定义类加载器：重写 findClass 而非 loadClassJava
public class MyClassLoader extends ClassLoader {
    private String classDir;   // 从自定义目录（如加密的 class 文件）加载

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] data = loadClassData(name);          // 读字节码（可在此解密）
        if (data == null) throw new ClassNotFoundException(name);
        // defineClass：把字节数组变成方法区里的类（JVM 提供的native能力）
        return defineClass(name, data, 0, data.length);
    }
    private byte[] loadClassData(String name) { /* 读文件省略 */ return null; }
}

// 为什么重写 findClass 而不是 loadClass？
// loadClass 里封装了"双亲委派"的模板流程；findClass 是留给子类填空的钩子。
// 重写 findClass = 保留双亲委派 + 扩展加载来源（推荐）
// 重写 loadClass = 彻底推翻双亲委派（Tomcat 式，需自担安全责任）

对象存活判定与 GC Roots面试高频★★★★★

GC 的第一个问题：怎么判断一个对象"死了"？两条技术路线：

路线一：引用计数（Java 没用，Python 在用）

每个对象带一个计数器，被引用 +1，引用失效 -1，归零即回收。优点：简单、实时。致命缺陷：循环引用永远不为零。

循环引用：引用计数的死穴Diagram
    objA ──┐         ┌── objB
           ▼互相引用 ▼
        ┌─────────────────────┐
        │  a.field = b        │   两个对象各自计数 = 1
        │  b.field = a        │   外部引用已断（objA/objB 变量已置 null）
        └─────────────────────┘
        引用计数视角：都非零 → 永远不回收 → 内存泄漏

        可达性分析视角：从 GC Roots 出发走不到它们 → 都是垃圾 → 回收
🐍 Python 对比：CPython 怎么处理的

CPython 主策略就是引用计数（所以 Python 对象 sys.getrefcount 可查、del 后多数立即释放），但它也知道循环引用救不了 → 另配一套分代标记清除 gc 专门扫描"容器对象"找环（gc.collect()）。Java 一开始就放弃引用计数，只用可达性分析——环不环无所谓，从根走不到就是死。面试被问"Python 和 Java GC 区别"，这就是核心差异点。

路线二：可达性分析（Java 的选择）

从一组叫 GC Roots 的根对象出发，沿着引用链走（图遍历），走得到的活，走不到的死。

可达性分析图解Diagram
 GC Roots（根）                          对象引用图
 ════════════════                       ═══════════
 ① 栈帧局部变量表中的引用
    ──────────────────────┐
 ② 方法区静态变量引用     │        obj1 ──▶ obj2 ──▶ obj4   ✅ 可达 → 活
    ──────────────────────┼──▶ obj1
 ③ 方法区常量池引用       │                  │
    ──────────────────────┘                  ▼
 ④ JNI（native 方法）栈引用                  obj3 ──▶ obj5    ✅ 可达 → 活
 ⑤ 活跃线程、同步锁持有的对象
                                          obj6 ──▶ obj7    ❌ 从任何根都走不到
                                                            → 判死，等回收
 （obj6 与 obj7 互相引用也没用——可达性分析不在乎环）
⚠ 背 GC Roots 别背成"堆里所有对象"

GC Roots 本质 = 堆外指向堆内的引用起点：各线程栈帧的局部变量、方法区静态变量、常量池引用、JNI 栈引用、活跃 Thread 对象、被 synchronized 持有的对象。高频追问："方法区算不算 GC Roots？"——方法区里的静态变量和常量是根，但方法区本身不是。

一句话回答

Java 用可达性分析判活：从 GC Roots（栈局部变量、静态变量、常量、JNI 引用、活跃线程等）沿引用链遍历，不可达即判定死亡。不用引用计数，因为它无法回收循环引用（CPython 因此需要额外加分代 gc 补刀）。

"判死"到"真死"还有一次缓刑：finalize()

不可达对象要经过两次标记：第一次发现不可达 → 检查是否重写 finalize() 且未执行过 → 放入 F-Queue 缓刑；若 finalize() 里把自己重新挂回引用链（如 this.save = this）→ 挽救成功。但 finalize() 执行时机无保证、性能差，JDK 9 已废弃——面试只需要知道"有这回事 + 别用，用 try-with-resources 替代"（模块 8 展开）。

四种引用强度高频★★★★☆

JDK 1.2 起，引用分四级（强 → 弱）。级别决定 GC 对它的态度：

引用类型回收时机典型用途对应 API
强引用 Strong永不回收（只要可达，OOM 也不回收）99% 的日常代码 Object o = new Object()—
软引用 Soft内存不足之前（抛 OOM 前会先回收一轮软引用对象，还不够才 OOM）内存敏感缓存（如图片缓存）SoftReference
弱引用 Weak只要发生 GC 就回收（活过一次 GC 都算它命大）ThreadLocalMap 的 key、WeakHashMap、规范映射WeakReference
虚引用 Phantom随时回收，形同虚设（不影响对象生命周期）回收时收到通知 → 管理堆外内存PhantomReference + ReferenceQueue
弱引用：一次 GC 就没Java
Object obj = new Object();                 // 强引用
WeakReference<Object> weak = new WeakReference<>(obj);
System.out.println(weak.get());            // java.lang.Object@... ✅

obj = null;                                // 断掉唯一的强引用，只剩弱引用指着它
System.gc();                               // 建议 GC（不保证立刻发生）
Thread.sleep(100);
System.out.println(weak.get());            // null  ← 只要 GC 跑了，弱引用对象必死
📌 虚引用唯一的存在意义：堆外内存的讣告

DirectByteBuffer 的堆外内存不归 GC 管（堆外！），堆内只留一个小的 DirectByteBuffer 壳。壳被回收时怎么知道去释放堆外内存？——给壳挂一个虚引用 + ReferenceQueue：壳被 GC 时虚引用进入队列， Cleaner 线程收到"讣告"后调用 native 方法释放堆外内存。这是"虚引用 = 对象死亡通知器"的唯一标准场景，面试答出这个就是加分。

🐍 Python 对比

Python 的 weakref 模块对应 Java 的弱引用，常用于缓存和避免父子对象循环引用（weakref.WeakValueDictionary ≈ Java 的 WeakHashMap）。Python 没有内置"软引用"分级——内存不足回收缓存这件事在 Python 里得自己实现。

📌 本节的伏笔

"弱引用只要 GC 就回收"这个特性，是理解模块 6 中 ThreadLocal 内存泄漏的钥匙：ThreadLocalMap 的 key 是弱引用（会被回收成 null），value 却是强引用链（回收不掉）——错位导致泄漏。此处先留印象。

三大 GC 基础算法高频★★★★☆

知道谁死了，怎么"收尸"？三种基础算法，后面的所有收集器都是它们的组合：

标记-清除 / 标记-复制 / 标记-整理Diagram
【标记-清除 Mark-Sweep】 先标后扫，直接把死对象位置标记为"可用"

一句话回答

标记-清除简单但碎片化；标记-复制无碎片但费一半空间，适合朝生夕死的新生代；标记-整理无碎片不浪费但要搬对象改引用，适合高存活率的老年代。"分代收集"就是把合适的算法用在合适的代上。

⚠ 面试防杠点

"分代收集"不是第四种基础算法，而是一种策略：按对象存活周期分区，不同区用不同算法。同理"自适应"收集器（如 G1 对不同 Region 动态选择）也是策略层面的组合。

Minor GC 全程：一次新生代回收的完整剧本

  1. Eden 满 → 触发 Minor GC（只回收新生代，快：新生代小 + 活得少）
  2. 可达性分析从 GC Roots + 老年代出发（跨代引用怎么办？见下方卡牌），标记 Eden + 当前存活 Survivor 里的活对象
  3. 活对象用标记-复制，全部搬到空的那个 Survivor（S0 有数据就搬到 S1），年龄 +1
  4. Eden 和旧 Survivor 一次性清空（整块清零，无碎片）
  5. 存活对象年龄达到阈值（默认 MaxTenuringThreshold=15，4 bit 计数上限）→ 晋升老年代

📌 跨代引用：记忆集与卡页（加分项）

Minor GC 只扫新生代，但老年代对象可能引用新生代对象——难道每次都全堆扫描？解法：卡表（Card Table）把老年代切成 512B 的卡页，只要老年代某处引用了新生代，对应卡页标"脏"。Minor GC 时只扫脏卡 + GC Roots，把扫描范围从整个老年代缩小到几 KB。G1 把这个思想放大成每个 Region 一份记忆集（RSet）。

对象进入老年代的 4 条路（高频追问）

路径条件说明
① 年龄达标age ≥ MaxTenuringThreshold（默认 15）每熬过一次 Minor GC 年龄 +1
② 动态年龄判定S 区中同龄对象总大小 > S 区一半该年龄及以上的对象直接晋升（"这一届人太多，S 区装不下"）
③ 大对象直通车≥ PretenureSizeThreshold避免大对象在 Eden/S 之间反复复制，直接进老年代（Serial/ParNew 生效）
④ 空间分配担保Minor GC 前老年代可用 < 新生代全部对象大小详见下卡
🧠 空间分配担保（难点，讲清就超越多数候选人）

Minor GC 前的保险检查：老年代剩余连续空间能否装下新生代所有对象（最坏情况全部晋升）？装得下 → 放心 Minor GC。装不下 → 再看历次晋升平均大小：历史均值装得下 → 赌一把 Minor GC；赌输（晋升对象超出预期）→ 担保失败（promotion failed）→ 触发 Full GC。JDK 6u24 后规则简化为"老年代连续空间 > 新生代对象总大小 或 > 历次晋升平均大小"就放行。

Minor GC / Major GC / Full GC 的区别（必背）

名称回收范围触发条件速度
Minor GC（Young GC）新生代（Eden + 一个 S）Eden 满快（毫秒级）：区域小、朝生夕死、复制算法
Major GC老年代老年代满 / 晋升失败慢；Major GC 常伴随至少一次 Minor GC
Full GC整堆 + 方法区① 老年代空间不足 ② 方法区（元空间）不足 ③ System.gc() 建议 ④ 空间分配担保失败 ⑤ CMS 运行期晋升失败 / concurrent mode failure最慢（STW 范围最大）——生产事故头号嫌疑人
⚠ 命名陷阱

不同资料对 "Major / Full" 的定义有分歧（有的把 Major=Full 混用）。面试建议主动澄清口径："我说的 Full GC 指收集整个堆和方法区的 stop-the-world 收集"，一句话体现严谨。另外注意：老年代 GC 不一定叫 Full GC——CMS 老年代回收是并发的，大多数资料不把它叫 Full GC。

收集器演进：CMS 与 G1超高频难点★★★★★

📌 并行 ≠ 并发（术语先对齐）

并行（Parallel）：多条 GC 线程同时干，但用户线程全程暂停（STW，吃满 CPU 换快）。并发（Concurrent）：GC 线程和用户线程同时运行，停顿大幅缩短，但 GC 要和业务抢 CPU，且并发带来"边扫边变"的一致性问题（三色标记的由来）。

 为什么快：两个 STW 阶段都只做"薄薄一层"工作（直连对象扫描/增量修正），
           最耗时的整图遍历和清除都与用户线程并发执行。

 三大代价：
 ① CPU 敏感：并发阶段 GC 线程抢业务 CPU（默认回收线程 =(核数+3)/4）
 ② 浮动垃圾：并发清除阶段用户线程新产生的垃圾本轮收不到 + 并发期用户线程
   还要分配内存 → 老年代必须预留空间（CMSInitiatingOccupancyFraction，
   默认 ~92% 老年代占比才启动）→ 预留不够 = promotion failed /
   concurrent mode failure → 退化为 Serial Old 单线程整理（大停顿事故）
 ③ 标记-清除 → 碎片 → 大对象没连续空间 → 又一个 Full GC 诱因

三色标记与"漏标"：并发标记的核心难题难点

并发标记时用户线程还在改对象图，于是对象被抽象成三色：

  • 白色：未被扫描（最终仍白 = 垃圾）
  • 灰色：自己已扫，但它的字段引用还没扫完
  • 黑色：自己和字段都扫完（认定存活，不会再重扫）
漏标：同时满足两个条件才会发生Java
class A { B b; }  class B { C c; }  class C { }

// 灰色 A 正在扫描中，黑色 A' 已扫完，白色 C 还没被扫到
A.b = null;        // 条件①：灰→白的引用被删除（A 不再指 B）
// ...
blackA.b = newC;   // 条件②：黑对象新增了指向白对象的引用（黑 A' 指向 C）

// 扫描结束时：C 从灰色链上够不着（B 断了），
//            而 A' 是黑色不会再扫 → C 被误判为白色垃圾 → 【活对象被回收】💥
// 注意：必须两个条件【同时】满足才漏标，于是两种解法各堵一个条件：
方案堵哪个条件做法副作用使用者
增量更新 Incremental Update条件②（黑插白）黑对象插入白引用时记下来，重新标记阶段把这些黑重新变灰、再扫一遍重新标记要 STW 多扫一些CMS
原始快照 SATB条件①（灰删白）删除引用时记录旧引用（快照），标记按快照进行——快照里够得着的都算活快照里的浮动垃圾本轮收不掉G1
一句话回答

并发标记时用户线程同时改图，可能"漏标"活对象（黑对象新指了白对象 + 灰对象到白的路径被删，两条件同时成立）。CMS 用增量更新堵第一个条件（记下黑→白新引用，重新标记时重扫）；G1 用 SATB 堵第二个（删引用时留旧引用快照，宁可多留浮动垃圾不可漏标）。

🐍 Python 对比：分代思想同源

CPython gc 也是分代（0/1/2 三代，阈值 700/10/10 次分配触发），思想一样：越年轻的代回收越频繁，多次幸存者往老一代搬。差异：Python 分代只针对"循环引用扫描"（引用计数仍实时收非环垃圾），Java 分代是全部回收策略；Python 没有可调停顿目标的收集器体系。

📌 ZGC 一句话（防追问）

JDK 11 实验 / 17 转正 / 21 支持分代。核心：着色指针（指针里带标记位）+ 读屏障，把几乎整个 GC（标记、转移、重定位）全部并发化，停顿亚毫秒级，支持 TB 级堆。答出"着色指针 + 读屏障 + 亚毫秒停顿"三个词就够了。

追问：为什么 G1 适合大堆？

内存泄漏与 OOM 排查项目向高频★★★★☆

先分清三个词

  • 内存溢出（OOM）：申请内存时空间不够，JVM 抛 OutOfMemoryError——是结果
  • 内存泄漏（Leak）：对象已无用了，却仍被引用着，GC 收不掉——是原因之一；泄漏越攒越多，最终以 OOM 爆发
  • 内存抖动：频繁创建回收（Java 内存抖动概念少提，Android 场景常说；Java 后端一般不考）

八个经典泄漏场景（面试能说三个 + 项目结合就过关）

泄漏场景 1+2：静态集合 & 未关闭资源Java
// ① 静态集合 = 全局生命周期，只进不出 → 缓存无限膨胀
static Map<String, byte[]> CACHE = new HashMap<>();
void handle(String key) {
    CACHE.put(key, new byte[1024 * 1024]);   // 永远不 remove → 慢性泄漏
}   // 修复：LRU 上限（LinkedHashMap/removeEldestEntry）、Guava Cache 设过期、Caffeine

// ② 流/连接未关闭 → 堆外的文件描述符/连接泄漏，也能拖死进程
void read(String path) throws IOException {
    InputStream in = new FileInputStream(path);   // 若中途抛异常，in 永远关不上
    // ... 抛异常 → in 泄漏
}
// 修复：try-with-resources（模块 8 展开），任何实现了 AutoCloseable 的都能自动关
泄漏场景 3：ThreadLocal + 线程池（重中之重，模块 6 深挖）Java
private static ThreadLocal<byte[]> BUF = new ThreadLocal<>();

void task() {
    BUF.set(new byte[1024 * 1024]);   // 用完忘了 remove
}                                      // 线程池的线程不死 → 泄漏链：

// Thread（池中长命）→ ThreadLocalMap → Entry
//   Entry.key  = ThreadLocal 对象 →【弱引用】→ GC 后变 null ✅ key 可回收
//   Entry.value= byte[]          →【强引用】→ value 被死 key 拽着 ✗ 收不掉！
//
// 两个关键认知：
// a) key 用弱引用正是为了"ThreadLocal 外部引用断了也能回收 key"（防 key 泄漏）
// b) value 仍是强引用 → 只要 Entry 在（线程不死 Entry 就在），value 就在
//    → 线程池场景必须 finally { BUF.remove(); }
// （ThreadLocalMap 源码在 set/get 时也会顺手清 stale entry，但不能依赖）

其余场景一句话（展开讲挑你项目相关的）：

#场景机理一句话
④监听器/回调未注销注册进全局事件源的监听器持有大对象，忘记 unregister
⑤非静态内部类内部类默认持有 Outer.this 强引用（Android Handler 泄漏同源）；改静态内部类 + 弱引用

⑧无界缓存本质同 ①，用软引用/Caffeine 弱键可缓解（呼应第 06 节引用分级）

OOM 排查工具链（能说出流程 = 有生产经验感）

1
事前：留好现场
启动参数 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump.hprof——OOM 发生瞬间自动导堆快照，事后分析的第一手证据。
2
事中：定位是什么 OOM、GC 是否还在干活
jps 找 PID → jstat -gcutil <pid> 1000 每秒看一次各代占用和 GC 次数：O 老年代占满且 FGC 次数疯涨 → 老年代泄漏；元空间涨 → 动态生成类失控（反思：CGLib 代理、Groovy 脚本）。jmap -histo <pid> 秒出"实例数 Top 榜"，往往一眼看到可疑类。
3
事后：MAT 分析堆快照
用 MAT（Eclipse Memory Analyzer）打开 hprof：① Leak Suspects 自动报告 → ② 支配树（Dominator Tree）看谁占着最多内存 → ③ 对可疑对象查 GC Roots 引用链（Path to GC Roots）——找到"是谁拽着它不放"，泄漏代码定位完成。在线环境可用 Arthas：dashboard / heapdump 不重启诊断。
🐍 Python 对比：排查工具对应关系

Python 你用 tracemalloc / objgraph / gc.get_objects() 找泄漏；Java 对应关系：objgraph 的"反向引用"≈ MAT 的 Path to GC Roots，tracemalloc 快照对比 ≈ jmap -histo 前后对比。思想一致：看数量异常 → 找持有链。

📌 项目话术模板（背下来直接用）

"我们服务有一次老年代持续上涨最终 OOM。jstat 看到 FGC 后老年代占用不降 → 判断泄漏；开了 HeapDumpOnOutOfMemoryError 拿到 hprof，MAT 支配树发现 XX 对象占了 70%，Path to GC Roots 显示被一个 static Map 持着 → 是历史代码里的本地缓存没有淘汰策略。改成 Caffeine（最大容量 + 过期时间）后，老年代稳定在 30%，问题闭环。"——把 XX 换成你项目里的真实对象即可。

对象分配策略补全：逃逸分析与 TLAB难点★★★☆☆

模块 1 第 8 节讲过 new 的字节码层面流程；现在补上"对象一定在堆上分配吗？"——这是 JIT 优化的高光区：

new 之后的分配决策树（HotSpot JIT 视角）Diagram
 new 指令
    │
    ▼
 【逃逸分析】(-XX:+DoEscapeAnalysis，JDK 7+ 默认开)
    ├─ 对象不逃逸出方法（不被外部引用、不返回、不传出去）
    │     └─▶ 标量替换：对象根本不创建！拆成零散局部变量放【栈帧】里
    │          方法结束自动消失 → 0 GC 压力
    │          （所以"Java 对象都在堆上"在 JIT 优化后并不绝对）
    │
    └─ 逃逸 → 真的要在堆分配
          │
          ▼
      【TLAB】Thread Local Allocation Buffer
          ├─ Eden 里给每个线程划一块私有缓冲区
          ├─ 分配 = 移动私有指针（指针碰撞），【无需加锁】
          └─ TLAB 放不下 → 同步申请新 TLAB / 直接在 Eden 共享区分配
                │
                ▼
            【大对象？】(≥ PretenureSizeThreshold)
                ├─ 是 → 直接进老年代（免得在 S 区之间来回复制）
                └─ 否 → Eden 出生 → 走第 08 节的分代剧本
🧠 三个容易混的概念，一次掰清

①栈上分配：HotSpot 实际是通过标量替换实现的（对象拆散成基本类型局部变量），并不是真把完整对象塞进栈；②锁消除：逃逸分析证明锁对象不逃逸（方法内局部的 StringBuffer）→ synchronized 直接被 JIT 擦掉（模块 6 锁优化呼应）；③TLAB：解决的是堆分配的并发竞争（多线程抢 Eden 指针），不是决定对象放哪一代。

常用参数速查（背前两行即可）

参数含义生产习惯
-Xms / -Xmx初始堆 / 最大堆设成一样，避免运行期动态扩缩引起抖动
-Xmn / -XX:SurvivorRatio=8新生代大小 / Eden:S 比例新生代 ≈ 堆的 1/3 ~ 1/2（G1 下别手动设 Xmn，交给停顿模型）

高频面试题速查

以下答案都来自上文，模拟真实问答节奏；点击展开。建议先自己回答再对照。

类的加载过程有哪几步？高频

五步：①加载——把 class 字节流转成方法区的运行时结构，并在堆里建 Class 对象；②验证——格式/元数据/字节码/符号引用四道安检；③准备——静态变量分配内存并赋零值（static final 编译期常量例外，直接赋真值）；④解析——符号引用转直接引用（可推迟到初始化后，支持晚期绑定）；⑤初始化——执行 <clinit>()（静态赋值+静态块按源码顺序），父类优先且 JVM 保证线程安全。

双亲委派是什么？为什么需要？怎么打破？超高频

是什么：子加载器收到请求先层层上交（App→Platform→Bootstrap），父级加载不了才退回自己加载。

为什么：①安全——防核心类被自定义同名类替换；②一致性——类身份 = 加载器+全限定名，保证核心类全局唯一一份。

怎么打破：重写 loadClass（或用线程上下文类加载器）。三个场景：JDBC/SPI（核心库借上下文加载器加载应用 jar 的驱动）、Tomcat（每应用独立 WebappClassLoader 先自查再委派，实现隔离）、热部署（丢弃旧加载器重新加载类，类身份不同即可替换）。

GC Roots 有哪些？静态内部类单例为什么线程安全？高频

GC Roots = 栈帧局部变量、方法区静态变量、常量池引用、JNI 栈引用、活跃线程、锁持有的对象——本质是"堆外指向堆内的引用起点"。

静态内部类单例：外部类加载不会触发内部类初始化（被动引用）→ 懒加载；首次调用 getInstance 才初始化 Holder，而 <clinit>() 由 JVM 保证只被一个线程执行一次、其他线程阻塞等待 → 免锁的线程安全。

怎么判断对象可以回收？和 Python 的区别？高频对比

Java：可达性分析——从 GC Roots 沿引用链遍历，不可达即死（两次标记 + finalize 缓刑机制已废弃）。引用计数因循环引用问题被 Java 弃用。

Python：CPython 主策略就是引用计数（实时性好），但环收不掉 → 另配分代标记清除 gc 专扫容器对象。Java 分代是为了效率分区，Python 分代是为了给引用计数补刀——出发点和 Java 完全不同。

Minor GC 和 Full GC 的触发条件？什么时候对象进老年代？超高频

Minor GC：Eden 满。Full GC：老年代空间不足、元空间不足、System.gc()、空间分配担保失败、CMS 并发失败退化。

进老年代四条路：①年龄 ≥ 15（MaxTenuringThreshold）；②动态年龄判定（同龄对象总大小超 S 区一半）；③大对象（PretenureSizeThreshold）直达；④空间分配担保时整体转移。

CMS 和 G1 的区别？必考

①堆布局：CMS 传统连续分代，G1 Region 化（~2048 块，逻辑分代）；②算法：CMS 标记-清除（碎片化），G1 整体整理+Region 间复制（无碎片）；③停顿：CMS 尽力而为，G1 有可预测停顿模型（MaxGCPauseMillis），按 Region 回收价值优先收垃圾最多的块；④并发标记：CMS 增量更新 vs G1 SATB；⑤大对象：G1 有 Humongous Region；⑥适用：CMS 小堆（JDK 14 已移除），G1 大堆（JDK 9+ 默认）。

什么是三色标记？漏标怎么发生、怎么解决？难点

并发标记时对象分三色：白（未扫，最终仍白=垃圾）、灰（自身已扫字段未扫完）、黑（全扫完不重扫）。漏标 = 死对象判断反了的反面：活对象被当垃圾，需同时满足：①灰色到白色的引用被删；②黑色对象新增了到白色的引用。CMS 增量更新堵②（记黑→白新引用，重新标记重扫）；G1 SATB 堵①（删引用时记旧快照，宁留浮动垃圾不漏标）。

强软弱虚四种引用？高频

强：永不回收；软（SoftReference）：内存不足前回收，做缓存；弱（WeakReference）：只要 GC 就回收，ThreadLocalMap 的 key、WeakHashMap；虚（PhantomReference）：不影响生命周期，唯一作用是对象被回收时进 ReferenceQueue 发通知——DirectByteBuffer 用它管理堆外内存的释放。

内存泄漏和内存溢出的区别？说说你排查 OOM 的思路。项目向

泄漏是无用对象仍被引用收不掉（原因），溢出是分配时空间不够抛 OOMError（结果）；泄漏累积导致溢出。

排查：①事前开 -XX:+HeapDumpOnOutOfMemoryError；②jstat -gcutil 看 GC 后老年代是否回落（不回落=泄漏嫌疑）、jmap -histo 看实例数 Top；③MAT 打开 hprof：Leak Suspects → 支配树找大对象 → Path to GC Roots 找持有者 → 定位代码。常见根因：静态集合无界、ThreadLocal 在线程池中未 remove、资源未关闭、可变 key。

对象一定分配在堆上吗？难点

不一定。JIT 逃逸分析（JDK 7+ 默认开）判定对象不逃逸出方法时，做标量替换：对象不真正创建，拆成局部变量放在栈帧里，方法结束即消失，零 GC 压力——所以"Java 对象都在堆上"在 JIT 优化后不绝对。逃逸的对象在堆上走 TLAB（线程私有缓冲，指针碰撞无锁分配）→ 大对象直接老年代，其余 Eden 出生。
