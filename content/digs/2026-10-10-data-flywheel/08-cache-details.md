## A1 · 第2轮

## 模块六：缓存细节

### Q19 为什么 >256KB 不进内存 / Redis 挂了 / 大对象怎么办

**为什么不进内存**：内存 LRU 预算 64MB、256 条。一条 256KB 的检索结果 = 普通结果（几 KB~几十 KB）的**几十倍体积**——几条大对象就能把整个 LRU 挤爆：**一条大冷门逐出几十个小热点**，命中率崩盘。这是 LRU 的经典缺陷（对大对象不公平），Redis 侧无所谓（128MB 硬顶 + allkeys-lru 兜底，按内存总量管理而不是条数）。

**Redis 挂了（实测代码路径，`cache.py:74-93, 156-171`）**：`get()` 时 ping 失败 → `_redis_ok=False` + 审计 `cache.degrade`（**每轮故障只打一次**，不刷屏）→ 之后所有请求只查内存 LRU → 内存 miss 直接回源真实检索。**不 crash、不用重启；Redis 恢复后**——异常路径会把 `_redis_ok` 重置为 None，下次调用重新探测，**自动恢复**。另外 `socket_timeout=2s`：Redis 挂死（不拒连接）时每个请求最多卡 2 秒，不会被吊死。

**大对象 Redis 挂了是不是只能走原流程**：对——大对象从来没进过内存层，Redis 读不到就回源。但要澄清：这不是“降级退化”，**回源本来就是大对象的常态**（Redis 只是在它命中时省一次检索）；降级丢掉的只是 Redis 层的加速，**正确性永远无损**。fail-open 哲学：缓存的所有故障模式都收敛为“慢一点”，而不是“错”或“挂”。

### Q20 “整组失配，粒度粗，TTL 兜底”啥意思

场景拆开就懂了：

```
Agent 全局检索一次查 5 个 KB
key 的版本维度 = {kb1:v3, kb2:v1, kb5:v2, ...}   ← 5 个 KB 的版本拼成一整个组合

现在 kb2 导入新文档 → kb2 的 cache_version 从 v1 → v2
新 key = {kb1:v3, kb2:v2, kb5:v2, ...}   ← 组合里任何一项变，整个 key 就变

后果：只有 kb2 变了，但之前缓存的检索结果（哪怕结果其实只跟 kb1/kb5 相关）
      全部失配 → 白白重算
```

**为什么不能按 KB 分开缓存**：检索是跨 KB **融合排序**（RRF）的——最终 Top-K 是 5 个 KB 的候选混在一起排的，没法把结果拆回“每个 KB 贡献了哪几条”分别缓存。融合层的缓存天然只能整组失效。

**为什么可接受**：① 失配 ≠ 错误，只是**多算一次**（正确性无损，fail-open 语义）；② 全局检索是低频路径；③ 600s TTL 让旧 key 自然过期，不会无限堆积；④ 嵌套 key（按 KB 分别缓存+合并层）能解决但复杂度不值当。这是**失效粒度 vs 实现复杂度**的显式取舍，诚实声明里写明。业界同族问题：HTTP 缓存的 `Vary` 头、CDN cache key 设计——缓存键粒度是缓存设计的通用难题。

## Q2 · 第3轮 · 追问

② 全局检索是低频路径；③ 600s TTL 让旧 key 自然过期，不会无限堆积；④ 嵌套 key（按 KB 分别缓存+合并层）能解决但复杂度不值当。全局检索不是高频路径。因为在 Agent 部分，应该会有一个工具用于获取相关的知识库及其描述，对吧？
首先，根据问题可以去进行对应库的检索，就不需要去做全局检索了。而且，如果针对单库进行检索，它的缓存也是单库的，对吧？
总之，全局检索使用这种缓存机制，是时效粒度和实现上难度的一种取舍：虽然粒度大一点，但复杂度小。而且，也没有必要完全把全局检索也做成单库的缓存。

## 7. 全局检索低频的确认

你的判断符合项目实际，而且逻辑链比我原文更完整：Agent 检索路径有**选库前置**（根据问题定位到相关 KB 再单库检索）→ 全局检索（跨库融合）只是兜底路径 → 单库检索的缓存版本维度就是 `{kb: v}` 一条，**失效粒度天然精确**；整组 key 失配的代价只落在低频的全局路径上。

你的总结可以直接当面试话术：“全局检索的缓存是**时效粒度与实现复杂度的取舍**——粒度粗一点，但省掉了‘按库拆分+融合层合并’的复杂度；而且以它的调用频率，不值得做精细缓存。” 补一句升级路径备用：如果全局检索变高频（比如多 KB 场景成为主流），升级方案是**两级缓存**——每库 Top-K 独立缓存（精确失效）+ 融合结果缓存（粗粒度兜底）。
