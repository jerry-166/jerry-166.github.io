## A1 · 第3轮

## C 组：协作路径

### ② 贡献给哪个共享库？随便挑吗？

**不是随便，两个硬约束**（`api/faq.py:214-231`）：

1. **只能提给“我可见的”共享 KB**——`check_kb_permission` 校验：你的 KB、分享给你的 KB 才行。不可见的库连检索都进不了视野，自然也不该能投稿。
2. **不能提给自己的 KB**——API 直接 400：“自己的知识库请直接补全，无需 PR”（走直写路径，何必绕队列）。

UI 上的对应设计（设计文档 §2.1）：提 PR 时弹“选择目标共享 KB”下拉，**候选集就是“我对其有权限的共享 KB 列表”**——前端把约束翻译成了选择框，后端再做一次校验（前端约束是体验，后端约束是安全，两层都要有）。

### ⑫ 反刷机制展开（Stack Overflow 模型怎么映射过来）

先立框架：**反刷的本质是让“伪造热度”的成本 > 收益**。四条可行路径，按落地难度排序：

**1. 热度来源去重（最贴近现状，改动最小）**
现状 `increment_faq_hit` 是无脑 +1——同一用户连续问 3 次就能刷过共享库阈值 3。改法：热度累计时带 user 维度，**同一 user 对同一 FAQ 在时间窗内只计 1 次**。实现：PG 加 `faq_hit_log(faq_id, user_id, hit_at)` 唯一约束表，或 Redis `SETNX faq_hit:{faq_id}:{user_id}` + TTL。一次查询变一次“插入或忽略”，成本可控。这一条就把“单人刷”堵死了，剩下的只有“多人合谋”。
**2. per-user 速率限制（拦异常行为模式）**
`supplement` 接口按 user+KB 维度限频（如 10 条/小时）。刷热度的前置动作是高频补全/提问，速率限制在入口就掐断。实现是标准中间件（Redis 滑动窗口），不碰业务逻辑。
**3. 声誉分（Stack Overflow 的核心，长期方案）**
SO 的公式：**参与度 → 声誉 → 权限**（提问/投票/编辑/审核权限逐级解锁）。映射过来：用户的“PR 历史 merge 率、补全存活率（提交后未被 delete/demote 的比例）、被引用次数”聚合成声誉分 → **高声誉用户自动获得共享库直写权**（`can_write_directly` 从静态授权变成动态授予）→ 低声誉用户走 PR。这就是 GitHub trusted contributor / SO trusted user 的同构：**用历史行为给信任定价，信任换写入权限**。
**4. 异常检测（audit 是数据基建）**
这就是审计事件的隐藏价值（呼应 F 组⑨）：`faq.candidate_create` / `faq.aggregate` 事件流里有 user_id + 时间戳——规则引擎扫“同 user 短窗口大量命中同一 faq”、“多账号同 IP 交替补全”就能发现刷量。**反刷不是新造监控系统，是审计数据的第二个消费方。**

诚实边界：当前一条都没实现（audit 留痕是唯一的威慑——事后可查）。面试讲这题的姿势：承认空白 → 给出分层方案 → 点出“审计是反刷的地基”这个体系视角。

## A2 · 第4轮

## ① per-user 速率限制到底是啥意思？逐词拆

**"维度 = user + KB"**：限流的计数钥匙不是“每秒总请求数”，而是 `(user_id, kb_id)` 组合——限制的是“**同一个用户对同一个知识库**，一小时最多补全 10 条”。不同用户互不影响，同一用户换不同 KB 也各自计数。

**为什么能反刷**：刷热度的动作链 = 反复提问（给 candidate 计热度）或反复补全（触发聚合）→ 无论如何都是**高频请求**。限流卡在 API 入口，第 11 次请求直接被 429 拒之门外，`faq_service` 里的热度代码根本没机会执行——**在门口拦，不在屋里追**。

**"滑动窗口"是什么**（对比固定窗口就懂了）：

```
固定窗口（每小时清零）的漏洞：
  10:59 刷 10 条（本小时额度用完）→ 11:01 再刷 10 条
  → 窗口边界两分钟内冲了 20 条，但每个窗口看都"没超"

滑动窗口：以"现在"为原点，往前看完整的 1 小时
  每次请求先扔掉 1 小时前的时间戳，再数剩余数量
  ┌──────────── 往前 3600 秒 ────────────┐
  │ ●●●●●●●  ← 最近的请求时间戳队列       │
  └──────────────────────────────────────┘
  队列里 ≥ 10 个 → 拒绝；否则 append 本次时间戳
  → 任意时刻往前看 1 小时都不超 10，无边界突刺
```

Redis 实现就是三板斧原子操作（Lua 脚本包起来）：`ZREMRANGEBYSCORE` 清窗口外时间戳 → `ZCARD` 数量 → `ZADD` 写入。

**"标准中间件，不碰业务逻辑"**：实现位置是 FastAPI 的 dependency（和现有的 `get_current_user` 鉴权同一层）——`supplement` 路由前挂一个检查函数，`faq_service.py` **一行都不用改**。这类需求叫**横切关注点**（cross-cutting concern）：鉴权、限流、日志、审计都是“每个接口都要但和业务无关”的东西，单独放一层，业务代码保持干净。

## ② 你的“FAQ 配置中心”构想：方向对，而且一半已经存在

你的提议拆开是两件事：**库主批量导入 FAQ + 直接生效**。先看已存在的语义——

`merge_pr`（PR 合并）做的就是这件事：库主审核通过 → `add_faq(status='active', distill_threshold=1)`——**库主的"yes"直接跨过热度闸门**。所以配置中心本质 = 给库主开一个“批量自我审核”的入口，**复用已有语义，不新增权限模型**。补齐的部分：批量接口、0.95 判重（导入时遇到已有近似条目 → 聚合或跳过）、`source='bulk_import'` 审计、蒸馏可选（导入的通常是精心整理过的，不需要 LLM 改写）。

你这个想法还贡献了一个反滥用设计的重要原则（我上一轮没讲到，你补上了）：

> **给正当需求开正门，歪门才好堵。**

库主“想让团队 FAQ 快速生效”是**合法的高频需求**——这个需求如果只能靠“补全+手动逐条 promote”满足，就把正常流量和恶意流量混在了一起，异常检测的信号被污染。配置中心把合法需求分流走之后，**剩下还在高频补全/提问的行为，恶意概率大幅上升**——异常检测的精确度反而提高了。这和验证码的哲学同构：让正常用户走最容易的路，卡住的那批人才值得怀疑。

**顺带把“刷热度攻击面”精确化**（你说的“别人去刷共享库”，具体是谁能刷）：

| 攻击者 | 能不能刷 | 原因 |
|---|---|---|
| 无直写权被分享者 | ❌ 刷不了热度 | 只能提 PR，PR 是隔离舱（从未产生 faq 行） |
| 有直写权 collaborator | ⚠️ 能刷 | 补全种 candidate（阈值3）→ 自己问 3 次 → 蒸馏升格 → 全员可见 |
| **任何被分享者（含只读）** | ⚠️ **更隐蔽** | `try_faq_hit` 对 candidate 命中**任何可见者都 +1**——反复提问同一问题就刷热度，连补全都不用 |
| 库主自己 | 无所谓 | 他本来就有 promote 直通权，刷不刷权限等价 |

所以热度去重（A1）和速率限制（A2）的真正目标：**collaborator 的补全刷 + 被分享者的提问刷**。这两条都已进缺口文档 A 组。

## 本轮记忆锚

1. **“滑动窗口 = 以现在为原点往前看一小时”**——固定窗口有边界突刺，滑动窗口没有。
2. **“正门开好，歪门才好堵”**——你的配置中心构想的反滥用价值：分流合法高频，剩余高频更可疑。
3. **“提问也能刷热度”**——任何被分享者反复问同一问题就给 candidate +1，比补全刷更隐蔽；热度 user 维度去重是第一优先。
4. **“03§7 就是手工回归集”**——你项目里已经做过一次 prompt 回归测试，缺的只是制度化成 CI。
5. **“换房卡，不拆门锁”**——bump 版本 = 换 key；旧缓存自然死，读路径零失效代码；失效粒度选粗不选细。
6. **“能增量不重启，必须重启就滚动”**——运行时刷新谱系 + 就绪门兜底。
