第 2 章 · HTML 五问

你的五道自查题：四道已经拿捏，一道（div vs section）是所有人的共同盲区。先解决它，再把另外四道补上"能加分的一句"。

Q1 · div 和 section 都能当盒子，什么时候用哪个？重点讲透

主册说 section 是"自带含义的盒子"，行为上和 div 一模一样——所以你的困惑完全合理：既然长得一样，浏览器又不管，我凭什么要多想一步？答案是：语义化标签不是写给浏览器看的，是写给三种"读者"看的：读屏软件（视障用户靠它念出"这是一个区域标题"）、搜索引擎（理解哪些是正文主体）、半年后的你自己和同事（扫一眼结构就知道页面骨架）。

判定标准就一条，三问定夺：

  • 这块内容有没有一个自己的主题？有，且通常配得上一个标题（h2/h3）→ 用 section；
  • 它是不是一篇"独立成篇、脱离页面也说得通"的内容？（一篇文章、一条评论、一张商品卡）→ 升级用 article；
  • 它只是"为了布局/分组/挂样式"才存在的？→ 用 div，没有心理负担。

对应到你熟悉的场景：一篇博客的正文是 article，正文里的"评论区""相关推荐"是 section，而"把左边的图和右边的文字排成两栏"的那个壳，什么都不是，就是 div。主册那句"想不出该用什么标签时用 div，绝不算错"的完整含义是：语义化是加分项，不是纠错项——用 div 代码照样跑，用对了 section 是对读屏用户和 SEO 的善意。

一句话记忆

有主题配标题 → section；独立成篇 → article；纯布局分组 → div。拿不准就 div，没有人会因此扣分。

Q2–Q5 · 你已经答对的四道，各补一句"加分话"

你的回答：span 上色、alt 加载失败时显示、radio 靠同名 name 成组、id 唯一而 class 可多选——全部正确。下面各补一个面试/实战的进阶点：

  • span 上色：span 是"行内的无意义盒子"，专门包一小段文字单独上样式。你在段落里写 <p>今天<span style="color:#D93025">限行尾号 3 和 8</span>，注意绕行</p>——span 不打断文字流，这是它和 div（会强制换行感）的本质区别。
  • alt：除了图挂了显示，它还是读屏软件念给视障用户听的内容，所以 alt 应该写"描述图片内容"而不是"图片1"。装饰性图片才允许 alt=""（明确告诉读屏：跳过我）。
  • radio 同 name：补一个对偶知识点——checkbox 天然允许多选，不需要共用 name 也各自独立；radio 必须同名才互斥。表单提交时，被选中的 radio 的 value 会以 name=value 形式提交。
  • id vs class：再补一层——一个元素可以同时挂多个 class（空格分隔：class="card active"），但 id 只能有一个；CSS 里 id 选择器权重 100 远高于 class 的 10（第 3 章展开），所以现代实践反而倾向"样式全挂 class，id 只留给 JS 精确查找"。

Q1 · 优先级：能理解成"从上到下依次覆盖、越接近内容优先级越高"吗？方向对，机制错
我可不可以理解成它是一个从上到下的依次覆盖，或者说优先级依次变高？越接近这个内容，它的优先级越高……以及那几个规则不太懂，排查口诀我看 style 面板也没有被划掉什么的。

你的直觉"内联 > ID > 类"的排序是对的，但"越接近内容优先级越高"这个因果是错的——内联样式赢不是因为它"贴得近"，而是因为它算分高。机制必须说精确，因为它决定你会不会掉进一个著名陷阱：

  • 规则一（算分）不是十进制加法，是三元组逐位比较。主册写"内联 1000 / id 100 / class 10 / 元素 1"是速记法，方便日常心算；但真实的比较方式是把一个选择器数成 (id 数, class 数, 元素数)，从左往右逐位比，左边大的直接赢。陷阱在这：.a .b .c .d .e .f .g .h .i .j .k（11 个类）vs #one（1 个 id）——按速记算是 110 > 100，类赢？错！三元组是 (0,11,0) vs (1,0,0)，第一位 0 < 1，id 赢。多少个 class 都堆不过一个 id，这就是"逐位比较"的含义。
  • 规则二（就近）的"近"是指源码顺序，不是距离。分数相同时，写在 CSS 文件后面的那条赢——是"文件的后面"，不是"离元素近"、"嵌套得深"、也不是"选择器里离标签名近"。你说的"从上到下依次覆盖"只在同分时才成立；分不同，顺序根本不参与比较（主册"玩起来"那题就是验证这个：p 挪到 .box p 下面，绿色不变）。
  • 规则三（!important）：跳过所有算分直接登顶，代价是"没人能管它了"——除了另一个 !important 再比谁靠后。所以它是调试的核武器、正式代码的坏味道。

完整的一条其实是四级瀑布：!important → 内联 style → 选择器算分（三元组）→ 同分比源码顺序。浏览器对每个属性独立走这条瀑布，赢的那条的值生效，输的才被划掉。

Q2 · margin 上下相遇合并：为什么？机制 + 边界
盒模型那块的主要问题，就是这个 margin 上下相遇会合并取较大值，然后它俩的间距就是最大值的，这个我测试了一下。

你测出的现象是对的：两个上下相邻的块级元素，上者的 margin-bottom 和下者的 margin-top 不相加，取较大者作为间距。但"为什么"值得讲透，因为规则有明确边界，知道了边界你才能预测它什么时候不发生：

  • 为什么这么设计：margin 的语义是"我和别人之间至少保持的距离"，不是"我贡献的间距"。段落 P1 说"我下面要 16px"，P2 说"我上面要 24px"——两个人商量社交距离，取双方要求的较大值 24px，而不是叠成 40px。这是排版系统的传统（印刷排版就叫 margin collapse），CSS 继承了下来。
  • 只在三个条件下发生：① 上下方向（左右永不合并）② 普通文档流的块级盒子之间（flex/grid 子项之间永不合并；浮动、绝对定位元素不合并）③ 同一个 BFC 里相邻（下一问 BFC 展开）。
  • 三种合并场景：相邻兄弟（你测的这种，取 max）；父元素和第一个/最后一个子元素（子元素的 margin-top 会"穿透"没有边框/内边距的父元素，直接把父元素顶下去——九成"奇怪的间距"其实是这种）；空块自己上下 margin 合并。
  • 实用结论：现代开发里你几乎不用背这些——用了 flex 布局 + gap 就根本不会遇到合并（主册推荐 gap 替代 margin 互挤的原因）。真正要会的是：看到"间距比预期小"，第一反应检查是不是 margin 合并。

Q3 · 3.5 单位："我太不能理解"换个讲法
3.5 单位那块我太不能理解。

单位难的根源：它们全是相对单位，但"相对谁"各不相同。表格记不住是因为没有锚点，下面给每个单位一个"人设"，然后你拖滑块亲眼看：

  • px · 定海神针：绝对单位，写多少是多少。边框、图标、小间距用——这些地方你不希望它跟着别的什么缩放。
  • % · 看爹单位：相对父元素同方向的尺寸。width: 50% = 父宽度的一半。两个坑：① height: 50% 在父高度是 auto 时直接失效（爹都没有确定高度，50% 无从谈起）；② padding 和 margin 的百分比一律按父元素的"宽度"算，哪怕你写的是上下方向的 padding-top——历史遗留，记住即可。
  • rem · 全站音量键：相对根元素 html 的字号（默认 16px），1rem = 16px，1.5rem = 24px。为什么存在：用户在浏览器设置里调大字号（视障用户常干），rem 跟着响应，px 无动于衷。全站缩放 = 只改 html 一个字号。
  • em · 看自己单位：相对当前元素的字号。组件内部用（padding: 0.5em = 半个字的高，字号变大留白自动变大）。经典坑：嵌套时层层累乘——列表里套列表，每层 1.2em，三级就是 16→19.2→23px 越缩越大。
  • vw / vh · 屏幕比例尺：视口（浏览器可视区域）宽/高的 1%。height: 100vh = 恰好一屏高，全屏首屏标配。
选择直觉（够用了）

正文/间距用 rem（跟用户走）；边框小图标用 px（钉死）；宽度自适应容器用 % 或 fr；一屏高度用 vh。em 知道含义即可，少用。

Q4 · inline-block 同行但一高一低，怎么回事？基线对齐
3.6 的 inline-block，我看见它可以放在同一行，但是位置又不对齐，一个偏上，一个偏下，这是怎么回事？

你撞上的是 inline 世界的一个隐藏规则：基线对齐（baseline）。机制一句话：凡是在一行里排队的东西（inline / inline-block），默认都按"文字基线"对齐——基线就是你写字时字母"坐"的那条隐形线（x 的底、j 的尾巴穿过它）。问题在于 inline-block 的基线怎么定：

  • 盒子里面有文字 → 基线 = 最后一行文字的基线（和旁边文字对得很整齐）；
  • 盒子里面没有文字（比如放图片、或者空盒子）→ 基线 = 盒子的下边缘（margin-box 的底）。

于是一个经典错位出现了：同一行里，A 盒子有两行字、B 盒子只有一行字、C 是个空盒子——三个盒子都想把自己的"基线"对到行内那条公共基线上，结果 C 的整个底边贴着基线（看起来飘在半空），A 的第二行文字坐在基线上（第一行顶得很高），B 看起来居中偏上。不是 bug，是三个盒子在各自履行基线对齐。

修复：给 inline-block 元素显式改对齐方式 vertical-align: middle（按中线对齐，最常用）或 top（顶边对齐，做卡片墙最整齐）。另一个现代解法：父容器直接 display: flex; align-items: center——flex 子项默认拉伸对齐，基线问题整个消失（这也是"flex 取代排队规则"的又一实例）。

Q5 · "flex 开启后，display 的规则就被取代了"是什么意思？要精确化
还有 Flex，它是自身布局是吧？它开启之后，display 的规则就被取代了？

主册这句话容易读出偏差，精确版是：flex 接管的是"孩子们怎么排队"，不是"孩子们是什么"。拆开说：

  • 你在父元素上写 display: flex，发生两件事：① 这个父元素自己变成一个块级的 flex 容器；② 它的所有直接子元素被强制变成 flex 子项——不管它们原来是 div（block）还是 span（inline）。
  • "取代"指的是：子项在父容器里怎么排队，不再由子项自己的 display 说了算。原来 div 独占一行、span 挨着排的"文档流规则"失效，改由 flex 容器的规则统一管理：沿主轴排、可伸可缩、用 gap 间隔。副作用还有一个好东西：flex 子项一律"块化"——span 做了 flex 子项后也能设宽高了。
  • 但子项自己内部的 display 完全不变：一个 div 子项里面再放 p 和 span，p 还是独占一行——flex 只管一层（它的直接孩子），不隔代指挥。
  • "它是自身布局"的理解也要修正：flex 不是"自身布局"，是"父开关、子生效"的一套体系——display/flex-direction/justify-content 写在父上（容器属性），grow/shrink/basis/align-self 写在子上（子项属性）。主册 3.7 那张属性卡的分类就是这个用意。
Q6 · flex-basis 是什么？shrink 和 basis 什么关系？flex:1 到底是啥？核心讲透 + 计算器
3.7 子项属性的 align-self、flex-basis 是什么意思？我看样例里 flex:1 就相当于 shrink 和 grow 为 1、basis 为 0%。看不懂 shrink、basis 的关系。

这三个属性（grow / shrink / basis）必须当成一个算法的三步来学，单独背必懵。浏览器把一排 flex 子项的宽度算出来，走的是固定的三步流水线：

  • 第一步 · 定基准（basis）：每个子项先领一个"基准宽度"。flex-basis 就是领基准的指令：200px 就领 200px；auto 就按自己的内容宽度（或 width 值）领；0% 就领 0——假装自己什么都不需要。这就是 flex:1 的精髓：basis 归零，起步一无所有，全靠第二步抢空间。
  • 第二步 · 算剩余：剩余空间 = 容器宽 − Σ所有基准 − 所有 gap。剩余 > 0（有富余）→ 走第三步 A；剩余 < 0（超支了）→ 走第三步 B。
  • 第三步 A · 分赃（grow）：富余空间按 grow 比例分。你 grow=1、我 grow=1，平分；你 2 我 1，你拿 2/3 我拿 1/3。grow=0 的一分不分，保持基准宽。
  • 第三步 B · 还债（shrink）：超支的部分按 shrink 分摊，且分摊权重 = shrink × 基准宽（基准大的多还——这就是 shrink 和 basis 的"关系"：它俩相乘才决定谁被压得多）。shrink=0 打死不缩。

所以 flex: 1 = 1 1 0% 读作："基准为零、有富余全按比例抢、超支了也按比例认压"——它和 flex: auto（= 1 1 auto，"先按内容占位，再分富余"）的行为完全不同：flex:1 是"绝对平均主义"（大家起点都是 0），flex:auto 是"先富后补"。侧边栏 flex: 0 0 220px 读作："不抢、不缩、固定 220"。

align-self 是另一条线：容器上的 align-items 给所有子项定交叉轴对齐，align-self 写在某个子项上让它"不服集体安排"，值同 align-items（center / flex-start / flex-end / stretch）。典型场景：一排按钮统一底部对齐，唯独某个要单独居中。

Q7 · static 是什么？为什么父子上 z-index 不生效？层叠上下文
3.8 定位不懂 static 默认值，还有 z-index 的层叠。我明明给 anchor 以及它内部的 badge 都写了 z-index，但他们还是原来的样子；但是复制两个同级角色改 z-index 可以；父子关系就不行。

你的实验做得非常好——"同级可以、父子不行"，这八个字正是层叠上下文（stacking context）的全部要害。先讲 static，再讲透这个。

  • static 的含义是"未定位"：position 的默认值，元素老老实实在文档流里排队。它带来三个直接后果：① top/right/bottom/left 写了也完全无效；② z-index 写了也无效（所以主册说"先加 position，z-index 才生效"——准确说是 z-index 只对定位元素和 flex/grid 子项生效）；③ absolute 的子元素往上找"参照祖先"时会跳过它。实践里几乎从不显式写 static，它的存在意义就是"什么都不设"的缺省态。
  • 层叠上下文是什么：一个"独立结算的图层"。浏览器画页面时，谁盖谁本来只看 DOM 顺序和 z-index；但某些元素会创建出一个新的独立图层，规则变成：图层内部的 z-index 只在图层内部比大小；整个图层作为一个整体，再和别的图层比。类比：楼层里的房间号（内部 z-index）决定不了你这栋楼和隔壁楼谁高——楼的高度（外层 z-index）在楼建好时就定了，房间号再大你也出不了这栋楼。
  • 什么会创建图层（常见的五种）：① 根元素 html；② position: relative / absolute 且 z-index 不是 auto（你给 .anchor 设了 z-index，正是这一条！）；③ position: fixed / sticky（自动创建）；④ flex / grid 的子项设了 z-index（哪怕 position 是 static）；⑤ opacity < 1、transform 非 none 等。

回到你的实验：你给 .anchor（父）写了 z-index → .anchor 立即建起一栋"楼"；.badge（子）的 z-index 再大，也只是这栋楼里的房间号，它永远无法越过 .anchor 这栋楼去和页面上的其他元素比高低。而你复制两个"同级角色"改 z-index——它们是两栋平行的楼，直接比楼高，当然有效。结论：子元素的 z-index 出不了父元素的层叠上下文；想让子元素参与全局竞争，父元素就不能创建层叠上下文（比如 relative 不配 z-index 就是 auto，不建楼，孩子直接上全球榜）。

Q9 · BFC 详细讲讲，不要缩写完整拆解
BFC 你要给我详细讲讲是啥呀？它这个概念是啥呀？你不要缩写。

好，不用缩写。BFC 全称 Block Formatting Context，中文：块级格式化上下文。逐词拆开：

  • 块级（Block）：管的是块级盒子（div、p 这种独占一行的）怎么排；
  • 格式化（Formatting）：即排版规则——盒子怎么定位、大小怎么算、 margin 怎么算，都有一套规则；
  • 上下文（Context）：一块独立结算的排版区域。

连起来的定义：页面排版不是一张大桌子上进行，而是被切成一个个独立的"包间"。每个包间内部按自己的规则排版，包间里面的浮动、margin 合并等"内部事务"，一律不出包间的门。根元素 html 天然是一个大包间；而某些 CSS 属性会让某个元素自己开一个新包间，这就是"创建 BFC"。

什么操作会开新包间（常见的五种）：

  • 根元素 html（整个页面那个最大的包间）；
  • float 不是 none（浮动元素自己开包间）；
  • position: absolute / fixed（脱离文档流，自己开包间）；
  • overflow 不是 visible（最常用的是 overflow: hidden——经典 hack）；
  • display: flow-root（现代标准做法：这个值被发明出来就为了干这一件事，没有任何副作用；flex / grid 容器同理自成体系）。

包间规则带来三个可观测的效果（也是它全部的实用价值）：

  • ① 包住内部浮动（最著名）：子元素全浮动后父元素高度塌陷（父元素只算得到不浮动的孩子）。给父元素开包间（display: flow-root），浮动孩子的高度被算回来——所谓"清除浮动"的原理。
  • ② 隔绝 margin 合并：包间自己的 margin 不和包间里孩子的 margin 合并（Q2 说的"父与子合并"用 overflow: hidden 破掉，就是靠这个）；相邻兄弟想不合并，让其中一个开包间即可。
  • ③ 不与旁边浮动重叠：包间的边界盒会避开旁边的浮动元素——经典"左侧固定浮动图 + 右侧自适应文字不环绕"两栏布局，就是给右侧开包间实现的。
给后端的类比

BFC ≈ 进程的独立地址空间：包间内部怎么折腾（浮动、margin 合并）不影响外部；开一个新包间 ≈ fork 出一个隔离的子进程。主册 3.9 把它标成"遇坑回填"是对的——你现在知道了机制，等真遇到"高度塌陷 / 间距诡异 / 文字环绕"三种坑，回来对症下药：display: flow-root 一行解决。

Q1 · querySelector 和 getElementById 到底返回什么？概念要摆正
querySelector(div/#id/.类)，getElementById（id）返回selector/element

你的表述里"返回 selector/element"把两个东西混在一起了。摆正：它们都返回"元素"（DOM 节点对象，也就是 Element），区别只在"你用什么写法找到它"：

  • document.querySelector("#msg") —— 参数是任意 CSS 选择器字符串（所以要带 # 或 .），返回第一个匹配的元素；一个都没有返回 null。弟弟 querySelectorAll(".item") 返回全部（NodeList，可用 forEach 遍历）。
  • document.getElementById("msg") —— 参数只填 id 名，不带 #（因为它只认 id，不需要选择器语法），返回那一个元素或 null。
  • 拿到的东西一模一样：一个 Element 对象，身上挂着 .textContent / .style / .classList / .value 这些属性，随你操作。

所以你的笔记应该改成："querySelector 按 CSS 选择器找（写法要 # .），getElementById 只按 id 找（不带 #）；两者都返回 Element 元素对象"。实战用 querySelector 全家桶即可——一个 API 走天下。

Q2 · "el.style 不是内联吗，不影响吧？"——为什么推荐 classList？好问题，正面回答
不知道，el.style不是内联吗，不影响吧？

你的直觉完全对：el.style.color = "red" 确实是在给元素加内联样式（优先级 1000，压过所有 CSS 规则）。但正因为"它总能赢"，才是问题所在——推荐 classList 不是因为它打不过内联，而是：

  • ① 赢了就下不来台：一旦 JS 写入内联样式，CSS 里的任何规则都盖不住它了（除了 !important）。你后想在 CSS 里改个主题色、加个响应式覆盖，全被 JS 写死的内联值挡死——样式被锁死在 JS 代码里。
  • ② CSS 的看家本领全部失效：:hover 伪类、@media 媒体查询、过渡动画，这些只能写在 CSS 规则里。样式全走 el.style，等于放弃了 CSS 一半的能力。
  • ③ 一次只能改一个属性，且很难撤销：改 5 个样式要写 5 行；撤销还得手动 el.style.color = "" 清空。而 classList 一个开关切换一整套样式。
  • ④ 分层洁癖（前端第一审美）：CSS 管外观全貌（.active 长什么样），JS 只管状态（"现在是不是 active"）——样式写在 CSS 里，JS 只拨开关。将来改样式去 CSS 找，改逻辑去 JS 找，互不干扰。

el.style 的合理场景只有一种：运行时才能算出来的动态数值——拖拽的位置、进度条百分比、随机偏移。这类值没法预先写进 CSS 类，就该 el.style 上。记住分工：状态切换用 classList，动态数值用 el.style。

Q4 · 事件冒泡：到底是谁触发了几次？怎么处理？机制 + 两种处理姿势

你的机制描述正确。先把"触发两次"说精确，再回答"怎么处理"：

  • 冒泡本身不产生"两次"：事件发生时，浏览器从最深的元素（e.target）开始，沿 DOM 树向上逐层"通知"。每一层要不要有反应，取决于那一层挂没挂监听器。所以"点一次触发两次"的精确原因是：冒泡路径上挂了两个监听器（比如按钮上一个、父容器上一个），各触发一次——不是事件被触发两次，是两个监听器各自听到了一次。
  • 处理姿势一 · 拦截（stopPropagation）：在子元素的监听里调 e.stopPropagation()，事件到此为止不再上浮。适合"子元素的点击不该惊动父级"（弹窗内点击不该关闭弹窗）。注意它和 preventDefault 是两码事：一个拦"传播"，一个拦"默认行为"（见 Q6）。
  • 处理姿势二 · 利用（事件委托）：反着来——故意只在最外层挂一个监听，让所有子元素的点击都冒泡上来统一处理。第 6 章项目里 listEl 只挂一个 click 就是这个姿势：列表有一万项也只挂一个监听器，动态新增的项天然被覆盖（不用再单独绑定）。用 e.target 判断"点的是谁"，用 closest() 找到有意义的祖先。
  • 什么时候用哪个：子元素行为和父元素冲突 → stopPropagation；一堆同类子元素要统一处理 → 委托。你问"是内部做捕获还是外部接收"——两个都存在，就是这两个姿势，按场景选。

  • e.target = 事件真正发生的地方（最深、最具体的那个元素）。你点了按钮里的文字，target 就是那个按钮（或文字节点所在的按钮）。
  • e.currentTarget = 监听器挂在谁身上（处理函数运行时，这个值永远等于你 addEventListener 的那个元素）。
  • 两者的关系就是委托的全部原理：监听挂在 ul 上（currentTarget 永远是 ul），但点击发生在 li 的删除按钮上（target 是那个 button）——于是外层监听既能收到通知，又能通过 target 知道"实际点的是谁"。第 6 章项目里 e.target.closest("li") 就是从实际点击处向上找回 li 的标准动作。

类比后端：target 是"请求真正的发起者"，currentTarget 是"当前处理这一层的中间件"——请求（事件）一层层往上传，发起者不变，当前处理层在变。

Q6 · preventDefault："默认行为"是谁规定的？"不刷新"是啥意思？两张默认行为清单
preventDefault，就是保持原来的样子吗？"不刷新"是啥意思？

先纠正方向：preventDefault 不是"保持原来的样子"，是"取消浏览器准备做的动作"。拆开讲：

  • "默认行为"是谁规定的？——HTML 规范 + 浏览器实现。某些事件发生时，浏览器除了"通知你的监听器"，还自带一套内置反应：表单 submit → 浏览器把表单数据打包、跳转到 action 地址（没写 action 就刷新当前页）；点击 <a> → 跳转 href；右键 → 弹出浏览器菜单；在输入框按键 → 字符被打进输入框；勾选 checkbox → 打上勾。这些内置反应写死在浏览器里，和你的 JS 无关、也不需要你写一行代码——这就是"哪里规定的"的答案。
  • preventDefault 做的事：告诉浏览器"你的内置反应取消，这件事改由我的 JS 全权接管"。提交表单默认要刷新页面，preventDefault 之后不刷了，数据由 fetch 发给后端；点链接默认要跳转，preventDefault 之后改由前端路由接管。
  • "不刷新"的完整含义：form 的 submit 默认动作 = 浏览器发起一次页面导航（整页重新加载）。整页一刷新，JS 加的所有 DOM、内存里的所有变量全部清零重来——你在待办清单里加的十条任务瞬间蒸发。所以任何"用 JS 接管表单"的代码，第一行必须是 e.preventDefault()，这是主册第 6 章注释里写"阻止页面刷新"的确切含义。
  • 两个易混点：① preventDefault 只拦"默认动作"，不拦"事件传播"（传播归 stopPropagation 管，见 Q4）；② 不是所有事件都可拦（e.cancelable 为 false 的拦不动，比如内存耗尽这种系统事件）。

VM142:4 Uncaught SyntaxError: Identifier 'count' has already been declared

这个报错和主册代码的对错无关，是 Console 的使用方式触发的：你把 5.1 那段代码粘贴运行了第二次。机制拆开：

  • 第一遍运行时，let count = 0 在全局作用域声明了 count，它一直活着；
  • 第二遍粘贴，又执行 let count = 0——JS 规定 let / const 在同一作用域里不允许重复声明（var 允许，这正是 var 的坑之一），于是抛 SyntaxError。语法错误发生在执行之前，所以整段代码一行都不会跑；

解决办法（按推荐排序）：① 用花括号把整段代码包起来再回车——let/const 是块级作用域，每个 {} 都是一个新块，块里的声明不污染全局，想跑几遍跑几遍；② 刷新页面再开 Console；③ 换变量名或改用 var——不推荐，等于绕开规则而不是理解规则。

Q2 · 0.1 + 0.2 ≠ 0.3：能做精确判断吗？三招修法
我知道浮点数有误差，比如 0.1 + 0.2 ≠ 0.3，那么能不能做一个精确的判断

先说透"为什么"，再给三招。原因：JS 的 number 底层是 IEEE 754 双精度浮点（64 位二进制）。二进制表示 1/10，就像十进制表示 1/3——无限循环，存不下只能截断，误差就此埋下。你熟悉的后端一模一样：Python 的 0.1 + 0.2 == 0.3 同样是 False（同为 IEEE 754）；Python 的解药 decimal.Decimal 在 JS 里没有内置等价物，所以前端要靠下面三招：

  • 招 1 · 容差比较（判断相等的标准答案）：不问"是否恰好相等"，问"差值是否小到可以忽略"——Math.abs(a + b - target) < 1e-9。容忍度怎么定：一般业务 1e-9（九位小数内视为相等，金额场景绰绰有余）；理论工具 Number.EPSILON（≈2.22e-16，"1 和它最近的浮点邻居的距离"，是浮点误差的最小刻度）。铁律：浮点运算结果永远不要用 === 直接判等。
  • 招 2 · 整数化（钱的正解，后端人最熟）：金额以"分"为单位存整数，运算全程整数零误差，只在展示时 /100。这就是数据库 DECIMAL / Java BigDecimal 的同一思路：钱不过浮点。
  • 招 3 · toFixed（只管展示，不参与比较运算）：(0.1+0.2).toFixed(2) 得 "0.30"——它是格式化显示工具。两个坑：返回字符串（拿去比较会踩 '5'===5 的坑）；有自己的舍入怪癖（1.005.toFixed(2) 是 "1.00" 不是 "1.01"）。
Console 片段 · 三招一次跑
// 招 1 · 容差比较：判断"是否相等"的标准答案
const sum = 0.1 + 0.2;                   // 0.30000000000000004
Math.abs(sum - 0.3) < 1e-9;              // true  —— 差 5.55e-17，远小于容忍度
sum === 0.3;                             // false —— 浮点和直接判等，永远别这么写

// 招 2 · 整数化：以「分」为单位运算，全程整数零误差
(199 + 201) / 100 === 4;                 // true —— 整数相加无误差，最后只除一次

// 招 3 · toFixed：只管展示。注意返回字符串 + 舍入怪癖
(0.1 + 0.2).toFixed(2);                  // "0.30"（字符串！比较要小心）
(1.005).toFixed(2);                      // "1.00" —— 不是 "1.01"，别拿它做运算
后端对照

Python：Decimal("0.1") + Decimal("0.2") == Decimal("0.3") 为 True——十进制精确运算。JS 没有内置 Decimal（BigInt 只管整数）。实务分工：钱的计算放后端（Decimal/DECIMAL），算好把结果以字符串传给前端，前端只渲染不算账——这也是"浮点判断"在前端大多只需要招 1 的原因。

Q3 · 5.3 的"常用缩写"看不懂，还有别的吗？你的直觉是对的：它们确实"读"不出来
常用缩写有点反直觉，我感觉看不出来那个意思。还有别的吗？我感觉可能不能靠普通理解去理解它。

先给你定性：你的直觉完全正确。这些东西不是"缩写"（abbreviation），是操作符的复用——设计者把已有符号借去表达新语义，字面上根本看不出来。所以"不能靠普通理解去理解"不是你的问题，是所有人的处境：正确学法是"记场景"，不是"读符号"——想干什么的时候查表，用三次就长在手感里了。

先把主册 5.3 出现的两个讲透，再补齐整个家族。它们能这么用的共同底层原因只有一个：JS 的逻辑运算符是短路求值、且返回操作数本身（不是布尔值）——a || b 返回的就是 a 或 b 其中的一个，这才是它能当默认值的全部原理：

  • || 默认值：inputSize || 20 读作"inputSize 是假值就拿 20"。缺陷：0 和 "" 也是假值——用户想查第 0 页，page || 1 会偷偷给他改成第 1 页。于是有了更精准的 ??。
  • ?? 空值合并（|| 的精准版，天天用）：page ?? 1 读作"只有 null / undefined 才拿 1"——0、""、false 原样保留，不再误伤。
  • ?. 可选链：user?.address?.city 读作"一路问过去，哪一环是 null/undefined，整个表达式就地得 undefined，不报错"。它治的是前端最高频报错 Cannot read properties of undefined——后端接口字段缺失时的保命符。
  • && 守卫：cond && fn() 读作"cond 为真才执行右边"。第二册 React 里的条件渲染 {isLoading && <Spinner/>} 全靠它。
  • 三元 cond ? x : y：表达式版的 if-else（JS 里没有 Python 的 x if c else y 写法，三元就是它的对应物）。

Q4 · 展开运算符 ...：抽象记不住？一个动作 + Python 全对照

Q5 · 闭包持有大对象不放 → 内存泄漏：前端和 Python 各怎么处理？机制 + 两端对策
5.7 闭包持有大对象不放手，存在潜在内存泄露怎么办？这个问题在 Python 里面应该也有，Python 中怎么处理？前端怎么处理？

先把泄漏的责任链说准：闭包本身没错，错的是"本该死掉的函数还被人引用着"。链条是：函数活着 → 它的闭包环境（捕获的变量）就活着 → 环境里那个 4MB 的大数组也跟着活着。谁在引用函数？九成是这三样：挂在定时器上、挂在事件监听器上、存进了全局变量/缓存。前端处理就三招：

  • 招 1 · 清理挂载点：clearInterval(id)、removeEventListener(同参数)——把"还在引用函数的那只手"松开。SPA（单页应用）最常见的泄漏就是"组件删了，它挂的定时器和监听器还在"——React 的 useEffect 要求你 return 一个清理函数，就是把这个动作制度化了；
  • 招 2 · 解除引用：用完把变量置 null（leak = null）——引用没了，下一轮 GC 就能回收函数连同它携带的环境；
  • 招 3 · 弱引用：WeakMap / WeakSet（键是弱引用，不阻止回收）——适合"缓存有最好、被回收了也无所谓"的场景，框架内部（Vue 的响应式、DOM 节点关联表）全在用。
代码片段 · 泄漏现场与修法（结构示意）
// 泄漏现场：闭包捕获大数组，定时器一直引用着闭包函数
function start() {
  const bigCache = new Array(1e6).fill("数据");   // MB 级大对象
  return () => bigCache.length;                  // 闭包函数引用着 bigCache
}
let leak = start();                              // 只要 leak 活着，bigCache 就永远活着
const timer = setInterval(leak, 1000);           // 挂在定时器上 → 想死都死不了

// 修法：① 清理挂载点 ② 解除引用 —— 两步之后，GC 下一轮就能回收
clearInterval(timer);    // 定时器不再引用闭包函数
leak = null;             // 全局引用解除 → 函数可回收 → bigCache 随之可回收
Python 对照 · 两套 GC，同一种泄漏

Python 闭包同样捕获变量（存在 __closure__ 的 cell 里），同样"函数活着环境就活着"——机制无差，差别在回收策略：CPython 主要靠引用计数（引用归零立刻回收，比浏览器"定期标记-清除"更及时），但引用计数搞不定循环引用，所以补了 gc 模块做分代扫描——这也是 Python 面试常考的"引用计数 vs 分代 GC"。对策一一对应：Python 的 del x = 前端的"解除引用"（都只是减引用，不是立即释放）；weakref.ref(obj) / weakref.WeakValueDictionary = 前端的 WeakRef / WeakMap；Python 里"定时器/监听器忘清理"对应"atexit、线程、信号处理器忘注销"。两边的教训是同一句话：泄漏的根源从来不是闭包，是忘记解除引用。

Q6 · async/await："把 Promise 写成同步样子"到底是啥意思？三段演进 + 时间线实测
async 和 await，是把 Promise 写成同步样子的语法糖。这个"写成同步样子"需要你再去解释。

看同一段逻辑的三种写法，盯着一个问题："结果还没到时，后续动作登记在哪"：

代码片段 · 同一件事的三种写法
// ① 回调时代：先把"拿到结果后干什么"作为函数交出去 —— 步骤一多就嵌套成地狱
getUser(1, (user) => {
  getOrders(user.id, (orders) => {
    render(orders);                 // 想按顺序做 3 件事，就得嵌 3 层
  });
});

// ② Promise 链：把"登记后续"标准化成管道 —— 但读代码是"顺着管道读"，先到的先接
getUser(1)
  .then(user => getOrders(user.id))     // .then = 登记"成功之后干什么"
  .then(orders => render(orders));

// ③ async/await：写法恢复"从上往下"——await 那行等结果，拿到再走下一行
// 底层和 ② 完全一样：编译器把 await 之后的代码，登记成 .then 回调（一个微任务）
async function load() {
  const user = await getUser(1);            // 挂起点 1：函数暂停，控制权交还主线程
  const orders = await getOrders(user.id);  // 挂起点 2
  render(orders);                           // 恢复后继续 —— 这就是"同步的样子"
}

"同步样子"的精确含义是两层：① 读写顺序一致——函数内部代码从上往下线性排列，await 行"等"到结果再继续，人类的阅读顺序 = 执行顺序，不再需要脑内画管道；② 错误处理回到同步语法——用普通的 try/catch（见下一问）。而底下那层机制完全没变：遇到未完成的 Promise，await 把函数挂起（恢复点登记为微任务），立刻把控制权还给主线程——它只是让编译器替你写 .then，这就是"语法糖"三个字的分量。

所以还有后半句你必须焊死："同步样子" ≠ "同步行为"。挂起期间主线程该干嘛干嘛——点按钮、渲染、跑别的任务，一个不耽误。点下面按钮亲眼看：

Q7 · "try-catch 包住 await ≈ 异常传播"——我自己处理了，异常不就传播不了了吗？你的质疑是对的，主册那句话另有所指

你的质疑本身完全正确：catch 到之后异常就"到此为止"了——这是所有语言的通则，Python 的 except 接住后同样不再上抛。主册那句话的本意不是讲"传播"，而是在讲await 的一件神奇的事：把"未来的、异步的错误"搬运到"现在"，变成同步的异常，让普通 try-catch 终于抓得到它。没有 await 的世界里，try-catch 对异步错误是瞎的：

代码片段 · 为什么必须 await 才能被 try-catch 抓到
// ✗ 没有 await：fetch 立刻返回 Promise，try 块瞬间走完
try {
  fetch("/api");            // 错误发生在"未来"（网络层），此时 try 已经结束了
} catch (e) {               // 永远等不到 —— 异步错误对同步 try-catch 是隐形的
  console.log("抓不到我");
}

// ✓ await 一个 rejected 的 Promise：会在 await 处"同步地"抛出异常
try {
  const res = await fetch("/api");   // 错误被搬运到这一行，以 throw 的形式出现
} catch (e) {                        // ✓ 抓到了 —— 这就是"约等于异常传播"的确切含义
  console.log("抓到：", e.message);
}

// 抓到之后，异常何去何从由你决定（三选一，和 Python 的 except 完全同构）：
// A. 吞掉：catch 里不 throw —— 到此为止，外面无感知（慎用）
// B. 记录再抛：console.error(e); throw e; —— 最常用的兜底姿势
// C. 转成兜底值：return 默认值 —— 把异常翻译成一个"正常结果"

连起来读："≈ 异常传播"说的是前半程：Promise 的 reject 沿着链路传播，到 await 处被翻译成同步异常——于是 try-catch 这种同步工具终于接得住异步世界的错误。"自己处理了就不传播"说的是后半程：接住之后 throw 不 throw 由你。两句话并不矛盾。第 6 章项目里的 catch 用的是姿势 A（吞掉 + 显示"加载失败"）——因为 UI 层是错误处理的终点站，必须给用户一个交代，不能再往上抛了。

Q8 · 事件循环大讲透：宏任务是啥？为什么"宏任务执行完还有微任务"？循环到底怎么转？重头戏 + 模拟器
微任务也就是 Promise，是有 IO 的对吧？……宏任务是啥？为什么宏任务执行完了，还有微任务？这怎么是个循环呢？太看不懂了。

你这段话里有两个模型性错误，先纠正，再正面重建：

  • 纠错 1 ·"微任务 = 有 IO 的任务"——不对。微任务/宏任务不是按"干什么活"分类的，是按排在哪个队列分类的：排在微任务队列的就是微任务，排在宏任务队列的就是宏任务。同一个回调函数，用 .then() 登记就进微任务队列，用 setTimeout(fn, 0) 登记就进宏任务队列——函数本身没有任何标签。而且恰好相反：IO（网络、定时器）的完成通知是宏任务；微任务全是"纯 JS 的事"：Promise 的 then/catch 回调、await 的恢复、queueMicrotask。
  • 纠错 2 ·"微任务 = 协程"——不是。协程是"可暂停恢复的执行体"。JS 里唯一像协程的东西是 async 函数（await 挂起、微任务恢复），但主线程本身从不让出——它只是在任务之间调度。Python 的 asyncio 是"整个世界都是协程"，JS 是"只有主线程一个工人 + 两个任务队列"，模型不同。

正面重建。事件循环的本体，就是浏览器主线程里一个永不停歇的调度循环：

伪代码 · 浏览器主线程的一生（事件循环的本体就是这个 while）
while (true) {
  const task = 宏任务队列.dequeue();   // ① 取一个宏任务（队列空就阻塞等待：点击/到点/网络到达都会唤醒它）
  task();                              // ② 同步地执行完它（执行中可能又注册新的微任务/宏任务）
  while (微任务队列.notEmpty()) {      // ③ 清空微任务队列——中途新产生的也要清完，一个不留
    微任务队列.dequeue()();
  }
  maybeRender();                       // ④ 可能渲染页面（约每 16.7ms 一次，60fps）

// 你问的"循环"就是 ①→②→③→④ 永远转圈；
// "宏任务执行完还有微任务"就是 ②→③ 的必然：刚跑完的宏任务里可能写了 .then，又注册了新微任务

两个队列的完整户口：

宏任务队列（一等公民，排队走）微任务队列（插队通道）

调度规则一轮只取一个，人人排队每个宏任务之后全部清空，新产生的也清
设计意图公平：点击不会被海量定时器饿死；给渲染留机会及时：Promise 状态一变，"后续"立刻执行，不等下一轮

现在逐条回答你的三连问："宏任务是啥"——上表左列那些"真实世界的事"（到点、网络回来、用户动手），它们的回调排进宏任务队列轮流执行；"为什么宏任务执行完还有微任务"——因为刚执行的那个宏任务自己又注册了微任务（比如定时器回调里写了 .then），规则要求每个宏任务之后把微任务清到空为止，所以永远出现"宏→一串微→宏→一串微"的节奏；"怎么是个循环"——主线程干完一轮（一个宏任务 + 清微任务 + 可能渲染）就立刻取下一个，没有任务就阻塞等待被唤醒，while(true) 转到页面关闭为止——循环的是调度，不是"同步-微-宏-同步"绕圈。

做题五步法（第 7 章过关标准最后一条的解题器）：① 从上往下扫：同步行立刻执行，顺手记输出；② 遇到 setTimeout/点击监听 → 登记"宏：××"；③ 遇到 .then / await 恢复点 → 登记"微：××"（注意：await 右边的代码是同步先执行的，挂起后恢复点才是微任务）；④ 同步代码跑完 → 按注册顺序清空全部微任务；⑤ 取最早注册的宏任务执行 → 再清微任务 → 直到两队列全空。下面把一道经典题做成模拟器，一步一步走：

第 1 题 · const 和 let 怎么选？为什么不用 var？选择策略要倒过来背
const 是先定义，定义完了想要改的话使用 let。let 好像也能赋值，不太清楚为什么不用 var，因为 var 是老代码里面的，现在不太用了。

你的策略说反了主次：不是"先 const、想改再换 let"，而是"默认 const，只有确需重新赋值才用 let"——const 是常态，let 是例外。为什么这么设计：const 声明时就向读代码的人承诺"这个绑定不会再变"，整个文件里凡是 count 出现的地方都可信；一旦看到 let，读者立刻警觉"这货后面会变"。这是用声明方式传递信息，和 Python 的命名约定（全大写=常量）异曲同工，但 JS 用语法强制了它。注意一个易混点：const 锁的是绑定（不能再指向别的东西），不锁内容——const list = [] 照样能 push，只是不能 list = 别的数组。

"var 是老代码"只是表象，本质是它有三个被 let/const 逐一修复的坑：

  • 坑 1 · 没有块级作用域：var 只有函数作用域——if (x) { var a = 1 } 之后 a 在 if 外面照样活着，泄漏到整个函数；let/const 的 {} 块即牢笼；
  • 坑 2 · 允许重复声明：var a = 1; var a = 2; 静默通过、悄悄覆盖——就是你 E 部分那个 Console 报错拦住的事故，let/const 直接报错；
  • 坑 3 · 提升行为怪异：var 声明被"提升"到函数顶部并初始化为 undefined——console.log(a); var a = 1; 不报错、打印 undefined（坑死人）；let/const 也提升但处于"暂时性死区"，提前访问直接 ReferenceError——错误越早炸越好修。
第 2 题 · map/filter/reduce/find 各返回什么？哪个改原数组？四个答案都要再精确一格
(a) map：返回对数组操作后收集起来的东西。(b) filter：返回满足条件的元素。(c) reduce：返回的是一个类似于累加器返回的数值吧。(d) find：返回对应的值……应该是原数组的内容。(e) map、filter、reduce、find 都不会修改原数组，只有 forEach 可以修改原数组。

方向都对，但四个表述都差"最后一格精度"，面试就抓这一格：

  • map → 新数组，长度与原数组相同，每个元素 = 回调的返回值（一对一变形）。"收集起来的东西"太虚，说"等长新数组"。
  • filter → 新数组，长度 ≤ 原数组，元素是原数组里满足条件的那些元素（不是"变形后的"）。
  • reduce → 你说了算的任意值：回调返回什么它就是什么——数字（求和）、数组（扁平化）、对象（分组统计）都行。"数值"说窄了，它是最通用的聚合器。
  • find → 原数组里的那个元素本身（引用），找不到返回 undefined。你答"原数组的内容"正确，加分句是"只找第一个满足的就停，和 filter 找全部是一对"。
  • (e) 半对半错，是最值得展开的一处："都不修改原数组"对了一半——数组结构确实不动（不增删元素、不换位置），但如果元素是对象，新数组里装的仍是原对象的引用——通过引用改属性，原数组照样遭殃。而"forEach 可以修改原数组"的说法也不准：forEach 只是"纯遍历"，修改是你在回调里自己动手干的（arr.forEach(u => u.age++) 里动手的是你写的 u.age++）。真正直接改原数组结构的是另一家人：push/pop/splice/sort。这个"新数组 ≠ 新对象"的引用陷阱，玩一遍就焊死：
演示 16 · "返回新数组" ≠ "返回新对象"（引用陷阱实测，点按钮对比）

第 3 题 · '5' === 5 与 ==完全正确
因为两个等于会进行类型转换，应该用三个等于。

正确，判定和结论都对。补一个让你答得更漂亮的细节：== 的转换规则叫抽象相等，方向是"数字优先"——字符串转数字（'5'→5）、布尔转数字（true→1，所以 true == 2 是 false 而 true == 1 是 true）、null 与 undefined 互相放过（null == undefined 是 true 这个特例值得单独记）。规则琐碎到没人背——这就是"永远用 ==="这条铁律的由来：不是 === 更正确，是 == 的规则不值得记。

第 4 题 · 用 makeCounter 讲闭包混入了另一个概念：高阶函数
闭包就是一个函数接收了一等公民函数作为参数，这个函数内部会有一个变量以及一个函数……

你的描述把闭包和高阶函数两个概念焊在了一起。"函数接收一等公民函数作为参数"是高阶函数（higher-order function）——函数当参数传/当返回值，5.4 的 run(fn) 是它；而 makeCounter 没有接收任何函数参数，它靠的是闭包，这是两件独立的事（可以同时发生，但互不依赖）。

用 makeCounter 讲闭包的标准口头版，三句话：

  • 现象：count 是 makeCounter 的局部变量，按理函数返回时它就该销毁；但返回的那个箭头函数身上引用着 count（词法作用域：内层函数生来就看得见外层的变量）——于是 count 被这个函数"随身带走"了，makeCounter 早就返回了，count 还活着；
  • 定义：函数 + 它记住的那个变量环境，合起来叫闭包。不是什么语法，是"函数记住出生地"的机制；
  • 旁证（面试加分）：counter 和 counter2 互不干扰——因为每次调用 makeCounter 都创建一套全新的 count，两个闭包各带各的；counter 连调三次得 1/2/3——因为同一个闭包里 count 是同一个。

用途收尾一句：计数器/缓存只是入门示例，真正的工业级用途是"模块私有变量"（外界拿不到 count，只能通过函数操作）和 React hooks 的地基（useState 的状态就是靠闭包记住的）。

第 5 题 · await 阻塞的到底是谁正确，表述微调
它在处理 IO 密集型任务时，在 IO 任务执行期间会出让控制权，去执行别的任务；真正阻塞的是 CPU 密集型的任务。

判断完全正确，只把主语说得更准：await 挂起的是"当前这个 async 函数"，从头到尾没有阻塞过主线程——主线程在函数挂起期间继续跑别的任务（E 部分演示 14 的时间线就是这句话的可视化）。CPU 密集的那半句也对：JS 主线程只有一个，同步的大循环一跑，渲染、点击全卡死（页面"未响应"）——这就是"JS 适合 IO 密集、不适合 CPU 密集"的原因，也是将来遇到 Web Worker 的伏笔。

Q1 · input 写了 flex:1，button 不会被挤掉吗？三步算法的实战落地
怎么确保 input 和 button 在同一行横排？input 不是 flex: 1 吗？那 button 不是被挤掉了吗？

不会挤掉——因为 flex 的分配顺序是「先保基准、再分剩余」，这正是 B 部分演示 5 那套三步算法在真实项目里的样子。把项目里的 CSS 逐条翻译成算法语言：

  • 第一步 · 定基准：input 写了 flex: 1（= 1 1 0%）→ 基准 0；button 什么都没写 → 用默认值 0 1 auto → 基准 = 内容宽（"添加"两个字 + 内边距，约 70px）。button 的 70px 是先入账的；
  • 第二步 · 算剩余：容器宽（比如 388px）− 70 − 8（gap）= 310px 富余；
  • 第三步 A · 分赃：grow 总和只有 input 的 1（button 是 0，一分不抢）→ 310px 全部归 input。结果：input ≈ 310px、button 稳稳 70px，同一行。

所以"flex:1 抢走一切"抢的是剩余空间，不是别人的基准。button 被挤掉只会发生在一种情况：容器窄到连基准都放不下（进入第三步 B 还债模式）。而这里还有个更隐蔽的真实行为：flex 子项默认 min-width: auto（最小宽 = 内容宽）——input 的默认内容宽约 170px，窗口极窄时 input 拒绝缩到 170px 以下，反而是它把 button 挤变形。实战解法一行：input { min-width: 0 }（允许我缩到 0）。这个 min-width:auto 的坑是 flex 布局最著名的坑之一，现在你知道它的名字了。

动手验证：回到 B 部分演示 5，点「预设：input + button」，把容器宽拖到最左——亲眼看 button 被压、input 卡在最小宽；这就是"容器窄到基准都放不下"的现场。

Q2 · emptyEl.style.display = "block" / "none"：none 是没有，block 是换行吗？后半句要换个说法
展示为 none 的话就是没有，是吧？展示为 block 的话是进行换行，对吧？

前半句对：none = 从布局里整个拿掉（不占位、量尺寸是 0、点不到、事件也不触发）。后半句换个更准的说法：block 不是"换行"这个动作，是一种显示类型——"块级显示：独占一行、可设宽高"。"换行"是这个类型的效果，不是它本身。这么较真的原因是：display 的值是一个类型系统（block / inline / inline-block / flex / grid / none），记"类型"才能举一反三，记"换行"只能答这一题。

放到这行代码的语境里还有一个细节：<p id="empty"> 本来就是 block，为什么还要显式写回 "block"？因为之前被设成 "none" 了——el.style.display = "block" 在这里的语义是"恢复默认身份"。整个三元表达式的业务含义："没有任务 → 空状态提示出场；有任务 → 彻底让位"。这正是 C 部分演示 9 讲过的"display:none 不占位"语义的落地，也是为什么这里用 display 而不是 visibility——空状态提示不能占着位置挡列表。

最后补一个体系上的呼应（这是你没问但值得点破的一处）：D 部分讲过"状态切换用 classList、动态数值用 el.style"——严格按这个原则，显示/隐藏这种状态切换应该用 classList（CSS 里写 .hidden { display: none }）。主册选 el.style 是教学取舍：两行搞定、不用先建一个 CSS 类。真实项目两种都常见，原则是方向性的，微型示例允许最短路径——知道这个权衡存在，你就同时掌握了两种姿势。

Q3 · 事件委托 else 块的 map：确认你的理解确认 + 连上展开运算符
else 块里 map t.id === ID 的时候去做这样一个操作，否则的话去获得 t……对对对，懂了懂了。

确认你的理解是对的，再把它钉成一句能脱稿说的话：map 负责生成新数组，对每个任务做判断——id 匹配的那个，用 { ...t, done: !t.done } 造一个"只翻转 done 的新对象"；不匹配的原样返回 t。旧数组、旧对象一个字节不动，这就是"不可变更新"。

它和 E 部分第 4 问的展开运算符正好接上：{ ...t, done: !t.done } = 把 t 的字段全部倒进新对象，最后用翻转后的 done 盖掉旧的（后倒的盖先倒的）；而 F 部分演示 16 从反面证明了为什么不能直接 t.done = !t.done——那只改了对象、没换数组，且污染了原数据。三层结构串起来：map 换数组（第一层新）→ 展开换对象（第二层新）→ 原 data 原封不动。第二册 React 的 setState 你将天天写这个套路，到时候它已经是你的肌肉记忆了。
