## F 组：体系咬合（审计 + 缓存，两条“暗线”）

### ⑨ 审计模块为什么存在？（你答了追责/日志，还有五个）

审计（audit）和普通日志的本质区别先立住：**日志面向调试（给开发者看，尽力而为），审计面向事件语义（给系统和对账用，结构化、不可抵赖、每条必达）**。项目里它的七个消费场景：

1. **追责/取证**：多租户共享模式的信任基石——谁提交的、谁 merge 的、何时升格，全可查（你已答）。
2. **对账**：Stage 4 压测“审计对账零缺口”的数据来源——50 轮操作 vs 事件计数逐类比对，证明闭环行为与账本一致（这是“可验证性”而不只是“可查询”）。
3. **蒸馏质量审计**：`faq.promote` 存 before/after 全文——LLM 改写质量的逐条人工审查入口（A 组⑩讲过）。
4. **运营洞察**：`audit.py` 有现成聚合——7 天窗口 by_action 排行、24h 活跃用户数（`audit.py:111-118`）——管理端的“系统在发生什么”仪表盘。
5. **排障时间线重建**：出问题时按 user/kb/时间窗口拉事件序列还原现场（CHAT_MODEL bug 那次，“召回成功但没直返”的异常链条就是靠埋点+日志拼出来的）。
6. **异常检测地基**：反刷规则引擎的数据源（C 组⑫第 4 条）——审计的第二个消费方。
7. **合规**：企业场景的硬需求（等保/SOC2 都要求操作留痕）——To B 卖点。

架构视角升华一句：`audit_log`（事件流）+ `faq`（当前状态表）的关系，就是 **Event Sourcing 的弱化版**——状态表是事件流的投影，事件表让你能回答“这个状态是怎么来的”。面试被问“为什么不用普通日志”就用这句打。

### ⑪⑮ 缓存一致性联动详解 + “协作组合关系”确认

**你的判断完全正确：是协作组合关系，不是耦合依赖。** FAQ 模块（Stage 3）不懂缓存内部，缓存模块（Stage 6）不懂 FAQ——它们只共享一个显式契约：**“KB 内容变了 → 调 bump_kb_cache”**。这就是“咬合成体系”的准确含义：模块各自独立演进，靠契约连接。

完整故事按“没有它会发生什么”讲（这是面试最抓人的讲法）：

**场景：缓存冻结自进化。** 时序——
```
t1  用户问 Q（KB7）→ FAQ 未命中（还是 candidate）→ 走正常检索 → 结果 R 存入缓存
t2  多次命中后 Q 蒸馏升格 active（answer 已是结构化知识）
t3  用户再问 Q → 检索缓存命中！→ 直接返回旧的 R（chunk 拼出来的答案）
t4  t3 永远发生——FAQ 直返永远不会被走到
```
危害比“旧数据”严重一个档次：**不是缓存了旧答案，是缓存把整个自进化闭环短路了**——candidate 升格在缓存面前形同虚设。Stage 3 的核心特性被 Stage 6 的优化静默杀死，两条独立正确的线，交叉点上出妖。

**修复（`ee39eb5`）的机制，三层设计**：

```375:392:backend/services/cache.py

    ...
```

1. **版本号直接进缓存 key 的 hash**（`build_search_key`，`cache.py:121-126`：`hash(query + 过滤 + 模式 + limit + rerank + 版本 + extra)`）——不是“读缓存后比对版本再丢弃”，而是**版本一变 key 就变，新请求天然 miss 到新 key，旧 key 的条目等 TTL 自然过期**。读路径零额外比较逻辑，失效逻辑完全藏进 key 构造，这是比“读后比对”优雅的地方。
2. **为什么版本号而不是精确删除**：精确失效需要维护“哪条缓存依赖哪个 faq”的倒排索引——复杂且易漏（多 KB 混合查询的 key 归属就很难算）。版本号策略是“**宁可多失效，不可少失效**”：一次 bump 让整个 KB 的缓存作废，损失一点命中率，换绝对正确。KB 级写入低频，命中率损失可忽略。**粗粒度换正确性，是失效策略的经典权衡。**
3. **双保险兜底**：bump 本身失败只 warning 不阻塞主流程（`cache.py:379`“旧缓存最多多活一个 TTL”）——版本失效是快路径，TTL 是慢路径兜底，两层叠加让最坏情况有界。

**六个 bump 点全景**（FAQ 视角，也是“写路径清单”的另一种数法）：

| bump reason | 触发 | 缓存为什么必须失效 |
|---|---|---|
| `faq_aggregate` | 判重聚合热度 | 热度变化可连锁触发升格 |
| `faq_writeback` | 新种 candidate | 保守项（candidate 不直返，但保证语义完整） |
| `faq_promote` | 蒸馏升格 | **answer 被改写 + 直返资格出现——最关键的一个** |
| `faq_demote` | 降级 | 直返资格消失 |
| `faq_delete` | 删除 | 答案不存在了 |
| `faq_pr_merge` | PR 合并 | 新 active 进入直返池 |

（另外注意 bump 自身也写 audit——**治理动作本身也被治理**，审计是全系统最底层的那个模块，它只被别人依赖、不依赖别人。）

## Q2 · 第4轮 · 追问

缓存把整个自进化闭环短路（好场景）但是我没看懂你说的解决措施

## A2 · 第4轮

## ⑥ 缓存短路自进化的解法——换个讲法：酒店换房卡

先把“被短路”的时序再走一遍（这次盯住 key 这个主角）：

```
缓存 key = hash(问题 + KB + 检索模式 + limit + rerank开关 + 【版本号】)
                                    ↑ 版本号是 key 的一部分！

t1  用户问 Q（KB7，版本=5）
    FAQ 召回：还是 candidate → 不直返 → 走正常检索 → 结果 R 存进 key A
    key A = hash("Q" + KB7 + ... + 版本5)

t2  Q 热度达标 → 蒸馏升格 active
    ★ 写路径触发 bump_kb_cache → KB7 版本 5 → 6 ★

t3  用户再问 Q
    计算 key = hash("Q" + KB7 + ... + 版本6) = key B ≠ key A ！
    → 查缓存：key B 从没存过 → miss
    → 重新走检索流程 → FAQ 召回命中 active → 直返蒸馏后的新答案
    → 存进 key B

    key A（旧答案）呢？没人再算出这个 key 了，它成了无人访问的死条目
    → 等 TTL 到期，被正常淘汰。完。
```

**理解的关键一跳**：解法不是“删掉旧缓存”，也不是“读缓存时比对版本”——是**版本号直接参与 key 的计算，版本一变 key 必然变，新请求天然 miss，旧条目自然作废**。读路径里没有任何“检查是否过期”的代码，失效逻辑完全藏在 key 构造函数里。

类比：**酒店换房卡**。住客换房（FAQ 升格）时，前台不是去把旧房间的门锁拆了（删缓存），而是直接换发新卡（版本+1）——旧卡（key A）还攥在手里，但刷不开任何门，等于废卡；保洁（TTL 淘汰）过几天清一次久无人住的房间。

**为什么敢“多失效”**：bump 一次，KB7 里**所有**问题的缓存全部作废（不止 Q 这一条）——看起来浪费。对比精确方案：只删 Q 相关的缓存条目，需要维护“哪条缓存依赖哪个 faq”的倒排关系，多 KB 混合查询时归属根本算不清，**漏删一条就是脏数据直返**。权衡结论：**宁可全作废（浪费但永远正确），不可漏作废（省了但可能出错）**——失效粒度的经典取舍，选粗不选细。
