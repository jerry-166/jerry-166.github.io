方案三：OPA 策略引擎

OPA（Open Policy Agent）是一个独立的通用策略守护进程（CNCF 毕业项目，默认 8181 端口）。策略用声明式语言 Rego 编写，打成 Bundle 热加载，输入任意 JSON、输出任意 JSON；海量行级数据靠部分求值下推 SQL。

01

定位：一个独立的策略守护进程 ★★★★★

CasbinOPA
形态库（jar/SDK，在应用进程内）独立进程 / 服务（默认 8181，Go 写的也可内嵌）
调用方式函数调用 enforce()HTTP/gRPC 请求（或 Go 库内嵌）
策略语言model.conf 表达式Rego，一门完整声明式逻辑语言
输入/输出三元组 → bool任意 JSON 输入 → 任意 JSON 输出（allow+字段+过滤条件）
典型场景单体/微服务里的应用权限多语言微服务、K8s 准入、Service Mesh、统一合规
一句话

Casbin 是"你调用的一个函数"，OPA 是"你咨询的一个决策服务"。它把策略从每个业务服务里抽出来，集中到一个语言无关的引擎。

02

权限模型：input + data + Rego → 决策

input（每请求变化）
本次请求上下文：当前用户、动作、资源。随每个 HTTP 请求传入。
data（内存全局）
策略 + 事实：角色权限映射、资源归属。随 Bundle 加载进内存。
Rego 规则
声明"什么条件下 allow 成立"，引擎自己求解（Datalog 谱系）。
→
decision 决策
任意 JSON：allow、visible_fields、filters…
图 4-1　OPA 四要素：input 是变量、data 是事实、Rego 是规则、输出是任意结构化决策
Rego 的两个语法直觉（import rego.v1 新语法）
  • 声明式：只写"满足什么条件就成立"，不写怎么循环查找；
  • 同名规则 = OR（规则有多段定义，满足任一段即成立）；同一个大括号内换行 = AND（每行条件都要满足）。
03

完整示例：一个素材平台的三层权限 Rego

authz.rego（功能权限 + 行级 + 字段级一体）
package material.authz
import rego.v1

default allow := false

# ① 功能权限：角色 → 权限码（映射在 data.role_permissions）
allow if {
    some role in input.user.roles
    input.perm in data.role_permissions[role]
}

# ② 行级权限：查看素材
allow if {
    input.action == "view"
    input.resource.kind == "material"
    can_view
}
can_view if { input.resource.owner_id == input.user.id }      # 本人
can_view if {                                                       # 分享给我所在组
    some group in input.user.groups
    data.resource_owners[input.resource.id][group]
}
can_view if { "admin" in input.user.roles }              # 超管

# ③ 字段级：输出可见列集合（基础列人人可见）
default visible_fields := {"id", "name", "create_time"}
visible_fields contains "phone" if { "admin" in input.user.roles }
visible_fields contains "cost"  if { "finance" in input.user.roles }
data.json（全局事实：角色权限映射 + 资源归属）
{
  "role_permissions": {
    "publisher": ["material:list:query", "material:list:add"],
    "admin":     ["material:list:query", "material:list:export"]
  },
  "resource_owners": {
    "M100": { "u101": "manage", "g5": "view" },
    "M101": { "u102": "manage" }
  }
}
调用（package material.authz 对应 URL /v1/data/material/authz）
curl -X POST http://localhost:8181/v1/data/material/authz \
  -H 'Content-Type: application/json' \
  -d '{
    "input": {
      "user":     {"id":"u101","roles":["publisher"],"groups":["g5"]},
      "perm":     "material:list:query",
      "action":   "view",
      "resource": {"kind":"material","id":"M100","owner_id":"u102"}
    }
  }'
# 输出（不止 bool，一次返回字段集合）：
# { "result": { "allow": true, "visible_fields": ["id","name","create_time"] } }
关键差异：决策输出是任意 JSON

Casbin 一次返回 bool；OPA 可以一次返回 allow、visible_fields（能看哪些列）、甚至 filters（行级 WHERE 条件），一个请求把功能/行级/字段三层的决策结果全拿回来（第 10 章）。

04

运行架构：PEP / PDP / PIP / PAP

这是理解 OPA 的必背四件套（源自 IETF 标准权限模型，不只是 OPA 在用）：

PEP 执行点
Policy Enforcement Point。业务服务的拦截器/网关/Envoy。负责"拦截请求、问 PDP、按结果放行或拒绝"。
⇄
PDP 决策点
Policy Decision Point。就是 OPA。收 input、算 Rego、返回决策，本身不读库。
⇄
PIP 信息点
Policy Information Point。实时属性来源=业务库。决策需要的实时数据（资源归属、用户组）从这里取。
PAP 管理点
Policy Administration Point。策略编写/审查/发布：Git + CI + Bundle Server，签名打包。
图 4-2　PEP 执行、PDP 决策、PIP 提供事实、PAP 管理发布；你之前的业务代码主要扮演 PEP

决策日志（你问的：是不是用来监控越权？）

对。OPA 可把每次决策（input + 结果）记录为决策日志，用途包括：① 安全审计（谁在什么时候访问了什么）；② 越权/异常事件告警（大量 deny 可能是攻击或误配）；③ 排障（为什么我被拒了）；④ 合规回放（重放历史决策）。

05

什么数据进 OPA？三个通道

这是 OPA 最容易踩的坑：不是所有数据都该塞进 OPA。按"变化频率 + 数据量"分三通道：

数据类型举例去哪怎么更新
策略/规则.rego 文件（判断逻辑）Bundle（Git）GitOps：提 PR → review → CI → 签名发布
低频配置角色-权限映射、小范围 ACL 分享Bundle 的 data.json（小）后台变更触发 webhook → CI 重建；或 Bundle Server 发布时现查库生成
海量/实时数据100 万素材、实时订单、实时归属不进 BundlePEP 查库塞进 input；或 Rego 用 http.send 实时回调
为什么 100 万素材不能进 Bundle（你问的"打包爆炸"）

Bundle 要被 OPA 加载进内存、轮询下载、原子切换。百万行 JSON 会让包体巨大、内存暴涨、每次发布慢、且数据秒级过期。规则：变化慢、体积小的进 Bundle；海量且实时的留在业务库，决策时按请求取。这正是行级 ACL 场景的主流处理方式。

回答你"是不是业务侧新增就调 Git API 上传策略"——不是。业务数据（素材、订单）永远不进 Git；只有策略代码进 Git。低频配置数据也不一定要人手工提交，通常由后台变更触发 webhook 自动跑构建，或 Bundle Server 在发布时实时查库生成 data.json。

06

PIP 实时取数：塞 input 还是 http.send

这就是你说"看不懂"的那两个机制，它们解决"决策需要业务库里的实时数据，而 OPA 又不连库"的问题：

方式一：PEP 查好塞进 input（推荐）
业务服务（PEP）在调 OPA 前，自己先查业务库拿到"这条素材的 owner_id、用户所在组"，放进 input 再发给 OPA。OPA 全程无状态、不主动连库。
方式二：Rego 里 http.send 回调
Rego 执行到一半，用 http.send() 主动发 HTTP 请求回调业务服务的接口取数（PIP）。OPA 变"有状态依赖"，要处理超时/缓存/性能。
图 4-3　实时数据要么由 PEP 预查塞 input（主流），要么由 OPA 用 http.send 回调取（灵活但复杂）
实践建议

绝大多数团队用方式一：业务服务本来就最懂自己的库和缓存，PEP 查好后塞 input，OPA 保持纯函数、快、可离线测试。方式二适合"规则复杂、需要查多个外部服务、且不想让 PEP 拼装"的场景。

07

持久化：OPA 无数据库，靠 Bundle

与 Casbin 落库不同，OPA 本身无状态、不连数据库。策略和数据打成一个 Bundle（本质是 .tar.gz 压缩包，里面是 .rego + .json，可签名校验），放在一个 HTTP 服务器 / S3 / Git 仓库上，OPA 启动时拉取、之后周期性拉取，全部加载进内存。

编写
Git 仓库里写 .rego / data.json
→
CI
校验、测试、签名、打包成 .tar.gz
→
Bundle Server
HTTP/S3/Git 静态托管
→
OPA 拉取
启动拉 + 周期拉，内存激活

08

同步与热更新：策略更新必须重新部署吗？

不用重启、不用重新部署 OPA 实例。OPA 默认周期性轮询（pull）Bundle 服务器，发现新版本就原子切换（新包整体加载成功才替换，失败继续用旧的）。

config.yaml（轮询配置）
services:
  - name: bundle-server
    url: https://bundles.example.com/bundles
bundles:
  authz:
    service: bundle-server
    resource: /authz.tar.gz
    polling:
      min_delay_seconds: 30        # 随机化轮询间隔
      max_delay_seconds: 60
    # 也可设 trigger: manual，不主动轮询，
    # 由外部 POST /v1/bundles/authz 立即触发拉取（秒级）
更新方式机制用途
Bundle 轮询（pull）周期性拉新包，原子热更新生产主路径
manual trigger配置 trigger:manual 后 POST 立即拉发布后想立刻生效，不等下个周期
Policy API PUT直接 PUT 一条策略到运行中的 OPA仅调试/实验，不用于生产（无版本管理、重启即丢）
回答"OPA 策略是不是不会更新 / 更新就得重新部署"

OPA 实例不用重启，但策略是"不可变发布物"，变更必须走 Git→CI→构建→发布 Bundle 的流程，不是在 OPA 里改一行就立即生效。这是刻意的权衡：牺牲一点即时性，换来版本化、代码评审、签名、灰度、秒级回滚。对比 Casbin 的 Watcher 是 addPolicy 后主动 push 广播，OPA 是周期 pull。

09

部分求值：OPA 的"杀手锏"（自动生成 SQL）

这是 OPA 处理海量行级数据的核心机制，也是面试最能体现深度的点。

9.1 数学直觉（先懂这个）

完整求值好比 f(x,y)=2x+y，你把 x=3、y=4 都给我，我算出 10（一个 bool）。部分求值是你只给我 x=3、y 暂未知（标成 unknown），我把式子化简为 f=6+y——输出一个"残余条件"，等以后 y 已知时再算。

完整求值
用户 + 资源对象都给全 → OPA 返回 allow:true/false（适合单条详情，1 次判断）
部分求值
只给用户，把"海量数据集合"标为 unknown → OPA 输出"满足权限的条件"：owner_id='u101' OR group_id IN('g5')
图 4-5　不把 100 万行逐行问 OPA，而是让 OPA 算出"过滤条件"，交给数据库一次性筛
部分求值输出残余条件（概念示意）
# 把 data.materials 标为 unknown：opa eval --partial --unknowns data.materials
# OPA 不返回 bool，而返回一组"可以直接当 WHERE 的表达式"：
owner_id = 'u101'  OR  group_id IN ('g5')

# 官方插件（OPA-SQL、PostgreSQL/MySQL/Mongo 集成）把它翻译成：
SELECT * FROM material
WHERE owner_id = 'u101' OR group_id IN ('g5');   # 下推给数据库执行
一句话定位

部分求值 = 自动化版本的若依 @DataScope。@DataScope 要你手写 AOP 拼 WHERE；OPA 把"策略规则"自动编译成"针对任意数据库的查询条件"，让数据库在源头过滤，而不是把数据捞出来逐行鉴权。

10

海量行级怎么落地：filters + visible_fields

你问"海量行级是不是只返回一些字段再去查数据库"——更准确地说，列表和详情是两种决策：

列表页（多行）
OPA 一次返回两份结构化结果：
① filters：行级过滤条件（部分求值 → WHERE），业务拿它拼 SQL
② visible_fields：列裁剪（哪些列返回）
→
业务库
WHERE filters 过滤行；SELECT 只取 visible_fields 的列，一次查询完成
详情页（单条）
PEP 先查出这一条，把完整对象塞进 input，OPA 完整求值返回 bool（+字段集合），false 则 403。
图 4-6　列表走"条件下推"（一次查库），详情走"对象判断"（一次 bool），都不逐行调 OPA
呼应你最初的 visible_fields 疑问

visible_fields: ["id","name","create_time","phone"] 由 OPA 一次返回，避免了像 Casbin 那样对每个字段循环 enforce。列表 n 行的序列化本身是 O(n·k)，但权限判断只在每请求一次，把权限成本压到常数。

11

批量决策 vs 逐条决策（你的问题 1）

OPACasbin
调用形态HTTP 网络请求，调用成本高，倒逼"一次返回集合"进程内函数，调用成本低，很容易顺手写成 n 次
批量能力一次决策输出 filters + visible_fields（天然面向集合）有 batchEnforce([请求...]) 批量 API，也能一次取权限 Set
正确做法列表条件下推、字段一次返回列表用 batchEnforce，或取权限 Set 内存判，不逐字段/逐行 enforce

所以你说的"OPA 批量 vs Casbin 决策 n 次"是两种框架的默认倾向，不是绝对能力：Casbin 也能批量（batchEnforce/权限 Set），只是写起来容易偷懒成 n 次。无论哪种，都要把"每对象一次远程/函数调用"压成"每请求一次"。

12

四种部署形态

Sidecar 边车
K8s 中每个业务 Pod 旁挂一个 OPA，localhost 调用、无网络跳数（最常见）。
主机 Daemon
每台节点一个 OPA，同主机所有服务共享。
中央服务
OPA 集群独立部署，所有服务远程调用（集中、但有网络开销与单点压力）。
Go 内嵌
用 Go 把 OPA 当库编进进程（仅 Go 生态）；其他语言只能用服务形态。

13

什么时候用 / 不用 OPA（含三个模型的更新共性）

适合 OPA
  • 多语言微服务（Java/Go/Python/Node 共用一套策略），不想每语言实现一遍；
  • Service Mesh / K8s 准入控制、网关统一鉴权；
  • 强审计、合规、需要策略版本化/签名/灰度/回滚的组织。
不必上 OPA

单体 Java 应用、团队没人会 Rego、只有常规 CRUD 权限——若依式自研或 Casbin 足够，引入 OPA 是过度设计。

三个模型的"初始化 + 增量更新"其实是同一套范式（你的问题 2）

初始化（种子）增量更新
若依menu.sql 随发版初始化后台授权 + 删 Redis 缓存（失效拉取 pull）
Casbinpolicy.csv / 种子 SQL / Adapter 直读addPolicy + Watcher 广播（主动推送 push）
OPAGit Bundle（含 .rego + data.json）重建 Bundle + 周期/手动拉取（周期 pull）

记住三种传播范式：失效后拉取（cache-aside）、主动推送（pub/sub）、周期轮询（poll），所有权限系统的缓存/多实例一致性都逃不出这三种。

14

本册小结与自测

14.1 必须带走的 9 句话

  1. OPA 是独立策略守护进程（默认 8181，CNCF 毕业），语言无关；与 Casbin 是服务/库的根本区别。
  2. 四要素：input（每请求）、data（全局事实）、Rego 规则、决策（任意 JSON）。
  3. 架构 PEP 执行 / PDP 决策（OPA）/ PIP 取数（业务库）/ PAP 管理（Git+CI），决策日志用于审计与越权告警。
  4. 数据三通道：策略走 GitOps、低频配置走 Bundle data.json、海量实时数据不进 Bundle 而走 input/http.send。
  5. 实时取数两方式：PEP 查好塞 input（主流） 或 Rego http.send 回调。
  6. OPA 无数据库，靠 Bundle（.tar.gz 签名包）持久化，轮询拉取、原子热更新、无需重启。
  7. 策略更新走构建发布（非即时生效），换来版本化/签名/灰度/回滚；Casbin 是 push、OPA 是 pull。
  8. 部分求值：把数据集合标 unknown，输出残余条件并翻译成 SQL WHERE 下推，等于自动化版 @DataScope。
  9. 列表返回 filters+visible_fields（一次决策），详情塞对象判 bool；批量而非逐行，部署以 Sidecar 为主。
