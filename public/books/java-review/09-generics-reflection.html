02

泛型为什么出现：把运行时爆炸提前到编译期 高频

2.1 没有泛型的惨案（Java 1.4 及之前）

集合的元素类型是 Object——什么都能装，代价是取出来必须记得它是什么并强转：

List.java · Java 1.4 时代
// 装的时候来者不拒（Object 是万物之父）
List list = new ArrayList();
list.add("hello");
list.add(42);          // 编译器不拦：int 自动装箱成 Integer，都是 Object

// 取的时候全凭记忆强转 —— 记错了就是运行时炸弹
String s = (String) list.get(0);   // OK
String t = (String) list.get(1);   // 💥 ClassCastException
                             // 编译完全通过，测试没覆盖到，生产环境炸给你看

问题的本质：类型信息在存入时被丢弃，取回时靠人脑恢复。人脑是不可靠的，错误应该让编译器在编译期就拦下——这是泛型的全部动机：

一句话回答

泛型为什么出现？——把"取回时强转"这个运行时炸弹，改造成"存入时检查"的编译期错误；类型的正确性从"程序员负责"变成"编译器担保"。

2.2 泛型怎么解决：类型参数化

List.java · Java 5+
List<String> list = new ArrayList<>();
list.add("hello");
list.add(42);          // ❌ 编译错误：add(String) 不接受 Integer
                             // 炸弹在写代码的那一刻就被拆除了
String s = list.get(0);       // 无需强转，编译器已担保类型

// 泛型方法：类型参数由调用处推断 —— 和 Python 泛型函数一个意思
public static <T> T first(List<T> list) {
    return list.get(0);
}
Integer n = first(Arrays.asList(1, 2, 3));  // T 被推断为 Integer

注意一个关键区别：Java 泛型不做运行时协变检查，全部靠编译期。这既是它的优点（零运行时开销——下一节的擦除），也是它一切限制的根源（第 4 节的代价）。

🐍 Python 对照 · typing 是"君子协定"

你写的 def first(l: list[T]) -> T 在 CPython 运行时完全不检查，传个 list[str] 装整数照样跑（直到你写 mypy 才报错）。Java 泛型则是 javac 的强制关卡——不通过就拒绝生成字节码。代价是 Java 泛型必须保守（类型参数在运行时不存在），收益是零成本抽象。另外 Python 3.12 的 class C[T] 语法糖和 Java 的 class C<T> 形式几乎一样，但底层哲学完全不同：Python 是"文档+工具链"，Java 是"语言契约"。

1
追问：那为什么不直接做成"每个 List<String> 在运行时是独立类型"？像 C# 那样
历史包袱。Java 5 发布时 JVM 上已经跑着海量的非泛型字节码（老代码里 List 装的 Object）。如果泛型做进运行时（C# 的 reified generics），新代码的 List<String> 和老代码的 List 就是两个类型，互操作全断——迁移成本不可接受。所以 Java 选了擦除式泛型：字节码层面完全兼容老代码，代价是把类型检查全部锁死在编译期。这是"兼容性优先"的经典工程权衡。
03

类型擦除：编译器的魔术 原理核心

泛型在字节码层面不存在——这就是类型擦除（Type Erasure），整个模块最重要的一个原理。

3.1 擦除规则：擦到哪一层？

Erasure.java · 源码 → 字节码
// 你写的源码
public class Box<T extends Number> {
    private T value;
    public T get() { return value; }
}

// javac 编译后，字节码里实际存在的等价形式（用 javap -c 可验证）
public class Box {
    private Number value;              // T 被替换为【最左边界】Number
    public Number get() { return value; }
}

三条擦除规则（面试标准答案）：

  • 无限定 <T> → 擦成 Object
  • 有限定 <T extends Number> → 擦成第一个边界 Number（多个边界取最左）
  • 使用处插入强转：调用 box.get() 的地方，编译器自动补 (Integer) box.get()——泛型的"担保"最终落回强转，只是这次强转编译器替你担保正确

3.2 运行时证据：亲手验证擦除

Proof.java · 可以跑的证据
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();

System.out.println(a.getClass() == b.getClass());   // true！同一个 Class
                                                    // 字节码里根本没有 String/Integer 的事

// 通过原生方法绕过编译期检查（raw type）
List<String> c = new ArrayList<>();
List raw = c;                 // 裸类型引用：逃出泛型检查的后门
raw.add(42);               // 编译只给 warning，不拦
String s = c.get(0);       // 💥 ClassCastException —— 编译器补的强转炸了

第三段代码值得细品：c.get(0) 编译后是 (String) list.get(0)，这个强转是编译器替你写的——它担保过类型安全，但你从裸类型后门塞了脏数据，担保失效，运行时爆炸。泛型的安全性是编译期的全封闭契约，漏了一个口子（raw type / 反射）就全部失效。

3.3 桥方法：擦除与多态的冲突怎么解决

擦除会立刻撞上一个矛盾：子类重写泛型方法时，签名对不上。看这个经典案例：

Bridge.java · 没有桥方法时的逻辑矛盾
interface Converter<T> { void convert(T t); }

class StringConverter implements Converter<String> {
    // 你写的重写：convert(String) —— 但父接口擦除后是 convert(Object)
    // 方法签名不一致 → 不构成重写 → 多态断裂？！
    public void convert(String s) { System.out.println(s); }
}

// javac 的解法：自动生成【桥方法】（javap -v 可见）
// class StringConverter 中多了一个编译器合成的方法：
//   public void convert(Object s) { convert((String) s); }  ← 桥
// 它重写了接口的 convert(Object)，内部转调你的 convert(String)
// 多态链修复：接口引用调用 → 桥方法 → 真实方法

桥方法是擦除和多态（模块 3 的方法表）之间的粘合剂。追问链里它还有个著名应用——invokevirtual 指令通过符号引用找到方法时，找到的往往就是桥方法。面试能主动讲出桥方法，说明真理解了擦除。

一句话回答

什么是类型擦除？——泛型只存在于源码和编译期，javac 编译时把 <T> 替换为边界类型（无限定则 Object），并在调用点自动插入强转；字节码和运行时完全没有泛型。子类重写冲突靠编译器合成的桥方法解决。这样换来了与 Java 1.4 字节码的完全兼容 + 零运行时开销。

1
追问：怎么在运行时拿到泛型参数？（反射框架天天干这事）
擦除擦的是"使用处"的变量类型，但类声明、字段声明、方法签名里的泛型信息以 Signature 属性的形式保留在字节码里（不是被擦干净了）。所以 Field.getGenericType() 能拿到 List<String> 的完整泛型——Spring 的依赖注入、FastJSON 的反序列化就是这么知道该把 JSON 转成什么类型的。但局部变量和使用处的泛型真没了：new ArrayList<String>() 这行的 String 只活在编译期。
2
追问：既然擦掉了，为什么不能有 List<int>？
擦除后 T 变成 Object，而 int 不是 Object 的子类（基本类型不参与继承体系，模块 2）。装箱成 Integer 可以进 Object 世界，但那性能代价（模块 4 讲过自动装箱的坑）在高频集合操作里不可接受。所以 Java 选择直接禁止 List<int>，逼你用 List<Integer>。对比：Kotlin/Scala 在编译期把 List<Int> 特化成 int[] 语义的类，规避了这个问题；C# 的 reified 泛型根本没这限制。Valhalla 项目（Java 未来版本）的 generic specialization 就是要补这个历史窟窿。
04

擦除的代价：那些"莫名其妙"的编译报错 易错

理解了擦除，一大类"为什么这么设计"的烦人限制全部豁然开朗——它们不是语言设计者蠢，是擦除的必然推论：

限制报错样例为什么（擦除视角）
不能用基本类型List<int> ❌擦成 Object 后 int 无处安放（非对象）
不能 new T()new T() ❌运行时 T 已是 Object，new 出来的是 Object 不是 T
不能 T.classT.class ❌字节码里没有 T 这个类型，Class 对象不存在
不能 instanceof Tx instanceof T ❌运行时无 T 可比对（但 instanceof List<?> 可以）
泛型数组受限new T[10] ❌
new List<String>[10] ❌		数组协变 + 擦除 = 类型安全漏洞（见下）
静态成员不能用 Tstatic T field ❌静态成员属于类（raw 的 Box），不属于某个 Box<String>

4.1 泛型数组为什么被禁：一个思想实验

Why.java · 假如允许 new List<String>[10]
// 前置知识：数组是协变的（模块 4）—— Object[] 可以引用 String[]
List<String>[] lsa = new ArrayList<String>[10];  // 假设合法
Object[] oa = lsa;                    // 数组协变：OK
oa[0] = Arrays.asList(42);         // 存 List<Integer>：数组只检查"是不是 List"
                                      // （元素类型擦成 Object，检查不出 String）—— 存入成功！
String s = lsa[0].get(0);        // 💥 取出时编译器补强转，炸弹引爆

// 结论：允许泛型数组 = 打开一个编译器看不见的投毒通道
// Java 的选择：直接禁止。要存就用 List<List<String>>（集合是不变的，没有这个洞）

数组协变 + 泛型擦除 = 类型安全漏洞，这个组合拳推导面试出现过（区分度极高）。记住结论：数组是协变的（运行时检查），集合是不变的（编译期检查）——两种不同的类型安全哲学，Java 各取一半。

4.2 不能 new T() 的官方解法：传 Class 对象进来

Factory.java · 框架里的标准姿势
// T 在运行时不存在 → 让调用者把"类型的替身"（Class 对象）显式传进来
public static <T> T create(Class<T> clazz) throws Exception {
    return clazz.getDeclaredConstructor().newInstance();
}

User u = create(User.class);   // Class<User> 同时提供了运行时类型 + 泛型参数

// 这就是为什么 MyBatis mapper、Jackson 反序列化、Spring 反射创建 Bean
// 的 API 全长着 Class/Type/TypeReference 参数 —— 都是在给擦除"还债"
💡 记忆锚点

所有"泛型为什么不能 XXX"的答案都指向同一句话：运行时 T 不存在。new T() 需要 T 的构造器（不存在）、T.class 需要 T 的 Class 对象（不存在）、instanceof T 需要 T 做比对（不存在）。而解法永远是一个：把类型信息用 Class/TypeToken 的形式在运行时显式携带——这也正是反射登场的原因，自然过渡到下一节。

05

通配符与 PECS：不变类型的补丁 区分度

5.1 先搞清问题：集合"不变"带来的不便

集合是不变的（invariant）：List<String> 不是 List<Object> 的子类——哪怕 String 是 Object 的子类。这是对的（否则又开投毒通道：往 List<Object> 引用的 List<String> 里塞 Integer）。但完全不变又太死板：

Invariant.java · 合理的需求被拒绝
// 想写一个"打印任意数字列表"的方法 —— 数字家族：Integer/Double/...都行
void printNums(List<Number> list) { ... }

List<Integer> ints = Arrays.asList(1, 2, 3);
printNums(ints);     // ❌ 编译错误！List<Integer> 不是 List<Number>
                     // 方法只读不写，明明很安全 —— 不变性一刀切误伤了

通配符就是给"只读"和"只写"两种场景各开一扇受控的门：

Wildcard.java · 两扇门
// 门一：? extends —— 上界通配符（协变，只读门）
void printNums(List<? extends Number> list) {
    Number n = list.get(0);      // ✅ 读出来一定是 Number（或子类）
    list.add(new Integer(1)); // ❌ 编译器拒绝写入
                                  // （不知道确切元素类型，写什么都可能投毒）
}
printNums(ints);                  // ✅ Integer 是 Number 子类，放行

// 门二：? super —— 下界通配符（逆变，只写门）
void fillInts(List<? super Integer> list) {
    list.add(42);              // ✅ 写 Integer 一定安全（消费者至少装得下 Integer）
    Object o = list.get(0);     // ⚠️ 读出来只能当 Object（精确类型未知）
}
List<Number> nums = new ArrayList<>();
fillInts(nums);                   // ✅ Number 是 Integer 的父类，放行

5.2 PECS：Producer Extends, Consumer Super

Joshua Bloch（《Effective Java》作者）的口诀，回答"什么时候用哪个"：

  变量/参数是【生产者】（你从它读数据）→ extends（读出按上界用）
  变量/参数是【消费者】（你往它写数据）→ super（按下界写入）

  ┌─────────────┐   读(生产)    ┌──────────┐
  │ List<? extends X> │ ────────→ │  你（消费数据） │   extends 门只开"出"
  └─────────────┘              └──────────┘
  ┌─────────────┐   写(消费)    ┌──────────┐
  │ List<? super X>  │ ←──────── │  你（生产数据） │   super 门只开"进"
  └─────────────┘              └──────────┘

JDK 源码的活例子——Collections.copy 的签名就是标准 PECS 应用：

Collections.java · JDK 源码
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    // src 是生产者（往外吐数据）→ extends：允许 List<Integer> 复制进 List<Number>
    // dest 是消费者（吞数据）  → super：同上场景，目标容器是更宽的类型
}
// 于是这样合法：把 List<Integer>（src）复制到 List<Object>（dest）
Collections.copy(objectList, integerList);   // ✅
一句话回答

? extends 和 ? super 怎么选？——PECS：参数是数据生产者（你读它）用 ? extends T，是消费者（你写它）用 ? super T。extends 开只读门（协变，写入被禁），super 开只写门（逆变，读出仅 Object）。JDK 的 Collections.copy(dest-super, src-extends) 是教科书现场。

1
追问：? extends 写入为什么一刀切禁止？我明明知道 list 是 List<Integer>，add 个 Integer 不行吗？
编译器不知道。引用 List<? extends Number> 可能指向 List<Integer> 也可能指向 List<Double>——静态类型系统只看声明不看运行时（而运行时泛型又被擦了）。它必须按"最坏情况"设防：任何写入都可能投毒，所以全禁。想写入？显式收窄类型（声明成 List<Integer>）。这又回到同一个母题：擦除之下，编译器宁可错杀不可放过。
2
追问：Python 有协变逆变这些事吗？
概念有（typing.List 不变、Sequence 协变、Callable[[T], None] 逆变），但只对 mypy 有意义——运行时零约束。Java 的 extends/super 是编译器强制执行的访问控制，Python 的变型标注是给类型检查器的提示。你在 FastAPI 里写的 Sequence[User] 参数能接 list[User]，那是 Pydantic 运行时转换，不是类型系统协变。
06

反射：运行时的解剖刀 高频

6.1 为什么出现：配置驱动架构的需求

四问框架：编译期你就得知道要 new 哪个类、调哪个方法。但 2000 年前后企业级开发提出了新要求——把"用哪个类"写成配置，运行时再决定：

Config.java · 早期 Spring 的核心卖点
// applicationContext.xml（配置文件，改配置不改代码）
// <bean id="userService" class="com.demo.UserService"/>

// 框架启动时：读配置拿到类名字符串 → 运行时"凭名字"创建对象
String className = "com.demo.UserService";       // 来自配置
Class<?> clazz = Class.forName(className);               // ① 加载并拿 Class 对象
Object obj = clazz.getDeclaredConstructor().newInstance(); // ② 反射创建实例
Method m = clazz.getMethod("save", User.class);        // ③ 反射拿方法
m.invoke(obj, user);                                      // ④ 反射调用
// 全程没有任何一行代码 import UserService —— "解耦"到字符串级别

这就是反射的定义：程序在运行时检查、修改自身结构与行为的能力——凭字符串拿类、拿方法、拿字段，还能调用和赋值。它是 Spring IoC（按配置造对象）、MyBatis（接口映射 SQL）、JUnit（扫 @Test 方法）、Jackson（字段 ↔ JSON）的共同地基。

6.2 Class 对象：每个类的运行时身份证

反射的入口是 Class<?> 对象——类加载（模块 5 的加载阶段）时由 JVM 从字节码生成，每个类全局唯一（同一个类加载器下）。四种拿法：

GetClass.java
Class<?> c1 = User.class;                        // 类字面量：编译期已知类型，最稳
Class<?> c2 = new User().getClass();           // 对象实例：运行时从对象反查
Class<?> c3 = Class.forName("com.demo.User");  // 全限定名字符串：会触发类加载
Class<?> c4 = UserClassLoader.loadClass("com.demo.User"); // 自定义加载器

System.out.println(c1 == c2 && c2 == c3);       // true —— 全局唯一（同一加载器）
// 模块 5 的双亲委派保证了"一个类一个身份"，这是反射可靠性的前提

拿到 Class 后的"解剖三件套"：

拿什么API说明
构造器getConstructor() / getDeclaredConstructor()带 Declared 的系列能拿 private（但不加 setAccessible 调不了）
方法getMethod(name, 参数类型...) / getDeclaredMethods()getMethod 只拿 public（含继承的）；Declared 拿本类全部（含私有）
字段getField(name) / getDeclaredField(name)读写字段值：f.set(obj, value) / f.get(obj)

6.3 setAccessible(true)：破坏封装的口子

Private.java · 反射能干"宪法不允许"的事
public class User {
    private String name = "secret";
}

Field f = User.class.getDeclaredField("name");
f.setAccessible(true);              // 关掉访问检查 —— private 形同虚设
f.set(user, "hacked");              // 直接改私有字段

// 应用：Spring 依赖注入私有字段 @Autowired、Jackson 反序列化填私有字段
// 代价：Java 9 模块化后，跨模块 setAccessible 会抛 InaccessibleObjectException
//      （JPMS 收紧了这个口子 —— add-opens 才能打开）

封装只是编译器的君子协定，反射提供了撕毁协议的合法通道。框架广泛依赖它（注入私有字段），JDK 9 的模块系统又试图收紧——这个拉扯本身说明了反射的"越权"本质。

🐍 Python 对照 · 你天天在用"反射"

getattr(obj, "name") = Java 的 clazz.getField("name").get(obj)；hasattr / dir(obj) = 检查结构；obj.__dict__ = 字段全表；type(obj) = getClass()。FastAPI 根据函数签名自动生成 API 文档用的 inspect.signature()，就是 Java 反射 + 注解的合体。差异在于默认值：Python 一切属性天生可反射访问（没有 private，只有 _name 的命名约定）；Java 的 private 是真锁，反射是万能钥匙但开门有开销（下一节）。

一句话回答

反射是什么、为什么框架离不开它？——反射是运行时凭 Class 对象解剖类结构（构造器/方法/字段）并调用它们的能力；它让"类名、方法名写在配置里"成为可能，实现了编译期解耦——Spring IoC 的 @Autowired、MyBatis 的 Mapper 接口、JUnit 的 @Test 扫描，全是"运行时才知道要操作谁"的场景，没有反射就没有框架。

07

反射为什么慢：开销的三本账 原理

7.1 三本账

普通调用 obj.save(x)                  反射调用 m.invoke(obj, x)
┌──────────────────┐                ┌────────────────────────────┐
│ 编译期已确定：      │                │ ① 安全检查：参数类型/访问权限 每次都查  │
│ · 方法偏移量定死    │    ≈ 慢 10~50 倍（量级）  │ ② 装箱拆箱 + Object[] 参数组装     │
│ · JIT 可内联       │                │ ③ JIT 无法内联：invoke 对 JIT 是黑盒    │
│ · 零额外分配       │                │    （方法体动态多变，激进优化不敢做）    │
└──────────────────┘                └────────────────────────────┘
  1. 安全检查账：每次 invoke 都要做参数类型匹配 + 访问权限检查（普通调用在编译期就查完了，且 JIT 直接编译成一条 call 指令）。
  2. 装箱账：invoke(Object obj, Object... args) —— int 参数要装箱成 Integer，返回值要拆箱，参数数组是堆上分配的 Object[]。
  3. 优化账（最大头）：普通热点方法 JIT 会内联展开（模块 1 的栈帧里讲过方法调用成本），而 Method.invoke 是个"什么方法都可能调"的动态分发黑盒，JIT 不敢做激进假设，内联优化全免谈。

7.2 框架怎么优化：三条路

Optimize.java · 工业级做法
// ① 缓存 Method 对象：查找（getMethod 遍历方法表）只做一次
private static final Method SAVE = User.class.getMethod("save", User.class);
SAVE.setAccessible(true);   // 顺手关掉每次调用的访问检查（快 ~20%）

// ② 高频场景换 MethodHandle / LambdaMetafactory（JDK 7/8+）
MethodHandle mh = MethodHandles.lookup().findVirtual(User.class,
        "save", MethodType.methodType(void.class, User.class));
// MethodHandle 更接近"函数指针"，JIT 能内联（这是 invokedynamic 的底层机制，
// 模块 7 讲过 Lambda 的实现就靠它）—— 但 API 丑，一般只在高性能库（Jackson/fastjson2）里用

// ③ 釜底抽薪：编译期直接生成代码（APT/字节码生成），运行时零反射
// MapStruct 编译期生成 new User().setName(...) 的真代码；Lombok 编译期生成 getter
// —— "最好的反射是不反射"，第 9 节展开

注意一个常见的面试陷阱：反射慢是相对的——单次 invoke 大约百纳秒级，对"启动时创建 Bean"（一次性的）毫无影响；只有放在热路径（每秒百万次调用的序列化/Getter 场景）才成为瓶颈。所以正确表述是"反射的开销使其不适合热点循环，框架通过缓存 + 字节码生成规避"。

1
追问：Spring 启动那么慢是因为反射吗？
部分是，但主因是类路径扫描（遍历 jar 里的所有 .class 找注解）和初始化链（Bean 依赖图拓扑排序 + 逐个反射构造）。所以 Spring Boot 2+ 用 CGLIB 代理提前生成类、Spring 6 支持 AOT（Ahead-of-Time，构建期把反射点冻结成代码）来砍启动时间——GraalVM Native Image 更是把"运行时反射"变成"构建时代码生成"的极致版。你能从"反射三本账"推导出这些优化方向，就是满分答案。
08

注解：贴在代码上的标签 高频

8.1 本质：一个继承了 Annotation 的接口

Override.java · 注解的真身
// 你写的 @Override，本质是这样一个接口：
public @interface Override { }   // javac 编译后：interface Override extends Annotation

// 带属性的注解 = 接口方法（所以注解只支持"看起来像常量"的类型）
public @interface MyAnno {
    String value();                // 属性 = 无参方法
    int priority() default 0;  // default 给默认值
}
@MyAnno(value = "test")        // 使用 = "实现"这个接口，传入"方法返回值"

注解本身没有任何行为——它只是一份结构化元数据，安静地躺在那里，等待某个"消费者"（编译器 / 运行时反射 / 工具）来读。这是和 Python decorator 最本质的区别：Python 的 @app.get("/users") 是立刻执行的函数（返回闭包、注册路由，行为全在装饰器里）；Java 的 @GetMapping("/users") 是一条静态记录（Spring 启动时反射扫描到它才发生点什么）。

8.2 @Retention：标签贴到哪一层被撕掉

元注解（贴在注解定义上的注解）里最重要的一条——生命周期三档：

策略活到哪谁能读例子
SOURCE只到源码，编译即丢弃编译器/静态工具@Override @SuppressWarnings
CLASS（默认）进 class 文件，运行时不加载字节码工具（ASM/AspectJ 织入）少见，框架一般不用默认值
RUNTIME一路活到运行时反射 getAnnotation@Autowired @Test @Transactional
Retention.java · 为什么你的注解反射读不到
@Retention(RetentionPolicy.RUNTIME)   // ← 没这行的注解，运行时反射是读不到的！
@Target(ElementType.METHOD)            // 只能贴在方法上（贴别处编译报错）
public @interface LogExecution { }

// 运行时读取 —— 和反射合体，构成"配置即代码"的闭环：
for (Method m : clazz.getDeclaredMethods()) {
    if (m.isAnnotationPresent(LogExecution.class)) {
        // 找到贴了标签的方法 → 反射调用 / 生成代理包一层日志（第 10 节）
    }
}
// Spring 扫描 @Component 的原理和这三行代码没有本质区别，只是加了缓存和索引
一句话回答

注解的本质是什么？——一个继承 Annotation 的接口，本身无行为，是贴在类/方法/字段上的结构化元数据；靠 @Retention 决定生命周期（SOURCE 编译即弃 / CLASS 留在字节码 / RUNTIME 活到运行时），运行时档的注解由反射 getAnnotation 消费——"注解贴标签 + 反射读标签"就是 Spring 一切魔法的最小闭环。

1
追问：@Autowired 为什么要求字段不能是 final？字段注入和构造器注入谁好？
字段注入靠反射 field.set(obj, value) 写入，而 final 字段反射改不了（JLS 限制，JDK 17 后更是直接抛异常）；构造器注入是把反射创建 new 的参数交给你 —— 类型安全、可测试（不用容器也能 new）、依赖显式（构造器参数一眼看清依赖面）。所以 Spring 官方和现代规范都推构造器注入，字段注入只在老代码里常见。这个追问把注解、反射、泛型串成了一条线——终章知识点的联动现场。
2
追问：Python 的装饰器和 Java 注解到底差在哪？
三个维度：① 执行时机——decorator 在 import 时立即执行（函数被替换/注册），注解在编译期只是元数据，消费与否看框架；② 能力——decorator 是真函数，能做任何事（闭包、注册、改行为），注解只能携带常量数据（String/Class/枚举/基本类型/注解嵌套/它们的数组）；③ 改行为靠谁——Python 装饰器直接改，Java 要"注解 + 动态代理"两件套（@Transactional 的实现 = 扫描注解 + 生成代理类加事务逻辑）。所以 Java 的"装饰器等价物"是注解 + AOP，不是注解本身。
09

APT：编译期消费注解，生成代码 拓展

注解的第二个消费时机不在运行时，而在编译期——注解处理器（Annotation Processing Tool，APT）。 javac 编译的轮次中留了钩子：让你在编译时读到注解，然后生成新的源码文件参与本轮编译。

Apt.java · Lombok 就是这么工作的
// 你写的：
@Data
public class User { private String name; }

// Lombok 的 APT 处理器在编译期"看到" @Data，直接修改/生成 AST（语法树），
// 编译出来的 class 文件等价于：
public class User {
    private String name;
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public boolean equals(Object o) { ... }   // + hashCode + toString
}
// 源码里没有这些方法，字节码里有 —— "编译期魔法"

同门师兄弟的分工：

技术消费时机产物代表
运行时反射运行时无代码生成，每次反射调用Spring/Jackson（灵活但有开销）
APT编译期生成新源码参与编译Lombok、MapStruct、AutoValue（零运行时开销）
字节码增强编译后/类加载时直接改写字节码AspectJ 织入、JaCoCo、SkyWalking Agent

面试一般问到"知道 Lombok 原理"即可，深问就答"APT 改 AST，所以 IDE 要装 Lombok 插件才能不报错"——这个细节能体现你真用过。

🐍 Python 对照

Python 没有"编译期生成代码"的对应物（有 __init_subclass__ / 元类这种运行时钩子，dataclasses 装饰器也是在 import 时给类动态加方法——时机对等于 Java 的"类加载时"，不是编译期）。@dataclass 和 Lombok @Data 是绝妙的对照组：功能一样，实现时机不同——前者运行时加，后者编译期生成，这是两种语言哲学的缩影。

10

JDK 动态代理：运行时合成 $Proxy0 原理核心

10.1 它解决什么：不改原类，给方法加前后缀

四问框架：日志、事务、权限、监控——这些功能要"包"在业务方法外面（方法前开事务、方法后提交/回滚）。直接改业务代码 = 侵入；继承重写 = 一个类一个子类，写不过来。需要一个运行时按需生成的"替身类"：接口方法全转发给一个统一的处理器。

ProxyDemo.java · JDK 动态代理三要素
// ① 业务接口（JDK 代理的硬性要求）
interface UserService {
    void save(String name);
    void delete(int id);
}

// ② 目标对象（真身，不实现接口也行——只要接口存在）
class UserServiceImpl implements UserService {
    public void save(String name) { System.out.println("保存 " + name); }
    public void delete(int id)   { System.out.println("删除 " + id); }
}

// ③ InvocationHandler：所有方法调用的统一收发室
UserService target = new UserServiceImpl();
InvocationHandler handler = (proxy, method, args) -> {
    System.out.println("[前置] 调用 " + method.getName());   // 加料：日志/事务/权限
    Object result = method.invoke(target, args);            // 反射调用真身
    System.out.println("[后置] 完成");                        // 加料：提交/回滚
    return result;
};

// 合成代理对象：运行时 JVM 动态生成类 $Proxy0（extends Proxy implements UserService）
UserService proxy = (UserService) Proxy.newProxyInstance(
        target.getClass().getClassLoader(),          // 用目标类的加载器（保证能见到接口）
        target.getClass().getInterfaces(),           // 要实现的接口列表（反射拿的！）
        handler);                                    // 统一处理器

proxy.save("jerry");   // 输出：[前置] 调用 save → 保存 jerry → [后置] 完成
proxy.delete(1);     // 两个方法都被同一套前后缀包住 —— 一处定义，处处生效

10.2 生成的 $Proxy0 长什么样（为什么必须接口）

$Proxy0.java · 运行时合成类的等价源码（javap 反编译可见）
public final class $Proxy0 extends Proxy implements UserService {
    // equals/hashCode/toString 和每个接口方法，全是同一个套路：
    public final void save(String var1) {
        try {
            // 不干正事，把"哪个方法 + 什么参数"打包交给 h（你的 Handler）
            super.h.invoke(this, m3_save, new Object[]{var1});
        } catch (Throwable t) { ... }
    }
}
// 谜底揭晓——【为什么 JDK 代理必须基于接口】：
// Java 单继承：$Proxy0 已经 extends Proxy（为了拿到 h 字段和基础设施），
// 只能把"身份"寄托在实现接口上。没有接口 = 没有第二张身份牌 = 无法成为替身。

把这句话说进面试：JDK 动态代理生成的类已经把唯一的继承名额用掉了（extends Proxy），所以只能通过实现接口来获得目标类型的行为契约——这就是"必须基于接口"的根本原因。

一句话回答

JDK 动态代理的原理？——运行时由 JVM 动态生成一个 $Proxy0 extends Proxy implements 你的接口 的类，它每个方法的实现都是把 (this, Method, args) 打包转发给 InvocationHandler.invoke()；你在 Handler 里反射调用目标对象并织入前后逻辑。因单继承名额被 Proxy 占用，所以必须有接口。

1
追问：method.invoke(target, args) 里再调 handler 不就死循环了？怎么保证调的是真身？
关键在两个对象：代理对象 proxy 和目标对象 target 是不同的引用。$Proxy0 的方法转发给 handler 时传的是 proxy（代理自己）；而 handler 内部 method.invoke(target, ...) 用的是你闭包里捕获的 target（真身）。如果你手滑写成 method.invoke(proxy, ...)——恭喜，无限递归 StackOverflow。这是动态代理面试的隐藏彩蛋题，考的就是"proxy 和 target 的引用区分"。
2
追问：Python 里怎么实现同样的效果？
你天天在写：装饰器就是"方法级"的动态代理（前后加料、转发调用）；__getattr__ 是"类级"的（任意属性访问统一收发，等价 InvocationHandler）；Django/FastAPI 的中间件是"请求级"的。区别是 Python 的替身在解释器层面天然支持（一切皆对象、一切可拦截），Java 的替身要生成一个真类——因为 Java 的方法调用必须落在静态类型上，没有"凭空拦截"这个能力，只能造一个"看起来一样"的类来顶包。这再次呼应终章主线：静态语言获得动态能力的每一步，都要付一次"生成代码"的代价。
11

CGLIB 与 Spring AOP 的选择策略 高频

11.1 CGLIB：用继承代替接口

没有接口的类怎么办？CGLIB（Code Generation Library）换了个思路：生成目标类的子类，重写所有非 final 方法：

CglibDemo.java · 子类代理
// 目标类：没有实现任何接口，JDK 代理无能为力
public class OrderService {
    public void pay() { System.out.println("支付"); }
}

Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(OrderService.class);          // 以真身为父类
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    System.out.println("[前置]");
    Object result = proxy.invokeSuper(obj, args);    // 调用父类（真身）方法
    System.out.println("[后置]");
    return result;
});
OrderService proxy = (OrderService) enhancer.create();  // 生成 OrderService$$EnhancerByCGLIB$$xxx
proxy.pay();   // [前置] → 支付 → [后置]

CGLIB 的三张红线（面试常考）：

  • final 类不能代理（不能被继承）——String 就不行
  • final/private/static 方法不能被增强（不能被重写，静默跳过——所以有时注解贴了却没生效，先查方法是不是 final）
  • 构造器会被调用两次（父类一次 + CGLIB 反射实例化一次），字段初始化逻辑重复执行——细节坑

11.2 两者对比与 Spring 的选择

维度JDK 动态代理CGLIB
实现方式实现接口（ extends Proxy）继承目标类（生成子类）
硬性要求目标必须实现接口类和方法不能是 final
依赖JDK 自带（java.lang.reflect）第三方库（Spring 已内嵌，JDK 17+ 需处理模块限制）
方法拦截只能拦接口里声明的方法能拦子类可见的所有方法
性能JDK 8 后 invoke 已高度优化生成慢一点、调用快一点（早期结论，现在差距很小）

Spring AOP 的实际策略（面试标准答案）：目标类实现了接口 → 默认用 JDK 代理；没实现接口 → 自动切 CGLIB；Spring Boot 2.x 起统一默认 CGLIB（proxyTargetClass=true）——因为混合模式下，一个 @Service 有接口一个没有，容器里会出现"有的 Bean 能按接口注入、有的必须按类注入"的不一致，统一 CGLIB 消灭了这种心智负担。这个"为什么默认变了"的演进故事是很好的加分项。

💡 记忆锚点 · AOP 的完整拼图

@Transactional 生效的完整链路（终章四件套串烧）：注解（贴标签 @Transactional）→ 反射（启动扫描发现它）→ 动态代理（CGLIB/JDK 生成代理类，方法被 MethodInterceptor 包住）→ 代理方法内开事务、反射调用真身、提交/回滚。同时自调用失效（this.method() 绕过代理直接打真身）的原因也在这：事务在代理层，不在真身层——这个经典坑的答案就藏在代理的结构里。

1
追问：既然 CGLIB 能代理无接口的类，为什么 JDK 还要自带那套基于接口的？
时间线：JDK 代理 2000 年前后进 JDK（JDK 1.3），CGLIB 1999 年诞生但作为第三方库存在。JDK 不能依赖第三方库，只能自己实现一套——而"实现接口"是 JVM 层面最容易被动态满足的契约（接口没有构造器、没有状态，合成类最简单）。CGLIB 走 ASM 字节码生成的路子更自由但更重。另外 JDK 17 的强封装（sun.misc 不可用）一度让 CGLIB 失效，催生 Spring 改用 JDK 内置的 ClassFile API / ByteBuddy——技术演进从不停歇，但"接口 vs 继承"这两条路二十年没变过。
2
追问：动态代理和静态代理（手写代理类）什么时候选谁？
静态代理：你提前知道要代理谁、方法少且固定（比如给第三方 SDK 的某个类包一层重试），编译期可见、IDE 可导航、无魔法。动态代理：方法多/不确定（日志事务权限这种横切关注面要罩住所有方法），或代理对象要按配置在运行时决定（MyBatis 的 Mapper 接口，编译期根本不知道有哪些 SQL）。一句话：确定性用静态，横切面和运行时决策用动态。

全模块小结：四块地基一块砖 收尾

12.1 四问框架回顾

为什么出现？  集合装 Object 的强转炸弹 + 框架需要"配置驱动、运行时组装"
什么场景？    集合类型安全 / IoC 容器造对象 / 注入私有字段 / 事务日志权限横切
怎么出现的？  Java 5（2004）泛型+注解革命；反射是 JVM 与生俱来的自省能力；
              JDK 1.3 动态代理；CGLIB 补齐无接口场景
解决了什么？  编译期类型合同（泛型）+ 运行时元编程（反射/注解/代理）
              —— 但各自留下代价：擦除限制、反射开销、代理的 final 红线

12.2 一张表带走全部

泛型
  • 动机：把强转炸弹拦在编译期
  • 实现：类型擦除（T → 边界/Object + 调用点强转）
  • 桥方法：擦除与多态的粘合剂
  • 代价：无基本类型 / new T() / T.class / 泛型数组
  • PECS：生产者 extends，消费者 super
反射
  • 入口：Class 对象（每类全局唯一）
  • 三件套：Constructor / Method / Field
  • 越权：setAccessible(true) 破封装
  • 慢的三本账：安全检查 / 装箱 / 无法内联
  • 优化：缓存 Method → MethodHandle → APT
注解
  • 本质：extends Annotation 的接口，无行为
  • @Retention 三档：SOURCE / CLASS / RUNTIME
  • 消费：运行时反射读 / 编译期 APT 生成代码
  • Lombok = APT 改 AST
  • vs decorator：标签 vs 会执行的函数
动态代理
  • JDK：$Proxy0 extends Proxy implements 接口
  • 必须接口的根因：单继承名额被 Proxy 占用
  • CGLIB：生成子类，final 是红线
  • Spring Boot 2+ 默认 CGLIB（一致性）
  • 自调用失效：事务在代理层不在真身层

🐍 终极 Python 对照 · 一以贯之

贯穿全书的对照关系收个尾：Java 泛型是强制契约，Python typing 是君子协定；Java 反射要持证上岗（Class 对象 + 开销），Python 反射是母语；Java 注解等框架消费，Python 装饰器当场执行；Java 动态代理生成真类，Python 拦截天生免费。面试被问"你从 Python 转 Java 最大的思维转变"，这四句就是满分答案的骨架：从"运行时一切皆可"到"编译期担保一切"——自由换确定性，代价换性能。
