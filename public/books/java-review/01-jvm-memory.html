02

JVM 运行时内存全景

2.1 五大区域：先背"谁私有、谁共享"高频★★★

JVM 把内存划分为 5 块。前三块跟着线程走（线程私有），后两块所有线程共用（线程共享）——这个划分直接决定了并发模块的一系列结论。

一句话回答

栈管运行（方法怎么一步步执行），堆管数据（对象放在哪），方法区管模板（类长什么样）。线程私有的栈保证每个线程执行互不干扰；共享的堆是所有对象交换数据的场所。

🐍 Python 对比

CPython 同样有"栈帧 + 对象堆"的模型（sys._getframe() 能看到帧对象，所有对象在堆上分配并靠引用计数回收）。区别：Python 连 int 都是堆上的对象（id(10) 就是地址），而 Java 的 int 是栈上的裸数值——这也是 Java 更快的原因之一。

03

虚拟机栈：方法执行的舞台

3.1 栈帧：每调用一个方法，压入一个栈帧高频★★★

方法调用 = 压栈；方法返回 = 弹栈。栈帧里最重要的两块：

  • 局部变量表：存放方法参数 + 方法内声明的局部变量（后面 3.2 详讲）
  • 操作数栈：计算的中转站。例如 int c = a + b; 会先把 a、b 压入操作数栈，执行 iadd 弹出相加，结果再压回去——JVM 是一台"栈式计算机"
方法调用与栈帧的变化结构
main() 调用 add()，add() 再调用 square()：

main 开始        main 调 add       add 调 square     square 返回      add 返回
┌────────┐      ┌────────┐       ┌────────┐
│        │      │        │       │square帧│  ←栈顶   （square弹出） （add弹出）
│        │      │  add帧 │       ├────────┤
├────────┤      ├────────┤       │ add帧  │
│ main帧 │      │ main帧 │       ├────────┤
└────────┘      └────────┘       │ main帧 │
                                 └────────┘
→ 结论：方法没执行完，它的栈帧就一直占着内存；
  调用层次太深（比如无限递归），栈被塞满 → StackOverflowError
两种栈相关错误Java
// ① StackOverflowError：栈深度超限（经典复现：无终止条件的递归）
void recurse() { recurse(); }          // 不久后抛 StackOverflowError
// 栈容量由 -Xss 设置（默认约 512KB~1MB），线程越多、每个栈越小

// ② OutOfMemoryError: unable to create new native thread
// 不断 new Thread 且不结束：每个线程一套私有栈，耗尽内存

3.2 局部变量表：局部变量真正的家难点★★

先明确概念——什么是局部变量：

局部变量 vs 成员变量（位置划分）Java
public class Demo {
    int memberVar = 10;              // ① 成员变量（实例变量）：定义在"类里、方法外"
                                     //    → 跟着对象走，存在堆中的对象体内

    static int staticVar = 20;       // ② 成员变量（静态变量）：也定义在类里方法外
                                     //    → 跟着类走，全局一份

    public void method(int param) {  // param：方法的参数，也是一种局部变量
        int localVar = 5;            // ③ 局部变量：定义在"方法内部"
                                     //    → 存在本方法栈帧的局部变量表里
        if (true) {
            int blockVar = 6;        // ④ 局部变量：代码块 {} 内声明，出了块就不能用
        }
        // blockVar 这里已经不可访问 —— 作用域到 } 为止
    }
}

局部变量表的本质是一排固定大小的槽位（slot）：

  • 一个 int 占 1 个槽（32 位），long/double 占 2 个槽
  • 基本类型：槽里直接放数值
  • 引用类型：槽里放地址（指向堆中对象）
  • 实例方法第 0 个槽固定放 this——这就是静态方法里没有 this 的原因
⚠ 关键结论：为什么局部变量没有默认值

局部变量表只是"划了一块地"，JVM 不负责把槽位清零，里面可能是上一个方法留下的脏数据。为避免读到随机值，Java 编译器强制"先赋值、后使用"，否则直接编译报错——把风险拦在编译期。（对比：堆中的对象分配后 JVM 会统一零值化，所以成员变量有默认值，见 07 章）

🐍 Python 对比

Python 的局部变量未赋值就使用会抛 UnboundLocalError（运行时才报）。Java 是编译期拦截。两者机制不同（Python 运行时查名字绑定，Java 编译器数据流分析），但设计意图一样：不让程序读到未初始化的内存。

04

堆：对象的家

4.1 堆的定位高频★★★

  • 所有对象实例和数组都在堆上分配（有例外：JIT 逃逸分析的栈上分配优化，视为高级细节，认知层面记住"对象在堆"即可）
  • 堆是线程共享的，所以多个线程可以同时拿到同一个对象的引用去操作——并发的各种问题（竞态、可见性）都源于此（模块 6 展开）
  • 对象不再被引用后，由 GC 自动回收——不用像 C 语言那样手动 free（GC 细节在模块 5）
  • 堆内存不足时抛 java.lang.OutOfMemoryError: Java heap space
堆的基本参数与分代（了解结构即可，细节模块5）Java
// 堆大小控制
-Xms512m    // 初始堆大小
-Xmx2g      // 最大堆大小（生产环境通常设成与 Xms 相等，避免运行时扩容抖动）

// 堆内部按"对象存活时间"分区（GC 的话题，这里只建立形状概念）
// 堆 ┬─ 新生代 ┬─ Eden（绝大多数对象在这里出生，也在这里夭折）
//    │         └─ Survivor ×2（从 Eden 幸存下来的对象）
//    └─ 老年代（多次 GC 后仍存活的对象，如缓存、Spring 单例 Bean）
堆和栈分别存什么？一个对象创建后哪些部分在栈、哪些在堆？

栈存局部变量（基本类型的值 / 引用类型的地址）和方法的执行状态；堆存对象本体（字段值、数组元素）。

以 Person p = new Person("Tom") 为例：p 这个变量在 main 的栈帧里（放地址）；new Person(...) 出来的对象（含 name 字段及其指向的 String）在堆里。另外"Person 类长什么样"这个模板信息在方法区。

05

方法区：类的家

5.1 方法区存什么高频★★★

方法区（Method Area）是类层面信息的仓库，一个类只存一份：

  • 类元信息：类名、字段、方法、字节码指令
  • 运行时常量池：字面量（如字符串 "abc"、final int X=10）和符号引用——其中字符串的部分叫字符串常量池（模块 2 重点用）
  • 静态变量（JDK 7 起实际存到了堆中，认知上仍归方法区管辖，见下）

5.2 一次重要演进：永久代 → 元空间难点高频★★★

方法区是规范（逻辑概念），怎么实现是虚拟机自己的事，而 HotSpot 的实现换过一次——这是面试的经典考点：

JDK 7 及以前（永久代）JDK 8 及以后（元空间）
位于哪堆的一部分（连续区域）本地内存（Native Memory，不在堆里）
大小限制-XX:MaxPermSize，容易满 → PermGen OOM默认仅受物理内存限制（可用 -XX:MaxMetaspaceSize 设上限）
为什么要改永久代大小难估：动态代理、热部署、大量类加载场景容易爆；且与 HotSpot 内部其他 VM 的架构不统一，JEP 122 干脆移除

同一时期的两个"搬家"事件（常被一起考）：

  • JDK 7：字符串常量池从永久代 移到堆（因为永久代容易满、而 String.intern 语义要调整）
  • JDK 7：静态变量也从永久代 移到堆（挂在 Class 对象上）
  • JDK 8：永久代整个废除，类元信息搬到元空间（本地内存）
一句话回答

方法区存"类的模板信息"：类结构、常量池、静态变量。JDK 8 前用堆里的永久代实现、易 OOM；JDK 8 起改为本地内存中的元空间，字符串常量池和静态变量则早在 JDK 7 就搬进了堆。

⚠ 面试官口径提醒

被问"字符串常量池在哪"：JDK 7 起在堆中（别再答"方法区"，这是老答案）。被问"静态变量在哪"：JDK 7 起在堆（随 Class 对象），JDK 8 的元空间里没有它。这两问坑过很多人。

6.2 赋值与"修改"的语义差异难点★★★

最容易混淆的三段代码Java
// 情形一：基本类型赋值 → 值拷贝，之后互不影响
int a = 10;
int b = a;       // b 拿到的是 10 这个值的副本
b = 99;
System.out.println(a);   // 10，a 不受影响

// 情形二：引用类型赋值 → 地址拷贝，两个引用指向同一个对象
Person p1 = new Person("Tom");
Person p2 = p1;          // p2 复制的是 0x100 这个地址
p2.setName("Jerry");     // 通过 p2 修改的是"那一个"对象
System.out.println(p1.getName());   // Jerry！p1 也看到修改（同一对象）

// 情形三：给引用本身重新赋值 → 只是改了这个变量自己的指向，别的引用无感
p2 = new Person("Spike");  // p2 指向新对象 0x200，p1 仍指向 0x100
System.out.println(p1.getName());   // 还是 Jerry
💡 心智模型

把引用类型的变量当成"遥控器"：赋值 = 复制一个遥控器（控制同一台电视）；p2 = new ... = 给这个遥控器重新配对到另一台电视（原电视不受影响）；p2.setName(...) = 按遥控器上的按钮（真的动了那台电视）。判断任何"改了之后谁受影响"的问题，都回到这张图。

🐍 Python 对比

Python 的变量全部是引用（连整数都是堆上对象的引用），没有"值拷贝"型赋值。但行为模型一致：可变对象（list/dict）= Java 的普通对象；不可变对象（int/str/tuple）≈ Java 的 String（改不动，只能新建）。所以 Python 的 a = [1]; b = a; b.append(2) 后 a 也变——和 Java 情形二完全同构。

1
基本类型和引用类型的区别？
存储内容不同：基本类型变量直接存值（栈），引用类型变量存对象地址（栈存地址、对象在堆）。由此推出：赋值语义、== 比较语义、参数传递行为全都不同。
2
引用可以理解为指针吗？
接近但受限：都是"存地址"，但 Java 引用不能做指针运算（不能 +1）、不能取地址、由 GC 管理。说"安全的指针"没问题。
3
对象一定在堆上吗？
认知层面：是。加分项：JIT 逃逸分析发现对象没逃出方法时，可能"标量替换"打散到栈上——这是优化细节，不违背"对象在堆"的语义模型。

7.2 "默认值之谜"的内存解释难点★★★

为什么成员变量自动有默认值、局部变量却必须手动初始化？从内存视角一句话讲透：

  • 成员变量（堆）：对象在堆中分配内存时，JVM 会把整块内存统一清零（这也是安全要求——不能让新对象读到上一个死掉对象的脏数据）。清零后的位模式按类型解释：int 的 32 个 0 就是 0，boolean 的 0 就是 false，引用的 0 就是 null。所以默认值 = "零值"，不是什么特别设计，是清零的副产品。
  • 局部变量（栈）：方法调用只是把局部变量表"划出槽位"，JVM 出于性能不负责清零（栈帧进出极频繁，每次清零开销大）。脏数据风险交给编译器解决——数据流分析确认"未赋值就使用"直接编译报错。
默认值速查（仅成员变量）Java
class Defaults {
    int i;              // 0
    long l;             // 0L
    double d;           // 0.0
    boolean b;          // false
    char c;             // '\u0000'（码值为 0 的字符）
    String s;           // null（引用类型都是 null —— 注意不是空串 ""！）
    int[] arr;          // null（数组引用也是引用，别以为是空数组）

    void method() {
        int x;
        // System.out.println(x);   // ❌ 编译错误：variable x might not have been initialized
        int y = 0;                   // ✅ 显式初始化后才能用
    }
}
⚠ 高频事故：null 默认值

成员变量是包装类型/集合/对象时，默认值是 null。典型事故：Controller/Service 的字段忘记注入或赋值，运行时 NullPointerException——这是"默认值"概念在工程里最常咬人的地方。

                 │   （初始化顺序的完整规则在模块 3 面向对象展开）

8.2 对象在堆中的内存布局高频★★★

对象的三个部分（64位 JVM，开启压缩指针）结构
┌──────────────────────────────────────┐
│ 对象头 (Object Header)               │
│   ├─ Mark Word (8B)：hashCode、GC 分代│ ← 模块5(GC)、模块6(锁) 都会回来讲它
│   │   年龄、锁标志位                   │
│   └─ 类型指针 (4B)：指向方法区的类信息  │ ← 所以对象知道自己是哪个类（反射的根基）
├──────────────────────────────────────┤
│ 实例数据 (Instance Data)              │
│   各字段的值（父类字段在前，子类在后）   │
├──────────────────────────────────────┤
│ 对齐填充 (Padding)                    │
│   补齐到 8 字节的整数倍                │
└──────────────────────────────────────┘

一个 int 字段的对象为什么不止 4 字节？
  Integer 实际 = 对象头 12B + int 字段 4B = 16B  → 装 4 字节的值要花 16 字节，
  这就是"包装类比基本类型重 4 倍"的量化依据，也是集合里存 Integer 的隐性成本。
对象头里的 Mark Word 是什么？为什么重要？

Mark Word 是对象头前 8 个字节，一块"多用途"存储区，内容随对象状态切换：无锁态存 hashCode + GC 分代年龄；偏向锁/轻量级锁/重量级锁状态下分别存线程 ID / 锁记录指针 / 监视器指针（模块 6 synchronized 锁升级的核心依据）。

它是"锁信息存在对象上而不是代码上"的原因——Java 任何对象都能当锁，就是锁信息记录在对象头里。

8.3 我们怎么访问对象：引用 → 对象★★

栈里的引用 p 指向堆对象，有两种实现方式：

  • 直接指针（HotSpot 采用）：p 里直接存堆地址 → 访问快一次到位
  • 句柄：p 存句柄池地址，句柄再存对象地址 → GC 移动对象时只需改句柄，引用本身不动（了解到这个对比即可）
09

包装类：为什么存在

9.1 设计动机：基本类型的三个"不能"高频★★★

有了基本类型（快、省内存），为什么还要包装类？因为基本类型作为"裸数值"有三件事做不到：

三个"不能"Java
// ① 集合/泛型只能装"对象" —— ArrayList 直接编译错误
List<int> wrong;                 // ❌ 泛型不支持基本类型（类型擦除的历史原因，模块9 详述）
List<Integer> right = new ArrayList<>();   // ✅ 必须用包装类

// ② 基本类型表达不了 null —— 而业务中"没有值"是真实存在的
int score = null;                       // ❌ 编译错误
Integer score = null;                   // ✅ 数据库字段为 NULL、Map 里查不到 key，都需要它
Map<String,Integer> m = new HashMap<>();
Integer v = m.get("不存在");            // null —— 用 int 接住会在拆箱时 NPE

// ③ 基本类型不是对象，没有方法、不能参与面向对象机制
10.toString();                          // ❌ int 就是裸数值，调不了任何方法
Integer.toString(10);                   // ✅ 包装类有静态方法
Integer.MIN_VALUE;                      // ✅ 常量也在类上
一句话回答

包装类 = 把基本类型包成对象，让它在"只能用对象"的场合（泛型集合、null 语义、调用方法/反射）也能出场。性能敏感的局部计算用基本类型，需要对象语义时用包装类。

9.2 自动装箱 / 拆箱：编译器的语法糖超高频★★★

装箱 = 堆里造对象；拆箱 = 取出值Java
Integer i = 10;    // 自动装箱：编译器翻译成 Integer i = Integer.valueOf(10);
                    //   → 在堆中创建/复用一个 Integer 对象（别忘了模块1的图：对象在堆！）
int n = i;         // 自动拆箱：编译器翻译成 int n = i.intValue();
                    //   → 从对象里把 int 值取出来放回栈

// 关键认知：装箱拆箱发生在【编译期】，是编译器插入方法调用，
// JVM 运行时并没有"自动"魔法 —— 所以能被反编译看清，也有性能成本

9.3 Integer 缓存池：== 陷阱的元凶超高频★★★

现在用本模块的内存知识解释那个经典问题——为什么 127 相等、128 不等：

缓存池的内存真相结构
Integer a = 127;  Integer b = 127;      Integer c = 128;  Integer d = 128;

 堆中的 IntegerCache（类加载时预建好的数组，装着 -128~127 的对象）
 ┌───────────────────────────────┐
 │  ... [126] [127] [128] ...    │
 │           ↑     ↑             │
 │           └──┬──┘             │      a == b → true
 │ a 和 b 指向【同一个】缓存对象    │      （同一地址）
 └───────────────────────────────┘
                                  ┌──────────┐   ┌──────────┐
                                  │ Integer  │   │ Integer  │
                                  │ 值: 128  │   │ 值: 128  │   c == d → false
                                  └──────────┘   └──────────┘   （两个不同地址的新对象）
                                   ↑ c 指向这个      ↑ d 指向这个
                                   （valueOf 超出缓存范围就 new 新对象，各造各的）
valueOf 源码与结论Java
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)   // low=-128, high=127
        return IntegerCache.cache[i + 128];   // 命中缓存：返回预建对象（地址相同）
    return new Integer(i);                    // 超范围：每次 new（地址必不同）
}
// 上限可通过 -XX:AutoBoxCacheMax=N 调大（仅 Integer 有这个待遇）

// 铁律：包装类型之间的比较，永远用 equals，不用 ==
Integer c = 128, d = 128;
c == d          // false：比地址（两个堆对象）
c.equals(d)     // true ：比值（Integer 重写了 equals 按数值比较）
包装类缓存范围
Byte / Short / Long / Integer-128 ~ 127（Integer 上限可调，其余固定）
Character0 ~ 127
BooleanTRUE / FALSE 两个单例
Float / Double无缓存（浮点值无穷多，缓存无意义）
🐍 Python 对比

CPython 的小整数池缓存 [-5, 256]：a=256; b=256; a is b 为 True。和 IntegerCache 动机完全一致（小整数高频，复用省内存）。记忆锚点：Python 的 is ≈ Java 的 ==（比地址/身份），Python 的 == ≈ Java 的 equals（比值）。

9.4 拆箱 NPE：内存视角的必然结果易错★★★

凡是"null 引用 + 拆箱"都会炸Java
// 拆箱 = 调用 对象.intValue() → 对象是 null 就是 null.xxx() → NPE
Map<String, Integer> map = new HashMap<>();
int cnt = map.get("不存在");     // get 返回 null，赋给 int 触发拆箱 → NullPointerException

Integer maybeNull = null;
int x = maybeNull + 1;          // 运算符要求 int，自动拆箱 → NPE

// 防御写法
Integer v = map.get("k");
int safe = (v == null) ? 0 : v;        // 显式判空给默认值
int safe2 = Objects.requireNonNullElse(v, 0);   // JDK 9+
⚠ 阿里规范（工程共识）

POJO / 数据库映射实体的字段用包装类型（要能表达 null）；局部变量 / 循环计算用基本类型（避免无谓装箱 + 天然免疫拆箱 NPE）。

1
为什么要有包装类？
基本类型进不了泛型集合、表达不了 null、没有方法可调。包装类把数值包成对象补齐这三点。
2
Integer a=127,b=127; a==b ？那 128 呢？
127 true（命中缓存池，同一个堆对象）；128 false（超范围各 new，地址不同）。所以包装类一律 equals。
3
什么时候会 NPE？
null 的包装类型参与拆箱：赋给 int、参与算术运算、Map.get 结果直接接 int。
4
Integer == int 呢？
一边是基本类型时，== 会把包装类【自动拆箱】按数值比 → 不受缓存影响，纯比值。（缓存坑只在两边都是包装类时出现）

== 与 equals：内存视角的第一课

10.1 == 的本质：比较"变量槽里存的东西"超高频★★★

有了前面的内存图，== 的规则不用背，是推出来的：== 比较的就是变量槽里放的内容——

  • 基本类型的槽里放数值 → == 比数值
  • 引用类型的槽里放地址 → == 比地址（是不是同一个对象）
== 全景Java
// 基本类型：比值（类型不同先自动提升）
int a = 100; long b = 100L;
a == b                     // true（int 提升为 long，比数值）

// 引用类型：比地址
String s1 = new String("x");   String s2 = new String("x");
s1 == s2                   // false：两个不同的堆对象（内容一样但地址不同）
s1.equals(s2)              // true ：String 的 equals 比内容

// 混合：一边基本类型一边包装类 → 拆箱比值
Integer i = 1000;  int n = 1000;
i == n                     // true：编译器插入 i.intValue()，变成数值比较

10.2 equals：Object 的方法，默认就是 ==高频★★★

  • equals 是 Object 类的方法（所有对象都有），默认实现就是 ==（比地址）：
Object.equals 的默认实现Java
// java.lang.Object 里（JDK 源码就一行）
public boolean equals(Object obj) {
    return (this == obj);          // 没重写时，equals 和 == 完全等价
}

// String / Integer 等对它做了"重写"（Override = 子类重新实现父类方法的逻辑，
// 模块 3 详解）—— 重写后 equals 变成"逐字符/按数值比内容"：
"abc".equals(new String("abc"))   // true：String 重写后比内容
new Integer(100).equals(100)      // true：Integer 重写后比数值
一句话回答

== 比变量槽里存的东西：基本类型比值、引用类型比地址。equals 是 Object 的方法，默认等价于 ==；String、Integer 等常用类重写后按内容比较。自定义类不重写 equals 就只能比地址。

📌 本模块刻意不讲的部分

equals/hashCode 的重写规范、为什么"重写 equals 必须重写 hashCode"、只重写一个会怎样——这些属于"方法重写"和"哈希容器"的话题，放在模块 3（面向对象·重写）用 HashSet 分桶图详细讲透，届时你会看到只重写一半时 HashSet 里到底发生了什么。

高频面试题速查（自测清单）

合上笔记口头回答，答不出的回到对应章节。点击展开参考答案。

1. JVM 运行时数据区有哪几块？哪些线程私有？

五块：程序计数器、虚拟机栈、本地方法栈（线程私有）；堆、方法区（线程共享）。栈溢出 StackOverflowError（递归过深），堆/方法区不足 OOM。

2. 栈和堆分别存什么？

栈：方法调用的栈帧（局部变量表放参数和局部变量——基本类型直接放值，引用类型放堆地址；操作数栈做计算中转）。堆：所有对象实例与数组本体，线程共享，由 GC 回收。

3. 为什么局部变量必须初始化，成员变量却有默认值？

成员变量在堆中随对象分配，JVM 分配时统一清零 → 零值即默认值。局部变量在栈帧槽位中，JVM 出于性能不清零，编译器通过数据流分析强制"先赋值后使用"，否则编译报错。

4. 方法区、永久代、元空间是什么关系？字符串常量池在哪？

方法区是规范概念。HotSpot JDK7 及以前用堆中的"永久代"实现，JDK8 起改为本地内存中的"元空间"（避免类加载多时 OOM，参数从 MaxPermSize 变为 MaxMetaspaceSize）。字符串常量池和静态变量在 JDK 7 起就搬到了堆中。

5. 基本类型和引用类型的区别？

基本类型变量直接存值（栈），8 种；引用类型变量存对象地址，对象本体在堆。由此产生赋值语义（值拷贝 vs 地址拷贝）、== 语义（比值 vs 比地址）、参数传递行为的三重差异。

6. new 一个对象的完整过程？

① 检查类是否加载（未加载先触发类加载）→ ② 堆中分配内存（TLAB 优化）→ ③ 零值初始化（成员变量默认值的来源）→ ④ 设置对象头（Mark Word + 类型指针）→ ⑤ 执行属性显式赋值、构造代码块、构造方法。

7. 对象由哪几部分组成？一个 Integer 对象占多少内存？

对象头（Mark Word 8B + 压缩类型指针 4B）+ 实例数据 + 对齐填充（8 的倍数）。Integer = 12B 头 + 4B int = 16B，是基本 int 的 4 倍——包装类的空间成本。

8. 为什么要设计包装类？

① 泛型/集合只能存对象；② 需要 null 语义（数据库 NULL、Map 查不到）；③ 基本类型没有方法、无法参与反射等面向对象机制。工程规范：实体字段用包装类，局部计算用基本类型。

9. Integer 127==127 与 128==128？为什么？

true / false。IntegerCache 缓存 [-128,127]，valueOf 命中返回同一对象；超出则每次 new，地址不同。== 比地址所以 128 不等，equals 比值恒为 true。Float/Double 无缓存，包装类比较一律 equals。

10. == 和 equals 的区别？

== 比变量槽内容：基本类型比值、引用类型比地址；Integer 与 int 比较会先拆箱。equals 是 Object 方法，默认实现就是 ==；String/Integer 等重写后比内容；自定义类不重写则仍比地址（重写规范与 hashCode 联动见模块 3）。
