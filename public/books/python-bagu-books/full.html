第 1 章 · MRO：类找方法的路线图P0 高频考点

1.1 为什么出现：多继承的歧义问题

普通函数调用没有歧义：方法名写在哪，就去哪找。但多继承一出现，麻烦就来了——一个方法同时出现在多个父类里，到底先去哪个找？

MRO（Method Resolution Order，方法解析顺序）就是答案：它是一个元组，把从当前类到 object 的所有祖先类按线性顺序排好。运行时查找方法，就是沿这条队伍从头到尾问一遍，谁先应答用谁的。

🏠 比喻：族谱排队

把一个类的所有祖先想象成一支排好队的家族队伍：自己站第一排，爸爸们按声明顺序站第二排，爷爷们往后排，object 永远垫底。找方法就是从队头往队尾挨个问「你有 who 吗？」，第一个说「有」的就成交，后面的不再打扰。

1.2 C3 线性化：三条规则

CPython 用 C3 线性化算法计算这个顺序，规则就三条：

  1. 子类永远排在父类前面（不然爸爸会抢儿子的方法）；
  2. 多个父类按声明顺序排（class D(B, C) 里 B 先于 C）；
  3. 同一个类只出现一次（菱形继承的共同祖先去重）。
class A:
    def who(self): print("A")

class B(A):
    def who(self): print("B")

class C(A):
    def who(self): print("C")

class D(B, C):      # 菱形继承：D → B、C → A
    pass

D().who()           # 输出 B —— 沿 MRO 先找到 B 的，C 根本没被查
D.__mro__           # (D, B, C, A, object) —— 这条队伍就是 MRO
# 队伍怎么来的：
#   规则1：D 排最前（子类在前）
#   规则2：B 在 C 前（class D(B, C) 的声明顺序）
#   规则3：A 只出现一次（B、C 共同的祖先去重，排在他们之后）

如果继承图无法线性化（比如两个类互相要求对方在前），Python 会直接报 TypeError: Cannot create a consistent method resolution——不给运行时埋雷。

展开：菱形继承的查找路径图
MRO：菱形继承的查找路径
D 继承 B 和 C，B、C 都继承 A；C3 线性化为 D → B → C → A → object

1.3 super() 走序列，不走继承图

最容易考的一问：super() 到底跳到哪？直觉答案是「父类」，这是错的。正确答案是：跳到 MRO 的下一个类。

⚙️ 机制：super() 等价于 super(B, self)

super() 的落点不是编译期定的，是运行时按两步算出来的：拿 type(self).__mro__ → 在这条队伍里找到当前类（比如 B）→ 从下一位开始找。B 的下一位是谁？由实例的类的 MRO 说了算，跟「B 的父类是谁」无关。

class A:
    def who(self): print("A")
class B(A):
    def who(self):
        print("B")
        super().who()      # 落点运行时才知道 —— 关键就在这行
class C(A):
    def who(self):
        print("C")
        super().who()
class D(B, C): pass

B().who()   # 输出 B A  ← B 实例：MRO=(B, A, object)，super 跳到 A
D().who()   # 输出 B C A ← D 实例：MRO=(D, B, C, A, object)，B 里的 super 跳到 C！
🧑‍🎓 追问（原话）

「第一个问题是 D 走到 B，我可以理解 D 应该也走到了 C，而不是说 B 里面的 super who 走到了 C。B 和 C 没有关系啊？」

这个追问质量很高，答案分两层：

机制谁发起走法
属性查找 d.who()解释器沿 MRO 找到第一个命中就停：D → B，结束。C 从头到尾没被查过
super() 链你写的代码沿同一条 MRO 显式往下续：B → C → A

所以「走到 C」的不是查找，是 B 方法体里那句 super().who()。B 和 C 之间确实没有继承关系——但它们是 D 的线性化序列里的邻居；super 走序列，不走继承图。这就是为什么 mixin 模式能工作：mixin 不需要认识谁，只要它在最终类的 MRO 里排对位置就行。

🎭 面试作答：MRO 与 super()

30 秒版：MRO 是类查找方法的线性顺序，CPython 用 C3 线性化计算：子类在前、父类按声明顺序、去重。super() 不是跳到父类，是跳到「实例类的 MRO 里当前类的下一位」——落点由实例决定，不由代码位置决定。

2 分钟版：先讲问题来源：多继承时方法可能出现在多个父类，需要一条无歧义的查找顺序。再讲三条规则和菱形继承例子（D→B→C→A→object）。然后甩出关键区分：属性查找找到第一个命中就停；super() 链是显式沿同一条 MRO 往下续。举例：同一份 B.who() 代码，B 实例上 super 跳到 A，D 实例上跳到 C——因为 super() 等价于 super(B, self)，运行时取 type(self).__mro__ 找下一位。最后补一句：MRO 无法线性化时直接 TypeError，错误在类定义期就暴露。

第 2 章 · ob_type 与 __dict__：对象的内部世界P1 高频考点

2.1 类型对象就是类：三个容易混的概念

讨论对象模型之前，先把三个词拆干净：

概念是什么一句话
ob_type字段名每个对象头部那个类型指针，指向「它的类型」
类型对象就是类type(42) 是 int、type(d) 是 D——你自己写的类同样是类型对象；类自己也是对象，type(D) 是 type
object根类所有类隐式继承它，每条 MRO 的最后一站，兜底提供 __init__、__repr__
🧑‍🎓 追问（原话）

「object type 不是 int、string 那些吗？难道 object type 可以是类？一个对象去找方法的时候，会走到 object type 这个类，这个类又有它的一个 MRO，进行了 C3 线性化，然后去里面一个一个去找方法？」

这段复述只改一个词就全对：对象找方法时走到的是它自己的类（D），不是「object type 这个类」。链路是：d --ob_type--> D --__mro__--> 逐类翻 __dict__。int、str 是类，你自己写的 D 也是类——类型对象不神秘，它就是类。

2.2 __dict__：对象的「属性仓库」

每个对象身上（几乎）都有一个 __dict__，就是个字典，存这个对象自己的属性。分两种：

class Point:
    color = "red"                  # 类属性 → 存进「类的 __dict__」

    def __init__(self, x, y):
        self.x = x                 # 实例属性 → 存进「实例的 __dict__」
        self.y = y

    def show(self):                # 方法 → 也存进「类的 __dict__」
        return f"({self.x}, {self.y})"

p = Point(1, 2)

p.__dict__        # {'x': 1, 'y': 2}  ← 实例仓库：只有数据，没有方法
Point.__dict__    # mappingproxy({'color': 'red', '__init__': ..., 'show': ...})

四条要点：

  • 方法不住在实例身上，住在类的 __dict__ 里。第 1 章说「沿 MRO 逐类查 __dict__」，查的就是这排仓库——哪个仓库先命中用哪个；
  • 取属性的完整路径：p.x 先翻 p.__dict__（命中返回）；p.color 实例仓库没有 → 沿类的 MRO 翻类仓库；全没有才 AttributeError；
  • 赋值只写实例仓库：p.color = "blue" 往 p.__dict__ 加了一条，把类里的 "red" 遮住（shadow），类的 __dict__ 纹丝不动——这就是为什么改一个实例不影响别的实例；
  • 两个花边：类的 __dict__ 是 mappingproxy（只读视图，防止绕过语法直接塞东西进类）；定义了 __slots__ 的类没有 __dict__，属性存在固定槽位——「__slots__ 省内存」的原理就在这。
🏠 比喻：两层仓库

实例仓库是你随身的口袋，类仓库是全村共用的祠堂。找东西先掏口袋，口袋没有再去祠堂（按 MRO 的顺序挨家祠堂问）；往口袋里放新东西不会动祠堂，所以你改自己的不影响别人。

2.3 ob_type 的用处：它是「行为说明书」

🧑‍🎓 追问（原话）

「这个 object type 有什么用？是用于 type 包裹的时候去判断它的类型吗？」

type() 判断只是它最不重要的一个用途。ob_type 真正的身价是：Python 一切动态行为都靠它决定「这个对象该怎么表现」。

用途例子说明
类型判断type(x) is int、isinstance(x, T)type() 只是读出 ob_type 指向谁
方法派发d.show()沿 ob_type 指向的类的 MRO 找 show——第 1 章的链路
运算符行为1 + 2、"a" + "b"执行引擎查 type(左值) 的 __add__，同一运算符不同类型不同结果
迭代/长度for x in obj、len(obj)查它的类有没有 __iter__、__len__
造类本身type("D", (B, C), {...})type 是「类的类」（元类），类都是它造出来的

一句话：ob_type 指向的类型对象是所有行为的说明书。判断类型只是翻开说明书看封面，方法派发和运算符分派才是每行代码都在用的功能。

2.4 属性查找的完整链路（把两章拼起来）

d = D()
d.__dict__          # {} —— 实例身上没有 who
'who' in D.__dict__ # False
'who' in B.__dict__ # True ← 方法住在 B 的 __dict__ 里
type(d).__mro__     # (D, B, C, A, object) ← 查找沿这条走
# 完整链路：d --ob_type--> D --__mro__--> 逐类翻 __dict__，B 命中
🎭 面试作答：__dict__ 与属性查找

30 秒版：每个对象有 __dict__ 属性仓库：实例仓库存实例属性，类仓库存类属性和方法。取属性先翻实例 __dict__，没有再沿 type(X) 的 MRO 逐类翻类 __dict__，全没有才 AttributeError；赋值只写实例仓库，遮住类属性但不修改它。

2 分钟版：展开三条：一是方法住在类 __dict__ 而非实例身上，这解释了为什么一千个实例共享一份方法、内存不爆炸；二是 shadow 机制：p.color = "blue" 只是实例口袋里加了一条，类仓库不动，其他实例不受影响；三是 __slots__：定义后实例没有 __dict__，属性存固定槽位，省掉每个实例一个字典的开销——大规模对象（比如百万级数据类）的常规优化。最后点题：这套「口袋+祠堂」的两层结构，配合 MRO，就是 Python 属性系统的全部。

第 3 章 · 魔术方法 vs 魔术属性P1 概念辨析

3.1 一个 callable 判别法

🧑‍🎓 追问（原话）

「我之前应该让你给我展示过它的一个魔术方法，但是你好像并没有给我展示这个 dict 属性。我就奇怪，这个 dict 是魔术方法吗？如果是的话，它还有别的魔术方法，你没有给我说明吗？」

答案：__dict__ 不是魔术方法，是「魔术属性」。双下划线家族其实分两支，判别标准一句话：魔术方法是「函数」，被你写的语法隐式调用；魔术属性是「数据」，挂在你身上等你主动去读。

callable(d.__dict__)     # False —— 是个字典，不是函数 → 魔术属性
callable(Demo.__init__)  # True  —— 魔术方法，可调用
callable(d.__call__)     # True  —— 魔术方法，可调用
🏠 比喻：钩子 vs 数据兄弟

魔术方法是钩子：你写 d + other、len(d)、with d:，Python 替你悄悄调用对应的 __add__、__len__、__enter__——你不喊它，它只在语法触发时出现。魔术属性是数据兄弟：__dict__、__mro__、__closure__ 只是安静挂在身上的仓库和账本，你不主动读它就永远不工作。

值得盯住的细节：一个「全副武装」的演示类里，整个脚本没有一处显式调用 .__add__()、.__len__()——全是 d + Demo(1)、len(d) 这种普通语法，钩子被隐式触发。还有一个彩蛋：list(d) 会多触发一次 __len__——因为 list() 构造时会先问对象「你大概多长」来预分配空间，协议之间也会互相调用。

3.3 魔术属性的来源：三线供应

🧑‍🎓 追问（原话）

「我知道 __init__、__call__ 这几个魔术方法是由元类提供的；而关于迭代、调用、运算符比较以及上下文等一些魔术方法，是由 object 类提供的。那我想知道，魔术属性应该也是由 object 类提供的吧？」

两个前提都要修，先看事实：

  • 「__init__、__call__ 由元类提供」——半对。 Demo(3) 这整个动作确实走元类：type.__call__ 在 type 身上，它内部再去调 __new__ 和 __init__。但 __init__/__new__ 本身是 object 提供的（证据：Demo.__init__ is object.__init__ → True，你没写 init 时直接用 object 的）；而 d()（实例被调用）查的是 Demo 的 __call__，object 不提供，得自己写；
  • 「迭代、运算符、上下文由 object 提供」——不对。 object 只提供一小撮默认：__init__、__new__、__repr__、__eq__、__hash__。__iter__、__len__、__add__、__enter__ 没有任何默认实现，你不写就是 TypeError: object is not iterable。这正是鸭子类型的立足点：协议靠你实现，不靠从 object 白拿。

魔术属性的完整答案是分三线供应，规则统一：

谁的魔术属性描述符挂在哪例子
实例的object 身上 + 造类时注入每个类的命名空间__dict__（getset_descriptor）、__class__
类的type 身上__mro__（member_descriptor）、__name__、__bases__
函数的FunctionType 身上__code__、__closure__、__defaults__

统一规则：查 X 的魔术属性和查普通属性走同一条路——沿 type(X) 的 MRO 找。实例沿 (Demo, object)，类沿 (type, object)，函数沿 (FunctionType, …)。魔术属性不是特殊通道，找到的只是一个 C 级描述符。两个收尾认识：描述符和数据是分离的——描述符只定义「怎么读写」，数据存在每个对象自己的 C 结构里，所以 d.__dict__ 是 {'x': 1} 而 d2.__dict__ 是 {}；例外是 __wrapped__——object 和 type 身上都没有它，它是 functools.wraps 手动塞的普通属性。

🎭 面试作答：魔术方法 vs 魔术属性

30 秒版：双下划线家族分两支：魔术方法是函数钩子，被语法隐式触发（len() 触发 __len__、+ 触发 __add__）；魔术属性是数据（__dict__、__mro__、__closure__），要主动去读。判别法一条：callable() 测试。来源上，魔术属性沿 type(X) 的 MRO 查，描述符分别在 object、type、FunctionType 身上。

2 分钟版：先给判别法，再给全景表里的三四个高频族（容器协议、比较哈希、上下文管理、异步协议）。然后讲两个容易答错的细节：一，object 只提供 __init__/__new__/__repr__/__eq__/__hash__ 等一小撮默认，__iter__/__len__/__add__ 没有默认实现——鸭子类型的协议是「你不写就没有」；二，「类() 被调用」这个动作本身走 type.__call__（元类），但 __init__ 的默认版本来自 object。最后点题：这套机制统一在「沿 type(X) 的 MRO 找属性」一条路上——Python 的对象模型没有第二套查找逻辑。

第 4 章 · 生成器协程：yield from 与 send()P0 高频考点

为什么叫「协程」？普通函数是调用-返回一次就结束；生成器是暂停-恢复多次产出值；加了 send() 之后还能接收外部传进来的值——函数和调用方能双向通信，这就有了协程的雏形。

4.1 send()：不只是取值，还能塞值进去

普通 yield 生成器是单向的（只产出）：

def gen():
    yield 1
    yield 2
    yield 3

g = gen()
next(g)    # 1  ← 取值
next(g)    # 2

给 yield 加接收能力——x = yield value：yield value 把 value 抛出去、暂停；下次 g.send(数据) 把数据塞回 yield 表达式，赋值给 x，函数继续跑：

def accumulator():
    total = 0
    while True:
        x = yield total      # 抛出 total，暂停；send(n) 时 x = n
        total += x           # 接收到外部传来的 x，累加

acc = accumulator()
next(acc)          # 0  ← 第一次必须 next「启动」，跑到第一个 yield，返回 total=0
acc.send(10)       # 10 ← 把 10 塞给 x，total=0+10=10，抛出
acc.send(20)       # 30 ← 把 20 塞给 x，total=10+20=30，抛出
acc.send(5)        # 35

send() 的两条规则：第一次必须用 next() 启动（首个 yield 前没有接收点，send 无处可塞，会报错）；send(v) 和 next() 一样返回下一个 yield 抛出的值——区别只是 next() 塞的是 None，send(v) 塞的是你指定的值。

展开：send() 双向通信时序图
send()：调用方与生成器双向通信
yield 既是出口（抛出值）也是入口（接收 send 的值）

4.2 yield from：委托子生成器

yield from 让一个生成器把产出职责委托给另一个生成器：

# 不用 yield from：手动逐个转发
def chain(a, b):
    for x in a:
        yield x      # 从 a 取一个，抛给调用方
    for x in b:
        yield x

# 用 yield from：直接委托整个子生成器
def chain(a, b):
    yield from a     # 把 a 的产出全部转发，a 结束才继续
    yield from b

list(chain([1, 2], [3, 4]))   # [1, 2, 3, 4]

它等价于把子生成器的每个值透传出去，但还做了三件手动 for 做不到的事：

yield from 自动做的事说明
1 值透传子生成器的产出直接给调用方
2 send 透传调用方的 send 塞回子生成器
3 return 透传子生成器的 return 值成为表达式结果：result = yield from sub

手动 for+yield 只能做第 1 件，后两件做不到。验证「return 透传」：

def sub():
    yield 1
    yield 2
    return "done"          # 子生成器的返回值

def outer():
    result = yield from sub()   # 透传 1、2；sub 结束后 result = "done"
    print(f"sub 返回: {result}")
    yield 3                    # sub 结束后 outer 继续

g = outer()
next(g)   # 1       ← sub 产出，透传给调用方
next(g)   # 2       ← sub 产出，透传
next(g)   # 打印 "sub 返回: done"，然后产出 3

yield from 的价值：把多层生成器串起来时，send 和 return 能穿透中间层直达底层。这是异步编程的基石——await 本质上是增强版的 yield from。

4.3 三件套与准协程

g = accumulator()
next(g)              # 启动

g.send(10)           # 塞值进去（数据通道）
g.throw(ValueError)  # 在 yield 处抛异常，生成器内可 try/except 捕获
g.close()            # 在 yield 处抛 GeneratorExit，生成器收尾退出

throw 让调用方能往生成器注入异常，close 通知生成器终止。三个方法让生成器从「被动产出器」变成「能接收值、能被注入异常、能被通知终止的受控执行体」——这就是协程的雏形。

把 send + yield from 拼起来，一个能接收数据、能委托的「准协程」：

def sub_accumulator():
    """子生成器：累加，send 进来的数加到 total"""
    total = 0
    while True:
        x = yield total      # 抛出 total，暂停等 send
        if x is None:        # None 表示结束信号
            return total     # 返回累加结果
        total += x

def main():
    result = yield from sub_accumulator()   # 委托，sub 的 return 值传给 result
    print(f"最终: {result}")

g = main()
next(g)         # 启动，sub 跑到 yield，返回 total=0
g.send(10)      # 10  ← sub 收到 10，total=10
g.send(20)      # 30
g.send(None)    # 打印 "最终: 30"，sub return 30 传给 result

整个链条：调用方 send → 外层 yield from 透传 → 子生成器收到并处理 → 子 return → 外层 result 接住。外层只做「接线」，真正干活的是子生成器。

🎭 面试作答：生成器怎么变协程

30 秒版：生成器本来只产出；PEP 342 加了 send/throw/close——send 把值塞回 yield 表达式，实现双向通信；PEP 380 加了 yield from——委托子生成器并透传产出、send、return。三者合起来，生成器成了能暂停恢复、能双向通信、能受控终止的执行体，就是协程雏形；async/await 底层就是这套协议。

2 分钟版：按演化讲：先讲 yield 单向产出（暂停-恢复），再讲 x = yield value 双向版（send 塞值、首次必须 next 启动、next 就是 send(None)），再讲 yield from 三件透传（值、send、return）——手动 for 只能做第一件。举例 accumulator：send(10) → total=10 → yield 10。最后收在 send/throw/close 三件套：这是「受控执行体」的完整协议，原生协程对象至今沿用同一套 send/throw/close，只是挂起点从 yield 换成了 await。

第 5 章 · async/await：从生成器协程到原生协程P0 高频考点

5.1 三个常见误解修正

学习者的类比（async=子生成器用 yield 收参数，await=外部调用 send 传参数）骨架对，三处要修——这三处正是面试的区分点：

误解修正
「async 用 yield 接收参数干活」这条通道 asyncio 压根不用：send 的永远是 None，只是「继续跑」的信号；原生协程里写 yield 会变成异步生成器（另一个东西）
「await 时传入参数」方向反了：await 是等结果。值走 yield from 的 return 透传通道（见下方 Future.__await__）
「我的代码驱动协程」驱动者是事件循环：唤醒、传值、抛异常全是循环和 Task 干的，你的代码只负责写 await
# Future.__await__ 的真身（简化）——值走 return 通道的铁证
def __await__(self):
    if not self.done():
        yield self           # 把 Future 抛给 Task：我还没好，先挂起
    return self.result()    # 值从这里 return，沿 await 链一路上传

5.2 状态总账房：Future / Task / 事件循环

🏠 比喻：取餐叫号屏、一桌的总账、总调度台

Future 是一次性的取餐叫号屏：PENDING → FINISHED（记 result 或 exception）/ CANCELLED，一个屏管一件事。Task 是一整桌的总账本：包住一条协程负责驱动，协程抛的异常记在 Task 身上，没人取才在 GC 时打警告。事件循环是总调度台：管三本账——就绪队列（谁该跑了）、定时器堆（何时该跑）、selector（I/O 好了没）。

5.3 跟一个 await 走完一圈（六步）

  1. Task.__step 调 coro.send(None)，协程跑到 await fut；
  2. fut 未完成：Task 把自己挂到 fut 的完成回调上，控制权还给循环；
  3. 循环去跑别的就绪任务，或用 selector.select(timeout) 等 I/O——单线程的「同时」就发生在这里；
  4. I/O 就绪：回调调 fut.set_result(数据)，顺手把 Task.__step 重新排进就绪队列；
  5. 轮到它：coro.send(None) 恢复，Future.__await__ 里 return self.result()，值沿 await 链上传；
  6. 协程继续跑到下一个 await，或结束（StopIteration.value 成为 Task 的结果）。

「谁成功谁失败」的用户出口：

results = await asyncio.gather(fetch_a(), fetch_b())   # 全成功给结果列表；一个失败立刻抛

async with asyncio.TaskGroup() as tg:                   # 3.11+：一个失败 → 取消其余 → 抛 ExceptionGroup
    tg.create_task(fetch_a())
    tg.create_task(fetch_b())

真正实现并发的杠杆是 create_task：await job() 是顺序（当场跑完才继续），create_task(job()) 才是把协程注册给循环、让它和别的任务交错跑。单线程并发 = 在 await 点之间来回切换，把 I/O 等待时间让给别人——I/O 密集赚翻，CPU 密集不加速（GIL 还在）。

第 6 章 · 事件循环与 selector：摸到内核门口P0 高频考点

6.1 协程是惰性的：没有循环它根本不跑

🧑‍🎓 追问（原话）

「原来 await 是顺序的，只有加入了事件循环，它才是一个并发的。没有事件循环它也还是阻塞呗。」

比阻塞更彻底：协程对象是惰性的，根本不会跑。async def 函数被调用只产出协程对象，一行代码都不执行，直到被 send() 驱动；asyncio.run() 的第一件事就是建循环。所以并发公式是：多任务 + 一个调度器，async/await 只贡献「挂起点」这个原材料，本身不给并发。

6.2 迷你事件循环：三个部件

手写一个 60 行的循环（不用 asyncio），核心就三个部件，对照 asyncio 内部：

while ready or timers:                  # 还有活干就转

        wake_at, _, coro = heapq.heappop(timers)

当时对真实 asyncio 流程的复述被打分 90 分，被修正的三处细节（也是面试易错点）：

易错说法修正
「小顶堆，先执行时间短的任务」堆确实是小顶堆，但按到期时刻排，不是任务时长——弹出的永远是「下一个该响的闹钟」
「循环最后一步把 socket 交给 selector」注册发生在协程请求等待的那一刻（request 分支里）；select() 调用发生在没人可跑时——两件事时机不同
「操作系统和程序实时通信」OS 不推送，是程序主动问：select/epoll_wait 阻塞等待，OS 只在被问时回答「哪些 fd 就绪了」

「没有任务了就等着呗」——对，但分三种情况：ready 空但 timers/I/O 有货 → 阻塞在唯一的等待点等最近的事件（真实 asyncio 里 select(timeout=距最近闹钟)，I/O 和定时器共用这一个等待点）；全空 → while 条件不成立，循环退出收尾；有人不挂起（纯 CPU 循环）→ 单线程被独占，别人全卡住——协作式调度的代价。

6.3 selector：外包给操作系统的监控台

🏠 比喻：外包监控台

selector 是「外包给操作系统的监控台」——你把一堆 socket 登记给它，然后在一个地方睡觉，OS 谁就绪了就叫醒你并告诉你「是哪几个」。没有它，单线程想同时等 3 个连接，只能挨个 recv 试试（忙轮询烧 CPU）或者一个连接开一个线程（1000 连接就是 1000 线程）。它就是「一个线程 + 一次等待 + N 个连接」的那个开关。

三个动作对到代码就是三行：

  • 请求分支里 sel.register(target, EVENT_READ, data=coro)——登记，顺手把协程当包裹存进 data 字段；
  • 等待区 sel.select(timeout)——全脚本唯一一次真正的睡觉；
  • 醒来后 sel.unregister + key.data 取回协程塞回 ready。

关键道具是 data 字段：登记时把协程存在登记簿上，fd 就绪时从登记簿上把协程领回来——这就是 asyncio 里「Future.set_result 的完成回调把任务排回就绪队列」的迷你版。

任务 A 的完整闭环（六步对应六行代码）：

  1. coro.send(None) 跑到 yield from wait_read(r_A)，把 ("read", r_A) 抛给循环——协程挂起，它自己不碰 selector，只递申请单；
  2. 循环在 request 分支里 sel.register(r_A, EVENT_READ, data=coro_A)——fd 进登记簿，协程存进 data；
  3. ready 空了，循环算出 timeout = 0.30 - now = 0.15（距最近闹钟），调 sel.select(0.15)——线程在这里睡着，这一觉同时等两件事：3 个 fd 谁可读、闹钟响；
  4. t=0.20 后台线程 sendall，内核把 r_A 标记可读，select 立刻醒来返回 [(key_A, ...)]——是 OS 叫醒的，不是我们轮询发现的；
  5. sel.unregister(r_A)（一次性，用完即注销），key_A.data 领回 coro_A，塞进 ready；
  6. 下一轮 coro_A.send(None)，从 yield 处恢复，recv(1024) 拿到数据（fd 已被担保可读，绝不阻塞），函数 return，StopIteration.value 进 results。

6.4 fd：内核发的取件号；epoll 比 select 强在哪

🏠 比喻：取件号

fd（file descriptor）= 内核发给每个 I/O 资源的取件号，一个小整数：socket 是 3 号、文件是 5 号，管道、终端都有号——Unix「一切皆文件」的落地。Python 的 socket 对象只是包装纸，sel.register 真正登记进内核的是 fileno() 那个数字。

顺带三个高频小问题：

  • recv(1024) 是什么、为什么 1024？recv 就是「取件」：把内核替你存在接收缓冲区里的字节搬进 Python 内存；1024 是这一次最多取多少字节的缓冲区大小，纯属习惯值。recv 返回「现在有的」，可能少于 1024——发了 7 字节就还你 7 字节；10MB 大文件得循环拼到够数为止。它平时是阻塞调用，但醒来时内核已担保可读，所以必不阻塞——「先确认就绪、再动手」。
  • OS 不知道协程的存在：ready 队列和 timers 堆是循环自己的账本；selector 登记簿是「循环写入、内核盯梢」；OS 只认 fd，叫醒到 fd 就收工。「fd → 协程」的换算是循环用 key.data 自己做的。
  • 模拟实验里的角色分配：socketpair() 造一对互通的真 socket——写端 w 给后台线程（扮演「0.2 秒后才回包的假服务器」），读端 r 给事件循环登记进 selector；中间隔的是真内核：sendall 的字节由内核搬进 r 的接收缓冲区并标记可读、叫醒 select。内核侧机制和真实网络通信一字不差。

epoll 强在哪：老 select 每次调用都要把全部 fd 拷进内核再挨个扫一遍；epoll 在内核里常驻一份就绪清单，返回的直接就是就绪的那几个——fd 一多差距就爆炸。DefaultSelector 自动挑当前系统最强的实现：Linux 是 epoll，macOS 是 kqueue，兜底才是老家伙 select。

6.5 「不还是 for 循环去问吗？」——select 睡等 vs 轮询

🧑‍🎓 追问（原话）

「while ready or timers or sel.get_map(): … for key, _ in sel.select(timeout): … 可是这里不还是 for 循环去问吗？」

不是。这个 for 不问任何东西——等待发生在 sel.select(timeout) 这一次调用的内部，for 只是在拆它醒来后交回来的返回值列表。实测数据说话：同样等 0.5 秒，select 只花了 0.146 毫秒 CPU（线程真在睡），轮询烧掉 0.5 秒 CPU、空转了 567,650 次。

片段发生什么问 OS 几次
sel.select(timeout)一次系统调用：问一遍「谁就绪了？」然后线程挂起，数据到达或闹钟到点才返回问 1 次，睡到底
返回值 [(key_A, ...)]一个普通 Python 列表，通常 0~2 项0 次
for key, _ in ...遍历上面这个列表，逐项拆包0 次，纯内存操作

两个循环也别混：外层 while 是调度循环，一圈代表「处理一批就绪事件 + 跑一轮协程」，节奏是「问一次 → 睡 → 醒 → 干活」慢慢转；「每秒问一百万次」的那种 while True 才叫轮询。睡觉发生在括号里，for 发生在睡醒后。

🎭 面试作答：事件循环的工作原理

30 秒版：事件循环是个 while 调度循环，管三个结构：就绪队列（待驱动的协程）、定时器堆（按到期时刻排的小顶堆）、selector 登记簿（fd → 协程）。协程在挂起点递交申请（睡多久/等哪个 fd），循环驱动其他任务；没人可跑时阻塞在唯一等待点 select(timeout)，被 OS 或闹钟叫醒后把就绪协程塞回队列。单线程并发就发生在这场重叠的等待里。

2 分钟版：先纠正两个常见误区：协程是惰性的，async def 调用只产出对象、不执行代码，必须被循环 send(None) 驱动——所以「多任务 + 调度器」才等于并发；等待不是轮询，select 是一次系统调用内部挂起，被 OS 主动叫醒，for 只是拆返回值。再讲数据流六步：协程 yield 申请单 → 循环 register(fd, data=coro) → 循环睡在 select(timeout) → OS 标记可读并叫醒 → key.data 换回协程塞回 ready → send(None) 恢复、recv 取件、StopIteration 收结果。最后补协作式调度的代价：谁不挂起谁独占线程，CPU 密集任务会把别人全卡住——所以 asyncio 只适合 I/O 密集。

第 7 章 · Python 是编译型还是解释型？P0 经典问题

经典疑问：「教程说 Python 是解释型语言，Java 是编译为字节码然后由虚拟机运行——到底哪个对？」

结论：两种说法各对一半。机制上 Python 和 Java 是同一种东西：源码 → 编译成字节码 → 虚拟机执行。教程没讲错运行机制，错在分类标签——「解释型」是历史遗留的简化叫法。真正的区别不在「有没有编译」，而在编译发生在什么时候、编译产物给谁看。

类是从一堆对象/实体中抽取公共部分形成的范式（属性 + 方法）；对象是实际的实体，拥有类的属性和方法，还可以自己升级改造（动态语言特色）。这条主线引出两个深入方向：可见性（封装的强度）和动态性（改造的自由度）。

1.2 可见性与名称改写：Python 没有"真的私有"

梳理里说"私有双下划线、保护单下划线"——但停在表面。背后还有一层：名称改写（name mangling）。

⚙️ 机制：__x 会被改名

__x 不是"真的私有"——解释器把它改名为 _ClassName__x，外面仍能 obj._Student__name 访问到。单下划线 _x 则连改名都没有，纯靠自觉。Python 没有真正的 private，这是 "consenting adults"（成年人的约定）哲学：约定优先于强制。

⛔ 面试反例：说"Python 私有属性外面访问不到"

错。双下划线触发的只是名称改写：外界用 obj._ClassName__attr 照样读写。它的设计目的更多是避免子类意外覆盖，而不是防外访问。说"Python 没有真私有，只有约定"才是加分答案。

1.3 动态属性与 __slots__

Python 是动态语言：运行时可以改变结构——新函数、新属性可以引进，已有的可以删除。落到对象上就是两件事：

class Student: pass

s = Student()
s.name = "trae"        # (a) 动态添加：实例化之后，"点属性=值"随时能加

class Strict:
    __slots__ = ("name", "score")   # (b) 限制动态添加：只允许这两个属性
    # __slots__ 让实例不再有 __dict__，属性存固定槽位
    # —— 顺带省掉"每个实例一个字典"的内存开销（大规模对象的常规优化）

t = Strict()
t.name = "ok"           # ✓ 在白名单里
t.age = 18              # ❌ AttributeError: 'Strict' object has no attribute 'age'

面试常把两者串着问：__slots__ 的一石二鸟——既限制动态添加（白名单），又省内存（没有 __dict__，存固定槽位）。

🎭 面试作答：Python 的"私有"和 __slots__

30 秒版：双下划线触发名称改写（__x → _ClassName__x），不是真私有——Python 的哲学是约定优先于强制（consenting adults）。__slots__ 做两件事：声明属性白名单禁止动态添加，同时去掉实例 __dict__ 换固定槽位省内存。

2 分钟版：展开三点：一，name mangling 的主要目的其实是防止子类无意覆盖父类内部属性，而不是访问控制；单下划线纯约定、连改名都没有；两种都拦不住真想访问的人。二，__slots__ 的机制：类定义它后实例没有 __dict__， setattr 走槽位描述符，白名单外直接 AttributeError；继承时注意——子类不定义 __slots__ 会重新长出 __dict__，限制失效。三，动态性本质：Python 实例属性默认存在实例的 __dict__ 里（第一册第 2 章的"口袋"），动态添加就是往口袋里塞新键，__slots__ 相当于把口袋换成固定格子。

第 2 章 · 三种方法与 propertyP0 高频考点

2.1 实例方法 / 静态方法 / 类方法

种类装饰器第一个参数典型用途
实例方法（无）self（实例）操作单个对象的状态
类方法@classmethodcls（类本身）工厂方法（以另一种方式构造实例）、操作类级状态

2.2 property 四件套：读、写、删，以及"增"不存在

🧑‍🎓 追问（原话）

「property 怎么判断调的是哪个？增删改查」「property 补充代码示例，什么是 setter，正确用法是什么？」

关键认知：property 的回调不看"你写了哪个方法名"，看"你对这个属性做了什么操作"——读、赋值、删除三种语法，分别触发 getter / setter / deleter：

class Temperature:
    def __init__(self, celsius=0):
        self._c = celsius              # 真实数据放私有字段，property 只是门面

    @property
    def celsius(self):                 # 查：t.celsius      → getter
        return self._c

    @celsius.setter                    # 改：t.celsius = 100 → setter（可做校验）
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("低于绝对零度")   # 赋值时校验——setter 的核心价值
        self._c = value

    @celsius.deleter                   # 删：del t.celsius   → deleter
    def celsius(self):
        self._c = 0

    @property
    def fahrenheit(self):               # 计算属性，只读（没写 setter）
        return self._c * 9 / 5 + 32

五条铁律：

  1. 真实数据存 _ 私有字段（_c），property 是它的门面；
  2. setter 的方法名必须和 property 同名（都叫 celsius），装饰器写 @celsius.setter，不是 @property.setter；
  3. 只读属性 = 只写 @property 不写 setter；再赋值会抛 AttributeError；
  4. 别在 getter 里干重活（每次 t.celsius 都跑一遍 getter，别塞 IO/DB 查询）；
  5. 判断"调的是哪个"就看你做了什么操作：读→getter、赋值→setter、del→deleter。
⛔ "增"对应不到任何回调

属性在 @property 被定义的那一刻就存在了，运行时无法"新增"一个已被 property 接管的属性——你以为是"增"的 t.celsius = 1，走的是 setter，不是新增。查改删三种操作三种回调，唯独没有"增"的钩子。

2.3 描述符：三种方法为什么"能那样用"的统一答案

实现 __get__/__set__ 的类叫描述符（descriptor）。property 本身就是一个数据描述符（同时实现 __get__ 和 __set__，所以能拦住读写删三种操作）；类方法、静态方法、super() 底层都靠它。这是"property/classmethod 为什么能那样用"的统一答案——也是第一册"魔术属性三线供应"的续篇：描述符只定义"怎么读写"，数据存在对象自己的 C 结构里。

🏠 比喻：门面与仓库

property 是门面，_c 才是仓库。客人在门面上读/写/删，门面把每种动作翻译成对应的回调（getter/seller/deleter），中间可以加校验、记日志、触发副作用——仓库里的真货从不直接露面。

🎭 面试作答：property 与三种方法

30 秒版：property 是数据描述符，把读写删三种语法翻译成 getter/setter/deleter 三个回调；setter 是赋值校验的正点（如温度不能低于绝对零度）；只写 @property 就是只读属性。staticmethod 不自动传参、classmethod 传 cls，后者的招牌用法是工厂方法。

2 分钟版：先答"怎么判断调哪个"：看操作不看名字——t.celsius 走 getter、赋值走 setter（可校验可转换）、del 走 deleter，且没有"增"的回调（property 定义的属性无法被运行时新增）。再给 Temperature 例子展示校验和计算属性（fahrenheit 只读派生）。最后上价值：property、classmethod、staticmethod、super 底层统一是描述符协议（__get__/__set__），这就是"三种方法为什么能那样用"的答案——能说出描述符这一层，就把 80% 的候选人甩在身后了。

3.2 扑克正解：一次串起四个缺口

🧑‍🎓 追问（原话·场景思维的自白）

「通过这个扑克游戏，我看出来自己的场景思维不是很强。我会去想卡片是什么样子，但我不会去想扑克。我更多的是去想它的继承关系，比如有个"牌"，然后有一堆东西去继承它。但实际上我想多了，应该想的是：在这个场景下，我们要使用到哪些对象。」

这段自白的病根：下意识给所有东西找继承关系。Pythonic 的正解是——Deck / Hand 各自持有 Card 列表（组合），再靠魔术方法让它们直接吃 Python 语法：len(deck)、deck[0]、for c in deck、sorted(hand) 全部"天然就成立"，根本不用写 deck.getCards() 这种 Java 味接口。

from dataclasses import dataclass
from enum import Enum

class Suit(Enum):                  # 枚举：花色比裸字符串安全（拼错立刻暴露）
    SPADE = "♠"; HEART = "♥"; CLUB = "♣"; DIAMOND = "♦"

@dataclass(order=True)             # 值对象：自动生成 __init__/__repr__/__eq__/__lt__
class Card:
    rank: int
    suit: Suit

class Deck:                         # 注意：没有继承 Card！Deck"有一堆"Card（组合 has-a）
    def __init__(self):
        self.cards = [Card(r, s) for r in range(1, 14) for s in Suit]
    def __len__(self): return len(self.cards)          # len(deck)     剩几张
    def __getitem__(self, i): return self.cards[i]     # deck[0]、切片、随机访问
    def __iter__(self): return iter(self.cards)        # for c in deck 发牌循环
    def __contains__(self, c): return c in self.cards  # c in deck      验牌

这段代码一次补齐四个缺口：Enum（类型安全的花色）、@dataclass（值对象样板代码全免）、容器协议（四种魔术方法接住四种原生语法）、组合——而继承一行都没用。注意 @dataclass(order=True) 自动生成 __lt__ 等比较方法，sorted(hand) 直接能用。

🎭 面试作答：怎么用魔术方法设计一个类

30 秒版：按协议背不按方法名背：表示、比较、容器、迭代、运算符、上下文、属性访问。设计类时先问"这个对象要吃哪些原生语法"——要 len 就 __len__、要下标就 __getitem__、要 for 就 __iter__、要排序就 __lt__。核心价值：让自定义对象长得像内置类型，调用方写原生语法而不是 getXxx()。

2 分钟版：拿扑克举例串一遍：Card 用 @dataclass(order=True) 白嫖 repr/eq/lt（值对象）；Suit 用 Enum 防拼写错误；Deck 用组合持有 Card 列表，实现 __len__/__getitem__/__iter__/__contains__ 四件套，于是 len(deck)、deck[0]、for c in deck、card in deck 全部天然成立。顺势点出设计观：能用组合就别继承（Deck has-a Card 而不是 is-a），魔术方法替代 Java 味的 getter 接口——这就是"Python 式地怎么用"。

第 4 章 · 继承进阶：MRO、super() 真义与 MixinP0 高频考点

4.1 菱形问题的答案：MRO + C3

梳理里自陈"多重继承有菱形问题，不太知道"——答案就是 MRO（方法解析顺序）+ C3 线性化：Python 3 用 C3 把继承图展平成一条确定、单调的线性顺序，ClassName.__mro__ 可查。菱形继承下不会重复调用顶层 object.__init__，靠的就是这条线性表（C3 三规则：子类在前、父类按声明顺序、去重——详见第一册第 1 章）。

⛔ "super().__init__ 调用父类"只对单继承成立

super() 的真正含义：不是"父类"，是"MRO 里位于当前类之后的下一个类"。多重继承中 super() 跳到的未必是直接父类——这正是菱形继承能协作的关键。面试时说"super 跳到父类"是扣分答案，说"跳到实例类 MRO 的下一位"是加分答案。

4.2 Mixin：多重继承的正当用法

🧑‍🎓 追问（原话）

「Mixin 啥意思？正确用法是啥？」「Mixin 是不是我自己也可以实现注入什么的？」

🏠 比喻：插件

Mixin 直译"混入"。它不是 is-a 意义上的父类，而是一小段可复用能力的插件，通过多重继承"混"进你的类。就像手机装 App：手机（你的类）不需要重新出厂（改基类），装上 App（混入 Mixin）就有新能力。

正确用法四条：

  1. 单一职责：一个 mixin 只加一种能力；
  2. 不单独实例化：它是配件不是成品；
  3. 避免 mixin 之间互相菱形继承；
  4. 命名用 XxxMixin 后缀。

关于"自己实现注入"：是的，Mixin 就是个普通类，你随便写。所谓"注入" = 把它放进目标类的基类列表，它定义的方法就进了目标类的 MRO，实例查找时能命中。不是运行时注入，是类定义时就定好的。

4.3 自写 Mixin：super 协作是灵魂

class ToDictMixin:                       # 你自己写的 mixin：序列化能力
    def to_dict(self):
        return {k: v for k, v in vars(self).items() if not k.startswith("_")}

class CacheMixin:                        # 再写一个：缓存能力
    def __init__(self, *a, **kw):
        super().__init__(*a, **kw)       # 灵魂：用 super 保证在继承链里协作
        self._cache = {}                 #   ——直接写 self._cache 会跳过其他基类的 __init__

    def cached_get(self, key, loader):
        if key not in self._cache:
            self._cache[key] = loader()  # 惰性加载：第一次才算，之后走缓存
        return self._cache[key]

class UserService(ToDictMixin, CacheMixin):   # 把两种能力混进来
    def __init__(self):
        super().__init__()
        self.name = "trae"

svc = UserService()
svc.to_dict()                            # {'name': 'trae'} —— 来自 ToDictMixin
svc.cached_get("u1", lambda: load_user("u1"))  # 来自 CacheMixin

要点：mixin 里用 super().__init__() 而不是直接覆盖，这样它在多重继承链里能和其他基类协作（协作式多继承）——这正是 4.1 里"super 跳到 MRO 下一位"的直接应用：CacheMixin 的 super() 跳到的是 UserService MRO 里的下一位，不是它的"父类"。

🎭 面试作答：Mixin 是什么、怎么用

30 秒版：Mixin 是通过多重继承混入的小能力插件，单一职责、不单独实例化、命名带 Mixin 后缀、互相不做菱形继承。它和 DI 的区别：mixin 在类定义期注入方法，DI 在运行时注入对象实例——后者能运行时换实现。

2 分钟版：先定义（能力插件，不是 is-a 父类），再给例子（ToDictMixin 给任何类加序列化、CacheMixin 加缓存），然后讲两个工程细节：一，mixin 的 __init__ 里必须 super().__init__(*a, **kw) 协作，因为 MRO 链上它后面还有别的基类，直接覆盖会断链；二，mixin 是类定义期的静态组合，FastAPI Depends / Spring 那种是运行时的实例注入，两回事但常被混问。收尾一句：Mixin 是多重继承在 Python 里的正当用法——C3 + super() 让"多能力组合"不翻车。

第 5 章 · 多态本质：鸭子类型P0 概念题

5.1 不查类型，查方法名

🧑‍🎓 追问（原话）

「多态本质和抽象与元没有太听懂」

梳理里用里氏替换原则讲多态（子类重写父类方法、调用相同方法出不同结果）——这是 Java 视角。Python 多态的真正引擎是鸭子类型，关键认知：

⚙️ 机制：Python 的多态不要求继承同一基类

Python 的多态不查"你是什么类型、是不是某基类的子类"，只查"你有没有这个方法名"。运行时按属性名查找（沿 type(x) 的 MRO），找到就调。所以 Dog 和 Robot 毫无继承关系，只要都有 speak()，就能被同一个函数统一处理。

def draw_all(things):       # 不关心 things 是不是某个基类的子类
    for t in things:
        t.draw()            # 有 .draw() 就行——这就是鸭子类型

# Dog 和 Robot 没有任何继承关系，照样都能进 draw_all
class Dog:   def draw(self): print("🐕 简笔画")
class Robot: def draw(self): print("🤖 矢量图")

draw_all([Dog(), Robot()])   # 都能画——只看"有没有 draw"，不看"是谁的子类"
🏠 比喻：类型关卡 vs 协议关卡

Java 的多态要过类型关卡：必须继承 Animal 才能放进 List<Animal>。Python 把这道关卡拆了，换成协议关卡：走起来像鸭子、叫起来像鸭子，那就当鸭子。协议（sequence、iterator、context manager……）就是鸭子类型的"官方认证"——实现约定的一组方法，就算这个协议的成员。

5.2 两个配套工具：total_ordering 与 __call__

🧑‍🎓 追问（原话）

「totalordering？call？」

# @functools.total_ordering —— 比较方法的"自动补全器"
# 只要定义 __eq__ + 一个比较方法（如 __lt__），它帮你推导出剩下的 __le__/__gt__/__ge__
from functools import total_ordering

@total_ordering
class Card:
    def __init__(self, rank): self.rank = rank
    def __eq__(self, o): return self.rank == o.rank
    def __lt__(self, o): return self.rank < o.rank
    # 自动获得 __le__ / __gt__ / __ge__（由 == 和 < 推导），省得手写六个

# __call__ —— 让实例像函数一样被调用；判断能不能调用用内置 callable(obj)
class Adder:
    def __init__(self, n): self.n = n
    def __call__(self, x): return x + self.n   # obj() 触发 __call__

add5 = Adder(5)
add5(10)        # 15 —— 实例当函数用
callable(add5)  # True

补一个延伸：@functools.singledispatch 是 Python 对"方法重载"的近似方案——按第一个参数的类型分派到不同实现（Python 没有真重载，靠它和默认参数补位）。

🎭 面试作答：Python 多态和 Java 多态的区别

30 秒版：Java 多态基于继承 + 里氏替换（过"类型关卡"）；Python 多态基于鸭子类型——运行时只查方法名不查继承关系（过"协议关卡"），有同名方法就能统一处理。协议是鸭子类型的官方认证。

2 分钟版：先讲机制差异：Java 在编译期绑定类型检查（List<Animal> 的关卡），Python 在运行期沿 MRO 按属性名查找，找到就调——所以 Dog 和 Robot 无继承也能多态。再讲这条设计的代价与补偿：代价是"拼错方法名"要到运行时才炸（AttributeError）；补偿一，ABC + @abstractmethod 把口头协议变成强制契约；补偿二，typing.Protocol（结构化子类型）给静态检查器看。最后可以带一句 total_ordering（比较协议的自动补全）和 singledispatch（按类型分派，Python 版"重载"）展示工具箱。

第 6 章 · 抽象与元类：ABC、type 与 metaclassP1 拉分题

6.1 ABC + @abstractmethod：把口头协议变成强制契约

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...        # 留空，强制子类实现

Shape()                        # ❌ TypeError: abstract method area 没实现，实例化被拦
class Circle(Shape):
    def area(self): return 3.14   # 实现了
Circle()                       # ✓ 可实例化

用法定位：ABC 用来声明接口/协议——"子类必须实现这些方法，没实现就别想被造出来"。日常 90% 的接口约束场景，ABC 就够了。补充两件配套工具：collections.abc 里的 Sequence/Iterable/Container 是现成协议基类；ABC.register(X) 能把非继承类"注册"成虚拟子类（isinstance 成立），给鸭子类型盖个章。

6.2 元类里到底有什么：一个必须修正的直觉

🧑‍🎓 追问（原话）

「我有点懂这个元类了，但是我想知道这个里面有什么。它肯定会去放一些公共的内容，对吧？比如说放一些基础的魔术方法？type 是默认有的对吧，如果没有 abc」

⛔ 关键混淆：基础魔术方法来自 object，不来自元类

"元类放一些公共内容/基础魔术方法"——方向对了一半。默认的基础魔术方法（__repr__、__eq__、__hash__、__init__、__getattribute__……）不是元类放的，是 object 放的：每个类都隐式继承 object，所以实例都有这些（第一册第 3 章讲过：object 也只提供这一小撮默认，__iter__/__len__ 没有默认）。元类干的是另一件事：控制"类怎么被造出来"——type 提供的是"造类机器"：__new__（建出类对象）、__init__（初始化类）、__call__（实例化时触发）。

展开：同一个 Card 类的两个身份（两层链路图）
type 三层链：类自己也是对象
实例 ← 类造出来；类 ← 元类（type / ABCMeta）造出来；"一切皆对象"不虚——连类都是 type 的实例

对照读法：默认魔术方法沿「object → 类 → 实例」的继承链给到实例；元类沿「type/ABCMeta → 类」的制造链控制类本身。两条链别混。

回答原话里的三个小问：

  • "type 是默认有的对吧"——对。不写 metaclass= 时，所有类都用 type 当元类；
  • "如果没有 abc"——没有自定义元类时退回默认 type，类照常造，没有任何强制校验。ABC 只是把 type 换成 ABCMeta，多加了"实例化前查 @abstractmethod"这一道检查——而这一道就在元类的 __call__ 里；
  • "元类放公共内容"——修正：那是 object 的事。元类也能往类里"塞东西"，但那是你在 __new__ 里手动加的，跟"默认魔术方法来自 object"是两码事。

6.3 元类实战：LoggedMeta 与轻量替代

class LoggedMeta(type):                 # 继承 type，自己写元类
    def __new__(mcs, name, bases, ns):  # 造类时触发（import 时就跑一次）
        cls = super().__new__(mcs, name, bases, ns)
        print(f"[元类 __new__] 造出了类 {name}")
        return cls

    def __call__(cls, *a, **kw):         # ClassName() 实例化时触发（每次）
        print(f"[元类 __call__] 要实例化 {cls.__name__}")
        return super().__call__(*a, **kw)

class Foo(metaclass=LoggedMeta):        # 用你的元类造这个类
    pass
# 造类时打印：[元类 __new__] 造出了类 Foo
f = Foo()
# 实例化时打印：[元类 __call__] 要实例化 Foo

对照记忆：__new__ 在"造类"那一刻跑一次（类定义时），__call__ 在每次 Foo() 时跑。ABCMeta 重写的就是 __call__——在 super().__call__ 之前先扫 @abstractmethod，没全实现就 TypeError。这解释了一个高频追问：为什么 ABC 的强制力只在"实例化"时生效，而"定义子类"时不报错？因为检查写在 __call__ 里，定义子类只是造类（走 __new__），不触发 __call__。

工程提醒：元类不一定要天天写——现代更轻量的替代是 __init_subclass__（子类被定义时触发，能做注册/校验）和 __class_getitem__（让 Foo[int] 可下标）。元类常见于框架：ORM、Django Model、ABCMeta、enum.EnumMeta。而 type 的"既是查询函数（type(obj)）又是造类的元类（X = type('X', (), {})）"这一双重身份，是理解"一切皆对象"的钥匙。

🎭 面试作答：ABC 与元类

30 秒版：ABC = 接口契约：@abstractmethod 标记必须实现的方法，没实现就实例化不了。它的强制力在 ABCMeta（元类）的 __call__ 里——实例化前扫一遍抽象方法。type 是默认元类（造普通类），ABCMeta 是 ABC 用的元类（造抽象类 + 强制检查）。

2 分钟版：先答 ABC 用法（Shape 例子：Shape() 报 TypeError，实现 area 的 Circle 通过；ABC.register 给鸭子类型盖章），再上元类层：class X: 等价 X = type('X', (), {})——type 既是 type(obj) 查询函数又是造类的元类，类自己也是对象。然后主动澄清易混点：默认基础魔术方法来自 object 的继承链，不是元类放的；元类提供造类机器（__new__ 造类/__call__ 实例化拦截），ABCMeta 正是重写 __call__ 加了抽象方法检查——所以定义子类不报错、实例化才报。收尾：日常用 ABC + __init_subclass__ 就够，元类留给框架（ORM/Enum）。

第 7 章 · 组合优于继承与依赖注入P1 设计题

7.1 has-a vs is-a：场景思维的第一性原理

🏠 比喻：是"是一辆"还是"有一辆"

继承表达 is-a（是一辆）：电动汽车 is-a 汽车。组合表达 has-a（有一辆）：车库 has-a 一堆车。扑克场景里，Deck "有一堆" Card（has-a），而不是"是一张" Card（is-a）——想把一切塞进继承树，就是把车库硬说成一种汽车。能用组合就别用继承。

落到场景建模的方法论：名词 → 类、动词 → 方法、关系 → 组合/继承。每次想画继承树前，先问"谁拥有谁（has-a）"——这一问，就是当时"扑克那关想多了"的解药。

7.2 Mixin vs 框架级依赖注入：FastAPI 的 Depends

🧑‍🎓 追问（原话）

「框架级的依赖注入，就相当于是 Spring Boot 那种运行时会有依赖注入，是吧？」

对，基本就是。框架级 DI 有个容器（IoC 容器），在启动/运行时按你声明的依赖关系，构造对象图并把实例塞进需要它的地方——Spring Boot 是最典型的实现。和 mixin 的关键区别不在"有没有注入"，而在"注入的是方法还是对象实例""是类定义期定死还是运行时可换"：

维度Mixin框架级依赖注入（Spring Boot 式）
注入时机类定义时（静态）容器启动/运行时（动态）
注入对象方法/能力（行为混进类）对象实例（依赖塞进对象）
关系本质is-a 行为组合has-a 依赖由外部提供
运行时换实现不能，写死在继承链能，改绑定即可（DI 的核心价值）
声明方式放进基类列表注解/类型注解 + 容器配置

Python 里最贴近、最好背的例子是 FastAPI 的 Depends：

from fastapi import Depends, FastAPI

class UserService:
    def get(self, uid): return {"id": uid}

def get_user_service():        # provider：告诉容器"怎么造"
    return UserService()

app = FastAPI()

@app.get("/users/{uid}")
def read_user(uid, svc: UserService = Depends(get_user_service)):
    #                        ^^^^^^^ 运行时被注入，函数里从没自己 new
    return svc.get(uid)

Depends(get_user_service) 声明"我依赖一个 UserService，运行时由框架塞进来"——函数体里从没出现 UserService()，和 Spring 的 @Autowired 本质一模一样。FastAPI 的 Depends 是 Python 里最轻量的 DI；要完整的 IoC 容器（配置、生命周期、作用域）就用 dependency-injector 这类库。一句话收尾：mixin 注入方法，DI 注入对象实例——后者能在运行时替换实现，这正是它存在的意义。

🎭 面试作答：组合、继承与 DI 怎么选

30 秒版：继承表达 is-a，组合表达 has-a，能用组合就别继承（Deck has-a Card，不是 is-a）。需要给一批类加可复用能力用 Mixin（类定义期、注入方法）；需要运行时可替换的依赖用 DI（注入对象实例，FastAPI Depends / Spring @Autowired）。

2 分钟版：按场景选：真子类型关系（Circle is-a Shape）→ 继承 + ABC 契约；能力拼装（序列化/缓存）→ Mixin 多重继承 + super 协作；跨层依赖（Service 注入 Router）→ DI 容器。展开 DI：IoC 容器负责"谁依赖谁"的装配，你只声明（Depends/@Autowired），好处是解耦 + 可测试（单测时换个 provider 就能 mock）+ 运行时可换实现。再对比 mixin：mixin 是静态的类定义期组合，编译后能力写死在 MRO 里，不能运行时替换——所以它适合"能力"，DI 适合"依赖"。这是把 OOP 设计题答出层次感的三段式。

1.1 IO 事件源机器：三级台阶

开头这一问的结论：loop、future、task、回调、取消这"五件套"是调度核，但骨架还剩最后一面承重墙没拆——IO 事件源机器（add_reader / Transport / Protocol）。除此之外，asyncio 里所有大名鼎鼎的东西没有一件是骨架，全是骨架零件的排列组合。

这面墙从下往上分三级台阶（同一条链路的三个层级）：

① IO 侧最底层一级:
  ① add_reader: 回调拿到 b'hello-raw' → set_result → await 醒来

②③ 中间层与顶层同台 (echo 服务器):
  ③ 客户端: await reader.read() ← 内部 create_future, 睡在 data_received 上
  ② Protocol.data_received: 回调拿到 b'hello-stream' → 原路写回
  ③ read() 醒来: b'hello-stream'

一条链: epoll事件 → 回调(字节) → 缓冲 → Future兑现 → await醒来

三级台阶的对应关系：台阶①是手写迷你循环里那一级——selector 事件进来，回调去读字节；台阶②的 Protocol 只是一份事件回调清单（connection_made / data_received / connection_lost），data_received 和①里的 on_readable 是同一物种；台阶③的 StreamReader.read() 内部就是 create_future + 睡在回调上。

⚙️ 机制：StreamReader 也是 Future 机器（源码铁证）

标准库 streams.py 的 _wakeup_waiter 亲手供认——read() 就是你手写过的 wait 的官方版：

def _wakeup_waiter(self):
    """Wakeup read*() functions waiting for data or EOF."""
    waiter = self._waiter
    if waiter is not None:
        self._waiter = None
        if not waiter.cancelled():
            waiter.set_result(None)   # ← 和 Lock.release 兑现等待者是同一个动作

_wait_for_data 的文档字符串更是自供状："StreamReader uses a future to link the protocol feed_data() method"。

💡 比喻：骨架永远是薄的那层

看代码量的分布：整个 asyncio 包 13129 行，其中"合同"futures.py 只有 426 行，比"积木"streams.py（726 行）、locks.py（438 行）都薄——骨架永远是薄的那层，厚的全是搭在骨架上的建筑。就像一栋楼：承重墙就几面，房间里的大部分面积是后续装修出来的。

1.3 uvloop：冻结的中间层的终极回报

💡 比喻：中间冻结，两端随便换

uvloop 能把整个 asyncio 提速数倍，靠的只是换掉"Loop + IO 墙"的实现——Future、Task、回调、取消、所有积木一行不动。这就是"冻结的中间层"的终极回报：中间的合同（Future 机器）冻结不动，两端（上层的积木 API、下层的事件源实现）才能随便替换。类比后端熟悉的模式：中间件协议不变，上游业务和下游存储随便换。

🎭 面试作答：asyncio 的骨架是什么？

30 秒版：Loop、Future、Task、回调、取消是调度核；再加一面 IO 事件源机器（add_reader / Transport / Protocol）才凑齐承重墙。其余知名 API——sleep、gather、Lock、Queue、TaskGroup——全是这些骨架零件的排列组合，零新机制。uvloop 提速数倍只换 Loop 和 IO 实现、Future/Task 一行不动，就是这句话的实证。

2.1 "解耦"是催问券

⛔ 反例："大概知道是解耦"恰恰是最容易被戳穿的答案

"解耦"是人人都会说的词，它是一张催问券：面试官听到这个词，下一句必然是"解耦了什么？怎么解耦的？"——答不上来，才是真正的露馅时刻。用关键词冒充答案，是面试最大的坑。

完整答案其实只有一句话，而离说出它只差把已经会的东西串起来：

一句话主线（背这个）：协程 await 一个 Future 就挂起；任何事件源（定时器、IO、线程）完成后 set_result 兑现它；Future 把任务排回就绪队列；循环从头到尾只认回调队列。所以"等什么"和"怎么醒"被分开了——加一种新的等待方式，循环一行不用改。Task 就是"会驱动协程的 Future"，协程的 return 被填进它自己。

第 3 章 · 四个动词：生成器地基P0 精华

🧑‍🎓 追问原话

（贴了别的 AI 给的 6 步流程后）"概念不理解：搞不懂 await 和 wakeup 是什么，对 yield 和 yield from 也还不太懂。调用流程不清晰：看不懂每一步是什么、在什么情况下进入下一步。运行机制不明确：我知道 send 是启动，其他的我就不知道了。"

三个"不懂"其实是同一个洞：asyncio 的一切都站在生成器机制上。这轮零 asyncio 概念，只讲 4 个动词。

3.1 动词翻译表 + 三个触发器

动词一句话备注
yield暂停。右边的东西交出去给驱动者；恢复时，send 塞进来的东西落在它身上全场唯一的暂停点在 Future.__await__ 里的 yield self
send(x)"继续跑"，顺便把 x 送入。第一次 send 叫"启动"，之后每次都叫"恢复"——所以它不只是启动asyncio 里 send 的永远是 None，只是"继续跑"的信号
yield from / await隧道。把自己的暂停权借给里层，里层的暂停不经过我的代码直接弹到最外层驱动者手里字节码层两者编译出同一条 YIELD_FROM
__wakeup一个普通回调函数，Task 预先挂在 Future 上的，名字就叫"该醒了"。工作只有一件：再 send 一次不是关键字，是方法名

"什么时候进入下一步"的答案——归根结底只有 3 个触发器，没有第四种：

  1. 函数自己跑到 yield → 暂停，交出东西（整台 asyncio 里这一幕只发生在一个地方：Future.__await__ 里的 yield self）
  2. 驱动者调 send → 恢复，从上次暂停的那一行继续
  3. 函数跑完 → 抛 StopIteration，return 值藏在异常里被驱动者取出
⚙️ 机制：字节码铁证——await 就是换了名字的 yield from

实测对照（Python 3.10）：yield from inner() 和 await inner() 编译出的核心指令是同一条 YIELD_FROM，唯一差别是前置安检门——GET_YIELD_FROM_ITER（是迭代器就行）vs GET_AWAITABLE（只放行 awaitable）。这是字面意义上的"换名字"。

3.2 三条通道各司其职

几乎所有人卡住的地方：结果不走 yield 这条路。三条通道从不混用：

通道负责什么不负责什么
yield self（第 7 步）只负责交出 Future——"请在完成时叫醒我"这个信号不传结果
send(None)（第 15 步）只负责说"继续跑"送来的是 None，不是结果！
return 通道（第 16 步）__await__ 被唤醒后执行 return self._result，return 值穿过隧道变成 await 表达式的值——
# 运行实测输出，注意第 2 行的括号
[Fut]       __await__: yield self     ← 全系统唯一的暂停点
[Fut]       被 send(None) 叫醒(注意: 送来的是 None 不是结果!)
[download] ③ 醒来, await 表达式的值 = '0.2秒后的世界'   ← 结果走 return 通道

这就是为什么别的 AI 给的 6 步流程第⑥步说"send(None)"却拿到了结果——送进来的是 None，结果是协程自己从 Future 里取出来 return 的。

3.3 12 行驱动者 = Task 的全部秘密

没有 Task 类、没有 Loop 类——赤手空拳当驱动者，12 行就能跑完一个协程的一生：

def driver(coro):
    """赤手空拳当驱动者：Task.__step 做的事和这里一模一样，
    只是多包了一层'收到 Future 后挂号'的壳。"""
    try:
        # 第一次 send(None) = 启动：协程第一次真正跑起来
        yielded = coro.send(None)
        # send 的返回值 = 协程在 yield 处交出的东西（这里是 Future）
        print(f"收到请求: 我在等一个 {yielded} 秒的定时器")
        import time; time.sleep(0.2)      # 驱动者闲下来去等（真循环里 = epoll/定时器堆）
        coro.send(None)                   # 第二次 send = 恢复：把协程从冻结点叫醒
    except StopIteration as e:
        # 协程跑完抛 StopIteration，return 值藏在 e.value 里
        print(f"函数死了, return 值从异常里取出: {e.value}")

driver(download())
# 实测输出：这段输出就是 Task 的全部秘密
[download] ① 出发
[驱动者]   ② 收到请求 '我在等一个 0.2 秒的定时器' → 去睡 0.2 秒
[download] ③ 被叫醒, 驱动者塞进来的东西是 None
[驱动者]   ④ 函数死了, return 值从异常里取出: '下载完成'
💡 比喻：yield 是双向窗口

普通函数是单程票：进去、干完、出来，一次性。生成器/协程是服务窗口：可以暂停（yield = "下一位，先等我叫你"）、可以恢复（send = "到你 了，继续"）。yield 既是出口（把值递出去）也是入口（把 send 的值接进来）。

4.1 三件套方法归位 + 六阶段

先把三件套的全部方法归位，每个方法一句话职责：

类方法一句话职责

一个协程任务的一生：19 步六阶段全景

逐阶段讲解：

  • 阶段 A（1-2）装弹：create_task(download(loop)) 造出 Task，Task 干的第一件事就是把自己推进就绪队列——出生即排队。
  • 阶段 B（3-8）协程开跑：第 3 步循环弹出 __step 执行；第 4 步 __step 调 coro.send(None)，协程这才第一次跑起来。最反直觉的一点：第 5、6、7 步全部发生在第 4 步那个 send() 的内部——download 跑到 await sleep，sleep 创建 Future、挂定时器（第 6 步），然后 await fut 走进 Future.__await__，执行 yield self（第 7 步，全场唯一的暂停点），函数在这里冻结，send() 这才返回，把冻住的 Future 交回 __step——于是第 8 步挂号：fut.add_done_callback(__wakeup)，"你完成时叫我"。第 4 步和第 8 步是同一次 __step 调用，中间夹着协程跑了半程。
  • 阶段 C（9）睡觉：就绪队列空了，循环睡在定时器上。单线程并发里"别的任务趁机跑"就发生在这——本演示只有一个任务，所以是真睡。
  • 阶段 D（10-12）兑现：0.05 秒到点，定时器回调被搬进队列（10），循环执行 fut.set_result(None)（11-12）。注意第 12 步：存结果，然后 call_soon(__wakeup) 排队——不直接叫醒。为什么不直接调？直接调就会在 set_result 里嵌套执行协程，队列的顺序保证就没了。
  • 阶段 E（13-18）复活到死亡：下一圈循环执行排队的 __wakeup（13-14），它只干一件事：再 __step 一次（15），send(None) 把协程从第 7 步冻住的那行解冻。第 16 步是关键：醒来后 __await__ 执行 return self._result——结果不是 send 送进来的（送的是 None），是协程自己从 Future 里取出来 return 的。download 拿到值继续跑完（17），函数结束抛 StopIteration，__step 捕获它，把 return 值填进 Task 自己（18）——协程死亡 = Task 这个 Future 被兑现。
  • 阶段 F（19）收官：while 发现 task.done() 为真，退出循环，return task.result()——就是第 18 步存进去的那个值。

4.2 三个数字 + 毕业作业

数字含义为什么
4 个编号，2 次调用__step 在 19 步里出现 4 个编号，但只被调用 2 次4/8 是一次（开头那半程），15/18 是一次（结尾那半程）

⚙️ 机制：__step 执行次数公式

__step 执行次数 = 1 + await 次数（第一次是出生排队被循环执行，之后每次 await 被唤醒都由 __wakeup 叫它）。19 步流程里 download 只有一次 await，所以 __step 恰好 2 次。

给 19 步流程里的 download 加第二个 await，先在纸上预测两个数——__step 会执行几次（按公式算）、编号会涨到第几步——再实际运行对答案。预测全对的那天，这台机器就是你亲手拆装过的了。

5.1 先订闹钟，再睡觉

sleep 里三行的顺序是铁律：create_future → call_later → await fut。为什么不能反过来？因为 await 一执行人就冻住了——冻住之后排在后面的代码一句都不会跑，闹钟永远订不上，这个任务就死锁在暂停里。所以必须先安排好"谁来兑现我"（定时器回调就是未来的 set_result），再躺下。

⚙️ 机制："yield self 相当于返回那个 future"——精确，但返回给谁？

它返回给的不是 sleep 的调用者，是驱动者：yield self 的效果 = send() 的返回值变成这个 Future。普通 return 只能给调用者，yield 的值是递到驱动者手上的——这就是为什么 __step 能拿到它。

5.2 关键修正：__step 没有在循环

"它暂停了就不跑了，然后就到了 task_step"——这半句完全正确。"因为 step 一直在循环"——这半句错了，__step 里没有任何循环。真相更简单也更漂亮：

coro.send(None) 是一个普通函数调用，而 yield 那一行就是它的返回点。暂停和返回是同一瞬间的两个视角——协程看是"冻结"，__step 看是"send 调用返回了"。

看第 7 步冻结瞬间的真实调用栈：

run_until_complete          ← 唯一的循环在这里(第2步的 while)
 └─ _run_once #1                    (第3步)
     └─ Task.__step                 (第4步)
         └─ coro.send(None)   ┐
             └─ download      │ 第5步
                 └─ sleep     │ 第6步   这些帧此刻
                     └─ __await__ │ 第7步   全在栈上
                        └─ yield self ┘ ← 冻结点 = send 的返回点
         ←─ send 在这行返回，返回值 = 那个 Future
     ←─ __step 接着跑第8步(挂号)，然后自己 return
 ←─ _run_once return，while 转下一圈 → 第9步

栈像普通函数返回一样逐层自然退回，没有任何人在"等它让出"。实测铁证（用 traceback 打印）：冻结瞬间栈是 step → download → __await__（协程的帧全在栈上）；send 返回后栈只剩 step——协程的帧被收进协程对象里随身保存，醒来再放回来。

⛔ 纠错：__step 是"被反复叫"，不是"自己在转"

__step 确实被调用了两次——但第一次是出生时排队被循环执行，第二次是 __wakeup 叫它。公式：__step 执行次数 = 1 + await 次数。唯一的循环在 run_until_complete 的 while 里。

__wakeup 的三个家：从登记簿到调度队列到栈上

第 12 步被兑现的是 future 本身（合同完成，_done=True）；被排队叫醒的是 Task（通过挂号在 future 上的 __wakeup）。set_result 遍历登记簿，把 __wakeup 从 Future 的登记簿搬进 Loop 的就绪队列——不经过这一步，第 13 步的队列里根本没有东西可弹。

6.1 set_result 被当作"值"卖掉了

推理链完全正确——是 sleep 造的那个 Future 被定时器兑现了。但"为什么在代码里找不到这次调用"这个困惑值得钉死，因为答案藏着一个机制：预售。回看 sleep 的第 6 步：

# ↑ 注意：这一行里 set_result 没有被调用（没有括号执行）！
# 它是被当作一个"值"（函数引用），连同参数 (None,) 一起塞进了定时器堆。
# 0.05 秒后到点，_run_once 执行 cb(*args) —— 那才是调用，
# 调用者是循环，不是任何协程代码。
# 实验第一幕：把定时器堆掏出来看
cb   = <bound method Future.set_result of <__main__.Future object at 0x...>>
args = (None,)
# 定时器堆里躺着的就是 set_result 本身——预售的订单

所以 grep 源码里的 set_result( 只能找到 StopIteration 那一处：这次调用在代码里长得像"传值"，不像"调用"。

💡 比喻：预售

就像预售的演唱会门票：钱现在不结，票提前订好，到点自动核销。set_result 提前 0.05 秒被"卖"进定时器堆，到点由循环执行。这也解释了 5.1 的"先订闹钟再睡觉"——冻结的协程什么都干不了，"醒来后谁来兑现我"必须在躺下之前就安排好。

两次 set_result 的完整对照（实验第二幕实测）：

第 11 步第 18 步
被兑现的对象睡眠 Future（sleep 内部造的）Task 自己（Task 也是 Future）
谁调的 set_result_run_once（执行定时器回调）Task.__step（except StopIteration 里）
语义事件源兑现合同 → 唤醒等待者协程死亡 → Task 兑现自己
在源码里的样子看不见——第 6 步以函数引用形式预售你 grep 到的那处（显式写在代码里）
⚙️ 机制：为什么死亡通道能显式写，唤醒只能预售

死亡通道的 return 值就攥在 __step 手里——同步的可以直接写；唤醒必须等未来某个事件，异步的只能预售。你 grep 到的那处其实是特殊情况，普遍情况（事件源兑现 Future）都以预售形式存在。

6.2 措辞精修三处 + 46 处

推理对了，但三处措辞拧一下会更准：

  1. "sleep 它也是一个 future" → sleep 是协程，是"造 Future 的人"。被兑现的是它内部 create_future() 造出来的那个对象，sleep 自己从头到尾没当过 Future。
  2. 时序反了 → 不是"sleep 结束了之后它去调 set_result"。set_result 发生时（第 11 步）sleep 协程从第 7 步起就冻结着，冻结的协程干不了任何事。正确因果链：定时器到点 → 循环执行预订的 set_result → 这才导致 sleep 能醒来。set_result 是因，醒来是果。
  3. "download 挂的 wakeup" → 挂号的人是 Task.__step（第 8 步，在 download 冻住之后由驱动器收尾时挂的），挂在睡眠 Future 身上。download 自己什么都没挂——它冻结时连代码都没在跑。
⚙️ 机制：真 asyncio 是同款套路（标准库源码）

asyncio.sleep 内部就是三步——和手写版一字不差的预售：

# asyncio 标准库 sleep 的骨架（简化）
future = loop.create_future()
loop.call_later(delay, futures._set_result_unless_cancelled, future, result)
#          ↑ 预售：set_result 系函数作为"值"提前卖进定时器堆
return await future
# 死亡通道在 tasks.py:241: super().set_result(exc.value)——就是你 grep 到的那处

整个 asyncio 包里 set_result( 出现 46 处，几乎全是各种事件源（socket、线程池、子进程、定时器）在兑现各自的 Future——"冻结的中间 + 开放的两端"，这 46 处就是"开放的两端"的实体。

7.1 协程到底用没用 yield：取决于你在哪一层看

一句话总答案：源码层没用（你一个都没写），字节码层全是（await 编译出来就是 yield），运行层只有一个真正执行（Future.__await__ 里那条）。

层答案实测证据（全部来自本机 3.10）
源码层没用download 里 grep yield：× 0；你写的每个关键字都是 await
字节码层全是await coro() 和 yield from coro() 编译出的核心指令是同一条 YIELD_FROM，唯一差别是前置安检门（GET_AWAITABLE vs GET_YIELD_FROM_ITER）
运行层只有一个标准 futures.py 原文：def __await__(self): yield self——你代码里每一个 await 沿隧道下钻的终点站都是它

三层串成一根线：yield self 交出去的是 Future → Task.__step 的 send() 返回值正是它（第 7 步）→ 交出后挂号 __wakeup（第 8 步）→ 定时器兑现后叫醒（第 11-13 步）。全系统唯一的真·yield 执行点，就是 19 步流程图上的第 7 步。

# 标准 futures.py 的原文（运行层唯一的 yield）
class Future:
    def __await__(self):
        if not self.done():
            yield self          # ← 全系统唯一的暂停点：把 Future 交给驱动者
        return self.result()   # ← 结果走 return 通道（第 3.2 节的三通道之一）

8.2 帧的照片模型：等待和运行怎么处理

💡 比喻：协程不是在"等待"，它是被停成了一张照片

实验实测：挂起中的协程，cr_frame.f_lasti = 10（指令指针冻结在 YIELD_FROM 那条指令上）、f_back = None（不在任何调用栈上）。合起来一句话：帧从 C 调用栈上被摘下来，折进协程对象里随身携带，指令指针写在背面，局部变量原样活着，整个对象几百字节，想挂多久挂多久。唤醒 = send 把照片压回栈、跳到 f_lasti 继续。
